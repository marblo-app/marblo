## 2. 유저 시나리오별 월 예상 비용 (개산 · 가정 명시)

> ⚠️ **개략 추정치.** 실제 요금은 Cloud Billing 콘솔이 정답. 아래는 "폭주 없이
> 정상 사용" 가정의 상한선 감각용이다. LLM 추론 비용은 BYO라 **전부 제외**.

### 공통 가정

- 유저당 월 활성 세션 ~20회, 세션당 에이전트 ~3개, 세션 길이 ~30분.
- heartbeat 30초 배치(큐 10) → 세션당 하트비트 insert 수십 건, 배치라 Functions 호출은 그보다 훨씬 적음.
- 텔레메트리 이벤트 10초 배치(큐 50). **단, 1st-party 텔레메트리 기본 OFF** → opt-in 유저만 BQ 적재. 아래는 "전원 opt-in"의 보수적 상한.
- Firestore: 유저당 활성 문서 ~10개, 월 읽기 수백~수천 건.
- BigQuery 저장: 행당 ~0.5KB, 스트리밍 insert $0.05/GB, 저장 $0.02/GB/월.

### 개산 결과

| 유저     | Functions 호출/월            | Firestore 읽기·쓰기 | BQ insert+저장 | BQ 쿼리(대시보드) | **월 합계(대략)**        |
| -------- | ---------------------------- | ------------------- | -------------- | ----------------- | ------------------------ |
| **100**  | ~수십만 (무료 200만 이내)    | 무료 티어 이내      | < $1           | < $1 (정상 사용)  | **~$0 (거의 무료 티어)** |
| **500**  | ~100만+ (무료 이내~경계)     | 무료 티어 근접      | ~$1–3          | ~$1–5             | **~$5–10**               |
| **1000** | ~200만 근접 (일부 초과 가능) | 소폭 초과 가능      | ~$3–8          | ~$5–20            | **~$15–40**              |

> 즉 **정상 사용 기준 1000 유저에서도 월 수십 달러 수준**. 유저 수만으로는 "요금
> 폭탄"이 나지 않는다. 위 표에서 변동폭이 가장 큰 칸은 **BQ 쿼리**이며, 그 이유는 §4.

### 가정이 깨지는 경우 (= 진짜 위험)

- 클라이언트가 배치를 무시하고 이벤트를 초당 수십 건 쏘는 **폭주 루프** → Functions 호출·BQ insert 급증. (→ §3에서 방어 확인)
- 대시보드가 **캡 없는 거대 쿼리**(days=∞, limit=∞)를 반복 → BQ 스캔 바이트 급증. (→ §4)
- BQ 테이블 **미파티션** → 대시보드 쿼리 1회가 전체 테이블을 스캔 → 데이터 총량에 비례해 요금이 선형 증가. (→ §4)

## 3. 클라이언트 폭주 방어 현황 (재확인 — 양호)

| 방어 지점              | 코드                                                        | 현황                                                         | 판정             |
| ---------------------- | ----------------------------------------------------------- | ------------------------------------------------------------ | ---------------- |
| 텔레메트리 이벤트 배치 | `telemetryService.ts` FLUSH_INTERVAL=10s, MAX_QUEUE_SIZE=50 | 10초 or 큐 50개마다 1회 전송                                 | ✅               |
| heartbeat 배치         | `telemetryService.ts` 30s / 큐 10                           | 별도 큐, 30초 or 10개마다 전송                               | ✅               |
| 1st-party 기본 OFF     | `lib/telemetry/firstPartyGate.ts`                           | 기본 비활성, opt-in 시에만 BQ 전송                           | ✅ 강력          |
| flush 실패 재큐잉 상한 | `flushTelemetry()`                                          | 실패 배치 재삽입은 `MAX_QUEUE_SIZE*2`(=100)까지, 초과분 drop | ✅ 무한증식 없음 |
| 서버 배치 크기 캡      | `logTelemetryBatch` ≤100/batch, `logHeartbeat` ≤50/batch    | auth 필수 + 초과 시 `invalid-argument`                       | ✅               |
| 버그 신고 스로틀       | `submitBugReport` (`bugReportThrottle` 트랜잭션)            | 유저당 최소 5초 간격 + **하루 30건 상한**                    | ✅               |
| 쿠폰 브루트포스        | `rateLimit.ts` `enforce()` + `COUPON_RULES_*`               | uid 5/분·30/5분, ip 20/분·100/10분                           | ✅               |

**결론:** 클라이언트 → 서버 방향의 폭주는 배치 + 큐 상한 + 서버 배치캡 + 스로틀로
다층 방어돼 있다. 별도 코드 수정 불필요.

> 참고: `rateLimit.ts`의 범용 `enforce()`는 현재 쿠폰 엔드포인트에만 연결돼 있다.
> 텔레메트리/버그신고는 각자 자체 방어(배치·전용 throttle)를 쓴다. 필요 시 신규
> 엔드포인트를 `enforce()`에 태우면 재사용 가능.

## 4. 어드민/목록 쿼리 & BigQuery 스캔 감사

### 4.1 Firestore 목록 쿼리 (요금 관점 — 양호)

| 함수                        | 바운드                                 | 인증           | 판정                                       |
| --------------------------- | -------------------------------------- | -------------- | ------------------------------------------ |
| `getFounderWaitlist`        | `.limit(1000)`                         | `requireAdmin` | ✅ 캡 있음                                 |
| `listFounders`              | `.limit(1000)`                         | `requireAdmin` | ✅ 캡 있음                                 |
| `listBugReports`            | `.limit(200)`                          | `requireAdmin` | ✅ 캡 있음                                 |
| `getWaitlistCount`          | `.count()` (aggregate)                 | 공개           | ✅ 문서 미인출                             |
| `getFounderFeedbackByEmail` | `.where(email).get()` — **limit 없음** | `requireAdmin` | ⚠️ minor (통상 email당 1건, 이론상 무제한) |

- 목록 함수 3종 모두 **어드민 전용 + 하드 리밋** → 유저가 대량으로 유발할 수 없고 읽기 비용도 상한이 있다.
- ⚠️ 정합성(비용 아님) 메모: `limit(1000)` 컬렉션이 1000건을 넘으면 조용히 절단된다. 데이터가 커지면 페이지네이션 필요 — 후속 과제.

### 4.2 BigQuery 쿼리 — **진짜 비용 레버 (후속 티켓 권장)**

> 티켓 규칙에 따라 **여기서는 코드 수정하지 않고 기록만 한다.** 아래는 후속 수정 티켓 대상.

| 함수                    | 기간/한도 필터                                                                                      | 문제                                                                                                                                                                             |
| ----------------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `getCostLogs`           | `WHERE userId=@userId AND projectId=@projectId`, `LIMIT @limit` where `limit = data.limit \|\| 200` | ⚠️ **limit 상한 캡 없음.** 클라가 거대 LIMIT 요청 가능. userId+projectId로 유저 자기 데이터에 한정되긴 함                                                                        |
| `getCostSummary`        | `WHERE userId AND projectId AND timestamp >= NOW - @days DAY` (`days` 양의 정수)                    | ⚠️ **days 상한 없음.** `days: 100000` 요청 시 전 기간 스캔. 대시보드 로드마다 집계 쿼리 **2건** 실행                                                                             |
| (공통) BQ 테이블 파티션 | 코드에서 확인 불가                                                                                  | ⚠️ `timestamp` WHERE 필터는 테이블이 **DAY 파티션일 때만** 스캔 바이트를 줄인다. 미파티션이면 필터가 있어도 **매 쿼리가 전체 테이블 스캔** → 데이터 총량에 비례해 요금 선형 증가 |

**후속 티켓 권장 조치 (이 PR 범위 아님):**

1. `getCostLogs`의 limit을 `Math.min(data.limit || 200, 1000)` 식으로 상한 캡.
2. `getCostSummary`의 `days`를 상한(예: `Math.min(days, 365)`)으로 클램프.
3. `cost_logs`(및 `events`, `agent_heartbeats`) 테이블을 **`timestamp` DAY 파티션 + `userId` 클러스터**로 재구성 → `WHERE timestamp>=` 와 `WHERE userId=` 가 실제로 스캔 바이트를 잘라내게. 이게 데이터가 커질 때 요금을 상수로 잡아주는 가장 큰 지렛대.

> BigQuery 요금 감각: 스트리밍 insert는 $0.05/GB(행이 작아 사실상 무시 가능), **쿼리는
> 스캔 바이트당 $6.25/TB**. 즉 문제는 "얼마나 많이 넣느냐"가 아니라 "쿼리가 매번
> 얼마나 많이 스캔하느냐"다. 파티셔닝 + 캡이 핵심.

## 5. GCP 예산 알림 (Budget Alert) 설정 절차

> ⚠️ **콘솔 설정은 결제 계정 권한이 있는 사용자(계정 소유자)가 직접 클릭해야 한다.**
> 아래는 절차 문서화이며, 이 에이전트는 콘솔을 건드리지 않는다.

예산 알림은 **비용을 막지 않고 알림만 준다**(하드 캡 아님). 서프라이즈 요금을 조기에
잡는 안전망이다. 진짜 폭주 방어는 §3·§4의 코드/파티셔닝이 담당한다.

### 콘솔 단계별

1. [Google Cloud Console](https://console.cloud.google.com) → 상단 프로젝트를 **`marblo-2253d`**로 선택.
2. 좌측 메뉴 **결제(Billing)** → 이 프로젝트에 연결된 **결제 계정** 진입.
3. **예산 및 알림(Budgets & alerts)** → **예산 만들기(Create budget)**.
4. **범위(Scope):**
   - 프로젝트: `marblo-2253d` 선택 (또는 결제 계정 전체).
   - 서비스: 전체(기본) 권장. 세분화하려면 App Engine/Cloud Functions·BigQuery만 골라도 됨.
5. **금액(Amount):** 유형 = "지정한 금액(Specified amount)", 대상 월 예산 입력. 권장값은 아래 §5.1.
6. **알림 임계값(Threshold rules):** 실제 비용(actual) 기준으로 백분율 규칙 추가.
   - 예산을 **$100**로 잡았다면: 50% ($50), 100% ($100), 200% ($200)에 알림 → 아래 권장값과 정렬.
7. **알림 대상(Notifications):**
   - "이메일 알림을 결제 관리자 및 사용자에게(Email alerts to billing admins and users)" 체크.
   - (선택) **Pub/Sub 토픽** 연결 → Cloud Function으로 자동 대응(예: Slack 알림, 심각 시 리소스 차단) 훅 가능. MVP는 이메일이면 충분.
8. **저장(Finish).**

### 5.2 추가 권장 (선택)

- **BigQuery 커스텀 비용 통제:** BigQuery 콘솔 → 쿼리당/프로젝트당 **최대 청구 바이트(maximum bytes billed)** 한도 설정 → 폭주 쿼리를 물리적으로 차단(예산 알림보다 강한 하드 가드).
