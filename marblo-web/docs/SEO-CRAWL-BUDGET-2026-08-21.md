### 2.3 링크를 어디에 놨나

| 위치                      | 파일                                      | 왜 여기인가                                                                     |

- **회전 배정**은 실측으로 잡은 버그다. 추천 글을 선언 순서대로 채웠더니
  `managing-agents-with-tickets` 가 0개였다(뒤쪽 추천 글은 영원히 안 뽑힘).
  현재 글 위치 기준으로 회전시켜 4편이 나눠 받게 고쳤다.

## 3. 처방 2 — 사이트맵 신호 정리

### 3.1 `lastmod` — 19편이 거짓말을 하고 있었다

사이트맵은 blog `lastmod` 로 frontmatter 의 `updated ?? date` 를 낸다. 즉 사람이
손으로 적는 값이다. 본문을 고치고 `updated` 를 안 적으면 그대로 어긋난다.

git 이력과 대조한 결과 **33편 중 19편이 어긋나 있었다.**

| 글                                 | sitemap lastmod | 실제 본문 수정 | 오차     |
| ---------------------------------- | --------------- | -------------- | -------- |
| `ko/managing-heterogeneous-agents` | 2026-07-05      | 2026-08-10     | **36일** |
| `en/managing-heterogeneous-agents` | 2026-07-05      | 2026-08-10     | **36일** |
| `ko/claude-code-subagents`         | 2026-06-27      | 2026-07-09     | 12일     |
| `en/mcp-advanced-tooling`          | 2026-07-01      | 2026-07-09     | 8일      |
| … (총 19편)                        |                 |                |          |

구글은 **신뢰할 수 없다고 판단한 `lastmod` 를 사이트 전체에서 무시한다.** 그래서
틀린 날짜는 없느니만 못하다. 19편 전부 실측값으로 교정했다(frontmatter `updated`
한 줄 추가 — **본문은 건드리지 않았다**: 19파일 19줄 삽입, 0줄 삭제).

재발 방지:

```bash
npm run check:lastmod            # 어긋나면 exit 1
npm run check:lastmod -- --fix   # frontmatter updated 를 실측값으로 교정
```

`scripts/check-blog-lastmod.ts` 는 git 이력에서 **본문(frontmatter 뒤쪽)이 실제로
바뀐 커밋**만 센다. `updated:` 한 줄만 고친 커밋은 변경으로 안 세므로, 날짜를
고칠 때마다 다시 어긋나는 무한루프가 생기지 않는다. 빌드가 아니라 스크립트인
이유: Docker 빌드 컨텍스트엔 `.git` 이 없을 수 있고, 파일 mtime 은 체크아웃
시각이라 **매 배포마다 "전부 방금 바뀜"** 이 되어 오히려 더 나쁘다.

### 3.2 `priority` — 정리는 했지만 효과는 기대하지 마시라

추천 4편 `0.7`, 나머지 블로그 `0.5` 로 갈랐다.

★**구글은 `priority` 와 `changefreq` 를 쓰지 않는다고 공개적으로 밝혔다.** 이
구분은 **우리 의도의 기록**이지 크롤 예산을 움직이는 장치가 아니다. 코드 주석에도
그렇게 적어놨다. 실제로 크롤 순서를 바꾸는 건 §2 의 내부 링크다.

사이트맵에서 진짜로 작동하는 필드는 `lastmod` 하나뿐이고, 그건 §3.1 에서 고쳤다.

### 3.3 ja 블로그 6편 — 안 뺐다. 판단 근거

"우선순위 낮은 URL 이 예산을 먹고 있지 않은가" 를 검토했고, **빼지 않기로 했다.**

근거:

1. **75 URL 규모에서는 크롤 예산이 고갈되지 않는다.** 크롤 예산은 구글 자신의
   설명 기준으로 대략 1만 URL 이상 규모에서 논의되는 개념이다. 6개를 뺀다고
   /en/blog 가 더 빨리 읽히지 않는다. ja 를 빼는 건 실측된 이득이 없는 손실이다.
2. **/ja 는 이미 색인되고 있다.** #1110 §2 에서 Startpage 로 건진 10 URL 중
   `/ja`, `/ja/download`, `/ja/lectures`, `/ja/legal/privacy` 4개가 ja 다. 구글은
   이미 ja 를 크롤할 이유를 찾았다는 뜻이다.
3. **ja 수요를 잴 수단이 없다.** ja 노출·세션은 Search Console·GA4 에만 있고
   이 워크트리에서 접근할 수 없다. 추측으로 URL 을 지우는 건 되돌리기 비용이 있다.

★**재검토 조건 (이 조건이 충족되면 다시 판단해야 한다)**

- GSC 실적 리포트에서 **ja 노출수가 3개월 누적 0** 이고, 동시에
- ja 블로그 6편이 **"발견됨" 상태로 3개월 이상 정체**하면

→ 그때는 ja 블로그를 사이트맵에서 빼고 `/ja/blog` 를 `noindex` 하는 게 맞다.
그 숫자는 오케스트레이터를 통해 요청해둔 상태다.

### 4.0 ★먼저 정정할 전제 하나 — GitHub 링크는 `nofollow` 다

티켓에 "공개 GitHub 레포에서 marblo.app 으로 링크 거는 게 지금 가장 현실적인
백링크다" 라고 적혀 있었다. 절반만 맞다. 실측했다:

```
$ curl -s https://github.com/vercel/next.js | grep -o '<a[^>]*nextjs\.org[^>]*>'
<a href="https://nextjs.org" rel="nofollow">                         ← README 본문
<a ... href="https://nextjs.org" target="_blank" rel="noopener noreferrer nofollow">  ← About 의 website 필드
```

**README 본문도, 저장소 About 의 website 필드도 전부 `rel="nofollow"` 다.**

그럼 쓸모없나 — **아니다.** 세 가지가 남는다:

1. **발견 경로.** 구글은 nofollow 를 2019년부터 "금지" 가 아니라 "힌트" 로 다루고,
   nofollow 링크도 크롤한다. 발견조차 안 되는 지금 상태보다는 낫다.
2. **레퍼럴 트래픽.** 사람이 실제로 눌러서 들어온다. 이건 nofollow 와 무관하다.
3. **브랜드 검색 유발.** GitHub 에서 보고 나중에 "marblo" 를 검색하는 사람이 생긴다.

정리: **GitHub 은 "가장 빠르고 우리가 통제 가능한" 채널이지 "가장 강한" 채널이
