## 1. 큰 그림 — 데이터로 오케스트레이터를 똑똑하게

마블로의 해자는 **라이브 오케스트레이션 엔진 + 의존성 DAG**다(메모 `marblo_vs_orca_strategy_and_moat`). 그 엔진의
핵심 판단 하나가 **"이 작업을 어떤 모델로 스폰할 것인가"**이다. 오늘 그 판단은 `dispatch-scoring.ts`의
순수 스코어링(`scoreModelsDetailed`)이 하고, 모델별 강점은 **손으로 박은 상수**(`MODEL_TAG_BONUSES`:
"claude architecture +25", "antigravity agentic +30")로 표현된다.

문제는 이 표가 **경험을 학습하지 않는다**는 것이다. antigravity를 복잡·자율 작업에 스폰했다가 무활동 스테일이
나도(사례 `wXOhvdp1`), 그 실패가 어디에도 누적되지 않아 **다음 dispatch가 똑같은 실수를 반복**한다.

### 전략의 순서: 데이터 → 휴리스틱 그래프 → (나중에) ML

SLM 라우터를 지금 학습·배포하는 것은 **시기상조**다. 감사(#555)와 1페이지 요약(`slm-router-summary.md`)의
공통 결론은 같다: **라벨이 부족하다.** 따라서 로드맵은 곧장 ML로 가지 않고, 세 계단을 밟는다.

```
[현재]  라우팅 피처는 건강, 결과 라벨은 비어 있음 (감사 #555)
   │    └─ 손으로 박은 정적 MODEL_TAG_BONUSES = 경험 무학습
   ▼
[v1]   라이브 지식그래프 = 그 정적 표의 "동적·감쇠·관측 기반" 버전 (스펙 #559)
   │    └─ ML 없이 결정론적 누적 휴리스틱. 결과를 결정에 되먹임. 머신 로컬.
   ▼
[v2]   크로스유저 글로벌 그래프 = 전 사용자 결과를 서버가 집계 → 각 머신에 push
   │    └─ 네트워크 효과 해자. 프라이버시=라우팅 집계는 비PII+동의.
   ▼
[SLM]  라벨이 충분히 쌓이면 KG가 "피처 생성기" 역할 → BQML/신경망 라우터 학습
```

**핵심 통찰**: 지식그래프는 SLM의 경쟁자가 아니라 **선행 계단이자 피처 공장**이다. v1/v2에서 그래프가
누적하는 셀(성공률·감쇠·어트리뷰션)은 그대로 SLM의 학습 피처가 된다(§5). ML을 서두르지 않아도 그래프는
**첫날부터** 라우팅을 개선하고, 그동안 학습에 필요한 라벨을 자연스럽게 축적한다.

## 3. v1 구현 계획 — 라이브 지식그래프 (머신 로컬)

> 전체 설계·근거·테스트 전략은 스펙 #559에 있다. 여기서는 **로드맵 관점의 착수 순서와 의존성**만 엮는다.

### 3.1 한 문장 정의

정적 `MODEL_TAG_BONUSES`의 **동적·감쇠·관측 기반 버전**을, `scoreModelsDetailed`의 **가법 성분 1개**
(`graphBias ∈ [-20,+20]`)로 추가한다. ML 없음. dispatch 시점 **동기·로컬 파일**(`~/.marblo/routing-graph.json`)
조회. 콜드스타트 = 0 = 현행 동작(무회귀).

### 3.2 세 기둥

1. **스토어**: 이벤트 로그가 아니라 **파생 집계**. 셀 키 = `(factorType:factorValue|model)`
   (예 `tag:agentic|antigravity`), 값 = outcome별 `raw`/`decayed` 카운트 + 신뢰도용 `n` + 멱등 `seen`.
   `dispatch-scoring.ts`가 이미 쓰는 `subscription-plans.json` 동기 mtime 캐시 패턴 재사용(신규 인프라 0).
2. **피드백 루프**: `dispatch:decision`(결정 스냅샷) + `CT3prjl4` 생애 결과(taskId+model 조인) →
   `GraphUpdater`가 셀 증분(감쇠·멱등) → 다음 dispatch의 `graphBias` 반영. **라이브 인-프로세스 증분이 주 경로**
   (BQ 왕복 불필요) — watchdog/agent-manager가 이미 직접 관측하는 스테일/크래시/완료를 소비.
3. **어트리뷰션 축(안전핀)**: 실패를 §3 택소노미로 분류해 **모델 탓만** 사전확률에 반영. `dependency_stuck`
   (오케 버그)은 `routingWeight=0`으로 **제외** — 안 그러면 그래프가 오케 버그를 antigravity 탓으로 오학습.
   호스트/가용성(spawn/auth/tool_zero)은 반영하되 **빠른 감쇠**(2d) — 인증 고치면 사라져야 하는 전이적 사실.

### 3.3 착수 순서 (의존성 정렬)

```
선행: CT3prjl4 landing (✅ 완료 — PR#556)
  │
  ├─ 단계 A (순수 로직, 선구현 가능):
  │    routing-graph.ts — 타입/로드/감쇠/수축/멱등/graphBiasForModel(순수)
  │    routing-graph.test.ts — 감쇠·수축·콜드스타트·멱등·dependency_stuck 제외
  │    → CT3prjl4 없이도 검증 가능. 무회귀(콜드스타트=0).
  │
  ├─ 단계 B (통합):
  │    dispatch-scoring.ts — PerModelScore.graphBias, scoreModelsDetailed(...,ctx?,graph?)
  │    bridge-server.ts — spawn 분기서 그래프 로드+ctx 주입, decisionReason에 graph 조각
  │    dispatchMeta 확장 — role·tags·taskType 추가 보존(인-프로세스 조인 키)
  │
  └─ 단계 C (피드백 배관):
       graph-updater.ts — watchdog/agent-manager/완료 훅에서 outcome+dispatchMeta → applyOutcome
       CT3prjl4 outcome 5종 → §3 세분으로 로컬 정규화(stale→no_activity_stale 등)
```

### 3.4 v1 경계 (비목표)

- SLM/신경망 학습 (라벨 부족).
- 프롬프트 원문 의미 피처 (프라이버시 계약).
- **크로스유저 서버 집계** — v1은 **머신 로컬**. "global"은 이 머신의 프로젝트 전역일 뿐. → **v2가 여기서 시작**.
- 새 실패 감지 로직 (watchdog/agent-manager가 이미 감지 — 스펙은 판정을 소비만).

### 3.5 자매 성분과의 관계 (`YDZUsWLb`, 예산인지)

KG의 `graphBias`와 예산인지의 `budgetBias`는 **같은 통합 지점**(`scoreModelsDetailed`)의 **같은 스케일**(±20)
가법 성분이다. 서로 보완:

- `graphBias` = **학습된 성공/실패 사전확률**(느린 시간축, 능력 신호).
- `budgetBias` = **실시간 잔여 예산 상태**(빠른 시간축, "지금 Codex에 토큰 많이 남았다").

```
total = base + tagBonus + tagPenalty + costEff + agyBias + graphBias + budgetBias
                                                            └ v1(KG) ┘ └ REVIEW ┘
```

둘 다 역할 하드게이트(100)/reuse 보너스를 못 뒤집는 타이브레이커~약우세. 둘 다 `decisionReason`에 기여를
기록해 관측 가능. 이 대칭성은 v1이 **단일 확장점에 정직하게 얹히는 설계**임을 보증한다.

## 4. ★v2 — 크로스유저 글로벌 그래프 (네트워크 효과 해자)

v1의 그래프는 **이 머신이 관측한 것**만 안다. 새 사용자·새 머신은 **콜드스타트**(빈 그래프)로 시작해 스스로
겪어봐야 배운다. v2는 이 콜드스타트를 없앤다: **전 사용자의 라우팅 결과를 서버가 집계해 하나의 글로벌 그래프로
만들고, 각 머신에 push**한다. 그러면 새 사용자도 **첫 dispatch부터 fleet 전체의 경험**을 물려받는다.

### 4.1 아키텍처 — 서버 집계 → push, 지역 읽기는 로컬 유지

핵심 원칙은 **"읽기 경로는 v1 그대로, 내용 출처만 글로벌"**이다. dispatch 핫패스는 여전히 로컬 파일을 동기로
읽는다(§3의 저지연 계약 불변). 달라지는 것은 그 파일이 **어디서 왔는가**다.

```
[각 머신]  dispatch:decision + CT3prjl4 outcome  ──(opt-in 텔레메트리)──▶  BQ events (전 사용자)
                                                                              │
                                                              ┌───────────────┘
                                                              ▼
[서버 잡]  주기적 집계 (일/시간 배치):
             BQ 전 사용자 outcome 조인 → (factor×model) 셀별 성공률·감쇠·n 롤업
             → 비PII 글로벌 그래프 산출 (routing-graph.global.json)
             → 서명·버전 스탬프
                                                              │
                          ┌───────────────────────────────────┘  push (앱 부팅/주기 fetch)
                          ▼
[각 머신]  글로벌 그래프를 base 계층으로 수신
             ~/.marblo/routing-graph.global.json   ← 서버 push (전 사용자 집계, 내용 출처=글로벌)
             ~/.marblo/routing-graph.json          ← 로컬 관측 (이 머신, v1 그대로)
             ~/.marblo/projects/<id>/routing-graph.json ← per-project overlay (v1 그대로)

           해석 규칙(3계층 폴백):
             per-project(n≥N_min)  >  local machine(n≥N_min)  >  global base  >  0(콜드스타트)
             │                        │                          │
             그 레포 특유              이 머신 경험                fleet 전체 경험(새 사용자도 물려받음)
```

- **읽기(dispatch)는 로컬 유지**: `graphBiasForModel`은 여전히 로컬 파일만 동기로 읽는다. 네트워크 왕복 없음.
  글로벌 그래프는 **미리 받아둔 로컬 base 계층**일 뿐 — dispatch가 서버를 때리지 않는다(§5.1 스펙의 저지연 계약 유지).
- **내용 출처만 글로벌**: v1의 2계층(local base + project overlay)에 **글로벌 base 한 층을 아래에 깐다.** 로컬
  관측이 충분(`n≥N_min`)하면 로컬이 이기고, 부족하면 글로벌로 폴백. 즉 **로컬 경험이 항상 우선, 글로벌은
  콜드스타트 보험**.
- **서버 잡은 v1의 "주기적 BQ 재조정(§7.1-2)"의 확장**: v1 스펙이 이미 예고한 자가치유 경로를 **전 사용자
  스코프**로 넓힌 것. 새 코드 개념이 아니라 스코프 확대.

### 4.2 프라이버시 — 라우팅 집계는 비PII + 동의

이것이 v2의 게이트다. **글로벌 그래프에 올라가는 것은 파생 카운트뿐, 원문이 아니다.**

| 글로벌로 나가는가 | 항목                                                       | 근거                                                                      |
| :---------------: | ---------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
|        ✅         | `(factorType:factorValue                                   | model)` 셀의 성공/실패 **카운트·성공률·감쇠값·n**                         | 파생 집계. 유한 카테고리(태그 사전·역할·complexity·taskType 분류기 출력). |
|        ✅         | 실패 **모드**(§3 택소노미: stale/crash_loop/spawn_failed…) | 카테고리 라벨. 개인 식별 불가.                                            |
|        ❌         | 프롬프트 **원문**·코드·파일 경로                           | v1과 동일 — 절대 미수집(감사 #555 프라이버시 계약).                       |
|        ❌         | `promptHash`/`promptLength` 개별값                         | 개별 태스크로 역추적 가능성 → 글로벌 롤업에서 제외. 집계 성공률에만 기여. |
|        ❌         | userId·projectId·taskId·cwd·레포명                         | 조인 키는 **서버 잡 내부에서만** 사용, 글로벌 산출물엔 미포함.            |

- **동의 계약**: 글로벌 집계 기여는 **opt-in 텔레메트리 계약**에 묶는다(메모 `telemetry_privacy_policy`:
  1차 BQ 비식별 상시, 3rd-party 옵트인). 라우팅 집계는 "1차 비식별"에 해당하나, **크로스유저 공유**라는
  성격상 명시적 opt-in을 별도로 받는 것이 안전(§6 결정).
- **비대칭 소비 허용 검토**: 기여(내 결과를 글로벌에 보냄)와 소비(글로벌 그래프를 받아 씀)를 분리할 수 있다.
  소비는 비PII 산출물 fetch라 프라이버시 부담이 낮고, 기여만 opt-in 게이트에 둘 수 있다 — §6 결정 포인트.
- **k-익명 임계**: 셀 `n`이 작으면(예 특정 사용자 1명만 기여) 그 셀은 글로벌에서 **억제**(개별 사용자 행동
  역추적 방지). `n ≥ k`(예 5) 셀만 글로벌로 승격.

### 4.3 네트워크 효과 = 해자

이 구조가 전략적으로 중요한 이유:

- **사용자가 늘수록 라우팅이 똑똑해진다**: 각 머신의 실패/성공이 글로벌 그래프를 살찌우고, 그 그래프가 모든
  머신의 콜드스타트를 개선한다. 경쟁사가 정적 휴리스틱을 베껴도 **fleet 관측 데이터는 못 베낀다.**
- **데이터 해자 = 오케 해자의 강화**: 마블로 해자(라이브 오케 엔진 + DAG, 메모 `marblo_vs_orca_strategy_and_moat`)
  위에, **"경험이 축적될수록 배정이 정확해지는"** 자가강화 루프를 얹는다. 이는 감사 수익화 웨지와 별개의
  **제품 코어 해자**다.
- **후발 진입 장벽**: 신규 사용자가 겪는 콜드스타트를 우리는 이미 fleet 데이터로 메운다 — 경쟁 제품은
  사용자마다 처음부터 다시 배워야 한다.

### 4.4 v2 경계

- **여전히 결정론적 휴리스틱** — v2도 ML이 아니다. 글로벌은 "더 큰 관측 모수"일 뿐, 모델은 그대로 감쇠 카운터.
- 실시간 스트리밍 아님 — 배치 push(일/시간). dispatch는 로컬 스냅샷만 읽는다.
- 개인화 학습 아님 — 글로벌은 fleet 공통 능력 신호. 사용자·레포 특유는 로컬/overlay 계층이 담당(폴백 우선순위).

## 5. SLM 학습 단계 — 라벨이 충분해진 뒤, KG가 피처 생성기

지식그래프(v1/v2)가 도는 동안 **부산물로 학습 데이터가 쌓인다.** 임계에 도달하면 그때 SLM/BQML로 간다.

### 5.1 착수 조건 (라벨 임계)

감사 #555와 ML-준비도 문서(§7)가 정한 최소 요건이 **동시 충족**될 때:

| 조건                            | 현재 (감사 #555)                    | 목표                                          | 지금 막는 것 → 해소 경로                             |
| ------------------------------- | ----------------------------------- | --------------------------------------------- | ---------------------------------------------------- |
| dispatch+cost+outcome 조인 샘플 | 141 (34.6%)                         | ML-1: `task_outcomes` 500+                    | 조인율 35% → `CT3prjl4`로 라벨 확장(진행)            |
| 부정 라벨 다양성                | 전부 `BLOCKED`                      | stale/crash/spawn_failed/review_rejected 분포 | `CT3prjl4` outcome 어휘로 **해소 시작** ✅           |
| 최상위 수락 라벨                | `task:merged` 0행                   | 실머지 라벨 축적                              | `d1afYIcV`: 코드 아닌 **앱 머지 경로 유도** 필요(§6) |
| 크로스검증 정답                 | `task_outcomes` 195행(72% taskType) | 안정 축적                                     | `task_outcomes` 라이브(§7.4 KG 스펙)                 |

### 5.2 KG → SLM 이행: 그래프가 피처 공장

**핵심**: v1/v2에서 그래프가 누적한 셀이 **그대로 SLM의 입력 피처**가 된다. 즉 KG는 SLM의 전 단계이자
**피처 엔지니어링 계층**이다.

```
[SLM 학습 피처 = 결정 스냅샷 + KG 파생 + 라벨]

  입력 X:
    - dispatch:decision 원 피처: role, taskType(classifyTaskType), complexity, tags[], perModelScores
    - KG 파생 피처: (factor×model) 셀의 성공률·감쇠·n·어트리뷰션 버킷   ← 그래프가 만든 것
    - 예산 상태: budgetBias 입력 스냅샷(YDZUsWLb)
  라벨 Y:
    - outcome(§3 택소노미) + task:merged(최상위 수락) + task_outcomes.success
       ▼
  BQML LOGISTIC_REG / Vertex AutoML (ML-1 모델 자동 선택)
  BQML LINEAR_REG (ML-3 비용 예측)
  BQML ARIMA_PLUS (ML-4 이상 탐지)   ← bigquery-ml-readiness §8 템플릿 재사용
```

- **KG가 손튜닝을 대체**한 지점을 SLM이 다시 **비선형·상호작용 학습**으로 대체 — 하지만 KG가 이미
  깨끗한 피처·라벨을 만들어 놨으므로 SLM은 **차가운 데이터가 아니라 정제된 데이터**로 시작한다.
- **KG는 SLM 배포 후에도 살아남는다**: (a) 콜드스타트 fallback(SLM이 못 본 새 factor는 그래프 사전확률),
  (b) 관측 가능한 baseline(SLM 예측 vs 그래프 사전확률 diff로 SLM 회귀 감지), (c) 온라인 적응(SLM 재학습
  주기 사이의 최신 결과 흡수).

### 5.3 SLM의 두 얼굴 (혼동 주의)

`slm-router-summary.md`가 말하는 SLM에는 **두 갈래**가 있고, 이 로드맵은 (A)만 다룬다:

- **(A) 라우팅/모델선택 SLM** — 본 문서의 종착점. KG가 피처 공장. **내부 최적화용**.
- (B) 엔터프라이즈 온프렘 SLM 게이트웨이 — 기밀 프로젝트를 사내 vLLM으로 보내는 **정책 라우팅**.
  별도 트랙(Gateway PoC, 감사 로그, 보안 마스킹). 본 로드맵의 데이터 계단과 **독립**(요약 doc 결론 유지).

## 6. 의사결정 포인트

로드맵을 진행하며 **사람이 결정해야** 하는 갈림길. 각 단계 착수 전 명시적으로 짚는다.

### v1 (지식그래프) 착수 시 결정

| #   | 결정                       | 선택지                                                                                                   | 로드맵 기본권고                                                                                                             |
| --- | -------------------------- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| D1  | **부트스트랩 시딩**        | (a) 정적 `MODEL_TAG_BONUSES`를 그래프 사전 셀로 약한 n 시딩 vs (b) 0-시작                                | **(b) 0-시작 권장** — 관측이 손튜닝을 이기게. 단 초기 방향성이 필요하면 (a)를 약한 n으로. (스펙 #559 §8.4·§13 오픈이슈)     |
| D2  | **outcome 어휘 세분 시점** | CT3prjl4 5종 → §3의 10+ 모드(auth_failed/tool_zero/crash_loop/dependency_stuck) 확장을 v1과 동시 vs 후속 | v1은 **로컬 정규화로 브리지**(stale→no_activity_stale), 세분은 후속 계약. 늦으면 품질만 저하(안전).                         |
| D3  | **머지 라벨 활성화**       | `d1afYIcV`가 코드 버그 아님으로 판정 → 앱 Merge 경로를 실제로 쓰게 **유도**할지                          | task:merged는 KG 최강 양신호 → **앱 내 머지 UX 유도**를 별도 검토(gh/CLI 우회를 앱 경로로). 코드 수정 아님, 습관/제품 결정. |

### v2 (크로스유저 글로벌) 착수 시 결정

| #   | 결정                 | 선택지                                                                                                   | 로드맵 기본권고                                                                                                                 |
| --- | -------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| D4  | **동의 계약 형태**   | 라우팅 집계 기여를 (a) 1차 비식별 상시(현 텔레메트리 정책) vs (b) 크로스유저 공유용 **별도 명시 opt-in** | **(b) 별도 opt-in 권장** — "내 결과가 fleet 글로벌에 기여"는 사용자에게 명시적으로 고지·동의. (메모 `telemetry_privacy_policy`) |
| D5  | **기여/소비 비대칭** | 소비(글로벌 그래프 받기)는 기본 on, 기여(내 결과 보내기)만 opt-in 게이트                                 | 소비는 비PII 산출물 fetch라 부담 낮음 → **비대칭 허용 검토**. 무임승차 방지 정책은 별도.                                        |
| D6  | **k-익명 임계**      | 글로벌 승격 최소 `n`(기여 사용자 수)                                                                     | `n ≥ k`(예 5) 셀만 글로벌 노출 — 개별 사용자 행동 역추적 차단.                                                                  |

### 공통

- **무회귀 불변식**: 어느 단계든 신호 없음/부족 → bias=0 → 현행 스코어링 그대로. 이 안전핀은 v1·v2·SLM
  전 단계에서 유지(역할 하드게이트·reuse 보너스 불가침).
- **관측 가능성 계약**: 그래프/예산/SLM의 기여는 항상 `decisionReason`+`perModelScores`에 기록 → 스스로의
  영향이 다시 텔레메트리로 감사·재학습된다(피드백 루프의 self-hosting).
