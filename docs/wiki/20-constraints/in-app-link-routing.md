# 링크는 앱 안에서 연다 — 밖으로 내보내는 예외는 임베디드에서 실제로 깨지는 것뿐이다

> **한 줄 판정**: ★채택 — **주소창에 쳐서 열리는 것은 클릭해서도 열린다.** 이 둘이 갈리면 사용자는 규칙을 배울 수 없다. 밖으로 내보내는 예외는 "외부 사이트라서"가 아니라 **임베디드 브라우저에서 실제로 깨지는 것**만이고, 예외는 반드시 이유를 말한다.

## 무엇을 물었나

앱 안 웹 탭이 있을 때, 어떤 링크를 안에서 열고 어떤 링크를 OS 브라우저로 내보내야 하는가. 그 경계를 무엇으로 긋는가.

## 규칙

**1. 두 입구는 같은 곳으로 간다.** 주소창 입력과 링크 클릭은 같은 URL에 대해 같은 결과를 내야 한다. 이 규칙이 깨지면 사용자는 "왜 어떤 건 안에서 열리고 어떤 건 밖으로 나가지"를 배울 수 없고, 규칙을 못 배우면 앱을 신뢰하지 못한다.

**2. 밖으로 내보내는 예외는 세 가지뿐이고, 셋 다 이유가 "임베디드에서 깨진다"이다.**

| 예외 | 왜 밖이어야 하나 |
| --- | --- |
| 로그인·OAuth | 구글은 embedded user agent 로그인을 **정책으로 거부한다**(`disallowed_useragent`). 탭 안에서 열어도 사용자는 막힌 화면을 본다. loopback PKCE 플로우는 시스템 브라우저에서 끝나도록 설계돼 있고, 그래야 기존 로그인 세션과 비밀번호 관리자를 쓴다 |
| 결제 | 사용자가 **진짜 주소창을 직접 보고** 신뢰를 판단할 수 있어야 한다. 앱이 그린 주소창 안에서 카드번호를 넣게 만들 이유가 없다 |
| http(s)가 아닌 스킴 | `mailto:` `tel:` 등은 애초에 웹 페이지가 아니다. OS 기본 앱이 연다 |

**3. "외부 사이트라서"는 예외 사유가 아니다.** 임베디드에서 깨지는 게 실측되면 그때 목록에 추가한다. 추측으로 미리 넓히면 규칙 1이 조용히 무너진다.

**4. 밖으로 나가는 경로에는 안내가 붙는다.** 이유 없이 OS 브라우저가 뜨면 사용자에겐 앱이 링크를 흘린 것으로 보인다. 탭으로 못 보낸 경우(창이 없음, 렌더러 무응답)도 마찬가지로 이유를 말한다. **분기 하나라도 침묵이면 규칙 전체가 안 지켜진 것**이므로, 이건 주석이 아니라 타입으로 막는다 — 라우팅 결과의 안내 필드를 `NonNullable`로 두면 침묵 분기가 컴파일되지 않는다.

## 함정 — 정규화가 스킴을 뭉개면 예외 목록은 죽은 코드다

URL 정규화는 보통 "사용자가 `example.com`이라고 쳤으면 `https://`를 붙인다"를 한다. 그런데 **스킴과 `host:port`를 구분하지 않으면** 이미 스킴이 있는 URL에도 접두사를 붙인다:

```
mailto:hi@example.com  →  https://mailto:hi@example.com
```

이건 실패하지 않는다. **`example.com` + credentials(`mailto:hi`)로 정상 파싱된다.** 그래서 `mailto:` 링크가 "외부 프로토콜" 예외 분기에 **도달한 적이 없고**, 평범한 허용 페이지로 분류돼 왔다. 예외 목록은 멀쩡히 존재하는데 아무도 그 앞을 지나가지 않는 상태다.

가르는 기준은 콜론 뒤다: **뒤가 숫자뿐이면 `host:port`, 아니면 스킴이다.** `localhost:3001`은 호스트와 포트, `mailto:hi@…`는 스킴이다.

일반화하면 — **정규화 함수는 입력 도메인을 좁게 잡아라.** "사용자가 주소창에 친 것"을 위한 함수를 "페이지가 넘긴 `href`"에 그대로 쓰면 안 된다. 두 입력은 신뢰도도 형태도 다르다.

## 함정 2 — 정책이 맞아도 **누구에게 묻느냐**가 틀리면 규칙 1은 다시 무너진다

라우팅 판정은 두 축이다. **어떤 URL인가**(정책)와 **이 클릭을 담아 줄 표면이 있는가**(배선). 사양·테스트는 앞 축에만 붙기 쉽고, 뒤 축은 "탭 서피스가 등록됐는가"라는 boolean 한 개로 눌려 들어간다. 그 boolean 을 **어떤 객체에게** 묻느냐가 조용히 규칙 1을 되돌린다.

이 저장소에서 실측된 형태는 이랬다 — 등록은 워크스페이스 셸의 webContents 하나만 하는데, 판정은 "핸들러를 발화시킨 webContents"에게 물었다. 같은 앱·같은 창 안이라도 **다른 webContents 에서 올라온 클릭은 전부 "탭을 놓을 창이 없다"로 판정**돼 밖으로 나갔다. 사용자에겐 웹 탭이 눈앞에 떠 있는데 "웹을 호스트할 창이 없다"는 안내가 뜬다.

그렇게 되는 경로가 둘이었다.

| 경로 | 왜 다른 webContents 가 되나 |
| --- | --- |
| 창을 먼저 열고 나중에 이동시키는 링크 핸들러 | `window.open()` 을 **URL 없이** 부르면 그 클릭은 "내부"로 분류돼 허용되고, Electron 이 기본 옵션의 떠돌이 창을 만든다. 이어지는 `location.href` 이동은 **그 새 창**에서 일어난다 |
| 앱 안 웹 탭(`WebContentsView`)의 페이지 | 전역 `web-contents-created` 훅이 앱 수준 링크 처리를 **먼저** 붙이고, 웹 탭 자신의 정책은 그 뒤에 붙는다. `will-navigate` 는 둘 다 살아 있어 앞의 것이 먼저 취소해 버린다 |

**규칙: "탭을 놓을 곳"은 하나의 webContents 속성이 아니라 opener 사슬(창 단위)의 속성이다.** 그리고 자기 정책이 완결된 표면(앱 안 브라우저)에서는 앱 수준 처리가 **물러서야** 한다 — 두 정책이 같은 이벤트에 겹치면 등록 순서가 동작을 결정하고, 등록 순서는 아무도 테스트하지 않는다.

## 왜

임베디드 브라우저를 `WebContentsView`로 띄우면 `X-Frame-Options`나 CSP의 영향을 받지 않아 대부분의 사이트가 뜬다. 그래서 "외부 사이트는 밖으로"라는 옛 직관은 근거를 잃었는데, 코드는 그 직관을 조건으로 계속 들고 있기 쉽다. 실제로 이 저장소에서는 조건이 "로컬 데모 URL인가"로 좁혀지면서 일반 외부 링크가 전부 조용히 밖으로 나갔고, 그건 구현 결함이 아니라 **사양이 사용자 기대와 어긋난 것**이었다. 그래서 분기를 고치기 전에 사양부터 썼다.

## 한계 / 정직성

- 예외 목록(어떤 호스트가 로그인·결제인가)은 시점 의존이다. 위키는 목록을 고정하지 않고 **목록에 넣는 기준**만 고정한다. 현재 목록은 원본 사양서가 갖는다.
- 앱 안에서 임의 웹을 실행하는 보안 경계(`nodeIntegration:false`, `contextIsolation:true`, 세션 파티션 분리, preload 미주입)는 이 규칙이 새로 연 것이 아니라 주소창 경로가 이미 쓰던 조건이다. 갈리면 원본이 옳다.
- 실화면 확인은 사장님 몫으로 남겨 뒀다 — [[no-live-gui-verify]].

## 실제 영향

판정의 "누구" 축을 창/opener 사슬 단위로 넓히고, 앱 안 웹 탭의 페이지에서는 앱 수준 링크 처리가 물러서게 했다. 터미널의 링크 핸들러는 앱의 다른 모든 링크와 같이 진짜 URL 을 그대로 넘긴다 — 떠돌이 빈 창이 애초에 생기지 않는다.

라우팅 판정에서 "로컬 데모인가" 인자를 없애 일반 http(s)도 앱 탭으로 보낸다. 탭으로 못 보내는 경로에 `no-tab-target` 사유를 신설해 침묵 분기를 없앴고, 라우팅 결과의 안내 필드를 `NonNullable`로 좁혀 침묵을 타입으로 막았다. 정규화는 스킴과 `host:port`를 구분한다.

브라우저 페인의 새 창 요청도 현재 페인에 `loadURL`로 덮어쓰지 않고, 동일한 정책 판정과 Web 탭 라우팅을 거친 뒤 native 창 생성을 거부한다. 따라서 로그인된 페이지가 팝업 하나 때문에 사라지지 않는다.
