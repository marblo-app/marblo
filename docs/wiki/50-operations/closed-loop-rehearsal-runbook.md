# 폐루프 리허설 — 코드를 안 다치고 한 바퀴를 눈으로 보는 절차

> **한 줄 판정**: 리허설 1회는 **티켓 5건 · 미션 2개 · 에이전트 4기 · 20~35분 · 실측 기반 $12~18**(권장 설정 `complexity="simple"` 기준 **약 $14**)이고, 그 비용의 **65~85%($9~13)가 오케 턴**이라 리허설 티켓을 아무리 싸게 만들어도 총액의 하한은 오케가 정한다. ★그리고 **폐루프는 오늘까지 라이브에서 한 번도 돈 적이 없다** — 라이브 오케 세션 **20,777턴** 전수를 훑어 `[Mission Advance]` 유저턴 **0건**, `[Mission Handoff]` **0건**이다(발화 흔적은 전부 이 기능을 만든 워크트리 세션 5개 안의 소스·테스트 텍스트였다). ★관찰 지점 하나는 **실제로 없다**: 완료이력(작업내역) 탭의 Mission Replay 는 2026-08-08 결정으로 파킹돼 **기본 OFF** 다(`localStorage["marblo.replayDashboard.enabled"] === "1"` 일 때만). 미션 종결은 다른 **세 자리**에서 본다. 아래 절차의 화면·로그는 전부 **직접 열어 확인**했고, 확인 결과가 티켓의 가정과 갈린 4건은 그 자리에 그대로 적었다.

## 무엇을 물었나

사장님 지시(2026-09-05 텔레그램): _"내가 시연을 하거나 테스트하려면 어떻게 하는 게 좋지 — 간단한 미션에서 두세개 태스크가 나눠져 있고 그게 돌아가고 알아서 클로즈하거나 다음 태스크가 연달아 오케한테 주입돼서 열리는 것까지 보이면 좋겠다. A 미션이 완료되면 오케브레인의 다른 미션들로 넘어가서 다음 태스크가 돌아가는 방식. 물론 토큰 잔여량은 체크하면서"_.

폐루프 문서 셋의 역할은 2026-09-05 에 확정됐다. 겹치는 서술은 한 줄도 다시 쓰지 않는다.

| 질문                          | 어느 노트                                |
| ----------------------------- | ---------------------------------------- |
| 지금 **어떻게 도는가**        | [[closed-loop-one-turn-and-its-stops]]   |
| **왜 안 돌았는가**            | [[five-layers-that-hid-the-closed-loop]] |
| ★**직접 한 바퀴 돌려보는 법** | 이 노트                                  |

(그 계층이 **왜 그렇게 생겼나**는 [[autonomous-advance-needs-caps-first]] 가 따로 맡는다.)

셋 다 코드 실측이라 **한 번도 실제로 돌려본 기록이 없다.** 그래서 이 노트의 물음은 셋이다.

1. 진짜 코드·라이브를 안 다치면서 한 바퀴를 돌리려면 **무엇을 만들어 무슨 순서로** 하는가.
2. 각 단계가 일어났음을 사장님이 **어디서** 보시는가 — 그리고 그 자리가 **실제로 그걸 보여주는가**.
3. **얼마가 드는가.** 반복 못 하는 시연은 한 번 쓰고 버리는 것이라 값을 못 한다.

## 무엇을 했나

절차를 쓰기 전에 **적을 자리를 전부 열어 봤다.** 문서가 가리키는 화면·로그가 실제로 그것을 보여주는지 확인하지 않으면 절차서가 처음부터 거짓이 된다. 확인 결과 **티켓이 가정한 것과 갈린 것이 4건**이었고, 넷 다 절차를 바꿨다(§확인한 것과 갈린 것).

비용은 추정하지 않고 **실측**했다. 로컬 세션 원장(`~/.claude/projects/**.jsonl`)의 턴별 `usage` 를 앱과 **같은 요율표·같은 공식**(`electron/model-registry.ts` 의 `pricing` + `cost-tracker.ts` 의 `cacheRead = input×0.1`, `cacheWrite = input×1.25`)으로 다시 계산했다.

#### 2단계(앱 재시작)는 이제 화면이 확인해 준다

전에는 "재시작했다고 믿는 것"과 "재시작된 것"을 가르려면 사람이 `ps` 의 프로세스 시작시각과 `dist-electron` 의 mtime 을 손으로 대조해야 했다. 2026-09-05(#1433)부터 **메인 프로세스가 스스로 대조하고 화면에 띄운다.** 배너가 떠 있으면 그게 곧 "아직 옛 코드로 돌고 있다"이다:

> **앱을 재시작하면 해결됩니다** — 화면은 최신 코드로 갱신됐지만, 메인 프로세스는 앱을 켠 시점의 코드로 실행 중입니다. …
> 터미널에서 `npm run dev` 를 다시 실행하세요. / 반영 대기 중: `bridge-server.js`, `tools.js` …

이 절차서에 직접 걸리는 이유가 있다 — 그 가드를 만들게 한 근거 세 건 중 **둘이 폐루프 층**이다(`main.ts` 주석이 그대로 적어 뒀다: #1418 웹탭 좌표 · **#1420 폐루프 스위치** · **#1422 텔레그램 큐**). 즉 "머지됐는데 안 고쳐졌다"가 이 기능에서 이미 두 번 났고, 두 번 다 원인이 재시작 누락이었다.

★**다만 셋을 혼동하지 마라.**

|                         | 무엇을 말해 주나                                                                                                                                               | 절차에서                              |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| 배너가 **떠 있다**      | 메인 프로세스가 디스크의 `dist-electron` 보다 **옛 코드**로 돌고 있다                                                                                          | 2단계 미완 — 재시작하고 다시 본다     |
| 배너가 **없다**         | ★"최신이다"의 증명이 **아니다.** 판정이 `stale` 일 때만 뜨고 `fresh` 와 `unknown`(부팅 스냅샷 없음 · 디스크 스캔 실패 · 빈 스캔 · 빌드 진행 중)은 **침묵**한다 | 5단계(부팅 한 줄)를 여전히 봐야 한다  |
| 배너와 **3단계는 무관** | 배너는 **메인 프로세스**의 코드 세대만 본다. 오케가 물고 있는 MCP config 스냅샷은 다른 축이다                                                                  | 오케 재스폰은 4·5단계로 따로 확인한다 |

두 가지 더: 판정 축은 mtime 이 아니라 **내용 해시**이고(빌드가 파일을 다시 써도 내용이 같으면 안 뜬다), **dev 실행에서만** 켜진다 — 패키징 빌드에선 코드가 `app.asar` 안이라 실행 중 바뀔 수 없어 감시자 자체를 켜지 않는다. 배너를 닫으면 그 앱 실행 동안 다시 뜨지 않는다(조건이 단조라 재알림이 정보를 더하지 않는다).

**★부팅 한 줄은 터미널 탭에서 안 보인다.** MCP 서버는 그 줄을 stderr 로 쓰는데 claude CLI 는 MCP stderr 를 화면에 올리지 않고 캐시 로그로 떨어뜨린다. 그래서 눈으로 확인할 자리는 화면이 아니라 이 파일이다:

```bash
# 오늘 기동한 MCP 서버들이 실제로 받은 값 — ON 이 아니면 안 켜진 것이다
grep -rho '\[advance-signal\][^\\"]*' \
  ~/Library/Caches/claude-cli-nodejs/*/mcp-logs-marblo/*.jsonl \
  | sort | uniq -c
```

기대 출력(2026-09-05 실측 그대로):

```
  18 [advance-signal] MISSION_ADVANCE_SIGNAL="on" → ON — 자율 전진 신호가 켜져 있다(한도는 advance-guards 가 건다).
```

`→ OFF` 가 섞여 있으면 그 줄이 보여주는 **원문 값**이 답이다(`"true"`·`"1"`·`" on "` 는 전부 옳게 OFF). 줄이 아예 없으면 그 오케는 **재스폰되지 않은 옛 프로세스**다.

### 1. 리허설 미션 두 개 — 티켓 5건, 에이전트 4기

미션이 **둘이어야** 하는 이유는 하나면 미션→미션 전환(9단계)이 아예 안 보이기 때문이다. 티켓은 5건이지만 **스폰되는 에이전트는 4기**다 — 하나는 일부러 자율 경로에서 빠진다.

| 미션 | 라벨(`mission_label`)        | 티켓 | 하는 일                                                               | 왜 이 모양인가                                                                   |
| ---- | ---------------------------- | ---- | --------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| A    | `[리허설] A — 스크래치 왕복` | A1   | `/tmp/marblo-rehearsal/<날짜>/a1.txt` 에 시각 + 자기 `agent_id` 한 줄 | 몇 분 안에 끝나고 산출물이 눈에 보인다                                           |
| A    | 〃                           | A2   | `a1.txt` 를 읽어 줄 수를 세어 `a2.txt` 에 한 줄                       | A1 과 **의존 간선 없이** 나란히 — 라벨로만 묶인 형제 티켓이 실제 보드의 모양이다 |
| A    | 〃                           | A3   | ★**제목에 "배포"가 들어간다.** 아무 일도 하지 않는다                  | 승인필요 표지가 잡혀 **자율 경로에서 빠지는 것**을 공짜로 보여준다               |
| B    | `[리허설] B — 스크래치 요약` | B1   | `a1.txt`·`a2.txt` 목록을 `b1.txt` 에                                  | 미션 A 가 닫힌 뒤 **다음 미션**으로 제안될 대상                                  |
| B    | 〃                           | B2   | `b1.txt` 를 읽어 요약 한 줄을 `b2.txt` 에                             | 미션 B 안에서도 전진 신호가 한 번 더 난다                                        |

**★실패해도 진짜 코드·라이브가 안 다치는 근거는 넷이고, 셋이 구조적이다.**

| #   | 근거                                                                  | 왜 구조적인가                                                                  |
| --- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 1   | 쓰기 대상이 `/tmp/marblo-rehearsal/` — **리포지토리 밖**              | 리포지토리 파일을 안 건드리므로 되돌릴 것이 없다                               |
| 2   | 에이전트는 **격리 워크트리**에서 돈다(`electron/worktree-manager.ts`) | 리포 안을 잘못 건드려도 다른 작업·`main` 과 분리돼 있다                        |
| 3   | 티켓 `notes` 에 `git commit`·`push`·PR 금지                           | 착지 경로가 없으면 사고가 밖으로 못 나간다                                     |
| 4   | 배포·메일·결제·심사화면 근처에 가지 않는다                            | 그런 항목은 **승인필요로 빠져 루프가 안 도는 것이 정상**이라 시연에 부적합하다 |

2·4 는 규율이 아니라 코드다. 1·3 은 티켓 본문이라 사람이 어긴다면 어길 수 있다 — 다만 어겨도 2 가 받는다.

**워크체인(오케브레인)에 항목 둘을 올린다.** 미션 B 가 **다음 미션 후보가 되는 유일한 길**이 이것이다 — 핸드오프는 다른 미션 문서를 훑지 않고 **워크체인만** 훑는다(`mission-handoff.ts :: selectHandoffCandidates`).

```
add_work_chain_item(
  what="[리허설] 미션 B — 스크래치 요약",
  why="폐루프 리허설: 미션 A 가 닫힌 뒤 미션→미션 전환을 눈으로 확인하기 위한 후보",
  mission_label="[리허설] B — 스크래치 요약",
  position=0)

add_work_chain_item(
  what="[리허설] 미션 C — 리허설 뒷정리",
  why="리허설이 남긴 티켓·항목·스크래치를 지우는 일. 미션 B 가 끝나야 의미가 있다",
  after_item_ids=[<위 B 항목 id>],
  position=1)
```

C 항목은 두 가지를 동시에 한다. ① `after_item_ids` 때문에 **WAITING** 이라 후보에서 빠지고, 그래서 신호의 `⏸ 선행 미충족으로 후보에서 제외` 줄을 공짜로 보여준다. ② B 를 선행으로 지목하므로 **B 의 "막고 있는 항목 수"가 1 이 된다** — 이게 순위 K2 다.

**★리허설 B 가 몇 순위로 제안될지 미리 계산할 수 있다.** 순위는 사전식 네 키(K1 사장님 지시 → K2 막고 있는 수 → K3 이미 착수 → K4 체인 배열 순서)이고 가중치가 없다. 그래서 시작 전에 **`get_work_chain(detail="full")`** 을 돌려 **지금 `ready` 이면서 (source=owner) 이거나 (다른 항목이 기다림) 이거나 (이미 착수)인 항목 수 N** 을 세면, 리허설 B 의 순위는 **N+1** 이다. ★`detail` 을 빼면 안 된다 — 기본 출력은 **항목당 한 줄**이라 `source:` 와 선행 관계가 접혀 있어 K1·K2 를 셀 수가 없다(#1437). 다만 K1 은 세지 않아도 된다: 접힌 출력의 **`★ 사장님 미션 N개` 절 머리줄이 그 수를 이미 준다**. 텔레그램에는 **상위 3건만** 실리므로(`OWNER_CHOICE_LIMIT = 3`):

| N      | 리허설 B 순위 | 어디에 보이나                                                                       |
| ------ | ------------- | ----------------------------------------------------------------------------------- |
| 0~2    | 1~3위         | 텔레그램 **과** 오케 신호 둘 다                                                     |
| 3 이상 | 4위 이하      | 오케 신호에만(텔레그램은 "그 밖에 후보 N건이 더 있습니다"로 개수만 정직하게 밝힌다) |

★**예측한 순위와 실제 순위가 같은지 확인하는 것 자체가 시연의 일부다.** 순서를 예측할 수 있다는 것이 이 계층이 파는 물건이다.

### 2. 실행 순서와 ★관찰 지점

각 줄의 "확인" 칸은 **그 자리가 실제로 그것을 보여주는지 이 티켓에서 직접 열어 확인했는가**다.

| #   | 사장님이 하시는 것                     | 기계가 하는 것                                                                                                                                                                   | ★어디서 보이나                                                                                                                                                                              | 확인                                                                                                                                                              |

### 3. ★멈추는 것도 보이게 — 무엇을 연출하고 무엇을 안 하는가

도는 것만 보이면 시연이 아니라 광고다. 다만 **연출해서는 안 되는 멈춤**이 하나 있다.

**★HALT 를 연출하지 않는 이유는 되돌릴 수 없어서다.** 저장소 전체를 훑어보면 `advanceState.haltReason` 에 **쓰는 자리는 둘**(`tools.ts:2099`·`2341`)인데 **지우거나 되돌리는 자리는 없다**. 렌더러에도 `advanceState` 를 읽거나 쓰는 코드가 한 줄도 없다. 즉 한 번 HALT 된 미션의 자율 진행은 **Firestore 문서를 직접 손대기 전까지 영구 정지**다. 시연을 위해 일부러 거는 것은 되돌릴 계획 없이 스위치를 내리는 것과 같다. 연속 스폰 5 는 형제 티켓 **6건 이상**을 사람 개입 없이 연달아 닫아야 닿으므로, 리허설 규모(미션당 2~3건)에서는 **우연히 걸릴 일도 없다**.

**★리허설 중에는 텔레그램으로 말을 걸지 마라**(7·8·11 의 답장 제외). 미해결 질문이나 미소비 오너 인바운드가 있으면 판정이 `owner-input-pending` 으로 **hold** 되는데, hold 는 `NO_SIGNAL` 이라 **오케 PTY 에도 티켓 활동에도 아무것도 남지 않는다**. 사장님이 보시기에 이 상태는 "루프가 조용히 죽었다"와 구별되지 않는다. 사장님 개입이 자율보다 우선하는 것은 옳은 설계지만, **그 hold 가 보이지 않는 것**은 이 노트가 확인한 관측 공백이다(§한계).

### 5. 정리 절차 — ★순서가 중요하다

```
1) update_work_chain_item(item_id=<C 항목>, close="dropped", reason="리허설 종료")
2) update_work_chain_item(item_id=<B 항목>, close="dropped", reason="리허설 종료")
3) delete_task(task_id=<A1|A2|A3|B1|B2>, mode="hard", confirm=true, reason="리허설 정리")   # 5번
4) rm -rf /tmp/marblo-rehearsal/<날짜>
```

**★1·2 를 3 보다 먼저 해야 한다.** 순서를 뒤집으면 리허설 B 항목이 **후보로 되살아난다.** 항목의 완료 판정은 `mission_label` 로 붙은 티켓들의 보드 상태인데(`evidenceTaskIds` = 명시 `task_ids` ∪ 미션 소속), 티켓을 먼저 지우면 그 집합이 **비고**, 라벨만 있고 티켓 0건인 항목은 "쪼개지 않은 것"이라 `done` 이 될 수 없어 상태가 `ready` 로 돌아간다. 반대로 `close="dropped"` 는 근거 판정보다 **먼저** 읽히므로(`deriveItemState` 의 첫 분기) 그 뒤에 티켓이 사라져도 항목은 계속 닫혀 있다.

**★남는 것 하나 — 미션 문서 2건.** implicit 미션(`missionKind: "implicit"`)을 지우는 경로가 MCP 도구에도 화면에도 없다. 티켓을 지워도 미션 문서는 `completed` 로 남고, 레인 탭의 **"지난 작업 이름표"** 섹션(기본 접힘, 상태 배지 없음, 제목과 티켓 수만)에 제목만 남는다. 지울 수 없으니 **알아볼 수 있게 만든다** — 그래서 라벨을 `[리허설]` 로 시작하게 짓는다. 보드·미션 탭·실행 중 집계에는 애초에 안 들어간다(implicit 은 "실행 중"으로 세지 않는 것이 `lib/missionVisibility.ts` 의 규칙이다).

### 6. 안 될 때 — 증상별로 볼 곳이 다르다

[[closed-loop-one-turn-and-its-stops]] 의 진단표는 **기능이 왜 안 도는가**를 다룬다. 아래는 **리허설이 왜 안 보이는가**로, 겹치지 않는 것만 적는다.

## 왜

**리허설이 필요한 이유는 폐루프가 한 번도 안 돌았기 때문이다.** 폐루프를 가리고 있던 **다섯 층은 2026-09-05 에 전부 착지했다**(#1420 · #1422 · #1425 · #1427 · #1429). 그 층들이 무엇이었고 왜 그렇게 오래 안 보였는지는 [[five-layers-that-hid-the-closed-loop]] 가 답하므로 여기서 다시 쓰지 않는다. 이 노트가 더하는 사실은 하나다 — **고쳐졌다는 증거가 아직 전부 단위 테스트와 코드 실측이다.** 라이브 오케 세션 20,777턴을 훑어 실제 발화는 0건이었다. 저 노트의 교훈(앞 층이 뒷 층의 증상을 만들지 못하게 막고 있었다)을 그대로 받으면 결론도 하나다 — **다섯 번째 층까지 고쳤다는 것 역시 아직 관측이 아니라 추론이다.** 그 추론을 관측으로 바꾸는 것이 이 절차서다.

**리허설이 진짜 작업이면 안 되는 이유**: 처음 켜는 자율 스폰이 무엇을 잘못하면 실물 코드가 함께 다친다. 그런데 안전을 규율("조심해서 하자")로 확보하면 규율을 잊는 첫 번째 순간에 무너진다. 그래서 안전 근거 넷 중 셋을 **구조**로 옮겼다 — 리포지토리 밖 경로, 격리 워크트리, 승인필요 표지의 자율 경로 제외.

**멈춤을 연출하되 되돌릴 수 있는 것만 연출하는 이유**: 시연의 목적은 "이 기계는 아무 데서나 안 선다"가 아니라 "**설 자리에서 서고, 사람이 풀 수 있다**"를 보이는 것이다. 푸는 경로가 없는 정지(HALT)를 시연에 넣으면 시연이 끝난 뒤 그 미션이 영구 정지 상태로 남는다 — 보여준 것보다 남긴 것이 나쁘다.

## 한계 / 정직성

- **이 노트의 절차는 아직 완주된 적이 없다.** 각 관찰 지점이 **그 자리에 있는지**는 코드·로그·화면 소스로 확인했지만(§2 확인 칸), **한 바퀴를 실제로 돌린 관측이 아니다.** 폐루프는 라이브에서 0회 발화했고 이 노트는 그 첫 회를 위한 절차서다. 첫 완주 뒤 실제와 갈리는 것이 나오면 **이 노트가 틀린 것이고 그때 고친다.**
- **비용은 실측 요율 × 실측 턴단가 × 추정 턴수**다. 요율과 턴단가는 로컬 세션 원장 실측(n=68 세션, 오케 20,777턴)이지만 **"에이전트 세션 12턴" · "오케 16~20턴"은 추정**이다. 리허설 태스크의 실제 턴 수 표본이 아직 0건이라 그렇다. 첫 완주 뒤 사용량 탭의 실제 증가분으로 이 칸을 교체해야 한다.
- **비용은 세션 원장 기준이라 앱의 사용량 탭과 완전히 같은 수가 아닐 수 있다.** 같은 요율표·같은 공식을 썼지만 집계 창(세션 파일 vs 롤업)이 다르다. 갈리면 **사용량 탭이 옳다** — 그쪽이 계정 프로브(`account-usage.getAccountRateLimits`)를 읽는 단일 지점이다.
- **`owner-input-pending` hold 는 아무 데도 안 남는다.** 판정이 `NO_SIGNAL` 을 돌려주고 호출자는 빈 문자열을 반환하므로, 오케 PTY·티켓 활동·미션 문서 어디에도 "사장님 입력 때문에 보류했다"가 기록되지 않는다(연속 카운터 리셋만 조용히 일어난다). 이건 조용한 정지 규약의 예외로 남아 있는 자리이고, 리허설 절차가 "텔레그램으로 말 걸지 마라"로 **우회**할 뿐 고친 것이 아니다.
- **셋째 경로는 닫혔지만 잃어버린 전진 신호를 되살리지는 않는다.** 이벤트가 없을 때도 미는 경로가 **2026-09-05 에 머지됐다**(#1427). 다만 그 경로가 미는 것은 **주의 상태의 티켓**(`REVIEW`·`FAILED`·`BLOCKED`·고아)과 체인 READY 항목이지 **유실된 `SIGNAL_ADVANCE` 자체가 아니다.** 즉 A1 이 `DONE` 인데 신호가 안 닿았다면 아무도 그 신호를 다시 만들어 주지 않는다 — 반면 A1 이 `REVIEW` 에서 잊히면 이제 120초 스위프가 집는다. 리허설이 `DONE` 이후에 조용히 멈추면 여전히 사람이 다음 `DONE` 을 만들어 재평가를 유발해야 한다.
- **텔레그램 순위 예측은 워크체인의 현재 상태에 달렸다.** N 은 리허설을 시작하는 시점에 세는 값이고, 리허설 도중 오케가 다른 항목을 체인에 추가하면 바뀐다. 예측이 빗나가면 **`get_work_chain(detail="full")` 을 다시 세어 K1~K4 로 검산**하는 것이 맞고, 순위 규칙을 의심하는 것은 그다음이다.
- **이 노트는 시연 절차이지 기능 설명도 사후 진단도 아니다.** 한 바퀴의 순서는 [[closed-loop-one-turn-and-its-stops]], 왜 안 돌았는지는 [[five-layers-that-hid-the-closed-loop]], 그 계층이 왜 그렇게 생겼는지는 [[autonomous-advance-needs-caps-first]] 가 답한다. 서술이 갈리면 **코드가 옳고**, 그다음은 각 질문을 맡은 노트가 옳다.

## 실제 영향

**코드 무변경. 설정 무변경.** 이 노트는 문서 한 장이고 런타임 동작을 바꾸지 않는다. 플래그(`MISSION_ADVANCE_SIGNAL=on`)는 이 노트 이전에 이미 켜져 있었다(2026-09-05, PR #1420).

절차를 실행하면 **일회성 데이터가 생긴다** — 리허설 티켓 5건, implicit 미션 문서 2건, 워크체인 항목 2건, `/tmp/marblo-rehearsal/` 아래 파일 4개. §5 를 그대로 밟으면 티켓·항목·파일은 사라지고 **미션 문서 2건만 `[리허설]` 접두사가 붙은 이름표로 남는다**(지우는 경로가 없다).

앞으로 자율 루프에 시연 경로를 만들 때 지킬 규칙 셋:

1. **절차서에 화면을 적기 전에 그 화면을 열어라.** 이 노트가 확인한 4건 중 2건은 화면이 파킹돼 있거나 배지가 없어서 **적었으면 거짓이 될 문장**이었다.
2. **되돌릴 수 없는 정지를 시연에 넣지 마라.** 푸는 경로가 코드에 없으면 그건 시연이 아니라 사고다. 넣기 전에 "끝나고 어떻게 되돌리나"를 먼저 답해라.
3. **시연 비용은 티켓이 아니라 오케가 정한다.** 자율 루프의 시연 단가를 낮추려면 작업 모델을 내리는 게 아니라 **오케를 깨우는 이벤트 수**를 줄여야 한다.
