# B2B 팀 층 — 권한이 아닌 경량 분석 라벨

> **한 줄 판정**: ★채택 — 팀은 (C) **경량 팀 라벨**이다. `org_teams`와 결합표 `teamId`로 분석만 그룹핑하며 멤버십·역할·권한의 입력값이 아니다.

## 무엇을 물었나

조직 > 팀 > 프로젝트 > 사람의 분석 관점을 추가하면서, 팀을 새 권한 축이나 자유 입력 문자열로 만들지 않는 방법.

## 결과

| 안 | 판정 | 기각/채택 근거 |
| --- | --- | --- |
| (A) 완전한 팀 엔티티 | 기각 | 팀 초대·역할·게이트는 요구를 넘고, 최근 취약했던 권한 축을 한 벌 더 만든다. 필요해질 때 불변 `teamId` 위에 승격한다. |
| (B) 프로젝트별 자유입력 팀명 | 기각 | 표기 분열이 분석을 조용히 깨고, 개명·이력·향후 멤버십 연결이 불가능하며 외부 프로젝트 멤버에게 내부 편제명이 샐 수 있다. |
| (C) `org_teams` + 결합표 `teamId` | 채택 | id로 정합한 그룹핑, 팀 문서 한 곳의 개명, 추가전용 결합 이력, 권한 표면 0을 함께 얻는다. |

프로젝트는 한 팀 또는 `null`이다. `null`은 숨기지 않는 “미지정” 소계와 배정 CTA로 그린다. 새 결합에서는 “팀 없음”을 명시해 판단을 강제하고, 재배정은 결합표 새 행으로 남긴다.

화면은 새 드릴다운 층을 만들지 않는다. L0 주 표에서 팀별 소계·접기·`?team=` 필터로 접고 L1/L2는 유지한다. 팀 소계는 구성 프로젝트 전수를 볼 수 있는 사람에게만 준다.

## 왜

사장님이 원하는 것은 팀별 분석이지 팀장·팀 권한이 아니다. (C)는 프로젝트를 팀에 넣는 자연스러운 UX는 보존하고, 자유 입력의 데이터 부채와 완전 엔티티의 보안 부채를 피한다. 나중에 유료 요구가 생기면 `org_team_members/{teamId}_{uid}`를 더하되 그때 방침·총계 불변식을 재판정한다.

## 한계 / 정직성

- 2026-09-01 실측상 `org_teams`와 결합표를 포함한 조직 인스턴스는 0건이다. 이는 배포된 팀 운영 기능이 아니라 Phase 1 설계 상태다.
- 팀 라벨은 새 열람자를 만들지 않으므로 Phase 0 게이트와 방침 문안을 바꾸지 않는다. 권한을 주는 승격 시에는 이 전제가 사라진다.

## 실제 영향

문서 변경만. BQ·원장에 `team_id`를 각인하지 않고 조회 시 Firestore 결합표로 그룹핑한다.
