# 배선이 살아 있다는 것은 화면에 나타나는 것으로만 증명된다

> **한 줄 판정**: ★채택 — 소스 문자열도, store 상태도, 성공 ack도 화면을 증명하지 않는다. 초록 테스트 옆에서 기능이 완전히 죽어 있을 수 있고, 실제로 그랬다.

## 무엇을 물었나

"이 기능은 테스트가 있다"가 왜 "이 기능은 동작한다"를 뜻하지 않는가. 초록인데 죽어 있는 것을 어떻게 잡는가.

## 무엇을 했나

링크가 앱 밖으로 새는 버그를 파다가, 그 경로를 지키던 테스트가 **동작이 완전히 깨진 채로 계속 초록**이었던 것을 실측했다. 원인이 층마다 하나씩, 세 번에 걸쳐 나왔다. 셋 다 "단언이 사용자가 보는 것에 닿지 않았다"는 같은 실패다 — 앞의 둘은 단언의 **대상**이, 셋째는 단언의 **범위**가 어긋났다.

## 세 함정

| | 함정 1 — 소스 문자열 가드 | 함정 2 — 고아 표면 |
| --- | --- | --- |
| 무엇을 단언했나 | 구현 파일을 읽어 `expect(source).toContain("...")` | store에 상태가 생겼는가 |
| 왜 초록이었나 | 그 문자열이 파일에 그대로 있으니까 | `addPane()`이 실제로 store를 갱신하니까 |
| 실제로는 | 그 코드가 사용자에게 무엇을 하는지는 한 글자도 안 봤다 | 그 store를 **렌더하는 컴포넌트를 아무도 import 하지 않았다** |
| 사용자가 본 것 | 링크가 안내 없이 OS 브라우저로 나감 | 아무 일도 안 일어남 |

**함정 1**: 소스 문자열 단언은 리팩터마다 깨지면서 정작 의도는 증명하지 못한다. 더 나쁜 건 그 반대다 — **문자열이 그대로면 동작이 뒤집혀도 초록이다.** 이 저장소에서는 `expect(source).toContain("isLocalBrowserPaneUrl(normalized, currentAppOrigin())")` 같은 단언이 통과하는 동안, 그 코드가 일반 외부 링크를 전부 조용히 앱 밖으로 내보내고 있었다.

**함정 2**: 컴포넌트를 아무도 import 하지 않으면 **실패 신호가 하나도 안 뜬다.** 이 사례의 체인은 이랬다 — main이 "탭으로 열어라"를 보내고, 렌더러가 store에 페인을 만들고, 렌더러가 **성공 ack를 보내고**, main이 성공으로 기록한다. 그런데 그 store를 렌더하는 `LayoutView`를 어떤 컴포넌트도 import 하지 않았고 탭 목록에도 그 탭이 없었다. 그래서 화면엔 아무것도 없는데 ack 타임아웃 폴백도 안 돌았다 — **실패로 취급되지 않았으니까.** 컴파일도 린트도 통과한다. 타입이 맞고, export 되어 있고, 자기 자신을 재귀 호출하니 "쓰이는" 것처럼도 보인다.

**함정 3 — 양쪽 다 초록인데 이음매가 비어 있다.** 위 둘을 고친 뒤에도 같은 기능이 다시 죽었다. 이번엔 테스트가 **둘 다 있었다** — 한쪽은 "이 URL 은 어디로 가야 하나"(순수 정책), 다른 쪽은 "탭으로 열라는 메시지를 받으면 화면에 뜨는가"(렌더). 둘 다 정직한 동작 테스트였고 둘 다 초록이었다. 비어 있던 건 **그 사이**였다: 정책이 "탭으로 보내라"를 판단할 때 쓰는 boolean 을 **누구에게 묻는가**. 등록하는 객체와 질문받는 객체가 달라서 답이 항상 false 였고, 두 테스트 중 어느 쪽도 그 질문을 하지 않았다.

일반화하면 — **모듈을 순수 함수로 잘 뺄수록, 잘린 자리(이음매)는 아무 테스트도 갖지 못한다.** 순수 함수 테스트는 입력을 **직접 준다.** 그래서 "실제 시스템이 그 입력을 어떻게 계산하는가"는 영원히 검증되지 않는다. 계약이 boolean 하나처럼 작을수록 눈에 안 띈다.

## 규칙

| 규칙 | 구체적으로 |
| --- | --- |
| 단언 대상은 **사용자가 보는 값** | 구현 소스를 읽는 테스트를 쓰지 않는다. 필요하면 결정 로직을 순수 함수로 빼고 **그 함수를 호출해** 결과를 단언한다 |
| 새 UI 표면은 **실제로 렌더해서** 확인한다 | store에 값이 생겼다까지가 아니라, **렌더한 화면에 그 값이 나타나는 것**까지 단언한다(예: 라우팅된 URL이 주소창에 보이는가) |
| 성공 신호를 마지막에 보낸다 | ack·완료 보고는 실제로 해낸 뒤에 보낸다. 먼저 보내면 실패가 성공으로 기록되고 폴백이 죽는다 |
| 시간은 주입한다 | 타임아웃 폴백은 기다리지 말고 주입 시계로 경계 양쪽(직전 미발동 / 직후 발동)을 단언한다 |
| 도달 불가를 의심한다 | 예외 목록·분기가 있으면 **거기까지 실제로 도달하는지**를 테스트한다. 도달 못 하는 분기는 있으나 마나다 — [[in-app-link-routing]]의 정규화 함정이 그 사례다 |
| 순수 함수의 **입력도** 테스트한다 | 결정을 순수 모듈로 뺐으면, 실제 시스템이 그 인자를 어떻게 계산하는지도 따로 못박는다. 특히 `hasX` 같은 boolean 인자는 "누구에게 물었나"가 통째로 숨는 자리다 |
| 이음매를 한 번은 **끝에서 끝까지** 돈다 | 양쪽 절반이 각각 초록이어도 이어 붙인 것이 도는지는 별개다. 실제 셸을 마운트해 등록부터 화면까지 한 테스트로 통과시킨다 |

## 왜

세 함정 모두 "테스트가 있다"는 안심을 주면서 그 안심의 근거만 없다. 그리고 셋 다 **정상 경로에서 예외가 안 뜬다** — 예외가 뜨면 사람이 알아차렸을 것이다. 조용히 성공으로 보고되는 실패가 가장 오래 산다. GUI를 띄워 확인할 수 없는 환경([[no-live-gui-verify]])에서는 이 규율이 유일한 방어선이다.

## 한계 / 정직성

- 렌더 테스트는 jsdom이라 실제 네이티브 뷰(`WebContentsView`)의 배치·표시는 증명하지 못한다. 증명하는 것은 "이 표면이 마운트되어 있고 라우팅된 값이 거기 도달한다"까지다. 그 위는 실화면 확인이 필요하다.
- "화면에 나타나는 것까지 단언" 이 모든 회귀를 잡지는 않는다. 잡는 것은 **표면이 통째로 죽어 있는** 종류다. 앞의 두 사례가 그 종류였다.
- 함정 3의 이음매 테스트는 셸의 무거운 이웃 컴포넌트를 대역으로 바꾼 채 돈다. 증명하는 것은 "셸이 마운트되면 등록이 나가고, 들어온 메시지가 주소창까지 도달한다"까지다. main 쪽 Electron 배선(어떤 webContents 가 핸들러를 발화시키는가)은 순수 함수 테스트가 결정만 덮고, 그 아래 세 줄의 접착은 여전히 실화면 확인 몫이다 — [[no-live-gui-verify]].
- 함정 1의 실측은 이 저장소의 한 파일에서 나왔다. 소스 문자열 단언이 언제나 무가치하다는 주장은 아니다 — Electron main처럼 테스트에 import 할 수 없는 모듈에서 쓰이던 우회였다. 그 경우의 옳은 답은 문자열 단언이 아니라 **결정 로직을 import 가능한 순수 모듈로 빼는 것**이다.

## 실제 영향

이음매를 끝에서 끝까지 도는 테스트를 추가했다 — 실제 셸을 마운트해 등록이 나가는지 보고, main 이 보내는 메시지를 밀어 넣어 라우팅된 URL 이 주소창에 나타나는 것까지 한 흐름으로 단언한다. 그리고 그 boolean 이 "누구에게 물어야 하나"를 별도 순수 함수로 빼서 따로 못박았다.

소스 문자열 가드 테스트를 전량 동작 테스트로 교체했다. 라우팅 결정을 Electron 의존 없는 순수 함수로 빼서 main은 얇은 어댑터가 되고, 테스트가 출하 경로를 그대로 돈다. 렌더러 쪽은 탭 컴포넌트를 실제로 렌더해 라우팅된 URL이 주소창에 나타나는 것까지 단언한다. ack는 페인 생성·탭 전면화 뒤 마지막에 보낸다.
