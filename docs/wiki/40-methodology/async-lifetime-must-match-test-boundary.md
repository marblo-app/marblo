# 테스트 경계와 비동기 작업의 수명을 맞춰라

> **한 줄 판정**: ★채택 — 간헐 실패의 원인은 대부분 "테스트가 틀렸다"가 아니라 **테스트의 시작·끝과 비동기 작업의 수명이 어긋난 것**이다. 어긋남은 대칭인 두 얼굴로 나온다: **앞쪽 어긋남**(작업이 끝나기 전에 읽어서 단언이 틀린다)과 **뒤쪽 어긋남**(작업이 테스트보다 오래 살아 워커 teardown 을 깬다). 2026-09-04 CI verify 를 무작위로 빨갛게 만들던 2건이 정확히 이 둘이었고, 둘 다 재시도가 아니라 **수명 정렬**로 고쳤다. ★뒤쪽 어긋남은 **테스트 8,795개가 전부 통과해도 job 이 exit 1** 이 되므로, 통과 수를 보고 초록이라고 판단하면 안 된다.

## 무엇을 물었나

변경과 무관한 PR 이 CI 에서 무작위로 막힌다. 테스트가 틀린 것인가, 코드가 틀린 것인가, 아니면 둘 다 아닌가.

## 무엇을 했나

`continue-on-error` 제거([[ci-empty-steps-is-billing]] 의 2026-09-03 갱신) 이후 드러난 실패 2건을 각각 재현했다. CI 러너(ubuntu-latest 2코어)가 개발 맥(12코어)보다 느린 것이 방아쇠라고 보고, CPU 를 포화시켜 러너를 흉내 냈다.

## 결과 (수치)

| 지표                                  | 값                                                                            |
| ------------------------------------- | ----------------------------------------------------------------------------- |
| 재현 단위                             | **vitest 실행 1회** (표본: 같은 파일 반복 실행)                               |
| 앞쪽 어긋남, 부하 없음                | 3회 중 **1회** 실패                                                           |
| 앞쪽 어긋남, CPU 포화                 | 6회 중 **1회** 실패 — CI 에러 문구와 **문자 그대로 동일**                     |
| 앞쪽 어긋남, 고친 뒤 같은 부하        | **10/10 통과**                                                                |
| 뒤쪽 어긋남, 테스트 종료 후 잔여 로그 | 수정 전 **6/6 (100%)** → 수정 후 **0/5 (0%)**                                 |
| 뒤쪽 어긋남의 CI 표면                 | `Test Files 549 passed` · `Tests 8795 passed` · `Errors 1 error` · **exit 1** |
| 전체 스위트 회귀 확인                 | 553파일 / 8,831테스트 **연속 5회** 전부 초록, Errors 0                        |

두 어긋남의 형태:

```
앞쪽 — 배달의 "시작"을 기다리고 "끝"을 단언했다
  handleUpdate():  injectMessage() → (awaited 파일 I/O) → 상태 기록
  테스트:          ↑ 여기서 신호를 받고            ↑ 여기 결과를 단언
  느린 러너에서 가운데 I/O 가 폴링 간격(5ms)을 넘기면 단언이 작업 도중에 실행된다.

뒤쪽 — write-behind 쓰기가 afterEach 보다 오래 살았다
  afterEach 가 tmp 디렉터리를 지운다 → 예약돼 있던 쓰기가 ENOENT
  → catch 가 console.error → vitest 의 onUserConsoleLog RPC
  → 워커가 rpc 를 닫는 중 도착 → EnvironmentTeardownError
```

고치는 법도 대칭이다:

| 어긋남 | 고치는 법                                                                                | ★하면 안 되는 것                     |
| ------ | ---------------------------------------------------------------------------------------- | ------------------------------------ |
| 앞쪽   | **단언 대상과 같은 사실**을 기다린다. 대리 신호(호출됐다)가 아니라 확정된 상태(기록됐다) | 단언을 느슨하게 하기, `sleep` 늘리기 |
| 뒤쪽   | 정리하기 **전에** 진행 중인 작업을 settle 한다                                           | 로그 죽이기, unhandled 무시 설정     |

## 왜

테스트는 "관측 가능한 신호"로 비동기 작업을 기다리는데, 그 신호가 작업의 **시작**에 붙어 있으면 작업의 **끝** 상태를 단언할 자격이 없다. 빠른 기계에서는 시작과 끝 사이가 폴링 간격보다 짧아 우연히 통과하고, 느린 기계에서 갈라진다 — 그래서 "로컬에선 되는데 CI 에서만" 이 된다. 뒤쪽도 같은 뿌리다: 예약만 하고 반환하는 write-behind 는 호출자 시점에서 끝난 것처럼 보이지만 실제 수명은 테스트보다 길고, 테스트가 그 작업의 **자원**(디렉터리·전역·모듈)을 회수하면 작업은 실패하며 로그를 친다. 그 로그가 워커 경계를 넘으면 실패한 테스트가 하나도 없는데 실행 전체가 빨개진다.

## 한계 / 정직성

- **재시도(retry)로 덮으면 안 된다.** CI 에 자동 retry 를 넣으면 이 어긋남과 진짜 회귀가 같이 가려진다. `continue-on-error` 를 되살리는 것과 같은 함정이다.
- 수치는 **이 저장소의 로컬 재현**이다. CPU 포화는 2코어 러너의 근사이지 동일 환경이 아니다. CI 원본 실패 로그(PR #1405 · #1406)와 대조해 **에러 문구가 일치**하는 것까지가 확인된 범위다.
- 같은 부하 실험에서 `tests/unit/intent-recorder.test.ts` 가 30초 타임아웃으로 넘어갔는데, 그건 이 노트의 어긋남이 아니라 **unit 스위트 안에서 진짜 Chromium 을 띄우는 것**이 원인이다. 부류가 달라 이 노트가 다루지 않으며, CI 에서 실제로 실패한 로그는 아직 없다.
- **문구가 갈리면 CI 실행 로그 원문과 현재 코드가 옳다.**

## 2026-09-05 확인 — 이 노트를 실제로 낡게 만드는 `build.yml` 변경은 무엇인가

2026-09-05 PR #1432 가 `.github/workflows/build.yml` 을 고치면서 위키 신선도 게이트가 이 노트를 "낡음 후보"로 지목했다. 대조한 결과 **이 노트의 판정도 인용도 그대로 유효**하다. 스킵 대장으로 덮는 대신, 왜 무관한지와 **무엇이면 진짜 관계있는지**를 여기 적어 다음 사람이 같은 위양성을 즉시 분류하게 한다.

이 노트가 `build.yml` 을 인용하는 지점은 **파일 전체가 아니라 두 스텝의 짝**이다:

1. `Test` 스텝의 `set -o pipefail` — `tee` 가 vitest 종료코드를 세탁하지 못하게 막고, 동시에 로그 사본을 `${RUNNER_TEMP}/vitest.log` 로 남긴다.
2. 실패 후에만 도는 **순수 보고 스텝**("WHERE DID IT COME FROM") — 그 로그에서 `This error originated in "<file>"` 한 줄을 뽑아 `::error::` 로 요약 맨 위에 올린다. 8,800줄 밑에 묻힌 한 줄이 이 노트의 **뒤쪽 어긋남**을 찾는 유일한 실마리이기 때문이다.

PR #1432 는 `Typecheck` 와 `Test` **사이**에 `npm run build:mcp` 스텝 하나를 끼웠다. 비동기 작업도, 테스트도, teardown 표면도 늘리지 않았고, 위 두 스텝과 `pipefail`·`tee` 를 건드리지 않았다. 신선도 게이트가 **파일 단위**로 걸었을 뿐이다.

**앞으로 이 노트를 진짜로 낡게 만드는 `build.yml` 변경은 셋뿐이다:**

- (a) `Test` 스텝의 `set -o pipefail` 이나 `tee` 를 바꿔 **종료코드나 로그 사본이 사라질 때** — 그 순간 위 2번 스텝이 읽을 것이 없어진다.
- (b) 발원지 보고 스텝을 **지우거나 조건을 바꿀 때** — 뒤쪽 어긋남이 다시 "묻힌 한 줄"로 돌아간다.
- (c) `continue-on-error` 나 **자동 retry 를 되살릴 때** — 이 노트가 "한계 / 정직성"에서 명시적으로 금지한 것이다. 이 어긋남과 진짜 회귀가 같이 가려진다.

그 밖의 `build.yml` 변경(스텝 추가·삭제, 설치 방식, 트리거, docs-only 단락)은 이 노트와 무관하다.

## 실제 영향

테스트 코드와 CI 설정 변경. 제품 동작 무변경 — 폴러의 프로덕션 경로는 건드리지 않았다.

앞으로의 규칙:

- **단언할 상태를 그대로 기다린다.** "함수가 호출됐다"는 "그 함수의 결과가 기록됐다"의 대리물이 아니다 ([[wiring-proven-on-screen]] 과 같은 축 — 중간 신호를 최종 증거로 쓰지 않는다).
- **폴링 헬퍼는 타임아웃에 throw 한다.** 조용히 빠져나가면 지연이 엉뚱한 단언 불일치로 둔갑해, 읽는 사람이 기다림 대신 단언을 의심한다.
- **테스트보다 오래 사는 비동기 작업을 남기지 않는다.** write-behind·타이머·미완 rpc 는 자원을 회수하기 전에 settle 한다. settle 훅이 없으면 그 훅이 없는 것 자체가 구멍이다.
- **테스트 파일은 자기가 건드리는 전역 자원을 격리한다.** 환경변수로 경로가 갈리는 저널·스풀은 tmp 로 돌린다 — 안 걸면 실제 홈을 오염시키고, 워커들이 한 파일을 놓고 경합해 어긋남 창을 넓힌다.
- **빨간 PR 을 읽는 순서에 한 칸이 늘었다**: `steps` 길이 0 인가([[ci-empty-steps-is-billing]]) → 체크가 목록에 있는가([[required-check-must-report]]) → **실패한 테스트가 있는가**(없는데 빨가면 `Errors` 줄을 본다) → 그다음이 진짜 테스트 실패다.
