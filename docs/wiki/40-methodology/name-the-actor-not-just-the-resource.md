# 계수기를 자원 키로만 묶으면 "혼자 계속 진다"와 "우리끼리 싸운다"가 구별되지 않는다

> **한 줄 판정**: ★채택 — 계수기를 **자원**(프로젝트·채널·봇) 키로만 묶으면, 그 자원을 다루는 **행위자가 둘**일 때 둘이 같은 칸에 겹쳐 쓴다. 그래서 "행위자 하나가 외부 경쟁자에게 계속 진다"와 "우리 행위자 둘이 서로를 걷어찬다"가 **완전히 같은 시계열**로 찍힌다. 실측 2건에서 이 모호함이 각각 조사 **3회**를 추론으로 끝냈고(1건), **사용자에게 없는 책임을 지웠다**(2건 — 안내문이 오케의 점유를 사장님 초안으로 단정). 한 칸(행위자 ID)이면 갈린다. ★모르는 경우를 담을 값(`unknown`)도 같이 둔다.
>
> **★2026-09-05 개정 — 행위자 ID 는 자기 범위 밖을 못 가른다.** 위 판정에 행위자 축을 넣고 하루 뒤, 같은 증상이 **4번째**로 돌아왔다. 넣은 행위자 ID(`loopId` = pid + 자원 + 세대)의 유효 범위가 **한 프로세스**였기 때문이다. 실제 경쟁자는 **다른 맥의 같은 앱**이었고, 그것은 프로세스 밖이므로 계측에 "밖"으로만 찍힌다 — 즉 "안이냐 밖이냐"는 갈렸지만 갈린 답이 **틀렸다**. 일반화: **행위자 ID 의 유효 범위가 자원의 경합 범위보다 좁으면, 그 바깥의 경쟁자는 전부 한 칸("밖")으로 뭉개진다.** 축을 넣을 때는 값만이 아니라 **범위**를 자원의 경합 범위에 맞춰야 한다.

## 무엇을 물었나

시계열 저널이 이미 있는데도 왜 원인이 안 잡히나. 표본에 무엇이 더 있어야 "관측했다"가 되는가.

## 무엇을 했나

3회 연속 실패한 조사 1건을 사후 분해했다. 저널 필드 목록과, 그 필드들로 **구별 불가능한 두 상태**를 대조했다. 사건의 수치는 원본에 있고 여기서는 재사용 가능한 구조만 뽑는다.

## 결과 (수치)

### 구별되지 않던 두 상태

텔레그램 `getUpdates` 는 봇당 **단일 소비자**다. 소비자가 둘이면 HTTP 409 가 난다. 저널의 모든 필드가 `projectId` 키 하나로만 묶여 있었다.

| 저널이 본 것                     | 상태 A: 우리 루프 1개가 **외부** 경쟁자에게 진다 | 상태 B: 우리 루프 **2개**가 서로를 걷어찬다 | ★상태 C: **다른 기기**의 우리 앱과 걷어찬다 |
| -------------------------------- | ------------------------------------------------ | ------------------------------------------- | ------------------------------------------- |
| `loopRunning`                    | `true`                                           | `true` (둘 다 등록돼 있진 않아도 true)      | `true`                                      |
| `consecutivePollErrors` 단조증가 | ✅                                               | ✅                                          | ✅                                          |
| `pollError = http-409`           | ✅                                               | ✅                                          | ✅                                          |
| 가끔 성공해 리셋                 | ✅                                               | ✅                                          | ✅                                          |
| **행위자 축 넣기 전 구별 가능?** | ❌ **불가**                                      | ❌ **불가**                                 | ❌ **불가**                                 |
| **`loopId` 넣은 뒤 구별 가능?**  | ✅ ("밖")                                        | ✅ (`concurrentLoops > 1`)                  | ❌ **A 와 똑같이 "밖"으로 찍힌다**          |

세 상태는 **고치는 방법이 전부 다르다**(밖을 찾는다 / 이 앱 안을 고친다 / 기기 사이에 소유권을 정한다). 행위자 축은 A·B 는 갈랐지만 **A 와 C 를 못 갈랐다** — `loopId` 가 pid 를 담고 있어 프로세스 경계에서 끝나기 때문이다. 자원(봇)의 경합 범위는 **계정 전체**인데 행위자 ID 의 범위는 **프로세스**였다. 이 범위 불일치가 4번째 조사를 만들었다.

### 비용

| 항목                                     | 값                                                     |
| ---------------------------------------- | ------------------------------------------------------ |
| 같은 증상으로 돈 조사                    | **4회** (#1397 · #1406 · #1415 · 2026-09-05 본건 개정) |
| 그 조사들이 세운 가설                    | App Nap → 화면 잠금 → "배달 주체와 저널 주체가 다르다" |
| 실측으로 살아남은 가설                   | **0개**                                                |
| 원인 특정에 필요했던 추가 필드           | **1개** (행위자 ID) — 단, ★그 ID 의 **범위**가 맞아야  |
| 그 필드 없이 소비자 중복을 볼 수 있는 곳 | 패킷 캡처뿐                                            |

표본: 사건 n=1 의 사후 분해다. 통계가 아니라 **구조**가 근거다 — 같은 모양은 단일 소비자/단일 리더/단일 라이터 계약을 쓰는 모든 곳(락, 큐 컨슈머, 웹훅, 폴러, 소켓)에서 재현된다.

### 두 번째 실측 — 같은 모양이 **안내문**으로 새어 나갔다 (2026-09-05)

첫 사례는 계수기가 행위자를 안 적어 **조사**가 막힌 건이었다. 두 번째는 같은 누락이 조사에서 끝나지 않고 **사용자에게 잘못된 지시**로 나갔다.

컴포저(오케 터미널 입력줄)의 점유 상태를 저널과 안내문이 `composer: "occupied"` 한 글자로만 적었다. 그 칸은 **자원의 상태**이지 **누가 점유했는지**가 아니다. 점유자는 최소 셋이다 — 사람이 친 미제출 초안 / 오케가 턴을 도는 동안 차례를 기다리는 우리 글 / 제출에 실패해 남은 우리 글. 셋은 사람이 할 일이 **정반대**인데(치워야 한다 / 아무것도 안 해도 된다 / 우리가 치운다) 코드는 전부 첫 번째로 안내했다.

| 실측 (`~/.marblo/telegram-route-health.jsonl`) | 값                                                    |
| ---------------------------------------------- | ----------------------------------------------------- |
| 구간                                           | 09:03:06 → 09:07:06                                   |
| 저널이 적은 것                                 | `hold={refusal:"pty-refused", composer:"occupied"}`   |
| `heldMs`                                       | 29 725 → 209 728                                      |
| `attempts`                                     | 10 → 65                                               |
| 결말                                           | `delivered` — **아무도 아무것도 안 했는데** 전달됨     |
| 실제 점유자                                    | 오케(턴 처리 중). 사람은 키보드 앞에 없었다           |
| 60초에 나간 안내문                             | "입력창에 제출되지 않은 글이 남아 있습니다 … 제출하거나 지우면 풀립니다" |
| 그 안내가 시킨 일                              | **존재하지 않는 초안 찾기**                           |

행위자 축을 안 적은 대가가 첫 사례에서는 조사 3회였고, 여기서는 **사용자에게 없는 책임을 지운 것**이었다. 관측이 모호하면 그 모호함은 로그에만 머물지 않는다 — 그 값을 문장으로 바꾸는 코드가 임의로 한쪽을 골라 단정한다.

## 왜

계수기의 키는 **누가 썼는지가 아니라 무엇에 대한 것인지**만 기록한다. 행위자가 하나뿐이라는 가정이 참인 동안에는 이 둘이 같아서 문제가 없다. 그런데 **그 가정이 깨졌는지를 확인하려고 저널을 보는 순간**, 저널은 그 가정을 이미 전제하고 있어서 답을 줄 수 없다. 자기가 검증해야 할 것을 전제로 깔고 있는 관측이다.

게다가 두 행위자가 같은 칸에 쓰면 서로의 흔적을 지운다 — 한쪽의 성공이 다른 쪽의 실패 연속을 리셋해 버려서, 시계열이 실제보다 건강해 보인다.

## 한계 / 정직성

- n=2 다(2026-09-04 폴러 루프 정체성, 2026-09-05 컴포저 점유자). 둘 다 사후 분해이고, 빈도를 주장하지 않는다. 주장하는 것은 "이 모호함은 조용하므로 사전에 한 칸 넣는 것이 싸다"이다.
- 행위자 ID 를 넣는다고 원인이 자동으로 나오지는 않는다. 나오는 것은 **"내 범위 안이냐 밖이냐"** 한 갈래뿐이고, ★그 "밖"은 **아직 이름이 없는 덩어리**다. 범위를 넓히기 전에는 그 덩어리 안에서 더 갈 수 없다.
- **★관측 완료(2026-09-05, 위 미확정 항목의 결말).** 넣은 계측은 원인을 지목하지 **못했다.** `concurrentLoops` 는 계속 1이었고 `lastPollLoopId` 도 안 흔들렸다 — 즉 계측은 "밖"이라고 정확히 말했고, 그 말이 맞았는데도 소용이 없었다. 실제 경쟁자는 **다른 맥에서 도는 같은 앱**이었기 때문이다. 계측이 틀린 게 아니라 **해상도가 자원의 경합 범위에 못 미쳤다.**
- 그래서 이 노트의 원래 결론은 **틀리지 않았지만 불완전했다.** "행위자 축을 넣어라"는 유효하고, 빠진 절반이 "그 축의 범위를 자원의 경합 범위에 맞춰라"다.
- 두 번째 사례의 사유 판정은 **우리가 볼 수 있는 신호 안에서만** 갈린다. 앱이 재시작된 뒤 남아 있던 초안처럼 입력측 증거가 없는 점유는 `unknown` 으로 남고, 그때는 지목 대신 확인을 청한다. 그 경계가 얼마나 자주 걸리는지는 **아직 관측 전이다.**
- **수치가 갈리면 원본이 옳다.**

## 실제 영향

코드 변경 있음. 폴러의 route health 와 시계열 저널에 행위자 축을 넣었다 — `loopId`(pid + 자원 + 세대), `concurrentLoops`, `loopStarts`, `lastPollLoopId`, `lastDeliveredLoopId`. `concurrentLoops > 1` 이거나 `lastPollLoopId` 가 두 값 사이를 오가면 그게 곧 "안"이고, 둘 다 아니면 "밖"이다. 토큰·chatId·본문은 담지 않는다(pid + 자원키 + 세대번호뿐).

같은 커밋에서 중복 소비자가 생기던 경로도 닫았다: **단일 소비자 가드는 등록 항목이 아니라 자원의 실제 점유 수명을 덮어야 한다.** 은퇴를 요청받은 폴러가 진행 중인 롱폴을 25초까지 계속 물고 있는데 등록에서는 먼저 지워졌고, 그 창에서 두 번째 폴러가 떴다.

**★2026-09-05 후속 커밋.** 범위를 자원에 맞췄다: 봇 소유권을 **기기 간** 리스로 확정한다(프로젝트 문서에 `holderId`·`hostLabel`·`tokenHash`·`renewedAt` — ★봇 토큰 원문이 아니라 해시만, 토큰은 기기 간 동기화되지 않기 때문). 리스는 90초 만료·30초 갱신이라 앱이 죽거나 맥이 잠들면 자연 만료되어 다른 기기가 인수한다 — 사람이 손으로 푸는 상태를 만들지 않는다. ★그리고 리스는 **fail-open** 이다: 리스를 읽거나 쓰지 못하면 폴링을 막지 않고 진행한다(리스 때문에 채널이 영영 죽는 경로는 겹쳐서 절반 유실되는 지금보다 나쁘다).

같은 커밋에서 **관측을 콘솔 밖으로 꺼냈다.** 이전까지 409 진단은 `log.warn` 하나였고 사용자는 이 상황을 전혀 볼 수 없었다 — 두 맥이 12초 주기로 서로를 강탈하는 동안 화면의 배지는 "연결"로 남아 있었다. 이제 경합이 구조화된 상태로 나가고, "다른 마블로 기기가 쓰는 중"과 "마블로가 아닌 무언가가 폴링 중"이 **다른 문구**로 갈린다(할 일이 정반대다: 기다린다 / 찾아서 끈다).

두 번째 사례에서도 같은 축을 넣었다(2026-09-05). 컴포저 점유에 **점유자** 칸(`OccupancyCause`)을 붙였다 — `human-draft` · `orchestrator-busy` · `self-injected` · `awaiting-choice` · `unknown`. 판정 근거는 이미 코드가 알고 있던 것뿐이다: PTY 입력의 출처(사람 키 vs 우리 주입), 마지막 busy 신호 이후 경과, 우리 write 의 제출 결말. 그 축이 생기자 세 가지가 따라왔다.

1. **문구가 갈렸다.** 오케가 도는 중이면 "차례를 기다리는 중입니다. 하실 일은 없습니다" 로 나간다.
2. **임계값이 갈렸다.** 사람이 할 일이 있는 보류만 60초에 알린다. 조용한 보류는 10분이다 — 위 실측의 정상 보류가 약 4분이었으므로, 60초 알림은 정상 동작 중에 나가고 있었다.
3. **자기교착이 닫혔다.** 점유자가 우리로 판정되면(오케가 조용하고, 우리 write 가 `unconfirmed` 로 끝났고, 그 뒤 사람 입력이 없을 때만) 우리가 CR 한 번으로 마저 제출해 치운다. 지우지는 않는다 — 그 글은 이미 '전달됨'으로 기록된 메시지라 지우면 그때 진짜 유실된다.

**★2026-09-05 정정 — 그 셋 중 무엇도 그날의 원인이 아니었다.** 같은 날 저녁 저널을 다시 폈더니, 27분·494회 동안 막혀 있던 실제 구간의 사유는 `human-draft` 도 `orchestrator-busy` 도 `self-injected` 도 아니었다 — `idleSec` 이 303→1803 으로 단조 증가했고(오케는 조용) `submit.unconfirmed = 0` 이었다(우리 찌꺼기도 없음). 즉 위 세 갈래는 **전부 반증됐고** 남은 것은 `unknown`, 그리고 그 `unknown` 이 **영원히 안 늙는다**는 사실이었다. 점유자를 적은 것은 옳았지만 그것만으로는 교착이 안 풀렸다 — 빠진 절반은 [[staleness-meter-must-not-be-driven-by-what-it-measures]] 에 있다. ★교훈 하나가 더 붙는다: **행위자 축을 넣었다고 원인을 잡은 것이 아니다.** 새 축이 후보를 반증해 주면, 그 다음은 남은 값(`unknown`)을 진짜로 조사해야 한다.

★그리고 갈리지 않는 경우를 위해 `unknown` 을 남겼다. 근거가 없으면 사람 탓으로 단정하지 않는다. 첫 사례의 교훈이 "행위자를 적어라" 였다면, 여기서 하나 더 붙는다 — **행위자를 모를 때 아무나 지목하지 마라.**

앞으로 "단일 X" 계약(단일 소비자·단일 리더·단일 라이터)이나 **단일 점유 자원**(컴포저·락·슬롯)을 쓰는 곳에서는 **네 가지**를 같이 확인한다.

| 1   | 계수기·로그가 **행위자**를 적나, 자원만 적나                                  | 위반을 관측할 수 없다 — 추론만 남는다                     |
| 2   | 중복 방지 가드가 자원의 **실제 점유 수명**을 덮나, 등록 항목만 덮나           | 등록에서 지워진 뒤에도 점유가 남는다                      |
| 3   | ★행위자 ID 의 **유효 범위**가 자원의 **경합 범위**를 덮나 (pid? 기기? 계정?)  | 범위 밖 경쟁자가 전부 "밖" 한 칸으로 뭉개진다 — 본건의 4회차 |
| 4   | 행위자를 **모를 때** 표현할 값이 있나                               | 문장을 만드는 코드가 임의로 한쪽을 단정한다        |

3번의 자문 형태: "이 자원을 두고 싸울 수 있는 가장 먼 상대는 어디 있나?" 답이 pid 밖이면 행위자 ID 에 pid 만 넣어서는 안 된다.
