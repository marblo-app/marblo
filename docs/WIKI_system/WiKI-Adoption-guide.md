# 지식위키 등록가이드 — 새 프로젝트 적용 절차

> [WIKI-SYSTEM.md](WIKI-SYSTEM.md)(사양) + [WIKI-SKILLS.md](WIKI-SKILLS.md)(스킬 4종)을 **처음 보는 프로젝트에 얹는** 절차서.
> 이 문서만 따라가면 도입이 끝난다. 사양서는 "왜"를, 이 문서는 "어떤 순서로"를 담는다.

| 항목   | 값                                                                                   |
| ------ | ------------------------------------------------------------------------------------ |
| 소요   | 1단계 30분(판단) · 2단계 1시간(구축) · 3단계 30분(등록) · 4단계는 지속               |
| 전제   | 마크다운 문서 30건 이상 · git 리포 · Python 3.9+                                     |
| 리스크 | **없음** — 전 과정이 새 서브트리 생성 + 기존 파일 읽기뿐. 기존 문서·코드·설정 무변경 |

---

## 0. 도입 판단 — 지금 넣을 때인가

| 신호                                           | 판정                                                |
| ---------------------------------------------- | --------------------------------------------------- |
| 마크다운 문서 **30건 미만**                    | ❌ 아직. 파일 목록으로 충분하다                     |
| 문서는 많은데 **전부 한 사람 머릿속에서 관리** | ⚠️ 지금이 마지막 기회다. 그 사람이 빠지면 복구 불가 |
| **같은 수치가 문서마다 다르다**                | ✅ 도입                                             |
| **"그거 전에 해봤나?"에 아무도 답 못 한다**    | ✅ 도입 — 기각 원장(§2.5-A)이 이 문제 전용 장치다   |
| 에이전트가 문서를 읽고 작업한다                | ✅ 도입 — 그래프가 곧 에이전트 컨텍스트다           |

★**도입하지 말아야 할 경우**: 문서가 곧 대규모 리팩터로 갈릴 예정이면 그 뒤에 한다. 위키는 원본을 링크하는데, 원본 경로가 통째로 바뀌면 앵커를 다시 깔아야 한다.

## 1단계 — 매핑 (판단, 30분)

★**파일을 만들기 전에** 아래 6가지를 정한다. 정하지 않고 시작하면 폴더를 두 번 판다.

### 1.1 도메인 슬롯 6개 이름 짓기

사양서 §1.2 의 **고정된 역할**에 프로젝트 언어를 입힌다.

| 슬롯 | 역할(고정) | 물어볼 질문                              |
| ---- | ---------- | ---------------------------------------- |
| `00` | 기반       | "나머지 전부가 전제하는 것이 뭐지?"      |
| `10` | 주력       | "지금 실제로 돌아가는 게 뭐지?"          |
| `20` | 제약       | "주력을 뭐가 막고 있지?"                 |
| `30` | 탐구       | "판정이 남는 시도가 뭐지?" ★대개 가장 큼 |
| `40` | 방법론     | "무엇을 근거로 믿기로 했지?"             |
| `50` | 운영       | "바깥과 부딪힌 기록이 뭐지?"             |

▶ 예시 매핑

| 프로젝트 유형       | `00`         | `10`       | `20`          | `30`           | `40`        | `50`       |
| ------------------- | ------------ | ---------- | ------------- | -------------- | ----------- | ---------- |
| 리서치/퀀트 랩      | foundations  | strategies | risk-gates    | experiments    | methodology | live-ops   |
| SaaS 제품           | architecture | features   | constraints   | experiments    | quality     | operations |
| 데이터 플랫폼       | data-model   | pipelines  | governance    | investigations | validation  | incidents  |
| 오픈소스 라이브러리 | concepts     | api        | compatibility | rfcs           | testing     | releases   |

★슬롯이 비면 만들지 않는다. 4개로 시작해도 된다.

### 1.2 탐구(`30-`) 하위 도메인 후보

기존 문서를 **"무엇을 건드렸나"** 축으로 묶는다. **시간·담당자·판정값 축 금지**(§1.3).
★한 묶음에 3건 미만이면 폴더를 파지 않는다.

### 1.3 원장(source-of-truth ledger) 지정

프로젝트에 **"결론이 모이는 단일 문서"** 가 있는가?

- 있으면 → **P2 대상**. 위키는 그 조항을 **인용·요약만** 하고 절대 편집하지 않는다. 조항 앵커 표기(`§x-y` 등)를 정한다.
- 없으면 → 생략. 위키 노트 자체가 결론의 집이 된다.

### 1.4 Evidence 디렉터리 지정

원시 산출물(리포트·로그·감사·실험결과)이 쌓이는 경로. 노트의 `## Evidence` 가 여길 가리킨다.
없으면 지금 만든다 — ★**노트 안에 원시 산출물을 넣지 않기 위해** 필요하다(중복 최소 원칙).

### 1.5 태그축 정하기

| 네임스페이스 | 정할 것                                         |
| ------------ | ----------------------------------------------- |
| `domain/`    | 1.1 의 6개와 1:1 (자동)                         |
| `topic/`     | ★**폴더가 표현 못 하는 교차축.** 10~20개면 충분 |
| `verdict/`   | 탐구 성격이면 4값 그대로. 아니면 **생략**       |
| `method/`    | 판정을 만드는 기법 이름들                       |
| (고유축)     | 시장·플랫폼·고객군·자산군 등 프로젝트 고유 축   |

### 1.6 정직성 규약 인스턴스화

세 가지를 프로젝트 언어로 답한다.

1. **"무엇이 죽었는지"가 이 프로젝트에선 무슨 형태인가** — 폐기된 기능? 기각된 가설? 롤백된 아키텍처?
2. **기각 사유코드 목록** — 사양서 §2.5-A 의 `C1`~`C0` 중 남길 것 + 프로젝트 고유 코드. ★각 코드에 **해금 조건**을 반드시 붙인다
3. **인용 규율이 필요한가** — 외부로 나가는 수치가 있으면 인용 금지 목록 노트를 둔다

## 2단계 — 구축 (1시간)

### 2.1 `/wiki-init` 실행

1단계의 결정을 입력으로 넣는다. 산출은 [WIKI-SKILLS.md](WIKI-SKILLS.md) §1 참조.

★스킬 없이 수동으로 할 경우 최소 순서: 폴더 트리 → `TAXONOMY` → `CONVENTION` → `LINK-MAP` → `LINT` → `lint_wiki.py` → 홈 `README` → 린트.
★`TAXONOMY` 를 `CONVENTION` 보다 먼저 만드는 이유: 규약 문서가 태그를 참조하기 때문.

### 2.2 린터 이식

`lint_wiki.py` 는 **표준 라이브러리만** 쓰고 위키 루트를 인자로 받으므로 **파일 하나 복사로 이식된다.**

프로젝트별로 손봐야 할 곳은 3군데뿐:

| 위치           | 무엇              | 기본값                                                        |
| -------------- | ----------------- | ------------------------------------------------------------- |
| `VALID_STATUS` | 상태 enum         | `stub/draft/active/verified/superseded` (건드릴 일 거의 없음) |
| `TOOL_OWNED`   | 도구 소유 파일명  | `index.md` `log.md` `MEMORY.md`                               |
| `FM_FIELDS`    | frontmatter 5필드 | ★**늘리지 않는다** (§2.1)                                     |

★검증: 위키를 만든 직후 린트가 **에러 0** 이어야 한다. 시드 노트가 아직 없어 `ORP` 가 뜨면, 홈 `README` 의 `links` 에 해당 슬러그를 넣어 해소한다.

### 2.3 시드 노트 3~8건

★**빈 위키는 죽는다.** 처음부터 전부 이관하지 말고 **가장 많이 참조되는 것 3~8건**만 `/wiki-note` 로 옮긴다.

시드 선정 기준(우선순위 순):

1. **의존이 가장 많은 것** — 다른 문서들이 전제하는 기반 노트
2. **지금 실제로 돌아가는 것** — 주력 1~2건
3. ★**가장 크게 실패한 것 1건** — 정직성 규약이 말이 아니라 실물임을 첫날에 보여준다
4. **방법론 1건** — 나머지 판정이 참조할 근거 문서

### 2.4 기각 원장 초기화

기존 문서에서 **폐기·기각·롤백된 것**을 훑어 `_meta/do-not-retry.md` 표를 채운다.
★완벽할 필요 없다 — **5건이라도 있으면 원장은 작동한다.** 0건이면 아무도 안 본다.

### 2.5 커밋

```bash
python3 docs/wiki/_meta/lint_wiki.py   # 에러 0 확인
git add docs/wiki
git commit -m "docs(wiki): 지식위키 도입 — 뼈대 + 시드 N건"
```

★**기존 파일이 diff 에 없는지 확인**한다. 있으면 P1 위반이므로 되돌린다.

## 3단계 — 스킬 등록 (30분)

### 3.1 스킬 파일 생성

[WIKI-SKILLS.md](WIKI-SKILLS.md) 의 4개 스캐폴드를 실제 스킬 파일로 옮긴다.

| 하네스                 | 경로                               |
| ---------------------- | ---------------------------------- |
| Claude Code (프로젝트) | `.claude/skills/<name>/SKILL.md`   |
| Claude Code (전역)     | `~/.claude/skills/<name>/SKILL.md` |
| 리포 자체 규약         | `skills/<name>.md`                 |

각 파일 = 스캐폴드의 **frontmatter 블록 + 목적/입력/단계/산출 4절**. ★단계 표의 **게이트 열을 빼지 않는다** — 그 열이 스킬의 값이다.

### 3.2 프로젝트 언어로 치환

스캐폴드의 플레이스홀더를 1단계 결정으로 바꾼다.

| 플레이스홀더              | 치환                              |
| ------------------------- | --------------------------------- |
| `docs/wiki`               | 실제 위키 루트                    |
| `<탐구폴더>` · `<도메인>` | 1.1·1.2 의 이름                   |
| 원장 경로 · 조항 표기     | 1.3                               |
| Evidence 디렉터리         | 1.4                               |
| `verdict/` 4값            | 1.5 (미사용이면 관련 게이트 제거) |

### 3.3 Marblo 위키 도구 연결 (선택)

`wiki_ingest` / `wiki_query` / `wiki_lint` 가 가용하면 `/wiki-ingest` 4~5단계가 활성화된다.
★`root_path` 를 **위키 서브트리로 고정**한다. 리포 루트로 두면 도입 첫날 P1 이 깨진다.

가용하지 않으면 `/wiki-ingest` 는 L1(로컬 린트)만으로도 동작한다 — ★**건너뛴 사실을 명시적으로 보고**하게 두고, 조용히 성공 처리하지 않는다.

### 3.4 등록 확인

```
/wiki-note  →  더미 노트 1건 작성 → R1~R6 게이트가 실제로 걸리는가
/wiki-ingest →  일부러 깨진 링크를 넣고 → BRK 에러로 커밋이 막히는가
```

★**막히는지를 확인**하는 것이 등록 검증이다. 통과만 확인하면 게이트가 죽어 있어도 모른다. 확인 후 더미는 되돌린다.

## 4단계 — 운영 (지속)

### 4.1 일상 루프

```
새 탐구 시작        →  /experiment-intake   (원장 조회 + 사전등록 + stub)
탐구 종료 / 문서화  →  /wiki-note           (R1~R6 채우기)
커밋 직전           →  /wiki-ingest         (에러 0 아니면 커밋 금지)
```

### 4.2 자동화 도입 순서

사양서 §4 를 그대로 따른다. ★**건너뛰지 않는다.**

```
L1 린트 에러 0  →  CI 훅  →  L2 ingest/query  →  L3-a 접수  →  L3-b 트래커  →  L3-c 파생
```

L3 는 **사람 문서에 쓰는 유일한 층**이므로 세 안전장치가 필수: **마커 블록 안에만 쓰기 · 원본은 읽기 전용 파싱 · 생성물은 `status: stub`**.

> ★**P4 정합 주석** — L3(`build_tracker.py` / `EXPERIMENT-INTAKE`)는 P4 티켓(`0NhSeu2s`) 설계 기준으로 기술됐다.
> **P4 구현 확정 후 오케스트레이터가 실제 스크립트·규약과 사양서 §4 및 본 절을 맞춘다.**

### 4.3 건강 점검 (월 1회, 10분)

| 점검      | 방법                                      | 나쁜 신호                                                 |
| --------- | ----------------------------------------- | --------------------------------------------------------- |
| 린트      | `lint_wiki.py`                            | 에러 ≥1 이 2주 이상 방치                                  |
| 고아      | `ORP` 결과                                | 신규 노트가 계속 고아로 태어남 = 인덱스 갱신이 밀림       |
| 허브      | LINK-MAP `## 허브`                        | ★허브가 **예상과 다르면 구조가 잘못**됐다는 신호          |
| 판정 분포 | 홈의 분포 표                              | ★**기각이 채택보다 적으면** 정직성 규약이 작동 안 하는 것 |
| staleness | `date` 가 6개월 이상 오래된 `active` 노트 | 살아있다고 표시된 문서가 안 갱신됨                        |
| 자체완결  | R1/R6 grep (§3.4)                         | deferral 문장이 늘어남 = 노트가 얇아지는 중               |

### 4.4 흔한 실패 모드

| 실패                    | 증상                                      | 처방                                                                         |
| ----------------------- | ----------------------------------------- | ---------------------------------------------------------------------------- |
| ★**빈 껍데기**          | 섹션은 다 있는데 내용이 없다              | R1~R6 게이트를 `/wiki-note` 에서 **실제로 막게** 한다. 린트는 이걸 못 잡는다 |
| ★**인덱스 드리프트**    | 노트는 늘었는데 README·LINK-MAP 이 그대로 | "같은 커밋에서 갱신"을 규약이 아니라 **스킬 단계**로 강제                    |
| ★**원본 오염**          | 위키 때문에 기존 문서를 고치기 시작       | P1 위반. diff 에 기존 파일이 있으면 되돌린다                                 |
| ★**태그 폭발**          | `#todo` `#important` 가 생김              | 자유태그 금지 + `TAG` 에러를 살려둔다                                        |
| ★**성공만 기록**        | 기각 노트가 없다                          | 원장을 먼저 채운다. 기각이 채택보다 적으면 규약이 죽은 것                    |
| ★**폴더 고민 과다**     | 배치에 30분씩 씀                          | 폴더는 저장일 뿐(§1.5). 하나 골라 넣고 태그·링크로 표현                      |
| ★**루트를 위키로 지정** | ingest 후 기존 문서 전부가 위키가 됨      | `root_path` 고정. 발견 즉시 되돌리고 서브트리로 재실행                       |

## 5. 체크리스트 (복사용)

```
[1단계 매핑]
[ ] 도메인 슬롯 6개 이름 확정
[ ] 탐구 하위 도메인 후보 (3건 이상 묶음만)
[ ] 원장 지정 (또는 없음 확정) + 조항 앵커 표기
[ ] Evidence 디렉터리 지정
[ ] 태그축 확정 (topic/ 10~20개, verdict/ 사용여부)
[ ] 기각 사유코드 + 각 코드의 해금 조건

[2단계 구축]
[ ] /wiki-init 실행 (루트가 리포 루트가 아닌지 확인)
[ ] _meta 4종 + lint_wiki.py 존재
[ ] 린트 에러 0
[ ] 시드 노트 3~8건 (★실패 사례 1건 포함)
[ ] 기각 원장 5건 이상
[ ] 커밋 diff 에 기존 파일 없음

[3단계 등록]
[ ] 스킬 4종 파일 생성 (게이트 열 유지)
[ ] 플레이스홀더를 프로젝트 언어로 치환
[ ] wiki_ingest root_path 고정 (선택)
[ ] ★게이트가 실제로 막는지 확인 (깨진 링크 테스트)

[4단계 운영]
[ ] 일상 루프 팀에 공유
[ ] CI 훅 (린트 에러 0 달성 후)
[ ] 월 1회 건강 점검 일정
```
