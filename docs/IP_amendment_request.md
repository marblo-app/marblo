# 특허 명세서 수정 검토 요청서

**제목**: 가상터미널로 격리되는 이종 에이전트를 포함하는 오케스트레이션 시스템, 방법 및, 컴퓨터판독가능기록매체
**작성일**: 2026-05-12

---

## 1. 요청 배경

변리사님께서 정리해 주신 명세서를 검토하면서, 본 발명의 핵심 차별점인 **PTY 격리 + 표준화 통신프로토콜 + 시각적 인터페이스를 통한 stdin/stdout 양방향 오케스트레이션**의 보호 범위를 한 단계 더 보강하면 좋을 것 같아 의견 드립니다.

특히 출원 이후 미국 특허 진입 가능성도 고려하여, 너무 넓혀서 빅테크가 보유한 컨테이너·SaaS 영역과 충돌하지 않으면서도, cmux/tmux/screen 등 종래 터미널 다중화 도구 및 OpenAI Assistants API 등 stateful API 기반 세션 회피와는 명확히 구별되도록 표현을 다듬어 보았습니다.

최종 채택 여부 및 표현은 변리사님 판단에 맡겨 드리며, 본 문서는 검토 편의를 위한 의견 정리본임을 양해 부탁드립니다.

## 2. 검토 의견 요약

- A) **유형**: 신규 종속항(청구항 1에 종속) — **제안 내용**: "이종(異種)" 정의 명문화 — **기대 커버 효과**: 동일 사업자의 다른 모델만으로 회피 시도 차단
- B) **유형**: 신규 독립항 — **제안 내용**: 시각적 인터페이스 ↔ PTY stdin/stdout 양방향 자동 동기화 — **기대 커버 효과**: cmux/tmux 등 멀티플렉서 및 단순 API session 회피 차단, 마블로 고유 인터랙션 보호
- C) **유형**: 신규 종속항(B에 종속) — **제안 내용**: 칸반보드 형태에서의 처리상태 변경 = stdin 신규지시 — **기대 커버 효과**: 칸반 UI 구현체에 대한 추가 방어
- D) **유형**: 신규 종속항(청구항 7에 종속) — **제안 내용**: 원자적 태스크 수락 메커니즘 — **기대 커버 효과**: 동시 claim race condition 회피 차단
- E) **유형**: 청구항 5 본문 보강 — **제안 내용**: "프로세스 비종료 + 중간산출물·사용량 정보 보존" 효과 명시 — **기대 커버 효과**: stateful API session 기반 회피와 차별 명확화
- F) **유형**: 명세서 선행기술 단락 보강 — **제안 내용**: cmux/tmux 및 stateful API session 대비 차별 적시 — **기대 커버 효과**: 진보성(inventive step) 인정 근거 확보
- G) **유형**: 명세서 본문 한 줄 추가 — **제안 내용**: 태스크보드의 클라우드 저장·복수 사용자단말 동시 접근 명시 — **기대 커버 효과**: 팀 협업(SaaS·멀티테넌트) 시나리오에 대한 침해 포섭 근거 확보

## 3. 항목별 상세

### 항목 A — "이종(異種)" 정의 종속항 신설

**현재 명세서 상태**: 본문에는 "서로 다른 사업자가 제공하는 인공지능 모델"이라는 표현이 있으나, 청구항에는 "서로 다른 종류의 에이전트"라는 표현만 있어 정의가 모호한 측면이 있습니다.

**우려되는 회피 시나리오**: 경쟁사가 "동일 사업자의 다른 모델 2개(예: gpt-4 + gpt-4-mini)"만 사용하면서 "본 발명의 이종(異種)이 아니다"라고 주장할 가능성이 있습니다.

**제안 청구항 문구**:

> 【청구항 13(신규)】 청구항 1에 있어서,
> 상기 서로 다른 종류의 에이전트는, 서로 다른 사업자가 제공하는 인공지능모델, 호출규약, 인증체계, 입출력 형식, 및 과금체계 중 1 이상이 상이한 2 이상의 에이전트를 포함하는, 오케스트레이션 시스템.

**기대 커버 효과**: 호출규약/인증체계/입출력형식/과금체계 중 어느 하나라도 다르면 침해로 포섭되어, 회피 폭이 좁아집니다.

### 항목 B — 시각적 인터페이스↔PTY 양방향 자동 동기화 독립 청구항 (가장 중요)

**현재 명세서 상태**: 명세서에 "에이전트 stdout → 태스크보드 → 칸반보드(상향) / 칸반보드 → 태스크보드 → 에이전트 stdin(하향)"의 양방향 데이터 흐름이 매우 명확하게 설명되어 있으나, 이 흐름 자체를 보호하는 독립 청구항이 부재합니다. 청구항 10은 칸반보드의 정적 구성(컬럼·카드)만 보호하고 있어 데이터 흐름은 보호되지 않습니다.

**본 발명의 진정한 차별점**: 본 발명에서 가장 독창적인 부분은 "사용자가 어느 가상터미널에도 직접 접속하거나 키 입력을 수행함 없이, 추상화된 시각적 객체에 대한 조작만으로 해당 객체에 대응되는 에이전트의 가상터미널 stdin에 신규지시가 자동 주입되는 변환 메커니즘"입니다.

- cmux, tmux 등 종래의 터미널 다중화 도구는 복수 PTY 세션의 출력을 화면에 스택 형태 또는 분할 형태로 표시하고 알림을 제공하지만, **사용자가 해당 PTY에 직접 포커스를 이동하여 키 입력을 수행해야 하며**, 시각적 추상화 객체에 대한 조작이 자동으로 stdin에 주입되는 메커니즘은 부재합니다.
- 본 발명은 사용자가 시각적 객체(태스크카드 등)를 조작하면 시스템이 그 의미를 해석하여 해당 객체에 대응되는 에이전트의 PTY stdin에 신규지시로 변환·주입하는 흐름을 갖고 있어, 이 점이 명확한 차별점입니다.

**제안 청구항 문구**:

> 【청구항 14(신규 독립항)】
> 가상터미널로 격리되는 이종 에이전트를 포함하는 오케스트레이션 시스템으로서,
> 각각이 독립된 가상터미널(PTY, Pseudo-Terminal)로 격리되어 실행되고, 동일한 표준화된 통신프로토콜을 통해 태스크보드와 통신하는 복수의 에이전트; 및
> 상기 태스크보드에 기록된 복수의 태스크에 대응되는 복수의 시각적 객체를 포함하고, 상기 시각적 객체에 의해 복수의 태스크의 처리상태를 표시하는 시각적 인터페이스;를 포함하고,
> 상기 오케스트레이션 시스템은,
> 복수의 에이전트 각각의 가상터미널의 표준출력(stdout)으로부터 출력된 출력데이터가, 상기 태스크보드를 거쳐 상기 시각적 인터페이스의 시각적 객체에 반영되는 상향동기화단계; 및
> 사용자가 상기 시각적 인터페이스의 시각적 객체에 대하여 수행한 조작에 따른 신규지시가, **사용자의 가상터미널에 대한 직접적인 접속 또는 키 입력 없이**, 상기 태스크보드를 거쳐 해당 시각적 객체에 대응되는 태스크를 처리하는 에이전트의 가상터미널의 표준입력(stdin)에 자동으로 주입되어, 해당 에이전트의 실행을 중단하지 않고 사용자의 조작에 따른 신규지시가 해당 에이전트의 태스크 수행에 반영되는 하향동기화단계;
> 를 수행하는, 오케스트레이션 시스템.

**보충 종속항(칸반 형태)**:

> 【청구항 15(신규, 14에 종속)】 청구항 14에 있어서,
> 상기 시각적 인터페이스는, 처리대기(TODO), 수락됨(CLAIMED), 처리중(IN PROGRESS), 검토중(REVIEW), 차단됨(BLOCKED), 실패(FAILED), 완료(DONE) 중 1 이상의 처리상태에 각각 대응되는 복수의 컬럼; 및 상기 복수의 시각적 객체로서 상기 복수의 태스크에 각각 대응되어 해당 태스크의 처리상태에 대응되는 컬럼에 표시되는 복수의 태스크카드;를 포함하는 칸반보드를 포함하고,
> 사용자가 상기 칸반보드 상에서 특정 태스크카드를 다른 컬럼으로 이동시키는 조작을 수행하는 경우, 해당 조작이 해당 태스크의 처리상태 변경지시로서 태스크보드에 반영되고, 변경된 처리상태에 따른 후속지시가 해당 태스크를 처리하는 에이전트의 가상터미널의 표준입력에 주입되는, 오케스트레이션 시스템.

**기대 커버 효과**:

- cmux/tmux 등 종래 터미널 다중화 도구의 알림/스택 표시 방식과 명확히 구별
- 칸반 UI가 아닌 다른 시각적 표현(그래프, 트리, 카드뷰 등)으로의 회피도 함께 차단 (청구항 14가 broader, 15가 narrower)
- PCT 진입 시 미국·EP 출원에서 본 발명의 "구체적 기술 효과"가 명확해 §101(추상적 아이디어) 거절 리스크 감소

또한 청구항 14에 대응하는 **방법항(청구항 17) / 컴퓨터판독가능기록매체항(청구항 18)** 도 함께 추가하면 권리범위가 완전해질 것으로 사료되며, 이는 변리사님께서 청구항 11·12와 동일한 구조로 작성해 주시기를 부탁드립니다.

### 항목 D — 원자적 태스크 수락 종속항

**현재 명세서 상태**: 청구항 7에 태스크수락도구(claim)가 정의되어 있고 명세서에 "다른 에이전트에 의하여 중복 할당되지 않을 수 있다"는 표현이 있으나, 동시 수락 시 충돌 처리 메커니즘이 청구항에 명시되어 있지 않습니다.

**우려되는 회피 시나리오**: 경쟁사가 "동시 수락 처리는 본 발명에 명시되지 않았다"고 주장할 가능성. 실제 본 발명의 구현(Firestore 트랜잭션 기반 first-claim-wins)을 보호하기 위해 종속항으로 보강이 필요합니다.

**제안 청구항 문구**:

> 【청구항 16(신규, 청구항 7에 종속)】 청구항 7에 있어서,
> 상기 태스크수락도구는, 2 이상의 에이전트가 동일한 태스크에 대하여 수락을 동시에 또는 순차적으로 요청하는 경우, 어느 하나의 에이전트의 수락 요청을 원자적(atomic)으로 수용하고 다른 에이전트의 수락 요청을 거절함으로써, 해당 태스크가 단일한 에이전트에 의해서만 처리되도록 보장하는, 오케스트레이션 시스템.

**기대 커버 효과**: 다중 에이전트 환경에서 발생할 수 있는 race condition 회피 시도를 차단합니다.

### 항목 E — 청구항 5 본문 보강

**현재 청구항 5**:

> "...해당 에이전트의 실행을 중단하지 않고 기존의 대화 컨텍스트를 유지한 상태에서 해당 신규지시를 추가입력으로 인식하여 태스크를 이어서 수행..."

**우려**: OpenAI Assistants API 등 stateful한 API session도 "기존 컨텍스트 유지 + 메시지 추가"가 가능하여, "기존의 대화 컨텍스트 유지"만으로는 차별이 약할 수 있습니다.

**제안 보강안 (밑줄 부분 추가)**:

> 【청구항 5(보강)】 청구항 1에 있어서,
> 상기 복수의 에이전트 각각은, 해당 에이전트를 격리하는 가상터미널의 표준입력에 입력된 초기지시에 따라 할당된 태스크를 수행하고, 태스크를 수행하는 도중 가상터미널의 표준입력에 신규지시가 입력되는 경우, **해당 에이전트의 실행 중인 프로세스가 종료되거나 재시작되지 않고, 해당 가상터미널 내에 누적된 대화 컨텍스트, 중간산출물 및 사용량 정보가 유지된 상태에서**, 해당 신규지시를 추가입력으로 인식하여 태스크를 이어서 수행하는, 오케스트레이션 시스템.

**기대 커버 효과**: "프로세스 비종료" 및 "중간산출물·사용량 정보 보존"이라는 검증 가능한 기술적 효과를 청구항에 명시함으로써, API session 방식의 회피와 명확히 구별되고, 미국 거절 리스크도 완화됩니다.

### 항목 F — 명세서 선행기술 단락 보강

현재 명세서 (종래 시스템의 한계) 직후에 아래 단락을 추가해 주시기를 부탁드립니다.

**제안 단락 ①** (cmux/tmux 등 터미널 다중화 도구 차별):

> 또한 종래의 cmux, tmux, screen 등 터미널 다중화(terminal multiplexing) 도구는 복수의 가상터미널 세션을 화면상에 스택 또는 분할 형태로 표시하고 각 세션에서 발생한 이벤트에 대한 알림 기능을 제공하나, 이러한 도구는 (i) 각 가상터미널 내에서 동작하는 프로세스 간의 협업을 매개하는 태스크보드 또는 표준화된 통신프로토콜이 부재하고, (ii) 사용자가 수행하는 작업의 처리상태가 시각적 객체로 추상화되어 표시되지 아니하며, (iii) 사용자가 추상화된 시각적 객체에 대한 조작을 통해 가상터미널 내에서 동작하는 프로세스에 지시를 전달하는 변환 메커니즘이 없어, 사용자가 각 가상터미널에 직접 접속하여 키 입력을 수행해야 한다는 제약이 있었다. 이에 따라 이종(異種) 에이전트의 협업 오케스트레이션 환경에 직접 적용하기에는 한계가 있었다.

**제안 단락 ②** (stateful API session 방식 차별):

> 또한 종래의 시스템 중 사용자의 추가요청을 반영하기 위해 인공지능모델 사업자가 제공하는 stateful API session(세션 기반 대화형 API)에 새로운 메시지를 추가 전송하는 방식이 시도되었으나, 이러한 방식은 (i) 특정 사업자의 API에 의존적이어서 서로 다른 사업자가 제공하는 이종 에이전트의 협업환경에 일관되게 적용하기 어렵고, (ii) 에이전트가 외부 도구를 호출하여 수행하는 중간산출물이나 작업로그 등 가상터미널 내부에 축적된 상태가 유지되지 아니하는 한계가 있었다.

**기대 커버 효과**: 진보성 거절 대응 시, 본 발명이 단순한 기능 조합이 아니라 cmux/tmux의 사용자 직접 키입력 방식 및 stateful API session 방식 양쪽 모두의 한계를 극복한 것임을 명확히 보일 수 있는 근거를 명세서에 확보합니다.

> **참고 — cmux의 스택형 알림 관련**: 본 출원 발명의 구현체에도 cmux와 유사하게 복수 에이전트의 이벤트를 스택 형태로 모아 표시하는 통합 알림 기능이 포함되어 있습니다. 다만 본 발명의 차별점은 알림 표시 자체가 아니라, 알림으로 표시된 시각적 객체에 대한 사용자 조작이 자동으로 해당 에이전트의 PTY stdin에 신규지시로 변환·주입되는 양방향 변환 메커니즘에 있으므로, 위 단락 ①의 (iii) 항목 표현으로 충분히 차별이 가능할 것으로 사료됩니다.

### 항목 G — 팀 협업 시나리오 포섭을 위한 명세서 본문 보강

**현재 명세서 상태**: 명세서에서 태스크보드를 "데이터영역"으로 정의하고 있으나, 이 태스크보드가 네트워크상의 클라우드 데이터베이스에 저장되어 복수의 사용자단말이 동시에 접근하는 형태로도 구현될 수 있다는 점이 명시되지 않았습니다.

**보강 필요 이유**: 본 출원 발명의 실제 구현체는 Firestore 등 클라우드 데이터베이스를 통해 복수의 사용자단말이 동일 태스크보드를 매개로 협업하는 팀 단위 사용 시나리오를 지원합니다. 청구항 14의 양방향 동기화 흐름(시각적 인터페이스 조작 ↔ 태스크보드 ↔ 가상터미널 stdin)은 단일 사용자/단일 머신 환경뿐 아니라 복수 사용자/복수 머신 환경까지 자연스럽게 포섭하므로, 이를 뒷받침하는 명세서 표현을 추가해 두면 SaaS·멀티테넌트 협업 도구 형태의 침해 사례에 대한 권리범위 주장 근거가 명확해집니다.

**제안 단락** (명세서 "태스크보드는 …데이터영역으로서…" 단락 직후에 추가):

> 본 발명의 일 실시예에서, 상기 태스크보드는 네트워크상의 클라우드 데이터베이스에 저장될 수 있고, 이 경우 복수의 사용자단말이 네트워크를 통해 동일한 태스크보드에 동시에 접근할 수 있다. 이에 따라 어느 한 사용자단말에서 발생한 태스크의 처리상태 변경, 활동로그 기록, 또는 신규지시 입력이 상기 태스크보드를 통해 다른 사용자단말에 실시간으로 반영될 수 있고, 본 발명의 오케스트레이션 시스템은 단일 사용자에 의한 운용 환경뿐 아니라 복수의 사용자가 협업하는 운용 환경에서도 동일한 표준화된 통신프로토콜 및 태스크보드를 매개로 일관되게 적용될 수 있다.

**기대 커버 효과**:

- 팀 단위·SaaS·멀티테넌트 협업 도구 형태의 회피 시도에 대한 침해 포섭 근거 확보
- 청구항 14의 "사용자"가 단일 사용자에 한정되지 않음을 명세서에서 직접 뒷받침
- PCT 진입 시 분산 시스템·실시간 협업 환경으로서의 기술적 효과 명확화
