# 애플워치 컴패니언 1페이지 요약

## 한줄권고

**NO에 가까운 보류.** 지금은 애플워치 앱을 만들지 말고, **모바일 PWA 컴패니언**을 먼저 승인하는 게 맞다. 워치는 PWA가 먹힌 뒤 알림/승인 전용 액세서리로 재검토한다.

## 핵심근거

- **핵심가치는 워치 화면에 안 맞음**: 마블로 컴패니언의 가치는 칸반 보드, 액티비티 스트림, 태스크별 대화, 승인 카드다. 애플워치 화면은 확인/간단 승인에는 좋지만 보드 운영에는 부적합하다.
- **모바일 PWA는 재사용 여지가 큼**: `tasks`, `activities`, `audit_logs`가 이미 Firestore에 있고 실시간 구독 구조가 있다. 웹/PWA는 인증, Firebase, i18n, 배포를 기존 marblo-web에서 이어받을 수 있다.
- **워치는 네이티브 비용이 붙음**: Apple Watch는 iOS 앱, WatchKit, 푸시, App Store 심사, 인증 흐름까지 필요하다. PWA 대비 구현/운영 비용이 크다.
- **선행 보안 문제가 더 중요함**: 현재 모바일 노출 전 `tasks`/`activities`/`pendingInstructions` Firestore 룰 하드닝이 필요하다. 워치를 붙이면 원격 오케 제어 표면이 더 넓어진다.
- **텔레그램이 이미 최소 모바일 대화 역할을 함**: 당장 이동 중 오케 대화는 텔레그램으로 가능하다. 전용 앱의 차별점은 워치가 아니라 시각적 보드/스트림이다.

## 투자규모/난이도

- **투자규모**: 중형 이상. 단독 워치 앱은 작아 보여도 iOS 동반 앱, 인증, 푸시, 배포/심사까지 필요하다.
- **난이도**: 중상. UI보다 인증/푸시/보안/오프라인 상태 표현이 어렵다.

## 블로커

- Firestore 룰 하드닝 전에는 읽기전용 모바일도 크로스테넌트 유출 위험이 있다.
- 오케 응답을 모바일/워치로 되돌리는 인앱 응답 채널이 없다.
- 데스크톱 오프라인 시 명령은 큐잉되지만 실행 지연/만료/일괄 실행 UX가 없다.
- Apple 개발자 계정, iOS/Watch 배포 파이프라인, 심사 대응이 별도 필요하다.
- 워치에서 처리할 승인 액션의 범위와 위험도 기준이 미정이다.

## 결정 포인트

- **모바일 컴패니언의 1차 형태를 PWA로 갈지** 결정.
- 워치를 **제품 핵심 기능**으로 볼지, **알림/승인 액세서리**로 볼지 결정.
- 우선순위를 “보드/스트림 가시성”에 둘지, “손목 알림”에 둘지 결정.
- 원격 오케 명령에 대해 워치에서 허용할 액션 범위: 읽기, 승인, 재시도, 중단 중 어디까지인지 결정.

## 제안

애플워치는 지금 착수하지 않는다. 1단계는 **PWA 읽기전용 컴패니언**, 2단계는 **대화/응답 채널**, 3단계는 **푸시/승인 카드**다. 워치는 3단계 지표가 나온 뒤 “리뷰대기 승인/차단 알림” 전용으로 판단한다.
