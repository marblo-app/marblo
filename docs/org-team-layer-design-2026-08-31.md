## 1. ★#1333 §1 정정 — 원본 근거를 읽고 판정한다

### 1.1 원본(#1205 §1)이 그때 3층으로 정한 근거 — 요약과 재검증

`#1333` §0 의 "팀 = 프로젝트. 새 `teams` 엔티티 없음. 3층으로 끝" 은 `v3/docs/org-access-and-login-flow-2026-08-24.md` §1 의 인용이다. 원본을 다시 읽으면 논거는 셋이다:

| #   | 원본 논거                                                                                                                                                                                                                                                | 무엇에 대한 논증인가        |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------- |
| 1   | **census**: 행 격리·역할·초대·비용·원장·사람그룹의 경계가 전부 `projectId` 다. "여기에 팀이라는 일곱 번째 축을 넣으면 그 축은 여섯 중 아무것도 소유하지 않은 채 여섯 개 전부와 매핑을 유지해야 하고, **그 매핑이 틀리는 날이 유출이 나는 날이다**"(§1.1) | ★**권한 축**으로서의 팀     |
| 2   | 프로젝트 묶음으로서의 팀은 **uid 에서 도출**된다 — 저장하면 `projects.members` 와 어긋나고, 어긋나면 권한 정본이 모호해진다(§1.3)                                                                                                                        | ★**멤버십 정본**으로서의 팀 |
| 3   | 사람 묶음 자체가 산출물(인사·평가·좌석)인 경우는 "우리가 팔 것이 아니다"(§1.4-3)                                                                                                                                                                         | 인사 축으로서의 팀          |

**세 논거 전부 "팀 문서가 권한·멤버십을 소유하는 경우"에 대한 것이다.** "유출이 나는 날" 은 팀 매핑이 read 게이트에 들어갈 때의 이야기고, "권한 정본 모호" 는 팀 문서가 사람 목록을 가질 때의 이야기다. **그 논거는 지금도 유효하다 — 그래서 (A) 를 이번에도 짓지 않는다(§2.3).**

### 1.2 원본이 답하지 않은 질문 — 그리고 사장님이 물으신 것

원본 문서가 검토하지 않은 경우가 하나 있다: **아무 권한도 갖지 않는, 분석 그룹핑 전용 라벨로서의 팀.** 원본은 "팀 = 권한 있는 엔티티" 와 "팀 = 프로젝트" 둘만 놓고 골랐고, 당시 요구(#1202 "관리자가 보고 / 팀장들한테 팀 내용만")는 권한 문제였으므로 그 이분법이 옳았다.

사장님의 이번 문장은 다른 요구다: **"조직-팀-프로젝트 구조로 분석이 가능해야"** — 권한이 아니라 **조직도 모양의 집계 축**이다. 라벨 축은 census 논거에 걸리지 않는다:

> 라벨 매핑이 틀리면 **차트의 행이 잘못 묶일 뿐, 행이 새지 않는다.** 권한 판정 어디에도 `teamId` 가 등장하지 않기 때문이다(§3.4 에서 금지로 못박는다). "매핑이 틀리는 날이 유출 나는 날" 이라는 원본의 경고는 권한 축의 성질이지 라벨 축의 성질이 아니다 — 실수의 최대 피해가 **오분류**로 상한이 잡힌다.

그리고 원본 §1.4-2 가 "팀은 그대로인데 프로젝트가 바뀐다" 를 조직 축(`OrgProjectBinding` 시점 결합)으로 답했는데, 4층에서는 정확히 같은 답이 팀 축에도 성립한다 — `teamId` 를 같은 추가전용 표에 실으면 팀 연속성도 시점 조회로 나온다(§3.2).

### 2.2 ★(B)의 함정 — 자유 입력이면 분석이 조용히 망가진다

사장님 대안("프로젝트 설정할 때 팀명도 설정")을 **자유 입력 문자열**로 구현하면:

1. **표기가 갈라진다.** `Platform` / `platform` / `플랫폼 ` / `Platform팀` 이 네 팀으로 집계된다. 팀이 3개인 조직의 L0 화면에 7개 행이 뜨고, **각 행의 숫자는 전부 "그럴듯하게 작다"** — 오류처럼 보이지 않아서 아무도 신고하지 않는다. 이 화면의 존재 이유가 팀 비교인데 비교 대상 자체가 깨진다.
2. **개명이 불가능하다.** "Platform팀 → 플랫폼실" 개명은 프로젝트 N개의 문자열을 전부 고쳐야 하고, 하나라도 놓치면 옛 이름이 유령 팀으로 남는다. 시점 이력도 없어서 "개명 전 분기의 팀 지출" 이 사라진다.
3. **승격이 막힌다.** 나중에 팀 멤버십이 필요해져도 문자열에는 멤버를 붙일 곳이 없다 — 그때 가서 id 를 도입하면 문자열→id 매핑(= 지금 안 한 정규화)을 그때 하게 된다. 미루는 게 아니라 이자 붙여 미루는 것이다.
4. **조직 밖으로 샌다.** `Project` 문서는 프로젝트 멤버 전원이 읽는다. 조직 멤버가 아닌 외부 대행사 멤버(#1205 §2.5-6, 정당한 케이스)에게 조직 내부 팀 편제명이 노출된다. (C) 는 팀명이 조직 쪽 표에 있어 이 경로가 없다.

★단 **사장님 문장의 UX 자체는 옳다** — "프로젝트를 설정할 때 팀도 정한다" 는 시점이 마찰이 가장 적다. 틀린 것은 시점이 아니라 **입력 방식**이고, §4 의 콤보가 그 UX 를 그대로 살리면서 (B) 의 함정만 제거한다.

### 2.3 ★(A)를 지금 짓지 말아야 할 이유

1. **요구에 없다.** 사장님 문장은 "조직-팀-프로젝트 구조로 **분석이 가능해야**" 다. 팀 초대·팀 역할·팀 단위 열람 권한은 문장에 없다. 요구를 넘어 지으면 그만큼의 보안 표면과 유지 비용을 근거 없이 산다.
2. **그 축은 최근 두 번 조용히 깨졌다.** 권한·멤버십 게이트는 우리가 가장 자주 다치는 곳이다 — `#1299`(초대 수락이 역할 문서를 안 박아 **역할 문서 없는 멤버의 저장소 write 누수**) · `#1293`(GitHub App 설치 후에도 기기 OAuth push fallback 이 살아 있던 구멍). 둘 다 "조용히" 가 핵심이다 — 깨져도 화면에 안 보인다. (A) 는 초대·역할·게이트 한 벌을 **추가로** 만들고, 원본 census 논증대로 그 벌은 기존 6축 전부와 정합을 유지해야 한다.
3. **판정 어휘가 이미 넷으로 갈라져 있다.** #1205 §2.1 census: `ProjectRole`/`TeamRole`/`TeamProjectRole`(viewer 없음)/룰 문자열 판정 — 다섯 곳 복제 위에 팀 역할 축을 얹으면 드리프트가 곱해진다는 원본 경고가 그대로 산다.
4. **되돌리기 비대칭.** (C) 로 시작해 (A) 로 승격하는 길은 열려 있다(§8). (A) 로 시작해 (C) 로 줄이는 길은 없다 — 한번 준 팀 권한을 회수하는 것은 기능 삭제이자 신뢰 사건이다.

### 2.4 권고

> **(C) 를 권고한다.** 오케의 권고와 같은 결론이나, 근거를 이 문서가 독립적으로 재검증했다: 결정적 근거는 (i) 원본 3층 논거가 라벨 축에는 적용되지 않음(§1.2), (ii) (B) 는 분석 정합·개명·승격·노출 네 축에서 실격(§2.2), (iii) (A) 는 요구 초과 + 최근 두 번 깨진 축의 증설(§2.3), (iv) Phase 1 미구현이라 지금 넣으면 비용이 타입 두 조각(§3.3).

## 3. 데이터 모양

### 3.1 새 컬렉션 `org_teams` — 컬렉션 1개, 필드 6개

```ts
/** 분석 그룹핑 전용 팀 라벨. ★멤버·역할·권한을 갖지 않는다.
 *  teamId 는 어떤 read/write 게이트 판정에도 입력되지 않는다(§3.4). */
interface OrgTeam {
  id: string; // Firestore 자동 id. 불변. displayName 은 id 가 아니다(조직 규약과 동일)
  orgId: string; // 소속 조직. 팀은 조직 밖에 존재하지 않는다
  displayName: string; // 사람이 정한다. 언제든 바꾼다
  normalizedName: string; // trim·NFKC·소문자 접기. ★생성 시 조직 안 중복 검사 키(§4.3)
  createdBy: string; // uid
  createdAt: Date;
  archivedAt?: Date; // 보관. 삭제하지 않는다 — 과거 결합 행이 이 id 를 가리킨다
}
```

- **개명**은 이 문서의 `displayName` 수정 + `OrgNameHistoryEntry` 와 같은 패턴의 추가전용 이력(`OrgTeamNameHistoryEntry`) 한 줄. 조직명 개명 규약을 그대로 축소 복제한다 — 새 규약을 만들지 않는다.
- **병합**(중복 팀 정리)은 §4.4.
- 문서 수 상한 걱정 없음: 고객사 팀 수 현실 2~5개(#1205 §3.5).

### 3.2 `OrgProjectBinding` 에 `teamId` 한 필드 — 재배정은 새 행

```ts
interface OrgProjectBinding {
  // …기존 필드 전부 불변(organization.ts:109)…
  /** 조직 안 팀 라벨. null = 미지정(§6). ★추가전용 규약을 그대로 탄다 —
   *  팀 재배정·정정은 이 행을 고치는 게 아니라 새 행을 덧붙인다(effectiveFrom). */
  teamId: string | null;
}
```

★이 선택이 (C) 의 숨은 이점이다. 결합표가 이미 추가전용·시점 결합(`effectiveFrom`·`resolveOrgIdAt`)이므로:

- **팀 재배정이 이력을 안 지운다.** "프로젝트 X 는 3월까지 플랫폼팀, 4월부터 앱팀" 이 행 두 개로 남고, 분기 집계가 시점별로 옳게 갈린다. 원본 §1.4-2 의 "팀은 그대로인데 프로젝트가 바뀐다" 연속성 문제가 **같은 메커니즘으로** 풀린다 — `resolveOrgIdAt` 옆에 `resolveTeamIdAt` 하나.
- **정정 가능.** 잘못 붙인 팀은 정정 행으로 고치고, 정정 사실이 남는다(#1204 "소급은 저장이 아니라 조회로").
- **원장·BQ 무접촉.** `orgId` 를 원장·BQ 에 안 박은 것과 같은 이유로 `teamId` 도 안 박는다(§9). 팀 롤업은 Node 에서 결합표로 프로젝트 집합을 팀별로 가르는 것뿐이다(§7).

### 3.3 마이그레이션 — 없다. 그리고 지금이 유일하게 공짜인 시점이다

- `organizations`·`org_project_bindings` 컬렉션은 **아직 0건**(#1333 §1 실측: "organizations 컬렉션 0건", Phase 1 미구현). 고칠 기존 행이 없다.
- 기존 프로젝트 24개는 조직에 결합된 적이 없으므로 팀 미지정 문제도 **결합하는 날** 생긴다 — 그날의 처리는 §6.
- 반대로 Phase 1 을 3층으로 짓고 나서 팀을 끼우면: 결합표 스키마 정정 + 쌓인 결합 행 전수 재작성(추가전용이라 정정 행 파도) + L0 화면 개편이 든다. **이 티켓이 Phase 1 착수 전에 온 것이 비용 구조의 전부다.**

### 3.4 ★불변 제약 — 라벨이 권한이 되는 것을 막는 두 겹

(C) 의 유일한 장기 리스크는 "라벨이 슬금슬금 권한이 되는 것" 이다. 두 겹으로 막는다:

1. **규약 문장**(타입 주석 + 룰 머리 주석): _"`teamId` 는 어떤 read/write 판정에도 입력되지 않는다. 팀 단위 열람 권한이 필요해지는 날은 (A) 승격의 날이고, 그날 §8 의 설계를 꺼낸다 — 라벨에 게이트를 덧대지 않는다."_
2. **테스트 고정**(Phase 1 구현 티켓에서): `firestore.rules` 소스에 `org_teams` 참조가 read 게이트 함수 안에 등장하지 않음을 소스 스캔으로 고정 — `team-usage-axis-guard` 가 콜러블 소스를 스캔하는 것과 같은 방식.

## 4. UX — 언제, 누가, 어떻게

### 4.1 시점: 프로젝트를 조직에 **결합할 때** 묻는다 (사장님 안 그대로, 입력만 콤보)

사장님 질문 _"프로젝트를 설정할 때 팀명도 설정하도록 할까?"_ 에 대한 답: **예 — 단 그 "설정할 때" 는 프로젝트 생성 시점이 아니라 조직 결합 시점이다.**

- 프로젝트 생성 시점에 물으면 개인 조직 사용자(오늘의 전원)에게 무의미한 질문이 하나 생긴다. 팀은 조직의 개념이므로 **조직이 문맥에 들어온 순간**(결합 폼)에만 묻는 것이 #1333 UX 원칙("조직이 하나면 묻지 않는다 — 물을 것이 생겼을 때만 묻는다")과 일관된다.
- **개인 조직(`personal_<uid>`)에는 팀 개념이 아예 안 보인다.** 콤보도, 미지정 버킷도, L0 팀 접기도 없다 — 혼자인 사람에게 팀을 그리는 것은 빈 개념을 파는 것이다.
- 이미 결합된 프로젝트의 팀 변경은 조직 화면의 프로젝트 행(또는 프로젝트 설정의 조직 섹션)에서 같은 콤보로 한다.

### 4.2 입력: 콤보 — 목록에서 고르되, 없으면 그 자리에서 만든다

```
프로젝트를 조직 <표시명> 에 결합
  팀:  [ 플랫폼팀            ▾ ]     ← org_teams 의 미보관 팀 목록
       ├ 플랫폼팀
       ├ 앱팀
       ├ (팀 없음 — 소규모 조직이면 이대로 두세요)
       └ ＋ 새 팀 만들기: "____"     ← 그 자리에서 생성. §4.3 중복 가드
```

자유 입력의 편의(그 자리에서 끝난다)와 목록의 정합(id 로 묶인다)을 둘 다 얻는다. 타이핑하면 목록이 필터되고, 일치가 없을 때만 "새 팀 만들기" 가 뜬다.

### 4.3 ★중복 가드 — (B)의 함정을 생성 지점에서 막는다

새 팀 생성 콜러블은 `normalizedName`(trim·NFKC·소문자 접기)으로 조직 안 중복을 검사한다:

- 정규화 일치가 있으면 **생성하지 않고 그 팀을 돌려준다** + "같은 이름의 팀이 이미 있어 그 팀으로 배정했습니다" 한 줄. `Platform` 을 치면 `platform` 팀이 재사용된다.
- 정규화는 동치 접기(대소문자·공백·전각)까지만 한다. `플랫폼` 과 `Platform` 은 **다른 팀이다** — 번역 동치까지 접으면 오배정이 생기고, 그건 사람이 §4.4 병합으로 정리할 일이다.

### 4.4 권한 — 누가 무엇을

| 행위                             | 누가                                                                             | 근거                                                                                                                                                                                  |

## 5. ★#1334 화면 영향 — 층을 늘리지 않고 L0 에서 접는다

### 5.1 판정: 드릴다운 층 추가 ✗, L0 주 표의 팀 그룹핑 ✅

두 안 중 — (i) L0 조직 → **L1 팀 화면** → L1.5 프로젝트 → L2 사용자로 층을 하나 더 그린다, (ii) 층은 그대로 두고 **L0 주 표를 팀으로 접는다** — **(ii) 를 택한다**:

- **화면이 깊어지면 아무도 안 본다.** 고객사 팀 수 현실이 2~5개인데(#1205 §3.5) 팀 전용 페이지는 L0 표를 필터한 것과 같은 내용을 한 클릭 깊은 곳에 복제한다.
- 팀은 권한 경계가 아니므로(§3.4) **팀 화면만의 권한 스코프라는 것이 없다** — 층을 그릴 권한적 이유도 없다.
- 라우트·콜러블 구조가 #1333 그대로 유지된다: `/org/<orgId>` · `/org/<orgId>/projects/<pid>` · `/org/<orgId>/members/<key>`. **새 라우트 0.** 팀 필터가 필요하면 `/org/<orgId>?team=<teamId>` 쿼리 파라미터 — 층이 아니라 필터다.

### 5.2 L0 주 표의 새 모양 (#1334 §2.1 델타)

```
├ 주 표: 팀별 › 프로젝트별 ──────────────────────────────────────────────┤
│ ▾ 플랫폼팀 (프로젝트 2)  │ 6 │ $1,100 │ 42 │ $26.2 │ 56 / 3 │ 3 │      │ ← 팀 소계 행
│    A                     │ 4 │ $800   │ 30 │ $26.7 │ 41 / 2 │ 2 │ →    │
│    B                     │ 2 │ $300   │ 12 │ $25.0 │ 15 / 1 │ 1 │ →    │
│ ▸ 앱팀 (프로젝트 1)      │ 1 │ $134   │ 6  │ 6/35  │ 8 / 0  │ 0 │      │ ← 접힌 팀
│ ▾ 미지정 (프로젝트 1)    │ … │        │    │       │        │   │      │ ← §6. 배정 CTA
│ 합계                     │ 7 │ $1,234 │ 48 │ $25.7 │ 64 / 3 │ 3 │      │
```

- 팀 소계 행이 사장님이 원하신 "팀 단위 분석" 의 실체다 — 머지·비용·머지당 비용·완료/실패가 팀 행에서 바로 비교된다. 지표 정의는 #1334 §3 그대로, **분모가 프로젝트 집합에서 팀별 부분집합으로 갈릴 뿐이다.** 표본 규율(몫 분모 35)도 팀 소계 행에 그대로 적용된다.
- ★**총계 불변식 검사**: L0 은 `org_owner`/`org_admin` 전용이고 그들은 결합 프로젝트 전수를 보므로(#1205 §3.6) 팀 소계 `f(S_team)` 은 항상 `S_team ⊆ visible(u)` 를 만족한다 — 새 유출 경로 없음. 규약으로 못박을 것 하나: **팀 소계는 L0 밖으로 내보내지 않는다.** 자기 프로젝트만 보는 프로젝트 관리자에게 "우리 팀 소계" 를 주면, 같은 팀의 남의 프로젝트가 뺄셈으로 나온다(2프로젝트 팀이면 완전 노출 — §3.2 와 같은 산수). 팀 소계가 보이는 조건은 팀 구성 프로젝트 전수 가시(轉載: 같은 불변식)다.
- L1(프로젝트)·L2(사용자) 화면은 **무변경.** 프로젝트 헤더에 "조직 › 팀명" 빵부스러기 한 줄만 는다.
- `getOrgUsageSummary` 봉투(#1333 §4.2): `byProject[]` 각 행에 `teamId·teamDisplayName` 을 싣고 `byTeam[]` 소계 배열을 더한다 — Node 에서 결합표로 접는 것이므로 **BQ 변경 0.**

| **신규 결합(정상 경로)**       | 팀 콤보는 **필수 입력**이다 — 단 "(팀 없음)" 이 명시 선택지로 있다. 강제 **배정**이 아니라 강제 **판단**: null 이 "안 물어봐서 없음" 인지 "없다고 답함" 인지 구분되게 한다. 소규모 조직(팀 개념이 없는 5인 회사)이 가짜 팀을 만들도록 밀어붙이지 않는다 |

## 7. ★Phase 0 게이트 — 기존 배선을 깨지 않고 얹어지는가: 그렇다

Phase 0 게이트가 방금 열렸다(`TEAM_USAGE_EFFECTIVE_FROM=2026-04-01`, 테스트용). 검증 결과 **팀 층은 기존 배선의 어느 조각도 건드리지 않는다**:

| 게이트 env                                        | `TEAM_USAGE_EFFECTIVE_FROM` 하나 공유(#1333 §4.2)                         | **불변.** 팀 소계는 조직 롤업의 부분합이라 같은 게이트 뒤에 있다. 팀 전용 게이트를 만들지 않는다 — 발효일 둘 = 사유 둘                                                                                                                        |

## 8. ★(C)→(A) 승격 가능성 — 얹을 수 있다

나중에 팀 멤버십이 정말 필요해지는 날(예: "팀 리더가 자기 팀 프로젝트 전체 집계를 본다" 는 유료 요구)의 경로:

1. `org_team_members/{teamId}_{uid}` 컬렉션 추가 — 프로젝트 `memberRoles/{projectId}_{uid}`·조직 `org_members/{orgId}_{uid}` 와 같은 결정적 id 규약. **`org_teams`·결합표·집계 코드는 무변.** `teamId` 가 처음부터 불변 실체 id 라서 걸 곳이 이미 있다 — (B) 였다면 여기서 전면 재설계다.
2. 팀 역할이 열람 권한을 갖는 순간 §3.4 의 금지가 해제되는 것이 아니라 **#1205 의 전체 절차가 적용된다**: 총계 불변식(팀 리더의 `visible(u)` 에 팀 구성 프로젝트 전수가 들어와야 팀 소계를 준다), 합집합 합성 규칙, `restricted`/omit 구분, 그리고 **방침 개정**(새 열람자). 승격은 필드 추가가 아니라 그 절차를 치르는 일이고, 치를 가치가 생겼을 때 치른다.
3. 분석 이력은 전부 보존된다 — 결합표의 팀 이력은 멤버십 도입과 무관하게 계속 유효하다.

**(C) 에 승격을 막는 결함이 없는지 점검**: (i) `teamId` 불변 id ✓ (ii) 팀 문서가 실체로 존재(문자열 아님) ✓ (iii) 시점 이력 보존 ✓ (iv) 유일한 제약 — 한 프로젝트 = 한 팀 — 은 (A) 로 가도 유지할 제약이다(원본 §1.4-1 판정: 나눠 쓰면 프로젝트를 쪼갠다). **결함 없음.**

## 11. 열린 질문 (사장님·오케)

1. **§6 신규 결합의 "(팀 없음)" 명시 선택** — 더 강하게(팀 생성을 아예 강제) 가길 원하시면 §6 의 근거(쓰레기 팀 축)를 감수하는 결정이 필요하다. 권고는 현행 유지.
2. **팀 목록 열람 범위**(§4.4) — 조직 멤버 전원에게 팀명 목록이 보이는 것을 조직도 수준 정보로 판정했다. 팀명 자체를 org_admin 전용 정보로 잠그길 원하시면 콤보 UX 가 org_admin 전용이 되어 §4.1 의 "프로젝트 owner 가 결합하며 배정" 이 막힌다.
3. **낱말** — 화면에서 이 라벨을 "팀" 이라 부를지 "부서"·"그룹" 같은 다른 낱말로 할지. 이 문서는 사장님 낱말 그대로 "팀" 을 썼다. (A) 승격 전까지 "팀 멤버"·"팀장" 이라는 표현은 화면에 등장하지 않는다는 제약만 지키면 된다.
