## 핵심 질문에 대한 답 — "발표에서 보여줄 1분짜리 루프가 사람 개입 없이 도는가?"

**부분적으로만 돈다. 경계는 정확히 여기다:**

1. 티켓 하나 완료(`DONE`) → 형제 티켓 자동 알림(`SIGNAL_ADVANCE`) — **자동, 코드 확인됨**(`MISSION_ADVANCE_SIGNAL=on` 조건)
2. 미션의 마지막 티켓 완료 → 토큰 잔여 충분 → `PROCEED`가 오케 PTY에 "지금 진행하라" 주입 — **자동, 코드 확인됨**
3. 오케가 그 문장을 읽고 실제로 `dispatch_task`/`spawn_agent`를 호출 — **여기서부터 오케(AI) 판단에 의존, 자동 보장 없음**
4. 오케가 3번을 안 하면 다시 불러줄 경로 — **없음, 코드로 확인**(`xKhErJdSwDH3LIItFe42` 미해결)

→ **1분 루프를 "완전 무인"으로 부르면 거짓말이 된다.** "완료→다음 지시까지는 시스템이 자동으로 잇는다. 그 지시를 받아 실행하는 것은 지금도 오케(AI)의 판단이고, 만약 오케가 멈추면 재호출 안전망이 아직 없다"가 정직한 문장이다. 사장님이 발표에서 이 정도 수위로 조정하시면 무너지지 않는다.

## 이번 주에 되게 만들 수 있는 것 vs 불가능한 것

**이번 주에 가능:**

- 3층 "Model별 성공률" v3 앱 UI — `routing-effectiveness.ts`의 순수 함수(`aggregateEffectiveness`)를 그대로 재사용해 작은 테이블 하나만 얹으면 됨. 로직은 이미 44% 결측·해상도(`model@effort` vs `provider`) 표시까지 되어 있음. **신규 개발이 아니라 배선 작업**
- 공개범위 리스크 완화 — 코드 수정 없이 **리허설 동선에서 Audit 탭/ProjectAuditPanel 확장 클릭을 피하는 것**만으로 이번 주 위험 제거 가능
- 발표 문구 조정 — "1분 루프" 설명을 "완료→지시 자동, 실행은 오케 판단"으로 정정

**이번 주엔 불가능(정직하게 빼야 함):**

- PROCEED 무반응 재호출 경로 신설(`xKhErJdSwDH3LIItFe42`) — 가드 설계·쿨다운·이중통보 방지까지 필요해 발표 전 완성 위험 큼. **차라리 "이 갭을 알고 있고 다음 스프린트에 닫는다"고 투명하게 말하는 편이 안전**
- 폐루프의 "실전 라이브 관측 사례" — 오늘 안에 실전에서 자연 발생한 사례를 새로 만들어 보여줄 순 없음(가짜 데이터 금지 원칙과 충돌). 코드 워크스루로 대체
- `audit_logs.params` write-time 스크럽(근본 수정) — 원장 불변성과 충돌 없이 하려면 화이트리스트 설계가 필요해 이번 주 완성 위험. 리허설 회피로 이번 주는 충분
