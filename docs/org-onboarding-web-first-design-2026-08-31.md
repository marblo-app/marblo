## 1. ★이 제안이 푸는 문제 셋 — 검증하거나 반박한다

### 1.0 먼저, 오케 관찰에 없던 사실 하나 — 현행 초대는 이미 역순이다

실측(2026-08-31): 초대는 앱 설정의 `TeamManagement.tsx` 에서 이메일로 만들고, 초대받은 사람은 **앱 안의 `InvitationBanner.tsx`** 로만 발견한다. **초대 메일을 보내는 코드가 functions 어디에도 없다**(grep 0곳). 즉 오늘의 초대 경로는:

```
관리자: 앱에서 이메일 입력 → invitations/{projectId}_{email} 문서 생성 → ★알림 수단 없음(구두/슬랙)
팀원:   (어떻게든 알아서) 다운로드 → 설치 → 가입/로그인 → 그제서야 앱 배너에서 초대 발견 → 수락
```

**초대받은 사람이 초대의 존재를 확인하려면 먼저 설치해야 한다.** 사장님 제안은 여기에 단계를 더하는 것이 아니라 **이 역순을 뒤집는 것**이다 — 이게 §10 마찰 논증의 뼈대다.

### 1.1 유입 추적 — ★부분 지지. 이득은 실재하되 부차적이다

- **역방향 확인**: 링크백은 앱이 첫 실행에 기본 브라우저로 `marblo.app/link?i=<설치ID>` 를 열어 그 브라우저의 `_ga` 쿠키를 읽는 구조다(`LinkClient.tsx` 머리 주석 — "웹 유입과 앱 설치를 잇는 유일한 결정론적 다리"). 다운로드한 브라우저와 기본 브라우저가 다르거나 쿠키가 없으면 끊긴다 — 실측 `ga_key` NULL 43건(지도 §3-①), 관통 사슬 864→647→2→1→1.
- **웹 선행의 이득**: 초대 팀원은 반드시 웹(로그인·수락·가이드)을 거친 뒤 다운로드하므로 **그 브라우저에 GA4 쿠키가 보장**되고, 링크백이 열리는 브라우저와 같을 확률이 높다. NULL 43 부류의 구멍이 초대 경로에서는 구조적으로 줄어든다.
- **★반박 절반**: 초대로 들어온 팀원의 설치는 **마케팅 유입 분석의 대상이 아니다** — 채널은 "조직 도입"이고 캠페인 귀속이 필요 없다. 이 축의 진짜 답은 유입 추적 개선이 아니라 **도입 현황 퍼널(§7)이 계정 축에서 직접 나온다**는 것이다(초대·수락·첫접속이 전부 계정 축 사실이라 링크백 없이도 셀 수 있다). 유입 추적은 개인(Pro) 경로의 문제로 남고, 그 경로는 이 티켓이 건드리지 않는다.

### 1.2 팀 정보 정확도 — 지지. 단 경계를 정확히 긋는다

- **지지**: 수락이 웹에서 끝나면 앱 첫 로그인 시점에 **사람의 소속**(조직 멤버십·프로젝트 멤버십·역할)이 이미 확정돼 있다. "설치는 했는데 어느 조직 소속인지 모르는 사람"이 안 생긴다.
- **★경계**: #1336 의 "팀 미지정"은 **프로젝트↔조직 결합의 속성**(`OrgProjectBinding.teamId`)이지 사람의 속성이 아니다. 온보딩이 원천 차단하는 것은 "소속 없는 **사람**"이고, 팀원이 나중에 앱에서 새 프로젝트를 만들면 그 프로젝트의 결합·팀 지정은 여전히 #1336 §6 의 결합 폼이 담당한다. "팀 미지정 프로젝트가 애초에 안 생긴다"는 문장은 **온보딩 시점에 존재하는 프로젝트**에 한해 참이다.

### 1.3 활성화 — 지지. 이탈 지점을 정확히 안다

베타 실측 퍼널 65(선정) → 34(접근권) → 17(켜봄) → 7(완료) → 4(계속). 이탈의 근본이 "제품 가치"가 아니라 **"못 쓴 것"** — 특히 "설치는 했는데 에이전트를 못 돌림" = **CLI 인증 단계**(Claude/Codex 로그인, BYOK)다. 기존 `guide/` 는 정확히 이 순서(설치→인증→프로젝트→미션)를 이미 덮고 있으나, 오늘은 **설치 후에야**(link/ 환영 페이지의 카드로) 만난다. 웹 선행은 가이드를 **다운로드 앞**에 놓아 "받기 전에 준비물(에이전트 계정)이 갖춰졌는지"를 먼저 확인시킨다 — §6 G1 이 그 지점이다.

## 4. ★(j) 메커니즘 — 초대 토큰을 다운로드에 싣지 않는다. 서버가 계정 축으로 붙인다

두 안을 비교하고 하나를 버린다:

| 안                                                            | 판정 | 이유                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------- | ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| (A) 초대 토큰을 다운로드에 싣는다(파일명·URL 파라미터·딥링크) | ✗    | ① 릴리스 자산이 GitHub 정적 파일(`Marblo-<ver>-arm64.dmg`)이라 사람별 산출물이 불가능 — 만들려면 사람별 서명 빌드(과잉). ② URL 파라미터는 설치 파일에 안 실린다(브라우저가 버린다). ③ 성사돼도 **익명 설치 축에 계정 축 값(초대=이메일 결속)을 싣는 것** — `install_attribution` 은 익명 축이고, 초대 토큰이 들어가는 순간 그 표가 명부가 된다(지도 §5 축 가드가 막는 바로 그것) |
| **(B) 앱 첫 로그인 때 서버가 붙인다**                         | ✅   | ★**붙일 것이 이미 붙어 있다.** (g) 수락 콜러블이 `org_members/{orgId}_{uid}` 와 (프로젝트 초대가 있었다면) `memberRoles/{projectId}_{uid}`·`projects.members` 를 만든다 — 전부 계정 축 Firestore. 앱은 같은 Firebase 계정으로 로그인하므로, 착지 규칙(#1205 §5.8)대로 서버가 uid 에서 조직·프로젝트를 도출하면 끝이다. **신규 전달 메커니즘 0**                                  |

**축 규율 검증** — 이 설계가 건드리는 축:

```
계정 축(Firestore):  invitations → (수락) → org_members·memberRoles·projects.members → 앱 로그인 시 도출
익명 축(BQ):         install_attribution · analytics_identity … — ★무접촉. 링크백은 지금 그대로 돈다
링크표:              analytics_user_install — ★무접촉(인증 텔레메트리 배치가 만드는 기존 경로 그대로)
```

온보딩은 처음부터 끝까지 **계정 축 안에서만** 움직인다. 익명 축과 잇는 유일한 다리는 기존 링크표뿐이고 이 설계는 거기에 아무것도 더하지 않는다 — 축 가드(`assertAxisPurity`)·`team-usage-axis-guard` 에 걸릴 새 표면이 없다.

★하나만 새로 적는다: **`org_members.firstAppLoginAt`**(§7 도입 현황용). 앱이 첫 로그인 후 조직 부트스트랩 콜러블(Phase 1 의 착지 규칙용 콜러블과 같은 것)을 부를 때 서버가 없으면 한 번 찍는다. 계정 축 문서의 필드 1개 — BQ·텔레메트리·동의 게이트와 무관한 멤버십 사실이다(열람 고지는 §8).

## 5. ★온보딩 URL 판정 — 초대 링크는 `/join/<token>`. 슬러그 우선순위는 안 올라간다

티켓의 질문: 초대 메일에 들어가는 링크라 사람이 읽는 이름(슬러그)이 필요한가.

**판정: 필요 없다.** 초대 링크는 조직 URL 이 아니라 **1회용 토큰 링크**여야 하고, 그러면 URL 가독성 요구 자체가 사라진다:

1. **존재 비노출** — `/org/<slug>` 를 초대 랜딩으로 쓰면 링크를 주운 누구에게나 조직의 존재(와 이름)를 확인해 준다. `/join/<token>` 은 토큰 없이는 아무것도 말하지 않고, 만료·취소 시 #1205 §5.5 의 접힌 문구를 그대로 쓴다.
2. **읽는 이름의 자리는 URL 이 아니다** — 초대 메일의 신뢰는 제목·본문의 조직 표시명과 초대자가 만들고, 클릭 후 랜딩(`/join/<token>`)이 조직 표시명을 크게 보여준다. 받는 사람은 URL 을 읽고 클릭을 결정하지 않는다(메일 클라이언트가 링크를 래핑하는 경우도 많다).
3. **피싱 축에서도 토큰이 낫다** — 슬러그는 선점·사칭이 가능한 이름 공간이다(`/org/hypemarc` 비슷한 철자). 토큰은 흉내낼 대상 자체가 없다.
4. **이메일 결속** — 토큰은 초대 문서(초대 이메일)에 결속돼 다른 계정 로그인 시 룰이 read 를 거부한다(#1205 §5.4 — 룰 수준 강제). 조직 URL 은 이 성질을 줄 수 없다.

★토큰은 초대 문서 id(`{projectId}_{email}` — 이메일이 URL 에 노출된다)가 아니라 **문서에 담긴 난수 필드**로 한다. 링크가 슬랙에 전달·전달되는 물건이라 URL 에 이메일·프로젝트 id 를 싣지 않는다.

사장님 문장의 `marblo.app/{조직}` 의 실체는 **로그인 후 조직 홈 = `/org/<orgId>`**(#1333 §3 그대로)다. 팀원은 초대 링크로 들어와 수락하면 그 뒤부터 `/org/<orgId>` 가 자기 화면이 된다 — "조직 페이지에 먼저 들어와서"는 성립하되, 주소를 쳐서 들어오는 게 아니라 초대가 데려다 준다. **슬러그는 #1333 Phase 5 옵트인 그대로 둔다** — 우선순위를 올릴 근거가 초대 축에서 나오지 않았다. (올라가는 날은 "조직 주소를 입으로 전달"하는 요구 — 예: 사내 위키에 적어두는 상시 가입 링크 — 가 실재할 때다.)

| ④첫 접속·⑤첫 작업 여부 | ★**문면 밖** — "완료/실패한 작업 수" 는 사용량 집계 어휘이고, "이 사람이 언제 처음 접속했고 첫 작업을 끝냈는지" 는 개인의 행동 시점 사실이다. 좁게 읽으면 새 열람 항목이다 |

**권고**: #1335 는 **아직 배포 전**(승인 대기)이다. 지금 §2 문단에 한 구절을 더하면 개정을 두 번 하지 않고 발효일도 하나로 유지된다(#1333 §6.2 "고지가 넓고 기능이 좁은 것은 문제가 없다" 그대로):

> (기존 문안에 이어) …또한 조직 관리자는 초대한 팀원의 온보딩 진행 상태(초대 수락·앱 첫 접속·첫 작업 완료 여부와 그 시점)를 볼 수 있습니다.

배너 문구(#1335 §3)에는 안 더한다 — 배너는 이미 배포된 사용자에게 바뀐 것을 알리는 것이고, 온보딩 진행 열람의 대상자(신규 초대 팀원)는 가입 시점에 방침 전문을 보므로 배너 축에서는 알릴 대상이 없다.

## 10. ★마찰 정면 대응 — 단계를 더하는데 왜 이탈이 줄어드나

실측 퍼널 65 → 34 → 17 → 7 → 4 앞에서 "웹 단계 추가"를 정당화해야 한다. 논증 셋 + 대안 기각 하나:

1. **단계를 더하는 게 아니라 옮기는 것이다.** 오늘도 팀원은 가입·로그인·수락을 전부 해야 한다 — 단지 **설치 후 앱 안에서**, 그것도 초대의 존재를 알 방법이 없는 채로(§1.0). 웹 선행은 같은 단계들을 설치 앞으로 옮기고, 초대 링크가 그 단계들을 한 줄로 꿰게 만든다. 총 단계 수는 같거나 적다(발견 단계가 사라진다).
2. **이 퍼널의 대상이 다르다.** 65→34 는 콜드 베타 모집(개인 동기)이고, 초대 팀원은 조직이 결제한 좌석 + 관리자가 지목한 사람이다 — 완주 압력의 구조가 다르다. 그리고 개인 경로(콜드 유입이 실제로 흐르는 곳)는 ★무변이라 이 설계로 나빠질 수 있는 퍼널이 없다.
3. **실측 이탈 최대 구간은 웹이 아니라 설치 후다**(17 켜봄 → 7 완료). 웹 단계는 그 구간의 원인(준비 없는 설치 — 에이전트 계정 없음)을 설치 앞(G1)에서 제거한다. 웹에서 사람이 새는 것과 설치 후 못 쓰고 새는 것 중, 후자가 우리가 가진 가장 비싼 손실이었다.

**더 가벼운 안 검토 — "초대 메일에 다운로드 링크 직행, 수락은 앱에서"**: 웹 화면 0개로 오늘의 발견 문제만 고친 안이다. 기각 — ① (j) 부착이 다시 앱 안 수락에 걸려 "설치했는데 소속 없음" 상태가 남고(§1.2 가 무효), ② 가이드가 다시 설치 뒤로 밀리며(§1.3 무효), ③ 도입 현황의 ②수락 신호가 첫 실행 뒤로 밀려 퍼널이 2단으로 준다. 아낀 것은 웹 화면 2개(join·소속확인)뿐 — §11 의 최소 구현에서 그 둘이 가장 싼 조각이다.

## 11. ★첫 고객 한 팀의 최소 — 그리고 #1333 로드맵과의 정합

실사용 외부 팀 0. 이 온보딩은 "아직 없는 고객"용이므로 **첫 한 팀을 손으로 받는 데 필요한 최소**를 먼저 긋는다:

## 14. 열린 질문 (사장님·오케)

1. **§8 방침 한 구절** — 온보딩 진행 상태 열람 문구를 #1335 §2 에 합쳐 넣는 것의 승인(문안은 법무·사장님 몫, 여기는 범위만). 넣지 않으면 도입 현황 카드에서 ④⑤ 열을 빼고 ①② 2단으로 시작한다.
2. **v0 의 초대 전달** — 링크 복사로 시작하는 안. 첫 고객 인상 때문에 메일 자동 발송을 v0 에 당기길 원하시면 메일 인프라(발신 도메인·템플릿) 선행이 필요하다 — 지금 0 이다.
3. **G1 체크리스트의 강도** — 권고는 "확인만"(체크 강제 없음). 에이전트 계정이 없는 팀원이 많은 조직이 실제로 나타나면, 조직 단위 BYOK/좌석 브리핑 같은 더 강한 준비 단계를 그때 검토한다.
4. **(h)에서 가이드를 건너뛴 사람의 후속** — 앱 첫 실행 후 G2/G3 를 다시 보여줄 자리(앱 내 온보딩)는 이 설계 밖이다. 필요 판정은 도입 현황 ④→⑤ 구간의 실측이 말해 줄 것이다.
