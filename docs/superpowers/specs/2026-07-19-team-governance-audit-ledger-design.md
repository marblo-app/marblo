# 해자 ④ 팀 거버넌스 — AI 개발 작업의 의사결정 원장

**첫 수직 슬라이스 설계 (2026-07-19 승인)**

## 0. 이 문서가 정하는 것

Marblo 해자 ④(팀 거버넌스)를 구현하는 첫 슬라이스의 설계. 워크트리 감사 UX는
독립 기능이 아니라 **이 원장 위에 얹히는 뷰**로 만든다.

### 왜 워크트리 감사가 ④에 속하는가

작업자가 워크트리를 볼 때 실제로 답해야 하는 질문이 ④의 요구와 1:1로 겹친다:

| 워크트리 감사 질문              | ④ 의사결정 원장                              |
| ------------------------------- | -------------------------------------------- |
| 이건 어느 티켓 건인가           | 누가 어떤 작업을 발주했는가                  |
| 누가(어느 에이전트가) 쓰고 있나 | 어떤 에이전트가 어떤 파일을 수정했는가       |
| 뭐가 바뀌었나 / 머지됐나        | 어떤 검증을 통과했는가 / 왜 PR이 Merge됐는가 |
| 지워도 안전한가                 | 어느 의사결정까지 되돌려야 하는가            |

우연이 아니다. **워크트리는 "오케가 왜 이 작업을 스폰했는가"가 파일시스템에
물리적으로 구현된 결과물**이다. 메모 ④가 지적한 "Git은 오케스트레이터가 왜
스폰했는지까지 설명하지 않는다"의 빈칸에 워크트리가 정확히 놓인다.

### 핵심 인식 — 개수가 아니라 구조가 문제다

152개를 20개로 줄여도 그 20개가 "경로 문자열의 평평한 목록"이면 감사가 안 된다.
반대로 152개여도 각각이 티켓·에이전트·PR에 묶여 상태가 보이면 감사가 된다.
**삭제는 개수를 줄일 뿐 감사 가능성을 만들지 않는다.**

그리고 정체성이 없는 것은 감사할 수도, 안전하게 지울 수도 없다. 인수인계 문서의
*"판별 불가한 건 지우지 말 것"*이 같은 이야기다 — 감사와 정리가 **같은 선행조건**에서
막혀 있었다.

## 1. 결정 사항

| 결정        | 선택                       | 근거                                                                                                                             |
| ----------- | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 원장 소유   | **이중 경로**              | 식별 원장 = 고객 테넌트(Firestore, 프로젝트 스코프, 조회·내보내기·보존기간 통제). 비식별 파생만 Marblo BQ로 흘려 ③ 플라이휠 유지 |
| 기록 단위   | **append-only 이벤트**     | 원장(ledger)은 사후 수정 불가 장부. "누가 승인했는가"를 나중에 고칠 수 있으면 감사 증거 가치가 0                                 |
| 첫 슬라이스 | **한 티켓의 전 생애**      | 발주→스폰→파일수정→검증→머지/폐기 한 줄기. 지금 고통(152개)을 풀면서 기업 고객에게 데모 가능한 완결된 서사가 나옴                |
| 변조 방지   | **해시 체인 + 체크포인트** | 룰만으로는 관리자 SDK 경유 삭제를 못 막음. 차별점이 "변조 불가한 귀속"인데 여기서 무너지면 Orca가 활동 피드 붙이는 순간 따라잡힘 |

### 1차 사용자

**팀·기업 고객, 규제·책임 목적.** 사장님 개인의 에이전트 감독은 부수 효과이지
설계 기준이 아니다. 이 구분이 스키마·스코프·보존 정책을 좌우한다.

## 2. 이미 있는 것 (재구현 금지)

원장을 처음부터 짓는 게 아니다. 실측 결과:

| 자산                 | 위치                                                  | 상태                                                                          |
| -------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------------- |
| `audit_logs`         | `firestore.rules:233`, 쓰기 `mcp-server/tools.ts:676` | **이미 append-only 불변**(`update:false, delete:false`). MCP 툴 호출마다 적재 |
| `auditedTool` 래퍼   | `mcp-server/tools.ts:894`                             | **MCP 툴 32개 전부**를 감쌈. 에이전트 행위의 단일 초크포인트                  |
| `merge_history`      | `firestore.rules:244`                                 | 룰 주석에 **"worktree audit trail"** 명시. 머지 초크포인트 기록, 동일 불변    |
| `recordMergeHistory` | `main.ts:1936`, `worktree-ipc.ts:455`                 | 단일 캡처 지점 설계 이미 확립                                                 |
| 안전 판정            | `#501` 머지분                                         | dirty/unpushed/busy 워크트리 보존 로직                                        |
| Activity Stream      | `services/activityStreamService.ts`                   | 이미 `audit_logs` 구독 렌더                                                   |

현재 한 건의 기록:

```
{ projectId, agentId, toolName, params(200자 절단), result(500자 절단),
  duration, success, createdAt }
```

귀속도 `attributionAgentId()`가 워커 에이전트를 정확히 집어낸다.

### ★캡처 지점을 새로 만들지 않는다

에이전트의 상태 변경은 **MCP→Firestore 직접 write라 렌더러를 안 거친다.**
원장 훅을 렌더러에 걸면 "사람이 UI를 클릭한 경우"만 잡혀 정작 감사 대상인
AI 행위가 통째로 빠진다 (과거 텔레메트리에서 실제로 겪은 함정 —
`task_outcomes` 29행/조인 1건 사고).

→ `auditedTool`(32개 툴)을 재사용한다. 렌더러보다 아래라 이 함정을 구조적으로 피한다.

## 3. 구멍 4개

| ④의 요구                      | 현재                                  | 필요                             |
| ----------------------------- | ------------------------------------- | -------------------------------- |
| 누가 **발주**했는가           | ❌ `agentId`만, 사람 주체 없음        | `actorUid` 승계                  |
| 어떤 **모델·프롬프트**        | ❌ 없음                               | `model`/`tier`/`instructionHash` |
| 어떤 에이전트가 **어떤 파일** | ⚠️ `merge_history`에만, 원장과 미연결 | 워크트리 정체성으로 조인         |
| **변조 불가**                 | ⚠️ 룰로 client update/delete만 차단   | 해시 체인 + 체크포인트           |

## 4. ★즉시 고쳐야 할 보안 구멍 (기획과 별개)

```
match /audit_logs/{logId} {
  allow read: if isAuthenticated();   // ← 인증만 되면 전 테넌트 읽힘
```

`audit_logs` · `merge_history` · `telemetry_events` 세 컬렉션이 프로젝트 스코프가
아니다. 다른 컬렉션은 `isProjectMember()`로 스코프됐는데(크로스테넌트 누출 차단
작업 `a7iz1slr` 산물) 이 셋만 빠져 있다.

**기업 고객에게 "규제·책임용 감사 원장"으로 파는 물건이 크로스테넌트로 읽히면
그 자체가 컴플라이언스 사고다.** 팔 수 있는 상태가 아니라 지금 열려 있다.

## 5. 스키마

굵은 것이 신규:

```
ledgerEvent {
  projectId, agentId, toolName, params, result, duration, success, createdAt,
  actorUid,         // 발주한 사람
  model, tier,      // 어떤 모델이 쓰였는가
  instructionHash,  // 프롬프트 원문 대신 해시
  taskId, worktreeId,
  seq, prevHash, hash
}
```

### 왜 프롬프트 원문이 아니라 해시인가

원문을 원장에 복제하면 지시문에 섞인 비밀·고객 데이터까지 **불변 컬렉션에 영구
박제**된다. 불변성은 잘못 넣은 것도 못 지운다는 뜻이므로, 감사 원장에는 오히려
적게 담아야 한다. 원문 대조가 필요하면 해시로 티켓과 맞춘다.

## 6. 해시 체인 — 설계의 핵심 난점

프로젝트 단위 단일 체인은 **에이전트 5기 동시 write 시 매 write마다 트랜잭션
경합**이 생긴다. 현재 `auditLog()`는 fire-and-forget이라 MCP 툴 호출을 안 막는데,
트랜잭션을 넣으면 모든 툴 호출이 느려지고 실패 지점이 생긴다.

### 채택: 에이전트별 체인 + 주기적 체크포인트

- 각 이벤트는 `(projectId, agentId)` 체인에 `seq`+`prevHash`로 연결.
  **에이전트당 MCP 서버는 하나라 쓰기가 자연히 단일 순서** → 경합 없음,
  비차단 성질 유지
- main 프로세스가 주기적으로 모든 체인 head를 모아 머클 루트를
  `ledger_checkpoints`에 기록 → **체인 통째 삭제도 탐지**, 에이전트 간 시점 순서 고정

| 공격                  | 탐지              |
| --------------------- | ----------------- |
| 이벤트 중간 삭제·변조 | 체인 단절         |
| 체인 통째 삭제        | 체크포인트 불일치 |

## 7. 조용한 유실 수정 (필수)

```
addDoc(collection(db, "audit_logs"), {...}).catch(err =>
  console.error("[Audit] Failed to write audit log:", err));
```

**감사 기록 실패가 콘솔 한 줄로 삼켜진다.** 활동 피드용으로는 괜찮지만 규제
원장으로는 치명적 — 네트워크가 끊긴 30분 동안의 에이전트 행위가 흔적 없이
사라지고 그 공백을 설명할 방법이 없다. **"기록이 없다"와 "일어나지 않았다"를
구분할 수 없게 된다.**

→ 로컬 스풀(디스크) + 재시도 + 복구 후 `seq` 순서 보존 재적재.
체인이 있으므로 유실 여부 자체는 `seq` 구멍으로 드러난다.

## 8. 워크트리 정체성

`~/.marblo/worktrees/<projectId>/<taskId>` 경로 규약이 이미 있다.

- **경로에서 역산**: projectId, taskId
- **원장에서 조인**: agentId, model, PR, 머지 여부, 안전 판정

워크트리를 무거운 Firestore 객체로 만들지 않는다. **원장의 파생 뷰로 충분** —
워크트리는 지워지는 일시적 존재이지만 원장은 남아야 하므로 진실원을 원장에 둔다.

물리 정리는 이 분류의 **부산물**로 안전하게 따라온다. 순서를 거꾸로 하면
기준 없이 지우게 되고, 판별 불가한 것을 지우는 위험이 생긴다.

## 9. ★구현 순서 (순서 자체가 안전장치)

룰 조이기가 이 슬라이스에서 압도적으로 위험하다. 이 프로젝트에서 이미 두 번
사고가 난 패턴이다:

- **#406** — fail-closed 룰 배포 후 메인 프로세스 custom-token 미인증 →
  Firestore 전면 permission-denied, revert 복구
- **#428** — 코드 게이트 4회 PASS인데 라이브에서 얼어붙음 → 리버트(#430)

**교훈: 테스트 통과 ≠ 라이브 인증 성공.** 렌더러와 메인 프로세스가 다른 인증
경로를 타서, 렌더러 기준 검증은 메인이 죽는 걸 못 본다.

`audit_logs`를 `isProjectMember()`로 조이면 **쓰는 쪽이 MCP 서버(에이전트
프로세스)**다. 이들이 `project.members` 소속 uid로 인증하는지 확인 없이 조이면
모든 에이전트의 감사 기록이 조용히 permission-denied로 죽는다 — 그리고 지금
그 실패는 `console.error` 한 줄로 삼켜지므로 **아무도 모른다.**

따라서:

1. **조용한 유실 수정** (스풀+재시도) — 실패가 보이게 만든다
2. **룰 조이기** + 라이브 3경로(메인 프로세스·MCP 서버·렌더러) 실제 R/W 왕복 확인
3. **체인·체크포인트**
4. **감사 뷰** (워크트리 목록 = 진입점)

거꾸로 하면 룰이 뭘 깨뜨렸는지 관측할 수단 없이 조이게 된다.

## 10. 마이그레이션 — 소급 보증은 포기한다

기존 `audit_logs` 엔트리에는 체인이 없다. **소급해서 변조 불가로 만들 수 없다** —
이미 쓰인 기록은 그 시점에 무결성 증거가 없었다. 없는 보증을 있는 척하면 그게
더 큰 컴플라이언스 문제다.

→ **제네시스 체크포인트**를 찍고, 이전 기록은 `preLedger: true`로 보존하되
감사 리포트에서 **"무결성 미보증 구간"으로 명시 표기**한다. 기업 고객에겐
"언제부터 보증되는가"가 명확한 게 오히려 신뢰를 준다.

## 11. 실패 모드

| 실패                        | 대응                                                    |
| --------------------------- | ------------------------------------------------------- |
| Firestore 쓰기 실패         | 로컬 스풀 → 재시도 → 복구 시 `seq` 순서 보존 재적재     |
| 스풀 디스크 무한 증가       | 상한 캡 + 초과 시 사용자 알림 (조용히 버리지 않음)      |
| 체크포인트 실패             | 다음 주기 재시도. 공백은 리포트에 표기                  |
| 시계 왜곡                   | 순서 권위는 `createdAt`이 아니라 `seq`+체인             |
| 에이전트 크래시로 체인 중단 | `seq` 구멍으로 드러남 — 유실을 숨기지 않는 게 설계 목표 |

## 14. ③ 플라이휠과의 관계

워크트리 수명주기(스폰 → 작업 → CI → 수정횟수 → merge/revert)가 ③이 원하는
이벤트 스트림과 같은 모양이다. 감사용 이벤트를 제대로 쏘면 **비식별 파생이
그대로 ③의 원료**가 된다. ②의 "티켓 의존성 그래프 / 에이전트별 성공·실패 이력"도
같은 조인에서 나온다.

단 식별성 요구가 반대다 — ④는 귀속이 살아야 하고 ③은 비식별이어야 한다.
