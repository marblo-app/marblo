# Marblo v3.0 — 에이전트 팀 워크스페이스

> "AI 구독을 엔지니어링 팀으로 바꿔주는 워크스페이스"

### Marblo (마블로) 랜딩 페이지 카피라이팅

#### [메인 히어로 카피 / Slogan]

> **"태스크를 보드에 올리세요. 목표까지 알아서 도달하는 AI 워크스페이스"** (Drop your tasks on the board. Let your agents roll.)

**서브 카피 (Sub-copy):** 인간은 룰(Governance)을 설계하고, AI 에이전트는 보드(Task) 위를 움직입니다. 팀의 업무를 게임처럼 직관적으로 자동화하고 완벽하게 통제하는 엔터프라이즈 에이전트 플랫폼, **마블로(Marblo)**를 만나보세요.

## 1. 핵심 통찰: 물리 분리 에이전트

### Claude Code 팀 vs Marblo 팀

```
Claude Code (기존 방식):
┌─────────────────────────────────┐
│ Claude Code Max ($100/월)       │
│                                 │
│  Main Agent ──┬── Sub-agent 1   │  ← 같은 프로세스, 같은 구독
│               ├── Sub-agent 2   │  ← 컨텍스트 분할됨
│               └── Sub-agent 3   │  ← 하나 바빠지면 전체 느려짐
│                                 │
│  한 구독의 rate limit 공유       │
└─────────────────────────────────┘

Marblo v3.0:
┌─────────────────────────────────────────────────────┐
│ Marblo 워크스페이스                             │
│                                                     │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐          │
│  │Claude Max│  │Claude Max│  │Gemini    │          │
│  │ $100/월  │  │ $100/월  │  │ Codex    │          │
│  │ 계정 A   │  │ 계정 B   │  │ 무료/Pro │          │
│  │          │  │          │  │          │          │
│  │ Backend  │  │ Frontend │  │ Research │          │
│  │ Agent    │  │ Agent    │  │ Agent    │          │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘          │
│       │              │              │                │
│       └──────────────┼──────────────┘                │
│                      │                               │
│              ┌───────┴───────┐                       │
│              │ Orchestrator  │  ← Claude Code 내장    │
│              │ (통합 관리만)  │     에이전트 스폰 안 함  │
│              └───────────────┘     MCP로 조율만        │
│                                                     │
│  각 에이전트 = 독립 프로세스, 독립 구독, 독립 rate limit │
└─────────────────────────────────────────────────────┘
```

### 왜 물리 분리가 중요한가

| | Claude Code 서브에이전트 | Marblo 물리 분리 |
|--|----------------------|---------------------|
| **프로세스** | 하나의 Claude Code 안에서 fork | 각각 독립 CLI 프로세스 |
| **구독** | 1개 구독 공유 | 각자 자기 구독 (BYOK) |
| **Rate Limit** | 공유 → 3명이면 1/3 속도 | 독립 → 3명 모두 풀 속도 |
| **모델** | Claude만 가능 | Claude, Gemini, GPT, Codex 혼합 |
| **컨텍스트** | 부모가 분배 (제한적) | 각자 풀 컨텍스트 200K+ |
| **장애 격리** | 하나 멈추면 전체 영향 | 하나 멈춰도 나머지 정상 |
| **비용 최적** | $100/월로 3명 = 느림 | $100×2 + 무료 = 3명 풀 속도 |

**결론:** 같은 돈이면 물리 분리가 3배 빠르고 안정적이다.

### /model 선택 = CLI 도구 선택

**핵심: 각 터미널 탭에서 다른 AI CLI를 실행하는 것**

| 모델 선택 | 실행되는 CLI | 구독 | 특징 |
|-----------|------------|------|------|
| Claude Code | `claude` | Max $100/월 또는 Pro $20/월 | 코딩 최강, MCP 네이티브 |
| Gemini Codex | `gemini` (향후) | Google One AI Premium | 긴 컨텍스트, 리서치 강점 |
| GPT CLI | `codex` / `openai` | ChatGPT Plus $20/월 | 범용, 플러그인 생태계 |
| Custom | 사용자 지정 명령 | 자유 | 오픈소스 LLM 등 |

**무제한 요금제 활용 전략:**
```
Claude Code Max ($100/월)  × 2개 = Backend + Frontend
Gemini Codex (무료~$20/월) × 1개 = Research / Docs
GPT CLI ($20/월)           × 1개 = Test / QA
────────────────────────────────
총 $240/월 = 4명의 풀타임 AI 엔지니어

vs Claude Code 서브에이전트:
Claude Code Max ($100/월) × 1개 = 4명 서브에이전트 (rate limit 공유)
→ 실질 속도 1/4, 컨텍스트 분할
```

## 4. Orchestrator 역할

### Claude Code = 내장 오케스트레이터

```
사용자: "회원가입 기능 만들어줘"
       │
       ▼
┌─────────────────────────────────────────┐
│  Orchestrator (Claude Code 내장)         │
│                                          │
│  1. 자연어 분석 → 태스크 분해             │
│     ├ BE-01: Auth API (backend)          │
│     ├ BE-02: DB Schema (backend)         │
│     ├ FE-01: Login UI (frontend)         │
│     ├ FE-02: Signup UI (frontend)        │
│     └ TS-01: Auth E2E Test (test)        │
│                                          │
│  2. 의존성 설정                           │
│     BE-02 → BE-01 → FE-01, FE-02 → TS-01│
│                                          │
│  3. 칸반에 티켓 일괄 생성 (MCP)           │
│                                          │
│  4. 각 에이전트가 자율적으로 claim         │
│     (오케스트레이터가 할당하지 않음)        │
│                                          │
│  5. 진행 모니터링 + 리뷰 승인/반려         │
│     (사용자에게 리뷰 요청 전달)            │
└─────────────────────────────────────────┘
```

**오케스트레이터는 코딩하지 않는다.** 역할 분리:

| 역할 | 담당 | 하는 일 |
|------|------|--------|
| Orchestrator | Claude Code (메인) | 태스크 분해, 티켓 생성, 리뷰, 보고 |
| Worker Agents | 각 터미널 탭의 독립 CLI | 실제 코딩, 테스트, 문서 작성 |

이 구조의 장점:
- 오케스트레이터는 가벼운 작업만 → rate limit 거의 안 씀
- 무거운 코딩은 각 독립 에이전트가 자기 구독으로 처리
- 오케스트레이터가 죽어도 워커들은 자율 루프로 계속 작업

## 5. Claude Code 자체 기능과의 비교

### 정면 비교

| 기능 | Claude Code 내장 팀 | Marblo v3.0 |
|------|-------------------|-------------------|
| **에이전트 수** | 서브에이전트 (부모 의존) | 독립 에이전트 (물리 분리) |
| **Rate Limit** | 1개 구독 공유 | 각자 자기 구독 |
| **모델 다양성** | Claude만 | Claude + Gemini + GPT + Custom |
| **시각화** | CLI 텍스트만 | 칸반 보드 + 코드 뷰어 + 대시보드 |
| **태스크 영속성** | 세션 끝나면 사라짐 | DB에 영구 저장 |
| **상태 머신** | 없음 (자유 상태) | 7단계 강제 (TODO→DONE) |
| **PM 피드백** | 텍스트 메시지만 | pty stdin 주입 (실시간) |
| **히스토리** | 컨텍스트 윈도우 내만 | 전체 활동 로그 영구 |
| **코드 뷰** | 없음 (터미널만) | VS Code 스타일 파일 브라우저 |
| **비용 효율** | $100으로 팀 = 느림 | $100×N으로 팀 = 각각 풀 속도 |
| **장애 격리** | 부모 죽으면 전체 사망 | 하나 죽어도 나머지 정상 |
| **비개발자 접근** | CLI만 (개발자 전용) | GUI (PM, Tech Lead 사용 가능) |

### Marblo가 이기는 5가지 핵심

#### 1. 물리 분리 = 진짜 병렬

```
Claude Code 팀:
  Time ──────────────────────────────────▶
  Agent A: ████████░░░░████████░░░░████████  (rate limit 대기)
  Agent B: ░░░░████████░░░░████████░░░░████  (번갈아 실행)
  Agent C: ░░░░░░░░░░░░████████░░░░░░░░░░░░

Marblo:
  Time ──────────────────────────────────▶
  Agent A: ████████████████████████████████  (독립 구독)
  Agent B: ████████████████████████████████  (독립 구독)
  Agent C: ████████████████████████████████  (독립 구독)
```

#### 2. 멀티 모델 = 최적 배치

```
태스크 특성에 맞는 모델 배치:
- 코딩 (복잡한 로직)  → Claude Code Max (추론 최강)
- 코딩 (빠른 반복)    → Claude Code Pro (속도 우선)
- 리서치/분석          → Gemini (긴 컨텍스트, 검색 강점)
- 문서/번역            → GPT (범용, 다국어 강점)
- 테스트 생성          → Codex (코드 생성 특화)
```

#### 3. 비주얼 워크스페이스 = PM 접근성

```
Claude Code: 개발자만 사용 가능 (CLI)
Marblo: PM이 보드에서 관찰 + 승인 + 피드백 (GUI)

→ "개발팀 전체"가 쓸 수 있음 (개발자 + PM + 디자이너)
→ Claude Code는 "개발자 1명의 도구"에 머무름
```

#### 4. 영속성 = 프로젝트 관리

```
Claude Code 팀: 세션 끝 → 전부 사라짐 → 다음날 처음부터
Marblo:   태스크 히스토리, 활동 로그, 의존성 그래프 영구 보존
              → 3개월 전 프로젝트도 /tf-resume로 즉시 복원
```

#### 5. 코드 뷰어 = 완전한 워크스페이스

```
기존: 칸반(Marblo) + 코드(VS Code) + 터미널(별도) = 3개 앱 전환
v3.0: 칸반 + 코드 + 터미널 = 하나의 앱에서 전부 해결

→ 에이전트가 수정한 파일을 즉시 확인
→ 코드 리뷰를 앱 안에서 바로 처리
→ VS Code 열 필요 없음 (간단한 수정은 인라인으로)
```

### 코드 뷰어 구현

| 방식 | 라이브러리 | 장단점 |
|------|-----------|--------|
| **Monaco Editor (추천)** | `@monaco-editor/react` | VS Code 동일 엔진, 구문 강조, 자동완성, Git diff 뷰 내장 |
| CodeMirror | `@codemirror/view` | 가벼움, 모바일 호환, 하지만 기능 적음 |
| 읽기 전용 | `react-syntax-highlighter` | 가장 가벼움, 편집 불가 |

Monaco 선택 이유:
- VS Code와 동일한 편집 경험 → 사용자 학습 비용 0
- Git diff 뷰 내장 → 에이전트 변경사항 리뷰에 필수
- TypeScript/Python/Dart 등 언어별 구문 강조 자동 지원
- Electron 환경에서 성능 문제 없음

```

- 에이전트가 수정한 파일에 아이콘 배지 (🔵 Backend-1, 🟢 Frontend-1)

### 에이전트 간 컨텍스트 동기화

```
동기화 방법: Git 중심

1. 에이전트 A가 코드 커밋
   → Git hook (post-commit) 발동
   → Marblo MCP에 이벤트 발행: "BE-01 커밋: auth_router.py 추가"

2. Marblo 오케스트레이터가 이벤트 수신
   → 관련 에이전트 판단 (depends_on 체크)
   → 해당 에이전트 터미널에 알림 주입:
     "[Marblo] Backend-1이 auth_router.py를 커밋했습니다. git pull 후 작업하세요."

3. 에이전트 B가 git pull → 최신 코드 확보 → 작업 계속

충돌 방지:
- 티켓 단위로 작업 파일 범위 지정 (scope 필드)
- 같은 파일 동시 수정 감지 → 오케스트레이터가 경고
- 브랜치 전략: 에이전트별 feature branch → 오케스트레이터가 머지
```

### 충돌 방지 메커니즘

```
1. 티켓 단위 격리
   - 각 티켓에 scope (관련 파일/디렉토리) 지정
   - 다른 사람의 에이전트가 같은 파일 수정 시도 → 경고

2. 브랜치 전략
   - 각 에이전트가 feature branch에서 작업
   - 브랜치명: {owner}/{agent}/{ticket} (예: minsu/FE-1/FE-02)
   - 머지는 리뷰 승인 후 자동 (merge agent)

3. 실시간 잠금
   - 에이전트가 파일 수정 시작 → 파일 잠금 표시
   - 다른 에이전트가 같은 파일 접근 시 → 대기 또는 알림
   - Firestore에서 distributed lock 구현
```

### 팀 플랜 가치

```
2명 개발자 × 3개 에이전트 = 6명 AI 엔지니어가 동시 작업
+ PM이 보드에서 실시간 관찰 + 승인

vs 현재 방식:
  각자 Cursor에서 1:1로 작업 → 머지할 때 충돌 → 소통 비용 높음

Marblo 팀:
  하나의 보드 → 태스크 자동 분배 → 독립 에이전트 병렬 작업 → 자동 머지
  = 소통 비용 최소화, 처리량 극대화
```

## 12. Agent Flow 상세 — 노드 기반 자동화 엔진

### 핵심 컨셉

에이전트 플로우는 **3가지 방식으로 만들 수 있다:**

```
방법 1: 터미널에서 LLM에게 요청 (자연어)
┌──────────────────────────────────────────────────────────┐
│ [Orchestrator 터미널]                                     │
│                                                           │
│ > "YouTube 영상 URL 받아서 자막 분석하고                    │
│    블로그 글로 변환하는 파이프라인 만들어줘"                  │
│                                                           │
│ Claude: 플로우를 생성합니다...                              │
│ ✓ Node 1: Input (YouTube URL)                             │
│ ✓ Node 2: Gemini (자막 추출 + 분석)                       │
│ ✓ Node 3: Claude (블로그 글 생성)                          │
│ ✓ Node 4: GPT (교정 + SEO 최적화)                         │
│ ✓ Node 5: Output (Markdown 파일 저장)                     │
│ Flow 'youtube-to-blog' 생성 완료. Flows 탭에서 확인하세요.  │
└──────────────────────────────────────────────────────────┘
       │
       ▼ Flow 탭에 자동 반영

방법 2: Flow 탭에서 GUI로 직접 구성
┌──────────────────────────────────────────────────────────┐
│ 🔀 Flow Editor                                           │
│                                                           │
│  노드 팔레트 (좌측)        캔버스 (우측)                   │
│  ┌────────────┐           ┌─────┐    ┌─────┐             │
│  │ 📥 Input    │           │ IN  │───▶│ LLM │──▶ ...     │
│  │ 🤖 Agent   │           └─────┘    └─────┘             │
│  │ 🧠 LLM     │                                          │
│  │ 🔌 API     │    드래그 앤 드롭으로 노드 추가             │
│  │ 👤 Human   │    노드 간 연결선 드래그                    │
│  │ 🔀 Branch  │    각 노드 클릭 → 설정 패널                │
│  │ 📤 Output  │                                          │
│  └────────────┘                                          │
└──────────────────────────────────────────────────────────┘

방법 3: 혼합 (LLM이 초안 → 사용자가 수정)
  터미널에서 "결제 시스템 플로우 만들어줘" → 자동 생성
  → Flow 탭에서 노드 추가/삭제/연결 수정 → 커스텀 완성
```

### 노드 타입 상세

#### 1. Input 노드 — 데이터 진입점

```
┌─────────────────────┐
│ 📥 Input             │
│                      │
│ 타입:                │
│ ○ 수동 입력 (텍스트)  │
│ ○ URL                │
│ ○ 파일 업로드         │
│ ○ Webhook (외부 트리거)│
│ ○ 스케줄 (cron)       │
│ ○ 이전 플로우 출력     │
└─────────────────────┘
```

#### 2. LLM 노드 — 단순 프롬프트 실행

```
┌─────────────────────────┐
│ 🧠 LLM Action            │
│                          │
│ 모델: [Claude Sonnet ▼]  │
│                          │
│ 시스템 프롬프트:          │
│ ┌──────────────────────┐│
│ │너는 기술 블로그 작성자 ││
│ │다. 입력된 내용을 기반  ││
│ │으로 블로그 글을 작성.  ││
│ └──────────────────────┘│
│                          │
│ 입력: {{prev.output}}    │
│ 출력: 텍스트 (다음 노드)  │
│                          │
│ API 키: [BYOK 설정 ▼]    │
└─────────────────────────┘

특징:
- 1회성 프롬프트 실행 (대화 없음)
- API 호출 기반 (구독 아님, 토큰 과금)
- 가볍고 빠름 — 간단한 변환/분석에 적합
- 모델 자유 선택 (Claude/GPT/Gemini API)
```

#### 3. Agent 노드 — 독립 에이전트 실행 (핵심 차별점)

```
┌──────────────────────────────┐
│ 🤖 Agent                      │
│                               │
│ 이름: [Backend-Builder   ]    │

│ 역할: [backend           ▼]   │
│ 스킬: backend_agent.md        │
│                               │
│ 실행 방식:                     │
│ ○ 자율 모드 (스킬 기반 자동)    │
│ ● 지시 모드 (입력 데이터 전달)   │
│                               │
│ 입력: {{prev.output}}         │
│ 지시: "이 API 스펙대로 구현해"   │
│                               │
│ 터미널: [Agent 탭에서 실행 ▼]   │
│ 타임아웃: [30분          ]     │
│                               │
│ ┌───────────────────────────┐ │
│ │ 🤖 Sub-Agents (선택)       │ │
│ │  + Add Sub-Agent           │ │
│ │  ├ Research (Gemini)       │ │
│ │  └ Test (GPT)              │ │
│ └───────────────────────────┘ │
└──────────────────────────────┘

특징:
- 독립 PTY에서 CLI 에이전트 실행
- 무제한 구독 활용 (Max/Pro)
- 실제 코딩, 파일 생성, 테스트 실행 가능
- 하위 에이전트 스폰 가능 (노드 안의 노드)
- 결과 = 커밋, 파일, 테스트 결과 등
```

#### 4. API 노드 — 외부 서비스 호출

```
┌─────────────────────────┐
│ 🔌 API Call              │
│                          │
│ Method: [POST     ▼]    │

│                          │
│ 응답 매핑:               │
│ output = response.data   │
└─────────────────────────┘

예시:
- YouTube Data API → 자막 가져오기
- GitHub API → PR 생성
- Slack API → 알림 전송

```

#### 5. Human 노드 — 사람 승인 대기

```
┌─────────────────────────┐

│                          │

### LLM 노드 vs Agent 노드 — 언제 뭘 쓰나

| | 🧠 LLM 노드 | 🤖 Agent 노드 |
|--|-------------|--------------|
| **실행** | 1회 API 호출 | 독립 PTY에서 CLI 실행 |
| **비용** | 토큰 과금 (API) | 무제한 구독 활용 |
| **지속성** | 상태 없음 (stateless) | 세션 유지 (stateful) |
| **능력** | 텍스트 입출력만 | 파일 생성, 코딩, 테스트, Git |
| **속도** | 빠름 (초 단위) | 느림 (분 단위) |
| **하위 에이전트** | 불가 | 가능 (sub-agent 스폰) |
| **적합한 작업** | 분석, 변환, 요약, 분류 | 코딩, 구현, 테스트, 배포 |

```
판단 기준:
- 텍스트만 처리? → 🧠 LLM 노드
- 파일/코드 건드려야? → 🤖 Agent 노드
- 빠르게 끝나야? → 🧠 LLM 노드
- 복잡한 멀티스텝? → 🤖 Agent 노드 (+ Sub-Agent)
```

### 플로우 + 칸반 통합

```
Flow의 Agent 노드가 실행되면:
1. 칸반에 자동 티켓 생성 (또는 기존 티켓 연결)
2. Agent가 티켓 claim → IN_PROGRESS
3. 작업 완료 → REVIEW (Human 노드가 있으면)
4. PM 승인 → DONE → 다음 노드 트리거

→ Flow 뷰: 파이프라인 전체 흐름 시각화
→ Board 뷰: 현재 실행 중인 노드들의 티켓 상태
→ 같은 데이터, 다른 관점
```

### 플로우 저장 + 재사용

```
저장된 플로우 = JSON 템플릿
├─ 개인 플로우: 내 워크스페이스에 저장
├─ 팀 플로우: 프로젝트 팀원 모두 사용 가능
└─ 커뮤니티 플로우: 마켓플레이스에 공유 (v3.5+)

예시:
- "YouTube → 블로그" 플로우를 한번 만들면
- URL만 바꿔서 반복 실행
- 팀원도 같은 플로우 사용 가능
- 커뮤니티에서 인기 플로우 다운로드
```

## 15. Flow → Docker → Cloud 배포 엔진

### 현재 vs v3.0

```
현재 (수동 파이프라인):
1. 클로드코드에서 Python 스크립트 작성
2. Dockerfile 수동 작성
3. gcloud builds submit → Cloud Run 배포
4. Cloud Scheduler에 cron 수동 등록
5. 로그는 Cloud Logging에서 따로 확인
6. 수정하면 1~5 전부 반복

→ 동작은 하지만 전체 흐름이 안 보임
→ 어떤 스케줄이 뭘 호출하는지 머릿속에만 있음

v3.0 (Flow 탭):
┌──────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌────────┐
│⏰9AM │──▶│🔌YouTube │──▶│🧠Gemini  │──▶│🧠Claude  │──▶│📤Slack │
│Daily │   │API 수집   │   │자막 분석  │   │블로그 변환│   │알림    │
└──────┘   └──────────┘   └──────────┘   └──────────┘   └────────┘

→ 전체 파이프라인이 한눈에 보임
→ 노드 클릭 → 로그/상태 즉시 확인
→ [Deploy] 버튼 → Docker 패키징 → Cloud Run 자동 배포
→ 스케줄 변경도 Flow 에디터에서 직접
```

### 배포 타겟 옵션

```
[🚀 Deploy ▼]

○ Docker Compose (로컬/VPS)
  → docker-compose.yml + .env
  → docker compose up -d

● GCP Cloud Run (추천)
  → Dockerfile + cloudbuild.yaml + scheduler.json
  → gcloud builds submit 자동 실행
  → Cloud Scheduler 자동 등록

○ AWS Lambda + EventBridge
  → handler.py + serverless.yml
  → serverless deploy

○ Self-hosted (Cron + Docker)
  → docker-compose.yml + crontab
  → SSH 배포
```

### Tier 1 — 즉시 구현 (v3.1 첫 릴리스)

#### 17-1. Health Check + Auto-Restart

```
목적: 에이전트 프로세스 장애 시 자동 복구
방식:
  - PTY 세션의 exit 이벤트 감지 (기존 onExit 활용)
  - 비정상 종료(exit code ≠ 0) 시 자동 재시작
  - 재시작 전 exponential backoff (1s → 2s → 4s → max 30s)
  - 최대 재시작 횟수 설정 (기본 5회, 초과 시 FAILED 상태로 전환)
  - UI에 재시작 카운트 및 마지막 에러 표시

구현 위치:
  - electron/agent-manager.ts: 재시작 로직
  - electron/main.ts: IPC 이벤트 전파
  - src/components/agents/AgentCard.tsx: 상태 표시 UI
```

#### 17-6. Routines (스케줄 기반 자동 실행)

```
목적: 정해진 시간/주기로 에이전트 작업 자동 실행
Flows와의 차이:
  - Flow: 복잡한 다단계 워크플로우 (DAG 기반, 승인 게이트 포함)
  - Routine: 단순 반복 작업 스케줄링 (cron 기반)

방식:
  - Routine 정의:
    { name, schedule (cron), agentId, prompt, enabled }
  - 예시:
    - "매일 09:00 백엔드 테스트 실행" → 0 9 * * *
    - "매주 월요일 코드 리뷰" → 0 10 * * 1
    - "매시간 보안 스캔" → 0 * * * *
  - Electron main process에서 node-cron으로 실행
  - 실행 이력 저장 (Firestore: routine_logs)

구현 위치:
  - electron/routine-scheduler.ts (신규)
  - src/components/routines/RoutineList.tsx (신규)
  - src/stores/routineStore.ts (신규)

    --resume + 요약 프롬프트 방식

구현 위치:
  - electron/session-compactor.ts (신규)
  - electron/agent-manager.ts: 통합
```

### Tier 3 — 나중에 구현 (v3.2 ~ v3.3)

#### 17-10. Webhook Triggers

```
목적: 외부 이벤트(GitHub push, Slack 메시지 등)로 에이전트 작업 트리거
방식:
  - Electron 내 경량 HTTP 서버 (또는 Firestore 트리거)
  - Webhook 수신 → 매칭되는 Routine/Flow 실행
  - GitHub webhook: push → 자동 테스트, PR → 자동 리뷰
```

#### 17-11. Approval Gates (승인 게이트)

```
목적: 에이전트 작업 중 사람의 승인이 필요한 지점 설정
방식:
  - Flow 노드 타입에 'approval' 추가
  - 승인 요청 시 UI 알림 + Slack/이메일 통보
  - 승인/거절 후 Flow 계속 진행
  - 타임아웃 설정 가능
```

#### 17-12. Agent Templates (에이전트 템플릿)

```
목적: 자주 사용하는 에이전트 설정을 템플릿으로 저장·공유
방식:
  - 현재 에이전트 설정을 템플릿으로 저장
  - 템플릿에서 새 에이전트 원클릭 생성
  - 커뮤니티 템플릿 공유 (추후)
```

### Tier 4 — 장기 계획 (v3.3+)

#### 17-13. Plugin SDK

```
목적: 서드파티 개발자가 Marblo 확장 기능을 만들 수 있는 SDK
방식:
  - MCP 서버 표준 기반 플러그인 인터페이스
  - 플러그인 매니페스트 (package.json 확장)
  - 샌드박스 실행 환경
```

#### 17-14. Skills Marketplace

```
목적: 커뮤니티가 만든 스킬/플러그인을 검색·설치
방식:
  - 중앙 레지스트리 (npm 스타일)
  - 별점/리뷰 시스템
  - 원클릭 설치
```

#### 17-15. Git Worktree Isolation

```
목적: 에이전트별 독립 Git 작업 공간으로 충돌 방지
방식:
  - 에이전트 실행 시 자동으로 git worktree 생성
  - 브랜치 네이밍: agent/{agentName}/{taskId}
  - 작업 완료 시 자동 PR 생성 또는 머지
  - worktree 자동 정리
```

#### 17-16. Budget Hard-Stop

```
목적: 프로젝트/에이전트별 비용 한도 초과 시 자동 중지
방식:
  - 비용 추적 (17-3) 기반
  - 프로젝트별 일/월 예산 설정
  - 80% 도달 시 경고, 100% 도달 시 에이전트 자동 중지
  - UI: 예산 설정 패널 + 잔여 예산 표시
```
