# Privacy & telemetry

What the Marblo desktop app sends, what it never sends, what stays on your
machine, and how to turn the optional parts off.

This page exists because [`docs/benchmark/`](benchmark/) publishes numbers
derived from our own telemetry — install counts, spawn counts, ticket outcomes.
If we are going to show you those numbers, you are owed the exact shape of the
pipe they came out of.

It follows the same rule as [SECURITY.md](../SECURITY.md): **what is true
today**, then **what is not true yet**. Where the in-app policy page and the
shipped code differ, this page describes the code.

---

## The short version

| Question                                     | Answer                                                                                                                     |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Does my **source code** leave the machine?   | **No.** Not on any default path. Your repos, diffs, and file contents are read by the CLI agent locally.                   |
| Are my **prompts or agent output** uploaded? | **No** by default. Free-text fields are dropped before the queue, not redacted. There is an off-by-default opt-in — below. |
| Do you **train models on my code**?          | **No.** Not from any default path, and never from anyone who has not switched on an explicit opt-in that ships **off**.    |
| Is there **analytics on by default**?        | **Yes** — de-identified operational events. We are not going to call that opt-in when it isn't.                            |
| Can I **turn it off**?                       | Yes: **Settings → Privacy → first-party analytics**. Takes effect immediately, and is remembered.                          |
| Are **crash reports** on by default?         | **No.** Sentry is opt-in, ships off, and is the only third party the app can send to.                                      |
| Do you **sell or share** any of it?          | **No.** The de-identified events and the opt-in raw-text store both live in our own GCP. Neither is shared or sold.        |

## 1 · What is on by default: de-identified operational events

The app sends a batched event stream to our own Google Cloud project
(BigQuery), roughly every 10 seconds while it is running.

**What an event row contains**

- The **event name** — `agent:spawned`, `task:completed`, `agent:crashed`,
  `onboarding:cli_setup_step`, and similar lifecycle points.
- **Coarse operational fields** — model id (`claude-opus-5`, `gpt-5.6-sol`, …),
  agent role, ticket status transitions, duration in ms, input/output token
  counts, estimated cost, process exit code, app version, platform.
- **Opaque ids** — an anonymous install id, plus the app's own ticket / agent /
  project ids. These are random identifiers generated by the app; they are not
  derived from your name, email, hostname, or repository.
- An **error category** on failure events (`cli_auth`, `runtime_crash`,
  `fast_fail_config`, …) and a short, scrubbed error message.

**What it does not contain**

Source code, file contents, diffs, file paths, prompts, model responses,
terminal output, chat messages, ticket titles or descriptions, API keys,
passwords.

**How that is enforced.** Every send — including events forwarded from the
app's main process — passes through one function before it can reach the queue.
That function:

| Input                                                                                                                       | Result                              |
| --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| `/Users/*`, `/home/*`, `C:\Users\*`                                                                                         | replaced with `<USER_HOME>`         |
| Email addresses                                                                                                             | `<EMAIL>`                           |
| Phone numbers (KR `010-…`, international `+…`)                                                                              | `<PHONE>`                           |
| API keys (`sk-ant-*`, `sk-*`, `AIza*`)                                                                                      | `<API_KEY>`                         |
| Any field whose key looks like a secret (`*_KEY`, `*_TOKEN`, `*_SECRET`, `ANTHROPIC_*`, `OPENAI_*`, `GOOGLE_*`, `MARBLO_*`) | `<REDACTED>`                        |
| Any field named `prompt`, `initialPrompt`, `message`, `userInput`, `content`, `raw_input`                                   | **dropped entirely** — not redacted |

Free-text is dropped rather than masked on purpose: partial scrubbing of
natural-language input is unreliable, so the field never ships at all.

**Where the account id does appear.** Two places, and we would rather spell
them out than round them down to "anonymous":

1. **Events.** The client sends no account identifier — the row key is the
   anonymous install id, and account fields are stripped client-side. The
   server-side function then attaches your account id to the stored row's
   metadata so repeat installs by one person can be de-duplicated. So the event
   stream is **de-identified in transit and in its row key, and re-linkable by
   us inside our own warehouse.** It is not anonymous in the strict sense, and
   we are not going to claim it is.
2. **Cost and token rows.** These are stored under your account by design —
   they are your own spend history, and the app reads them back to you in the
   Usage tab. Amounts, token counts, model ids, and timestamps; no prompt text.

**Why it is on.** Operational quality: which harness/model combinations crash,
where onboarding stalls, whether a release regressed. The
[benchmark docs](benchmark/) are the same data, published with its sample size
and its defects attached.

**Turning it off.** Settings → Privacy → first-party analytics. The effect is
immediate and persists across restarts. One honest trade-off: the same switch
governs the cost roll-up writes, so with it off the Usage tab stops accruing
new spend history. Everything else in the app behaves identically.

## 2 · What is off by default: crash reports (Sentry)

Ships **off**. When you switch it on, crash stack traces, PII-masked error
messages, and your OS/app version go to Sentry (US-hosted, 90-day retention).
The same scrubber runs on this path, and the SDK's user object is cleared
before send. Turning it on also asks for cross-border transfer consent
separately, because the destination is in another country.

The app sends **nothing** to GA4, Mixpanel, or any other analytics vendor. The
marblo.app **website** uses GA4 under its own cookie consent; that is the
website, not the app.

## 3 · What is off by default: contributing raw transcripts

There is one switch that changes the kind of data involved rather than its
destination, so it is described separately.

**Settings → Privacy → training-data contribution** — ships **off**, and asks
once. Switched on, it stores the raw prompt and response text of your own agent
turns, so we can train our own models on it.

- It is **raw text**. It can contain your code and it can contain PII. That is
  precisely why it is a separate, explicit, off-by-default switch instead of a
  line item in a bundled consent dialog.
- It writes to a **different BigQuery dataset** from the de-identified events,
  so access is separable at the IAM level.
- It is **fail-closed and double-gated**: the app uploads only after the server
  confirms this account is eligible, and the server re-checks eligibility and
  your stored consent on every insert. Unknown state — not yet fetched, fetch
  failed, signed out — means do not capture.
- **Today the server accepts it from one account: the operator's own.** Anyone
  else can switch the toggle on and nothing is collected; the app says so in
  the status line under the switch rather than pretending. Opening it further
  is a roadmap item, and it will still be opt-in.
- It is never shared with or sold to third parties, and it is not sent to
  Anthropic, OpenAI, xAI, or any other model vendor.

Turning it off stops collection immediately. Deleting what was already stored
is a request to **team@marblo.app**.

## 4 · What never leaves your machine

- **Your source code, repositories, worktrees, and diffs.** The agent CLI reads
  and writes them locally. Marblo spawns that CLI as a subprocess on your
  machine; the code path is local disk.
- **Your agent CLI credentials.** Marblo does not proxy your model traffic and
  does not hold your Claude / Codex / Grok logins. Those CLIs talk to their own
  vendors with their own credentials, billed to your own accounts.
- **Terminal output and session transcripts.** Streamed to your screen and
  stored locally. (The one exception is §3, off by default.)
- **BYOM / provider keys** you configure for local or alternative models.

## 5 · What syncs to your Marblo account (product data, not telemetry)

Marblo is a live board that a team can watch, so some product data does sync to
our Firestore under your account: ticket titles, descriptions, and activity
logs; agent and board state; chat messages; and cost roll-ups.

This is **not** de-identified, and it is **not** governed by the analytics
toggle — it is the product working. It is the same category as your data in any
hosted issue tracker. If you want a ticket's description to stay private, do
not put a secret in a ticket description.

## 6 · What you can verify yourself

The orchestration engine is closed source ([why](../README.md#whats-open-and-what-isnt)),
so "read the code" is not an option we can offer for the app. These are:

- **Watch the traffic.** Point Little Snitch, LuLu, Charles, or a proxy at the
  app. On a default install the only outbound hosts are Google/Firebase
  (authentication, Firestore, and the `cloudfunctions.net` callables that
  receive the event, heartbeat, cost, and outcome batches), the GitHub release
  feed for updates, and `github.com` / `raw.githubusercontent.com` when you
  install something from the Store. **A Sentry `ingest` host appearing without
  you having opted in would be a bug — please report it.** No other analytics
  vendor should ever appear.
- **Turn the switch off and watch the batches stop.** The event POSTs are on a
  ~10-second cadence while agents run; they end when the toggle goes off.
- **Read the in-app policy page.** Settings → Privacy → view policy, next to
  the switches themselves.
- **Read everything the agents consume.** Every skill, agent, workflow, MCP
  manifest, and knowledge pack in this repository is a plain file you can read
  before it ever loads into a model's context — and each referenced item is
  pinned to an upstream tag or SHA.
- **Check our numbers against their SQL.** Every figure in
  [`docs/benchmark/`](benchmark/) traces to committed queries you can re-run.

## 7 · What is not true yet

- **Deletion is a support process, not a button.** Requests go to
  team@marblo.app and are handled within 30 days. There is no self-serve
  "delete my telemetry" control in the app.
- **The event stream is de-identified, not anonymous.** See §1 — we can
  re-link rows to an account inside our own warehouse.
- **Analytics is on by default.** It is de-identified and it is one switch
  away, but a default-on collector is a default-on collector.
- **The in-app policy and this page now agree.** The in-app policy states that
  product-usage analytics use an anonymous install id with no account
  identifier — which is accurate for what the client sends. This page adds one
  detail the in-app copy keeps brief: an account id is attached server-side and
  rows stay re-linkable inside our own warehouse (§1).
- **No third-party privacy audit.** Nobody outside the company has verified any
  of this. What we can offer instead is §6.
