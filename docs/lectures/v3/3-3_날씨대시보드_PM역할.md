## 도입 (3분)

자, 에이전트들이 열심히 일하고 있습니다. 지금쯤 Backend Agent는 TASK-001을 마쳤고, Frontend Agent가 TASK-004를 작업 중일 거예요.

화면: 칸반 보드 — TASK-001 REVIEW, TASK-004 IN_PROGRESS

여러분은 지금부터 **PM — 프로젝트 매니저** 역할을 합니다. PM이 하는 일은 세 가지예요:

1. **모니터링** — `/tf-status`로 진행 상황 파악
2. **리뷰** — `/tf-review`로 완료된 태스크 검토
3. **피드백** — 승인(Approve) 또는 거절(Reject)로 방향 조정

코딩은 에이전트가 합니다. 여러분은 **의사결정**을 하는 거예요. 이 역할 분담이 마블로를 사용하는 가장 큰 포인트입니다.

---

## 본문

### `/tf-status`로 전체 현황 파악 (5분)

먼저 현재 프로젝트가 어디까지 진행됐는지 확인해봅시다.

**(실습)** 터미널에 입력:

```bash
/tf-status
```

화면: `/tf-status` 출력 결과

```
📊 Project: 날씨 대시보드
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Progress: ██████░░░░░░░░░░░ 2/6 (33%)

Tasks:
  ✅ TASK-001  날씨 API 프록시 엔드포인트    REVIEW    @Backend-Agent
  ⏳ TASK-002  즐겨찾기 도시 저장 API        TODO      (depends: 001)
  ⏳ TASK-003  도시 검색 UI                  TODO      (depends: 001)
  🔨 TASK-004  날씨 카드 컴포넌트            IN_PROGRESS @Frontend-Agent
  ⏳ TASK-005  5일 예보 차트                 TODO      (depends: 004)
  ⏳ TASK-006  API 연동 테스트               TODO      (depends: 003, 005)

Agents:
  Backend Agent   : IDLE (waiting for review on TASK-001)
  Frontend Agent  : WORKING on TASK-004

Recent Activity:
  [14:32] Backend Agent — TASK-001 완료, REVIEW 요청
  [14:33] Frontend Agent — TASK-004 클레임, 작업 시작
```

이 출력을 하나씩 읽어볼게요.

**Progress 바** — 현재 6개 중 2개가 어느 정도 진행된 상태입니다. TASK-001은 REVIEW 대기 중이고, TASK-004는 작업 중이죠.

**Tasks 목록** — 각 태스크의 현재 상태와 담당 에이전트가 한눈에 보입니다. blocked 상태인 태스크는 의존성 정보도 같이 나와요.

**Agents 섹션** — Backend Agent는 TASK-001 리뷰를 기다리고 있고, Frontend Agent는 TASK-004를 작업 중입니다.

**Recent Activity** — 최근 활동 로그. 에이전트가 뭘 했는지 시간순으로 볼 수 있어요.

여기서 중요한 걸 하나 캐치하셨나요? Backend Agent가 **IDLE** 상태예요. TASK-001 리뷰를 기다리고 있거든요. 즉, **여러분이 리뷰를 해줘야 에이전트가 다음 일을 할 수 있다**는 뜻입니다.

PM이 병목이 되면 안 되겠죠? 바로 리뷰를 해봅시다.

### `/tf-review`로 백엔드 태스크 리뷰 (7분)

**(실습)** 터미널에 입력:

```bash
/tf-review TASK-001
```

화면: TASK-001 리뷰 화면 — 코드 diff + 활동 로그

마블로가 TASK-001의 결과물을 보여줍니다:

```
📝 Review: TASK-001 — 날씨 API 프록시 엔드포인트
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Agent: Backend Agent
Time spent: 3m 42s

Files changed:
  + backend/app/routers/weather.py    (new, 68 lines)
  + backend/app/schemas/weather.py    (new, 32 lines)
  ~ backend/app/main.py              (modified, +3 lines)

Activity log:
  - OpenWeatherMap API 연동 구현
  - GET /api/weather/{city} 현재 날씨 엔드포인트
  - GET /api/weather/{city}/forecast 5일 예보 엔드포인트
  - Pydantic response model 정의
  - main.py에 라우터 등록

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[A]pprove  [R]eject  [V]iew code  [?] Help
```

코드를 확인하고 싶으면 `V`를 누르세요.

화면: 코드 diff 뷰

코드를 살펴보면 — FastAPI 라우터가 잘 구성되어 있고, Pydantic 모델로 응답 형태를 정의했고, 에러 핸들링도 되어 있네요. 괜찮습니다!

**승인합시다:**

```bash
A
```

```
✅ TASK-001 Approved!
  → TASK-001: REVIEW → DONE
  → TASK-002 unblocked (dependencies resolved)
  → TASK-003 unblocked (dependencies resolved)
  → Backend Agent: picking up TASK-002
```

승인하는 순간 연쇄 반응이 일어납니다:

1. TASK-001이 DONE으로 이동
2. TASK-002와 TASK-003의 의존성이 해소
3. Backend Agent가 자동으로 TASK-002를 클레임

화면: 칸반 보드 — TASK-001이 DONE으로, TASK-002가 IN_PROGRESS로

이 흐름이 핵심이에요. **PM이 승인하면 → 의존성 해소 → 다음 태스크 자동 시작**. 이게 마블로의 파이프라인입니다.

### 거절(Reject) 시나리오 (5분)

만약 코드가 마음에 안 들면 어떻게 할까요? 잠깐 가정을 해봅시다.

예를 들어 Frontend Agent가 완성한 날씨 카드에서 "온도가 섭씨/화씨 전환이 안 된다"고 해봅시다.

```bash
/tf-review TASK-004
```

```
[A]pprove  [R]eject  [V]iew code  [?] Help
```

이때 `R`을 누르고 피드백을 적습니다:

```bash
R
> 온도 표시에 섭씨/화씨 토글 버튼 추가해주세요. 사용자가 선택할 수 있어야 합니다.
```

```
🔄 TASK-004 Rejected with feedback
  → TASK-004: REVIEW → IN_PROGRESS
  → Frontend Agent: 피드백 반영 작업 시작
```

리젝하면:

1. 태스크가 다시 IN_PROGRESS로 돌아감
2. 에이전트가 피드백을 읽고 수정 작업을 시작
3. 수정이 끝나면 다시 REVIEW로 올라옴

화면: 칸반 보드 — TASK-004가 다시 IN_PROGRESS로, 에이전트 로그에 "피드백 반영 중" 메시지

이 사이클이 **PM ↔ 에이전트 간의 코드 리뷰 루프**입니다. 실제 개발팀에서 PR(Pull Request) 리뷰하는 것과 같은 구조죠.

### 병렬 작업 관찰 (5분)

자, 시간이 조금 지나면 이런 상황이 됩니다:

화면: 칸반 보드 — 여러 태스크가 동시 진행 중

```
📊 /tf-status

Progress: ████████████░░░░░ 4/6 (67%)

Tasks:
  ✅ TASK-001  날씨 API 프록시 엔드포인트    DONE      @Backend-Agent
  ✅ TASK-002  즐겨찾기 도시 저장 API        DONE      @Backend-Agent
  🔨 TASK-003  도시 검색 UI                  IN_PROGRESS @Frontend-Agent
  ✅ TASK-004  날씨 카드 컴포넌트            DONE      @Frontend-Agent
  🔨 TASK-005  5일 예보 차트                 IN_PROGRESS @Frontend-Agent
  ⏳ TASK-006  API 연동 테스트               TODO      (depends: 003, 005)
```

Backend Agent가 TASK-001, 002를 순서대로 끝냈고, Frontend Agent가 TASK-003과 005를 순차적으로 작업 중입니다. TASK-006은 아직 blocked — TASK-003과 005가 끝나야 시작합니다.

여기서 재미있는 점 — Backend Agent는 할 일이 다 끝났어요. 프론트엔드 태스크를 맡길 수는 없으니까 대기 상태가 됩니다. 실제 팀에서도 백엔드 개발자가 먼저 끝나면 기다리죠? 같은 원리입니다.

### 최종 리뷰 + 완성 (5분)

모든 태스크가 완료되면:

```
📊 /tf-status

Progress: ████████████████ 6/6 (100%) ✅

All tasks completed!
```

화면: 칸반 보드 — 모든 카드가 DONE 열에

**(실습)** 마지막으로 실제 결과물을 확인해봅시다:

```bash
# 백엔드 실행
cd backend && uvicorn app.main:app --reload --port 8001

# 프론트엔드 실행 (새 터미널)
cd frontend && npm run dev
```

화면: 브라우저에서 날씨 대시보드 — "Seoul" 검색 → 날씨 카드 + 5일 예보 차트

브라우저에서 `http://localhost:3000`을 열면:

1. 도시 검색창에 "Seoul" 입력
2. 현재 날씨 카드가 표시됨 — 온도, 습도, 풍속
3. 아래에 5일 예보 차트가 나옴

에이전트 2개가 6개 태스크를 처리해서 이 결과물을 만든 겁니다. 여러분이 직접 코딩한 건 **단 한 줄도 없어요**. PM으로서 기획하고, 관찰하고, 리뷰만 했죠.

---

## 정리

이번 섹션에서 익힌 PM 역할:

1. **모니터링**: `/tf-status`로 진행률, 태스크 상태, 에이전트 활동을 한눈에 파악
2. **리뷰**: `/tf-review`로 에이전트의 코드를 검토하고 Approve/Reject
3. **피드백 루프**: Reject 시 피드백 → 에이전트 수정 → 재리뷰
4. **의존성 파이프라인**: 승인 → 의존성 해소 → 다음 태스크 자동 시작
5. **PM은 병목이 되지 말 것** — 리뷰를 빨리 해줘야 에이전트가 쉬지 않는다
