# 상태 머신 — 왜 JIRA 칸반과 다른가

> 모듈 2 · 섹션 2-3 · 약 15분
> 관련: [[2-2_마블로_아키텍처]] | [[2-4_슬래시스킬_구조]]

---

## 도입 (2분)

모듈 1에서 칸반 보드에서 카드가 TODO → CLAIMED → IN_PROGRESS → REVIEW → DONE으로 움직이는 걸 봤죠?

"그냥 칸반 보드 아닌가요? JIRA에도 있잖아요?"
비슷해 보이지만 결정적인 차이가 있습니다.

JIRA는 사람이 카드를 자유롭게 아무 컬럼으로 옮길 수 있습니다.
TODO에서 바로 DONE으로? 가능합니다.
DONE에서 다시 TODO로? 그것도 가능합니다.

마블로는 **안 됩니다.**
왜냐하면 에이전트는 사람이 아니거든요.
자유도를 주면 혼란이 생깁니다.

마블로는 **상태 머신(State Machine)** 으로 전환 규칙을 강제합니다.

---

## 본문

### 7개 상태 (3분)

화면: 슬라이드 — 7개 상태 다이어그램

마블로 태스크에는 7개 상태가 있습니다:

```
TODO        — 아직 아무도 안 건드림
CLAIMED     — 에이전트가 "내가 하겠다" 선언
IN_PROGRESS — 실제 작업 중
REVIEW      — 작업 완료, PM 리뷰 대기
DONE        — 리뷰 통과, 완료
BLOCKED     — 외부 요인으로 중단
FAILED      — 실패
```

### 유효 전환 규칙 (5분)

화면: VS Code — state-machine.ts 파일

이 파일을 열어봅시다. `electron/mcp-server/state-machine.ts`:

```typescript
export type TaskStatus = 'TODO' | 'CLAIMED' | 'IN_PROGRESS' | 'REVIEW'
                       | 'BLOCKED' | 'FAILED' | 'DONE';

const VALID_TRANSITIONS: Record<TaskStatus, TaskStatus[]> = {
  TODO:        ['CLAIMED'],
  CLAIMED:     ['IN_PROGRESS', 'FAILED'],
  IN_PROGRESS: ['REVIEW', 'BLOCKED', 'FAILED'],
  REVIEW:      ['DONE', 'TODO'],
  BLOCKED:     ['IN_PROGRESS'],
  FAILED:      ['TODO'],
  DONE:        [],
};
```

이게 전체 규칙입니다. 생각보다 단순하죠?

하나씩 봅시다:

| 현재 상태 | 가능한 다음 상태 | 의미 |
|----------|----------------|------|
| TODO | CLAIMED | 에이전트가 선점 |
| CLAIMED | IN_PROGRESS | 작업 시작 |
| CLAIMED | FAILED | 시작 전 실패 (환경 문제 등) |
| IN_PROGRESS | REVIEW | 작업 완료, 리뷰 요청 |
| IN_PROGRESS | BLOCKED | 외부 요인으로 중단 |
| IN_PROGRESS | FAILED | 작업 중 실패 |
| REVIEW | DONE | PM이 승인 |
| REVIEW | TODO | PM이 거절 → 처음부터 다시 |
| BLOCKED | IN_PROGRESS | 차단 해제, 작업 재개 |
| FAILED | TODO | 재시도 |
| DONE | (없음) | 끝. 더 이상 전환 불가 |

화면: 상태 전환 다이어그램 (화살표)

```
TODO ──→ CLAIMED ──→ IN_PROGRESS ──→ REVIEW ──→ DONE
              │            │   │          │
              └─→ FAILED   │   │          └─→ TODO (reject)
                   │       │   └─→ BLOCKED
                   │       └─→ FAILED     │
                   └─→ TODO (retry)       └─→ IN_PROGRESS
```

**중요한 점:** `DONE`에서는 아무 데도 갈 수 없습니다. `DONE: []` — 빈 배열이죠.
한 번 완료되면 끝입니다. 되돌릴 수 없습니다.

그리고 `REVIEW → TODO`가 있죠?
이건 PM이 리뷰에서 **거절(reject)** 했을 때 사용됩니다.
다시 처음부터 — 다른 에이전트가 claim해서 다시 할 수도 있습니다.

### 상태 전환 강제 — 코드 레벨 (3분)

화면: VS Code — tools.ts의 update_task_status

이 규칙이 어떻게 강제되는지 코드를 봅시다:

```typescript
// electron/mcp-server/tools.ts — update_task_status

server.tool(
  'update_task_status',
  'Update a task status. State machine rules enforced.',
  { task_id: z.string(), status: z.string(), comment: z.string().optional() },
  async ({ task_id, status, comment }) => {
    const task = await fetchTask(task_id);
    const newStatus = status as TaskStatus;

    // 여기서 상태 머신 규칙을 체크!
    if (!canTransition(task.status, newStatus)) {
      const validTargets = VALID_TRANSITIONS[task.status] ?? [];
      return text(
        `Error: Cannot transition from ${task.status} to ${newStatus}. ` +
        `Valid targets: ${validTargets.join(', ')}`
      );
    }

    // 규칙 통과 → Firestore 업데이트
    await updateDoc(doc(db, 'tasks', task_id), {
      status: newStatus,
      updatedAt: Timestamp.now(),
    });
  },
);
```

`canTransition()` 함수가 핵심입니다:

```typescript
export function canTransition(from: TaskStatus, to: TaskStatus): boolean {
  return VALID_TRANSITIONS[from]?.includes(to) ?? false;
}
```

에이전트가 TODO에서 바로 DONE으로 가려고 하면?
```
Error: Cannot transition from TODO to DONE. Valid targets: CLAIMED
```

에러가 납니다. 반드시 CLAIMED → IN_PROGRESS → REVIEW → DONE 순서를 지켜야 합니다.

### 동시 claim 방지 (2분)

화면: VS Code — tools.ts의 claim_task

에이전트가 2개 이상일 때, 같은 태스크를 동시에 claim하려고 하면 어떻게 될까요?

```typescript
// claim_task 도구
async ({ task_id, agent_id }) => {
  const task = await fetchTask(task_id);

  // 이미 누가 claim했으면 거절
  if (task.status !== 'TODO') {
    return text('Error: Task is not available for claiming (not in TODO status).');
  }

  // 의존성 미충족이면 거절
  if (!task.dependsOnCompleted) {
    return text('Error: Task dependencies are not yet met.');
  }

  // 통과 → CLAIMED로 변경
  await updateDoc(doc(db, 'tasks', task_id), {
    status: 'CLAIMED',
    claimedBy: agent_id,
    claimedAt: Timestamp.now(),
  });
};
```

두 가지 검증:
1. **상태 체크**: `status !== 'TODO'`이면 거절
2. **의존성 체크**: `dependsOnCompleted`가 false면 거절

TASK-002가 TASK-001에 의존하고 있으면,
TASK-001이 DONE이 될 때까지 TASK-002는 claim할 수 없습니다.

이게 있어서 에이전트들이 의존성 순서를 자동으로 지킵니다.
백엔드 API가 완성되기 전에 프론트엔드가 API를 호출하는 코드를 짜는 일이 없어요.

## 정리 (1분)

상태 머신 핵심:

1. **7개 상태**: TODO → CLAIMED → IN_PROGRESS → REVIEW → DONE + BLOCKED/FAILED
2. **유효 전환만 허용**: `canTransition()` 함수가 모든 상태 변경을 검증
3. **DONE은 끝**: 더 이상 전환 불가
4. **동시 claim 방지**: 이미 CLAIMED면 다른 에이전트 거절
5. **의존성 강제**: 선행 태스크 DONE 전에는 claim 불가

JIRA와의 결정적 차이:
- JIRA는 사람이 자유롭게 이동 → 유연하지만 혼란 가능
- 마블로는 규칙에 따라 자동 이동 → 에이전트가 예측 가능하게 행동
