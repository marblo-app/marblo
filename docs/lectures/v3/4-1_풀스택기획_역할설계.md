# 풀스택 기획 + 역할 설계 — Claude + Codex 두 모델로

> 모듈 4 · 섹션 4-1 · 약 25분
> 관련: [[3-4_리뷰_워크트리머지_완료]] | [[4-2_의존성체인_병렬레인]]

---

## 이 강의에서 다루는 것

- **학습목표:** 풀스택 프로젝트(P2 날씨 대시보드)를 오케스트레이터로 기획하고, 백엔드/프론트/테스트로 분해한 뒤 **두 모델(Claude·Codex)에게 역할을 나눠 배정**하는 사고법을 익힌다.
- **시연할 마블로 화면·기능:** 하단 오케스트레이터 PTY(요구 입력 → 태스크 분해) + 보드 탭(역할 배지가 붙은 카드).
- **진행할 프로젝트 단계:** **P2 시작** — FastAPI + Next.js + OpenWeather 날씨 대시보드.
- **핵심 메시지:** "모델마다 잘하는 일이 다르다 — **역할로 나눠라**."

---

## 도입 — 한 명에서 한 팀으로 (3분)

모듈 3에서 우리는 첫 풀사이클을 한 바퀴 돌렸습니다. 할 일(Todo) 웹앱 — 프론트 단독, 에이전트 한 명이면 충분한 작은 프로젝트였죠.

이번 모듈은 한 단계 올라갑니다.

> 화면: 완성된 날씨 대시보드 데모 — 도시 검색 + 현재 날씨 카드 + 5일 예보 차트

우리가 만들 건 **날씨 대시보드(P2)**입니다.

- **입력:** 도시 이름 (예: "Seoul", "New York")
- **출력:** 현재 날씨 카드 + 5일 예보 차트
- **스택:** FastAPI(백엔드) + Next.js(프론트엔드) + OpenWeather API

겉보기엔 간단하지만, 이 안에는 **백엔드-프론트엔드 분리**, **외부 API 연동**, **컴포넌트 설계**가 다 들어 있습니다. 진짜 서비스의 축소판이에요.

그리고 결정적인 차이가 하나 있습니다. 모듈 3은 에이전트 한 명이었지만, **이번엔 두 모델이 동시에 일합니다.**

- **Claude Code** — 설계와 백엔드를 맡습니다.
- **Codex** — 프론트엔드와 테스트를 맡습니다.

이게 마블로의 진짜 시작입니다. 멀티에이전트 협업 — 서로 다른 모델이 한 보드 위에서 자기 역할을 하는 거죠. 그 첫걸음이 바로 **기획과 역할 설계**입니다.

## 본문

### 1. 오케스트레이터에게 풀스택 요구를 던진다 (6분)

> 화면: 마블로 하단 — 오케스트레이터 PTY 패널

모듈 2에서 프로젝트를 연결하면 하단에 오케스트레이터(팀리더)가 자동으로 떠 있다고 했죠? 거기에 자연어로 한 줄 던지는 것부터 시작합니다.

**(실습)** 오케 패널에 입력해봅시다:

```
날씨 대시보드를 만들어줘. 도시를 검색하면 현재 날씨 카드와 5일 예보 차트를 보여줘.
백엔드는 FastAPI로 OpenWeather API를 프록시하고, 프론트는 Next.js로.
```

오케스트레이터가 곧바로 코드를 짜기 시작하지 않습니다. 대신 **소크라테스식 질문**으로 요구를 다듬어요.

> 화면: 오케 PTY — 소크라테스 질문 출력

```
Q: UI 형태는? (대시보드 카드형 / 리스트형 …)
A: 카드형 대시보드, 반응형

Q: 인증이 필요한가요?
A: 아니요, 공개 서비스

Q: 추가로 원하는 기능이 있나요?
A: 즐겨찾기 도시 저장 정도
```

답을 주면 오케스트레이터가 **PRD(요구사항 문서)**를 만들고, 곧이어 **태스크로 분해**합니다. 이 흐름은 모듈 3과 똑같아요. 달라지는 건 프로젝트 규모와 — 곧 보겠지만 — **누가 그 태스크를 맡느냐**입니다.

### 2. 백엔드 · 프론트 · 테스트로 분해 (6분)

> 화면: 보드 탭 — TODO 컬럼에 카드 등장

오케스트레이터가 만든 태스크를 봅시다. 날씨 대시보드는 이렇게 쪼개집니다.

```
[TASK-001] 날씨 API 프록시 엔드포인트       (backend)
[TASK-002] 즐겨찾기 도시 저장 API           (backend, depends: 001)
[TASK-003] 도시 검색 UI                     (frontend, depends: 001)
[TASK-004] 날씨 카드 컴포넌트               (frontend, depends: 001)
[TASK-005] 5일 예보 차트                     (frontend, depends: 004)
[TASK-006] API 연동 테스트                   (test, depends: 003, 005)
```

좋은 태스크의 조건은 모듈 3에서 봤죠 — **하나의 명확한 결과물**을 가져야 합니다. "백엔드 만들어줘"는 나쁜 태스크, "GET /api/weather/{city} 프록시 엔드포인트"는 좋은 태스크예요.

여기서 두 가지를 다시 짚습니다.

- **의존성(`depends`)** — TASK-003·004는 TASK-001에 의존합니다. 백엔드 API가 있어야 프론트가 붙으니까요. 마블로가 이 순서를 자동으로 관리합니다.
- **역할(role)** — 각 태스크에 `backend` / `frontend` / `test` 배지가 붙습니다. 이 배지가 **다음 단계의 핵심**입니다. 바로 이 역할에 따라 어떤 모델을 붙일지 정하거든요.

### 3. 두 모델, 두 역할 — 왜 나누나 (7분)

> 화면: 슬라이드 — Claude(설계·백엔드) / Codex(프론트·테스트) 역할 배분

자, 핵심입니다. **모델은 다 똑같지 않습니다.** 사람 개발자가 백엔드 잘하는 사람, 프론트 잘하는 사람이 따로 있듯이, AI 모델도 강점이 다릅니다.

이번 P2에서는 이렇게 나눕니다.

| 역할          | 담당 모델       | 왜                                                   |
| ------------- | --------------- | ---------------------------------------------------- |
| 설계·백엔드   | **Claude Code** | 복잡한 로직·API 설계·데이터 모델링·MCP 활용에 강하다 |
| 프론트·테스트 | **Codex**       | 풀스택 UI 구현·테스트 작성·빠른 반복에 강하다        |

> (모델별 강점의 자세한 비교와 그 근거는 **모듈 6**에서 따로 다룹니다. 여기서는 "역할로 나눈다"는 감각만 잡으면 됩니다.)

그래서 태스크 배정은 이렇게 됩니다.

```
Claude Code  →  TASK-001 (날씨 API 프록시), TASK-002 (즐겨찾기 API)   ← backend
Codex        →  TASK-003 (검색 UI), TASK-004 (날씨 카드),
                TASK-005 (예보 차트), TASK-006 (연동 테스트)            ← frontend / test
```

> 💡 마블로는 태스크의 역할 배지를 보고 **적합한 모델을 자동 추천**합니다. 하지만 최종 결정은 PM인 여러분 몫이에요. "이 태스크는 Codex가 낫겠다" 싶으면 바꿀 수 있습니다. (자동 배정 스코어링은 모듈 6에서.)

여기서 마블로의 강력함이 드러납니다 — **한 모델에 묶이지 않는다**는 점이죠. Claude Code의 설계력과 Codex의 구현 속도를 **한 보드 위에서 동시에** 씁니다. 한쪽이 백엔드를 짓는 동안 다른 쪽이 프론트를 짓는 거예요.

> 화면: 보드 탭 — 카드마다 모델/역할 배지(🟣 Claude · Codex)

> ⚠️ 예전 강의에서는 여기에 Gemini가 있었습니다. 지금 마블로의 기본 팀은 **Claude Code + Codex** 두 주역이고, 떠오르는 3번째가 **Antigravity**입니다. Gemini는 빠졌어요. (자세한 건 모듈 2·6.)

### 4. 역할 설계 = PM의 첫 의사결정 (3분)

> 화면: 보드 탭 — 역할별로 정렬된 카드

코딩을 시작하기 전에 여러분이 한 일을 정리해봅시다.

1. 오케에 한 줄 던졌다.
2. 소크라테스 질문에 답해 PRD를 다듬었다.
3. 태스크 분해를 검토하고 **승인**했다.
4. 각 역할에 **어떤 모델을 붙일지** 정했다.

코드는 한 줄도 안 짰습니다. 대신 **팀을 설계**했어요. 이게 멀티에이전트 시대의 PM이 하는 일입니다 — 누구에게 무엇을 맡길지 정하는 것.

## 정리 (1분)

1. **P2 = 날씨 대시보드** (FastAPI + Next.js + OpenWeather). 모듈 3보다 한 단계 큰 풀스택.
2. **오케 → 소크라테스 질문 → PRD → 태스크 분해**의 흐름은 동일하다. 단, 이번엔 역할 배지가 핵심.
3. **모델마다 강점이 다르다.** Claude=설계·백엔드, Codex=프론트·테스트로 나눴다.
4. **PM의 첫 일은 코딩이 아니라 역할 설계.** 누구에게 무엇을 맡길지 정한다.

다음 섹션에서는 이 두 모델이 **실제로 동시에 일하는 모습** — 병렬 레인과 의존성 체인을 직접 봅니다.
