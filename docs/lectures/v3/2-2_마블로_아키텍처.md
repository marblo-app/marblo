## 본문

### 전체 구조 (4분)

화면: 슬라이드 — Electron 앱 아키텍처 다이어그램

마블로 v3는 Electron 앱입니다. Electron의 구조를 간단히 보면:

```
Electron App
├── Main Process (Node.js)
│   ├── main.ts             — 앱 시작점
│   ├── pty-manager.ts      — 터미널(PTY) 관리
│   ├── agent-manager.ts    — 에이전트 라이프사이클
│   ├── orchestrator-manager.ts  — 오케스트레이터 세션
│   ├── agent-config.ts     — 모델별 MCP 설정 생성
│   ├── bridge-server.ts    — HTTP 브릿지 (MCP ↔ Electron)
│   └── mcp-server/         — MCP 서버 (별도 프로세스)
│       ├── tools.ts        — 20개 MCP 도구 정의
│       ├── prompts.ts      — 4개 프롬프트 템플릿
│       ├── state-machine.ts — 상태 전환 규칙
│       └── firebase.ts     — Firestore 연결
├── Preload (preload.ts)
│   └── Electron API를 React에 안전하게 노출
└── Renderer (React)
    ├── src/components/     — UI 컴포넌트
    ├── src/pages/          — 페이지 (Board, Code, Agents, Flows)
    └── src/services/       — Firebase, API 호출
```

핵심 흐름:
```
React 렌더러 → (IPC) → Electron 메인 → (PTY) → Claude Code CLI → (stdio) → MCP 서버 → (SDK) → Firestore
```

하나씩 코드를 열어보겠습니다.

### `electron/mcp-server/tools.ts` — MCP 도구 정의 (5분)

화면: VS Code — tools.ts 파일

이 파일이 마블로의 핵심 중 핵심입니다.
20개의 MCP 도구가 여기에 정의되어 있어요.

```typescript
// electron/mcp-server/tools.ts

export function registerTools(server: McpServer): void {

  // 1. get_all_tasks — 전체 태스크 조회
  server.tool(
    'get_all_tasks',
    'Get all tasks regardless of status.',
    { project_id: z.string().optional(), role: z.string().optional() },
    async ({ project_id, role }) => {
      const q = query(collection(db, 'tasks'), ...constraints);
      const snap = await getDocs(q);
      // ... Firestore에서 직접 읽어옴
    },
  );

  // 5. claim_task — 태스크 선점
  server.tool(
    'claim_task',
    'Claim a specific task by ID.',
    { task_id: z.string(), agent_id: z.string() },
    async ({ task_id, agent_id }) => {
      // 상태 확인
      if (task.status !== 'TODO') return text('Error: not available');
      if (!task.dependsOnCompleted) return text('Error: dependencies not met');
      // Firestore 업데이트
      await updateDoc(doc(db, 'tasks', task_id), {
        status: 'CLAIMED',
        claimedBy: agent_id,
      });
    },
  );

  // 15. spawn_agent — 에이전트 스폰
  server.tool(
    'spawn_agent',
    'Spawn a new agent via the Electron bridge.',
    { name: z.string(), model: z.enum(['claude','gemini','gpt','custom']), role: z.string() },
    async ({ name, model, role }) => {
      // Bridge Server에 HTTP POST
      const response = await fetch(`http://127.0.0.1:${bridgePort}/spawn-agent`, {
        method: 'POST',
        body: JSON.stringify({ name, model, role }),
      });
      // → Electron AgentManager.launch() 호출됨
    },
  );
}
```

패턴이 보이시죠?
- **대부분의 도구**: Firestore에 직접 읽기/쓰기
- **spawn_agent만**: Bridge Server를 거침 (Electron 프로세스가 PTY를 만들어야 하니까)

또 하나 중요한 게 `notifyOrchestrator()` 함수입니다:

```typescript
function notifyOrchestrator(message: string): void {
  const bridgePort = process.env.MARBLO_BRIDGE_PORT;
  if (!bridgePort) return;
  fetch(`http://127.0.0.1:${bridgePort}/notify-orchestrator`, {
    method: 'POST',
    body: JSON.stringify({ message }),
  }).catch(() => { /* best-effort */ });
}
```

에이전트가 태스크 상태를 바꾸면, 이 함수가 오케스트레이터한테 알림을 보냅니다.
"Backend 에이전트가 TASK-001을 REVIEW로 올렸습니다" — 이런 메시지가
오케스트레이터 터미널에 자동으로 나타나는 이유가 이겁니다.

### `electron/agent-manager.ts` — 에이전트 라이프사이클 (4분)

화면: VS Code — agent-manager.ts

에이전트의 생명주기를 관리하는 파일입니다.

```typescript
// electron/agent-manager.ts

export class AgentManager {
  private agents: Map<string, AgentInstance> = new Map();
  private ptyManager: PtyManager;
  private configGenerator: AgentConfigGenerator;

  launch(params: AgentLaunchParams): AgentInstance {
    // 1. MCP 설정 + 스킬 파일 생성
    const launchConfig = this.configGenerator.getLaunchConfig(
      { id: params.id, model: params.model, role: params.role, command: params.command },
      params.cwd,
      params.initialPrompt,
    );

    // 2. PTY 세션 생성 (= 새 터미널)
    this.ptyManager.create(
      ptySessionId,
      `Agent: ${params.name}`,
      launchConfig.command,    // 'claude', 'gemini', 'codex'
      launchConfig.args,       // ['--dangerously-skip-permissions', '--mcp-config', ...]
      params.cwd,
      mergedEnv,
    );

    // 3. 초기 프롬프트 주입 (3초 후)
    setTimeout(() => {
      this.ptyManager.write(ptySessionId, prompt + '\r');
    }, 3000);

    // 4. 에이전트 인스턴스 등록
    this.agents.set(params.id, instance);
    return instance;
  }
}
```

`launch()` 메서드가 하는 일 4단계:
1. 모델에 맞는 MCP 설정 파일 생성 (JSON)
2. 새 PTY(가상 터미널) 세션 생성
3. CLI 부팅 후 초기 프롬프트 STDIN 주입
4. 에이전트 인스턴스를 Map에 등록

이 Map이 중요합니다. Agents 탭에서 에이전트 목록을 볼 수 있는 건
이 Map에 등록된 인스턴스를 읽어오기 때문이에요.

### `electron/orchestrator-manager.ts` — 오케스트레이터 (3분)

화면: VS Code — orchestrator-manager.ts

오케스트레이터는 앱당 하나만 존재합니다.

```typescript
// electron/orchestrator-manager.ts

export class OrchestratorManager {
  private session: OrchestratorSession | null = null;

  launch(projectId, rootPath, bridgePort, onPtyReady?, resumeSessionId?) {
    // 이전 세션이 있으면 자동 복구 (--continue)
    const shouldResume = resumeSessionId || this.hasClaudeSession(rootPath);
    if (shouldResume) {
      launchConfig.args.push('--continue');
    }

    // Bridge 포트를 MCP 설정에 주입
    launchConfig.env.MARBLO_BRIDGE_PORT = String(bridgePort);

    // PTY 생성 + 초기 프롬프트 전송
    // "You are the Marblo Orchestrator Agent.
    //  Read the orchestrator skill file: use get_agent_skill("orchestrator")
    //  Wait for user instructions."
  }
}
```

AgentManager와 비슷하지만 두 가지 차이:
1. **세션 1개만** — `this.session`이 단일 객체 (Map이 아님)
2. **자동 복구** — 이전 Claude Code 세션이 있으면 `--continue`로 이어받음

### `electron/bridge-server.ts` — HTTP 브릿지 (2분)

화면: VS Code — bridge-server.ts

MCP 서버와 Electron 메인 프로세스 사이의 다리입니다.

```typescript
// 이 서버는 127.0.0.1에서만 동작 (보안)
// 포트는 OS가 랜덤 할당 (port 0)
this.server.listen(0, '127.0.0.1', () => {
  this.port = addr.port;
});
```

왜 필요한지 다시 정리:
- MCP 서버는 **별도 Node.js 프로세스** (Claude Code가 실행)
- AgentManager는 **Electron 메인 프로세스**에 있음
- 서로 직접 통신 불가 → HTTP 브릿지가 중간 역할

두 개의 엔드포인트:
- `POST /spawn-agent` → AgentManager.launch() 호출
- `POST /notify-orchestrator` → 오케스트레이터 PTY에 메시지 전달

## 정리 (2분)

화면: 슬라이드 — 파일별 역할 요약

| 파일 | 역할 | 핵심 |
|------|------|------|
| `mcp-server/tools.ts` | 20개 MCP 도구 | Firestore 직접 읽기/쓰기 |
| `agent-manager.ts` | 에이전트 스폰/종료 | PTY 생성 + MCP 설정 + 초기 프롬프트 |
| `orchestrator-manager.ts` | 오케스트레이터 세션 | 세션 1개, 자동 복구 |
| `bridge-server.ts` | MCP ↔ Electron | HTTP로 spawn/notify |
| `agent-config.ts` | 모델별 설정 | Claude/Gemini/GPT MCP 설정 자동 생성 |
| `pty-manager.ts` | 터미널 관리 | node-pty로 가상 터미널 생성 |

전체 흐름을 한 줄로:
```
사용자 → 오케스트레이터 터미널 → Claude Code → MCP 도구 → Firestore → 칸반 보드
                                      ↓ (spawn_agent)
                               Bridge Server → AgentManager → 새 PTY → 새 에이전트
```

다음 섹션에서는 태스크 상태가 어떤 규칙으로 전환되는지,
상태 머신(State Machine)을 뜯어보겠습니다.
