# 리뷰 거버넌스 — 반려와 재작업

> 모듈 4 · 섹션 4-4 · 약 35분
> 관련: [[4-3_에이전트별_워크트리격리]] | [[4-5_통합_회고]]

---

## 이 강의에서 다루는 것

- **학습목표:** REVIEW에 올라온 카드를 코드 탭에서 검토하고, 부족하면 피드백과 함께 **반려(REVIEW → IN_PROGRESS)**해 에이전트를 재작업시키는 리뷰 루프를 익힌다. FAILED/BLOCKED 상태도 이해한다.
- **시연할 마블로 화면·기능:** 보드 탭(반려 흐름) + 코드 탭(diff 검토) + FAILED/BLOCKED 컬럼.
- **진행할 프로젝트 단계:** P2 품질 보정.
- **핵심 메시지:** "**에이전트는 틀릴 수 있다 — 게이트는 사람이.**"

---

## 도입 — 합치기 전에 검문소가 있다 (3분)

워크트리는 합칠 준비가 됐습니다. 하지만 합치기 직전에 반드시 거쳐야 할 검문소가 있어요 — **리뷰**입니다.

에이전트가 짠 코드는 대부분 훌륭합니다. 하지만 **항상 완벽하진 않아요.** 요구를 살짝 오해했거나, 엣지 케이스를 빼먹었거나, UI가 의도와 다를 수 있죠. 그래서 카드가 곧장 DONE으로 가지 않습니다. 일단 **REVIEW**에 멈춰 서서, **PM인 여러분의 승인**을 기다립니다.

> 화면: 보드 탭 — REVIEW 컬럼에 카드 여러 장 대기

이번 섹션의 핵심은 이겁니다 — **머지 권한은 끝까지 사람이 쥔다.** 에이전트는 제안하고, 결정은 PM이 합니다. 이게 칸반 거버넌스예요.

---

## 본문

### 1. REVIEW 카드 검토 — 코드 탭 diff (7분)

> 화면: 보드 탭 — REVIEW 카드 클릭 → 코드 탭으로 이동

REVIEW 컬럼의 카드를 클릭하면 무엇이 바뀌었는지 봐야겠죠. **코드 탭**에서 diff를 확인합니다.

```
📝 Review: TASK-004 — 날씨 카드 컴포넌트   (Codex)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Files changed:
  + frontend/components/WeatherCard.tsx    (new, 94 lines)
  + frontend/components/WeatherCard.css    (new, 30 lines)
  ~ frontend/app/page.tsx                  (modified, +6 lines)

Activity log:
  - 날씨 카드 컴포넌트 구현 (온도/습도/풍속)
  - 반응형 레이아웃 적용
```

> 화면: 코드 탭 — WeatherCard.tsx diff 뷰 (초록 추가 / 빨강 삭제)

diff를 읽을 때 PM이 보는 건 "코드 한 줄 한 줄이 완벽한가"가 아닙니다. 그건 에이전트가 신경 쓸 일이에요. PM은 더 높은 곳을 봅니다.

- **요구를 충족했나?** — 온도·습도·풍속이 다 나오나?
- **빠진 게 없나?** — 에러 상태(도시 못 찾음)는 처리했나?
- **다른 작업과 맞물리나?** — 백엔드 응답 형태와 키 이름이 맞나?

### 2. 승인(Approve) — 연쇄 반응 (5분)

> 화면: 코드 탭 / 보드 — Approve → DONE → 의존성 해제

코드가 괜찮으면 **승인**합니다. `/tf-review`로 Approve를 누르면 연쇄 반응이 일어나요.

```
✅ TASK-004 Approved!
   → TASK-004: REVIEW → DONE
   → TASK-005 unblocked (5일 예보 차트, 의존: 004)
   → Codex: picking up TASK-005
```

1. 카드가 DONE으로 이동.
2. 거기에 의존하던 TASK-005의 blocked가 풀림.
3. Codex가 자동으로 다음 태스크를 claim.

**승인 → 의존성 해소 → 다음 태스크 자동 시작.** 모듈 3에서 본 그 파이프라인이 그대로 돕니다.

### 3. 반려(Reject) — 피드백과 함께 되돌리기 (10분)

> 화면: 보드 탭 — REVIEW 카드를 Reject, 피드백 코멘트 입력

이번엔 코드가 부족한 경우입니다. 예를 들어 TASK-005(5일 예보 차트)를 검토했더니, **차트는 그렸는데 날짜 축 레이블이 없고 모바일에서 깨진다**고 해봅시다.

이때 **반려**합니다. `/tf-review`에서 Reject를 누르고 피드백을 적어요.

```
R
> 5일 예보 차트에 날짜 축 레이블을 추가해주세요.
> 그리고 모바일 화면(width < 480px)에서 차트가 잘립니다 — 반응형으로 고쳐주세요.
```

```
🔄 TASK-005 Rejected with feedback
   → TASK-005: REVIEW → IN_PROGRESS
   → Codex: 피드백 읽음, 재작업 시작
```

반려하면:

1. 카드가 다시 **IN_PROGRESS**로 돌아갑니다 (상태 머신: REVIEW → IN_PROGRESS).
2. 에이전트가 피드백을 읽고 **수정 작업**을 시작해요.
3. 수정이 끝나면 다시 REVIEW로 올라옵니다.

> 화면: 레인 탭 — Codex 레인에 "피드백 반영 중" 로그

```
[Codex] 피드백 수신: 날짜 축 레이블 + 모바일 반응형
[Codex] Editing ForecastChart.tsx: x축 dateFormatter 추가
[Codex] Editing ForecastChart.css: @media (max-width: 480px) 처리
[Codex] Activity: "피드백 반영 완료 — 재제출"
[Codex] Status: IN_PROGRESS → REVIEW
```

이게 **PM ↔ 에이전트의 리뷰 루프**입니다. 실제 개발팀의 PR(Pull Request) 리뷰와 똑같은 구조예요 — 리뷰어가 코멘트를 달면, 작성자가 고쳐서 다시 올립니다. 차이는 작성자가 사람이 아니라 에이전트라는 것뿐이죠.

> 💡 좋은 피드백은 **구체적**입니다. "별로예요"가 아니라 "날짜 축 레이블 추가, width<480px 반응형". 구체적일수록 에이전트가 정확히 고칩니다. PM의 실력 = 피드백의 구체성.

### 4. FAILED와 BLOCKED — 멈춤의 두 종류 (7분)

> 화면: 보드 탭 — FAILED / BLOCKED 컬럼

반려(REVIEW → IN_PROGRESS)는 "코드가 부족해서 다시"입니다. 하지만 작업이 멈추는 다른 두 가지 경우가 있어요. 보드에 별도 상태로 표시됩니다.

| 상태           | 언제                                      | PM이 하는 일                     |
| -------------- | ----------------------------------------- | -------------------------------- |
| 🟥 **FAILED**  | 에이전트가 작업 중 실패(에러로 못 끝냄)   | 원인 확인 후 **재시도**(Restart) |
| 🟧 **BLOCKED** | 외부 요인으로 막힘(키 누락, 의존 미완 등) | 막힌 원인을 제거하고 **재개**    |

- **FAILED** — 예: API 키가 잘못돼서 에이전트가 테스트를 못 돌리고 멈춤. 원인을 고치고 재시도하면 됩니다.
- **BLOCKED** — 예: TASK-006(연동 테스트)이 TASK-003·005를 기다리는 중. 선행이 끝나면 자동으로 풀립니다. 또는 OpenWeather API 키가 없어서 막혔다면, 키를 넣어주면 풀려요.

> 화면: 보드 탭 — FAILED 카드를 Restart, BLOCKED 카드가 의존 해소로 자동 풀림

핵심은 — **멈춤은 정상**이라는 겁니다. 실제 개발에서도 항상 뭔가 막히죠. 중요한 건 마블로가 멈춘 이유를 **상태로 명확히 보여주고**, 각각에 손잡이(Restart/재개)가 있다는 점입니다. (FAILED/BLOCKED를 포함한 상황별 대응의 전체 카탈로그는 **모듈 5**에서 더 깊이 다룹니다.)

> **[설명보드: 4-4 리뷰 루프 + 상태 게이트]** — Excalidraw (후속 제작)
>
> - 가운데: 카드 한 장이 `IN_PROGRESS → REVIEW`로 올라오고, PM(사람 아이콘)이 검문.
> - 두 갈래: 위쪽 "Approve → DONE → 의존성 해제", 아래쪽 "Reject + 피드백 → IN_PROGRESS(에이전트 재작업) → 다시 REVIEW" 순환 화살표.
> - 옆: FAILED(🟥)·BLOCKED(🟧) 박스 — 각각 "Restart" / "원인 제거 후 재개" 손잡이.
> - 강조 카피: "에이전트는 제안, 결정은 PM. 머지 게이트는 끝까지 사람이." ※ Gemini 표기 금지.

## 정리 (1분)

1. **모든 카드는 REVIEW 검문소를 거친다.** 코드 탭 diff로 요구 충족·누락·정합성을 본다.
2. **Approve → DONE → 의존성 해제 → 다음 자동 시작.**
3. **Reject + 구체적 피드백 → IN_PROGRESS 반려 → 에이전트 재작업 → 재제출.** PR 리뷰와 같은 루프.
4. **FAILED(재시도)·BLOCKED(원인 제거 후 재개)** — 멈춤은 정상, 각각 손잡이가 있다.
5. **게이트는 사람이.** 에이전트는 틀릴 수 있고, 머지 권한은 끝까지 PM이 쥔다.

품질 보정까지 끝났습니다. 이제 마지막 — 두 모델이 만든 결과물을 **하나로 합쳐 동작시키고**, 한 바퀴를 회고합니다.
