# 날씨 대시보드 기획

> 모듈 3 · 섹션 3-1 · 약 15분
> 관련: [[2-6_플로우에디터_기초]] | [[3-2_날씨대시보드_실행]]

---

## 도입 (3분)

자, 여러분! 드디어 Part 3 — 실전 파트에 들어왔습니다.

지금까지 모듈 1에서 마블로를 설치하고, 모듈 2에서 아키텍처와 에이전트 스킬까지 이해했죠? 이제 직접 프로젝트를 만들어볼 차례입니다.

화면: 마블로 데스크탑 앱 — 빈 워크스페이스 상태

다만, 바로 큰 프로젝트에 들어가면 부담스러우실 수 있어요. 그래서 **워밍업 프로젝트**를 하나 먼저 해봅니다. 바로 **날씨 대시보드**입니다.

이 프로젝트의 목적은 단 하나예요:

> **"마블로의 전체 워크플로우를 한 바퀴 돌려보는 것"**

`/tf-plan` → `/tf-start` → 관찰 → `/tf-review` — 이 흐름을 몸에 익히는 겁니다. 기술적으로 어려운 건 없어요. 에이전트들이 다 해줄 거니까요. 여러분은 **PM(프로젝트 매니저) 역할**에 집중하시면 됩니다.

---

## 본문

### 프로젝트 개요 (2분)

화면: 완성된 날씨 대시보드 데모 — 도시 검색 + 날씨 카드 + 5일 예보 차트

우리가 만들 건 이렇습니다:

- **입력**: 도시 이름 (예: "Seoul", "New York")
- **출력**: 현재 날씨 카드 + 5일 예보 차트
- **기술 스택**: FastAPI (백엔드) + Next.js (프론트엔드) + OpenWeatherMap API

되게 심플하죠? 하지만 이 안에 백엔드-프론트엔드 분리, 외부 API 연동, 컴포넌트 설계 등 실제 서비스의 핵심 구조가 다 들어있습니다.

### `/tf-plan`으로 기획 시작하기 (5분)

자, 이제 마블로에서 기획을 해볼까요?

화면: 마블로 터미널 패널 — Claude Code 세션

**(실습)** 터미널에 다음 명령을 입력해봅시다:

```bash
/tf-plan 날씨 대시보드. 도시 검색하면 현재 날씨 + 5일 예보. FastAPI + Next.js + OpenWeatherMap API.
```

이 한 줄이면 됩니다. 마블로가 뭘 하느냐면요:

1. **Socratic Questions** — "어떤 형태의 UI를 원하시나요?", "인증은 필요한가요?" 등 질문을 먼저 해요
2. 여러분이 답하면, **PRD(Product Requirements Document)**를 자동 생성합니다
3. PRD를 기반으로 **태스크 분해**까지 자동으로 해줘요

화면: `/tf-plan` 실행 후 Socratic Questions 출력 화면

질문이 나오면 간단히 답해주세요. 예를 들어:

```
Q: UI 형태는?
A: 카드형 대시보드, 반응형

Q: 인증 필요?
A: 아니요, 공개 서비스

Q: 추가 기능?
A: 즐겨찾기 도시 저장 정도
```

이렇게 대화하면 마블로가 PRD를 만들고, 곧이어 태스크 목록을 제안합니다.

### 생성된 태스크 확인 (3분)

화면: 태스크 목록 출력 — 6개 태스크

자, 마블로가 만든 태스크를 보겠습니다:

```
[TASK-001] 날씨 API 프록시 엔드포인트      (backend)
[TASK-002] 즐겨찾기 도시 저장 API          (backend, depends_on: 001)
[TASK-003] 도시 검색 UI                    (frontend, depends_on: 001)
[TASK-004] 날씨 카드 컴포넌트              (frontend, depends_on: 001)
[TASK-005] 5일 예보 차트                   (frontend, depends_on: 004)
[TASK-006] API 연동 테스트                 (test, depends_on: 003, 005)
```

여기서 주목할 포인트가 세 가지 있어요:

**첫째, 태스크의 크기.** 각 태스크가 하나의 명확한 결과물을 가지고 있죠? "날씨 API 프록시 엔드포인트" — 이건 에이전트가 딱 하나 만들면 되는 거예요. 이게 좋은 태스크입니다.

**둘째, 의존성 관계.** `depends_on`을 보세요. TASK-003, 004는 TASK-001에 의존합니다. 백엔드 API가 먼저 준비되어야 프론트엔드가 연동할 수 있으니까요. 이걸 마블로가 알아서 파악해줍니다.

**셋째, 태스크 유형.** backend, frontend, test — 각 태스크에 역할이 있어요. 이에 따라 적합한 에이전트가 배정됩니다.

### 좋은 태스크 vs 나쁜 태스크 (2분)

여기서 중요한 개념 하나 짚고 갈게요.

화면: 좋은 태스크 vs 나쁜 태스크 비교 슬라이드

**나쁜 태스크의 예:**
```
❌ "백엔드 만들어줘"
❌ "프론트엔드 완성"
❌ "전체 API 구현"
```

이런 태스크는 너무 크고 모호합니다. 에이전트가 뭘 해야 할지 알 수 없어요.

**좋은 태스크의 예:**
```
✅ "날씨 API 프록시 엔드포인트 — GET /api/weather/{city}"
✅ "도시 검색 UI — 자동완성 + 디바운싱"
✅ "날씨 카드 컴포넌트 — 온도, 습도, 풍속 표시"
```

차이가 보이시죠? **구체적인 결과물**이 명확한 게 좋은 태스크입니다.

마블로의 `/tf-plan`이 자동으로 이런 수준의 태스크를 만들어주지만, 여러분이 검토하고 필요하면 수정해야 해요. **PM은 태스크를 승인하는 사람**이니까요.

태스크가 마음에 들면 승인하고, 아니면 "TASK-002는 빼주세요" 또는 "TASK-004를 더 세분화해주세요" 같이 피드백을 줄 수 있습니다.

---

## 정리

이번 섹션에서 배운 핵심:

1. **`/tf-plan` 한 줄**이면 기획이 시작된다
2. Socratic Questions → PRD → 태스크 분해까지 자동으로 진행
3. 좋은 태스크는 **구체적이고, 독립적이며, 결과물이 명확**하다
4. PM으로서 태스크를 **검토하고 승인**하는 게 여러분의 역할이다

다음 섹션에서는 이 태스크들을 실제로 에이전트에게 맡겨서 실행하는 과정을 보겠습니다. 에이전트들이 코딩하는 걸 실시간으로 지켜보는 거죠 — 꽤 재미있을 겁니다!
