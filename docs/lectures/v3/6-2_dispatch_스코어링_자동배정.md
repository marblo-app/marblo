# dispatch 스코어링 + 자동 배정

> 모듈 6 · 섹션 6-2 · 약 25분
> 관련: [[6-1_모델별강점_Claude_Codex_Antigravity]] | [[6-3_에이전트_재활용_멀티윈도우]]

---

## 이 강의에서 다루는 것

- **학습목표:** 마블로가 "이 태스크엔 누구"를 정하는 **dispatch 스코어링**의 규칙(역할 게이트 → 모델 강점 → 비용효율 → 부하·재사용)을 이해하고, 자동 추천을 사람이 보정하는 워크플로를 익힌다.
- **시연할 마블로 화면·기능:** 에이전트 탭(자동 배정 결과) + 점수 계산 코드 한 조각.
- **진행할 프로젝트 단계:** **P3 배정 복기** — 콜드메일 SaaS의 태스크가 왜 그 모델에 갔는지 점수로 되짚기.
- **핵심 메시지:** "배정은 **규칙 기반 + 사람 보정.**"

---

## 도입 — 왜 자동 배정인가 (3분)

6-1에서 "Claude는 설계, Codex는 구현, Antigravity는 자율 흐름"이라는 강점을 봤습니다. 그런데 태스크가 6개면 손으로 나눌 수 있어도, **30개·50개**가 되면요? 매번 "이건 누구, 저건 누구"를 사람이 다 정하긴 어렵습니다.

> 화면: 보드 탭 — TODO 컬럼에 수십 개 카드가 쌓인 모습

그래서 마블로는 **dispatch 스코어링**을 씁니다. 태스크 하나와 에이전트 하나를 놓고 **점수를 매겨**, 가장 높은 점수의 에이전트에게 배정하는 거예요. 사람이 만든 규칙을 기계가 일관되게 적용하는 거죠.

핵심은 이겁니다 — **자동은 추천이지, 독재가 아닙니다.** 점수는 출발점일 뿐, 최종 결정은 PM인 여러분이 한 번 더 봅니다. 그 균형을 이번 섹션에서 잡습니다.

## 본문

### 1. 1단계 — 역할 게이트 (hard gate) (4분)

> 화면: 슬라이드 — "역할이 안 맞으면 0점"

가장 먼저, **역할(role)이 맞는지**부터 봅니다. 이건 점수가 아니라 **관문**이에요.

```
backend  태스크  →  backend 에이전트가 아니면  배정 후보에서 탈락(0점)
frontend 태스크  →  frontend 에이전트라야 후보
```

역할이 맞으면 **기본 100점**을 깔고 시작하고, 안 맞으면 그냥 후보에서 빠집니다. 그래서 프론트 태스크가 백엔드 에이전트에게 잘못 가는 일이 구조적으로 막힙니다. 모듈 4·5에서 태스크마다 `backend`/`frontend`/`test` 배지를 붙였던 게 바로 이 게이트의 입력값이었어요.

### 2. 2단계 — 모델 강점 점수 (heterogeneous scoring) (6분)

> 화면: `dispatch-scoring.ts` — MODEL_BASE_SCORE / MODEL_TAG_BONUSES

역할 게이트를 통과한 후보들 사이에서, **어떤 모델이 더 적합한가**를 가립니다. 여기서 6-1의 "강점 태그"가 실제 숫자로 들어옵니다.

먼저 모델마다 **기본 점수**가 다릅니다.

```
MODEL_BASE_SCORE
  claude       50
  codex(gpt)   45
  antigravity  45
```

Claude가 살짝 높은 건 범용 코딩 기본기 때문입니다. 다만 차이를 작게 둬서, 다른 모델이 **자기 강점 태그로 역전할 여지**를 남겼어요. (예전엔 Claude 강점이 전부 30점이라 거의 항상 Claude가 이겼는데, 그걸 의도적으로 낮췄습니다.)

그 위에 **강점 태그 보너스**를 더합니다.

```
MODEL_TAG_BONUSES (발췌)
  Claude       architecture +25 · multi-file +25 · coding +25 · mcp +20
  Codex(gpt)   simple-fix +25 · quick-edit +20 · test +15 · boilerplate +15
  Antigravity  agentic +30 · multi-agent +25 · autonomous +25 · research +15
```

그리고 **약점 태그 페널티**도 있습니다 — 강점이 없는 모델에 억지로 보내면 감점됩니다.

```
MODEL_TAG_PENALTIES (발췌)
  Codex(gpt)   architecture -10 · large-refactor -10
```

예를 들어 봅시다.

- **`simple-fix` 태스크** → Codex: 45(base) + 25(simple-fix) = **70**, Claude: 50 + 0 = 50 → **Codex 승**
- **`architecture` 태스크** → Claude: 50 + 25 = **75**, Codex: 45 − 10(페널티) = 35 → **Claude 승**
- **`agentic` 자율 태스크** → Antigravity: 45 + 30 = **75** → **Antigravity 승**

보이시죠? 강점 태그가 점수를 뒤집습니다. "Claude는 설계, Codex는 빠른 수정, Antigravity는 자율 흐름"이라는 6-1의 직관이 **그대로 숫자로** 구현된 겁니다.

### 3. 3단계 — 비용효율 보정 (3분)

> 화면: 슬라이드 — 비용효율 점수

비슷한 점수라면, **더 싼 모델**이 약간의 가산점을 받습니다. 똑같은 결과라면 저렴한 쪽이 합리적이니까요.

```
비용효율 지표 (높을수록 저렴/효율적)
  Codex(gpt)   10
  Antigravity   9
  Claude        3
```

단, 이 보정에는 **상한(cap)**이 걸려 있습니다. 비용효율이 좋다고 `architecture` 같은 **고난도 태스크를 싼 모델로 끌고 가지 못하도록**, 어려운 태그에서는 비용 보정을 약화시켜요. "싸다고 아무 데나 보내지 않는다" — 이 균형이 중요합니다.

### 4. 4단계 — 부하·재사용 보정 (4분)

> 화면: 에이전트 탭 — idle / working 상태가 섞인 카드들

마지막으로 **지금 상황**을 반영합니다.

```
- idle(유휴) 에이전트          → 보너스 (+20)
- 고우선(priority≥4) + idle    → 추가 보너스 (+30)
- 이미 바쁜 에이전트           → 부하 페널티 (현재 태스크 수 × −15)
- 기존 에이전트 재사용(reuse)  → 새로 spawn 하는 것보다 우대
```

같은 역할의 에이전트가 둘이면 **부하가 적은 쪽**으로 갑니다. 그리고 **재사용 우대**가 핵심인데 — 이미 떠 있는 idle 에이전트에게 새 일을 주는 게, 매번 새 프로세스를 띄우는 것보다 빠르고 싸기 때문입니다. (재사용은 6-3에서 직접 다룹니다.)

이 모든 단계를 한 함수가 묶습니다. 깊은 DAG·배치 라우팅 코드까지 보고 싶다면 **[부록 A]**에 전체가 있지만, 여기서는 점수의 골격만 봅니다.

```typescript
// 한 (태스크, 에이전트) 쌍의 적합도 점수 — 골격
function calculateScore(task, agent): number {
  // 1) 역할 게이트 — 안 맞으면 후보 탈락
  if (agent.role !== task.role) return 0;
  let score = 100;

  // 2) 모델 강점/약점 (base + 태그 보너스 − 페널티)
  score += MODEL_BASE_SCORE[agent.model];
  score += tagBonus(agent.model, task.tags);
  score -= tagPenalty(agent.model, task.tags);

  // 3) 비용효율 (상한 cap 적용)
  score += cappedCostEfficiency(agent.model, task.tags);

  // 4) 부하·재사용·유휴 보정
  if (agent.status === "idle") score += 20;
  if (task.priority >= 4 && agent.status === "idle") score += 30;
  score -= agent.currentTaskCount * 15;

  return Math.max(0, score);
}
```

> 💡 코드를 외울 필요는 없습니다. 기억할 한 줄은 — **"역할로 거른 뒤, 모델 강점·비용·부하를 더해 가장 높은 점수에게 준다."**

### 5. 사람 보정 — 마지막 한 수 (3분)

> 화면: 에이전트 탭 — 자동 추천 위에서 PM이 모델을 바꾸는 모습

자동 배정은 **최선의 추천**이지 명령이 아닙니다. P3를 복기해봅시다 — 점수상으로는 Codex가 맡을 태스크였는데, "이 화면은 결제 흐름이라 품질이 더 중요하다" 싶으면 PM이 Claude로 **바꿀 수 있습니다.**

마블로의 설계 철학이 여기 있습니다.

- **기계는 일관성** — 50개 태스크를 같은 규칙으로 빠르게 배분
- **사람은 맥락** — 점수가 모르는 비즈니스 중요도·리스크를 마지막에 반영

그래서 dispatch는 PM의 일을 **없애는 게 아니라 줄여줍니다.** 30개 중 28개는 자동으로 맞고, 여러분은 손이 가는 2개만 손보면 되는 거예요.

## 정리 (2분)

1. **4단계 점수.** ①역할 게이트(hard) → ②모델 강점(base+태그−페널티) → ③비용효율(상한) → ④부하·재사용·유휴.
2. **강점이 점수를 뒤집는다.** `architecture`는 Claude, `simple-fix`는 Codex, `agentic`은 Antigravity — 6-1의 직관이 그대로 숫자로.
3. **싸다고 아무 데나 안 보낸다.** 비용 보정엔 상한이 있어 고난도 태스크를 저비용 모델로 끌고 가지 않는다.
4. **자동은 추천, 결정은 PM.** 기계의 일관성 + 사람의 맥락 = 가장 좋은 배정.

다음 섹션에서는 배정된 에이전트를 **재활용하고 정리하는 법**, 그리고 P2·P3를 **멀티윈도우로 동시에** 굴리는 법을 봅니다.
