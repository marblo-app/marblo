# 태스크 일괄 생성 + 이종 에이전트 배정

> 모듈 5 · 섹션 5-2 · 약 25분
> 관련: [[5-1_요구사항분석_페르소나]] | [[5-3_Sprint1_백엔드_라이브빌딩]]

---

## 이 강의에서 다루는 것

- **학습목표:** 기획 단계에서 만든 18~22개 태스크를 보드에 **일괄 등록**하고, 역할 배지에 맞춰 **이종 에이전트 팀(Claude·Codex, +선택 Antigravity)을 스폰·배정**하는 방법을 익힌다.
- **시연할 마블로 화면·기능:** 보드 탭(`/tf-create-tasks` 일괄 생성 → TODO 카드 22개) + 에이전트 탭(`/tf-spawn-agents`로 모델별 스폰) + `/tf-status`.
- **진행할 프로젝트 단계:** P3 백로그 등록 + 팀 투입.
- **핵심 메시지:** "팀 편성 = 태스크 성격 × 모델 강점. 한 모델로 다 밀지 않는다."

---

## 도입 — 기획을 시스템에 올린다 (3분)

지난 섹션에서 `/tf-analyze`로 ReachWave PRD를 만들고 22개 태스크를 분해했습니다. 각 태스크엔 역할 배지가 붙어 있죠.

> 화면: 마블로 워크스페이스 — 아직 비어 있는 보드 + 하단 오케 PTY

이제 이 기획을 **실제 시스템에 등록**하고, **이종 팀을 투입**할 차례입니다. 워밍업(P1)에선 `/tf-start` 하나로 기획+실행을 일체로 갔지만, 졸업 작품은 단계를 끊습니다.

```
/tf-analyze (5-1, 완료)  →  /tf-create-tasks  →  /tf-spawn-agents  →  /tf-status
       ↑                          ↑                     ↑
   PRD + 분해             보드에 22개 일괄 등록    역할별 이종 스폰     실시간 추적
```

왜 끊을까요? **22개를 한꺼번에 에이전트에 맡기기 전에, 한 번 더 검토할 시간**을 갖기 위해서입니다. 큰 프로젝트일수록 시작 전 1분 점검이 몇 시간짜리 스프린트의 안정성을 좌우합니다.

## 본문

### 1. `/tf-create-tasks` — 22 태스크 일괄 등록 (6분)

**(실습)** 오케 패널:

```
/tf-create-tasks
```

내부적으로 `create_tasks_bulk` MCP 도구가 호출되어 22개 태스크를 한 번에 생성합니다.

> 화면: 보드 탭 — TODO 컬럼에 22개 카드가 한꺼번에 등장

보드를 보면 22개 카드가 TODO 컬럼에 줄 서 있습니다. 의존성이 풀린 3개(001/002/019)는 회색이 아니라 바로 시작 가능 상태로 표시돼요.

> 화면: 보드 카드 클릭 — 상세 패널(역할·의존성·블록 관계)

### 2. 마지막 점검 (4분)

에이전트를 투입하기 전, 마지막으로 확인합니다.

```
✓ 22개가 적절한가? (너무 많으면 4~5개씩 묶기)
✓ 의존성이 병목을 안 만드는가? (백엔드와 프론트가 병렬 가능한가)
✓ 역할 배지가 정확한가? (결제 010·011은 backend로 묶였는지)
✓ 빠진 태스크는 없는가? (에러 페이지, 404 등)
```

수정이 필요하면 그 자리에서:

```
# 태스크 추가
/tf-add "에러 페이지 + 404 라우트" --role frontend --depends-on TASK-013

# 우선순위/의존성 조정
/tf-update TASK-019 --priority high   # Docker는 빨리 깔리게
```

오타·누락이 없으면 다음으로 갑니다.

### 3. `/tf-spawn-agents` — 이종 팀 스폰 (8분)

**(실습)**

```
/tf-spawn-agents
```

> 화면: 에이전트 탭 + 오른쪽 터미널 패널에 에이전트 탭이 줄줄이 생성

```
🤖 Spawning heterogeneous agent team for ReachWave...

역할·태그 기반 자동 배정(dispatch 스코어링):
  - Claude 우위: 002·004·005·007·009·010·011 (architecture · multi-file · 견고함)
  - Codex 우위 : 001·003·006·008·012·019 / 013-018 / 020·021·022 (boilerplate · UI · test)

Agent Team (4 agents):
  [backend-claude]   → 7 backend tasks (model: claude)  ← 인증·LLM·A/B·결제·집계
  [backend-codex]    → 6 backend tasks (model: codex)   ← DB·CSV·큐·webhook·한도·Docker
  [frontend-codex]   → 6 frontend tasks (model: codex)
  [test-codex]       → 3 test tasks (model: codex)      ← Sprint 막바지 합류

Starting work (의존성 없는 태스크 자동 claim):
  backend-codex   : claiming TASK-001 (Postgres + Alembic)
  backend-codex   : claiming TASK-019 (Docker Compose, parallel)
  backend-claude  : claiming TASK-002 (Email + Google OAuth)
  frontend-codex  : IDLE (002 OAuth 완료 후 로그인 UI 시작)
  test-codex      : IDLE (개발 태스크 완료 대기)
```

여기서 마블로의 핵심이 드러납니다.

**① 같은 역할도 모델로 분리됩니다.**
백엔드 12개 중 7개는 Claude(architecture·견고함), 6개는 Codex(boilerplate·CRUD)가 맡습니다. 결제 webhook(011)·LLM 분석(004)처럼 설계 비중이 큰 건 Claude로, DB 스키마(001)·큐(006)처럼 패턴화된 건 Codex로. **한 모델로 다 밀지 않습니다.**

**② 의존성 풀린 태스크만 자동 claim 합니다.**
backend-codex는 TASK-001·019를 동시에 잡고, backend-claude는 TASK-002로. 의존성 걸린 것들은 잠시 대기.

**③ 유휴 에이전트는 자원이 회수되지 않습니다.**
frontend-codex·test-codex는 idle이지만 컨텍스트가 살아 있어, OAuth가 끝나는 순간 그대로 합류합니다.

> 💡 **선택: 3번째 멤버 Antigravity**
> 응답률 집계(009)처럼 대용량 분석이 많은 태스크가 있거나, 손이 더 필요하면 에이전트 탭에서 **Antigravity**를 추가로 스폰해 합류시킬 수 있습니다. 기본은 Claude + Codex 2인이고, Antigravity는 "있으면 좋은 3번째"예요. (스폰 옵션 UI는 claude / codex / antigravity / local(Ollama) / custom 순으로 보입니다.)

> 화면: 에이전트 탭 — 4개 에이전트 카드(모델 아이콘·담당 태스크 수·상태)

## 정리 (1분)

1. **`/tf-create-tasks`** — 22개 태스크를 보드에 일괄 등록(`create_tasks_bulk`).
2. **마지막 점검** — 의존성·역할·스코프를 시작 전에 한 번 더 확인.
3. **`/tf-spawn-agents`** — 이종 팀 4명 스폰(Claude 1 + Codex 3), 역할·태그 기반 자동 배정.
4. **같은 역할도 모델로 분리.** Claude는 견고함이 필요한 백엔드 핵심, Codex는 양 많은 보일러플레이트·UI·테스트.
5. **Gemini는 빠졌고**, 손이 더 필요하면 **Antigravity**를 선택적 3번째로 합류.

다음 섹션부터 본격 라이브 빌딩입니다 — Sprint 1 백엔드. backend-claude와 backend-codex가 어떻게 다르게 일하는지 직접 봅니다.
