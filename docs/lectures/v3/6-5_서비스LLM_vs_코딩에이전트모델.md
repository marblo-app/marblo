# 서비스 LLM vs 코딩 에이전트 모델

> 모듈 6 · 섹션 6-5 · 약 20분
> 관련: [[6-4_사용량탭_비용추적최적화]] | [[7-1_워크트리통합_main머지]]

---

## 이 강의에서 다루는 것

- **학습목표:** **내가 만드는 서비스 안에서 호출하는 LLM**과 **나를 도와 코드를 짜는 마블로 에이전트의 모델**이 **완전히 다른 축**임을 구분하고, 서비스 LLM은 저비용 1개로 추상화해 "1줄 교체" 가능하게 두는 법을 익힌다.
- **시연할 마블로 화면·기능:** 코드 탭 — P3 콜드메일 SaaS의 LLM 호출부(`llm/client`).
- **진행할 프로젝트 단계:** **P3 서비스 LLM 정리** — 분석·메일 생성을 부르는 코드를 한 곳으로 모은다.
- **핵심 메시지:** "**둘은 다른 축이다.**"

---

## 도입 — 가장 흔한 혼동 (3분)

수강생이 가장 자주 헷갈리는 지점이 여기입니다.

> 화면: 슬라이드 — 두 개의 화살표가 그려진 그림
> (왼쪽) 나 → 마블로 에이전트 → 코드를 짠다
> (오른쪽) 내 서비스 → LLM API → 사용자에게 기능을 준다

P3 콜드메일 SaaS를 떠올려봅시다. 여기엔 **LLM이 두 군데** 등장합니다.

1. **마블로 에이전트의 모델** — Claude·Codex·Antigravity가 **나를 도와 SaaS의 코드를 짭니다.** (지금까지 모듈 내내 다룬 것)
2. **서비스 자체의 LLM** — 완성된 SaaS가 **사용자의 회사·직책을 분석하고 콜드메일 5톤을 생성**할 때 부르는 LLM API. (이건 내 제품의 일부)

이 둘은 **이름만 같지(LLM) 완전히 다른 축**입니다. 한쪽을 정하는 기준이 다른 쪽엔 적용되지 않아요. 이번 섹션에서 이걸 확실히 못 박습니다.

## 본문

### 1. 두 축을 분리한다 (5분)

> 화면: 슬라이드 — 비교 표

표로 갈라봅시다.

| 구분              | 🛠️ 코딩 에이전트 모델                  | 🤖 서비스 LLM                         |
| ----------------- | -------------------------------------- | ------------------------------------- |
| **누구를 돕나**   | 개발자(나)를 도와 코드를 짠다          | 내 제품의 사용자에게 기능을 준다      |
| **어디서 사나**   | 마블로 보드 위 에이전트                | 내 서비스 코드(`llm/client`) 안       |
| **어떻게 고르나** | dispatch 스코어링 — 태스크별 자동 추천 | 내가 직접 1개 선택 — 비용·품질 보고   |
| **몇 개 쓰나**    | 이종 플릿 (Claude+Codex+Antigravity)   | **하나로 단순히 시작** (필요 시 교체) |
| **예시**          | "백엔드는 Claude, 테스트는 Codex"      | "회사 분석 → 저비용 모델 1개로 호출"  |

핵심 차이는 **선택의 주체와 목적**입니다.

- **코딩 에이전트 모델**은 마블로가 태스크 성격에 맞춰 **여러 모델을 섞어** 자동 추천합니다. 6-2에서 본 그대로요.
- **서비스 LLM**은 **내가** 제품 설계자로서 고릅니다. 그리고 여기서는 보통 **이종 플릿이 필요 없습니다** — 저비용 모델 하나로 단순하게 시작하는 게 정석이에요.

### 2. 서비스 LLM은 저비용 1개로 추상화 (6분)

> 화면: 코드 탭 — P3의 `llm/client.py`

P3 콜드메일 SaaS의 LLM 호출부를 봅시다. 분석도, 5톤 생성도, 편집도 — 전부 **하나의 저비용 모델**로 시작합니다. 왜요?

1. **비용 최소** — 사용자 한 명이 메일 250통(5톤 × 50리드)을 뽑습니다. 서비스 LLM은 **대량 호출**이라 모델이 비싸면 단가가 그대로 폭발해요. 저비용 모델이 정답입니다.
2. **복잡도 0** — 듀얼 LLM·모델 라우팅은 **내 학습 본질과 무관한** 복잡도만 더합니다. 제품 초기엔 단순한 게 이깁니다.
3. **교체 가능성** — 그래도 나중에 더 좋은 모델로 바꾸고 싶을 수 있죠. 그래서 **추상화**해 둡니다.

추상화의 정석은 **호출을 한 곳으로 모으고, 모델 이름만 상수로 빼는 것**입니다.

```python
# llm/client.py — 서비스 LLM 호출을 한 곳에 모은다
MODEL = "low-cost-model-v1"   # ← 모델 이름은 여기 한 줄만

def complete(prompt: str) -> str:
    return llm_api.chat(model=MODEL, messages=[...])
```

분석·생성·편집 어디서든 `complete()`만 부릅니다. 모델 이름은 `MODEL` **상수 한 줄**에만 박혀 있어요.

> 💡 예전 강의에선 여기에 특정 모델명(예: Gemini Flash)을 박았습니다. 지금은 **"저비용 모델 1개"라는 추상화**로 봅니다 — 어떤 저가 모델이든 좋고, 중요한 건 **호출이 한 곳에 모여 있다는 것**입니다. 특정 모델에 묶이지 마세요.

### 3. "1줄 교체" 데모 (4분)

> 화면: 코드 탭 — MODEL 상수 한 줄을 바꾸는 장면

추상화가 잘 됐는지는 **교체 한 번으로** 증명됩니다. 서비스가 커져서 "분석 품질을 올리고 싶다"는 순간이 오면?

```python
# Before
MODEL = "low-cost-model-v1"

# After — 단 한 줄
MODEL = "claude-sonnet"        # 또는 다른 상위 모델
```

`complete()`를 부르는 코드는 **한 줄도 안 바뀝니다.** 분석부도, 생성부도, 편집부도 그대로예요. 모델 이름 한 줄만 갈았을 뿐인데 서비스 전체의 LLM이 바뀝니다.

> ⚠️ 만약 호출이 코드 곳곳에 흩어져 있었다면, 교체할 때 **수십 군데를 찾아 고쳐야** 했을 겁니다. 한 곳으로 모으는 추상화의 가치가 여기서 드러나요 — **"1줄 교체"는 잘 추상화한 코드의 보상**입니다.

이게 제품 설계의 좋은 습관입니다. **싸게 시작하되, 비싸게 갈아탈 길을 열어둔다.** 마블로 에이전트(Claude)에게 이 추상화를 시키면, 처음부터 `llm/client`로 모아서 짜줍니다 — 6-2의 dispatch가 이 설계 태스크를 Claude에 배정하는 이유이기도 하고요.

### 4. 다시, 헷갈리지 않기 (2분)

> 화면: 슬라이드 — 도입의 두 화살표 그림 재등장

정리 삼아 한 번 더 못 박습니다.

```
🛠️  코딩 에이전트 모델  = 나를 돕는 도구
     → 마블로가 태스크별로 Claude/Codex/Antigravity를 자동 추천 (이종, 섞어 씀)

🤖  서비스 LLM          = 내 제품의 부품
     → 내가 저비용 1개를 골라 llm/client로 추상화 (단일, 1줄로 교체)
```

"백엔드는 Claude, 테스트는 Codex"는 **코딩 에이전트** 이야기. "회사 분석은 저비용 모델 1개"는 **서비스 LLM** 이야기. 같은 'LLM'이라는 단어를 쓰지만 **고르는 사람도, 목적도, 개수도 다릅니다.**

---

## 정리 (1분)

1. **두 개의 다른 축.** 🛠️ 코딩 에이전트 모델(나를 돕는 도구) vs 🤖 서비스 LLM(내 제품의 부품). 이름만 같지 완전히 별개다.
2. **코딩 에이전트는 이종·자동.** 마블로가 태스크 성격에 맞춰 Claude·Codex·Antigravity를 섞어 추천한다(6-2).
3. **서비스 LLM은 단일·저비용으로 시작.** 대량 호출이라 단가가 중요하고, 복잡도를 더할 이유가 없다.
4. **추상화로 1줄 교체.** 호출을 `llm/client` 한 곳에 모으고 모델 이름만 상수로 빼면, 나중에 상위 모델로 한 줄에 갈아탈 수 있다.

이것으로 모듈 6 — 플릿·오케 심화와 사용량/비용 — 을 마칩니다. 모델을 구분하고, 자동 배정을 이해하고, 에이전트를 운영하고, 비용을 실측으로 통제하는 법까지 익혔습니다.

다음 모듈에서는 이렇게 완성한 P3를 **프로덕션으로 — 워크트리 통합부터 GCP 배포까지** 올립니다.
