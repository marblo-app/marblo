# 날씨 대시보드 회고

> 모듈 3 · 섹션 3-4 · 약 10분
> 관련: [[3-3_날씨대시보드_PM역할]] | [[4-1_요구사항_분석]]

## 도입 (2분)

방금 여러분이 한 일을 정리해봅시다.

화면: 마블로 워크스페이스 — 모든 태스크 DONE, 프로젝트 완료 상태

도시 이름을 검색하면 현재 날씨와 5일 예보를 보여주는 대시보드를 만들었습니다. FastAPI 백엔드, Next.js 프론트엔드, OpenWeatherMap API 연동까지. 에이전트 2개가 6개 태스크를 처리해서 완성했죠.

여러분이 직접 코딩한 건 없습니다. 대신 **기획하고, 관찰하고, 리뷰하고, 승인**했습니다. 이게 마블로에서의 개발 방식이에요.

---

## 본문

### 전체 워크플로우 복습 (3분)

화면: 워크플로우 다이어그램 — 4단계 흐름도

한 바퀴 전체를 정리하면:

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  /tf-plan   │ →  │  /tf-start  │ →  │  /tf-status │ →  │  /tf-review │
│  기획       │    │  실행       │    │  모니터링   │    │  리뷰       │
│             │    │             │    │             │    │             │
│ PRD 생성    │    │ 태스크 등록 │    │ 진행률 확인 │    │ Approve /   │
│ 태스크 분해 │    │ 에이전트    │    │ 에이전트    │    │ Reject      │
│             │    │ 자동 스폰   │    │ 활동 추적   │    │             │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
```

**`/tf-plan`** — 한 줄 설명으로 기획 시작 → Socratic Questions → PRD → 태스크 목록

**`/tf-start`** — 태스크 일괄 생성 + 에이전트 자동 스폰

**`/tf-status`** — 실시간 진행 상황 모니터링

**`/tf-review`** — 완료된 태스크 코드 리뷰 → 승인 또는 거절

이 네 가지 명령만 기억하시면 됩니다. 어떤 프로젝트든 이 흐름으로 진행돼요.

### 의존성 순서의 중요성 (2분)

화면: 의존성 그래프 — TASK-001 → 003, 004 → 005 → 006

이번 프로젝트에서 의존성 순서가 어떻게 작동했는지 다시 볼까요:

```
TASK-001 (백엔드 API)
  ├── TASK-002 (즐겨찾기 API)
  ├── TASK-003 (도시 검색 UI)
  └── TASK-004 (날씨 카드)
        └── TASK-005 (5일 예보 차트)
              └── TASK-006 (연동 테스트) ← TASK-003도 필요
```

이 순서가 자연스럽죠?

- 백엔드 API가 있어야 프론트엔드가 연동할 수 있고
- 날씨 카드가 있어야 그 위에 차트를 추가할 수 있고
- 모든 UI가 완성되어야 연동 테스트를 할 수 있다

마블로가 이 순서를 자동으로 관리했기 때문에, 에이전트가 엉뚱한 순서로 일하는 일이 없었습니다. **의존성 관리 = 프로젝트의 핵심**이에요.

### 규모를 키워봅시다 (3분)

화면: 날씨 대시보드 vs AI SaaS 비교 슬라이드

자, 이번 워밍업에서는:
- **6개 태스크**
- **2개 에이전트** (Backend, Frontend)
- **약 30분** 소요

이제 다음 모듈에서는 **진짜 프로젝트**를 합니다:
- **15-20개 태스크**
- **4-5개 에이전트** (Backend, Frontend, DevOps, Test 등)
- **약 4시간** 분량

규모가 확 커지죠? 하지만 걱정하지 마세요. **워크플로우는 완전히 동일합니다.**

`/tf-plan` → `/tf-start` → `/tf-status` → `/tf-review`

이 흐름을 방금 한 바퀴 돌려봤으니까, 이제 큰 프로젝트에서도 자신 있게 PM 역할을 할 수 있을 거예요.

프론트엔드와 백엔드가 왕복하면서 잘 맞물리는 거 보셨죠? 이 감각을 가지고 모듈 4로 넘어갑시다. **AI YouTube 인사이트 서비스**를 처음부터 끝까지 만들어볼 겁니다!

## 정리

모듈 3 전체 핵심 요약:

1. **4개 명령어**: `/tf-plan`, `/tf-start`, `/tf-status`, `/tf-review`
2. **의존성 관리**: 백엔드 → 프론트엔드 → 테스트 순서가 자동으로 지켜진다
3. **PM 역할**: 코딩 대신 기획, 관찰, 리뷰, 의사결정에 집중
4. **규모 확장**: 같은 워크플로우로 더 큰 프로젝트도 가능하다
5. **다음 모듈**: AI SaaS 빌드 — 15-20 태스크, 4-5 에이전트
