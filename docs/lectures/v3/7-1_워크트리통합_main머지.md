# 워크트리 통합 → main 머지

> 모듈 7 · 섹션 7-1 · 약 20분
> 관련: [[6-5_서비스LLM_vs_코딩에이전트모델]] | [[7-2_GCP_CloudRun_배포]]

---

## 이 강의에서 다루는 것

- **학습목표:** M5 스프린트에서 에이전트들이 **각자 워크트리**에 흩어놓은 P3(ReachWave) 작업을, **워크트리 탭에서 일괄 Rebase/Merge(squash)** 해 하나의 깨끗한 `main`으로 모은다. 머지 신호등을 읽고, 충돌은 리졸버로 풀고, **완료 이력(감사 추적)**으로 "누가 언제 무엇을 합쳤나"를 확인한다.
- **시연할 마블로 화면·기능:** **워크트리 탭(WorktreeTab)** — 워크트리 행·상태 pill·Rebase/Merge/Open/Delete·📜 완료 이력.
- **진행할 프로젝트 단계:** **P3 main 통합** — 흩어진 레인을 main 한 줄기로 합친다.
- **핵심 메시지:** "**배포의 시작은 깨끗한 main.**"

---

## 도입 — 배포 전, 코드는 아직 흩어져 있다 (3분)

모듈 6까지 P3 ReachWave를 완성했습니다. 그런데 한 가지 짚고 넘어갈 게 있어요. **그 코드는 아직 한 곳에 모여 있지 않습니다.**

> 화면: 슬라이드 — main 원 하나에서 가지 여러 개가 뻗어 나간 그림

M5 스프린트를 떠올려 보세요. backend-claude는 자기 워크트리에서 OAuth·LLM 분석·5톤 생성·결제를 짰고, frontend-codex는 다른 워크트리에서 대시보드를 짰고, 통합·테스트도 또 다른 워크트리에서 돌았죠([[4-3_에이전트별_워크트리격리]]). **각자 자기 방에서 일했기 때문에** 서로 안 엉켰지만, 그 결과가 아직 `main`에 다 들어온 건 아닙니다.

배포는 **`main` 브랜치 하나를 통째로** 클라우드에 올리는 일입니다. 그러니 배포의 첫 단추는 코드 작성이 아니라 **통합** — 흩어진 워크트리를 깨끗한 `main` 한 줄기로 모으는 것입니다. 이번 레슨에서 그걸 합니다.

---

## 본문

### 1. 워크트리 탭 — 무엇이 남아 있나 (4분)

> 화면: 워크트리 탭(WorktreeTab) — P3 워크트리 행 + 상태 pill + 액션 버튼

워크트리 탭을 엽니다. M5에서 만든 레인들이 **워크트리 행**으로 나열돼 있어요. 각 행에는 [[2-4_프로젝트연결_워크트리체크]]에서 배운 **신호등 pill**이 붙어 있습니다.

```
워크트리 탭 — P3 ReachWave
  agent/reachwave-backend     [TASK-1..8]   🟢 머지 가능    + 14 파일
  agent/reachwave-frontend    [TASK-9..13]  🟡 뒤처짐       + 9 파일
  agent/reachwave-integration [TASK-14]     🟢 머지 가능    + 3 파일
     각 행:  [ Rebase ]  [ Merge (squash) ]  [ Open ]  [ Delete ]
```

신호등이 곧 다음 행동입니다.

| pill              | 뜻                                | 할 일                               |
| ----------------- | --------------------------------- | ----------------------------------- |
| 🟢 머지 가능      | main 최신과 깔끔히 합쳐짐         | 바로 **Merge (squash)**             |
| 🟡 뒤처짐(behind) | 내가 일하는 사이 main이 앞서 나감 | 먼저 **Rebase** → 🟢 되면 머지      |
| ⚠️ stale          | 오래 방치된 워크트리              | Open으로 확인 후 Rebase 또는 Delete |
| 🔴 충돌           | 같은 파일을 다르게 고침           | **Resolve**(리졸버) 후 머지         |
| ⚪ 작업중         | 아직 에이전트가 작업 중           | 끝날 때까지 대기                    |

> 💡 합치기 **전에** 봐야 할 게 diff입니다. 행의 **Open**을 누르면 그 워크트리가 [[3-4_리뷰_워크트리머지_완료|코드 탭]]에서 열려 변경 사항이 초록(추가)/빨강(삭제)으로 보여요. P3는 M5에서 이미 리뷰를 거쳐 DONE까지 갔으니, 여기선 **통합 관점**(충돌·순서)만 확인하면 됩니다.

### 2. 일괄 Rebase → Merge (8분)

> 화면: 워크트리 탭 — Rebase 진행 → pill이 🟡→🟢 전환 → Merge(squash)

**(실습)** 순서대로 합쳐 봅시다. 핵심 원칙은 하나예요 — **🟡는 먼저 따라잡고(Rebase), 🟢가 되면 합친다(Merge).**

**① 의존성 없는 것부터, 또는 base가 되는 레인부터.**
ReachWave는 backend가 frontend의 API 계약 기반이었으니 backend를 먼저 정리하는 게 자연스럽습니다. `agent/reachwave-backend`가 🟢라면 바로 합칩니다.

```
agent/reachwave-backend  🟢 → [ Merge (squash) ]
  ✅ merged: agent/reachwave-backend → main (squash)
```

**Merge (squash)** 는 그 워크트리의 커밋 여러 개를 **하나로 압축**해 `main`에 깔끔히 넣습니다. 히스토리가 "기능 단위 한 줄"로 정리돼요.

**② backend가 들어가면서 main이 앞섰다 → frontend는 🟡로 바뀜.**
이제 `agent/reachwave-frontend`가 🟡 **뒤처짐**일 겁니다(방금 main이 backend만큼 앞으로 갔으니까). 먼저 **Rebase**:

```
agent/reachwave-frontend  🟡 → [ Rebase ]
  → main 최신을 끌어와 그 위에 frontend 변경을 다시 얹음
  → 🟡 뒤처짐 → 🟢 머지 가능
agent/reachwave-frontend  🟢 → [ Merge (squash) ]
  ✅ merged: agent/reachwave-frontend → main (squash)
```

**③ 마지막 통합 레인도 같은 흐름.**
`agent/reachwave-integration`도 필요하면 Rebase 후 Merge. 모든 행이 합쳐지면 워크트리 탭은 비고, `main`에 P3 전체가 한 줄기로 모입니다.

> ⚠️ **🔴 충돌이 떴다면?** 같은 파일을 두 레인이 다르게 고친 경우입니다. 행의 **Resolve**를 누르면 리졸버 에이전트가 양쪽 변경을 비교해 병합안을 만들고, 사람이 확인 후 적용합니다([[4-3_에이전트별_워크트리격리]]). P3는 M5에서 의존성 체인(백→프)으로 레인을 갈라 작업해 충돌이 드물지만, 떴을 때의 절차는 알아두세요. **충돌은 막는 게 아니라 푸는 것** — 워크트리 격리 덕에 main은 충돌 중에도 안전합니다.

### 3. 완료 이력 — 팀 작업의 감사 추적 (3분)

> 화면: 워크트리 탭 — 📜 완료 이력 패널

머지를 마쳤으면 **📜 완료 이력**을 봅니다. 합쳐진 모든 머지가 한 줄씩 기록돼 있어요.

```
📜 완료 이력
  🙂 사람  2026-06-22 14:05  agent/reachwave-backend     → main  (squash, a1b2c3d)
  🙂 사람  2026-06-22 14:08  agent/reachwave-frontend    → main  (squash, e4f5g6h)
  🙂 사람  2026-06-22 14:10  agent/reachwave-integration → main  (squash, i7j8k9l)
```

각 줄에 **누가(🙂 사람 / 🤖 에이전트)·언제·어느 브랜치를·어떤 SHA로** 합쳤는지가 남습니다. 머지는 끝까지 **사람이 쥔 결정**이므로([[3-4_리뷰_워크트리머지_완료]] 칸반 거버넌스) 배지는 🙂 **사람**이에요.

이게 **팀 작업의 감사 추적**입니다. 에이전트 여러 명이 동시에 짜도, 무엇이 언제 어떻게 main에 들어왔는지 한눈에 추적되죠. 배포 후 문제가 생기면 "어느 머지부터 이상한가"를 이 이력으로 거슬러 올라갑니다.

> 💡 머지 직후 `main`이 진짜 멀쩡한지 한 번 더 확인하고 싶으면, 오케스트레이터에 "main에서 테스트 전체 돌려서 통과 여부만 알려줘"라고 시키면 됩니다. **배포 전 마지막 그린 체크**예요.

## 정리 (1분)

1. **배포의 시작은 통합.** 에이전트들이 각자 워크트리에 흩어놓은 P3를 `main` 한 줄기로 모으는 게 첫 단추다.
2. **신호등이 곧 행동.** 🟢는 바로 Merge(squash), 🟡는 Rebase 후 Merge, 🔴는 Resolve 후 Merge.
3. **base 레인부터 순서대로.** backend → frontend → integration. 하나 합칠 때마다 나머지가 🟡로 바뀌면 다시 Rebase.
4. **완료 이력 = 감사 추적.** 누가 언제 어느 SHA로 합쳤나가 남고, 머지 권한은 끝까지 사람이 쥔다.

`main`이 깨끗해졌습니다. 다음 섹션에서는 이 `main`을 **에이전트 주도로 GCP Cloud Run에 배포**합니다. 나는 확인만 해요.
