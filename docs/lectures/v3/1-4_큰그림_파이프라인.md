## 이 강의에서 다루는 것

- **학습목표:** 자연어 한 줄이 태스크·에이전트·코드 변경으로 이어지는 전체 파이프라인을 그린다.
- **시연할 마블로 화면·기능:** (개념도 → 실제 화면 짧게) 오케 요청 → 보드 카드 → 레인 진행 → 워크트리 diff → REVIEW → 머지. 상태머신 한 장.
- **진행할 프로젝트 단계:** — (모듈 3에서 직접 실행할 흐름의 예고편)

## 도입 — 자연어 한 줄의 여정 (3분)

지금까지 탭을 하나하나 봤습니다. 보드, 레인, 코드, 워크트리…
"각각은 알겠는데, 이것들이 어떻게 이어지지?"

이번 섹션이 그 답입니다.

마블로 안에서 무슨 일이 순서대로 벌어지는지 — 그 **파이프라인**을 그려보겠습니다.

이건 예고편입니다. 실제로 손으로 돌려보는 건 모듈 3이에요.

## 본문

### 파이프라인 — 5단계 (10분)

> 화면: 개념도 — 오케 → 보드 → 레인 → 워크트리 → REVIEW → 머지

여러분이 오케스트레이터에 이렇게 입력했다고 합시다:

```
localStorage로 동작하는 할 일 웹앱 만들어줘
```

이 한 줄이 다섯 단계를 거칩니다.

**① 오케스트레이터 — 요청을 태스크로 분해**

> 화면: 하단 오케 PTY
> 오케스트레이터(팀리더)가 요청을 받아 소크라테스식 질문으로 다듬고,
> PRD를 만든 뒤 **태스크 여러 개로 분해**합니다. 역할과 의존성도 자동으로 붙죠.

**② 보드 — 카드로 등장**

> 화면: 보드 탭 — TODO 컬럼에 카드 등장
> 분해된 태스크가 보드의 TODO 컬럼에 카드로 나타납니다.
> 추상적이던 요청이 **추적 가능한 카드**가 되는 순간입니다.

**③ 레인 — 에이전트가 진행**

> 화면: 레인 탭 — 에이전트가 카드 claim 후 작업
> 에이전트가 카드를 claim하면 카드가 CLAIMED → IN_PROGRESS로 움직이고,
> 레인에서 그 에이전트가 코드를 짜기 시작합니다. 터미널을 attach해 들여다볼 수 있죠.

**④ 워크트리 — 격리된 곳에서 diff**

> 화면: 워크트리 탭 / 코드 탭 diff
> 에이전트는 **자기만의 워크트리**에서 작업하므로 다른 작업과 충돌하지 않습니다.
> 변경 사항은 코드 탭에서 diff로 확인합니다.

**⑤ REVIEW → 머지**

> 화면: 보드 REVIEW 컬럼 → 워크트리 머지 → DONE
> 작업이 끝나면 카드가 REVIEW로 올라옵니다.
> PM인 여러분이 diff를 검토하고, 워크트리에서 Rebase/Merge(squash)를 누르면
> 카드가 DONE으로 가고 변경이 main에 반영됩니다. **결과물 완성.**

> 한 줄 요약: **오케 → 보드 → 레인 → 워크트리 → REVIEW → 머지.**
> 여러분이 직접 한 건 처음 한 줄과 마지막 머지 승인뿐입니다.

### 그 밑에서 도는 상태 머신 (8분)

> 화면: 슬라이드 1장 — 상태 전환 다이어그램

카드가 "자동으로 움직인다"고 했죠? 그 움직임을 강제하는 게 **상태 머신**입니다.
태스크에는 상태가 있고, 아무 데로나 점프할 수 없습니다.

```
TODO ──→ CLAIMED ──→ IN_PROGRESS ──→ REVIEW ──→ DONE
              │            │   │          │
              └─→ FAILED   │   │          └─→ TODO (반려)
                   │       │   └─→ BLOCKED
                   └─ 재시도 │       │
                            └─→ FAILED └─→ IN_PROGRESS (재개)
```

| 상태        | 의미                             |
| ----------- | -------------------------------- |
| TODO        | 아직 아무도 안 건드림            |
| CLAIMED     | 에이전트가 "내가 하겠다" 선언    |
| IN_PROGRESS | 실제 작업 중                     |
| REVIEW      | 작업 완료, PM 리뷰 대기          |
| DONE        | 리뷰 통과, 완료 (되돌릴 수 없음) |
| BLOCKED     | 외부 요인으로 중단               |
| FAILED      | 실패 (재시도 가능)               |

핵심은 두 가지입니다:

- **유효한 전환만 허용됩니다.** TODO에서 바로 DONE으로 점프? 안 됩니다.
  반드시 `CLAIMED → IN_PROGRESS → REVIEW → DONE` 순서를 거쳐야 해요.
- **DONE은 끝입니다.** 한 번 완료되면 더는 전환되지 않습니다.

그리고 `REVIEW → TODO`(반려)가 있죠. PM이 리뷰에서 거절하면 카드가 처음으로 돌아가
다시 작업됩니다. **게이트는 사람이 쥡니다.**

> JIRA는 사람이 카드를 아무 데나 옮길 수 있지만(유연하지만 혼란),
> 마블로는 규칙으로 강제합니다(에이전트가 예측 가능하게 행동).
> 상태 전환을 강제하는 실제 코드(`VALID_TRANSITIONS`, `canTransition()`)는 **부록 A**에서 다룹니다.

### "오늘 배운 모든 기능 = 이 파이프라인의 일부" (4분)

> 화면: 개념도 위에 9탭을 매핑

이제 처음 본 9개 탭이 이 파이프라인 위 어디에 있는지 보이시죠?

| 파이프라인 단계 | 관련 탭         |
| --------------- | --------------- |
| 요청 입력       | 하단 오케 PTY   |
| 태스크/카드     | 보드            |
| 에이전트 진행   | 레인 · 에이전트 |
| 코드 변경       | 코드(diff)      |
| 격리·머지       | 워크트리        |
| 비용 추적       | 사용량          |
| 설치·설정       | 하네스 · 설정   |
| 막힐 때         | 가이드          |

탭들이 따로 노는 게 아니라, **하나의 흐름을 위한 도구들**이었던 겁니다.

## 정리 (1분)

1. 파이프라인: **오케 → 보드 → 레인 → 워크트리 → REVIEW → 머지.**
2. 그 밑에 **상태 머신**이 카드의 이동을 강제한다 (유효 전환만, DONE은 끝, 반려는 REVIEW→TODO).
3. 9개 탭은 모두 **이 한 줄 파이프라인의 일부**다.

여기까지가 모듈 1 — "왜 팀인가"부터 "전체 그림"까지였습니다.
다음 모듈(M2)에서는 이 파이프라인을 실제로 돌리기 위한 **셋업**을 합니다 —
하네스로 설치하고, CLI를 인증하고, 프로젝트를 연결하죠.
그리고 모듈 3에서, 방금 그린 이 파이프라인을 **직접 손으로** 한 바퀴 돌립니다.
