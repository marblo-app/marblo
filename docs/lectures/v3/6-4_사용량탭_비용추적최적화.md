# 사용량 탭 — 토큰·비용 추적과 최적화

> 모듈 6 · 섹션 6-4 · 약 30분
> 관련: [[6-3_에이전트_재활용_멀티윈도우]] | [[6-5_서비스LLM_vs_코딩에이전트모델]]

---

## 이 강의에서 다루는 것

- **학습목표:** 마블로 **사용량 탭(UsagePage)**에서 토큰을 모델별·일자별·에이전트별로 읽고, rate-limit을 점검한 뒤 **실측에 근거한 절감 전략**을 세운다.
- **시연할 마블로 화면·기능:** 사용량 탭 — 최근 7일 요약 · 모델별/에이전트별 · 일자별 추이 · rate-limit 패널.
- **진행할 프로젝트 단계:** **P3 비용 점검** — 콜드메일 SaaS 스프린트가 실제로 얼마를 썼는지 확인.
- **핵심 메시지:** "비용은 **측정되는 순간 통제된다.**"

---

## 도입 — 추정이 아니라 실측 (3분)

예전 강의에서는 비용을 **슬라이드 시뮬레이션**으로 다뤘습니다. "이 작업은 대략 80K 토큰이니 얼마쯤" 하는 식이었죠. 문제는 — 그게 **추정**이라는 겁니다. 실제 스프린트는 재시도·맥락 누적·캐시 때문에 추정과 다르게 흘러갑니다.

> 화면: 사용량 탭(UsagePage) 첫 화면 — "사용량" 헤더

마블로에는 **사용량 탭**이 있습니다. 슬라이드가 아니라 **여러분의 진짜 스프린트가 쓴 진짜 숫자**예요.

> 헤더 아래 한 줄: _"모델·에이전트·일자별 토큰 사용량. 라이브(에이전트 문서) + 히스토리(BigQuery) 합산."_

이 한 줄에 구조가 다 들어 있습니다 — **라이브(지금 도는 에이전트)** + **히스토리(BigQuery에 쌓인 과거)**를 합산해서 보여줍니다. 추정 단가표를 외우는 시대는 끝났어요. 이번 섹션은 **이 탭을 읽고 그걸로 절감하는 법**입니다.

---

## 본문

### 1. 최근 7일 요약 — 한눈에 (5분)

> 화면: 사용량 탭 상단 — 요약 카드 3장 + 모델별 막대

탭을 열면 맨 위에 **최근 7일 총 토큰량** 요약이 뜹니다.

```
[ 총 토큰 ]   [ Input / Output ]   [ Cache (R/W) ]
```

- **총 토큰** — 7일간 플릿 전체가 쓴 토큰
- **Input / Output** — 입력(읽기) vs 출력(생성)의 비율. 출력이 비싸므로 이 비율이 비용 감각의 핵심
- **Cache (R/W)** — 캐시 읽기/쓰기. 같은 맥락을 재사용하면 캐시가 비용을 크게 깎습니다

그 아래 **모델별 막대**가 색으로 갈립니다.

```
🟣 Claude   🟢 Codex   🟠 Antigravity   (· 기타)
```

여기서 P3를 복기합니다 — "설계는 Claude(보라)가, 구현·테스트는 Codex(초록)가 많이 썼겠지?" 하는 가설을 **막대 길이로 즉시 검증**할 수 있어요.

> 💡 출력 토큰이 입력보다 과하게 많다면, 에이전트가 **불필요하게 장황한 결과**를 내고 있을 수 있습니다. 반대로 캐시 비율이 높다면 재활용(6-3)이 잘 돌고 있다는 신호예요.

### 2. 모델별 / 에이전트별 — 누가 얼마를 (5분)

> 화면: 사용량 탭 — "모델별 / 에이전트별" 섹션

요약 아래 **모델별 / 에이전트별** 분해가 있습니다. 같은 토큰이라도 **어느 모델·어느 에이전트**가 썼는지가 비용 구조의 핵심이에요.

- **모델별** — 6-1의 비용효율(Claude는 비싸고, Codex·Antigravity는 상대적으로 저렴)이 여기서 금액 차이로 드러납니다.
- **에이전트별** — 특정 에이전트가 토큰을 과하게 먹고 있으면, 그 에이전트의 태스크가 너무 크거나 재시도가 많다는 뜻. 쪼개거나 재배정할 신호입니다.

P3 점검 예: "콜드메일 분석 에이전트(Claude)가 5톤 생성까지 다 떠안아서 토큰이 몰렸네 → 5톤 양산은 더 싼 모델로 옮기자" — 이런 판단이 **숫자에서** 나옵니다.

### 3. 일자별 추이 — 언제 튀었나 (4분)

> 화면: 사용량 탭 — "일자별 추이 (모델별)" 막대 그래프

**일자별 추이**는 날짜축 위에 모델별 토큰을 쌓아 보여줍니다. (마우스를 올리면 그 날의 모델별 토큰이 툴팁으로 떠요.)

여기서 보는 건 **패턴**입니다.

- 특정 날 막대가 유독 길다 → 그날 무슨 일이 있었나(대규모 리팩토링? 반복 재시도?)
- 며칠째 우상향 → 스프린트가 과열되고 있다는 조기 경보
- 빈 날(gap) → 작업이 없던 날 (정상)

추세를 보면 **비용이 새기 전에** 손쓸 수 있습니다. "어제 갑자기 3배 튀었네?"를 다음 청구서가 아니라 **그날** 알아채는 거예요.

### 4. rate-limit 점검 — 구독 한도 (4분)

> 화면: 사용량 탭 하단 — RateLimitPanel

토큰 비용과 **별개로** 봐야 할 게 있습니다 — **구독 plan의 사용량 한도(rate limit)**입니다. Codex(ChatGPT Pro)나 Claude 구독은 토큰당 과금이 아니라 **plan 한도** 안에서 돌아가니까요.

사용량 탭 하단의 **rate-limit 패널**은 각 에이전트가 어느 provider에 묶이는지를 잡아 한도 상태를 보여줍니다.

```
cli-claude-code  → claude  (Claude 구독 한도)
cli-codex        → gpt     (Codex / ChatGPT Pro plan 한도)
```

한도에 가까워지면 — 스프린트 도중 에이전트가 갑자기 느려지거나 멈추는 일을 **미리** 예측할 수 있습니다. "오후에 Codex 한도가 찰 것 같으니, 무거운 양산 작업은 오전에 몰자" 같은 운영 판단이 가능해져요.

> ⚠️ **토큰 비용 ≠ rate limit.** 토큰 비용은 "돈을 얼마 썼나"(주로 Claude API), rate limit은 "구독 한도를 얼마 썼나"(Codex plan). 둘을 같이 봐야 비용·가용성을 모두 통제합니다.

### 5. 측정에서 절감으로 — 실전 전략 (6분)

> 화면: 슬라이드 — "측정 → 전략" 루프

이제 본론입니다. 숫자를 **봤으면 줄여야죠.** 사용량 탭이 알려준 사실을 절감으로 바꾸는 전략입니다.

**전략 1 — 작업 유형별 배치 (6-2의 실천)**

dispatch 스코어링이 자동으로 하지만, 사용량 탭으로 **결과를 검증**합니다.

```
설계·복잡 로직   → Claude     (비싸도 품질 — 꼭 필요한 곳에만)
UI·테스트·양산   → Codex      (빠르고 plan 안에서 처리)
자율 멀티스텝     → Antigravity (저비용 + 자율 실행)
```

사용량 탭에서 **Claude 막대가 단순 작업까지 먹고 있다면**, 그건 비싼 모델을 잘못 쓰고 있다는 증거 — 재배정 대상입니다.

**전략 2 — 2단계 파이프라인**

가장 실용적인 절감 패턴입니다.

```
1단계: 저비용 모델(Codex/Antigravity)로 초안 생성  (싸게, 빠르게)
2단계: Claude가 리뷰·수정만                         (품질, 적은 토큰)
```

초안은 싸게 양산하고, **비싼 모델은 마무리에만** 투입합니다. 전체 토큰의 상당 부분을 저비용 쪽으로 옮기면서 최종 품질은 지키는 거예요.

**전략 3 — 캐시·재활용 활용 (6-3 연결)**

요약 카드의 **Cache(R/W)**가 보여주듯, 같은 맥락을 재사용하면 비용이 깎입니다.

```
"이전에 만든 UserController.ts와 같은 패턴으로 ProductController.ts를 만들어줘"
```

비슷한 태스크를 **같은 idle 에이전트로 재활용**(reuse)하면 컨텍스트가 이어져 캐시 효율이 오르고, 더 적은 토큰으로 더 정확한 결과가 나옵니다.

> 💡 **측정 → 전략 → 재측정** 루프로 돌리세요. 전략을 바꾼 뒤 다음 스프린트의 사용량 탭을 다시 보면, 그 전략이 진짜 효과가 있었는지 **숫자로** 확인됩니다. 추정이 아니라 실측이니까요.

## 정리 (2분)

1. **사용량 탭 = 실측.** 라이브(도는 에이전트) + 히스토리(BigQuery)를 합산해 모델별·에이전트별·일자별 토큰을 보여준다. 슬라이드 추정의 시대는 끝났다.
2. **네 화면을 읽어라.** 7일 요약(총/IO/캐시) → 모델별·에이전트별 → 일자별 추이 → rate-limit.
3. **토큰 비용 ≠ rate limit.** 돈(주로 Claude API)과 구독 한도(Codex plan)를 따로 본다.
4. **측정에서 절감으로.** 작업 유형별 배치 검증 + 2단계 파이프라인(저비용 초안 → Claude 리뷰) + 캐시·재활용. 바꾼 뒤 **다시 측정**해 효과를 확인한다.

다음 섹션에서는 헷갈리기 쉬운 한 가지를 못 박습니다 — **내가 만드는 서비스의 LLM**과 **나를 돕는 코딩 에이전트의 모델**은 다른 축이라는 것.
