## 도입 (3분)

지난 섹션에서 `/tf-plan`으로 ReachWave PRD를 만들고 22개 태스크를 분해했습니다. 각 태스크에 추천 모델까지 매핑되어 있죠 (`gpt`/`claude`/`gemini`).

화면: 마블로 워크스페이스 — 빈 칸반 보드 + 오케스트레이터 터미널

이제 이 기획을 **실제 시스템에 등록**하고, **이종에이전트 팀을 투입**하는 단계입니다.

워밍업(모듈 3)에선 `/tf-start` 하나로 plan+execute를 일체로 했지만, 큰 프로젝트는 다릅니다:

```
/tf-plan (4-1, 완료) → /tf-create-tasks → /tf-spawn-agents → /tf-status
      ↑                       ↑                    ↑
   PRD + 분해              Firestore 일괄        역할별 이종 에이전트
                          태스크 등록          자동 스폰 + 모델 추천
```

분리해서 가는 이유: **22 태스크를 에이전트에 한 번에 맡기기 전에 한 번 더 검토**할 시간을 갖기 위함입니다. 큰 프로젝트일수록 시작 전 1분 점검이 5시간 라이브 빌딩의 안정성을 좌우합니다.

### 마지막 점검 (3분)

화면: 칸반 카드 클릭 — 상세 패널 (의존성·역할·추천 모델·예상 난이도)

에이전트 투입 전에 마지막으로 확인합니다:

```
✓ 22개가 적절한가? (너무 많으면 4-5개 묶기)
✓ 의존성이 합리적인가? (병목 안 만드는지)
✓ 모델 추천이 OK한가? (직접 보낼 모델 명시 원하면 수정)
✓ 토스 결제(010-011)는 Sprint 1 백엔드에 묶일 거 — OK?
```

수정이 필요하면:

```bash
# 태스크 추가
/tf-add "에러 페이지 + 404 라우트" --role frontend --depends-on TASK-013

# 모델 강제 지정
/tf-update TASK-009 --model gemini   # 이미 자동 추천이지만 명시 락
```

오타·누락 없으면 다음으로.

### `/tf-spawn-agents` — 이종 에이전트 4-5명 동시 스폰 (7분)

**(실습)**:

```bash
/tf-spawn-agents
```

화면: 에이전트 스폰 로그 + 오른쪽 터미널 패널에 에이전트 탭이 줄줄이 생성

```
🤖 Spawning heterogeneous agent team for ReachWave...

dispatch-scoring 자동 추천 분석 (청구항 9 [식 1] 가중합):
  - gpt 우위: TASK-001/003/006/008/012/019/020/021 (8개) — simple-fix · github · test
  - claude 우위: TASK-002/004/005/007/010/011/013-018 (11개) — architecture · multi-file · design
  - gemini 우위: TASK-009/022 (2개) — large-context · analysis

Agent Team (4 agents):
  [backend-codex]    → 8 backend tasks (model: gpt)
  [backend-claude]   → 4 backend tasks (model: claude)  ← 결제·LLM·A/B 같은 architecture 필요
  [frontend-claude]  → 6 frontend tasks (model: claude)
  [security-gemini]  → 1 test 태스크 (model: gemini)  ← Sprint 3에서 합류

DevOps tasks (TASK-019)는 idle agent 풀 사용으로 첫 GPT 에이전트가 picking.

Starting work (의존성 없는 태스크 자동 claim):
  backend-codex     : claiming TASK-001 (Postgres + Alembic)
  backend-codex     : claiming TASK-019 (Docker Compose, parallel)
  backend-claude    : claiming TASK-002 (Email + Google OAuth)
  frontend-claude   : IDLE (Sprint 2 대기 — 002 OAuth 완료 후 시작)
  security-gemini   : IDLE (Sprint 3 대기)
```

여기서 마블로의 핵심 차별점이 드러납니다:

**① 모델별 강점에 따라 같은 역할도 분리됩니다.**
백엔드 태스크 12개 중 8개는 Codex(simple-fix/test에 +25)가, 4개는 Claude(architecture/multi-file에 +25)가 맡습니다. 한 모델로 다 미는 게 아닙니다.

**② 의존성 풀린 태스크만 자동 claim 합니다.**
backend-codex는 TASK-001/019 동시에 잡고, backend-claude는 TASK-002로. 의존성 있는 것들은 잠시 대기.

**③ 에이전트가 idle이면 자원 회수 안 됩니다.**
frontend-claude와 security-gemini는 idle이지만 컨텍스트는 살아 있어 Sprint 2/3 시작 시점에 그대로 합류.

화면: 터미널 패널 — 4개 에이전트 탭 (backend-codex/backend-claude/frontend-claude/security-gemini), 앞 두 개에 로그 스트리밍

## 정리

이번 섹션에서 한 일:

1. **`/tf-create-tasks`** — 22 태스크 Firestore 일괄 등록 (모델 추천 메타 포함)
2. **마지막 점검** — 의존성·모델·스코프 최종 확인
3. **`/tf-spawn-agents`** — **이종 에이전트 4명** 자동 스폰 (Codex/Claude×2/Gemini)
4. **dispatch-scoring 자동 추천** — 같은 backend 역할도 태스크 성격에 따라 GPT/Claude로 분리
5. **`/tf-status`** — 실시간 진행 + ETA

핵심 학습 포인트:

> **태스크 수가 비슷해도 강점이 다른 모델을 골고루 쓰면 시간·비용 모두 이득.**
> 8개를 Codex(저렴 + 빠름)에, 11개를 Claude(설계 강점)에, 2개를 Gemini(맥락 크게)에. 한 모델 만 사용 시 비용 3-5배.

다음 섹션부터는 본격 라이브 빌딩 — Sprint 1 백엔드. backend-codex와 backend-claude가 어떻게 다르게 일하는지 직접 보겠습니다.
