# 해시 이메일로 구글 광고 타겟팅 — 구조가 잡혔나 (2026-09-07)

티켓 `B9bu0vBvyhYvydM8ZaTE` · 역할 backend · 판정 시각 2026-09-07

> **사장님 질문**: "구글광고 타겟마케팅 하려면 결국 우리측에서 hashed email 정보를 가지고 있어야 하지 않나 수집해서? GA4측 수집과 텔레메트리측 수집을 봐야할 것 같은데 구조가 잡혔나?"

> **한 줄 답**: **해시 구조는 있다. 광고에 쓰기엔 아직 아니다.** 막는 것은 코드가 아니라 (a) **동의 범위**(우리 동의는 "이메일 발송"이지 "구글에 제공"이 아니다)와 (b) **모수**(현재 199명, 구글 최소선 근처)다. 기술(해시 정규화)은 오히려 예상보다 문제가 작다 — 확인 결과 구글 공식 사양과 지금 코드가 일치한다.

---

## 1. 이미 있는 것

`v3/functions/src/marketingContacts.ts`에 마케팅 컨택트 SoT(Source of Truth)가 이미 구현돼 있다.

- **컬렉션**: `marketing_contacts`, docId = `sha256(normalizeMarketingEmail(email))`
- **평문 이메일 미저장**: AES-256-GCM 암호문(`emailEnc`, 키 미설정 시 null)과 sha256 해시(`normalizedEmailHash` = docId)만 Firestore에 있다
- **BigQuery 미러엔 암호문조차 없다**(`contactToBqRow`) — `email_hash`·`email_domain`·상태·세그먼트만 나간다
- **동의 상태 4종**: `granted`(발송 가능) / `pending`(재동의 대상 풀, 발송 불가) / `revoked`(철회, 절대 안 되살림) / `unknown`(증거 없음)
- **동의의 유일한 정상 근거는 `explicit_opt_in`**(마케팅 전용 체크박스) — waitlist의 `agreed=true`(활동/인용 동의)는 근거로 안 쓴다. 코드 주석이 `COMPLIANCE-AUDIT.md` D2 판정을 직접 인용하며 이 경계를 명시적으로 지킨다
- **unsubscribe 토큰은 HMAC 파생**(stateless, 평문 토큰 무저장)
- **발송 게이트 단일소스**: `isEmailable()` — `unsubscribed` 또는 `consent≠granted`면 무조건 거부

## 2. 막는 것 — 기술 아니고 동의·모수다

### 2-1. 기술: 해시 정규화 — ★예상보다 문제가 작다

구글 공식 문서(`support.google.com/google-ads/answer/7476159`, 2026-09-07 직접 확인, "Formatting guidelines for uploading hashed data")의 이메일 규칙 전문:

> "Lowercase all characters" / "Remove any extra spaces before and after, or in between the email address" / "Include a domain name for all email addresses"

우리 `normalizeMarketingEmail`:

```ts
export function normalizeMarketingEmail(email: string): string {
  return email.trim().toLowerCase();
}
```

→ **trim + lowercase, 구글 공식 사양과 일치한다.** 해싱 알고리즘도 양쪽 다 SHA256, 솔트 없음(구글은 무솔트 SHA256을 요구·자체 수행하기도 한다) — `sha256Hex(normalized)`도 일치.

★**확인 못 한 것**: 흔히 알려진 "Gmail/Googlemail 주소는 `.`(점)을 지운다"는 규칙을, 위 공식 페이지와 연결된 "Customer Match basics"·"How Google uses Customer Match data" 페이지 어디에서도 지금 찾지 못했다. 이 규칙이 (a) 실제로 존재하지 않게 됐거나 (b) 다른 페이지에 있거나 (c) 업로드 단계가 아니라 매칭 단계에서 구글 내부적으로만 적용되는 것일 수 있다 — 어느 쪽인지 이 조사로는 확정하지 못했다. **"정규화가 안 맞아 매칭률이 0에 가깝다"는 우려는 지금 확인된 공식 문서 기준으로는 근거가 약하다.** 다만 이건 "괜찮다"는 단정이 아니라 "확인 못 했다"이니, 실제로 리스트를 올리기 전에 구글이 제공하는 매칭률 리포트로 실측 검증이 필요하다.

### 2-2. 동의: ★여기가 진짜 병목이다

세 가지 서로 다른 동의를 섞으면 안 된다:

| 동의 종류                          | 지금 있나                                           | 근거                                                                                                                                                                                                                                                                                                                      |
| ---------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 마케팅 이메일 수신동의             | ✅ 있음(`marketing_contacts.emailMarketingConsent`) | 체크박스 라벨: **"마케팅·광고성 정보 수신 동의"**, 힌트: "신규 기능·혜택·이벤트 소식을 **이메일로** 받아봅니다"(`messages/ko.json:797-798`)                                                                                                                                                                               |
| 제3자(구글)에 개인정보 제공 동의   | ❌ 없음                                             | 배포된 처리방침 5절 "개인정보의 제3자 제공": **"회사는 정보주체의 별도 동의가 없는 한 개인정보를 제3자에게 제공하지 않습니다"**(예외: 사전 동의 / 법령·수사기관 요구). 6절 "개인정보 처리 위탁" 목록(Firebase·Vercel·Cloudflare·Toss/Stripe·Resend)에 **구글 광고(Customer Match)는 없다**                                |

★그런데 **취지의 충돌**은 있다: 저 문장이 표방하는 "특정 개인을 되짚지 않는다"는 정신과, Customer Match(정확히 그 개인을 다른 플랫폼에서 다시 찾아 광고를 보여주는 행위)는 방향이 반대다. 법적으로 별개 데이터라 문장이 깨지는 건 아니지만, 발표·홍보에서 "우리는 개인을 되짚지 않는다"고 말한 직후 "그런데 광고는 개인을 되짚어서 탑니다"라고 하면 사용자 신뢰 관점에서 이상하게 들릴 수 있다 — 이건 코드·법률 문제가 아니라 **커뮤니케이션 판단**이라 사장님 몫으로 남긴다.

**결론**: `granted` 상태(=이메일 수신동의)가 있다고 해서 그 사람의 해시를 구글에 업로드할 법적 근거가 되지 않는다. Customer Match를 쓰려면 최소한 다음 중 하나가 필요하다:

- (a) 처리방침 6절에 "Google LLC (Google Ads Customer Match) — 제공 항목: 이메일 해시값, 목적: 광고 타겟팅"을 신설하고, 마케팅 동의 체크박스와 **별도로** 이 조항에 대한 동의를 받거나
- (b) 마케팅 동의 체크박스 자체를 "이메일 발송 + 제3자(구글) 광고 타겟팅 제공"까지 포괄하도록 문구를 다시 쓰고 재동의를 받거나(기존 `granted` 199명 전원 재동의 필요 가능성)

★어느 쪽이든 코드가 아니라 **방침·문구 개정 + 재동의 캠페인**이 선행돼야 한다.

### 2-3. 모수 — 2026-09-07 실측

구글 공식 최소 기준(`support.google.com/google-ads/answer/7476159`, `.../6334160`, 2026-09-07 확인): **"리스트가 효과적으로 채워지려면 최근 30일 내 활성 사용자 100명 이상"**, 그리고 유지 조건은 **"540일 내 추가·갱신된 멤버 100명 이상"**.

→ 199는 이 100명 최소선을 **숫자상으로는** 넘는다. 다만:

- 구글 매칭률은 100%가 아니다(업계 통상 40~70%대로 알려져 있고, 구글이 정확한 수치를 공개하지 않는다) — 199명 업로드가 곧 199명 매칭을 뜻하지 않는다
- "최근 30일 활성"이 기준이라 **오래된 동의자가 섞여 있으면 유효 모수는 199보다 작을 수 있다**(가입 시점 분포는 이번 조사에서 안 봤다 — 확인 못 함)
- 즉 **"넘겼다"가 아니라 "여유가 없다"**에 가깝다. 재동의 캠페인으로 모수를 더 키우는 게 안전하다.

## 5. 결합 테이블 — 있다, 그러나 광고용이 아니다 (후속, 티켓 QTJlFNjmCg5RLIGvqpkX)

사장님 후속 질문: _"우리 기기아이디 기준으로 묶은 다음 사람으로 구분하는 방식으로 매핑했을 거야. 우리 결합테이블이 있어. 다만 텔레메트리에 쌓이는 해시드 이메일 등을 마케팅 타겟팅으로 쓸 수 있냐. 혹은 GA4의 비식별자에 붙인 hashed ID를?"_

★**말씀이 맞다 — 결합 테이블은 실재한다.** 다만 그게 왜 구글 광고에 못 쓰이는지를 알고리즘 수준으로 정리한다.

### 5-1. "텔레메트리에 쌓이는 해시드 이메일"이라는 표현부터 정정한다

★★**텔레메트리에는 이메일 해시가 없다.** 이 문서 §1의 `marketing_contacts.normalizedEmailHash`(이메일을 해시한 것)와 이름이 비슷해서 헷갈리기 딱 좋지만, 텔레메트리(익명·계정 축)에 쌓이는 값은 **전부 다른 원본**을 해시한 것이다:

- `install` 종류 — 익명 설치 UUID를 해시
- `ga` 종류 — GA4 client_id를 해시
- `user`/`teamMember` 종류 — Firebase Auth **uid**를 해시(이메일이 아니다)

`v3/functions/src/analyticsPseudonym.ts:141-157`(`AnalyticsIdKind` 유니온)에 이메일을 원본으로 삼는 kind는 없다. **텔레메트리 전체를 뒤져도 "이메일을 해시한 값"은 안 나온다** — 그런 값은 `marketing_contacts` 밖에 없다.

### 5-2. 결합 테이블의 정체

`marblo_identity.analytics_user_install`(BQ, `personAxis.ts:210`의 `TABLE_USER_INSTALL`) — `(user_key, install_key)` 쌍 하나만 담는 표. 이게 사장님이 말씀하신 "기기아이디 기준으로 묶은 다음 사람으로 구분"하는 그 다리다.

- `user_key` = `pseudonymizeAnalyticsId("user", uid, salt)`
- `install_key` = `pseudonymizeAnalyticsId("install", installUuid, salt)`
- **`PERSON_AXIS_EFFECTIVE_FROM=2026-04-01` 게이트가 열려 있을 때만 채워진다(지금 열려 있음, 과거분 포함)**
- `analyticsPseudonym.ts:36-42` 주석이 명시: 익명축과 계정축을 잇는 자리는 **이 표 하나뿐**이고, 그 좁은 예외를 의도적으로 만든 것이다(2026-08-21 개정, PR #1081)

### 5-3. 왜 이 표의 가명이 구글에 못 쓰이는가 — 세 가지가 전부 다르다

| 항목     | `analytics_user_install`의 가명(`user_key`/`install_key`) | 구글 Customer Match가 요구하는 것 |
| -------- | --------------------------------------------------------- | --------------------------------- |
| 입력값   | Firebase uid 또는 설치 UUID(**이메일 아님**)              | 정규화된 **이메일 주소**          |
| 알고리즘 | **HMAC**-SHA256(비밀 솔트로 키드)                         | 순수 **SHA256**(솔트 없음)        |
| 길이     | hex 64자를 **24자로 절단** + 종류 접두사(`us_`/`in_` 등)  | hex **64자 전체**, 접두사 없음    |

★**세 축이 전부 다르므로 이건 "동의를 더 받으면 되는" 문제가 아니라 방침 이전에 수학적으로 다른 값이다.** 같은 사람이라도 `us_<24자>`는 SHA256(이메일)과 절대 같아질 수 없다 — HMAC은 원본이 같아도 SHA256과 다른 함수족이고, 24자 절단은 원래 64자 값의 정보를 이미 버렸다.

### 5-4. 결합 테이블이 실제로 하는 일 — 내부 분석 전용

`analytics_user_install`이 존재하는 이유는 광고가 아니라 **내부 분석**이다: "이 계정(uid)이 로그인 전 익명 설치 상태에서부터 지금까지 얼마나 썼는가"를 인입 경로(익명 설치 시점)와 이어보는 것 — `personAxis.ts:1043-1048` 주석이 이 용도를 그대로 확인해준다. 이게 게이트(`PERSON_AXIS_EFFECTIVE_FROM`)가 지키는 목적이고, 이 표를 만든 티켓들의 의도다.

★**이 티켓이 새로 제안하는 것은 없다.** 이미 있는 이 다리를 넓히거나, 여기에 이메일 축을 얹는 설계는 하지 않는다 — 그러면 익명·계정·마케팅 세 축이 한곳에서 만나고, 그게 정확히 `analyticsPseudonym.ts`가 막으려는 사고다.

### 5-5. GA4 쪽 두 번째 질문 — "GA4 비식별자에 붙인 hashed ID"

명령이 실제로 돌았는지부터 확인했다(오늘 앞선 조사에서 글롭 오류로 빈 출력을 "0건"으로 오독한 전례가 있어서):

```
$ ls marblo-web/src/lib/gtag.ts marblo-web/src/components/GoogleAnalytics.tsx
(둘 다 존재 확인, exit 0)
$ grep -n "user_id\|user_properties\|setUserId\|set_user" <두 파일>
(exit code 1 = 매칭 없음으로 정상 종료, 글롭 실패 아님)
$ grep -rn "user_id\|user_properties\|setUserId" marblo-web/src --include="*.ts" --include="*.tsx"
(exit code 1 = 저장소 전체에서도 매칭 없음)
```

`GoogleAnalytics.tsx`의 실제 `gtag('config', ...)` 호출도 `{ page_path: ... }`만 넘긴다 — `user_id` 파라미터 없음(직접 코드 확인).

**답: 지금 GA4는 순수 익명 `client_id`만 받는다. "GA4 비식별자에 붙인 hashed ID"는 아직 없다.** 붙이려면:

- GA4 `user_id` 파라미터(로그인 사용자를 GA4 세션에 연결 — 이것 자체도 PII는 아니고 우리 uid 등을 쓸 수 있다)를 `gtag('config', ..., { user_id })`에 추가하고
- 그 위에 **Enhanced Conversions**(구글이 자체적으로 이메일 해시를 요구하는 별도 기능, Customer Match와는 다른 기능)를 별도로 붙여야 한다 — 이것도 §2-2의 동의 범위 문제가 그대로 적용된다

### 5-6. #1518과 이어지는 결론

### 6-2. 신규 동의 vs 재동의 — 모수 영향(숫자)

| 경로                                                                                   | 무슨 일이 일어나나                                                                                               | 모수 영향                                                                                                                                                                                                   |
| -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **신규 동의만**(기존 `granted`는 그대로 두고, 앞으로 가입하는 사람에게만 새 항목 노출) | 기존 199명은 이 목적에 **못 쓴다**(새 동의 항목에 동의한 적이 없으므로). 광고용 리스트는 **0명에서 다시 쌓인다** | 즉시 사용 가능 모수 = 0. 100명 도달까지 시간이 걸린다                                                                                                                                                       |
