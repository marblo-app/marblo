### 2.1 방침 문면 — ③ 을 막는 자리 셋

배포된 처리방침(`v3/src/components/legal/privacyContent.tsx`)에서 그대로 인용한다:

1. **비식별 1차 지표 항목(:162)**: _"이용 목적: 서비스 품질 분석과 함께, 이 비식별 데이터에서 파생된 특징(모델·소요시간·성공 여부 등)을 모델 라우팅 … 품질 개선에 이용합니다 — **프롬프트·응답 원문은 여기에 포함되지 않습니다.**"_
2. **사용량·비용 기록 항목(:167)**: _"… 연결한 결과는 통계 분석에만 쓰이고, 특정 개인을 알아보거나 특정 계정이 무엇을 했는지 되짚는 데는 쓰지 않습니다. **코드·프롬프트·응답 원문은 여기에도 포함되지 않습니다.**"_
3. **수집하지 않는 것(:187)**: _"코드 내용, BYOK 키 …, 사용자 작성 텍스트, 파일 내용, 비밀번호 — 비식별 1차 지표와 Sentry 경로에서는 **어떤 경우에도 수집하지 않습니다.**"_

원문이 존재하는 유일한 경로는 **학습데이터 기여(선택·원문, :170-172)** 이고, 그 항목은 _"자체 모델 학습 목적으로 별도 보안 저장소에 보관 … 제3자에게 제공·판매하지 않습니다"_ 라고 못박았다. **조직 관리자에게 보여주는 것은 "자체 모델 학습" 이 아니고, 관리자는 그 직원에게 제3자다.** 동의의 목적 범위 밖이라 B2B 계약으로도 열 수 없다 — 열려면 **직원 개인마다 새 목적의 별도 동의**가 필요하고, 그건 "회사가 시켜서 동의한 것" 이 되어 자발성이 성립하지 않는다. 그래서 ③ 은 방침 개정 항목이 아니라 **짓지 않는 것 목록(§9)** 에 둔다.

### 2.2 ③ 대신 줄 수 있는 것 — "무엇을 안 보는지 말하는 화면"

`enterprise-org-dashboard-screen-design-2026-08-24.md` §7.3 의 판정을 조직 층에 그대로 올린다: 감사 탭 하단의 `withheld` 10줄(툴 인자 원문·지시문·툴 결과·활동 본문·개인 툴 호출·에스컬레이션·미션 목표 문장·저장소 경로·금액·원시 신원)을 **접지 않고 상시 노출**한다. 기업 고객이 자기 직원에게 이 화면을 설명할 때 필요한 것이 정확히 이 목록이다. 실행 로그 원문은 **그 사람의 데스크톱에만** 있고(Electron 로컬), 거기서 본인이 보는 것은 이 설계 밖이다.

### 2.3 "로그" 낱말의 화면 표기

세 뜻을 한 낱말로 두면 영업이 ③ 을 약속한다. 화면·문서에서 낱말을 고정한다: ① **"사용량"**, ② **"활동 기록(원장)"**, ③ 은 낱말 자체를 쓰지 않는다. `teamUsage.ts` 가 "사용량 환산 비용(추정)" 을 고정한 것과 같은 규율.

★`orgId` 는 Firestore 자동 id 라 URL 로 조직 존재를 열거할 수 없다(추측 불가). 개인 조직 `personal_<uid>` 는 **uid 가 URL 에 실리므로** `/org/personal_…` 는 만들지 않는다 — 개인 조직은 `/org/me` 별칭 하나로만 열고 서버가 `personalOrgId(uid)` 로 푼다.

- 미들웨어 파일은 `src/proxy.ts` 이고 `export function proxy`(middleware 아님). matcher `"/((?!api|_next|_vercel|.*\\..*).*)"` 가 `/org/...` 를 이미 덮으므로 **proxy 변경 0** — 로케일 협상·www 301·`x-pathname` 헤더가 그대로 적용된다.
- `params` 는 Promise(`team/[projectId]/page.tsx` 가 이미 `await params`). 새 라우트도 같은 모양.
- 내부 링크는 전부 `localeHref(locale, "/org/…")` 경유(`i18n/routing.ts` 규약, 손으로 `/ko/` 붙이면 301 홉).
- SEO: `/org/*` 는 `sitemap.ts` 에 넣지 않고 `noindex` 메타. `robots.ts` 주석대로 disallow 는 하지 않는다(로그인 게이트가 200 이 아니므로 크롤 자체가 무의미).
- **로그인 게이트는 화면이 판정하지 않는다** — `enterprise-org-dashboard-screen-design` §5.1 규약. 미로그인은 `/auth/login?redirect=/org/<id>`(`sanitizeRedirect` 가 상대경로만 허용).

### 3.3 로그인 후 어디로 — `#1205` §5.8 을 그대로 쓴다

```
1) 마지막으로 본 조직(localStorage)  — 단 서버가 "아직 멤버인가" 를 확인. 아니면 무시
2) 없으면: 비개인 조직이 정확히 하나면 그것
3) 여럿이면: /org 조직 선택 화면(개인 조직 포함)
4) 비개인 조직이 없으면: 개인 조직(/org/me)
```

- **"조직 없음" 상태는 존재하지 않는다** — 모든 uid 에 `personal_<uid>` 가 파생값으로 있다(백필 불필요). 그래서 조직 층은 **첫날부터 비어 있지 않다**: 개인 조직 = 내 프로젝트들 = 오늘의 `/team` 화면과 같은 내용(§7).
- 여러 조직 소속자는 **자동 착지하지 않는다**(2번의 "정확히 하나" 조건). 대행사가 고객 A 화면을 열어 둔 채 B 와 회의하는 사고 방지.
- 조직 전환은 헤더의 스위처(드롭다운)로, 전환 시 localStorage 갱신. 스위처 목록 = `org_members` 에서 uid 로 도출(멤버가 아닌 조직은 목록에 없다 = 존재 비노출).

## 4. 3단 드릴다운 — 데이터 모양

### 4.1 층과 각 층에서 보이는 것

```
L0 조직 (organizations/{orgId})
 │  집계: 결합 프로젝트 전체 합(사용량·비용·활동 카운트) · 프로젝트별 행 · 일별
 │  보는 사람: org_owner / org_admin (§6)   ← 총계 불변식
 └ L1 프로젝트 = 팀 (projects/{projectId}, OrgProjectBinding 으로 결합)
     │  집계: 오늘의 팀 탭 그대로 — byMember · byModel · byActorKind · byDay + 감사 탭
     │  보는 사람: 프로젝트 owner/admin (팀장)
     └ L2 사용자 (memberKey = tm_ 가명)
         │  집계: 그 사람의 model × actor_kind(worker/orchestrator) × day · 티켓 완료/실패 건수
         │  보는 사람: 프로젝트 owner/admin, 본인(self)
         └ L3 오케 · 에이전트 · 모델 (행, 층이 아니다)
              오케: actor_kind=orchestrator — 지금 "미수집"(0 아님)
              에이전트: distinct_agents 카운트 + 역할(role) 분해 — 에이전트 id 개체는 안 보인다(§4.4)
              모델: model 컬럼 그대로
```

★L3 은 드릴다운 층이 아니라 **L2 표의 열**이다. "사용자 아래 오케·에이전트·모델" 은 사람 한 명의 표에 세 열이 있다는 뜻이고, 그 아래로 더 내려가면 ③ 실행 로그가 되므로 여기서 끝난다.

### 4.2 ★조직 롤업은 새 뷰가 아니라 **기존 콜러블을 감싸는 것**

`v_team_usage_daily` 의 grain 이 `day × project_id × account_uid × model × actor_kind` 다. 조직 합은 **`project_id ∈ 조직 결합 집합`** 으로 같은 뷰를 읽으면 나온다. 즉:

```
getOrgUsageSummary({ orgId, days, refresh })
  1. context.auth.uid 로 org 역할 판정 (org_members/{orgId}_{uid})        ← Admin SDK, 룰 밖. 직접 본다
  2. OrgProjectBinding 에서 창 구간의 결합 프로젝트 집합 S 를 resolveOrgIdAt() 로 도출
     (시점별 결합 — 분기에 프로젝트가 바뀌어도 조직 연속성 유지, #1204 §1.1)
  3. 불변식 검사: visible(u) ⊇ S 인가 (org_admin/owner 는 정의상 전수, org_member 는 자기 프로젝트 집합)
     ⊉ 이면 totals 를 봉투에 싣지 않는다(restricted) — 0 으로 접지 않는다
  4. 기존 buildTeamUsageDailyQuery 를 @projectIds = S 로 실행 (capProjectScope 25 → 조직은 상한 상향 필요, §8 Phase 2)
  5. 봉투: teamUsage 계약 + byProject[] (프로젝트별 행) — 나머지 필드 이름·상태 5종·노트 코드 전부 계승
```

| 필요한가               | 판정                                                                                                                                                                                                                                                                                                         |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 새 BQ 뷰               | **불필요.** 조직↔프로젝트 결합은 Firestore(원장 밖 추가전용 표)에 있고 Node 에서 집합으로 푼다. BQ 에 `org_id` 컬럼을 넣지 않는다 — 넣으면 정정이 소급 UPDATE 가 되어 "소급은 저장이 아니라 조회로" 규약이 깨진다                                                                                            |
| 새 콜러블              | **필요.** `getTeamUsageSummary` 에 `orgId` 인자를 얹는 대신 별도 콜러블 — 권한 판정 축이 다르고(org 역할 vs 프로젝트 역할) 봉투에 `byProject` 가 추가되며, 축 가드 소스 스캔(`team-usage-axis-guard.test.ts`)을 그대로 상속한다                                                                              |
| 감사(원장)의 조직 롤업 | **카운트만.** org_admin 은 프로젝트 **내용**을 못 보므로(§6) 조직 화면의 감사 영역은 프로젝트별 `tasksDone/tasksFailed/에이전트 워크로드` **요약 숫자**이고, 피드는 프로젝트 역할이 있는 프로젝트에서만 `/org/<id>/projects/<pid>` 로 내려가 본다. 새 콜러블 없이 `getTeamProjectAudit` 을 프로젝트별로 호출 |

### 4.3 L2 사용자 드릴다운 — 뷰는 되고 콜러블만 손본다

현재 콜러블의 `aggregateTeamUsage()`(`teamUsage.ts:1083~`)는 `byMember` 와 `byModel`·`byActorKind` 를 **독립된 Map** 으로 접는다. 멤버×모델 교차는 뷰에 이미 있으므로 **`byMember[].byModel[]`·`byMember[].byActorKind[]` 를 봉투에 추가**하면 된다(BQ 변경 0, 계약 추가만). 상태 5종·`hasRows`·`rows_zero` 노트는 멤버 행에서도 그대로.

★오케 열은 멤버 행에서도 **`미수집`** 이다 — `orchestratorAxis.state === "not_collected"` 를 멤버 행마다 반복하지 말고 표 머리에 한 번, 셀은 `—`(대시) + 툴팁.

### 4.4 에이전트 "개체" 축은 열지 않는다

`cost_logs.agentId` 로 에이전트별 행을 낼 수는 있다. 안 내는 이유: (a) `agentId` 는 원시 id 라 가명화가 또 필요하고 (b) 에이전트 = 사람이 띄운 프로세스라 **에이전트별 행 = 그 사람의 분(分) 단위 작업 단위**가 되어 감사 탭이 뺀 "개인 행동 로그" 와 같은 것이 된다(설계 §12.3). 대신 **역할(role: backend/frontend/…)** 분해를 준다 — `task_outcomes.role` 은 익명 축이라 지금은 못 붙이고, `cost_logs` 에는 role 이 없다. → §8 Phase 3 에서 `cost_logs` 에 `role` 을 forward-only 로 더하는 것이 선행(작은 배선). 그 전까지 에이전트 열은 `distinct_agents` 카운트 + `미수집(역할)`.

**★쓸 만해지는 시점 — 두 개의 숫자**:

> **T₀ = 2번이 배포된 날.** 그 이전 1,797행은 영원히 익명이다(백필 안 함, `#1320` 규약). 화면은 `first_stamped_at` 을 데이터에서 읽어 "YYYY-MM-DD 이후" 라벨을 붙인다(env 값을 그리지 않는다 — 배포가 밀리면 화면이 거짓말한다).
>
> **N = 사람당 판정(success IS NOT NULL) 35건.** 성공률 p≈0.94 에서 95% 신뢰구간 폭 ±8%p 가 되는 최소 표본(n = 1.96²·p(1−p)/0.08² ≈ 34). ±5%p 면 **85건**, 모델별로 갈라 보려면 **모델마다** 그만큼.

이걸 오늘 실측 속도에 대면:

| 사용자 유형                                   | 판정 속도(실측) | 사람당 35건   | 사람당 85건 | 모델 3개 × 35건 |
| --------------------------------------------- | --------------- | ------------- | ----------- | --------------- |
| 내부 개발 설치(713행/28일 ≈ 21건/일)          | 21/일           | **T₀ + 2일**  | T₀ + 4일    | T₀ + 5일        |
| 외부 실사용 4명의 최대치(19행/8일 ≈ 2.4건/일) | 2.4/일          | **T₀ + 15일** | T₀ + 36일   | T₀ + 45일       |
| 링크된 사람 B(2 task/2일)                     | 1/일            | T₀ + 35일     | T₀ + 85일   | T₀ + 105일      |

★그리고 그 전에 **사람이 링크돼 있어야** 한다 — 지금 `analytics_user_install` 에 사람 4, 각인된 사람 2. **실사용 팀이 0** 이므로 이 표의 "외부" 행은 **팀이 생긴 뒤**의 시계다. 정직한 문장은: _"각인 배포 후 내부 도그푸드는 이틀 안에 숫자가 나온다. 외부 팀은 팀이 생기고 사람이 링크된 날로부터 2~5주다. 그 전까지 이 탭의 기본 모습은 `적재 전(사람 축 각인 YYYY-MM-DD 이후)` 이고, 그건 버그가 아니다."_

★**표본 35 미만이면 퍼센트를 그리지 않는다** — `counting-unit-first` 규약. `n/35` 로 그리고 "표본 부족" 라벨. 2명·4명을 %로 접지 않는다.

## 6. 권한표 — 누가 무엇까지, 각 칸에 방침 고지가 필요한가

### 6.1 표

### 6.2 ★방침 개정은 **한 번**에 — 세 열람자를 한 항목으로

지금 방침 :167 항목은 목적을 _"구독·요금 정산과 회원님 본인의 사용량 확인"_ 으로만 적었다. Phase 0 에서 이 항목에 **한 문단**을 더한다(문안은 법무·오케 판단, 여기는 범위만):

> 팀 요금제에서는 회원님이 속한 **프로젝트의 관리자**와 그 프로젝트가 결합된 **조직의 관리자**가 회원님의 사용량(모델별 토큰·사용량 환산 비용(추정)·완료/실패 티켓 수)을 **가명 표시명으로** 열람할 수 있습니다. 코드·프롬프트·응답 원문은 포함되지 않습니다.

이렇게 한 번에 적는 이유: L0(조직)과 L1(프로젝트)을 따로 개정하면 발효일이 둘이 되고 `TEAM_USAGE_EFFECTIVE_FROM` 이 둘이 되어 화면이 두 사유를 그린다. **범위를 한 번에 고지하되 기능은 단계별로 연다** — 고지가 넓고 기능이 좁은 것은 문제가 없고, 반대는 문제다.

각인(`task_outcomes.userKey`)은 :162 항목이 이미 "이 기록(비식별 1차 지표)에 가명 구분값을 함께 적습니다" 라고 고지하므로 **추가 고지 없이** `EVENTS_PERSON_STAMP_FROM` 게이트만 통과하면 된다. 단 **화면에서 팀장이 그것을 본다**는 건 위 문단의 "완료/실패" 에 "task 성공률" 을 한 낱말 더해 덮는다.

- **0 이 먼저**: 코드가 0 이고, 이것 없이는 1~3 이 전부 `disabled` 문장 위에 지어진다. 그리고 §6.2 대로 고지를 한 번에 넓게 적어 두면 2 가 별도 개정 없이 열린다.
- **1 이 2 보다 먼저**: 결합표가 없으면 롤업 키가 없다. 그리고 `#1204` 가 경고한 대로 **규약이 늦으면 그 사이 쌓인 귀속을 못 고친다** — 결합표는 추가전용이라 늦게 만들어도 정정 가능하지만, `restricted` 셀 종류가 없는 채 조직 화면을 먼저 지으면 `0` 으로 접는 경로가 생긴다(`#1205` §7).
- **3 은 0 만 있으면 된다**: 팀 탭에서 바로 값이 나오므로 1·2 와 병렬 가능. 한 사람이 1→2, 다른 사람이 3 을 해도 충돌 없음.
- **4 는 마지막**: 가장 새 데이터이고 T₀ 이후만 유효하므로 **빨리 배포할수록 좋지만**, 화면 자리(3)가 있어야 값을 보여줄 곳이 있다. 각인 6줄(2번)만 먼저 떼어 배포해 T₀ 를 앞당기는 것은 **권장** — Phase 4a(각인만, 화면 없음)로 쪼갠다.

## 11. 열린 질문(사장님·오케 판단)

1. **§6.2 방침 문안** — "프로젝트 관리자와 조직 관리자가 가명 표시명으로 열람" 의 실제 문구와 인앱 배너 방식(1회 배너 vs 재프롬프트 — `privacyContent.tsx` 머리 주석의 #797~#809 saga 는 배너 쪽).
2. **Phase 4a 를 Phase 0 앞에 배포하나** — 각인은 방침상 이미 덮이므로 가능. T₀ 를 앞당기는 이득 vs "쓸 곳 없는 데이터" 의 규율(`empty-query-first`). 내 권고는 **앞당긴다**(6줄, 되돌리기 쉬움, T₀ 는 빠를수록 좋다).
3. **`/org/me` 별칭** — 개인 조직 URL 에 uid 노출을 피하기 위한 안. 대안은 개인 조직을 URL 로 열지 않고 `/team` 을 그대로 두는 것(그러면 "조직 URL" 은 비개인 조직에만).
4. **표본 임계 35** — ±8%p 기준. 사장님이 ±5%p 를 원하시면 85. 임계는 화면 상수 하나다.
