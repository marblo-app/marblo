# SLM 라우터 1페이지 요약

## 한줄권고

**보류.** SLM/모델 라우터는 엔터프라이즈 확장 카드로는 유효하지만, 지금은 제품 코어에 넣기보다 **LLM 호출 추상화 + 사용량/성과 데이터 축적**을 먼저 해야 한다.

## 핵심근거

- **전략적 가치는 있음**: 기밀 프로젝트를 사내 vLLM/SLM으로 보내고, 일반 작업은 외부 모델로 보내는 정책 기반 라우팅은 엔터프라이즈 보안/비용 메시지와 맞다.
- **현재 제품의 당면 병목은 아님**: 마블로의 코딩 에이전트 배정은 이미 Claude/Codex/Antigravity 강점, 비용효율, 부하를 기준으로 추천하는 흐름이 있다. SLM 라우터는 이 위에 얹는 추가 복잡도다.
- **데이터가 아직 부족함**: 모델별 성공률, 태스크별 비용, 토큰 사용량, task-cost 연결키가 충분히 쌓이지 않았다. 라우터를 넣어도 “무엇을 SLM에 보내야 하는가”를 방어하기 어렵다.
- **구현 범위가 크다**: 정책 엔진, LLM 프록시/게이트웨이, 감사 로그, 가격/성능 메타데이터, fallback, 보안 마스킹까지 들어간다. 단순 모델 선택 UI가 아니다.
- **초기 서비스 LLM 원칙과 충돌 가능**: 고객이 만드는 서비스 내부 LLM은 저비용 단일 모델 + 1줄 교체 추상화가 더 단순하다. 라우팅은 엔터프라이즈/고호출량 단계에서 의미가 커진다.

## 투자규모/난이도

- **투자규모**: 중대형. MVP도 최소 2-4주급, 엔터프라이즈급은 별도 백엔드/Gateway 트랙 필요.
- **난이도**: 높음. 모델 품질 문제가 아니라 보안, 감사, 비용 추적, 장애 fallback, 정책 운영 문제다.

## 블로커

- 태스크 결과와 모델 비용을 연결하는 데이터 스키마/로그 부족.
- 모델 가격/성능 메타데이터 최신화 체계 없음.
- LLM 호출 프록시/Gateway와 정책 엔진 미구현.
- 외부/사내 모델 라우팅 시 프롬프트/소스코드 유출 방지 정책 필요.
- 라우팅 실패 시 fallback, 재시도, 감사 로그 기준 미정.

## 결정 포인트

- **지금 SLM 라우터를 제품 로드맵에 넣을지, 엔터프라이즈 백로그로 둘지** 결정.
- SLM의 목적을 **비용 절감**, **보안/온프렘**, **속도**, **벤더 독립성** 중 무엇으로 잡을지 결정.
- 우선순위를 **데이터 축적/비용 추적 고도화**로 둘지, **Gateway PoC**로 바로 갈지 결정.
- 사내 vLLM/SLM을 실제 운영할 예산과 책임 주체를 정할지 결정.

## 제안

지금은 **GO 아님**. 먼저 LLM 호출부를 한 곳으로 모으고, 모델별 task outcome/cost/latency 데이터를 쌓는다. 데이터가 300건 이상 쌓인 뒤 “SLM으로 보내도 되는 태스크”를 룰 기반으로 PoC 하는 순서가 맞다.
