사장님 지시는 "4명 전부"였고 표본 1을 피하려는 의도도 옳다. 그런데 나머지 2명은

### A·D 도 opt-in 은 아니다 — 어떻게 정당화하는가

A·D 는 철회는 안 했지만 `pending`(명시적 동의 없음)이다. "Pro 3개월 무료"는
영리목적 광고성 정보로 읽힐 여지가 있다. 그래서 발송하려면 아래 셋을 **전부** 건다.

1. **본문의 무게중심을 의견 청취에 둔다.** 제목·본문 첫 질문이 "무엇 때문에
   멈추셨나요"이고, Pro 는 감사 표시로 한 문장만 붙는다(3절 초안 그대로).
   거래관계(무료 grant 이용) 기반 CS 문의의 성격이 본체다.
2. **수신거부 경로를 반드시 붙인다.** 기존 `marketingEmailDelivery()` 재사용 —
   `List-Unsubscribe` + `List-Unsubscribe-Post: One-Click` 헤더와 본문 푸터
   (RFC 8058 / CAN-SPAM). 초안 HTML 은 `</body>` 를 가지고 있어
   `withUnsubscribeFooter()` 가 그대로 삽입된다(테스트로 고정).
3. **1회 발송, 리마인더 없음.** 답이 없으면 그걸로 끝낸다.

> ★이건 법률 자문이 아니다. 위 3개는 리스크를 줄이는 조치지 면제가 아니다.
> "그래도 보내지 말자"는 판단은 사장님 몫이고, 그 경우 A 한 명에게만 보내거나
> 캠페인 자체를 접는 선택지도 정상이다.

### 표본이 2명뿐인 문제 — 대안

사장님 의도(표본 1 회피)는 이 제약 안에서도 살릴 수 있다. 셋 중 택일:

- **(가) A + D 2명에게만 발송** — 지금 초안. 안전하고 즉시 가능. **권장.**
- **(나) B·C 에게는 Pro 제안 없이 "한 줄만 여쭙습니다"만** — 광고성 요소를 빼면
  성격이 달라지지만, 철회 의사를 표시한 사람에게 재접촉하는 것 자체가 신뢰를
  깎는다. **권하지 않는다.** (C 는 사장님이 직접 아시는 분이면 개인 채널이 낫다.)
- **(다) 모수를 넓힌다** — 진짜 큰 구멍은 "써보고 떠난 1명"이 아니라 **grant 를
  받고 토큰을 한 번도 안 쓴 29명**이다. 광고 집행 근거로는 이쪽 표본이 더 크고
  더 아프다. 다만 그건 다른 질문("왜 시작조차 안 하셨나요")이고 기존
  `sendFounderFollowupEmails`(미가입 팔로업)와 세그먼트가 겹치는지 봐야 한다.
  **별도 티켓 제안.**

## 4. ★그랜트가 실제로 되는가 — 검증 결과 (코드 근거)

결론부터: **기존 `founder_grant` 경로를 그대로 재사용할 수는 없다.** 두 가지 벽이 있고,
둘 다 우회 절차가 확인됐다. **코드 수정은 필요 없다.**

### 벽 ①: 모든 부여 경로가 `founder_feedback` 문서를 전제한다

`index.ts` 의 Pro 부여 진입점은 셋뿐이고 전부 설문 제출물이 있어야 돈다.

| 진입점                             | 전제                                                          | 우리 상황         |
| ---------------------------------- | ------------------------------------------------------------- | ----------------- |
| `reviewFounderFeedback`            | `founder_feedback` 문서 필요 (`getFounderFeedbackBySelector`) | 한 줄 답장엔 없음 |
| `markFounderInterviewed`           | 같은 문서 + `interviewRequested === true`                     | 없음              |
| `handleTgProGrant` (텔레그램 버튼) | 같은 문서                                                     | 없음              |

**uid 만으로 Pro 를 부여하는 어드민 콜러블은 존재하지 않는다.** (`grep`으로
`onCall` export 전수 확인.) 실제 부여자는 전부 내부 함수
`grantFounderProTotalInternal(userId, months, reason, grantStartedAt)` 다.

### 벽 ②: "3개월"은 **더하기가 아니라 채우기**다

`upsertProSubscription` 은 트랜잭션 안에서

```
periodEnd = max(기존 currentPeriodEnd, grantStartedAt + months)
```

를 쓴다. `grantStartedAt = now` 로 부여하면 실제로 늘어나는 기간이 이렇게 된다.

| 코드 | 기존 만료일 | `now` 앵커 실효 | **만료일 앵커 실효** | 부여 후 만료일 |
| ---- | ----------- | --------------: | -------------------: | -------------- |
| A    | 2026-08-29  |            86일 |             **92일** | 2026-11-29     |
| B    | 2026-12-24  |         **0일** |                 90일 | 2027-03-24     |
| C    | 2026-09-07  |            78일 |                 91일 | 2026-12-07     |
| D    | 2026-11-15  |         **9일** |                 92일 | 2027-02-15     |

`now` 앵커로는 A 조차 86일밖에 못 받고, D 는 9일, B 는 0일이다. **"Pro 3개월"이라
써놓고 9일을 주는 건 안 하느니 못하다** — 사장님이 짚으신 그 위험이 실제로 여기 있다.

**해법은 코드 수정이 아니라 앵커 선택이다.** `grantStartedAt` 을 `max(기존 만료일, now)`
로 주면 `target = 기존만료일 + 3개월` 이 되어 `max` 를 그대로 통과한다 → 온전한 3개월.
이 계산은 `churnOutreach.ts` 의 `projectGrant()` 로 떼어내 테스트했다
(`npm run test:churn-outreach`, 27/27 통과). 위 표는 그 함수의 출력이다.

### 벽 ③: C 에게 부여하면 결제가 깨진다 (제외 사유의 기술적 근거)

`isFounderGrantSubscription()` 은 `founderGrant === true` 만 보고 무료 grant 로 판정한다.
C 는 실결제자인데 과거 `founder_backfill`(07-17) 잔재로 이 플래그가 남아 있다
→ `isLivePaidSubscription()` 이 **false** → 보호 가드가 안 걸린다
→ `upsertProSubscription` 이 `paymentProvider` 를 `portone` → `founder_grant` 로 **덮어쓴다**.
`index.ts` 주석이 정확히 이 사고("결제 정체성 stomp")를 경고하고 있는데, 플래그
잔재 때문에 가드가 우회되는 경로다. **C 제외는 취향이 아니라 안전 조치다.**

### ✅ 확정된 수동 부여 절차 (답장 1건당, 운영자 실행)

전제: 답장이 실제로 왔고, 사장님/오케가 지급을 승인했다.

1. **대상 구독 문서 확인** — `subscriptions/{uid}` 를 읽어
   `currentPeriodEnd` 와 결제 흔적(`portoneBillingKey`/`tossBillingKey`)을 본다.
   **결제 흔적이 있으면 여기서 중단하고 오케에 보고한다**(벽 ③).
2. **앵커 계산** — `anchor = max(currentPeriodEnd, now)`.
   `projectGrant()` 로 `addedDays > 0` 을 확인한다. 0이면 지급 방식을 다시 정한다.
3. **`founder_feedback` 문서 1건 생성** — 필수 필드:
   `{ userId: <uid>, email: <email>, createdAt: <anchor>, source: "churn_email_reply", replySummary: <답장 요약> }`.
   ★`createdAt` 이 곧 `grantStartedAt` 으로 쓰인다 — 여기에 **anchor** 를 넣는 것이
   2절 계산을 실현하는 지점이다.
4. **어드민 콜러블 호출** —
   `reviewFounderFeedback({ feedbackId, rubricScore: {specificity:0, usageEvidence:0, insightQuality:0, actionability:0, icpFit:0}, overrideGrantPro: true })`
   - `parseFounderRubricScore` 가 `rubricScore` 를 **필수**로 요구하므로 0점이라도 반드시 넘겨야 한다(없으면 `invalid-argument`).
   - 루브릭 총점과 무관하게 `overrideGrantPro === true` 면 부여된다
     (`grantPro = total >= 10 || overrideGrantPro === true`).
   - 결과로 `subscriptions/{uid}.currentPeriodEnd` 가 갱신되고
     `founders/{email}.status = "pro_granted"` 가 기록된다.
5. **검증** — 응답의 `proExpiresAt` 이 2절 표의 "부여 후 만료일"과 일치하는지 확인.
   불일치면 즉시 오케 보고(부여 스킵됐을 가능성 = `skippedReason: "live_paid"`).

**호출 주체**: `requireAdmin(context)` 는 `ADMIN_UID` 단일 대조다 → **사장님 계정으로만**
호출된다. 에이전트는 이 단계를 대신 실행할 수 없다. 오케가 사장님께 요청하는 구조.

> 대안으로 `grantFounderProByUid` 같은 어드민 콜러블을 새로 만들 수도 있지만,
> 이번 대상이 최대 2명이라 신규 부여 경로를 늘릴 이유가 없다. 답장이 5건을
> 넘어가면 그때 만드는 게 맞다.

## 5. 답장은 어디로 가고 누가 보는가

**받는 곳**: `Reply-To: team@marblo.app` (env 고정, 이미 그렇게 나간다).
사장님 개인 메일함이 아니라 팀 주소다 — 여기까지는 코드가 보장한다.

**문제**: 거기서 멈추면 보드에 안 남는다. 그래서 답장 1건당 아래를 **의무**로 한다.

| 단계 | 무엇을                                                                      | 어디에                                | 누가        |
| ---- | --------------------------------------------------------------------------- | ------------------------------------- | ----------- |
| 1    | 답장 수신                                                                   | `team@marblo.app` 수신함              | (자동)      |
| 2    | **이탈 사유 티켓 생성** — 원문이 아니라 **요약**만. 이메일·이름·회사명 제거 | Marblo 보드 (`[리텐션] 이탈 사유 #N`) | 오케        |
| 3    | 지급 승인                                                                   | 티켓 activity                         | 사장님      |
| 4    | 그랜트 부여 (4절 절차)                                                      | `founder_feedback` + `subscriptions`  | 사장님 계정 |
| 5    | 부여 결과 기록 — `addedDays`, 부여 후 만료일                                | 같은 티켓 activity                    | 오케        |
| 6    | 사유를 제품 티켓으로 승격                                                   | 보드                                  | 오케        |

- **3건 이상 모이면 사유를 분류해 한 장으로 묶는다** — 광고 집행 판단의 입력이
  되려면 개별 답장이 아니라 패턴이어야 한다.
- **PII 규칙**: 티켓·activity·PR 어디에도 이메일·uid·이름을 쓰지 않는다. 대상은
  uid 해시 앞 8자리로만 지칭한다. 이 문서와 코드가 그 규칙을 지키고 있다.
- 답장 원문이 필요하면 수신함에 남아 있고, 보드에는 요약만 간다.

## 7. 파생 발견 — P1 매출 누수 (이 티켓 범위 밖, 별도 티켓 필요)

C 의 구독 문서에 과거 `founder_backfill`(07-17) 잔재로 `founderGrant: true` 가 남아 있다.
`billing.ts` 의 `selectDueForCharge` 첫 줄이

```ts
if (sub.founderGrant === true) return false;
```

다. 즉 **유효한 `portoneBillingKey` 와 monthly 주기가 있는데도 재청구 크론이 이 사람을
영구히 건너뛴다.** 08-07 첫 결제는 체크아웃 경로로 통과했지만, 09-07 만료 이후
자동 갱신은 영원히 오지 않는다. 결과는 둘 중 하나이고 둘 다 사고다.

- 만료 처리가 안 걸리면 → **무료로 계속 사용**(매출 누수)
- 만료 처리가 걸리면 → **돈 낸 고객이 조용히 Pro 를 잃는다**(신뢰 사고)

같은 패턴("결제자에게 남은 grant 플래그")이 다른 계정에도 있는지 전수 점검이 필요하다.
`founderGrant == true` 34건 중 결제 흔적을 함께 가진 문서를 세면 즉시 나온다.
**오케 판단 요청** — 이 티켓에서 고치지 않았다.
