## 0. 한 문단 요약

완료 후크는 **DONE 전이**에 건다(머지 시점이 아니다). 전진 대상은 **암묵 미션(라벨)만**이다
— 명시 미션은 지휘자가 이미 운전하고 있고, 암묵 미션은 **아무도 안 밀고 있다**. 신호에는
남은 목록이 아니라 **"지금 집을 수 있는 것 / 아직 막힌 것 / 이미 도는 것 / 사장님 승인이 필요한 것"**
을 갈라 담는다. 세 개의 한도(연속 스폰·동시 슬롯·진행 없음)가 전진 로직 **아래**에 깔리고,
어느 한도에 걸려 멈추든 **사유가 세 곳에 남는다**.

## 1. 이건 #1412 과 다른 축이다

| 축      | #1412 (오늘 착지)                                 | 이 티켓                      |
| ------- | ------------------------------------------------- | ---------------------------- |

| 고친 것 | 조용한 정지에 사유를 달고, 죽은 클레임을 되살린다 | 전진 동력을 만든다           |
| 없으면  | 멈춘 걸 아무도 모른다                             | 멈추지 않아도 스스로 안 간다 |

#1412 가 전부 들어갔어도 루프는 여전히 스스로 안 돈다. **아무도 "다음"을 밀어주지 않기 때문이다.**

### 오늘 DONE 시점에 실제로 일어나는 일

`update_task_status` 의 DONE 분기는 이미 세 가지를 한다:

1. `resolveDependentsAfterDone` — 이 티켓을 `dependsOn` 으로 가리키는 후행을 열고 각각
   `[Dependency Resolved]` 를 오케에 넣는다.
2. `closeImplicitMissionIfComplete` — 그 배치가 다 끝났으면 암묵 미션을 `completed` 로 닫는다.
3. `notifyOrchestrator("[Task Update] … → DONE")`.

**빠진 것은 "중간일 때 다음을 밀어라"** 하나다. 그리고 1번이 그 자리를 메우지 못한다:

> `[Dependency Resolved]` 는 **명시적 `dependsOn` 간선이 있는 티켓에만** 나간다.
> 라벨로만 묶인 형제 티켓(간선 0개)은 아무 신호도 못 받는다.

그런데 오늘 보드에서 일이 흐르는 실제 모양이 바로 그것이다 — 진단 §5.1 의 고아 티켓
`VCGuLWmNTlhoRvwGAKJA` 는 `contextId: "board"` 에 `missionId` 조차 없었다. 간선으로 엮인
계획이 아니라, 라벨로 묶인 배치가 실물이다.

## 2. 질문 1 — 완료 후크 지점: **DONE 전이**

후보는 둘이었다. **DONE 전이**로 정한다.

### 근거 (a) — 머지는 이미 DONE 으로 흘러들어온다

`merge_and_close` 는 `evaluateMergeCloseout` 을 거쳐 `path: TaskStatus[]` 를 돌려주고,
그 경로의 종착점이 `DONE` 이면 **`update_task_status` 와 같은 지점**을 지난다.
즉 DONE 에 후크를 걸면 머지 경로는 **공짜로 포함된다.** 후크를 두 개 만들 이유가 없다.

### 근거 (b) — 머지 시점에 걸면 틀린다 (이게 결정적이다)

`merge-closeout.ts` 의 설계 주석이 이미 이 판정을 내려놨다:

> **"코드 머지 ≠ 작업 완료"**: the PR lands, but the ticket's actual goal still needs a
> secret, an approval, or a live re-run.

`evaluateMergeCloseout` 은 후속 표지(`detectFollowupSignals`)가 잡히면 **머지됐어도**
`HOLD_REVIEW` 로 붙잡는다. 그 분기가 실제로 잡은 티켓들:

| 티켓         | 상황                                             |
| ------------ | ------------------------------------------------ |
| F1 콜러블    | 오늘 — 머지됐지만 배포·후속 남음                 |
| F4 조직 초대 | 오늘 — 머지됐지만 배포·후속 남음                 |
| `N8sAY4Tj`   | PR #585 MERGED, `marketing_contacts` 백필 미실행 |
| `84tDu7UW`   | Sentry 알림 규칙, 승인 대기                      |

**머지 시점에 후크를 걸면 이 네 건 전부에서 "다음"을 불렀을 것이다.** 아직 안 끝난 일 위에
다음 일을 쌓는 것이고, 그건 사장님이 막으라고 하신 비용 폭주의 가장 흔한 시작점이다.
반대로 DONE 에 걸면 HOLD 로 붙잡힌 티켓은 **사람이 후속을 마치고 DONE 으로 닫는 순간** 전진한다
— 지연이지 유실이 아니고, 그 지연이 정확히 의도다.

### 근거 (c) — DONE 은 판정 지점이 하나다

상태머신(`state-machine.ts`)이 이미 소유하고 있고 `applyProjection` 이 트랜잭션으로 커밋한다.
후크가 그 뒤에 붙으면 "커밋된 사실 위에서만 판정한다"가 공짜로 성립한다.

### 결론 — 단, DONE 에 이르는 경로는 **둘**이다

후크는 `closeImplicitMissionIfComplete` **바로 옆**에 붙인다. 새 진입점을 만들지 않는다.
그런데 그 자리가 두 곳이다 — 구현하면서 확인했다:

| 경로                                            | 위치                      |
| ----------------------------------------------- | ------------------------- |
| `update_task_status` 의 DONE 분기               | 에이전트가 직접 닫는 완료 |
| `merge_and_close` 의 `applied.includes("DONE")` | 머지가 닫는 완료          |

`merge_and_close` 는 `update_task_status` 를 거치지 않고 `applyProjection` +
`resolveDependentsAfterDone` 를 **직접** 부른다(그 자리의 기존 주석도 같은 함정을 말한다:
_"DONE 에 이르는 두 경로가 암묵적 미션 마감에서 갈리면 merge_and_close 로 닫은 묶음만
Replay 가 안 뜬다"_). 그래서 **양쪽에 다 건다.** 한쪽만 걸면 "머지는 이미 DONE 으로
흘러들어온다"는 위 근거가 실제로는 성립하지 않는다.

그리고 `HOLD_REVIEW`(머지됐지만 후속 남음)는 `applied` 에 DONE 이 없어 그 자리에 **도달하지
않는다** — 근거 (b)가 코드로 지켜지는 지점이 정확히 여기다.

## 3. 질문 2 — 귀속 판정: `contextId`, 그리고 **암묵 미션만** 전진 대상

### 귀속은 이미 필드 하나로 결정돼 있다

`tasks.contextId === missionId` 다 — 명시·암묵 공통(`tools.ts` `notifyOrchestrator` 주석:
"mission tasks carry contextId=missionId"). `"board"` 와 `lane:*` 는 미션이 아니다.
새 귀속 규칙을 만들지 않는다.

### ★그런데 미션 두 종류는 성격이 다르고, 전진 대상은 하나뿐이다

| 종류                                      | 지휘자가 운전하는가                          | 전진 대상 |
| ----------------------------------------- | -------------------------------------------- | --------- |
| **명시 미션** (`steps.length > 0`)        | ✅ grant → `mission_step_done` 루프가 운전   | ❌ 제외   |
| **암묵 미션** (`missionKind: "implicit"`) | ❌ **설계상 건너뛴다** (`wire.ts:219, :264`) | ✅ 대상   |

명시 미션을 제외하는 이유는 단순하다 — **거긴 이미 운전자가 있다.** 지휘자가 스텝을 grant 하고,
`wait`/`dispatch` 게이트는 `onEvent` 에서 `task.status_changed` 로 재평가된다. 거기에 완료후크가
또 "다음을 스폰하라"를 넣으면 그게 정확히 이중 스폰이다.

암묵 미션을 대상으로 삼는 이유는 그 반대다 — **거긴 운전자가 없다.**

```ts
// electron/mission-engine/wire.ts
// ★암묵적 미션(오케가 ad-hoc 배치에 붙인 Replay 라벨)은 실행 계획이
// 없다(steps=[]). 엔진이 이어받으면 0-스텝 미션을 헛돌린다.
if (isImplicitMission(d.data())) continue;
```

### "implicit 은 Replay 라벨이지 실행 계획이 아니다" 에 대한 답

맞다. 그래서 **우리는 스텝을 진행시키지 않는다.** 이 설계가 하는 일은 계획을 만드는 게 아니라,
**이미 만들어져 있는 형제 티켓을 오케에게 상기시키는 것**뿐이다. 라벨은 "이 티켓들은 사장님 지시
1건에 속한다"는 오케의 선언이고(`implicit-mission.ts` 설계 주석: _"경계는 오케가 dispatch 시점에
선언한다"_), 그 선언을 근거로 형제를 세는 것은 라벨의 원래 용법을 넘지 않는다.
새 태스크를 만들지 않고, `steps` 를 채우지 않고, 미션 문서의 실행 의미를 바꾸지 않는다.

그리고 실측이 이 판단을 강제한다 — 진단 §2 기준 **활성 미션 3건이 전부 implicit** 이다.
implicit 을 빼면 전진 대상이 0건이고 이 티켓은 무의미해진다.

## 4. 질문 3 — 종결 판정

**이미 있는 것을 쓴다.** `shouldCloseImplicitMission(mission, tasks)` 이 순수 함수로
"열린 티켓 0건인가"를 판정하고, `closeImplicitMissionIfComplete` 이 미션을 `completed` 로 닫는다.

- 남은 열린 티켓 **0** → 미션을 닫는다. **전진 신호는 나가지 않는다.**

명시 미션의 종결은 지휘자 `completeMission` 이 소유한다 — 건드리지 않는다.

## 5. 질문 4 — ★신호에 무엇을 담는가

여기가 핵심이다. **남은 목록만 주면 부족하다.** 오케가 그 메시지만 읽고 다음 dispatch 를
결정할 수 있어야 한다. 그래서 형제 티켓을 4갈래로 **갈라서** 담는다.

| 갈래                     | 판정                                                   | 오케가 해야 할 일                           |
| ------------------------ | ------------------------------------------------------ | ------------------------------------------- |
| **`readyNow`**           | `TODO` ∧ `dependsOnCompleted` ∧ 미클레임 ∧ 승인 불필요 | **지금 바로 dispatch**                      |
| **`blocked`**            | `TODO` ∧ `dependsOnCompleted === false`                | 손대지 마라 — 무엇을 기다리는지 함께 적는다 |
| **`inFlight`**           | `CLAIMED` / `IN_PROGRESS` / `REVIEW`                   | 또 뽑지 마라 — 슬롯 계산의 근거             |
| **`needsOwnerApproval`** | 승인 필요 표지가 잡힌 것                               | **스폰 금지 — 사장님께 여쭤라**             |

`readyNow` 의 판정은 `get_available_tasks` 의 쿼리 조건(`status=="TODO"` +
`dependsOnCompleted==true` + 미클레임)과 **정확히 같다**. 새 readiness 개념을 만들지 않았다 —
피드가 집을 수 있다고 말하는 것과 신호가 집을 수 있다고 말하는 것이 어긋나면 그게 버그다.

### 메시지 형태

```
[Mission Advance] '<라벨>' 전진 — 방금 닫힘: "<제목>" (id=…)
남음 N건 / 지금 가능 K건 / 대기 M건 / 진행중 J건 / 승인필요 P건
▶ 지금 집을 수 있음 (K): [id] "제목" (role, prio)
⏸ 선행 대기 (M): [id] "제목" ← 대기: [선행 id …]
⚙ 진행중 (J): [id] "제목" (status)
🔒 사장님 승인 필요 (P): [id] "제목" — 자율 스폰 대상 아님
권고: <한 줄>
```

`[Mission Advance]` 접두사는 `shouldInjectOrchestratorNotification` 의 미분류 기본값
(`return true`)을 타므로 게이트를 고치지 않고도 오케 PTY 에 닿는다 — 회귀 0.

**★신호 본문에는 티켓 id·제목·역할·상태만 넣는다.** PTY 원문도, 주입 메시지 본문도, 토큰도
넣지 않는다 — #1412 가 세운 규약을 그대로 지키고, 테스트로 고정한다.

## 6. 질문 5 — 중복 방지: 두 경로의 관계

| 축          | 지휘자 grant 루프                        | 이 완료후크                         |
| ----------- | ---------------------------------------- | ----------------------------------- |
| 운전 대상   | 미션 **스텝** (`steps[i]`)               | 보드 **티켓** (`tasks/*`)           |
| 미션 종류   | 명시 (`steps.length > 0`)                | 암묵 (`missionKind === "implicit"`) |
| 트리거      | `mission_step_done` / task 이벤트 wakeup | 티켓 `DONE` 전이                    |
| 무엇을 넣나 | "이 **스텝**을 실행하라"                 | "이 **티켓들**을 집을 수 있다"      |

**두 경로는 `missionKind` 필드 하나로 배타다.** 런타임 락이 아니라 **분기**라서 경합 자체가
성립하지 않는다. 락은 잊히지만 분기는 타입에 남는다. 그리고 지휘자는 이미 implicit 을 건너뛰는
코드를 가지고 있다(`wire.ts:219, :264`) — 우리는 그 반대편의 빈자리를 채울 뿐이고,
양쪽이 같은 미션 문서를 동시에 운전하는 상태는 **만들어질 수 없다**.

### 같은 완료가 두 번 들어오는 경우

`force=true` 로 `DONE → DONE` 을 다시 밀거나, 재시도로 같은 전이가 두 번 커밋될 수 있다.
그래서 신호는 **티켓당 1회**로 못 박는다:

`missions/{id}.advanceState.signaledTaskIds` 에 `arrayUnion(taskId)` 로 기록하고,
**읽기와 쓰기를 같은 트랜잭션 안에서** 한다. 이미 들어 있으면 신호를 만들지 않고
`"duplicate completion"` 사유만 남기고 끝낸다.

## 7. ★안전장치 — 전진 로직보다 먼저 깔린다

사장님이 특히 짚으신 부분이다. 세 한도 + 두 우선순위 규칙 + 기본값 OFF.

| #   | 안전장치         | 기본값 | 판정                                                      | 넘었을 때                                              |
| --- | ---------------- | ------ | --------------------------------------------------------- | ------------------------------------------------------ |
| 1   | 연속 자율 스폰   | **5**  | `advanceState.consecutiveSignals` (사람 개입 시 0 리셋)   | **HALT** + 사유                                        |
| 2   | 동시 슬롯        | **3**  | `inFlight` 개수                                           | **back-pressure** (신호는 나가되 `readyNow` 를 비운다) |
| 3   | 진행 없음        | **2**  | 연속 신호 사이 열린 티켓 수가 안 줄면 `stagnantSignals++` | **HALT** + 사유                                        |
| 4   | 승인 필요 작업   | —      | 배포 / 메일 발송 / 결제 / 심사 기간 화면 변경             | `readyNow` 에서 제외 → `needsOwnerApproval`            |
| 5   | 사장님 입력 우선 | —      | 미해결 오너 질문 또는 미소비 오너 인바운드                | 자율 신호 보류 + 사유                                  |
| 6   | 기본값 OFF       | off    | `MISSION_ADVANCE_SIGNAL` 이 정확히 `on` 일 때만           | 아무 일도 안 한다                                      |

### 1. 연속 자율 스폰 한도 (기본 5)

한 미션이 **사람 개입 없이** 연달아 밀 수 있는 횟수. 사장님/사람의 개입이 관측되면 0으로 리셋된다.
5는 "한 지시가 5단계까지는 스스로 굴러도 되지만 6단계째엔 사람이 한 번 봐야 한다"는 값이고,
플래그로 조정 가능하다.

### 2. 동시 슬롯 한도 (기본 3)

오늘 실측으로 11기까지 갔지만 **그건 손으로 배치한 것**이다. 자율이면 더 빨리 는다.
그래서 자율 경로의 기본값은 보수적으로 3이다.

★이건 HALT 가 **아니다**. 슬롯이 포화면 신호는 그대로 나가되 `readyNow` 를 비우고
`"슬롯 포화 (3/3) — 지금은 새로 뽑지 마라"` 를 담는다. 티켓 하나가 끝나면 자연히 풀리므로
사람이 풀어줘야 하는 정지가 아니다. **정보는 전달하고 행동만 막는 것**이 back-pressure 다.

### 3. 진행 없음 감지 (기본 2) — 무한루프의 실제 모양

한도 1·2 만으로는 무한루프가 안 잡힌다. 신호는 티켓이 DONE 될 때만 나가므로 매 신호가
"티켓 하나 닫힘"을 동반한다 — 겉으로는 늘 진행 중으로 보인다.

**진짜 폭주의 모양은 이것이다: 오케가 신호를 받고 형제 티켓을 집는 대신 새 티켓을 더 만든다.**
그러면 티켓은 계속 닫히는데 **미션의 열린 티켓 수는 줄지 않는다.** 그게 비용이 무한히 나가는
모양이고, 한도 1은 사람 개입 때마다 리셋되므로 이걸 못 막는다.

그래서 판정은 **열린 티켓 수의 단조 감소**로 한다:

```
openCount(now) >= openCount(직전 신호 시점)  →  stagnantSignals++
openCount(now) <  openCount(직전 신호 시점)  →  stagnantSignals = 0
stagnantSignals > 2  →  HALT
```

### 4. ★승인 필요 작업은 자율 스폰 대상에서 뺀다

배포 · 메일 발송 · 결제 · 심사 기간 화면 변경. 이런 게 걸린 티켓은 `readyNow` 에 **절대**
들어가지 않고 `needsOwnerApproval` 로 옮겨져 "오케가 사장님께 여쭤보라"고 표시된다.

판정 어휘는 `merge-closeout.ts` 의 `detectFollowupSignals` 와 같은 규율로 만든다 —
표지 목록 + 부정어 창(`"배포 없음"`, `"결제 아님"` 은 걸리지 않는다). 다만 **스캔 면이 다르다**:
`merge-closeout` 은 본문을 오탐 때문에 거의 안 보지만, 여기서는 **본문도 본다.**
방향이 반대이기 때문이다 — 저기서는 오탐이 티켓을 REVIEW 에 붙잡는 것(가벼움)이고,
여기서는 누락이 승인 없이 배포를 스폰하는 것(무거움)이다. **의심스러우면 승인 필요 쪽으로 붙인다.**

### 5. 사장님 입력이 자율 진행보다 우선한다

미해결 오너 질문(`openQuestions`)이나 미소비 오너 인바운드(`readOwnerInbound`)가 있으면
자율 신호를 내지 않는다. 사장님이 방향을 주고 계신 중에 기계가 다음을 밀면 그 지시와 경합한다.
사유(`"owner input pending"`)를 남기고, 그 입력이 처리되면 연속 카운터가 0으로 리셋된 채 재개된다.

### 6. 기본값 OFF

`MISSION_ADVANCE_SIGNAL` 이 **정확히** `on` 일 때만 동작한다. 미설정·오타·빈 값은 전부 off —
`getMissionDriver()` 가 `"orchestrator"` 정확일치만 받는 것과 같은 규율이다.
off 일 때 이 코드는 **아무것도 읽지 않고 아무것도 쓰지 않는다**(회귀 0).

### ★멈춤에도 사유가 남는다 — 3중 기록

조용히 멈추면 오늘 고친 #1412 의 문제가 그대로 재발한다. 그래서 HALT 는 세 곳에 남는다:

| 어디                                               | 왜                                              |
| -------------------------------------------------- | ----------------------------------------------- |
| 티켓 `activities`                                  | 보드에서 사람이 보는 durable 기록               |
| `missions/{id}.advanceState.haltReason`/`haltedAt` | 다음 판정이 읽는 상태 (같은 사유로 계속 멈춘다) |
| 오케 PTY (`[Mission Advance] ⏸ …`)                 | 사람이 개입해야 풀리므로 **반드시 깨운다**      |

### ★신호가 오케에 안 닿았을 때

`postOrchestratorNotification` 의 3분기를 그대로 읽는다:

| 결과         | 처리                                                                      |
| ------------ | ------------------------------------------------------------------------- |
| `delivered`  | `consecutiveSignals++`, `signaledTaskIds` 확정                            |
| `suppressed` | 실패가 아니다(브리지의 의도적 억제) — 기록하지 않는다                     |
| `failed`     | **티켓 activity 로 사유를 남기고, `consecutiveSignals` 를 올리지 않는다** |

닿지도 않은 신호를 한도에 세면 미션이 진행 없이 한도만 태우고 멈춘다. 카운터는 **배달된
신호만** 센다.

## 8. 전체 판정 순서

```
DONE 전이 커밋됨
  │
  ├─ 플래그 off?                          → NO_SIGNAL "flag off"        (아무것도 안 읽음)
  ├─ contextId 가 board/lane?              → NO_SIGNAL "not a mission"
  ├─ 미션이 implicit 이 아님(명시)?         → NO_SIGNAL "conductor-owned"
  ├─ 미션이 이미 terminal?                 → NO_SIGNAL "mission closed"
  ├─ 이 taskId 로 이미 신호했음?            → NO_SIGNAL "duplicate completion"
  │
  ├─ 열린 티켓 0건?                        → CLOSE_MISSION  (신호 없음 — 질문 3)
  │
  ├─ [안전] 이미 HALT 상태?                → NO_SIGNAL "halted: <이전 사유>"
  ├─ [안전] 사장님 입력 대기?               → HOLD "owner input pending"
  ├─ [안전] 연속 스폰 한도 초과?            → HALT "consecutive-spawn-cap"
  ├─ [안전] 진행 없음 한도 초과?            → HALT "no-progress"
  │
  └─ SIGNAL_ADVANCE
       ├─ 형제 4갈래 분류 (승인 필요는 readyNow 에서 제외)
       ├─ [안전] 슬롯 포화면 readyNow 를 비운다 (back-pressure)
       └─ 배달 결과에 따라 카운터 갱신
```

**한도 판정이 전진 판정보다 위에 있다** — 안전장치가 전진 로직 위에 얹힌 게 아니라 아래에 깔렸다.

## 9. 테스트로 고정하는 것

### 안전장치 (`mission-advance-guards.test.ts`)

- 한도(연속 스폰 / 슬롯 / 진행 없음) 도달 시 **멈추고 사유가 남는다**
- 승인 필요 작업(배포·메일·결제·심사 화면)은 **자율 경로가 안 집는다** — `readyNow` 에서 제외
- 부정어(`"배포 없음"`)는 승인 필요로 오탐하지 않는다
- 같은 완료가 두 번 들어와도 신호는 **한 번**
- 사장님 입력 대기 중에는 자율 신호가 안 나간다
- 플래그 기본값이 **OFF** 이고, 오타/빈 값도 OFF

### 전진 로직 (`mission-advance-signal.test.ts`)

- 마지막 태스크면 **미션이 닫히고 신호 없음**
- 중간이면 **신호가 나가고 그 안에 "지금 집을 수 있는 것"이 구분돼 있음**
- 미션에 안 속한 단발 태스크(board/lane)면 **아무 신호도 없음**
- 명시 미션(steps>0)이면 신호 없음 — 지휘자 소유
- 신호 본문에 PTY 원문·메시지 본문·토큰이 **안 들어간다**
- 배달 실패(`failed`) 시 사유가 남고 연속 카운터가 안 오른다

## 10. 하지 않은 것

- **미션 엔진을 새로 설계하지 않았다.** 완료후크와 신호 경로만 더했다.
- 명시 미션 경로는 한 줄도 안 건드렸다 — 지휘자 소유 그대로다.
- 암묵 미션에 `steps` 를 만들지 않는다. 라벨은 라벨로 남는다.
- 기본값을 ON 으로 두지 않았다.
- 새 readiness/귀속 개념을 만들지 않았다 — `contextId` 와 `dependsOnCompleted` 를 그대로 쓴다.

## 11. 켜는 순서

1. 이 문서를 사장님이 보신다.
2. 한도 기본값(5 / 3 / 2)에 대한 판단을 받는다.
3. `MISSION_ADVANCE_SIGNAL=on` 으로 켠다.
4. 실측: 연속 스폰이 실제로 몇 회에서 멈추는지, 슬롯 포화가 얼마나 자주 걸리는지.
