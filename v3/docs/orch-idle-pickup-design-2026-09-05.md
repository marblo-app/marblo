# 오케 자율 진행 — 큐가 비지 않는 한 다음을 스스로 집는다 (설계)

**티켓** `6hWxqjbzGQs1hzTUTihx` · **날짜** 2026-09-05 · **선행** #1414(전진 신호) · #1416(한도) · #1425(배달 폴백)

---

## 1. 사장님이 짚으신 것, 그리고 짚으신 처방을 그대로 만들지 않는 이유

> _"리뷰티켓들 19개나 있는데 그것들 체크도 안하고 너는 서있잖아. 이게 클로즈드루프가 제대로 안 돈다는 거야."_ > _"오케스트레이터한테 턴을 멈추지 말고 계속 돌아라라는 stdin 주입을 계속 줘야 되나?"_

증상은 정확하다. 처방은 **대증요법**이라 그대로 만들지 않는다. "계속 돌아라"를 주기적으로 주입하면

- 할 일이 없을 때도 오케가 턴을 돌아 **토큰이 그냥 나간다**,
- 오케가 바쁠 때도 들어가 **큐만 쌓인다**,
- #1416 이 세운 무한루프 방지 설계(연속 5·정체 2 에서 HALT)와 **정면으로 부딪힌다** — "쉬지 말고 돌아라"는 한도가 막으려던 바로 그 모양이다.

그래서 이 문서가 답하는 질문은 하나로 좁힌다:

> **무엇이 있을 때 스스로 집는가. 그리고 밀 것이 없으면 조용히 있는가.**

## 1-1. ★주어진 성질 — 오케는 한 작업을 끝내면 멈춘다

> _"전진신호가 계속 가야 되도록 설계해줘. 클로드가 보면 특정 작업을 하고 멈춰버리는 경향이 있더라고."_
> _"이건 거의 모든 모델들이 공통일 거야."_

이것을 **고쳐야 할 결함이 아니라 주어진 성질**로 놓는다. 오케는 턴이 끝나면 멈춘다. 2026-09-05 에 실제로 그랬다 — 리뷰 19장이 쌓이도록 서 있었고 사장님이 지적하신 뒤에야 움직였다. 모델을 바꿔도 안 바뀐다.

여기서 설계 원칙이 하나 나온다. **이 문서 전체가 이 한 줄의 따름정리다.**

> ★**루프가 오케의 "계속하려는 의지"에 의존하면 안 된다. 밖에서 밀어야 한다.**

세 갈래로 구체화된다.

| 원칙                                                | 이 설계에서 무엇으로 나타나나                                                                                                                                                                    |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 오케가 "다음을 집어야지" 판단하기를 기다리지 않는다 | 판정은 **보드 층**(`OrchestratorBoardResync` 틱)이 한다. 오케는 밀려 들어온 것을 처리할 뿐이고, 판정에 참여하지 않는다                                                                           |
| **모델 무관**                                       | 판정 입력이 전부 보드 상태(티켓 status·나이·미션 귀속)와 프로세스 관측(busy 신호·세션 id)이다. 모델 이름도 능력도 안 본다. "더 좋은 모델이면 알아서 계속하겠지"에 기대는 자리가 **한 곳도 없다** |
| 이벤트가 없을 때도 밀린다                           | #1425 가 고친 "완료 → 다음 신호"는 **이벤트 기반**이다. 이 티켓은 완료가 하나도 안 일어나는 상태(리뷰만 쌓임)를 맡는다                                                                           |

★그러나 **"조건 없이 밀기"는 여전히 금지다**(§1). 밀되 **밀 이유가 있을 때만** 민다 — §3 이 그 이유의 전부이고, §6 이 밀지 말아야 할 상태의 전부다.

## 2. 실측 — "아무도 안 깨운다"가 아니었다

조사해보니 깨우는 층은 **이미 있다**. 그 층이 오늘의 19장을 **구조적으로 못 볼 뿐**이다. 근거 셋은 전부 `main` 코드 실측이다.

### 2-1. 주기 스위프는 이미 돈다

`electron/orchestrator-board-resync.ts` 가 **120초마다** 보드를 진실원으로 읽어 REVIEW·FAILED·BLOCKED·고아 티켓·체인 READY 를 오케 PTY 로 민다(#1354 규율의 DI 하니스). 즉 "주기적으로 오케를 깨운다"는 것은 이미 있는 기능이고, stdin 주입은 그 위에 한 겹 더 얹는 것이다.

### 2-2. ★그 스위프가 미션 티켓을 통째로 건너뛴다 — 이것이 19장의 정체다

```ts
// orchestrator-board-resync.ts :: classifyResyncAttention
if (row.isMission) return null; // "미션 티켓은 컨덕터 report-watchdog 소관"
```

그 근거가 지금은 성립하지 않는다. 세 사실이 겹친다.

| 사실                                                                                       | 코드                                                       |
| ------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| `isMission` 은 `missionId` 필드 유무다                                                     | `main.ts:3245` `isMission: !!data.missionId`               |
| **암묵 미션 티켓에도 `missionId` 가 박힌다**                                               | `tools.ts:4714` `data.missionId = implicit.missionId`      |
| 컨덕터의 report-watchdog 은 `grantStep` 이 거는 **스텝별** 타이머라 **명시 미션에만** 있다 | `conductor-driver.ts:471`, key=`${missionId}:${stepIndex}` |

암묵 미션은 보드 오케가 라벨로 만드는 묶음이라 `steps` 가 없고 `grantStep` 을 타지 않는다. 따라서 **암묵 미션의 REVIEW 티켓은 스위프도 컨덕터도 보지 않는다.** 아무도 안 보는 사각지대에 티켓이 쌓인 것이 19장이다.

★이것은 **#1425 가 배달 층에서 고친 것과 같은 종류의 가정**이다 — _"미션 컨텍스트면 미션 오케/컨덕터가 있다"_. #1425 는 그 가정이 깨진 자리에서 알림이 버려지는 것을 고쳤고(→ 보드 오케 폴백), 이 티켓은 **한 층 위에 남아 있던 같은 가정**을 고친다.

### 2-3. 스위프는 "전했다"만 세고 "행동했다"는 안 본다

seen 집합의 단위는 `ptySessionId × (kind,taskId,status)` 이고, **주입 성공 시 기록**된다. 같은 세션에는 같은 항목을 두 번 밀지 않는다(알림 폭주 방지 — 정당한 설계다). 그런데 그 대가로:

> 오케가 그때 바빠서 못 집었으면, 그 항목은 그 세션 동안 **영원히 다시 말해지지 않는다.**

전달의 신뢰성은 이미 보강됐지만(#1412·#1425), **"전달 ≠ 행동"** 을 확인하는 자리가 없다. 사장님이 보신 "서 있는 오케"의 절반은 여기다.

## 3. 깨우는 조건 — 둘만 넣는다

★규율: **"이게 없으면 무엇을 놓치는가"를 못 적는 조건은 넣지 않는다.**

| #   | 조건                    | 판정                                                                            | 없으면 무엇을 놓치나                                                                 |
| --- | ----------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| A   | **주인 없는 미션 티켓** | attention 행이 `isMission` 이고 그 프로젝트에 **미션 오케가 안 돌고 있다**      | §2-2 의 19장. 스위프도 컨덕터도 안 보는 티켓이 무한히 쌓인다                         |
| B   | **정체된 항목**         | 이미 이 세션에 통보했는데 보드 활동 없이 `staleAfterMs` 이상 같은 상태에 머문다 | §2-3. "한 번 전하고 잊는" 구멍 — 오케가 바쁠 때 도착한 알림이 영영 재통보되지 않는다 |

### 3-1. 넣지 않은 후보와 그 이유

| 후보                          | 왜 뺐나                                                                                                      |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------ |
| REVIEW 가 **N개 이상**        | 1장이 막힌 것과 19장이 막힌 것의 위험이 **같다**. 개수는 판정축이 못 되고, N 은 새 한도다(#1416 금지)        |
| 열린 PR 이 **머지 가능 대기** | 이 스위프에 PR 상태 소스가 없다. GitHub 조회를 새로 붙이면 "없으면 무엇을 놓치나"보다 새 실패 모드가 더 크다 |
| 워크체인이 **다음을 가리킴**  | 스위프의 체인 축(`listReadyChainItems`)이 **이미 민다.** 넣으면 같은 사실을 두 번 말한다                     |

## 4. 무엇을 보내나 — "돌아라"가 아니라 "무엇이 왜 대기 중인가"

#1414 의 `SIGNAL_ADVANCE` 가 형제를 4갈래로 갈라 담는 것과 **같은 규율**이다. 오케가 이 메시지만 읽고 다음 행동을 정할 수 있어야 한다.

```
[자율 진행] 오케가 유휴 상태인데 아래 3건이 아직 움직이지 않았습니다.
· REVIEW 정체: "…" (id=…, backend, PR: …) — 18분째 REVIEW, 이미 통보함 — 검증/머지 또는 반려가 필요합니다
· 미션 티켓(주인 없음): "…" (id=…, status=REVIEW) — 미션 오케가 돌지 않아 이 티켓을 보는 감시자가 없습니다
🔒 사장님 승인 필요 (1) — ★자율 대상 아님. 사장님께 여쭤라:
· "…" (id=…)
권고: 위 자율 대상 2건을 처리하라. 집을 때 add_activity 에 "자율 진행으로 집음" 을 남겨 사장님이 구분할 수 있게 하라.
```

승인필요 분류는 `advance-guards.ts :: detectApprovalSignals` **그대로** 재사용한다 — 배포·메일발송·결제·심사기간 화면. 새 분류기를 만들지 않는다. 잡힌 항목은 **집는 목록에서 빠지고** 정보로만 실린다.

## 5. 한도 — 새로 만들지 않는다 (#1416 준수)

| --------------- | --------------------------------------------------------------- | ------------ |

### 5-1. 한도 상태를 어디에 두나 — 미션 문서가 없다

`SIGNAL_ADVANCE` 의 `advanceState` 는 `missions/{id}` 에 산다. 자율 픽업은 **보드 단위**라 걸 미션 문서가 없다. 새 컬렉션을 만들지 않고 **오케 PTY 세션 단위 인메모리**로 둔다 — 스위프의 seen 집합과 **같은 수명·같은 리셋 규율**이다(세션이 갈리면 빈 상태로 시작).

`AdvanceStateSnapshot` 모양 그대로 채워 `evaluateAdvanceGuards` 에 넘기므로, **한도 판정 코드는 한 벌**이다. `openCount` 는 이 프로젝트의 열린 attention 항목 수 — 큐가 안 줄어든 채 픽업만 반복되면 `no-progress` HALT 로 잡힌다.

### 5-2. ★한 곳만 다르게 했다 — 사장님 개입이 HALT 를 푼다

미션 쪽 HALT 는 사람이 Firestore `advanceState` 를 손으로 풀어야 재개된다. 자율 픽업의 HALT 는 **사장님 인바운드가 관측되면 풀린다**(연속 카운터 0 리셋과 함께). 이유는 대칭이다 — 미션 쪽은 사람이 만질 문서가 있지만 여기는 인메모리라 **사람이 만질 손잡이가 없다**. 그러면 한 번 HALT 된 프로젝트는 앱을 재시작할 때까지 죽는데, 그게 정확히 이 코드베이스가 반복해서 고쳐 온 **조용한 정지**다. 사장님 메시지는 "사람이 루프에 들어왔다"의 관측이고, 그것이 여기서는 손잡이다.

## 6. 언제 **안** 깨우나 — 피해야 할 것을 타입으로 막는다

| 금지                      | 어떻게 막나                                                                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 무조건 주기 깨우기        | 후보가 0이면 `NO_PICKUP` 이고 **메시지를 만들지 않는다.** 한도 상태도 안 건드린다(빈 틱이 한도를 태우지 않는다)                             |
| 오케가 바쁠 때 깨우기     | `isBusySignal`(pty-manager) 의 busy→idle 턴 경계를 쓴다 — 텔레그램/슬랙 nudge 가 이미 쓰는 그 관측. 조용해진 지 `idleQuietMs` 미만이면 스킵 |
| 방금 밀어놓고 또 밀기     | **같은 틱에 스위프가 이미 주입했으면 픽업은 건너뛴다**                                                                                      |
| 승인필요 자율 픽업        | `detectApprovalSignals` 가 잡으면 `picked` 에서 빠지고 `withheld` 로만 실린다                                                               |
| 사장님 지시보다 앞서기    | `ownerInputPending` 이면 `hold` — #1414 와 같은 코드(`owner-input-pending`)                                                                 |
| **잔여량 부족일 때 밀기** | `evaluateTokenBudgetGate`(#1416) 를 그대로 부른다. 예비선 이하면 이번 틱은 밀지 않는다 — ★HALT 가 아니다(한도 창이 지나면 저절로 풀린다)    |
| 조용한 틱에 계정 찌르기   | ★토큰 프로브는 **밀 후보가 있고 오케가 한가할 때만** 돈다. 할 일이 없는 틱의 추가 비용은 0이다                                              |

### 6-1. 중복 억제 — 19장이 쌓였다고 19번 밀지 않는다

세 겹이고, 셋 다 **기존 규율의 재사용**이다.

| 겹               | 무엇                                                                                                                                                    | 효과                                        |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| 한 통으로 합친다 | 항목별 N통이 아니라 **다이제스트 1통** — 스위프 다이제스트와 같은 규율                                                                                  | 19장 → 메시지 1통                           |
| 항목별 쿨다운    | seenKey 별 마지막 픽업 시각을 들고 `staleAfterMs`(600초) 안에는 다시 안 싣는다. 픽업한 항목은 seen 에도 넣어 다이제스트가 같은 사실을 또 밀지 않게 한다 | 같은 티켓을 120초 틱마다 다시 말하지 않는다 |
| 연속 한도        | 사람 개입 없이 연속 5회에서 HALT                                                                                                                        | 한 세션에서 자율 픽업 메시지는 **최대 5통** |

★`orchIdleForMs === null`(부팅 후 busy 신호를 한 번도 못 봄)은 **바쁨이 아니라 모름**이고, 통과시킨다. 모름을 차단으로 접으면 프로브가 없는 기기에서 폐루프가 영영 멈춘다 — 토큰 게이트의 `no-data` 를 통과시킨 것과 같은 판단이다.

## 7. 판정 순서 (이 순서가 곧 우선순위)

```
0. 플래그 OFF                      → NO_PICKUP(flag-off)      아무것도 읽지 않는다
1. 오케 세션 없음/미실행           → NO_PICKUP(no-session)
2. 오케가 바쁨                     → NO_PICKUP(orch-busy)     ★한도 앞 — 빈 틱이 한도를 태우지 않게
3. 이미 HALT 됨                    → NO_PICKUP(already-halted) 메시지 없음(같은 정지를 매 틱 떠들지 않는다)
4. 후보 0                          → NO_PICKUP(nothing-stale)  상태 변화 없음
5. 한도 (evaluateAdvanceGuards)    → HALT | hold
6. 토큰 잔여 (evaluateTokenBudgetGate) → NO_PICKUP(token-insufficient)  ★HALT 아님
7. 슬롯 back-pressure              → PICKUP (+ "지금은 새로 뽑지 마라")
```

- 한도가 여전히 듣는지: 연속 5 초과 → `HALT`, 정체 2 초과 → `HALT`, 동시 3 → back-pressure(HALT 아님).
- `npm run typecheck`(tsconfig 3벌) · `npm test` · 위키 신선도 게이트.

## 9. 켜는 법 / 끄는 법

기본값 **OFF**. 켜는 스위치는 `MISSION_ADVANCE_SIGNAL=on` **하나**이고 전진 신호와 **공유**한다(사장님 지시 "한번에 켜줘"). 끄는 법 세 겹:

1. 플래그를 내린다 → 이 경로는 아무것도 읽지 않는다.
2. 사장님이 텔레그램/슬랙으로 말씀하신다 → 미소비 인바운드가 있는 동안 `hold`(+ 연속 카운터 0 리셋, HALT 해제).
3. 한도 초과 → `HALT` + 사유가 로그와 메시지에 남는다.

## 10. ★텔레그램 인바운드와의 경계 — 배선은 공유, 정책은 가른다

> _"텔레그램은 텔레그램대로 큐에 있다가 다시 들어가도록 해야 하고."_

텔레그램/슬랙 인바운드 큐는 **이 티켓 소관이 아니다**(형제 티켓 `nMpBzIMJmkSFqrrZfSKz`). 이 설계는 그 큐를 만들지도 건드리지도 않는다. 두 흐름을 한 큐로 합치면 안 되기 때문이다 — **규율이 정반대다.**

| 축        | 전진 신호 / 자율 픽업 (이 티켓)                   | 텔레그램 인바운드 (형제 티켓)                |
| --------- | ------------------------------------------------- | -------------------------------------------- |
| 무엇인가  | **시스템 이벤트** (보드 상태의 파생)              | **사람의 말** (사장님 문장 원문)             |
| 유실      | 허용 — 다음 틱에 같은 보드 상태에서 다시 파생된다 | ★**불가**                                    |
| 순서      | 무관 — 한 통으로 합쳐 보낸다                      | ★**유지**                                    |
| 합치기    | ★**해야 한다** (19장 → 1통)                       | ★**불가** — 두 문장은 두 문장이다            |
| 중복 억제 | ★**해야 한다** (쿨다운 + seen + 연속 한도)        | ★**금지** — 같은 말을 두 번 하시면 두 번이다 |

★교차 적용의 실패 모양을 적어 둔다. 전진 신호 규율(합치기·중복 억제)을 사람 말에 적용하면 **사장님 메시지가 합쳐지거나 버려진다.** 반대로 사람 말 규율(전부·순서대로)을 시스템 이벤트에 적용하면 **같은 알림이 수십 번 쏟아진다** — 오늘의 19장이 19통이 된다.

### ★#1422 가 착지한 뒤 — 경계가 양쪽에서 확인됐다

#1422(`nMpBzIMJmkSFqrrZfSKz`)가 `electron/telegram-inbound-queue.ts` 로 인바운드 내구 큐를 세웠다. 그 커밋 본문이 같은 경계를 **저쪽에서 먼저** 적었다:

> _"★이 큐의 규율은 형제 티켓(6hWxqjbz)의 전진 신호 큐와 정반대라 합치지 않았다 — 전진 신호는 중복 억제·합치기가 옳지만 인바운드는 사람의 말이라 유실 불가·순서 유지·합치기 금지다."_

이 설계는 그 큐에 **쓰지도 드레인하지도 않는다.** 접점은 **읽기 한 방향**뿐이다 — `readOwnerInbound()` 로 "미소비 인바운드가 있나"를 보고 자율 진행을 비킨다. 큐의 배달은 #1422 의 드레인 루프가 전담하고, 이 경로는 그 순서에 손대지 않는다.

한 가지가 덤으로 좋아졌다. #1422 는 `composer-gate` 의 관측 유효기간에 **시간 기준(45초)** 을 더해, 오케가 조용할 때 낡은 관측이 영원히 "지금 화면"으로 남던 자기잠금을 풀었다. 자율 픽업은 **정의상 오케가 조용할 때만** 주입하므로 그 자기잠금의 정면 피해자였다 — #1422 없이 이 기능을 켰다면 픽업이 `composer-occupied` 로 계속 거절당했을 것이다. (거절되면 이 설계는 한도를 태우지 않고 다음 틱에 재시도하므로 안전 쪽으로 실패하긴 했겠지만, 신호는 안 닿았을 것이다.)

★이 경로의 유휴 판정(`orchIdleForMs = now − lastBusyAt`)은 처음부터 **시계 기준**이라 #1422 가 고친 그 버그의 모양을 갖고 있지 않다. 계량기가 PTY 출력량이 아니라 시간이다.

### 무엇을 공유하나

**주입 배선 한 겹만** 공유한다: `OrchestratorManager.injectMessage` (정직한 boolean 을 돌려주는 그 경로). 이 설계는 그 함수를 부를 뿐, 큐도 재시도도 순서 보장도 자기 것을 만들지 않는다. 정책(무엇을·언제·몇 번 미는가)은 §3·§6·§6-1 에 있고, 그것은 **이 파일 안에만** 있다.

★한 자리에서 두 흐름이 만난다: 사장님 인바운드가 **미소비 상태면 자율 픽업이 보류된다**(§6). 방향이 한쪽뿐인 것이 요점이다 — 사람 말이 시스템 이벤트를 멈추게 하지, 그 반대는 없다.
