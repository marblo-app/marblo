# 이벤트 행 사람키 각인 · 내부계정 판정 · GA4 결합 (2026-08-29)

티켓 `VZ0K2FIeASLrWy9bwvN1`. 사장님 지시(텔레그램 2026-08-29)에 대한 **판정과
설계**다. 선행 정본은 `person-axis-user-key-design-2026-08-21.md`(PR #1081)이고,

## 1. ★판정 — "조회 vs 저장" 은 어느 쪽이 옳으냐의 문제가 아니었다

선행 설계 §5.4 는 이렇게 못박았다.

> "저장: 절대 소급하지 않는다. **이벤트 행에 `user_key` 컬럼을 만들지 않는다.**"

사장님 지시는 정반대다. 이 티켓의 첫 과제는 "왜 그때 그렇게 정했는지" 를 읽고
지금 바꾸는 것이 맞는지 판단하는 것이었다.

### 1.1 원결정의 근거 넷과, 각각이 지금도 서는가

| #   | §5.4 의 근거                                     | 지금도 서는가                                                                                          |
| --- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| 1   | 소급을 저장에서 조회로 옮기면 **되돌릴 수 있다** | ★**선다.** 그래서 링크표를 그대로 뒀다. 각인은 forward-only 라 소급을 대체하지 않는다                  |
| 2   | 삭제요청이 **한 줄**이 된다                      | 부분적으로. 각인 삭제도 한 줄(`UPDATE … SET userKey=NULL`)이지만 **줄이 둘로 늘었다** → §6.3 거래 조건 |
| 3   | 상한을 거는 **비용이 실측 0** 이다               | 무관(상한은 그대로)                                                                                    |
| 4   | 뷰 이름이 곧 고지다                              | ★**선다.** 각인 축에도 같은 규율을 옮겼다(§2.4 `EventStampCoverage`)                                   |

그리고 §4.2-4 의 기각 사유 하나가 **실측으로 무너진다**:

> "컬럼이면 익명 표를 UPDATE 해야 한다 … 삭제요청 = 1,100만행 UPDATE"

실측 2026-08-29 (`__TABLES__`, 무료 메타데이터):

| 표                 | 행          | 크기      |
| ------------------ | ----------- | --------- |
| `events`           | **437,114** | **68 MB** |
| `agent_heartbeats` | 14,502,795  | 1,753 MB  |
| `cost_logs`        | 411,895     | 58 MB     |
| `task_outcomes`    | 1,739       | 0.3 MB    |

★1,100만행은 `agent_heartbeats` 였다. `events` 는 그 1/33 이고, 삭제요청 UPDATE 가
BQ 최소 과금 수준이다. **그래서 각인 대상은 `events` 하나로 한정한다** —
`agent_heartbeats` 에는 각인하지 않는다. 같은 논거가 그 표에서는 성립하지 않는다.

### 1.2 ★그런데 판정을 실제로 뒤집은 것은 실측이 아니라 **방침 문면**이다

배포 중인 `v3/src/components/legal/privacyContent.tsx` "비식별 1차 지표
(BigQuery)" 항 원문:

> "다만 기기 단위가 아니라 사람 단위로 볼 수 있어야 해서, 로그인한 계정의
> 식별자를 그대로 쓰지 않고 가명처리해 만든 가명 구분값을 **이 기록에 함께
> 적습니다**. … 이 가명 구분값으로 할 수 있게 되는 일은 두 가지입니다: 사람
> 단위로 이용 흐름을 보는 것과, **통계에서 운영자 본인의 활동을 빼는 것**."
>
> EN(:241): "…we write a pseudonymous key made from it instead… What this
> pseudonymous key makes possible is exactly two things: seeing how one person
> moves through the product, and **leaving our own operator activity out of the
> stats**."

**"이 기록" 은 이벤트 기록이다.** 즉 우리는 이미 이용자에게 _"이벤트 행에 가명
사람키를 적는다"_ 고 고지해 두고, 구현은 링크표에만 적고 있었다 — 방침이 코드보다
앞서 있었던 것이고, 지금 상태는 **과소 구현**이다.

선행 문서 §1 이 남긴 교훈은 _"설계를 먼저 구현했다가 배포된 방침과 어긋나
되돌렸다"_ 였다. 이번은 어긋난 **방향이 반대**일 뿐 같은 종류의 어긋남이다.
그래서 각인은 방침 확장이 아니라 **코드를 방침에 맞추는 일**이다.

같은 문장이 약속한 운영자 제외도 지금 **안 된다**:
`adminEventExclusion()`(`functions/src/index.ts:9573`)의 절은
`JSON_VALUE(metadata,'$.accountUserId')` 를 보는데, 계정축 은퇴 이후 행에는 그
값이 없어 절이 항상 NULL 로 통과한다 = **아무것도 제외되지 않는다.**

### 1.3 ★결론 — 둘은 배타적이지 않다. 다만 역할이 다르다

|              | 링크표(조회)                     | 각인(저장)                |
| ------------ | -------------------------------- | ------------------------- |
| 과거 43만 행 | ★**붙는다**(`v_person_all_time`) | 안 붙는다(forward-only)   |
| 조인         | 2단 필요                         | 없음                      |
| 공용 기기    | 설치째 **제외**(§5.5)            | 행 단위로 **귀속**        |
| 운영자 제외  | 설치 단위                        | 행 단위                   |
| 되돌리기     | 표 하나 삭제                     | `UPDATE … SET NULL` 한 줄 |
| 커버리지     | ★**같다** — 아래 참조            |                           |

★**각인이 커버리지를 늘리지 않는다는 사실이 이 판정의 핵심이다.** 링크 MERGE 와
각인은 **같은 함수의 같은 요청**(`logTelemetryBatch`, auth 강제) 안에서 일어난다.
링크가 생기는 배치는 각인도 되고, 각인이 안 되는 배치는 링크도 안 된다. 즉
사장님이 "왜 내부 사용자가 구분이 안 되지" 라고 보신 문제는 **각인으로 안 풀린다** —
그 문제의 원인은 링크 커버리지(§3)와 내부 판정 규칙(§4)이다.

각인이 실제로 사는 자리는 셋뿐이다: **행 단위 귀속(공용 기기)** · **조인 없는
운영자 제외** · **쿼리 단순화**. 작지 않지만, 크게 말하지도 않는다.

## 2. 각인 설계 — 구현됨 (`functions/src/personAxisStamp.ts`)

### 2.1 키의 정확한 형태

```
events.userKey = "us_" + HMAC-SHA256(ANALYTICS_ID_SALT, "user:" + uid).hex[0:24]
```

- kind `user` · 솔트 `ANALYTICS_ID_SALT` — ★**새 kind 도 새 솔트도 만들지 않았다.**
  `analytics_user_install.user_key` / `analytics_purchase.user_key` 와 **한 글자도
  같은 값**이다(테스트가 고정: `personAxisStamp.test.ts` "★각인 값은 링크표·
  analytics_purchase 의 user_key 와 한 글자도 같다").
- 계산 위치: **Node 안에서만.** BQ 로 나가는 SQL·파라미터에 원시 uid 도 솔트도 없다.
- fail-safe 계승: 솔트가 없으면 원시값 폴백이 아니라 **각인 안 함**.

### 2.2 ★컬럼 이름이 `user_key` 가 아니라 `userKey` 인 이유

`events` 의 컬럼은 전부 camelCase 다(`userId`·`appVersion`·`projectId`·`taskId`·
`parentAgentId`). 그 표 안에서만 snake_case 를 쓰면 다음 사람이 "다른 데서 복사해
온 컬럼" 으로 읽는다. 조인은 별칭 한 줄이다: `e.userKey = l.user_key`.

★**이 철자 차이가 축 가드의 구멍 하나를 드러냈다** — §7 참조.

### 2.3 게이트가 **둘**인 이유

| 게이트                       | 묻는 것               | 값                             |
| ---------------------------- | --------------------- | ------------------------------ |
| `EVENTS_PERSON_STAMP_FROM`   | 기술: **컬럼이 있나** | unset = 각인 안 함(기본)       |
| `PERSON_AXIS_EFFECTIVE_FROM` | 법: **고지가 섰나**   | 이미 `2026-04-01` 로 켜져 있음 |

★후자를 재사용하지 않은 것이 이 설계에서 제일 실무적인 결정이다. 그 값은
**이미 프로덕션에 켜져 있어서**, 각인을 거기 매달면 머지하는 순간 존재하지 않는
컬럼에 스트리밍 insert 가 나가 `logTelemetryBatch` 가 배치째 실패한다 =
**텔레메트리 수집 중단.** 분석 기능 하나 때문에 제품 기능이 죽는 순서를 만들지 않는다.

코드 쪽 이중 방어: 게이트가 꺼져 있으면 행에 컬럼을 **언급조차 하지 않는다**
(`applyEventUserKeyStamp` 가 키를 넣지 않고 원본을 그대로 돌려준다). ALTER 전에
배포돼도 적재가 안 깨진다.

### 2.4 전환 시점을 **데이터에서** 읽는다

완료 기준의 _"전환 시점 이전/이후를 화면이 구분할 수 있는 근거가 데이터에 남는다"_
가 이 절이다. env 상수를 화면에 그리면 **배포가 밀렸을 때 화면이 거짓말을 한다**
(선언 ≠ 사실). 그래서 경계는 각인된 **첫 행의 시각**으로 읽는다:

`buildEventStampBoundarySql()` → `first_stamped_at` / `stamped_rows` /
`total_rows` / `stamped_people`, 파라미터는 `@since` 하나뿐.

`summarizeEventStampCoverage()` 가 `state: "off" | "stamping" | "complete"` 와
**선언값·실측값을 나란히** 실어 보낸다 — 둘이 갈라진 것을 화면이 볼 수 있다.
`stamping` 동안 퍼센트를 헤드라인으로 그리지 말라는 문장이 사유에 들어 있다
(선행 설계 §10.4-1 의 연장이다).

### 2.5 각인이 **닿지 않는** 곳 — 숨기지 않는다

| 못 하는 것                    | 왜                                                                                 | 크기                                                         |
| ----------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| ★미인증 텔레메트리            | `logAnonymousTelemetryBatch`(`index.ts:8007`)는 **auth 가 없다** — uid 자체가 없다 | 이벤트 축 사람 커버리지가 어느 설계로도 100% 가 안 되는 이유 |
| 과거 43만 행                  | forward-only                                                                       | 링크표 소급으로만 붙는다                                     |
| `agent_heartbeats`(1,450만행) | 삭제요청 비용이 25배                                                               | 각인 대상에서 제외                                           |
| 한 사람 여러 계정 병합        | 다른 uid = 다른 `user_key`                                                         | 미측정                                                       |

## 3. ★`analytics_identity` 로 이미 되는 것 / 안 되는 것 (실측)

BQ 직접 조회 2026-08-29.

| 조인/집계                                                     | 값                                                          | 뜻                            |
| ------------------------------------------------------------- | ----------------------------------------------------------- | ----------------------------- |
| `ga4_first_touch_current ⋈ analytics_identity` (`ga_key`)     | **550 / 593 = 93%**                                         | ★채널↔설치는 **된다**         |
| `analytics_identity ⋈ analytics_user_install` (`install_key`) | **4**                                                       | ★병목이 여기다                |
| 최근 30일 활동 설치 / 그중 링크됨                             | **10 / 4 = 40%**                                            | 정직한 분모로 본 커버리지     |
| 링크표                                                        | 5행 · user 4 · install 4 · 최초 `2026-08-21 11:42Z`         | 켠 지 8일                     |
| `analytics_identity`                                          | 593행 · `ga_key` 550 · ★**`ft_source` 0 · `ft_campaign` 0** | 컬럼은 있고 **데이터가 없다** |
| `ga4_first_touch_current`                                     | 863행 · 실 source/campaign **245**                          | 채널의 **정본은 여기다**      |
| `analytics_account_profile`                                   | 34행 · `is_admin` **1**                                     | §4 의 출발점                  |

### 3.1 되는 것 — 사장님 요구 ④는 배선이 이미 서 있다

```
analytics_user_install(user_key ↔ install_key)
  → analytics_identity(install_key ↔ ga_key)
  → ga4_first_touch_current(source · medium · campaign · content · term)
```

유입 **국가**는 별도 축이다 — `countryFunnel.ts` / `install_attribution` 이 든다.

### 3.2 안 되는 것 — **없는 절반이 무엇인가**

1. ★**링크 커버리지 4/10.** 이것 하나가 사장님이 보신 증상의 대부분이다.
   원인은 forward-only(8일 전 시작) + 잠자는 설치. 각인으로 **안 풀린다**(§1.3).
2. ★**`analytics_identity.ft_*` 가 비어 있다.** 오케 보고의 "절반이 이미 있다"는
   **컬럼 기준으로는 맞고 데이터 기준으로는 틀렸다.** 채널을 읽으려면
   `ga4_first_touch_current` 를 타야 한다. 저 빈 컬럼을 채울지(백필) 뷰로
   대체할지는 별건 판단이다 — 두 벌이 되면 조인이 조용히 갈린다.
3. **마케팅 웹사이트 ↔ 앱 계정.** 이건 정말로 없다. 그리고 그것을 여는 유일한
   길이 §5 다.

## 4. 내부 계정 판정 — 구현됨 (`functions/src/analyticsInternal.ts`)

### 4.1 지금 왜 오너 한 명만 잡히나

`analyticsProfiles.ts:1665` — `is_admin: adminUid !== "" && a.key === adminUid`.
`adminUid` 는 env `ADMIN_UID` **하나**다(`index.ts:14985`). 즉 melocream ·
datagadapida · 팀 추가 계정은 판정 근거 자체가 없다.

### 4.2 ★하드코딩하지 않는다 — 설정 두 소스의 **합집합**

| 순위 | 소스                                                         | 배포 필요   | 왜                                        |
| ---- | ------------------------------------------------------------ | ----------- | ----------------------------------------- |
| 1    | Firestore `config/analyticsInternal`                         | ★**불필요** | 계정이 늘 때마다 배포하지 않는다          |
| 2    | env `ANALYTICS_INTERNAL_UIDS` / `_EMAILS` / `_EMAIL_DOMAINS` | 필요        | 부트스트랩·비상용                         |
| 항상 | env `ADMIN_UID`                                              | —           | ★**폴백.** 설정을 못 읽어도 오너는 내부다 |

★합집합인 이유: Firestore 를 못 읽는 순간(권한·장애) 내부 판정이 조용히 0명이
되면 그 순간 KPI 가 낙관 편향되고 화면은 그걸 모른다. **fail-safe 는 "아무도 내부가
아님" 이 아니라 "최소한 오너는 내부" 다.**

★uid 를 소스에 박지 않는 두 번째 이유: 박으면 계정 식별자가 **git 히스토리에
영구히** 남는다.

### 4.3 판정은 boolean 이 아니라 (내부여부, **사유**)다

`InternalReason = "owner" | "listed_uid" | "listed_email" | "email_domain"`.

우선순위는 **좁은 규칙부터**다(owner → uid → email → domain). 넓은 규칙이 먼저
잡으면 "오너인데 도메인 때문에 빠졌다" 처럼 읽혀서, 목록을 고쳐도 왜 안 바뀌는지
설명이 안 된다.

★`email_domain` 은 편의이자 위험이다 — 도메인 하나를 잘못 넣으면 고객이 통째로
내부로 빠져 **분모가 조용히 줄어든다.** 그래서 사유를 남기고,
`summarizeInternalMatcher()` 가 규칙 종류별 개수를 따로 센다.

★이메일 비교 규약은 `normalizeEmail()` **한 곳**에만 있다. 설정에 적힌 값과 계정에
붙은 값이 같은 함수를 통과해야 `John.Kim@` 과 `johnkim+beta@` 가 같은 사람으로
잡힌다. gmail 계열만 점을 무시한다 — 다른 도메인에서 점을 지우면 **남을 잡는다**.

### 4.4 BQ 로 나가는 것은 `us_` 가명 배열 하나뿐

`deriveInternalUserKeys(uids, salt)` → 정렬된 고유 `us_` 키.
쿼리는 `WHERE userKey NOT IN UNNEST(@internalUserKeys)`.

★**새 표를 만들지 않았다.** 표를 만들면 두 축을 잇는 자리가 하나 더 생기고, 그
순간 _"링크표 하나 지우면 사람 축이 사라진다"_ 는 성질이 깨진다
(`personAxis.LINK_AXIS_TABLES` 주석). 내부 계정은 한 자릿수라 파라미터로 충분하다.

★**한계를 감추지 않는다:** 이메일·도메인으로만 잡힌 계정은 uid 를 모르므로
`user_key` 를 파생할 수 없다 = **그 규칙들은 이벤트 축 제외에 참여하지 못한다.**
`summarizeInternalMatcher().emailOnlyRules` 가 그 수를 센다. 테스트가 이 사실을
고정한다.

### 4.5 기존 `is_admin` 은 **지우지 않는다**

`is_admin` 은 배포된 컬럼이고 `includeAdmin` 토글이 그걸 필터로 쓴다
(`analyticsProfiles.ts` 스키마 주석: "새 운영자 판정 규약을 만들지 마라").
`is_admin`(=`ADMIN_UID` 하나)과 `is_internal`(=넓은 집합)은 **다른 질문**이라
컬럼도 다르다. 후자를 `analytics_account_profile` 에 더하는 것은 별건이다 —
이 티켓은 판정 규칙과 그 배선점까지만 만들었다.

## 7. ★축 가드에 구멍이 있었다 (막힌 게 아니라 안 보고 있었다)

티켓이 _"`assertAxisPurity` 를 우회하지 마라 — 막히면 그 사실이 설계 입력이다"_
라고 했다. **막히지 않았다. 그게 설계 입력이다.**

구멍 둘을 찾아 메웠다:

1. ★**원천 표가 어느 축 목록에도 없었다.** `ANONYMOUS_AXIS_TABLES` 는
   `analytics_user_daily`/`analytics_install_profile` 뿐이고 `events`·
   `task_outcomes`·`agent_heartbeats` 는 등재돼 있지 않았다. 등재되지 않은 표는
   가드가 **던지므로**, 원천 표에 대해 이 가드는 한 번도 돈 적이 없다.
   → `EVENT_AXIS_TABLES` + `FORBIDDEN_ON_EVENT_AXIS` 추가(`analyticsProfiles.ts:201`),
   `assertAxisPurity` 가 넷째 축을 판정한다.
2. ★**camelCase 철자가 금지 목록을 통과했다.** 가드는 컬럼명을 소문자화해 대조하는데
   `userKey` → `"userkey"` 는 `"user_key"` 와 **안 걸린다.** 각인 컬럼이 camelCase 라
   그 구멍이 이론에서 경로가 됐다.
   → 익명축에 `userkey`, 계정축에 `installkey`/`gakey`/`gaclientid`, 링크축에
   `ga_key`/`gakey` 추가. 테스트가 세 철자를 다 시도한다.

★**남긴 한계도 테스트가 들고 있다:** `events.userId` 는 못 막는다. 그 컬럼은
실재하고 값은 익명 설치 UUID(36자)인데, 이름만 보는 가드는 "여기 계정 uid 가
들어갔나" 를 볼 수 없다. 해소는 컬럼 개명(`telemetryIdentityAxis.USERID_COLUMN_RENAME`)
이고 별건이다. **한계를 알고 두는 것과 모르고 두는 것은 다르다** — 그래서 주석이
아니라 테스트에 적었다.

그리고 새 provisioning 스크립트가 ALTER **전에** 라이브 스키마 + 새 컬럼으로 가드를
돌린다. 2026-08-29 dry-run 통과 = 지금 `events` 에 금지 컬럼이 하나도 없다는 실측이다.

`WHERE userKey IS NULL OR userKey NOT IN UNNEST(@internalUserKeys)`.
그게 §4 의 배선점이고, 방침이 이미 약속한 _"통계에서 운영자 본인의 활동을 빼는 것"_
이다.

### 8.5 ★census 의 결론 — "전 탭 사람 축" 은 **지금은 못 한다**

- **이미 사람 축**: KPI 사람 수 3종 · 리텐션 사람 축 비교 · 수익 사람 축 뷰 = **3블록**
- **각인 후 가능**: `events` 를 읽는 블록 전부(획득 국가·활성화 퍼널·운영 3종) —
  단 **각인 이후 구간만.** 과거 43만 행은 링크표 소급으로만 붙는다.
- **사람 축으로 갈 이유가 없는 것**: CAC·광고비(**B**축), 릴리스 건강도(배포 축)
- **원리적으로 불가**: 미인증 이벤트(§2.5)

★그리고 어느 경우에도 **설치축 숫자와 사람축 숫자를 한 화면에 라벨 없이 두면 안
된다**(티켓 지시). 지금 실측이 정확히 그 위험이다: 활동 설치 **10** vs 링크된 사람
**4**. 라벨이 없으면 둘 다 거짓이 된다.
