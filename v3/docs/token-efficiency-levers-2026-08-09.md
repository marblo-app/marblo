## 1. 측정 방법과 신뢰 범위

먼저 이 표의 숫자를 어디까지 믿어도 되는지 못박는다. 이 프로젝트에서 `cost_logs` 는 반복해서 오독돼 왔다.

**측정 경로**: `gcloud auth application-default print-access-token` → BigQuery REST `jobs.query`.
프로젝트 `marblo-2253d`, 데이터셋 `marblo_telemetry`. 기간 = `CURRENT_TIMESTAMP() - 30 DAY`.

**반드시 붙는 단서**

1. **`cost_logs` 1행 = 15초 폴링 델타이지 "턴"이 아니다.** 행 수를 턴 수로 읽으면 오답이다. 이 문서에서 "폴(poll)"은 항상 이 15초 단위를 뜻하고, "요청(request)"은 실제 API 호출을 뜻한다. 한 폴에 요청이 몇 개 들어가는지는 직접 계측되지 않으므로 §3.3 에서 별도로 상·하한을 잡는다.
2. **`totalCost` 는 청구액이 아니라 list-price 로컬 추정치다.** 구독 정액제가 반영되지 않는다. 따라서 아래의 달러 값은 **비율을 보기 위한 축**이지 실지출이 아니다.
3. **전역 `SUM` 오염**: 세션파일 재읽기 중복이 존재하며 `taskId IS NULL` 행에 몰려 있다. 이 문서의 **태스크 단위 통계(§3.2)는 전부 `taskId IS NOT NULL` 로 한정**했다. 전역 합계(§3.1)는 오염을 포함하지만, 오염은 특정 성분(cache_read)에 편중되지 않으므로 **구성비 판단에는 사용 가능**하다 — 다만 절대액으로 읽지 말 것.
4. **단가 계수**는 코드에서 확인했다 (`v3/electron/cost-tracker.ts:767-768`): `cache_read = input × 0.1`, `cache_write = input × 1.25`. 모델 단가는 `v3/electron/model-registry.ts` (opus-5/opus-4.8 $5/$25, fable-5 $10/$50, sonnet-5 $3/$15, gpt-5.5 $5/$30).
5. **재계산 vs 적재값 차이**: 위 계수로 내가 재계산한 총액은 $20,303, 같은 모델 집합의 적재된 `SUM(totalCost)` 는 $18,091 (12% 차). 트래커가 일부 모델에 다른 단가를 썼다는 뜻이다. **구성비는 한 계수로 일관되게 계산했으므로 유효**하고, Claude 전용으로 좁혀도 결론이 바뀌지 않는다(§3.1 각주).

**계측 갭 (이번에 못 잰 것)**

- `cost_logs.sessionId` — 30일 전 행에서 **DISTINCT 0**. 세션 축 분석 불가.
- `cost_logs.taskType` — 전행 NULL.
- `agent:restarted`(969) / `agent:crashed`(865) 이벤트의 `agentId` 는 `cost_logs.agentId` 와 **거의 겹치지 않는다** (865개 중 12개만 조인됨). 재시작·크래시의 토큰 비용을 **정량화할 수 없다.** → §8 후속.

## 2. "98.4% 캐시 히트"가 감추는 것

오케 실측대로, 최근 30일 토큰 개수는 이렇다.

| 성분          |           토큰 | 입력측 비중 |
| ------------- | -------------: | ----------: |
| `cache_read`  | 24,089,793,552 |       96.9% |
| `cache_write` |    376,471,931 |        1.5% |
| 신규 입력     |    381,926,732 |        1.5% |
| (출력)        |    147,665,294 |           — |

`cache_read ÷ (cache_read + 신규입력)` = **98.44%** — 오케 수치와 일치한다. 히트율은 실제로 최적이다.

**그런데 캐시 히트는 토큰을 0으로 만들지 않는다. 0.1배로 만들 뿐이다.**
240억 토큰 × 0.1 은 여전히 24억 토큰어치 비용이다. 단가 가중을 하면 그림이 뒤집힌다.

### 비용 구성 (30일, list price 추정)

| 성분             | 추정 비용 |  **비중** |
| ---------------- | --------: | --------: |
| **`cache_read`** |   $12,146 | **59.8%** |
| 출력             |    $3,982 |     19.6% |
| `cache_write`    |    $2,506 |     12.3% |
| 신규 입력        |    $1,669 |      8.2% |
| 합계             |   $20,303 |      100% |

> Claude 모델(opus-5/4.8, fable-5, sonnet-5)만으로 좁힌 교차검증: `cache_read` **61.1%** / 출력 21.0% / `cache_write` 17.9% / 신규입력 **0.0%**. 결론 동일.

**해석.** 캐시 히트율을 98.4% → 100% 로 올려도 남는 절감은 신규입력 8.2% 중 일부뿐이다. **반면 `cache_read` 는 비용의 60%이고, 그 크기는 히트율이 아니라 다음 항등식으로 결정된다:**

```
cache_read 총량  =  Σ(요청마다 프리픽스 크기)  ≈  (평균 프리픽스 크기) × (요청 수)
```

**프리픽스 크기**와 **요청 수** — 이 둘이 진짜 레버다. 캐시는 이미 최적이므로 이 문서 어디에서도 캐시 설정을 건드리지 않는다.

### 재전송 증폭 계수

세션 전체에서 "새로 등장한 재료"는 `신규입력 + cache_write` 이고, 실제로 청구된 입력측 총량은 여기에 `cache_read` 가 더해진 값이다. 그 비율이 **재전송 증폭**이다.

```
전체:              24,089.8M ÷ (381.9M + 376.5M)  =  31.8배
claude-opus-5:     11,417.0M ÷ (0.23M + 226.2M)   =  50.5배
```

**Claude 워커는 컨텍스트 한 토큰당 평균 50번 다시 보낸다.** 프리픽스를 1토큰 줄이면 그 세션에서 50토큰이 절약된다는 뜻이다. 이 레버리지가 §7 추천의 근거다.

- **하한 (요청/폴이 동일하다고 가정)**: 부트는 매 요청 프리픽스의 **31%**
- **상한 (최소 폴 1요청, 전형 폴 2~3요청)**: **63~94%**

**예상 절감 계산**

```
프리픽스 감축률           = 22.3K / 53K            = 42%
부트가 요청 프리픽스에서 차지하는 비율 = 31% (하한) ~ 63% (상한)
cache_read 감축           = 42% × 31~63%          = 13% ~ 26%
총비용 감축               = 13~26% × 59.8%        = 7.8% ~ 15.8%
+ cache_write 동반 감소분 (프리픽스가 작아지면 재수립 비용도 비례)  ≈ +0.5~1.5%p
──────────────────────────────────────────────────────────────
총비용 절감 추정          = 8% ~ 17%
```

**구현 난이도: 중.** A1 은 MCP 서버가 이미 역할 개념을 갖고 있고(`tool-surface.ts` 에 `CODEX_ORCH_REQUIRED_MCP_TOOLS` 화이트리스트가 존재) `tools/list` 응답을 세션 역할로 필터링하면 된다. A2/A3 는 스폰 시 환경/설정 레벨 조정.

**리스크: 낮음.**

- 주된 위험은 "워커가 필요한 툴을 못 봐서 막히는 것". 완화: 화이트리스트를 넉넉히 잡고, `ask_orchestrator` 는 **반드시 남긴다**(막힘 보고 경로). 툴 목록은 설정 한 줄로 되돌릴 수 있다.
- A2 의 위험은 워커가 과거 함정(예: `selectinload` 규칙류)을 모른 채 같은 실수를 반복하는 것. 완화: 전역 인덱스 대신 **역할 스킬 안에 압축된 상시 주의사항**만 남긴다.
- ★프리픽스를 바꾸면 **기존 세션의 캐시가 한 번 깨진다.** 배포 직후 1회성 `cache_write` 스파이크가 나지만, §5 실측대로 재수립 비용은 작다(총비용의 1.4% 상한). 무시 가능.

### 4.2 (1b) 누적 트랜스크립트 — 더 크지만 더 어렵다

부트를 뺀 나머지(전형 프리픽스의 37~69%)는 누적 대화다: 파일 읽기 결과, 툴 출력, 어시스턴트 턴. 증가배수 3.19×(opus-5)가 이걸 말한다.

**중요한 제약**: 스폰된 Claude Code 워커의 트랜스크립트 압축은 **우리가 통제하지 않는다.** 하네스 내부 로직이다. 우리 통제면은 오직 **MCP 툴이 무엇을 돌려주는가** 다 — 그 응답은 트랜스크립트에 영구히 남아 이후 모든 요청에서 다시 읽힌다.

**측정**: `get_all_tasks` 응답 = 51개 티켓에 **9,280 바이트 (~2,650 토큰)**, 티켓당 1줄로 이미 압축되어 있다. 나쁘지 않다. 그러나 오케가 진행 상황 확인차 이걸 20번 호출하면 **~53K 토큰의 보드 스냅샷이 트랜스크립트에 쌓이고**, 그 대부분은 직전 호출과 거의 동일하다.

**조치 후보**

- B1: `get_all_tasks` / `get_task_activities` **델타 응답** — "직전 호출 이후 바뀐 티켓만 + 변경 없음 N건" 요약. 오케 세션에 집중.
- B2: 툴 응답에 명시적 크기 상한 + 절단 시 **소리 나는 절단**(몇 건 잘렸는지 반환). 조용한 절단은 이 레포가 이미 한 번 데인 실패 모드다(`task-listing.ts` 주석).

**예상 절감**: 오케(비용의 33.6%)의 누적분 중 보드 스냅샷 반복이 차지하는 비율을 보수적으로 30~50% 로 보면 **총비용 5~12%**. 단, 이 30~50% 는 **추정이지 실측이 아니다** — 툴 호출별 응답 크기가 계측되지 않아 지금은 잴 수 없다(§8).

**난이도: 중~상. 리스크: 중** — 오케가 보드 전체를 못 보면 판단 품질이 떨어질 수 있다. 델타 응답은 "변경 없음"을 명시적으로 말해줘야 안전하다.

## 5. 레버 3 — 캐시 만료(TTL) 재수립 · **실측 반증**

가설: 유휴 > 5분이면 캐시 TTL 이 만료되어 다음 요청이 프리픽스 전체를 `cache_write` 로 다시 쓴다 → 세션 warm 유지 또는 1시간 TTL 로 절감.

**직전 행과의 시간 간격별 `cache_write` 분포:**

| 직전 간격               |  행 수 | `cache_write` 합 | **행당 `cache_write`** |
| ----------------------- | -----: | ---------------: | ---------------------: |
| 첫 행                   |  1,503 |             2.6M |                  1,723 |
| **≤ 60초 (활동 중)**    | 51,010 | **330.2M (88%)** |              **6,474** |
| 60–300초                | 47,399 |            28.5M |                    602 |
| **5분–1시간 (유휴 후)** | 42,179 |             8.0M |                **190** |
| > 1시간                 |  7,949 |             7.1M |                    898 |

**가설과 정반대다.** `cache_write` 의 88% 는 에이전트가 **쉬지 않고 일하는 중**(간격 15초)에 발생하고, 5분 이상 쉰 직후 행은 오히려 행당 `cache_write` 가 **최저(190)** 다. 이건 TTL 만료 재수립이 아니라 **매 턴 새 내용을 캐시에 덧붙이는 정상적인 증분 캐싱**이다.

큰 쓰기(≥200K)만 따로 보면 유휴와의 상관이 나타나긴 한다:

| `cache_write` 크기 |   행 수 |      합계 | 직전 간격 중앙값 | 5분 유휴 직후 비율 |
| ------------------ | ------: | --------: | ---------------: | -----------------: |
| 0                  | 113,110 |         0 |             300s |              44.2% |
| < 10K              |  30,305 |     99.8M |              15s |               0.2% |
| 10–50K             |   5,260 |    100.7M |              15s |               0.1% |
| 50–200K            |   1,275 |    132.8M |              15s |               1.2% |
| **≥ 200K**         |  **98** | **43.2M** |             104s |          **27.6%** |

**절감 상한**: 유휴 상관이 있는 구간은 `cache_write` 총량의 **11.5%(43.2M/376.5M)** 뿐이고, 그중에서도 유휴 기인은 27.6%. `cache_write` 는 비용의 12.3% 이므로

```
최대 절감 = 11.5% × 12.3% = 총비용의 1.4%   (그마저 전부 회수 가정 시)
```

**판정: 추진 안 함.** 1시간 TTL 은 `cache_write` 단가를 1.25× → 2× 로 올리므로, 88% 를 차지하는 활동 중 증분 쓰기 비용이 **60% 증가**한다. 1.4% 를 벌러 가서 7% 를 잃는다. 세션 warm 유지(하트비트 요청)도 유휴 요청 자체가 프리픽스 전량 `cache_read` 를 발생시키므로 **순손실**이다.

## 6. 레버 4 — 프리픽스 안정성 (모델 스위치·재시작)

### 6.1 모델 스위치 — 실측됨, 그러나 작다

한 `agentId` 가 세션 중 2개 모델을 쓰면 캐시가 깨진다. Claude 모델만 쓴 에이전트로 한정해(gpt 는 `cache_write` 를 0으로 보고하므로 섞으면 오염) 비교:

| 사용 모델 수 | 에이전트 |     폴 | `cache_read` | `cache_write` |    **`cw`/`cr`** |
| ------------ | -------: | -----: | -----------: | ------------: | ---------------: |
| 1개          |      447 | 96,208 |      10,039M |        197.9M |        **1.97%** |
| 2개          |      410 | 36,982 |       6,280M |        176.3M | **2.81%** (+43%) |

전체 모델 포함 시 격차는 더 크다 — 폴당 `cache_write`: 1모델 1,782 / 2모델 6,807 / 3모델 9,900.

**실재하는 효과다.** 그러나 규모:

```
초과분 = 6,280M × (2.81% - 1.97%) = 52.8M cache_write
       = 전체 cache_write 376.5M 의 14%
       = 총비용 12.3% × 14%     = 총비용의 1.7%
```

**판정: 단독 추진 안 함.** 다만 **비용이 0인 위생 규칙**은 채택할 만하다 — "세션 중간 모델 스왑을 피하고, 바꿔야 하면 새 에이전트로 시작한다". 어차피 스왑은 캐시를 깨므로 재사용의 이득이 없다. 이미 `request_model_escalation` 이 티켓당 1건으로 제한되어 있어 구조적으로도 억제되어 있다.

> 상관≠인과 단서: 2모델 에이전트가 원래 더 길거나 더 어려운 작업일 수 있다. 다만 분모를 `cache_read` 로 잡아 세션 길이를 정규화했으므로 길이 효과는 대체로 제거된다.

### 6.2 재시작·크래시 — **정량화 불가 (계측 갭)**

30일간 `agent:restarted` 969건 / `agent:crashed` 865건. 스폰 이벤트 4,227건 대비 **43%** 다. 재시작은 세션 재개 = 프리픽스 재수립이므로 원리상 비싸다.

**그런데 잴 수가 없다.** 크래시/재시작 이벤트의 `agentId` 865개 중 `cost_logs` 에 나타나는 것은 **12개뿐**이다. 두 가지 해석이 가능하다: (a) 재시작 시 새 `agentId` 가 발급되어 이력이 끊긴다, 또는 (b) 크래시한 에이전트는 토큰을 만들기 전에 죽는다. 어느 쪽인지 이 데이터로는 구분 불가.

관련 정황: 스폰 이벤트 4,227 vs 고유 스폰 `agentId` 2,380 → **에이전트당 1.78회 스폰**(재개/재스폰). 그리고 스폰된 2,380개 중 **1,503개만 토큰을 남겼다** — 877개(37%)는 무산출.

**추정치를 지어내지 않는다.** §8 에 계측 요구사항으로 남긴다.

## 7. 레버 2 — 턴 수, 그리고 최종 추천

### 7.1 턴 수 레버의 위치

요청 수는 `cache_read`(59.8%) + `cache_write`(12.3%) + 출력(19.6%) = **비용의 92%** 에 곱해지는 계수다. 원리상 가장 큰 레버다. 실측된 재전송 증폭 50배가 그 지렛대다.

**하지만 이번 조사에서 "낭비된 턴"을 특정하는 실측치를 얻지 못했다.** 태스크당 에이전트 1개(96%), 세션 길이 분포 정상, 팬아웃 없음 — 구조적 낭비의 지문이 안 보인다. 턴 수를 줄이려면 에이전트의 행동(툴 호출 습관, 파일 재읽기)을 바꿔야 하고, 그건 품질 저하 리스크가 직결된다.

**따라서 턴 수는 "다음 스파이크에서 계측부터"로 미룬다** (§8). 지금 아는 것만으로 행동을 바꾸면 근거 없는 추측이 된다.

그 대신 **프리픽스 크기**는 같은 50배 지렛대에 올라타면서도 품질 리스크가 없다 — 워커가 절대 호출하지 않는 33개 툴 스키마를 지우는 것은 능력을 깎지 않는다.

### 7.2 추천

**★1순위 — 워커 부트 프리픽스 다이어트 (§4.1)**

- 조치: 역할별 MCP `tools/list` 스코핑(A1) + 메모리 인덱스 주입 범위 축소(A2) + 스킬 목록 역할 스코핑(A3)
- **예상 절감: 총비용 8~17%**
- 난이도 중 / 리스크 낮음 / 되돌리기 쉬움 / 품질 영향 없음
- 근거의 강도: **강함.** 부트 프리픽스 106K vs 16.8K 는 직접 실측, 정적 재고 32K 도 직접 실측, 증폭 50배도 직접 실측. 유일한 추정 구간은 "요청/폴" 하나이고, 그것도 상·하한을 모두 계산해 범위로 제시했다.
- 검증법: 배포 후 `claude-opus-5` 의 에이전트별 최소 단일-폴 `cache_read` p50 이 105.7K → 목표치로 내려가는지 확인. **단일 지표로 즉시 판정 가능하다.**

**2순위 — MCP 응답 델타화 (§4.2 B1)**

- 조치: `get_all_tasks` / `get_task_activities` 를 "직전 호출 이후 변경분 + 무변경 N건" 형태로
- **예상 절감: 총비용 5~12%** (단, 오케 트랜스크립트 내 보드 스냅샷 비중이 추정치임 — 먼저 §8-C 계측 권장)
- 난이도 중~상 / 리스크 중 (오케 판단 근거 축소)

**추진하지 않음**

| 레버                      | 상한 | 사유                                                               |
| ------------------------- | ---: | ------------------------------------------------------------------ |
| 캐시 TTL / 세션 warm 유지 | 1.4% | 실측 반증 — `cache_write` 88%가 활동 중 증분. 1h TTL 은 순손실(§5) |
| 모델 스위치 방지          | 1.7% | 실재하나 소액. 무비용 위생 규칙으로만 채택(§6.1)                   |
| 캐시 히트율 개선          |  ~0% | 이미 98.4%. 지시대로 손대지 않음                                   |

**두 추천을 합치면 총비용 13~29% 절감**이 상한 범위이나, 1순위만 단독 실행해도 **8~17%** 를 확보하며 이쪽 근거가 훨씬 단단하다. **1순위 먼저, 실측 확인 후 2순위.**

## 8. 후속 — 지금은 못 재는 것들

이 조사에서 추정에 의존해야 했던 지점들이다. 각각 계측을 붙이면 다음 스파이크는 추측 없이 끝난다.

- **(A) 요청/폴 비율** — `cost_logs` 가 15초 델타만 남겨서 실제 API 요청 수를 모른다. §3.3 의 31%↔63% 범위가 전부 여기서 나온다. **요청 카운터 하나면 이 문서의 절감 추정치가 범위에서 점 추정으로 바뀐다.**
- **(B) 재시작·크래시의 토큰 비용** — 라이프사이클 이벤트의 `agentId` 가 `cost_logs.agentId` 와 조인되지 않는다(865 중 12). 재시작 시 id 승계 규칙을 확인하고 잇는다. 43%라는 발생률이 사실이면 §6.2 는 1순위 후보가 될 수도 있다.
- **(C) MCP 툴 호출별 응답 바이트** — 어느 툴이 트랜스크립트를 부풀리는지 모른다. 2순위 추천의 절감폭이 여기 달려 있다. `tools/call` 응답 길이를 이벤트로 남기면 된다.
- **(D) `sessionId` 사망** — 30일 전행 NULL. 세션 축 분석이 통째로 불가능하다.
- **(E) `taskType`** — 전행 NULL. 태스크 유형별 토큰 프로파일을 못 낸다.

```sql
WITH a AS (
  SELECT agentId, ANY_VALUE(model) model, COUNT(DISTINCT model) nm,
    MIN(IF(cacheReadTokens>0, cacheReadTokens, NULL)) min_cr,
    APPROX_QUANTILES(IF(cacheReadTokens>0,cacheReadTokens,NULL),4)[OFFSET(2)] med_cr,
    COUNT(*) polls
  FROM `marblo-2253d.marblo_telemetry.cost_logs`
  WHERE timestamp >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
  GROUP BY agentId)
SELECT model, COUNT(*) agents,
  APPROX_QUANTILES(min_cr,10)[OFFSET(5)] boot_p50,
  APPROX_QUANTILES(med_cr,10)[OFFSET(5)] typical_p50,
  ROUND(APPROX_QUANTILES(SAFE_DIVIDE(min_cr,med_cr)*100,10)[OFFSET(5)],1) boot_pct
FROM a WHERE nm=1 AND min_cr IS NOT NULL AND polls>=20
GROUP BY model HAVING COUNT(*)>=10 ORDER BY agents DESC;
```
