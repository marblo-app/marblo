### 2-C. ★"로그인 없이"의 정직한 해석

티켓은 "유저는 로그인 없이 동작"이라고 적었다. 절반만 맞다.

| 없앨 수 있는 것                                                  | 못 없애는 것                                                   |
| ---------------------------------------------------------------- | -------------------------------------------------------------- |
| Claude/Codex **구독** — 없어도 동작한다 ★이게 이 안의 전부다     | **미터링 신원** — 누구에게 얼마를 줬는지 모르면 한도를 못 건다 |
| `claude login` **CLI 인증 플로우**(브라우저 왕복, 토큰 붙여넣기) | 익명 Firebase auth 수준의 device 계정(1클릭, 화면 없음도 가능) |
| 유저가 **키 문자열을 다루는 일**                                 | 우리 백엔드가 토큰을 발급하는 왕복 1회                         |

이건 #868 §2-B 가 오카 대비 지적한 것과 **같은 구조**다: 클라우드는 설치·인증을 없애지만 계정 게이트는 오히려 강제한다. 여기서도 **순 마찰 감소는 "구독+CLI인증 − 익명계정"** 이지 "구독+CLI인증" 이 아니다. 다만 익명 auth 는 화면 없이 통과시킬 수 있어서 체감 비용이 훨씬 작다.

**그리고 신원 없이 가면 안 되는 결정적 이유**: 앱에 정적 토큰을 박으면 우리 엔드포인트는 **인터넷에 공개된 무료 LLM API** 가 된다(§8).

## 3. ★우리 워크로드의 진짜 모양 — 원가 산식을 지배하는 사실 [BQ]

무료 티어 원가를 추정하려면 "태스크 1건이 토큰을 얼마나 태우나"를 알아야 한다. 실측했다.

`cost_logs` 를 `taskId` 로 그룹(n=**1,371** 태스크):

| 분위              | 총입력(캐시 포함) |  출력 | 실측 비용(프론티어, list price) |
| ----------------- | ----------------: | ----: | ------------------------------: |
| p25 (작은 태스크) |         **2.33M** | 15.9k |                       **$1.79** |
| **중앙값**        |         **7.39M** | 60.1k |                       **$5.25** |
| p75               |             17.9M |  124k |                          $12.59 |
| 최대              |             97.4M |  507k |                          $73.25 |

평균 분해(태스크당): 순수 입력 74.3k · **캐시 재읽기 11.9M** · 캐시 쓰기 249k · 출력 79.0k.

**★여기서 나오는 두 가지 구조적 결론**

1. **우리 워크로드는 입력이 99.2%다.** 중앙값 기준 입력:출력 = **123:1**. 원인은 결함이 아니라 에이전트 하네스의 정의다 — 매 턴 시스템 프롬프트 + MCP 툴 정의(라이브 41개) + 누적 대화 + 파일 내용을 통째로 다시 보낸다.
2. **그래서 "SLM 은 출력 단가가 싸다"는 우리에게 거의 무의미하다.** 우리가 사야 하는 건 **싼 입력(prefill)** 이다. 그런데 Anthropic 은 캐시 재읽기를 입력가의 10% 로 청구하는 반면, 오픈웨이트 서버리스는 **할인이 없거나(DeepInfra) 50%(Fireworks·Groq)** 다. → **헤드라인 per-token 비가 그대로 절감비가 되지 않는다.** 실효 절감은 §5 대로 **4.5\~9배**지 50배가 아니다.

> **[정직성]** 이 분포는 **프론티어 모델이 만든 워크로드**다. SLM 은 컨텍스트 창이 작고 더 일찍 실패하므로 태스크당 토큰이 이보다 **작을** 수 있고(완주 못 해서), 반대로 재시도가 늘어 **클** 수도 있다. §5 는 이 분포를 **상한 가정**으로 쓴다.

## 6. 자체 GPU 호스팅 vs 서버리스 — 손익분기 [추정]

| 항목                                              | 값                                                        |
| ------------------------------------------------- | --------------------------------------------------------- |
| 32B fp8 서빙에 필요한 GPU                         | H100 80GB **1장**(가중치 ≈32GB + KV 캐시). 70B fp8 은 2장 |
| H100 1장 월 고정비                                | **$1,433**(RunPod community) \~ $5,040(Fireworks)         |
| 같은 돈으로 살 수 있는 서버리스 입력 토큰(@$0.08) | **17.9B 토큰/월**                                         |
| 그걸 GPU 로 만들려면 필요한 지속 처리량           | **≈6,800 tok/s 를 24/7** (prefill 기준)                   |
| 데모캡 유저로 환산                                | **월 ≈11,900명**을 **가동률 100%** 로 태워야 손익분기     |

**결론: 자체 GPU 는 지금 규모에서 명백히 진다.** 이유 셋 —

1. **고정비 vs 0**: 서버리스는 유저 0명이면 $0. GPU 는 유저 0명이어도 월 $1,433 이다. 무료 티어 트래픽은 정의상 **버스티**하다.
2. **가동률**: 위 손익분기는 **100% 가동** 가정이다. 실제 무료 티어 가동률이 20% 라면 손익분기는 월 6만 명으로 밀린다.
3. **운영 부담**: vLLM 튜닝·프리픽스 캐시·OOM·모델 업데이트·GPU 장애가 **1인+에이전트 팀의 상시 부담**이 된다(#868 §3-D 와 같은 결론).

**자체 호스팅이 이기는 유일한 지점**: 우리 워크로드가 **같은 프리픽스를 반복**하므로 vLLM automatic prefix caching 이 아주 잘 듣는다(실사례: Qwen2.5-32B/H100 에서 정상상태 히트율 ≈94%) — 서버리스가 캐시 재읽기를 **정가로** 청구하는 것과 대비되는 우리 쪽 구조적 이점이다. 하지만 그 이점은 **GPU 를 이미 채우고 있을 때만** 현금이 된다. → **월 1만 명 무료유저를 넘긴 뒤 재검토**(§11 보류 항목).

## 7. 품질 리스크 — SLM 을 어느 역할에 쓸 것인가

### 7-A. 우리 하네스가 모델에 요구하는 것 [코드/메모]

- Anthropic `tool_use` 스키마를 **정확히** 지킬 것(형식이 틀리면 CLI 가 루프를 못 돈다)
- MCP 툴 **40개+**(그록 라이브 41개 실측)를 매 턴 시스템 컨텍스트로 들고 갈 것
- 수십 턴의 도구 루프에서 **드리프트 없이** 목표를 유지할 것
- 실패에서 **복구**할 것(잘못된 패치 → 테스트 red → 재시도)

이건 채팅 벤치(MMLU 류)가 측정하지 않는 능력이다.

### 7-B. 근거 — 작은 모델은 여기서 무너진다

| 근거                                                                                                                          | 출처                                                                              |
| ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **우리 실측**: 프론티어급인 **gpt·grok 도 복잡 in-repo 코딩에서 무산출**. 오케·조사·단순 작업은 OK                            | 메모 `spawn_model_pref_codex_grok_save_claude`·`grok_orchestrator_and_byom_stack` |

| 오픈웨이트가 따라잡은 축은 대형(DeepSeek V4·Kimi K2.6·Qwen3.6-Plus)이지 **7\~32B 급이 아니다**                                | [출처] mindstudio 2026                                                            |

**즉: 32B 급으로 "무료 자율 오케"를 주면, 유저가 처음 보는 마블로가 *조용히 틀린 일을 열심히 하는 팀*이 된다.** 첫인상 제품에서 이건 최악의 실패모드다 — 에러보다 나쁘다.

### 7-C. ★역할 분리 권고 (이 문서의 핵심 산출물 중 하나)

| 역할                           | SLM 으로 되나         | 왜                                                                     | 무료 티어에서 어떻게                                  |
| ------------------------------ | --------------------- | ---------------------------------------------------------------------- | ----------------------------------------------------- |
| **오케(분해·라우팅·머지판단)** | ✕ **금지**            | 가장 어렵고, **실패가 조용하다**. 잘못된 분해는 하류 전부를 낭비시킨다 | **사전 제작**: 데모 티켓을 우리가 미리 쪼개 놓는다    |
| **에이전트 — 좁은 첫 티켓**    | ✅ **여기가 쓸 자리** | 스코프가 좁고 검증이 명확(테스트 1개 통과, 파일 1\~2개)                | SLM 1기. 이게 "가치 체감"의 전부                      |
| 에이전트 — 실 유저 레포 작업   | ✕ 무료 범위 밖        | §7-B. 게다가 abuse·프롬프트 인젝션 표면(§8)                            | 유료(자기 구독) 로 인계                               |

**보강 사실**: `planLimits.ts` 상 **free 플랜은 이미 `hasOrchestrator: false`** 다. 즉 "무료유저에게 자율 오케를 주지 않는다"는 **이미 제품 정책**이고, 이 권고는 그것과 충돌하지 않는다 — 오히려 정합한다.

**그래서 무료 티어의 정직한 스코프**: \*"완전 자율 오케"가 아니라 **"미리 쪼개진 첫 티켓 1건을 에이전트가 실제로 완료하는 것을 눈으로 보는 것"\*** — 티켓이 제안한 "첫 작업 데모·가치체감까지" 라는 스코프는 **현실적이다. 지지한다.**

## 8. 한도 · abuse 방어

### 8-A. 위협모델 — 왜 이게 남의 얘기가 아닌가

우리 엔드포인트는 **Anthropic 호환 API** 다. 앱에 정적 토큰을 박는 순간 그것은 **"인증 불필요한 공개 LLM API"** 가 된다 — 추출은 자명하고, 재판매 봇의 표적이다. 우리 워크로드 기준 **태스크 1건 = 7M 토큰**이니, 스크립트 하나가 시간당 수십 달러를 태울 수 있다.

### 8-B. 통제 (전부 **서버측**. 클라이언트 통제는 통제가 아니다)

| #   | 통제                                                                                                      | 막는 것                          |
| --- | --------------------------------------------------------------------------------------------------------- | -------------------------------- |
| C1  | **정적 토큰 금지** — 백엔드가 `installId` 별 **단명 토큰(≤24h)** 발급. 익명 auth + **Firebase App Check** | 토큰 추출 후 무한 사용           |
| C2  | 클라이언트 저장은 기존 **safeStorage 벤더 시크릿 축** 재사용(`vendor-secrets.ts`)                         | 평문 유출                        |

### 8-C. 남는 구멍 (정직하게)

- 익명 계정은 **재발급이 싸다**. installId 를 지우고 다시 받으면 새 쿼터다. 완전 차단은 결제수단 등록뿐인데, 그건 이 안의 존재 이유(제로마찰)를 죽인다. → **감수한다. 대신 C6 전역 상한이 손실을 유한하게 만든다.**
- 유저 코드는 **유저 맥에서** 돈다(우리 컨테이너가 아니다). 그래서 #868 이 안고 있던 임의코드실행·테넌트 격리·egress 위협이 **이 안엔 아예 없다.** ★이 안의 가장 큰 구조적 장점이다.

| 보안 표면        | **작다**(코드가 우리 인프라에 안 옴)   | 작다                               | 없음                   | **최대**(임의코드실행이 제품 기능)              |
| 품질 상한        | **낮다**(SLM) — 데모까지               | 유저 선택(프론티어 가능)           | 유저 선택              | 프론티어 가능                                   |
| 언제             | **첫 접촉 · 구독 없는 사람**           | 첫 접촉 후 **지불 의사 있는 사람** | 이미 구독 있는 사람    | **설치 자체를 안 하는 사람**                    |

**★겹치지 않는다 — 겨냥하는 사람이 다르다.** A 는 "설치는 했는데 구독이 없어서 못 쓰는 사람", D 는 "설치를 아예 안 하는 사람", B 는 "돈은 낼 텐데 구독을 새로 만들기 싫은 사람". 셋 중 **A 가 가장 싸고 표면이 가장 작다** — 컴퓨트를 안 옮기기 때문이다.

**그러나 A 와 D 는 같은 예산·같은 분기의 경쟁자다.** 둘 다 하지 말 것. §11 이 순서를 정한다.

## 13. 한계 · 정직성

- **§5 의 모든 원가는 [추정]이다.** 단가는 공시가 실측이고 토큰량은 BQ 실측이지만, **둘을 곱한 것은 가정**이다. 특히 SLM 이 만드는 토큰 분포는 프론티어가 만든 §3 분포와 **다를 것이다**(§3 각주) — P1-5 가 실측한다.
- **§3 의 분포는 사실상 오너 1인의 사용 패턴**이다. 메모 `admin_exclude_johnkim_external_zero_value_2026_07` 대로 외부 실사용이 ≈0 이라, 이 분포가 "신규 무료유저의 첫 태스크"를 대표한다는 보장은 없다. 그래서 §5-A 는 별도로 **데모캡** 행을 두었다.
- **캐시 할인 가정이 보수적이다.** DeepInfra 의 캐시 입력 할인 여부를 공시에서 확인하지 못해 **할인 0%** 로 계산했다. Fireworks·Groq 의 50% 가 적용되면 총원가는 최대 절반이 된다.
- **게이트웨이를 라이브로 검증하지 않았다.** GLM/MiniMax/Kimi 는 **벤더가 준** Anthropic 호환 엔드포인트였다. 우리가 **번역기를 끼워** claude CLI 를 완주시킨 적은 **없다.** 이것이 이 문서의 최대 미지이고, R1 이다.
- **§6 의 GPU 처리량(6,800 tok/s)은 자릿수 추정**이다. 실측 벤치가 아니라 "H100 1장 32B fp8 prefill" 의 통상 범위에서 잡았다. 자체 호스팅을 실제로 검토할 때는 실벤치가 선행이다.
- **품질 판정은 2차 출처 + 우리 내부 메모**다. 우리가 32B 급 모델을 **우리 하네스로** 돌려 본 적이 없다(로컬 Ollama 축은 배선만 착지, 완주 실측 없음 — 메모 `local_model_rides_env_swap_axis`). P1-1 이 이 판정을 처음 실측한다.
- **§11 의 "30%" GO 임계는 제안이지 도출된 값이 아니다.** 사장님/오케가 조정할 값이다.
- **ToS·마진(B안)은 이 문서가 판단하지 않았다** — `OF2wawHo` 가 정본이다.
- 날조 없음. 벤더 수치는 §14 URL 을 직접 열어 읽었고, 코드 인용은 파일·행으로 확인 가능하며, BQ 수치는 §14 의 쿼리로 재현 가능하다.

WITH t AS (
  SELECT taskId,
         SUM(inputTokens) + SUM(cacheReadTokens) + SUM(cacheWriteTokens) AS tin,

         SUM(totalCost)    AS c
  FROM `marblo-2253d.marblo_telemetry.cost_logs`

  GROUP BY taskId

SELECT COUNT(*) n,
       APPROX_QUANTILES(tin, 4) q_in,
       APPROX_QUANTILES(o,   4) q_out,
       APPROX_QUANTILES(c,   4) q_cost
FROM t;
