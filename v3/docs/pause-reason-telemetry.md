## 왜 있나

**떠나는 사람은 실패해서 떠나지 않는다.** 173 task 를 하고 떠난 설치는 마지막 이틀 33/33 성공, `agent:crashed` 0, `errorCategory` 전부 NULL, 마지막 이벤트가 정상 종료였다. task 에 도달한 설치 7개 중 6개가 첫 시도에 성공했고 그중 3개는 1~2일 만에 사라졌다.

즉 **성공률·실패율·첫 성공 시간에는 이탈 신호가 없다.** 그리고 그 신호는 앱 안에 애초에 없으므로 BigQuery 를 아무리 더 봐도 나오지 않는다. 그래서 직접 묻는다.

| 코드             | 문구                             | 이 답이 나오면                     |
| ---------------- | -------------------------------- | ---------------------------------- |
| `no_need`        | 바빴거나 마블로로 할 일이 없었다 | 제품 문제가 아니다. 수요 타이밍    |
| `other_tool`     | 다른 도구로 같은 일을 했다       | 대체재에 졌다 — 가장 전략적인 신호 |

★`no_need` 를 맨 앞에 둔 것은 의도다. 제품 탓 선택지를 위에 깔면 "뭐가 문제였냐" 고 유도하는 문항이 된다.

## 이벤트 스키마

`events` 테이블, `event = 'retention:pause_reason'` 한 종류. `metadata` JSON:

| 키              | phase               | 값                                          |
| --------------- | ------------------- | ------------------------------------------- |
| `phase`         | 전부                | `shown` · `answered` · `dismissed` · `note` |
| `gapDays`       | 전부                | 마지막 실행 이후 공백(일, 내림)             |
| `reason`        | `answered` · `note` | 위 코드 6종                                 |
| `noteLength`    | `note`              | 한 줄의 길이(글자수)                        |
| `noteDelivered` | `note`              | 그 한 줄이 실제로 전달됐는가                |

- **집계는 `phase='answered'` 만 센다.** 그 행은 사람당 정확히 한 번 난다(메모를 보낸 사람이 두 번 세어지지 않게 후속 결과를 `note` 로 뺐다).
- **`shown` 이 분모다.** 이게 없으면 "답 0건" 이 미노출인지 무응답인지 갈리지 않는다 — 활성 설치가 한 자릿수인 지금 그 구분이 답 자체보다 중요하다.
- **산문은 이 이벤트에 없다.** `scrub.ts` 의 `USER_INPUT_KEY` 가 free-form note 를 스펙상 전면 차단한다. 한 줄 메모는 `submitPauseReason` callable → Firestore `pauseReasons/{uid}` 로만 간다(계정당 1건, 클라이언트 접근 전면 차단).

## ★잔존 계산 오염

이 이벤트는 `KPI_RETENTION_EXCLUDED_EVENTS`(`functions/src/index.ts`)에 **등록돼 있어야 한다.**

코크핏 잔존 CTE 는 (프로젝트×날짜) 조합 수로 세션을 근사하는 **전량 스캔**이다. 이 이벤트는 정의상 "멈췄다가 돌아온 날" 에만 발화하므로, 빼지 않으면 **"저는 멈췄었습니다" 라고 답한 그 행동이 잔존 세션 한 칸으로 계상된다.** 부호가 뒤집힌 오염이고, 이탈을 물을수록 잔존이 좋아 보이게 된다.

퍼널 쪽 `FUNNEL_EVENTS_EXCLUDED_FROM_RETENTION` 에는 **넣지 않는다** — 그쪽 raw CTE 는 `event IN (퍼널 목록)` 으로 이미 닫혀 있어 이 이벤트가 스캔에 들어오지 않는다. 등록/미등록 둘 다 `tests/unit/pauseReasonSurfaceParity.test.ts` 가 지킨다.

## 읽는 법 (n=5 를 전제한다)

```sql
-- 노출 대비 응답, 그리고 사유 tally. 백분율을 쓰지 마라 — 분모가 한 자릿수다.
SELECT
  JSON_VALUE(metadata, '$.phase')  AS phase,
  JSON_VALUE(metadata, '$.reason') AS reason,
  COUNT(DISTINCT userId)           AS installs
FROM `marblo-2253d.marblo_telemetry.events`
WHERE event = 'retention:pause_reason'
GROUP BY phase, reason
ORDER BY phase, installs DESC;
```

읽는 순서: ① `shown` 몇 건인가(문항이 도달은 했나) → ② `answered` / `dismissed` 로 갈렸나 → ③ 사유가 어디에 몰렸나. 한 칸이 0 이냐 1 이냐도 의미가 있다. 산문은 Firestore `pauseReasons` 컬렉션에서 직접 읽는다(콘솔).

## 이 계측이 답할 수 **없는** 것

- ★**영영 안 돌아온 설치.** 앱이 화면을 띄울 수 없으므로 도달 불가다. #1310 이 관측한 즉시 소멸 설치(E·F·G)가 여기 해당하고, 그 구간은 복귀 안내 메일 경로(커밋 `87323489`)의 몫이다. 여기 모이는 것은 이탈자 전수가 아니라 **일시정지자 표본**이다.
- **왜 그 사유였는지.** 6칸은 방향을 가리킬 뿐 원인을 설명하지 않는다.
- **응답률의 대표성.** 한 자릿수 표본에 통계는 없다.

## 첫 성공·실패율은 어떻게 됐나

**내리지 않았다. 진단용으로 강등했다**(`getAdminKpiCockpit` 의 `zeroFriction` 주석에 근거를 못박아 뒀다).

두 지표의 판별력은 이 표본에서 0 이지만 — (1) n=7 에서의 관측이지 증명이 아니고, (2) #1310 처방 3의 **반증조건 자체가** "다음 이탈자가 마지막 3 활동일에 `errorCategory` 상승 또는 `agent:crashed` 급증을 보이는가" 라 그 관측을 지우면 그 처방을 반증할 길이 함께 사라진다. 계속 재되, **"첫 성공이 빨랐으니 정착한다" 로 읽지 마라.**
