## 0. 사장님께 — 다섯 줄

1. **비기너가 깔끔한 건 탭을 덜어내서가 아닙니다.** 탭 차이는 13개 → 9개, **4개뿐**입니다(§1).
2. 진짜 이유는 비기너 폴더의 **파일 11개가 같은 시각 어휘 한 장을 공유**한다는 것입니다(`beginnerUi.tsx`). 마블로 모드에는 그 공유가 없습니다 — **파일 75개가 각자 색을 칩니다**(§2).
3. ★**그런데 그 "한 장" 은 이미 앱 전체에 있습니다.** 8/22 에 `tailwind.config.js` + `index.css` 로 머지됐습니다(#1134). **쓰이는 곳이 32번, 손으로 친 색이 2,362번입니다** — 그중 **2,052번(86.9%)이 이미 정의된 토큰과 글자까지 똑같은 값**입니다(§2-2).
4. 그래서 이건 **디자인 문제가 아니라 채택 문제**입니다. 새로 그릴 게 없습니다. 있는 걸 안 쓰고 있을 뿐입니다. 리디자인 없이, 파일 단위로, 매일 배포하면서 좁힐 수 있습니다(§5).
5. **오케브레인 패널이 그 증거입니다.** 토큰이 머지되고 **3시간 56분 뒤에** 머지됐는데, 토큰을 0번 쓰고 색을 70번 직접 쳤습니다(§4).

### 4-2. 접힘 한 줄 — 필요한 것만 담았는가: **거의. 한 칸이 남는다**

접힘 줄(`:391-443`) 구성: `제목`(`:392`) · `열림N·준비M`(`:397`) · `▶ 다음 항목`(`:404`) · `+ 항목 적기`(`:426`) · `펼치기/접기`(`:435`).

- ✅ `▶ 다음 항목`(`:404`)이 `flex-1 truncate` 로 남는 폭을 다 먹는다 — 한 줄에서 **가장 긴 자리를 가장 중요한 것에** 줬다. 옳다.
- ✅ `title={next.item.why}`(`:405`) 로 "왜" 를 툴팁에 뒀다. 한 줄에 안 밀어 넣었다.
- ⚠️ **`제목`(`:392`)이 상시 폭을 먹는다.** 이 패널은 화면에 **하나뿐**이고 항상 같은 자리에 있다. 이름표가 매 순간 필요하지 않다 — `▶` 다음 항목이 truncate 되고 있을 때 이름표가 폭을 쥐고 있는 건 뒤바뀐 우선순위다.
- ⚠️ **`열림N · 준비M`(`:397-399`) 두 수치가 항상 붙는다.** `준비M` 은 `▶ 다음 항목`이 있을 때 **중복**이다(다음 항목이 보이면 준비된 게 있다는 뜻). 다음 항목이 **없을 때**만 의미가 있다.

→ §5 의 **B1**.

### 4-3. ★한 화면에 결정 하나 — 행동 4개는 과한가: **접힘은 과하다. 펼침은 적절**

| 행동 | 줄 | 노출 |
| --- | --- | --- |
| 항목 적기 | `:426` | ★**접힘 줄에 상시** |
| 펼치기/접기 | `:435` | 접힘 줄에 상시 |
| 지금 시작 | `:553` | 펼침 안, 해당 항목에만 |
| 내리기 | `:562` | 펼침 안, 해당 항목에만 |
| 리사이즈 | `:652` | 펼침 하단 |

- ✅ **쓰기 행동을 둘로 묶은 판단이 옳다.** `:10-11` 주석: "화면에서 할 수 있는 쓰기는 둘뿐이다 — 항목 적기, 내리기. **완료를 적는 버튼은 없다: 완료는 보드가 판정한다.**" ★이건 이 코드베이스에서 가장 잘 쓰인 제약이다. 상태를 사람이 선언하지 않고 파생시킨다(`:6-8`).
- ✅ `지금 시작`·`내리기` 는 **해당 항목 안에만** 뜬다(`:553`·`:562`) — 대상 없는 전역 버튼을 안 만들었다.
- ⚠️ **`+ 항목 적기`(`:425`)가 접힘 줄에 상시 있다.** 접힘 상태의 이 줄이 답하는 질문은 **"오케가 지금 뭘 하려 하나"** 하나인데, 거기에 **쓰기 버튼**이 함께 있어 읽는 줄과 쓰는 줄이 겹친다.

  ★**재현 결과 — 결함은 아니다.** 폼 자체는 `expanded` 블록 안(`:462`)에 있어서 "누르면 폼이 안 보이는 것 아닌가" 를 의심했으나, `openForm`(`:275-279`)이 `setExpanded(true)` 를 **먼저** 호출한다. 눌리면 패널이 펼쳐지며 폼이 뜬다. **무반응 버튼이 아니다.**

  남는 것은 훨씬 가벼운 지적 하나뿐이다: 이 버튼은 **두 가지 일(펼치기 + 폼 열기)** 을 한 번에 한다. 라벨은 `+ 항목 적기` 라 "펼쳐진다" 는 예고가 없다. 다만 결과가 즉시 보이므로 유저가 길을 잃지는 않는다 — **P2 의 다듬기이지 P0 결함이 아니다.**

### 4-4. ★3분기(빈/권한없음/실패) — 좋은 사례인가 반례인가: **★좋은 사례다. 앱 전체의 본보기로 써야 한다**

`ChainLoad` 타입(`:56-59`)이 `loading` / `ready` / `failed{reason: "permission"|"load"}` 로 갈라 놓고, 렌더는 `StateBlock`(`:509`)에 넘긴다.

**좋은 사례로 판정하는 근거 셋:**
1. ★**권한없음과 불러오기실패를 타입에서 갈랐다**(`:59`). 대부분의 화면은 둘 다 `setError(...)` 한 줄로 뭉갠다 — 정본 문서가 `ConnectionStatusPanel.tsx:885-891` 을 두고 지적한 바로 그 패턴이다. 원인이 다르면 **다음 행동이 다르므로**(권한없음 → 관리자에게 요청 / 실패 → 재시도) 갈라야 맞다.
2. ★**빈 상태에 행동이 실제로 배선돼 있다** — 말뿐이 아니다. `:365-373` 이 `kind: "empty"` 에 `create: { label, onClick: openForm }` 를 붙이고, 실패에는 `retry: () => setRetryToken(n => n + 1)`(`:362`)을 붙인다. `loadState.ts` 타입이 **다음 행동 없는 상태를 거부**하므로 이건 규율이 강제한 결과다.
3. ★**`minHeight={48}`+`skeletonLines={2}`**(`:512-513`) — 로딩에서 레이아웃이 안 튄다. 이 패널은 대화창 위에 얹히므로 높이가 튀면 아래 대화가 밀린다.

★**확인 완료 — 갈래는 화면까지 살아 있다.** `:357-360` 이 `reasonCode` 를 `orchestrator.chain.failed.permission` / `orchestrator.chain.failed.reason` **두 키로 실제로 가른다.** 타입만 갈리고 문구가 수렴하는 흔한 실패가 **아니다.**

**단, 진짜 반례가 하나 남는다 — 다음 행동이 갈리지 않는다.**

```ts
// WorkChainPanel.tsx:355-363
: load.kind === "failed"
  ? {
      kind: "failed",
      reasonCode: load.reason === "permission" ? "…failed.permission" : "…failed.reason",
      detail: load.detail,
      retry: () => setRetryToken((n) => n + 1),   // ← :362 ★두 경우 모두에 붙는다
    }
```

★**권한이 없어서 못 읽은 것에 "다시 시도" 버튼이 붙는다.** 눌러도 **반드시 같은 실패**로 돌아온다 — 이 티켓이 찾으라고 한 "눌러도 아무 일도 안 일어나는 자리" 의 정확한 사례이고, 사장님이 어드민에서 겪으신 "화면이 스스로 설명하지 못한다" 와 같은 계열이다. 게다가 `StateBlock` 어휘에는 **`denied` 라는 별도 상태가 이미 있는데**(`StateBlock.tsx:25` 가 `failed`/`denied`/`not_ready` 를 나란히 든다) 여기서는 둘 다 `failed` 로 보낸다.

→ 고칠 방향: `permission` 은 `kind: "denied"` 로 보내고 `retry` 대신 **"관리자에게 요청"/"권한 확인"** 같은 실제로 상태를 바꿀 수 있는 행동을 준다. → §5 의 **B3**.

**종합 판정: ★좋은 사례다.** 위 결함 하나는 어휘를 안 써서가 아니라 **덜 써서** 생긴 것이고, 앱의 나머지 228개 컴포넌트는 이 논의의 출발선에도 없다. 이 패널을 본보기로 삼되 `denied` 까지 쓰게 만드는 것이 맞다.
