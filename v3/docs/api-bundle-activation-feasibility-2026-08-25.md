★가장 강한 증거는 **로컬 모델**이다. Ollama 는 우리 머신에서 도는 로컬 서버인데도 CLI 를 거친다:

### 2-B. 정정 — 직접 API 경로가 **두 곳 있다**. 단 에이전트 경로는 아니다

티켓은 "api.anthropic.com 을 직접 부르는 경로가 코드에 없다" 고 적었다. **정확히는 있다.** 정직하게 적는다.

| ----------------------------------------- | -------------------------- | ------------------------------------------------------ |
| `v3/electron/flow-engine/llm-provider.ts` | `createLLMProvider()`      | `main.ts:138` import → `FlowRunner` (플로우 노드 실행) |

둘 다 `@anthropic-ai/sdk` · `openai` 를 직접 부른다. **그러나 결론은 바뀌지 않는다** — 이 둘은:

- **단발 chat 호출**이다(`chat(messages) → string`). 도구 루프가 없다
- **파일을 편집하지 못한다.** 파일시스템 접근이 없다

즉 **에이전트를 돌리는 경로가 아니라, 텍스트를 한 번 뽑아 오는 경로**다. "카드 넣고 바로 티켓을 태운다" 는 이 경로로 안 된다.

★다만 이 사실은 §2-F 에서 **좋은 소식으로도** 쓰인다: 길 B 를 간다면 완전한 맨땅은 아니다. SDK 배선과 프로바이더 추상은 이미 있다. 없는 것은 그 위의 **에이전트 루프**다.

### 2-D. ★★판정 — 길 A 는 no_cli 74건을 **한 건도** 없애지 못한다

이건 추정이 아니라 **코드가 명시적으로 말하는 사실**이다.

**[코드]** `v3/electron/harness-manager.ts:1319`, `checkSpawnAuthGate` 의 독스트링:

> **"★바이너리 설치 검사는 어느 경우에도 건너뛰지 않는다 — env-swap 벤더도 결국 우리 `claude` 바이너리로 뜨기 때문이다."**

그리고 구현이 그대로다. 설치 검사가 **벤더 분기보다 먼저** 온다:

```ts
// harness-manager.ts:1336~
const vendorSpawn = envSwapSpawn(model, pinnedModelId);
const r = await probeCliAuth(cliModel);
if (!r.installed) {                       // ← ★여기서 먼저 잘린다
  reportSpawnGateBlocked({ reason: "not-installed", ... });
  return { ok: false, installed: false, reason: "not-installed", ... };
}
if (vendorSpawn) {                        // ← 벤더키 판정은 그 다음이다
  if (vendorSpawn.ready) { ...통과... }
  ...
}
```

**[코드]** 그리고 그 사유가 BQ 어휘로 접히는 규칙(`spawn-block-reason.ts:82~`):

```ts
case "not-installed":       return "no_cli";
case "not-authenticated":   return "needs_auth";
case "plan-cap-free":       return "no_subscription";
case "plan-cap-paid":       return "quota_exhausted";
default:                    return "other";   // ← vendor-not-configured 가 여기
```

**따라서 산술은 이렇게 된다:**

| 차단 사유                            |   건수 | 마블로 크레딧(길 A)이 없애나                           |
| ------------------------------------ | -----: | ------------------------------------------------------ |
| `no_cli` (= `not-installed`)         | **74** | ❌ **아니다.** 설치 검사는 벤더키와 무관하게 먼저 돈다 |
| `needs_auth` (= `not-authenticated`) |  **6** | ✅ 그렇다. 키가 있으면 이 분기에 도달조차 안 한다      |
| **합**                               | **80** | **6건 = 7.5%**                                         |

★**길 A 의 활성화 효과 상한은 7.5% 다.** 프록시(L)·원장(M)·결제·약관·세무·환불 리스크를 전부 안고 얻는 것이 그것이다.

그리고 한 가지 더 나쁜 소식: 벤더키 미등록 차단은 `vendor-not-configured` → **`other`** 로 접힌다. `needs_auth` 가 아니다. 즉 **크레딧 경로가 새로 만드는 실패는 우리가 지금 세는 어휘에 칸이 없다** — 켜고 나서 "왜 안 늘지" 를 물으면 그 답이 `other` 에 섞여 안 보인다. 켜기 전에 칸을 하나 나눠야 한다.

### 2-E. 그리고 게이트는 5칸이다 — 두 칸을 없애도 세 칸이 남는다

**[코드]** `v3/src/lib/cliSetupGate.ts:52~` — 온보딩 마법사는 선형 5단계다:

```
① install  →  ② auth  →  ③ prd  →  ④ git  →  ⑤ firstTicket
```

| 단계          | 무엇                    | 길 A       | 길 B       |
| ------------- | ----------------------- | ---------- | ---------- |
| ① install     | CLI 설치                | **남는다** | 없어진다   |
| ② auth        | 로그인                  | 없어진다   | 없어진다   |
| ③ prd         | 폴더 연결 + PRD 시드    | **남는다** | **남는다** |
| ④ git         | 워크트리 생성 가능 확인 | **남는다** | **남는다** |
| ⑤ firstTicket | 첫 티켓 전달            | **남는다** | **남는다** |

### 3-C. ★후불 청구 vs 선불 크레딧 — 정확도 요구가 다르다

티켓의 핵심 질문이다. 갈라서 적는다.

| 축                    | **후불 청구**(썼으니 청구서를 보낸다)            | **선불 크레딧**(미리 충전, 차감)                                |
| --------------------- | ------------------------------------------------ | --------------------------------------------------------------- |
| 과대계상 시           | ★**고객에게 과청구.** 환불·분쟁·신뢰 사고        | 잔액이 빨리 닳음 → **고객 불만**(사고보다는 CS)                 |
| 과소계상 시           | 우리 손해(조용히)                                | 우리 손해(조용히)                                               |
| 최악의 사고           | ★**"안 쓴 돈을 청구당했다"** — 회복 불가         | "잔액이 이상하게 빨리 준다" — 회복 가능                         |
| 필요한 정확도         | **센트 단위, 벤더 청구서와 대조 가능**           | **보수적이면 된다** — 우리 쪽으로 안전하게 틀려도 사고가 아니다 |
| 상한 손실             | ★**무한**(루프 지출을 청구 전까지 우리가 안는다) | **잔액**으로 확정                                               |
| 신용 리스크           | 있다(카드 거절·미수)                             | **없다**(선수금)                                                |
| 벤더 청구서 대조 필요 | ★**필수, 사전에**                                | 사후 정산으로 충분                                              |
| 지금 착수 가능한가    | ❌ **아니다**                                    | ⚠️ 조건부(§3-E)                                                 |

**첫 단계 판단 — 선불이 맞다. 근거 넷:**

1. **오류의 방향이 안전하다.** 선불에서 우리가 보수적으로(우리 손해로) 차감하면 고객에게 사고가 안 난다. 후불은 같은 오차가 곧 과청구다
2. ★**루프 지출 상한이 자동으로 생긴다.** 잔액이 곧 하드캡이다. 후불은 "고객 에이전트가 폭주하면 청구 전까지 우리가 안는" 무한 노출이다 — §5 R1 의 유일한 구조적 해법이 선불이다
3. **신용·미수·추심이 없다.** 결제 실패 처리 로직이 통째로 필요 없다
4. **선행 설계가 이미 선불이다.** [`onramp-l2-credit-tier-design`](./onramp-l2-credit-tier-design-2026-08-09.md) 이 크레딧 원장으로 설계돼 있고, 결제 배관(`kind:"one_time"`)도 단건이다(§6-A)

★**단, 선불이라고 정확도가 면제되는 것은 아니다.** 두 가지가 여전히 요구된다:

- **멱등성**은 후불과 동일하게 필수다. 같은 소비를 두 번 차감하면 그건 방향과 무관하게 **과청구**다
- **미사용 잔액은 부채다.** 전자상거래법상 환불 요구가 가능하므로 매출로 인식할 수 없다(#883 §3-E)

### 3-D. ★그런데 선불도 프록시 없이는 계량 자체가 불가능하다

여기가 이 절의 결론이고, §2 와 만나는 지점이다.

**길 A(키 주입)에서 우리는 무엇을 보고 차감하는가?**

- CLI 가 벤더에 직접 붙는다. 요청·응답이 **우리를 지나가지 않는다**
- 우리가 볼 수 있는 것은 CLI 가 남긴 **세션 JSONL** 뿐 — 즉 지금의 `cost_logs` 축이고, §3-A 대로 **그건 원장이 아니다**
- 유저 머신의 파일이다. 유저가 고칠 수 있다. **원장으로 쓸 수 없다**

**따라서 길 A 는 두 가지 중 하나여야 한다:**

| 변형                                         | 계량                                             | 판정                                                                          |
| -------------------------------------------- | ------------------------------------------------ | ----------------------------------------------------------------------------- |
| A-1: 우리 벤더 키를 그대로 env 로 내림       | 벤더 청구서만. **유저별 분해 불가**              | ❌ 게다가 유저가 키를 읽을 수 있다 → 모양 B → **전 벤더 ToS 위반**(#883 §5-A) |
| A-2: **우리 계량 프록시** + 스폰당 단명 토큰 | 프록시가 자기 응답의 `usage` 를 원장에 직접 기록 | ✅ 유일하게 성립. **단 규모 L**                                               |

★**즉 "env-swap 행 1개면 된다" 는 배선에 대해서만 맞고, 그 행이 가리키는 곳에 프록시(L)가 서 있어야 한다.** 선행문서 #883 §5-D 가 같은 말을 했다 — "프록시는 편의가 아니라 과금의 전제조건이다."

**그리고 이게 §2-D 와 겹쳐지면 이렇게 된다:**

> 프록시(L) + 크레딧 원장(M) + 결제(S) + 약관(S) + 세무를 지어서, **활성화 차단의 7.5% 를 없앤다.**

### 3-E. 이 티켓이 답해야 할 질문 하나는 **아직 답할 수 없다**

티켓 본문의 질문: "지금 추정치와 실청구액의 오차가 얼마인가."

**[미확인]** 답할 수 없다. 이유는 둘이다:

1. **BQ 접근이 막혀 있다**(§8) — 추정치 쪽 숫자를 못 뽑는다
2. ★**더 근본적으로, 실청구액 쪽이 없다.** 벤더 콘솔 청구서를 이 저장소에서 볼 방법이 없고, 대조하려면 벤더 계정 로그인이 필요하다(선행문서 `onramp-p0-env-key-audit` 도 같은 이유로 계정 상태 확인을 사장님 액션으로 뺐다)

**대조하려면 무엇이 필요한가 — 세 가지다:**

| 필요한 것                          | 왜                                                                                         | 누가                        |
| ---------------------------------- | ------------------------------------------------------------------------------------------ | --------------------------- |
| ① 벤더별 usage API 또는 청구서 CSV | 실청구액의 원천                                                                            | 벤더 콘솔 접근 = **사장님** |
| ② 우리 추정치의 재집계 스크립트    | 같은 기간·같은 축으로 접기                                                                 | backend (BQ 열리면)         |
| ③ ★대조 가능한 **공통 키**         | 지금 축이 안 맞는다 — 벤더는 API 키·조직 단위로 청구하고 우리는 `agentId`·`taskId` 로 센다 | 설계 필요                   |

★③이 진짜 문제다. **프록시가 있으면 ③이 저절로 풀린다**(프록시가 양쪽을 다 안다). 프록시가 없으면 대조는 "우리 총합 vs 벤더 총합" 수준으로만 가능하고, 그건 유저별 차감의 근거가 못 된다.

## 4. ③벤더 약관 — 재조사하지 않는다. 인용한다

**이 항목은 이미 답이 있다.** [`api-reseller-onramp-feasibility-2026-08-09.md`](./api-reseller-onramp-feasibility-2026-08-09.md) §2 가 5개 벤더 약관 **원문**을 직접 열어 인용했고, [`onramp-p0-env-key-audit.md`](./onramp-p0-env-key-audit.md) 가 우리 현행 키의 종류를 확정했다. 그 판정을 그대로 옮긴다.

## 6. ⑤재사용 가능한 기존 자산 — 무엇이 있고 무엇이 없나

★티켓 지시대로 **새로 짓지 말고 이어받는다.** 그리고 선행문서가 "없다" 고 적은 것 하나가 **실제로는 있다.**

### 6-B. 실행 배선 — 행 1개면 된다 (단 §3-D 를 읽을 것)

**[코드]** `model-registry.ts` 의 env-swap 프로파일은 이미 이 모양이다:


마블로 프록시 행은 **같은 모양의 행 1개**다. 하네스 코드 0줄. GLM(PR#609)·Kimi(PR#626) 편입이 이미 증명했다.

★**그 행이 가리키는 곳에 프록시(L)가 서 있어야 한다**(§3-D). 그리고 `${...}` 자리표시자는 **전부-아니면-전무**로 주입된다(`agent-config.applyVendorEnv`) — 부분 주입하면 우리 Anthropic 크레덴셜을 든 claude 가 남의 모델 id 로 붙는다.

### 6-C. 조직·팀 축 — 있다. 단 ★좌석 개념이 코드에 없다

사장님 첫 메시지가 "기업용이나 팀용" 이므로 이 축이 중요하다.

**[코드]** 있는 것:

| 팀 사용량 오버뷰       | `functions/src/teamUsage.ts`                                                    | 게이트·상태 5값(`complete`/`partial`/`not_provisioned`…)                       |

> "★금액은 **'청구액' 이 아니다.** **좌석(seat) 개념이 코드에 존재하지 않아** ('누구 몫으로 청구되나' 를 답할 원장이 없다) 이 화면이 답할 수 있는 것은 '누가 얼마 썼나' 뿐이다."

## 7. ⑥순서 제안과 중단 조건

★**티켓의 오케 제안 순서는 "계량 정밀도 → 마진 → 약관 → 파일럿" 이었다. 반대한다. 근거를 적는다.**

**반대 이유:** 그 순서는 전부 **길 A 를 간다고 이미 정한 뒤의 순서**다. 그런데 §2-D 가 밝힌 대로 길 A 의 활성화 효과 상한은 7.5% 다. **계량을 청구 등급으로 만드는 일(수개월)을 먼저 하고 나서 "그래서 7.5% 였다" 를 알게 되는 건 순서가 거꾸로다.** 가장 싼 판정을 앞으로 당긴다.

## 8. 한계 · 미확인 — 추측으로 메우지 않은 것

- ★**BQ 접근이 막혀 있다.** `bq query` 가 `Reauthentication failed. cannot prompt during non-interactive execution` 으로 떨어진다(2026-08-25 확인). 따라서:
  - **no_cli 74 · needs_auth 6 은 티켓이 제공한 실측이며 이 문서가 재검증하지 못했다.** §2-D 의 7.5% 산술은 그 두 수에 전적으로 의존한다. 두 수가 바뀌면 판정도 바뀐다
  - §7-A 의 S0 쿼리를 **돌리지 못했다** — 그래서 S0 이 이 문서의 결과가 아니라 **제안**으로 남아 있다
  - "지금 추정치와 실청구액의 오차" 를 **답하지 못했다**(§3-E)
- **벤더 콘솔에 접근하지 못했다.** U1(우리 MiniMax 키 종류)은 [미확인]이다. `.env` 파일의 **존재 여부도 값도 확인하지 않았다**(스킬 §시크릿 규율).
- **어떤 벤더와도 접촉하지 않았다.** U2 는 미착수다.
- **법률 자문이 아니다.** §4 는 선행문서의 공개 약관 인용을 옮긴 것이고, D.4 "resell" 을 좁게 읽은 해석이다. Anthropic 이 넓게 읽을 가능성을 배제하지 못한다.
- **세무 판단(R9)은 법 정의 대조 수준**이다. "모양 A = 재판매 = 국내 10% 과세" 는 상식적 독해이며 세무 자문이 아니다.
- **§3-A 의 수치는 #1207 의 실측을 인용한 것**이고 이 문서가 재현하지 않았다. 그 티켓은 현재 REVIEW 이며 **아직 머지되지 않았다** — 결론이 바뀌면 §3-A 도 따라 바뀐다.
- **길 B 의 규모를 "XL" 로 적었으나 그건 등급이지 견적이 아니다.** 실제 견적은 별도 스파이크가 필요하다. 이 문서가 한 것은 "무엇을 만들어야 하는지의 목록"(§2-F)까지다.
- **§2-B 의 두 직접-API 모듈이 실제 런타임에서 얼마나 자주 도는지 재지 않았다.** 코드 경로가 살아 있음(main.ts:138 import)만 확인했다.
- **활성화 효과의 상한만 계산했다.** 7.5% 는 "needs_auth 6명이 전원 전환된다" 는 낙관 가정이다. 실제는 그 이하다.
- 날조 없음. 코드 인용은 전부 파일·행으로 확인 가능하고, 선행문서 인용은 §10 에 위치를 적었다.
