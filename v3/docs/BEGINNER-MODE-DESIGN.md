## 1. 무엇을 고치는가

진단 문서가 외부 코호트에서 **실제로 관측한 유일한 UX dead-end** 는 S4 다:

```
03:34:20  cli_setup_step(firstTicket, success)
03:34:34  cli_setup_step(firstTicket, success)   ← +14초
03:34:48  cli_setup_step(firstTicket, success)   ← +14초
(끝. 스폰 0, 재방문 0)
```

30초 안에 같은 버튼을 3번 눌렀다. 세 번 다 오케에 **실제로 전달됐다**(`delivered`).
즉 실패한 게 아니라 — **눌러도 화면에서 아무 일도 일어나지 않았다.**

근인은 셋이다:

| #   | 근인                                                                          | 코드                                                 |
| --- | ----------------------------------------------------------------------------- | ---------------------------------------------------- |
| ①   | 성공 표면이 초록 텍스트 한 줄뿐 — 오케가 일하는 곳(터미널/보드)은 화면에 없다 | `StartHereTab.tsx:694-722` + `FirstTicketResultNote` |
| ②   | 중복 전송 가드 없음 (`disabled = sendingTicket \|\| !hasProject`)             | 같은 파일                                            |
| ③   | 오케가 티켓을 만드는 데 걸리는 수십 초~수 분 동안 "진행 중" 표면이 아예 없다  | —                                                    |

여기에 사장님 설계가 얹힌다: **신규 유저에게 마블로의 어드밴스드 표면(사이드바·15개 탭·보드·워크트리)을 첫 화면으로 주지 말자.** Codex/Antigravity 처럼 인증 하나만 하면 큰 대화창이 열리고, 거기서 첫 성공까지 손을 잡고, 준비되면 승격시킨다.

**한 줄**: 비기너 모드는 "탭을 줄인 워크스페이스"가 아니라 **"오케챗 하나만 있는 셸"** 이다. S4 는 그 셸 안에서 "별도 탭으로 보내지 않고 챗 안에 진행상황을 그려서" 해소된다.

## 2. 설계 원칙 (무엇을 하지 않는가)

1. **PTY 재배선 0.** 풀스크린 오케챗은 `OrchestratorPanel fill` 을 **그대로** 쓴다. 오케는 이미 Claude Code TUI 를 태운 실 PTY 이고, 그게 곧 대화창이다. 새 챗 프로토콜을 만들지 않는다.
2. **기존 유저를 절대 끌어내리지 않는다.** 비기너 진입은 **깨끗한 신규 설치**에만 적용된다(§4). 기존 설치는 첫 렌더에서 `advanced` 로 확정된다.
3. **워크스페이스 셸은 무변경.** `workspaceModeStore`(단일 플래그, PR#477)는 손대지 않는다. 비기너는 그 **위에 얹히는 한 층**이고, 승격하면 그대로 통과해 기존 셸이 뜬다.
4. **탈출구는 항상 있다.** 비기너 셸 안에서 언제든 "고급 모드로", 설정에서 언제든 되돌리기.
5. **판정은 순수함수로.** 진입/승격/진행요약 규칙은 `src/lib/beginnerMode.ts` 에 두고 유닛테스트로 못박는다 — 라이브 확인이 실계정을 요구하는 구간이라 컴포넌트에 규칙을 묻으면 회귀를 못 잡는다(`firstTicketDelivery` 와 같은 이유).

## 3. 셸 층위

```
AppContent (App.tsx)
  ├─ loading / !user          → BrandLoader / LoginPage      (무변경)
  ├─ detached=board|code      → DetachedLayout               (무변경, 비기너보다 우선)
  ├─ ★beginner               → <BeginnerShell />            ← 신규
  ├─ workspaceMode           → <WorkspaceShell />            (무변경)
  └─ else                    → <Layout />                    (무변경)
```

detached 팝아웃 창이 비기너보다 **먼저** 걸린다: 팝아웃은 메인 창에 종속된 보조 표면이라 비기너 셸을 그릴 이유가 없다(`first_run` 마커가 팝아웃을 세지 않는 것과 같은 규칙).

`useAppLifecycle()` 은 비기너 셸에서도 **동일하게** 마운트한다. 오케 자동기동·에이전트 재접속·세션 복원·비용 기록이 전부 그 훅에 있어서, 빼면 비기너 유저의 오케가 아예 안 뜬다.

## 4. 상태 모델 — 누가 비기너가 되는가

`marblo.beginnerMode.state` = `"beginner" | "advanced"` (localStorage).

키가 **없을 때만** 판정한다(`resolveInitialBeginnerMode`). 한 번 판정하면 그 값을 써서 다시는 흔들리지 않는다.

| 신호                                          | 의미                             | 판정          |
| --------------------------------------------- | -------------------------------- | ------------- |
| `marblo.beginnerMode.state` 있음              | 이미 정해짐(승격했거나 되돌렸음) | 저장값 그대로 |
| `marblo.onboarding.progress` 있음             | 온보딩을 이미 걸어 본 기존 설치  | `advanced`    |
| `marblo.workspaceSplit.activeTab` 있음        | 워크스페이스 셸을 이미 쓴 설치   | `advanced`    |
| `marblo.workspaceMode.enabled` 있음(옵트아웃) | 셸 토글을 만져 본 설치           | `advanced`    |
| `marblo.cliSetupGateDismissed` 있음           | 구 모달을 만져 본 설치           | `advanced`    |
| 위 어느 것도 없음                             | **깨끗한 신규 설치**             | `beginner`    |
| 저장소 읽기 실패(프라이빗 모드)               | 판정 불가 → 기존 경험 유지       | `advanced`    |

**왜 이렇게 보수적인가**: 이 규칙이 틀리면 기존 유저가 어느 날 앱을 켰을 때 보드가 사라진다. 잘못된 방향의 오탐(신규를 어드밴스드로 보냄)은 종전과 같은 화면일 뿐이지만, 반대 방향의 오탐은 회귀 사고다. 그래서 **"신규라는 증거가 전부 있을 때만"** 비기너로 간다.

저장소 실패가 `advanced` 인 것도 같은 이유다 — `workspaceModeStore` 의 "읽기 실패 → 기본 경험" 규칙과 동형이다.

### 승격 상태

같은 스토어가 함께 들고 있는 것(전부 localStorage 1키에 직렬화):

- `enteredAt` — 비기너로 확정된 시각(ms). 계측의 TTFV 분모이자 "며칠 사용" 트리거의 기준.
- `firstCompletionAt` — 챗 안에서 첫 완료를 관측한 시각. **1회만** 기록(계측 중복 방지).
- `promotionShownAt` — 승격 모달을 띄운 시각. 있으면 다시 안 띄운다.

## 5. 진입: 인증 하나만

`ORCHESTRATOR_CLI_IDS = ["cli-claude-code", "cli-codex"]` 에 대해 `requiredReady`(installed && authenticated 를 `.some`, #579)가 참이면 게이트를 통과한다. **둘 다 요구하지 않는다** — 하나만 있어도 오케를 태울 수 있다는 게 이미 코드의 규칙이고, 비기너 화면은 그걸 문구로도 못박는다("둘 중 하나만 연결하면 됩니다").

원클릭 인증 = `cliSetupActions.launchLogin(model, cmd)` 재사용:

1. 실 터미널 세션을 만들고 `claude login` / `codex login` 을 타이핑한다.
2. **★비기너 셸은 터미널 열이 없으므로**, 그 세션을 `<TerminalView>` 로 **연결 카드 안에 인라인 임베드**한다. CLI 가 인쇄하는 인증 URL·키 입력 프롬프트를 유저가 볼 수 있어야 로그인이 끝난다 — 숨기면 그대로 dead-end 가 된다.
3. `cliSetupStore` 의 자동 재확인 폴(`loginRunning`)이 인증 성립을 감지하면 게이트가 스스로 열린다. 수동 "다시 확인" 은 폴백으로 남긴다.

BYOM(벤더 키) 경로는 비기너 화면에 **넣지 않는다.** 비기너의 정의가 "선택지를 줄이는 것"이라 택1 카드 2장이 상한이다. BYOM 유저는 어드밴스드의 시작하기 탭에서 계속 지원된다.

## 6. ★S4 해결: 챗 안 첫 성공

### 6-A. 첫 요청 (`BeginnerFirstAsk`)

- 오케 PTY 에도 입력창이 있지만, 첫 화면에서 유저는 "여기다 뭘 쳐야 하나"를 모른다. 그래서 첫 요청 **전에만** 큰 입력칸 + 예시 프롬프트를 띄운다. 보내고 나면 사라지고, 이후 대화는 PTY 에서 이어간다.
- 전송은 `routeInstructionToOrchestrator` — `StartHereTab` 이 쓰는 그 경로다. 결과 3값(`delivered`/`queued`/`failed`) 해석은 `lib/firstTicketDelivery` 를 **그대로** 재사용한다(큐잉을 성공으로 접지 않는 규칙 유지).
- **중복 전송 가드(진단 P1-2 ①)**: `delivered` 후에는 버튼이 잠기고, 재전송은 명시적 "다시 보내기"로만 가능하다. 이게 8/4 유저가 14초 간격으로 3번 누른 그 지문의 직접 수리다.

### 6-B. 인라인 라이브 (`BeginnerLiveStrip`)

별도 탭으로 보내지 않는다. 챗 바로 위 한 줄이 오케/에이전트가 지금 뭘 하는지 말한다.
`summarizeBeginnerProgress()` 순수함수가 `tasks`(taskStore) + `agents`(agentStore) + `sentAt` + `now` 로 국면을 판정한다:

| 국면        | 조건                         | 문구                                          |
| ----------- | ---------------------------- | --------------------------------------------- |
| `idle`      | 아직 아무것도 안 보냄        | (표시 안 함)                                  |
| `thinking`  | 보냈고 티켓 0개, 경과 < 90초 | "오케가 요구사항을 읽고 있어요… (보통 1~3분)" |
| `stalled`   | 보냈고 티켓 0개, 경과 ≥ 90초 | "아직 티켓이 안 보여요" + 다시 보내기/도움말  |
| `planned`   | 티켓 ≥ 1, 일하는 에이전트 0  | "티켓 N개를 만들었어요"                       |
| `working`   | 일하는 에이전트 ≥ 1          | "에이전트 N명이 일하고 있어요"                |
| `completed` | 완료 티켓 ≥ 1                | "✓ N건 완료"                                  |

`stalled` 임계 90초는 진단 §7 P1-2 ④의 권고 그대로다. 국면은 **단조 증가가 아니다** — 완료 후 새 요청을 하면 다시 `thinking` 으로 내려간다.

**추상화 수준**: 티켓 제목·에이전트 모델명·워크트리는 노출하지 않는다. 비기너에게는 "일하고 있어요 / 몇 개 끝났어요" 가 정확한 해상도다. 세부는 승격 후 보드에서 본다.

## 7. 승격

### 트리거 (`shouldPromote`)

셋 중 **하나라도** 만족하고, 아직 모달을 띄운 적 없으면 승격 제안:

| 트리거    | 임계    | 근거                                                      |
| --------- | ------- | --------------------------------------------------------- |
| 완료 건수 | `≥ 3`   | 한 건은 우연일 수 있다. 세 건이면 흐름을 이해한 것        |
| 첫 머지   | `≥ 1`   | 머지까지 갔으면 diff/워크트리를 볼 이유가 생겼다          |
| 사용 일수 | `≥ 3일` | 완료가 없어도 사흘째면 화면이 좁아서 못 하는 것일 수 있다 |

### 모달

"이제 진짜 힘 써볼까요?" — 보드에서 여러 에이전트 직접 지휘 / 워크트리·diff 검토 / 모델 골라 스폰. 두 버튼: **[어드밴스드로 전환]** · [지금은 그대로]. 후자를 눌러도 모달은 다시 안 뜬다(`promotionShownAt` 기록) — 조르지 않는다.

### 되돌리기

설정 → 프로필 섹션에 **"비기너 모드"** 토글. 어드밴스드에서 다시 비기너로 갈 수 있다. 되돌린 뒤 승격 트리거가 또 도달하면 모달은 다시 뜨지 않는다(이미 본 사람이라서) — 토글이 곧 명시적 선택이므로 재권유는 소음이다.

## 8. 계측

기존 `logTelemetry` 초크포인트(비식별 scrub + firstParty 게이트)를 그대로 탄다. 서버 변경 없음(`logTelemetryBatch` 는 event 문자열을 화이트리스트 없이 적재).

| 이벤트                                 | 언제                              | metadata                                                 |
| -------------------------------------- | --------------------------------- | -------------------------------------------------------- |
| `onboarding:beginner_entered`          | 비기너 화면에 들어온 세션마다 1회 | `{ reason: "fresh_install" \| "restart" \| "settings" }` |
| `onboarding:beginner_first_completion` | 챗 안에서 첫 완료 관측 (1회)      | `durationMs` = 진입→첫완료                               |
| `onboarding:beginner_promoted`         | 어드밴스드로 전환                 | `{ trigger, manual }`                                    |

`durationMs` 를 싣는 이유: 진단 §3 이 지적한 대로 서버 `timestamp` 는 수신시각이라 단계 지연을 계산할 수 없다. **클라가 계산한 경과**를 실으면 P1-3(`occurredAt`)을 기다리지 않고도 비기너 축의 TTFV 를 볼 수 있다.

퍼널: `first_run` → `login_success` → `beginner_entered(fresh_install)` → (`cli_setup_step(auth,success)`) → `beginner_first_completion` → `beginner_promoted`.

`reason` 를 세 값으로 쪼갠 건 분모 때문이다. 재시작마다 `fresh_install` 을 찍으면 "비기너 진입 수" 가 세션 수만큼 부풀어 진입→첫완료 전환율이 무의미해진다. `fresh_install` 만이 설치 단위이고, `restart` 는 리텐션 축(진단 §S6 의 최대 절벽), `settings` 는 승격을 되돌린 신호다.

첫 요청 전달은 새 이벤트를 만들지 않고 기존 `onboarding:cli_setup_step(firstTicket, …)` 을 그대로 쓴다 — 같은 어휘라 비기너 축과 기존 온보딩 퍼널이 한 축에서 조인된다.

## 10. 회귀 가드

- **기존 유저 무회귀**: `resolveInitialBeginnerMode` 유닛테스트가 "기존 마커가 하나라도 있으면 advanced" 를 6가지 조합으로 못박는다. 여기가 깨지면 보드가 사라진다.
- **워크스페이스 셸 무변경**: `workspaceModeStore`·`splitWorkspaceStore`·`WorkspaceShell` 은 이 PR 에서 한 줄도 안 바뀐다. 승격 = 비기너 층을 벗는 것이지 셸을 고치는 게 아니다.
- **첫 티켓 전달 규칙 무변경**: `lib/firstTicketDelivery` 재사용. `queued` 를 성공으로 접지 않는 F3 규칙이 비기너에도 그대로 적용된다.
- **앱 재시작 필요**: 셸 분기는 렌더러이지만 `App.tsx` 진입점을 바꾸므로, 개발 중에는 HMR 로 반영되어도 **패키지 앱은 재시작**해야 새 셸이 뜬다.

### E2E 하네스 — 기본 옵트아웃

클린룸은 정의상 "마커가 하나도 없는 새 설치" 라 §4 의 판정이 **비기너**로 떨어진다. 그런데 기존 Playwright spec 들(시작하기 탭·CLI 배너·레거시 모달 위저드)은 어드밴스드 표면의 회귀 가드이고, 그 표면들은 지금도 살아 있다(기존 유저·승격한 유저의 경로).

그래서 두 하네스가 **기본으로 비기너를 옵트아웃**한다 — `launchCleanRoom`/`launchMarblo` 가 `marblo.beginnerMode` 를 advanced 로 시드하고 한 번 리로드한다(셸 분기가 스토어 모듈 평가 시점에 굳으므로 시드만으론 이번 로드에 안 먹는다). 비기너 화면을 보고 싶은 spec 은 `beginnerShell: true` 로 켠다.

부수효과 하나가 더 있다: 개발 머신(마커 있음)과 CI 신규 러너(마커 없음)의 판정이 갈리는 것도 이 시드가 막는다. 시드가 없으면 같은 spec 이 로컬에선 통과하고 CI 에선 탭을 못 찾는다.

**비기너 셸 자체의 E2E 는 이 PR 에 없다**(§9 F5). 클린룸은 빌드된 Electron 이 필요해 이 작업 세션에서 실행·확정할 수 없었고, 검증 못 한 spec 을 넣는 건 가드가 아니라 소음이다.
