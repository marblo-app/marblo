## 0. 한 문단 요약 — 이 문서가 줄이는 것

사장님 지시는 "화이트+블루로 신뢰감 있게" 였다. 전수 확인 결과 **그건 새 팔레트가 아니다.**
`marblo-web` 의 브랜드는 이미 인디고이고(`--color-brand-500 = #6366f1`, 50~950 **11단계 완비**),
Tailwind v4.2.2 CSS-first 라 라우트 래퍼 아래에서 CSS 변수만 다시 정의하면 같은 브랜드가 밝은
바탕 위로 옮겨간다. **두 번째 디자인 시스템을 짓는 일이 아니라 같은 토큰을 두 번째 바탕에
놓는 일이다.**

그래서 이 문서의 비싼 부분은 색이 아니라 셋이다: **차트를 무엇으로 그리나(§4)**,
**테마 드리프트를 무엇이 막나(§3)**, **게이트 뒤에 무엇이 보이나(§5·§6)**.

★그리고 이 문서는 티켓 지시 두 개를 **근거를 붙여 정정한다**(§7.1, §8.2). 둘 다 지시의
*취지*는 그대로 지키고, *수단*만 실제 코드가 이미 정한 것으로 바꾼다.

## 2. 스코프 테마 — 기술 검증 (추정 아님, 실제 컴파일 결과)

`tailwindcss@4.2.2` + `@tailwindcss/cli@4.2.2` 를 실제로 설치해 컴파일한 결과다. 아래 CSS 는
인용이 아니라 **출력물 원문**이다.

### 2.1 ★스코프 테마가 실제로 싸다 — 근거

```css
/* 입력: @theme { --color-brand-500: #6366f1 } + @theme inline { --color-accent: var(--color-brand-500) } */
/* 출력: */
@layer theme {
  :root, :host {
    --color-zinc-400: oklch(70.5% 0.015 286.067);
    --color-brand-500: #6366f1;
  }
}
@layer utilities {
  .text-zinc-400  { color: var(--color-zinc-400); }      /* ← 리터럴이 아니라 var */
  .bg-brand-500   { background-color: var(--color-brand-500); }
  .text-accent    { color: var(--color-brand-500); }     /* ★토큰 이름이 사라졌다 */
}
```

여기서 화면 설계를 좌우하는 사실 셋이 나온다.

1. **기본 팔레트(`zinc`·`red`·`amber` …)도 전부 CSS 변수다.** `text-zinc-400` 은 값을 굽지 않고
   `var(--color-zinc-400)` 을 참조한다. → 래퍼 아래에서 변수를 다시 정의하면 **컴포넌트를 한 줄도
   안 고치고** 색이 바뀐다.
2. **테마 변수는 `@layer theme` 안의 `:root`** 에 있다. 레이어 밖(unlayered) CSS 는 **레이어 안
   CSS 를 특이도와 무관하게 이긴다.** → `.marblo-console { --color-…: … }` 를 `globals.css` 에
   레이어 없이 적으면 `!important` 도, 특이도 경쟁도 필요 없다.
3. **★`@theme inline` 은 스코프를 타지 않는다 — 함정 둘째.** 위 출력의 마지막 줄을 다시 보라:
   `.text-accent` 가 내보낸 것은 `var(--color-accent)` 가 아니라 **`var(--color-brand-500)`** 이다.
   `inline` 의 뜻이 곧 "토큰 자기 이름을 쓰지 말고 참조 대상을 직접 박아라" 이기 때문이다.
   → **`.marblo-console { --color-accent: … }` 는 죽은 규칙이 된다.** 아무 오류도 안 난다.

   ★이건 가정이 아니다. `globals.css` 는 이 티켓 전까지 `--color-accent`·`--color-ring` 을
   `@theme inline` 에 두고 있었고, **그대로 뒀으면 스코프 테마의 강조색이 조용히 안 먹었다.**
   고친 방법은 지우는 게 아니라 **`inline` 만 떼는 것**이다 — 값(`var(--color-brand-500)`)은
   그대로 두면 브랜드 추적과 스코프 재정의를 **둘 다** 얻는다(실제 컴파일로 확인):

   ```css
   @theme { --color-accent: var(--color-brand-500); }
   /* → :root { --color-accent: var(--color-brand-500) }   브랜드를 계속 따라간다 */
   /* → .bg-accent { background-color: var(--color-accent) }  스코프가 먹는다   */
   ```

   > **규율:** 어떤 스코프든 다시 가리킬 수 있어야 하는 **색 별칭은 `@theme inline` 에 두지
   > 않는다.** `inline` 이 꼭 필요한 것은 next/font 처럼 **빌드 시점에 값을 알 수 없는** 변수뿐이다.

### 2.2 ★그런데 함정이 하나 있다 — 알파 수식자는 스코프 안전하지 않다

같은 컴파일에서 나온 출력이다. **이건 새로 발견한 것이고, 지시에 없던 사실이다.**

```css
.bg-surface\/60 {
  background-color: color-mix(in srgb, #09090b 60%, transparent);        /* ← ★어두운 값이 구워졌다 */
  @supports (color: color-mix(in lab, red, red)) {
    background-color: color-mix(in oklab, var(--color-surface) 60%, transparent);
  }
}
```

**폴백 가지에는 토큰의 값이 빌드 시점에 리터럴로 박힌다.** `@supports` 를 통과하지 못하는
브라우저에서는 스코프 재정의가 **무시되고 어두운 색이 밝은 화면에 칠해진다.**

★**토큰 값이 그 자체로 `var(...)` 여도 마찬가지다.** `--color-accent: var(--color-brand-500)`
에 대해 `bg-accent/60` 은 폴백에 `#6366f1` 을 굽는다 — Tailwind 가 빌드 시점에 참조 사슬을
끝까지 풀어 버린다. 즉 **이 함정은 우회로가 없다.**

`@supports (color: color-mix(in lab, …))` 는 최신 브라우저에서 통과하므로 실무 영향은 작다.
그러나 **`/team` 은 지금 이 알파 수식자를 55회 쓴다**(전수 집계 — `TeamUsageView` 27 ·
`TeamAuditView` 22 · `TeamOverviewClient` 6; 최다는 `bg-zinc-950/40` 16회).
조용히 어긋나는 자리를 55개 남기는 것은 이 화면의 성격에 맞지 않는다.

> **규율:** 콘솔 스코프 안에서는 **스코프 토큰에 알파 수식자를 붙이지 않는다.**
> 반투명 표면이 필요하면 그 표면을 **별도 토큰으로 정의한다**(`--color-surface-sunken`).
> 이 규율은 §3.3 의 가드가 기계로 잡는다.

### 2.3 ★그리고 죽은 클래스는 v4 에서도 그대로 난다

티켓이 말한 "데스크톱 앱에서 CSS 를 한 줄도 안 만드는 클래스 16개" 와 **정확히 같은 실패가
v4 에서도 재현된다.** 같은 컴파일에서 `border-line` 과 `text-ink-muted` 는 — 토큰이 정의되지
않았으므로 — **출력 CSS 에 한 줄도 안 나온다.** 오류도, 경고도 없다.

이게 §3.3 에서 가드를 넣기로 판단한 직접 근거다. **v4 는 v3.4 와 실패 원인이 다르지만
(설정 파일 누락이 아니라 토큰 미정의) 증상은 똑같다: 조용한 무색.**

### 2.4 그래서 스코프 방식은 이것으로 정한다

```
marblo-web/src/app/globals.css
  @theme { … 오늘 그대로 … }              ← 브랜드 인디고. 손대지 않는다
  @theme { --color-surface: …; --color-ink: …; … }   ← ★의미 토큰 신설(어두운 값 = 오늘과 동일)
  .marblo-console { --color-surface: #fff; --color-ink: …; … }  ← 레이어 밖. 밝은 값만 재정의

marblo-web/src/app/[locale]/audit-dashboard/layout.tsx
  <div className="marblo-console"> {children} </div>
```

**왜 `zinc` 팔레트를 뒤집지 않는가 — 검토했고 기각한다.**
`.marblo-console { --color-zinc-50: <950 의 값>; … }` 로 회색 램프를 통째로 뒤집으면 컴포넌트를
**한 줄도 안 고치고** 265개 클래스가 한 번에 밝아진다. 실제로 작동한다(§2.1-1). 기각 이유:

- `zinc-400` 이 어떤 화면에서는 밝고 어떤 화면에서는 어둡다는 뜻이 되어, **낱말이 거짓말을
  하기 시작한다.** 다음 사람이 읽는 것은 이 문서가 아니라 클래스 이름이다.
- `red`·`amber` 도 같이 뒤집어야 하는데(§3.1 의 사용처), 경고색은 명도만 뒤집으면 안 된다 —
  밝은 바탕의 경고는 **채도와 명도가 함께** 바뀌어야 읽힌다.
- **가드를 걸 자리가 사라진다.** 뒤집기는 "하드코딩 색을 그대로 둬도 된다" 는 뜻이라,
  §3.3 이 막으려는 드리프트를 오히려 영구화한다.

★뒤집기는 **싸지만 되돌리기 어려운 종류의 싸구려**다. 의미 토큰은 **한 번 비싸고 그 뒤로 싸다.**

| `#4f46e5`(brand-600) on `#ffffff` | **6.29:1** | ✅ AA 통과 (AAA 7:1 은 미달) |
| `#4338ca`(brand-700) on `#ffffff` | 7.90:1 | ✅ AAA — 본문 링크가 필요하면 여기 |

**색을 만든 게 아니라 같은 램프에서 한 칸 내려온 것이고, 그 한 칸이 AA 미달을 통과로
바꾼다.** 어두운 화면에서 500 이 맞았던 것도 같은 이유다 — 램프는 이미 양쪽을 갖고 있었다.

### 3.3 ★가드 — 넣는다. 무엇을 잡는지 정확히 쓴다

티켓이 "가드를 넣을지 판단해라" 고 했다. **넣는다.** 근거는 셋이다: (a) §3.1 의 242개 자리,
(b) §2.3 의 조용한 무색이 v4 에서도 재현됨, (c) **이 저장소에 이미 같은 방식의 가드가 있고
작동 중이다** — `v3/tests/unit/team-usage-axis-guard.test.ts`(소스에 축 이름이 **등장하는 것
자체**를 실패로 잡는다). 새 방식을 발명하지 않고 그 관용구를 그대로 쓴다.

가드가 잡는 것 다섯:

1. **콘솔 스코프 파일에 팔레트 클래스 금지** — `text-zinc-*` `bg-red-*` `border-amber-*` 등이
   등장하면 실패. 의미 토큰만 허용.
2. **하드코딩 색 리터럴 금지** — `#rrggbb` · `rgb(` · `oklch(` 가 컴포넌트에 등장하면 실패.
   (색 리터럴이 사는 곳은 `globals.css` 하나다.)
3. **★죽은 토큰 금지 — §2.3 이 요구한 검사.** 소스에 쓰인 모든 `bg-…`/`text-…`/`border-…`
   의미 토큰 이름을 모아, 그 각각이 `globals.css` 의 `@theme` **와** `.marblo-console` **양쪽에**
   정의돼 있는지 본다. **한쪽만 있으면 실패** — 그게 정확히 "한쪽만 고쳐서 반대쪽이 조용히
   낡는" 사고다.
4. **★스코프 토큰에 알파 수식자 금지 — §2.2 가 요구한 검사.** 콘솔 파일에서
   `bg-surface/60` 같은 `토큰/숫자` 형태가 나오면 실패. 반투명이 필요하면 토큰을 만든다.

5. **★`@theme inline` 에 색 별칭 금지 — §2.1-3 이 요구한 검사.** `globals.css` 의
   `@theme inline` 블록에 `--color-*` 가 등장하면 실패. (거기 있어도 되는 것은 `--font-*`
   처럼 빌드 시점에 값을 알 수 없는 변수뿐이다.) **이 검사가 없으면 누군가 색 별칭을 다시
   `inline` 으로 옮기는 순간 스코프 테마가 조용히 죽는다.**

★검사 3번이 이 가드의 본체다. 1·2번은 규율이고, **3·5번만이 "조용히 죽는" 종류를 잡는다.**
그리고 3·5번의 공통점이 이 문서가 계속 말하는 것이다 — **v4 의 실패는 빨간 글씨가 아니라
무색이다.** 눈으로는 절대 못 잡는다.

실행 위치: `marblo-web` 의 기존 러너 그대로(`npm test` = `tsx --test "src/**/*.test.ts"`).
새 도구도, 새 CI 단계도 없다.

### 3.4 공용 컴포넌트를 어떻게 양쪽에서 살리나

★**규칙 하나로 끝난다: 공용 컴포넌트는 자기 바탕색을 모른다.**

- 공용 컴포넌트(`StatTile`·`BasisBadge`·`ActorChip`·표·배지)는 **의미 토큰만** 쓴다.
  `bg-surface-raised text-ink border-line` — 어떤 스코프에 놓이든 그 스코프의 값을 읽는다.
- **바탕을 정하는 것은 래퍼뿐이다.** `.marblo-console` 이 있으면 밝고, 없으면 어둡다.
  컴포넌트에 `theme` prop 도, `isDark` 분기도 넣지 않는다 — 분기를 넣는 순간 두 벌이 된다.
- ★**선행 문서 §2 의 금지선은 그대로다:** 밝아졌다고 `/admin` 컴포넌트를 `/team` 이 재사용하면
  안 된다. `ProjectAuditPanel.tsx` 가 안전한 이유는 컴포넌트가 아니라 **게이트**다. 공유하는
  것은 **토큰과 무색(無色) 프리미티브**까지이고, **노출 필드를 아는 컴포넌트는 공유하지 않는다.**

## 4. ★결정 ① — 차트 라이브러리를 도입하나

### 4.1 결론

> **도입한다. 정본은 `recharts` 다.**
> 사장님 결정(2026-08-25)과 #1211 의 머지 결과를 따른다. 근거는 bakeoff 가 제시한 기준

> 클릭 인터랙션이 필요하다.

이 문서의 기존 결론은 "도입하지 않는다" 였다. 그 결론은 **뒤집혔다.** 하지만 반대 근거는
지우지 않는다. 특히 "라이브러리는 결측을 선으로 잇고 값 없으면 0 으로 떨어뜨린다" 는
지적은 실제 위험이었고, #1211 이 그 위험을 코드와 테스트로 닫았다(§4.5).

### 4.2 번들 — 추정이 아니라 실측

esbuild 로 실제 번들해 gzip 을 잰 값이다(React 19.2.4 + react-dom 기준선을 뺀 순증).

| 후보 | 버전 | gzip 총 | **순증** | 렌더 방식 |
| --- | --- | --- | --- | --- |
| 기준선 (react + react-dom) | 19.2.4 | 60,141 B | — | — |
| **손 SVG (오늘)** | — | 60,141 B | **+0 B** (앱 코드 ~1.5 KB) | SVG |
| `uplot` | 1.6.32 | 83,162 B | **+22.5 KB** | **canvas** |
| `@visx/*` (shape·scale·axis·tooltip·group) | 4.0.0 | 88,638 B | **+27.8 KB** | SVG |
| `chart.js` + `react-chartjs-2` | 4.5.1 | 120,141 B | **+58.6 KB** | **canvas** |
| `recharts` | 3.10.1 | 175,381 B | **+112.5 KB** | SVG |

★측정 방식의 한계를 밝힌다: esbuild 번들이라 Next/Turbopack 의 트리셰이킹과 정확히 같지는
않다. 다만 `recharts` 는 배럴 재수출 구조라 실제로도 잘 안 털리는 쪽으로 알려져 있고,
**순위가 뒤집힐 만한 차이는 아니다.**

`/team` 은 **로그인 게이트 뒤 화면**이라 초기 LCP 압박이 크진 않다. `recharts` 의 +112.5 KB 는
여전히 비싸다. 다만 사장님 결정은 단일 화면의 네 인터랙션만이 아니라 **앞으로 늘어날 분석
차트 종류와 클릭 상호작용의 표준화 비용**까지 본 것이다. 이 기준에서는 손 SVG 의 +0 B 보다
라이브러리의 일관된 축·툴팁·범례·상호작용 레이어가 더 값이 있다.

### 4.3 SSR 호환

| 후보 | SSR | 문제 |
| --- | --- | --- |
| 손 SVG | ✅ 서버에서 완전히 렌더 | 없음 |
| `@visx` | ✅ 폭·높이를 명시하면 서버 렌더 | `ParentSize` 를 쓰면 클라 전용이 된다 → 안 쓴다 |
| `recharts` | ⚠️ `ResponsiveContainer` 가 DOM 을 재서 폭을 얻는다 | 클라 전용 + 첫 프레임 `width=0` |
| `chart.js` / `uplot` | ❌ `<canvas>` 는 서버 출력이 **없다** | 스크립트 실행 전까지 빈 상자 |

#1211 의 대응: `ChartFrame` 이 같은 높이의 스켈레톤을 먼저 세우고, 차트는 클라이언트에서
hydration 된 뒤 그린다. 즉 SSR 마크업 0개라는 비용은 남지만, 빈 칸과 레이아웃 이동은 막는다.

### 4.4 접근성 — ★여기서 남는 조건

**오늘의 손 SVG 는 이미 접근성이 있었고, 대부분의 라이브러리는 그걸 후퇴시킬 수 있다.**
`AnalyticsPanel.tsx:1190` 의 실제 코드가 하고 있는 것:

- `role="img"` 를 단다.
- **수치를 `<text>` 로 직접 그린다** — 코드 주석이 이유를 적어 뒀다:
  *"값 라벨 — 색·툴팁에만 의존하지 않고 수치를 직접 노출"*.
- 각 데이터 포인트에 투명 히트 사각형 + 네이티브 `<title>` 툴팁 + 클릭 드릴다운.

`chart.js`·`uPlot` 은 canvas 라 **스크린리더에 아무것도 안 준다** — 접근 가능한 표를 옆에
따로 지어야 하고, 그러면 라이브러리가 아낀 분량이 되돌아온다. `recharts` 도 기본 툴팁만으로는
부족하다.

#1211 의 대응: `accessibilityLayer` 를 켜고, 같은 데이터를 표로 노출하며, 툴팁 row 렌더링을
순수 함수로 떼어 테스트한다. 이건 "라이브러리가 접근성을 알아서 준다" 가 아니라
**라이브러리 위에 Marblo 접근성 계약을 얹는다** 는 결정이다.

### 4.5 ★기존 반대 근거 — 맞았다. 그래서 #1211 이 테스트로 닫았다

이 대시보드의 규율은 **"모르는 값은 NULL + 사유, 0 으로 그리지 않는다"** 이고, 그건 장식이
아니라 이 제품이 파는 것 자체다(선행 문서 §5.4). 그런데 **모든 차트 라이브러리의 기본 동작은
정확히 그 반대다:**

- 결측 구간을 **선으로 이어 버린다**(interpolate) → "그 기간에도 값이 있었다" 는 거짓 시계열.
- 값이 없으면 **0 으로 떨어뜨린다** → 오케 미수집이 "오케는 공짜" 가 된다.
- 범례에 축을 넣으면 **미수집 축도 0짜리 계열로 그려진다.**

이 지적은 틀리지 않았다. #1211 이 실제로 그 싸움을 했다. 다음 줄들은 다음 사람이 지우면 안
되는 안전장치다.

| 위험 | #1211 이 닫은 방식 | 고정 근거 |
| --- | --- | --- |
| 결측 구간을 선으로 잇는다 | `connectNulls={false}` 를 `TimeSeriesChart` 와 `MultiSeriesChart` 에 명시 | `discipline.test.tsx` 가 선 path 의 `M` subpath 개수를 검사해 값 없는 날에서 선이 실제로 끊기는지 본다 |
| 값 없는 날을 0 으로 떨어뜨린다 | row 에 `null` 을 넣고 표·툴팁은 `—` 를 렌더 | 같은 테스트가 꼭짓점 개수와 축 바닥 접촉 여부를 검사한다. `interaction.test.tsx` 는 툴팁 row 가 `null` 을 0 으로 채우지 않는지 본다 |
| 적재 전·미수집·empty 가 0 선처럼 보인다 | `ChartDataState` 를 호출부가 명시하고 `pending`/`empty` 는 선을 그리지 않는다 | `discipline.test.tsx` 의 "적재 전 / 값 없음 / 전부 0" 케이스 |
| 축 자동 스케일로 스코프 밖 최댓값이 눈금에 새어 나온다 | `resolveYDomain` 이 숫자 도메인을 만들고, 숨긴 계열은 축에서도 뺀다 | `discipline.test.tsx` 의 Y축·범례 테스트 |
| 숫자 도메인을 줬는데도 상한이 안 막힌다 | `allowDataOverflow` 를 켠다 | 같은 테스트가 `[0,100]` 을 줘도 900 눈금이 찍히지 않는지 검사한다 |

★마지막 항목은 #1206 의 반대 근거 덕에 새로 잡힌 구멍이다. "도메인을 숫자로 주면 자동 스케일을
끈 것" 이라고 적어 둔 코드가 있었지만, **recharts 는 `allowDataOverflow` 없이는 데이터를 보며
도메인을 늘린다.** 즉 막았다고 생각한 축 누출 경로가 실제로는 열려 있었다. #1211 은 그 사실을
테스트로 재현하고 `allowDataOverflow` 를 명시해 닫았다.

`/team` 이 그려야 하는 특수 상태 넷 — 라이브러리 기본값으로는 하나도 안 나온다:

| 상태 | 어떻게 그리나 |
| --- | --- |
| `notCollected` (오케) | 계열을 **안 그린다.** 차트 위에 빗금 밴드 + 사유 문장 |
| `partial` (수집 시작을 걸친 창) | 수집 시작일 이전 구간을 **회색 빗금**, 그 뒤만 실선 |
| `pending` (수집됐지만 이 구간 적재 없음) | 빈 차트 + "적재 전" 문장. 0 선을 **안 긋는다** |
| `unwired` (봉투에 축이 없음) | 차트 자리를 **비우고** "계약 미배선" 을 적는다 |

★**기간 줌은 드래그 브러시로 만들지 않는다.** 30점짜리 일별 시계열에서 드래그 브러시는
가치가 낮고(픽셀당 하루), 비용이 가장 크며(포인터 이벤트 + 키보드 동등 경로 + 터치), 무엇보다
**서버가 이미 `days` 인자를 받는다**(`getTeamUsageSummary({ days })`).

> **기간 선택기(7 / 30 / 90일 + 사용자 지정)로 만든다.** SaaS 대시보드의 표준 조작이고,
> 서버 재조회라 **줌한 구간의 수치가 실제로 정확해진다**(브러시는 이미 받은 30점을 확대할
> 뿐이다). 접근성은 그냥 버튼 그룹이라 공짜다.

★이 재해석은 `recharts` 를 쓰더라도 유지한다. 브러시는 이미 받은 점을 확대할 뿐이지만,
기간 선택기는 서버가 `days` 로 실제 그 구간을 다시 계산하게 만든다. **정확성은 브러시가 아니라
서버 재조회에서 온다.**

### 4.8 뒤집는 트리거 — 이제는 "라이브러리 제거" 트리거다

`recharts` 를 정본으로 둔다. 다만 아래가 깨지면 라이브러리 선택을 다시 연다.

1. #1211 의 discipline 테스트가 약해져 결측·0·축 누출을 다시 못 잡게 된다.
2. `recharts` 의 SSR/클라 전용 비용이 로그인 뒤 콘솔에서도 실제 성능 문제로 측정된다.
3. 조직 대시보드 호출부가 차트 계약 바깥에서 값을 보정하기 시작한다. 집계는 차트 밖, 차트는 그리기만 한다.

## 5. ★결정 ③ — 로그인 게이트와 그 뒤의 열람 범위

### 5.1 게이트는 이미 있다. 화면이 할 일은 **판정하지 않는 것**이다

`TeamOverviewClient.tsx` 는 이미 3상태다: `!authReady` → 스피너 / `!user` → 로그인 유도 /
`user` → 본문. 그리고 그 파일 머리말이 이 설계의 핵심을 이미 적어 뒀다:

> *"★권한을 화면에서 판정하지 않는다. 서버가 `context.auth.uid` 로 테넌트를 도출해 걸러
> 보내고, **화면은 못 볼 것을 안 받는다.** 그래서 여기에 role 검사도, owner 비교도 없다 —
> 있으면 그게 곧 우회 가능한 게이트다."*

### 5.2 ★"firestore 룰 위에 얹어라" 를 정확히 어떻게 지키나

티켓의 지시는 옳고, **지키는 방법이 이미 코드에 있다.** 다만 한 가지를 분명히 해야 한다:

> **Cloud Functions 는 Admin SDK 를 쓰므로 firestore 룰을 우회한다.**
> `teamAudit.ts:43` 이 이걸 명시한다 — *"Admin SDK 는 보안 규칙을 우회하므로 룰이 막아주리라
> 기대할 수 없다."*

그래서 "룰 위에 얹는다" 의 실제 뜻은 **"룰과 같은 판정을 서버가 한 번 더 한다"** 이고,
`teamAudit.ts:57-63` 이 룰의 술어와 **1:1로** 맞춰 뒀다:

| 역할 | firestore.rules 술어 | 서버 재판정 | 화면이 받는 것 |
| --- | --- | --- | --- |
| owner | `projects/{id}.ownerId == uid` (`isProjectOwner`) | `scopeForRole → "team"` | 프로젝트 전체 사건 |
| admin | `memberRoles/{id}_{uid}.role == 'admin'` | `scopeForRole → "team"` | 프로젝트 전체 사건 |
| member | `uid in projects/{id}.members` (`isProjectMember`) | `scopeForRole → "self"` | **자기 사건만** |
| none | — | `null` | `state:"disabled"` + **0행** |

★**웹 클라이언트는 Firestore 를 직접 한 줄도 읽지 않는다.** 콜러블 두 개(`getTeamUsageSummary`,
`getTeamProjectAudit`)가 전부다. 이게 룰 표면을 안 늘리는 방식이고, **화면 설계로서의 함의는
이것이다: 조직 관리자가 자기 조직 것만 보는 것을 화면이 보장하는 게 아니라, 화면이 그 보장을
망칠 수 없는 구조로 두는 것.**

### 5.3 화면 설계에 남는 몫 — 셋

서버가 다 해 주므로 화면이 할 일은 **UI 로 권한을 흉내 내지 않는 것** 셋뿐이다.

1. **프로젝트 셀렉터는 서버가 준 목록으로만 만든다.** `auditEnv.projects` = 호출자가 역할을
   가진 것만. **화면이 프로젝트를 찾아 나서면 그게 곧 권한 판정이다.** (오늘 이미 그렇다.)
2. **URL 의 `projectId` 는 권한 근거가 아니다.** 서버가 허용 집합과 **교집합**으로만 쓴다.
   → 없는 id 를 넣어도 404 를 그리지 않는다. **존재 여부조차 화면이 판정하지 않는다** —
   판정하면 그 자체가 "이 프로젝트는 있다" 는 정보 누설이다.
3. **`scope:"self"` 를 숨기지 말고 밝힌다.** 일반 멤버 화면 상단에 *"본인 기록만 표시됩니다"*
   를 상시 배지로 둔다. ★이게 신뢰의 핵심이다 — 감사 화면에서 **덜 보인다는 사실 자체가
   보여야** 사용자가 화면을 믿는다.

★그리고 **`self` 스코프에서 팀 총계를 절대 그리지 않는다.** `teamUsage.ts:31` 이 이유를 적어
뒀다: 2인 팀에서 `팀총계 − 내사용량 = 상대방 사용량` 이라 **총계를 여는 순간 약속이 산술로
깨진다**(차분 공격). 밝은 화면에서 "요약 타일" 을 예쁘게 만들려다 이 자리에서 사고가 나기
가장 쉽다 — 요약 타일은 **스코프에 따라 개수가 달라진다.**

### 5.4 로그인 게이트 화면 자체

오늘은 어두운 껍데기 안의 문단 하나다(`TeamOverviewClient.tsx:192-210`). 콘솔 스코프가 생기면
**게이트도 콘솔 안에 있어야 한다** — 로그인 전엔 검고 후엔 흰 화면은 "다른 사이트로 갔나" 로
읽힌다.

## 7. 원장 열람 — 무엇을 그리고 무엇을 안 그리나

### 7.1 ★티켓 지시를 정정한다 — `instructionRedacted` 는 **이 화면에서 금지 필드다**

티켓은 *"원장에 `instructionRedacted` 라는 표시용 필드가 이미 있으니 그걸 써라"* 고 했다.
**고객 화면에서는 그 반대다.** 근거 넷:

| # | 근거 |
| --- | --- |
| 1 | `teamAudit.ts:1240` `FORBIDDEN_RESPONSE_KEYS` 에 `"instructionRedacted"` 가 `params`·`instruction`·`result` 와 **나란히** 있다 |
| 2 | `teamAudit.ts:1374` `OPERATOR_ONLY_PATTERNS` 정규식이 사용자 문장에 그 낱말이 나오면 실패시킨다 |
| 3 | `teamAudit.test.ts:403` — *"★원장 자유 텍스트(`params`·`result`·`instructionRedacted`)가 응답에 없다"* |
| 4 | `docs/team-usage-overview-design-2026-08-21.md:812` 의 **"안 보여주기로 한 것"** 표: `instructionRedacted` \| *"scrub 됐어도 **지시문 = 프롬프트**다"* |

`instructionRedacted` 를 **쓰는** 곳은 `projectAudit.ts:658` 이고 **그건 우리(플랫폼 admin)
화면**이다. 즉 이 필드는 **어드민 축에서 허용, 고객 축에서 금지**다. 티켓이 두 축을 섞었고,
그건 선행 문서 §2 가 *"한번 섞으면 두 번 다시 못 푼다"* 고 경고한 바로 그 경계다.

★**지시의 취지는 그대로 지킨다 — 오히려 더 세게.** 취지는 "지시문 원문을 뿌리지 마라" 였고,
웹 화면은 **`params` 도 `instructionRedacted` 도 애초에 받지 않는다.** 화면이 조심하는 게
아니라 **봉투에 자리가 없다.**

### 7.2 데스크톱 구멍은 여기서 고치지 않는다 — 반복만 안 하면 된다

`v3/src/components/agents/AuditTimeline.tsx:137` 의 `JSON.stringify(log.params, null, 2)` 는
선행 문서가 **PR-1** 로 이미 떼어 놓은 별건이다(데스크톱 렌더러). 이 티켓의 임무는
*"웹에서 같은 실수를 반복하지 마라"* 이고, §7.1 이 그 답이다:
**웹은 서버가 안 보내므로 반복할 수단이 없다.**

### 7.3 대신 화면이 반드시 하는 것 — **안 보여준다는 사실을 보여준다**

`getTeamProjectAudit` 응답의 `withheld` 배열(10줄, 안정 코드 + ko 문장)을 **접어 두지 말고
감사 탭 하단에 상시 노출한다.**

> **이 화면이 일부러 빼는 것 (10)**
> · 툴 인자 원문 · 지시문 · 툴 실행 결과 · 활동 본문 · 개인 툴 호출 전부
> · 에스컬레이션 · 미션 목표 문장 · 저장소 경로 · 금액·토큰 전부 · 원시 신원

★**이건 면책 문구가 아니라 제품 기능이다.** 기업이 사는 것은 "다 보여주는 화면" 이 아니라
**"무엇을 안 보는지 말할 수 있는 화면"** 이다 — 고객사가 자기 직원에게 이 화면을 설명해야 하고,
그때 필요한 게 정확히 이 목록이다. 접어 두면 그 가치가 사라진다.

★그리고 **금액이 감사 탭에 한 필드도 없다는 사실**도 밝힌다. 이유가 있다 — 감사 탭은 사용량
게이트 밖이라, 돈을 실으면 `TEAM_USAGE_EFFECTIVE_FROM` 게이트가 감사 탭을 경유해 우회된다
(`teamAudit.ts:32`). 밝은 화면에서 "요약 타일에 비용도 넣자" 는 제안이 나올 자리가 정확히
여기다. **넣으면 게이트가 뚫린다.**

## 8. 숫자 표기 규율 — 어드민 재설계와 같은 규율

### 8.1 ★오케 지출 — `0` 이 아니라 `미수집`

**완료기준이자 출시 차단 사유다.** 화면이 지켜야 할 것 넷:

1. **요약 타일 4번째 칸을 빈칸 + 빗금으로 그린다.** 숫자를 안 쓴다.
2. **최상단 배너**로 고지한다(§6.1). 접히지 않는다.
3. **차트에서 오케 계열을 안 그린다.** `<GapBand>` 로 미수집 구간을 빗금 처리(§4.6).
4. **잔재 구간(2026-05~06)을 시계열로 그리지 않는다.** `deriveOrchestratorCell` 이 이미
   `not_collected` 면 측정값이 딸려 와도 버린다 — **화면이 그 판정을 되돌리지 않는다.**

★**문장은 서버가 준 것을 그대로 그린다. 화면이 수치를 지어내지 않는다.**
이건 규율이자 실무적 이유가 있다 — 서버 산문(`ORCHESTRATOR_NOT_COLLECTED_NOTE`)과 프론트
계약 주석(`teamUsageContract.ts:13-18`)이 **"29%" 라는 수치의 진위에 대해 지금 서로 다른 말을
하고 있다.** 서버는 *"전체 사용량의 29%"* 라 적고, 프론트 계약은 *"그 행들은 콜드부트
reconnect 버그의 중복청구로 밝혀졌고, 실지출이 아니었으므로 비중을 말하면 그 자체가 거짓"*
이라 적는다. **화면이 문장을 그대로 그리면 이 논쟁이 서버 한 곳에서 끝난다** — PR-3(오케 수집
배선) 소유자가 산문을 고치면 화면은 배포 없이 따라온다. 오케에 별건으로 넘겼다.

★**빈칸의 대비.** 밝은 바탕에서 "빈칸" 은 그냥 흰색이라 **아무것도 없는 것처럼 보인다.**
어두운 화면에서보다 훨씬 위험하다. 그래서 미수집 칸은 흰 여백이 아니라
**`--color-warn-soft` 바탕 + 빗금 + 아이콘** 으로 **적극적으로 그린다.**

### 8.2 모르는 값은 NULL + 사유

- `UsageCell` 다섯 상태(`measured`/`partial`/`notCollected`/`pending`/`unwired`)를
  **화면이 숫자로 환원하지 않는다.** 계약이 이미 타입 수준에서 그 경로를 막아 뒀다.
- `null` 은 `0` 이 아니다. `—` 로 그리고 **왜 모르는지**를 옆에 적는다.
- **라벨 없는 숫자 금지** — `basis` 가 항상 실리고, 화면은 항상 그린다.
- `hasRows === false` 는 **0 이 아니다** — 텔레메트리를 끈 사람이 "가장 일 안 한 사람" 으로
  보이는 자리다. 그 행은 금액 대신 사유를 그린다.

### 8.3 표본 5 미만이면 수치 대신 표본 부족

어드민에 이미 있는 규약을 그대로 쓴다(`AnalyticsPanel.tsx:1509-1512`):

- **분수를 크게, 퍼센트를 그 옆 작은 글씨로.** 그 반대가 아니다.
- 분모가 0 이면 `0.0%` 가 아니라 `—` — 실패가 아니라 **판단할 표본이 없다.**
- **표본 5 미만이면 퍼센트를 안 그린다.** 수치 자리에 "표본 부족(n=4)" 을 적는다.
- ★`/team` 은 어드민보다 **표본이 더 작다** — 지금 다중 멤버 프로젝트가 **2인 하나**다.
  구성원별 '비중' 열은 거의 항상 표본 부족 상태로 그려진다. **그게 정상이고, 그렇게 보여야
  한다.** (어드민 임계 `SMALL_SAMPLE_MAX = 10` 과 달리 티켓이 지정한 5 를 쓴다.)
