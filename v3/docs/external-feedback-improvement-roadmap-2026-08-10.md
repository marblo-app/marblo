## 3. ★핵심 리프레임

### 3-A. 솔로 단일 에이전트 축에서 피드백은 **전부 맞다** — 여기서 다투지 않는다

한 사람이 에이전트 한 대를 굴려 코드를 짜는 축에서 Marblo 가 Cursor·Claude Code·Codex 보다 나은 이유는 **없다.** 그들은 모델 벤더 본인이거나 몇 년치 IDE 통합을 가진 팀이다. 그 축에서 UI/UX 로 이기려는 시도는 구조적으로 진다.

**이 문장을 우리 입으로 먼저 말하는 것이 §4 전체의 전제다.** 이걸 인정하지 않으면 F4·F5 에 대한 모든 답이 변명으로 읽힌다.

### 3-B. 우리 축은 **멀티에이전트 팀 조율**이다 — 정직하게, 과장 없이

"Claude Code 로는 안 되는 것" 을 과장하면 F7(기획자 느낌)을 스스로 증명하게 된다. 그래서 **경쟁사가 실제로 되는 것은 된다고 적는다.**

| 능력                                         | Claude Code 단독         | Marblo                                     | 정직한 단서                                                         |
| -------------------------------------------- | ------------------------ | ------------------------------------------ | ------------------------------------------------------------------- |
| 서브에이전트 병렬 실행                       | ✅ 된다(in-process Task) | ✅                                         | **여기서 이기려 하지 않는다**                                       |
| 서로 다른 **벤더 CLI** 동시 운용             | ❌                       | ✅ Claude·Codex·Grok·GLM·MiniMax·Kimi·로컬 | 하네스별 세션·resume 계약이 전부 다르다는 것이 실제 난이도          |
| 실행 중 에이전트를 **죽이지 않고** 관측·개입 | ❌ (중단하면 맥락 소실)  | ✅ 라이브 PTY + 보드                       | `CORE_VALUE_PROPOSITION` P1·P2 가 이미 이 문장을 갖고 있다          |
| **티켓당 워크트리 격리**                     | ❌                       | ✅                                         | 동시 N대가 서로를 밟지 않는 유일한 이유                             |
| 에이전트·모델별 **비용 귀속**                | ❌                       | ✅ `cost_logs` + taskId 축                 | 단, 구독 무시 list-price **추정치**다 — 이 단서를 뗀 채 팔지 않는다 |
| **safe-merge 판단의 append-only 기록**       | ❌                       | ✅                                         | "누가 무엇을 왜 머지했나" 가 남는다                                 |
| 같은 티켓의 **모델 교차검증**                | ❌                       | ✅                                         | `#896` 이 재려는 바로 그 축                                         |

> **한 문장 정리**: Claude Code 는 **에이전트를 잘 돌린다.** Marblo 는 **여러 에이전트가 같은 저장소에서 동시에 일해도 서로를 안 밟고, 그 결과를 사람이 증명할 수 있게** 한다. 앞은 그들이 이겼고, 뒤는 그들이 풀지 않는 문제다.

| `marblo.app/legal/privacy`         | 한국어 | 공개           | **PIPA 법정 문서**(14개 조항) — 개발자용 요약 아님 |
| 영어 · 다운로드 **전** 표면        | —      | **없음**       | ❌                                                 |

Edward 의 "텔레메트리 불명" 은 **정보 부재가 아니라 순서 문제**다. 그가 결정을 내려야 하는 시점(다운로드 전)에, 그가 읽는 언어(영어)로, 그가 묻는 형식(무엇을 보내고 무엇을 안 보내는가 · 끌 수 있는가)으로 된 문서가 없다.

**④ "한 방 데모" 자산은 완성돼 있고, 꺼져 있다**

공개 Replay 는 저장·비식별화·공개 페이지·OG·원클릭 소셜 공유까지 전부 착지했다(`#732`·`#735`·`#737`·`#740`). 그런데 진입점이 `replayDashboardFlag`(기본 **OFF**) 뒤에 파킹됐다 — 2026-08-08 에 "데일리 UX 로 안 쓰인다" 는 **옳은 판단**으로 내린 결정이고, 코드는 "마케팅 기능으로 재사용할 백로그" 를 이유로 남겨 뒀다.

> 그 백로그가 **지금** 필요한 것이다. F6("모먼트가 없어서 테스트조차 안 했다")에 답하는 물건은 새 데모가 아니라, **이미 만들어 둔 공유 가능한 실행 기록**이다.

### 3-D. 그래서 개선의 형태

```
❌  기능을 하나 더 만든다  →  크라우디드 마켓에 한 칸 더 들어간다(F5 를 스스로 증명)
✅  있는 것을 보이게 한다  →  L1 투명성
✅  차별화를 읽히게 한다   →  L2 레지빌리티
✅  주장을 근거로 바꾼다   →  L3 개발자 신뢰
✅  우리 입을 하나로 맞춘다 →  L4 포지셔닝
```

### 2주 권장 순서

```
주 1  ─  A1 → A3 → A7 → A2 → A4        (전부 "있는 걸 보이게". 신규 개발 거의 0)
         └ 이 다섯이 F1·F2·F3·F4·F7 을 닫는다

주 2  ─  A5 → A6                        (포지셔닝 정합 → ★한 방 데모 발간)
         └ A6 이 F6("모먼트 부재")에 답하는 유일한 물건

이후  ─  A8 → A9                        (기술 해자 서사. 별도 예산·시간 결정 필요)
```

**왜 이 순서인가**: A1~A4 는 합쳐도 하루치 작업이면서 피드백 10개 중 5개를 닫는다. A6 은 가장 임팩트가 크지만 "실제로 한 번 운용해서 발간" 이라는 실행이 필요해 뒤에 둔다. A8 은 임팩트가 최고지만 유일하게 **난이도 고**이고 별도 판단이 필요하므로 2주 밖에 둔다.
