## 2. 관점 A — GTM / 시장

**한 줄**: 우리 문제는 제품이 아니라 **아무도 우리를 모른다는 것**이고, 그 앞에서 로컬/클라우드 논쟁은 사치다. 다만 클라우드는 **제품이 아니라 마케팅 도구**로 지금 필요하다.

### A-1. 내가 읽은 데이터

월 웹 방문 542. 이건 "전환율이 낮다"의 문제가 아니다. **모수가 없다.** 542 는 개인 블로그 수준이다.
그 아래 141 → 26 → 6 을 보면 다운로드 페이지까지 온 사람의 **96% 를 잃는다.** 이 사람들은 이미 관심을 표명한, 우리 퍼널에서 제일 비싼 사람들이다.

그리고 파운더 데이터가 더 아프다: **선정 61명 → 그랜트 32 → 최근 앱을 켠 사람 19 → 로그인 이벤트 6.**
이건 유입 문제가 아니다. **이미 손에 쥔 61명을 놓친 것**이다. 우리는 "유저가 없다"고 말하면서 61명에게 무료 Pro 를 줘놓고 55명을 잃었다.

### A-2. 그래서 로컬 vs 클라우드에 대한 내 답

**둘 다 틀린 질문.** 다만 실무적으로:

- **로컬 유지**에 동의한다. 클라우드가 유입을 만들지 않는다. 클라우드는 **전환을 만든다** — 그런데 우리는 전환시킬 트래픽 자체가 없다.
- **그러나 "클라우드 나중"에는 반대한다.** 141 명이 매달 다운로드 페이지에 온다. 그 사람들에게 지금 줄 수 있는 건 "받아서 설치하고 CLI 깔고 인증하세요" 뿐이다. **웹에서 30초 안에 뭔가 도는 걸 보여주는 표면**이 없으면 저 141 은 계속 새 나간다.
- 내가 원하는 건 클라우드 **제품**이 아니라 **"지금 브라우저에서 돌아가는 것 하나"** 다. 완료 1건 상한, 데모 레포 고정, 우리 토큰. 유저당 실비 $10~25 로 잡으면 월 100명 체험에 **$1,000~2,500**. 이건 한국 개발자 타겟 광고 예산보다 싸고, 전환 품질은 비교가 안 된다.

### A-3. 한국 시장 관점 — 아무도 안 보고 있는 카드

Cursor 가 2026-07-28 에 **인도 전용 ₹649** 를 냈다. 글로벌 플레이어가 **지역 가격·지역 결제(UPI)** 를 쓰기 시작했다는 뜻이다. 한국에도 온다.

우리가 가진 구조적 이점은 지금 딱 두 개다:

1. **한국어가 1급 시민** — 앱·오케 대화·문서 전부. Cursor 는 한국어 로케일이 있지만 제품 경험은 영어 기준이다.
2. **국내 결제(토스/포트원)와 국내 고객 접촉** — 우리는 이미 배선돼 있고, 이건 글로벌 플레이어가 제일 늦게 하는 일이다.

**GTM 권고: "한국 개발자를 위한 에이전트 함대 관제" 로 좁힌다.** 글로벌 개발자 시장에서 Cursor·Orca 와 싸우는 건 지금 우리 규모로 불가능하다. 국내에서 1위가 되고 그걸 근거로 나간다.

### A-4. 대중 세그먼트 — 죽이지 마라

개발자 시장은 **Cursor 가 무료 티어로, Orca 가 OSS 로** 양쪽에서 막고 있다. 우리가 개발자에게 파는 논리는 "오케가 여러 에이전트를 지휘한다"인데, 그건 **이미 CLI 구독을 여러 개 굴리는 상급 개발자**에게만 의미가 있다. 그 시장은 한국에 몇 천 명 규모다.

비개발자/기획자/1인 창업자에게 "티켓 만들면 에이전트가 짠다"는 훨씬 강한 이야기다. 지금 추격하자는 게 아니다. **죽이지 말라는 것**이다. 비기너 모드가 이미 그 방향이고, 그걸 "개발자 온보딩 개선"으로만 프레이밍하면 우리가 가진 유일한 차별 서사를 스스로 버린다.

### A-5. GTM 권고 3줄

1. 8주 예산의 **절반을 유입에** 쓴다. 제품 개선은 나머지 절반.
2. **파운더 61명 리커버리 캠페인**을 최우선. 이미 손에 있는 사람이고, 왜 떠났는지 물어볼 수 있는 유일한 표본이다(n=55).
3. **웹 데모(클라우드 최소형)를 지금** 만든다 — 제품이 아니라 랜딩의 일부로.

## 3. 관점 B — 엔지니어링 / 인프라 비용

**한 줄**: 토큰 비용은 두 번째 문제다. **첫 번째 문제는 우리에게 이걸 지을 사람이 없다는 것**이고, 클라우드는 그 희소자원을 통째로 먹는다.

### B-1. 바인딩 제약은 돈이 아니라 빌드 용량

GTM 이 "월 $2,500 이면 광고보다 싸다"고 하는데, **그 계산에서 빠진 게 엔지니어링 시간**이다. 클라우드 최소형이라도 실제로 필요한 것:

| 구성요소                           | 왜 필요한가                                      | 규모 추정 |
| ---------------------------------- | ------------------------------------------------ | --------- |
| 컨테이너 오케스트레이션 + 수명주기 | 유저별 격리 VM/컨테이너, 유휴 회수, 동시성 상한  | 2~3주     |
| CLI 프리설치 이미지 + 인증 주입    | claude/codex 를 헤드리스에서 기동, 자격증명 전달 | 1~2주     |
| 시크릿·레포 접근                   | GitHub App 권한(FFrgruR7 미완), 유저 코드 격리   | 2주+      |
| 남용 방지 / 비용 상한              | 완료 건수 상한, 러너웨이 차단, 크레딧 회계       | 1~2주     |
| 운영 (온콜·장애·업데이트)          | **끝나지 않는다**                                | 상시      |

**보수적으로 6~9주.** 그리고 우리 Phase 1 전체 예산이 8주다. 즉 **클라우드 최소형 = Phase 1 을 통째로 취소하는 것**이다. GTM 의 "$2,500" 은 이 트레이드오프를 안 보여준다.

### B-2. 인증 모델 — A안은 논의에서 빼야 한다

클라우드에서 "유저의 Claude Max 구독을 서버에서 로그인시킨다"(A안)는 기술적으로도 계약적으로도 성립하지 않는다:

- 브라우저 device-code 인증을 헤드리스 VM 에서 대행 = 남의 구독 자격증명을 우리가 보관·재생하는 것.
- 우리 사내 메모리에 이미 같은 계열 사고가 기록돼 있다 — 크레덴셜 없는 env-swap 이 우리 Anthropic 자격증명으로 남의 모델명을 붙여 쿼터를 새게 한 건. 스폰 게이트를 `spawnNewAgent` 초크포인트로 내린 것도 그 이유다.
- **결론: A안 폐기.** 남는 건 B(유저 API 키) 와 C(우리 토큰).

B는 "CLI 설치 마찰"을 "API 키 발급 마찰"로 바꾼다. **초보에게 API 키는 CLI 설치보다 어렵다** — 결제수단 등록이 붙기 때문이다. 그러니 초보 온램프 목적에선 **C뿐**이고, C는 우리가 원가를 전부 진다.

### B-3. 비용 — 숫자를 정직하게

완료 1건 $3.85~$13.90 (평균 $8.25). **단 이 수치는 축이 흔들린다** — 같은 날 `cost_logs` 외부 합은 $0.19 다(#850 §11). 두 테이블이 다른 키를 쓴다.

**엔지니어링 관점에서 이건 "비용을 모른다"는 뜻이다.** 그리고 **비용을 모르는 채로 우리 토큰을 쓰는 서비스를 여는 건 하면 안 되는 일**이다. 클라우드 논의의 선행 조건은 아키텍처가 아니라 **비용 축 정합화**다.

컴퓨트는 상대적으로 싸다: 에이전트 러닝 시간 기준 완료 1건이 8~20분이므로, 유휴 회수를 제대로 하면 유저당 컴퓨트는 시간당 $0.05~0.2 수준에서 몇 십 센트다. **문제는 토큰이지 컴퓨트가 아니다.**

### B-4. Phase 1 목록도 너무 길다

CEO 리뷰의 F1~F5 중 F1(계측 3종)·F3(비기너 마감)은 이미 있는 걸 끝내는 것이라 싸다. F2(결과카드+공유)는 신규이고 공유 링크는 **서버 사이드 렌더 + 권한 모델**이 붙어 중간 이상이다. F4(install-ping)는 App Check 배선 + 텔레메트리 옵트인(E4w8) 선행 의존이 있다.

**엔지니어링 권고: F2 의 "공유 링크"를 1차에서 뺀다.** 결과 카드(로컬 표면)만 먼저. 공유는 리텐션이 실제로 올라간 다음에.

### B-5. 엔지니어링 권고 3줄

1. **클라우드는 게이트 후.** 이유는 비용이 아니라 **6~9주 빌드 용량 = Phase 1 전체**이기 때문.
2. **선행조건 2개 없이는 클라우드 논의 자체가 불가**: (i) `task_outcomes` vs `cost_logs` 비용 축 정합화, (ii) 인증 모델 A안 공식 폐기.
3. 지금 지을 수 있는 클라우드 비슷한 것 하나는 있다 — **스크립티드 데모 리플레이**(이미 `DemoMode` 존재). 인프라 0, 며칠. GTM 이 원하는 "브라우저에서 뭔가 도는 걸 본다"의 90% 를 준다.

## 4. 관점 C — 경쟁 (Cursor · Orca 실조사)

**한 줄**: 우리가 논쟁하는 사이 **카테고리를 뺏겼다.** Orca 가 3주에 star 를 2배로 늘렸고, 그 카테고리 이름이 "Agent IDE" 다. 로컬/클라우드는 이 사실 앞에서 부차적이다.

### C-1. Orca 는 우리 전제를 그대로 갖고 이겼다

이게 이번 조사에서 제일 불편한 발견이다.

| 항목               | Orca                               | Marblo             |
| ------------------ | ---------------------------------- | ------------------ |
| 설치               | 로컬 데스크탑                      | 로컬 데스크탑      |
| 모델               | **BYO CLI** (Claude Code/Codex 등) | **BYO CLI** (동일) |
| 워크트리 격리      | 있음                               | 있음               |
| 여러 에이전트 병렬 | 있음                               | 있음               |
| 모바일             | iOS/Android 컴패니언               | 텔레그램           |
| 라이선스           | **OSS (MIT)**                      | 클로즈드           |
| star               | **39.6k**                          | —                  |
| 호스티드/클라우드  | **없음**                           | 논의 중            |

**"로컬 설치 + BYO CLI 가 활성화 장벽"이라는 가설은 Orca 가 정면으로 반증한다.** 같은 장벽을 갖고 3주에 20k star 를 더 벌었다. 우리 이탈은 로컬 때문이 아니다.

그리고 Orca 가 **클라우드를 안 하고 있다**는 사실을 "선점 기회"로 읽으면 안 된다. 39.6k star 를 가진 팀이 클라우드를 안 하는 건 **못 해서가 아니라 그게 이 카테고리의 승부처가 아니라고 판단해서**일 가능성이 훨씬 높다. 우리가 그들보다 시장을 잘 안다고 볼 근거가 없다.

### C-2. Cursor 의 클라우드는 초보용이 아니다 (결정적)

`docs/cloud-agent` 원문:

> "Before anyone can start a cloud agent from a repository, a Cursor account **admin needs to connect source control**."
> "**Environment setup is the most important step** to improve the effectiveness of cloud agents."

셋업 문서가 요구하는 것: `.cursor/environment.json`, Dockerfile/스냅샷, install script, startup command, Secrets 등록, 네트워크 allowlist, 필요시 Tailscale userspace 네트워킹·Cloudflare Tunnel.

**즉 업계 1위가 클라우드를 "초보 제로셋업 온램프"로 쓰지 않는다. 상급자·팀 표면으로 쓴다.**
초보 온램프는 여전히 로컬 데스크탑 + 번들 모델이다.

`udbSiAAo` 티켓의 전제("클라우드 = 제로셋업 초보 온램프")는 **업계 최선 사례와 어긋난다.** 이건 그 스파이크가 도착하면 정면으로 되물어야 할 지점이다.

### C-3. 비어 있는 땅은 어디인가

세 플레이어를 놓고 보면:

| 축                      | Cursor                | Orca                    | 비어 있나                     |
| ----------------------- | --------------------- | ----------------------- | ----------------------------- |

### C-4. 반대로, 내가 틀릴 수 있는 지점

- star 는 사용이 아니다. 39.6k star 중 실제 주간 사용자가 몇 명인지 모른다. GitHub star 는 개발자 도구에서 **관심의 지표이지 매출의 지표가 아니다.**
- Cursor 의 클라우드가 상급자용인 것은 **현재 시점의 선택**이지 영구적 진리가 아니다. 그들이 초보 온램프로 내리면 우리 §C-2 논거는 무효가 된다.

### C-5. 경쟁 권고 3줄

1. **로컬 유지.** 로컬이 문제라는 가설은 Orca 가 반증했다.
2. **개인 ADE 패리티 추격 중단.** 39.6k star OSS 를 기능으로 이기는 경로는 없다.
3. **팀의 병합 결정·감사 축으로 좁힌다.** 이게 세 플레이어 중 가장 덜 점유된 땅이고, 유일하게 유료가 성립하는 땅이다.

## 5. 관점 D — 타이밍 / 페이즈닝

**한 줄**: 페이즈드는 맞다. 그러나 **게이트를 잘못 걸면 영원히 Phase 1 에 갇힌다.** 그리고 지금 우리가 제일 위험한 건 늦는 게 아니라 **틀린 것을 오래 하는 것**이다.

### D-1. 시장 시계

- Orca: 20.8k(7/17) → 39.6k(8/8). **3주에 2배.**
- Cursor: 7/28 인도 지역가격, 7/29 iPad, 8/3 Google Workspace 플러그인. **주 단위 출시.**
- 우리: 같은 3주 동안 벤더 편입·라우팅·계측 부채 정리. **외부 유저는 6명 그대로.**

이 대비가 타이밍 관점의 전부다. 우리는 지금 **경쟁자보다 느린 게 아니라 다른 종목을 하고 있다.**

### D-2. 8주 게이트에 대한 내 반대

CEO 리뷰의 게이트(주간 신규 로그인 ≥ 8, D7 재방문 ≥ 30%)는 **논리적으로는 옳지만 실무적으로 위험**하다:

- 주간 신규 로그인 8 = 월 32. 지금 6. **5배**를 8주에 만들어야 한다. 그런데 CEO 리뷰가 배정한 유입 작업은 "F5 배포 레인 1개"뿐이고 W5-8 에 몰려 있다. **게이트를 못 넘는 게 기본값**이다.
- 게이트를 못 넘으면 어떻게 되나? CEO 리뷰 §7 은 세 갈래를 적었지만, **"유입도 재방문도 안 오른 경우"** 가 빠져 있다. 그게 제일 가능성 높은 결과다. 그때 우리는 **또 8주를 Phase 1 에 쓰게 된다.**

**타이밍 권고: 게이트에 "실패 시 어떻게 하는가"를 미리 박아라.** 8주 뒤 셋 다 미달이면 → 로컬 개인 축을 유지 모드로 내리고 **경쟁 관점의 팀·병합 결정 축으로 전환**한다. 자동 전환. 재논의 없음.

### D-3. 대중 세그먼트 — 죽이지 말고 보류

CEO 리뷰는 대중 세그먼트를 "죽인다"고 썼다. **반대한다.**

죽인다와 보류한다는 실행 관점에서 같아 보이지만 **의사결정 비용이 다르다.** 죽이면 나중에 되살릴 때 "전략 번복"이 되고, 그 정치적 비용 때문에 실제로는 안 되살아난다. 비기너 모드는 이미 그 방향의 자산이고, 살려두는 데 드는 추가 비용이 **0**이다.

**"12개월 보류, 비기너 모드는 유지"** 가 맞는 표현이다.

### D-4. 페이즈 순서에 대한 내 이견

경쟁 관점(C)이 "지금 팀·병합 축으로 좁히자"고 하는데, **순서상 불가능하다**:

- 팀 축의 구매자는 팀 리드다. 팀 리드는 **팀원이 이미 쓰고 있는 도구**에 돈을 낸다.
- 우리 팀원(개인 개발자) 활성 유저가 6명이다. **바텀업 채택 없이 팀 판매는 안 된다.**
- 게다가 감사·safe-merge 스파인은 엔지니어링 관점(B)의 용량 계산으로 **3~6개월**이다.

**즉 C 의 방향은 맞고 D 의 타이밍은 반대다.** 팀 축은 Phase 2 의 목적지이지 Phase 1 의 작업이 아니다. 다만 Phase 1 에서 **팀 축으로 가는 데 재사용될 것**(티켓↔워크트리↔diff↔결정 연결)을 우선한다.

### D-5. 타이밍 권고 3줄

1. **Phase 1 = 8주, 로컬·개인 활성화.** 단 게이트 **실패 시나리오를 미리 확정**해서 자동 전환하게 한다.
2. **유입 작업을 W5-8 이 아니라 W1 부터** 병렬로. 안 그러면 게이트가 형식이 된다.
3. **대중 세그먼트는 죽이지 말고 12개월 보류.** 비기너 모드는 유지 자산으로 남긴다.

## 6. 직접 충돌 — 패널이 실제로 다투는 지점

### 충돌 1. 클라우드 데모, 지금인가 게이트 후인가 (A vs B)

- **A(GTM)**: 월 $1,000~2,500 이면 광고보다 싸고 전환 품질이 압도적이다. 141명이 매달 다운로드 페이지에서 샌다.
- **B(엔지니어링)**: 네 계산에서 빠진 게 **6~9주 빌드 용량**이다. 그건 Phase 1 전체다. 토큰 $2,500 이 문제가 아니라 **Phase 1 을 취소하는 것**이 문제다.
- **A 재반박**: 그러면 완료 상한을 1건으로 더 낮추고 데모 레포를 고정하면 범위가 줄지 않나.
- **B 재반박**: 범위가 줄어도 **격리·시크릿·남용방지·운영은 안 줄어든다.** 그게 대부분의 시간이다. 그리고 우리는 아직 **비용 축조차 정합하지 않았다**(`task_outcomes` $11.20 vs `cost_logs` $0.19).
- **부분 합의 도달**: B 가 대안을 냈다 — **스크립티드 데모 리플레이**(기존 `DemoMode` 활용, 인프라 0, 며칠). A 가 "브라우저에서 실제로 도는 것"의 상당 부분을 대체한다고 인정. **단 A 는 "리플레이는 실행이 아니다, 전환 효과는 열등하다"는 이의를 유지.**
- **미해결 잔여**: 리플레이가 실제 클라우드 체험의 몇 %를 대체하는지 아무도 모른다. **측정 없이는 이 논쟁이 안 끝난다.**

### 충돌 2. 대중 세그먼트 — 죽이나 보류하나 (A·D vs C)

- **C(경쟁)**: 대중 추격 = Cursor 의 무료 티어(모델 번들·원가 마진)와 정면충돌. 우리는 모델 벤더가 아니라 **구조적으로 그 싸움에서 진다.** 죽여야 한다.
- **A(GTM)**: 개발자 시장은 Cursor(무료)와 Orca(OSS) 양쪽에서 막혀 있다. 우리가 "오케가 함대를 지휘한다"로 파는 대상은 **이미 CLI 구독 여러 개 굴리는 상급 개발자**뿐이고, 한국에 몇 천 명 규모다. 대중이 유일한 확장 축이다.
- **D(타이밍)**: 둘 다 지금 결정할 문제가 아니다. **비용 0으로 살려둘 수 있는 것을 죽이는 건 순손실.**
- **C 재반박**: "비용 0"이 거짓이다. 세그먼트를 살려두면 **모든 UI 결정이 두 청중을 상대하게 되고** 그게 비기너 모드가 어정쩡해지는 경로다.
- **결과: 불합의.** 2:1 로 "보류" 우세지만 C 의 반박(설계 비용은 0이 아니다)이 반박되지 않았다. **사장님 결정 사항으로 올림.**

### 충돌 3. 팀·병합 축으로 언제 가나 (C vs D)

- **C**: 지금 좁혀라. 개인 워크벤치는 이미 뺏겼다.
- **D**: 팀 구매자는 바텀업 채택 위에만 산다. **활성 개인 유저 6명으로 팀 판매는 불가.** 게다가 B의 계산으로 스파인이 3~6개월.
- **B(엔지니어링, 개입)**: D 의 용량 판단이 맞다. 다만 **"팀 축으로 재사용되는 것"과 "개인 활성화"가 겹치는 구간**이 실제로 있다 — 티켓↔워크트리↔diff↔결정의 연결. 그걸 우선하면 낭비가 아니다.
- **합의 도달**: **방향은 C, 타이밍은 D.** Phase 1 은 개인 활성화, 단 팀 축에 재사용되는 것부터. 이 합의는 견고하다.

### 충돌 4. 게이트 숫자가 현실적인가 (D vs 전원)

- **D**: 주간 신규 로그인 6 → 32 를 8주에? 그런데 유입 작업은 W5-8 에만 배정됐다. **설계상 실패한다.**
- **A**: 동의. 그래서 내가 **8주 예산의 절반을 유입에** 쓰라고 한 것.
- **B**: 유입에 절반을 쓰면 F1~F4 중 뭘 빼나. **F2 공유 링크를 뺀다**(권한 모델·서버 렌더 때문에 제일 비싸다).
- **C**: 유입 작업이 뭔지가 안 정해졌는데 예산부터 나누는 건 순서가 틀렸다.
- **결과: 부분 합의.** "유입을 W1 부터 병렬로" 는 전원 합의. **"무엇을 유입 작업으로 하는가"는 §7-D 에서 투표했고 갈렸다.**

### 충돌 5. 파운더 61명 리커버리의 우선순위 (A vs C)

- **A**: 최우선. 이미 손에 있고, **왜 떠났는지 물어볼 수 있는 유일한 표본(n=55)** 이다.
- **C**: 그 55명은 이미 한 번 실패한 코호트다. 제품이 안 바뀐 채로 다시 부르면 **두 번째 실패**가 되고, 그건 첫 번째보다 회복이 어렵다.
- **A 재반박**: 부르는 게 아니라 **묻는 것**이다. 설문·인터뷰는 제품 변경 전에 하는 게 맞다.
- **합의 도달**: **"재초대"가 아니라 "이탈 인터뷰"로 지금 한다.** 재초대는 F2(결과 카드) 착지 후. 전원 동의.

| **L3. 한국 개발자 직접 접촉** | 밋업·디스코드·1:1 온보딩 — 저비용 고접촉                    | A, B | D: 스케일 안 됨. 월 30명이 상한. C: 그래도 지금 필요한 게 딱 30명                          |

**투표: L2 2표, L3 2표, L1 1표(중복 허용).** 종결 안 됨.
패널 공통 의견 하나만 적는다: **"셋 중 하나만 고른다. 셋 다 조금씩 하면 아무것도 안 된다."**

## 10. 한계·정직성

- 외부 코호트 **n=6**. 모든 비율은 유저 1~3명이다.

- Cursor 의 매출·유저 규모는 인용하지 않았다 — 1차 출처를 확보하지 못했다. 가격·온보딩·클라우드 요구사항만 원문 확인.
