## 0. 서문 — 프롬프트 캐시는 "아웃풋 캐시"가 아니다

이 문서를 읽는 사람이 딱 하나만 가져간다면 이것이다.

**프롬프트 캐시는 모델의 답을 캐싱하지 않는다. 입력 프리픽스를 캐싱한다.**

에이전트 한 턴의 요청 본문은 이런 모양이다:

```
[툴 정의들] [시스템 프롬프트] [대화 이력] [읽어들인 파일 내용] ←── cache_control 여기
                                                              [이번 유저 메시지]
```

`cache_control` 표시 지점까지가 **캐시 가능한 프리픽스**다. 다음 요청이 **바이트 단위로 같은 프리픽스**를 들고 오면 벤더는 그 부분을 다시 prefill 하지 않고 **입력가의 10%**로 청구한다. 같지 않으면 — 단 1바이트라도 — 전량을 정가로 다시 청구한다.

우리 워크로드는 티켓당 **캐시 재읽기 11.9M 토큰 vs 출력 79k 토큰**(#885 §3, n=1,371)이다. 즉 **비용의 거의 전부가 입력**이고, 그 입력의 거의 전부가 캐시 재읽기다. 그래서:

| 시나리오        | 티켓 1건 원가 | 출처               |
| --------------- | ------------: | ------------------ |
| 캐시 보존(정상) |     **$9.85** | #897 §4-A          |
| 캐시 파손       |    **$63.10** | #897 §4-A          |
| 배수            |    **★6.4배** | 이 코드가 재현한다 |

> ⚠️ **숫자 정정**: 이 티켓 지시문에는 "원가 18배"라고 적혀 있었는데, #897 §4-A 의 값은 **원가 6.4배**다. 18배에 가까운 수는 다른 축이다 — 마크업 30%가 버는 돈 ≈$3 대비 캐시 파손 손실 +$53 = **마진의 약 17배**. 즉 *원가 6.4배 = 마진 17배*이고, 둘 다 맞지만 같은 축이 아니다. 이 문서는 §4-A 축(원가 6.4배)을 쓴다. 산술은 `src/cost.ts` 에 실행 가능한 형태로 박아 두었고 테스트가 $9.85 / $63.09 / 6.40 을 그대로 검증한다.

**따라서 계량 프록시의 1순위 요구사항은 계량이 아니라 "아무것도 하지 않기"다.** 요청 본문을 파싱해서 다시 직렬화하는 순간 — 키 순서가 같아도 공백 하나만 달라져도 — 프리픽스 해시가 바뀌고 티켓당 $53이 날아간다.


## 3. 측정 방법 — 키 없이 어디까지 갈 수 있나

### 3-A. 문제

라이브 측정에는 Anthropic **pay-go 키**가 필요하고, 지금 없다(#897 §10-A L-1·L-2 미착수). 그러나 "키 없으니 아무것도 못 잰다"는 틀렸다. 관문 G-P1 이 묻는 것은 사실 **두 개의 질문**이다:

| 질문                                          | 누구의 문제 | 키 없이 잴 수 있나                |
| --------------------------------------------- | ----------- | --------------------------------- |
| Q1. **우리 프록시가 프리픽스를 변형하는가**   | 우리        | **★잴 수 있다**                   |
| Q2. Anthropic 캐시가 우리 가정대로 키잉되는가 | 벤더        | **못 잰다** — 벤더만 답할 수 있다 |

L2 를 죽이는 쪽은 **Q1** 이다(#897 §12 R1: "프록시가 캐시를 깬다"). Q2 는 벤더의 공개 동작이고, 틀렸다면 직접 호출도 똑같이 틀린다 — 프록시 고유의 리스크가 아니다.

### 3-B. 그래서 만든 것 — 진짜 캐시를 가진 모의 업스트림

`src/mock/anthropicMock.ts` 는 usage 를 지어내는 스텁이 **아니다**. 벤더가 문서화한 방식 그대로:

1. 요청 본문에서 **마지막 `cache_control` 지점까지**의 내용을 순서대로 직렬화하고(툴 정의 → 시스템 → 메시지),
2. 그 문자열의 **sha256** 을 캐시 키로 삼아 TTL 맵에 넣고,
3. 같은 해시가 TTL 안에 다시 오면 그 토큰 수를 `cache_read_input_tokens` 로 청구한다.
4. 최소 캐시 가능 길이(1024토큰) 미만이면 벤더처럼 **`cache_control` 을 무시**한다.

★따라서 **우리 릴레이가 본문을 1바이트라도 건드리면 해시가 달라지고 모의가 miss 를 낸다.** "잘 되겠지"가 아니라 실제로 실패한다. 이게 키 없이 Q1 을 재는 유일하게 정직한 방법이다.

### 3-C. 레인 설계 — 왜 salt 를 분리하나

```
direct  레인 :  probe ─────────────▶ upstream     (salt = "…-direct")
proxied 레인 :  probe ── proxy ────▶ upstream     (salt = "…-proxied")
각 레인 내부 :  같은 바이트 2회.  1회차 = 캐시 쓰기, 2회차 = 캐시 읽기 → 2회차 비율을 본다
```

★**두 레인의 salt 가 다른 것이 핵심이다.** 캐시는 _계정 + 프리픽스_ 스코프다. 두 레인이 같은 프리픽스를 쓰면 direct 레인이 proxied 레인의 캐시를 먼저 데워 놓고, proxied 레인은 **자기가 벌지 않은 히트**를 기록한다 — 프록시가 본문을 망가뜨려도 초록으로 보일 수 있는 가짜 통과다. 라이브 프로브(`runCacheProbe.ts`)도 같은 규율을 쓴다.

## 4. 오늘의 실측 결과 (키 없음)

명령: `cd v3/credit-proxy && npm run probe:mock` — 재현 가능하고, 리포트는 `probe-out/mock-probe.json` 에 떨어진다.

### 4-A. G-P1 — 캐시 보존

| 레인        | 1회차(쓰기)                     | 2회차(읽기)                 | **캐시 히트율** |
| ----------- | ------------------------------- | --------------------------- | --------------: |
| **direct**  | `cache_creation` 2,576 / read 0 | read **2,576** / creation 0 |      **98.66%** |
| **proxied** | `cache_creation` 2,582 / read 0 | read **2,582** / creation 0 |      **98.66%** |

- **델타 = +0.003%p** (허용 ±10%p) → **G-P1 GREEN** (모의 축)
- proxied 프리픽스가 6토큰 더 큰 건 **salt 문자열 길이 차이**("direct" vs "proxied")이지 프록시가 뭔가 붙여서가 아니다. 바이트 동일성은 별도로 sha256 으로 단언된다.
- 그 읽기 턴의 **캐시 파손 배수 = 8.54배**(코드가 usage 에서 직접 계산). §4-A 의 티켓 평균 6.4배보다 높은데, 정상이다 — 이 프로브 턴은 출력이 3토큰뿐이라 입력 비중이 티켓 평균보다 더 극단적이다. **배수는 믹스 비율의 함수**라는 #897 §13 의 서술과 일치한다.

### 4-B. G-P2 — 툴루프 완주

| 턴  | stop_reason | 블록       | 툴                    |
| --- | ----------- | ---------- | --------------------- |
| 1   | `tool_use`  | `tool_use` | `lookup_build_status` |
| 2   | `end_turn`  | `text`     | —                     |

- 스트리밍(`stream: true`), 툴 왕복 1회, 종료 `end_turn` → **G-P2 GREEN** (모의 축)

## 5. ★라이브 측정 런북 (키 확보 후)

키가 생기면 아래 3단계로 **이 문서의 §4 표를 라이브 값으로 교체**하면 된다. 코드 변경은 필요 없다.

```bash
cd v3/credit-proxy

# 1) 프록시 기동 (터미널 1). 키는 env 로만, 파일/이미지에 넣지 않는다.
ANTHROPIC_API_KEY=<pay-go 키> npm run build && npm start

# 2) G-P1 라이브 (터미널 2). direct 레인과 proxied 레인을 자동으로 A/B 한다.
ANTHROPIC_API_KEY=<같은 키> PROBE_MODEL=claude-sonnet-5 npm run probe:cache
#    → probe-out/cache-probe.json, 종료코드 0=GREEN / 1=RED

# 3) G-P2 라이브
ANTHROPIC_API_KEY=<같은 키> npm run probe:toolloop
```

**추가로 반드시 할 것 — 진짜 하네스 왕복** (프로브는 우리 클라이언트이지 `claude` 가 아니다):

```bash
ANTHROPIC_BASE_URL=http://127.0.0.1:8080 \
ANTHROPIC_AUTH_TOKEN=<아무 값이나> \
claude -p "이 레포에서 X를 고쳐줘"     # 티켓 1건 완주시킨 뒤
curl -s http://127.0.0.1:8080/__poc/metrics | jq '.records[] | {model, cacheHitRatio, stopReason}'
```

`__poc/metrics` 는 요청별 `cacheHitRatio` 를 그대로 준다. **티켓 전체의 평균 히트율이 직접 실행 대비 ±10%p 안이면 G-P1 라이브 통과**다.

| 판정 기준 (#897 §11 승계·정밀화)                            | 조치                                          |
| ----------------------------------------------------------- | --------------------------------------------- |
| proxied 히트율이 direct 대비 **−10%p 초과 하락**            | **G-P1 RED → L2 중단.** 벤더 교체로 안 풀린다 |
| 하락이 −10%p 이내                                           | GREEN → P2(T-6\~T-10) 착수                    |
| proxied 가 direct 보다 **높음**                             | **RED 아님**(§6-B) — 공유 계정 웜캐시. 기록만 |
| 툴루프가 `end_turn`/`max_tokens` 로 못 끝나거나 재조립 실패 | **G-P2 RED**                                  |

> ★판정 비대칭에 대해: #897 §11 은 "±10%p 이내"라고 대칭으로 적었다. 코드는 두 값을 **모두** 계산하되(`withinTolerance` / `preserved`), **행동 판정은 하락에만 건다.** 상승은 결함이 아니라 공유 업스트림 계정에서 다른 세션이 이미 데워 둔 프리픽스를 맞은 것이기 때문이다(§6-B). 대칭 기준을 그대로 쓰면 **정상 동작을 red 로 오판**한다.

## 6. PoC 가 새로 발견한 것 (#897 에 없던 조각)

### 6-A. 캐시를 깨는 4경로 — 우리 구현과 1:1 대조

| #897 §4-A 의 파손 경로              | 이 구현의 상태                                                                                                                              | 증거                     |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| 1. 본문 정규화·재직렬화             | **막힘.** Buffer 를 그대로 전달. 프레임워크 미들웨어 없음                                                                                   | sha256 대조 E2E          |
| 2. 시스템 프롬프트에 헤더/필드 주입 | **막힘.** 업스트림 헤더에 `x-marblo-*` 조차 안 넣는다                                                                                       | `headers.test.ts`        |
| 3. 유저별 라우팅이 계정·리전을 섞음 | **막힘(현재).** 단일 `UPSTREAM_BASE_URL` + 단일 키. ★단, §6-C 의 확장 리스크 있음                                                           | `config.ts`              |
| 4. 재시도가 캐시 TTL(5분)을 넘김    | **부분.** 프록시는 자체 재시도를 **하지 않는다**(추가 지연 0). 단 `retry-after`·rate-limit 헤더는 그대로 내려보내 클라의 백오프를 살려 둔다 | `buildDownstreamHeaders` |

### 6-B. ★단일 서버 키 = 유저 간 캐시 공유 (양날)

L2 프록시는 **모든 유저의 요청을 우리 계정 키 하나**로 낸다(§5 설계). 캐시는 계정+프리픽스 스코프이므로:

| 결과                                                                                     | 평가                                                                                                                                                                                                             |
| ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 유저 A 가 캐시 쓰기(1.25×)를 내고, 유저 B 가 같은 프리픽스를 0.1× 로 읽을 수 있다        | **원가에는 이득.** 공용 시스템 프롬프트·툴 정의는 유저 공통이라 히트율이 오른다                                                                                                                                  |
| **회계 공정성**: A 가 낸 쓰기 비용을 B 가 공짜로 쓴다                                    | 균일 마크업이라 마진율은 안 흔들린다. 단 유저별 원가 귀속은 **정확하지 않다**                                                                                                                                    |
| **★신규 리스크(#897 위험등록부에 없음)**: 캐시 히트 여부는 타이밍/usage 로 관측 가능하다 | 유저 B 가 특정 프리픽스가 캐시에 있는지 **추측**할 수 있다. 내용은 못 읽지만 "누가 이 파일을 다뤘나" 류의 존재 추론 여지. 심각도 **낮음**(프리픽스를 정확히 맞춰야 함), 그러나 약관·프라이버시 문구에 한 줄 필요 |

### 6-C. ★확장 시 3번 경로가 되살아난다

#897 §4-A 행3 의 "단일 계정·단일 리전 고정"은 **지금은 지켜지지만 확장과 충돌한다.** 유저가 늘면 벤더 rate limit 때문에 계정을 늘리고 싶어지고, 그 순간 캐시가 계정별로 쪼개져 히트율이 무너진다.

**설계 규율로 못박을 것**: 계정 샤딩을 도입하려면 **유저 단위가 아니라 프리픽스 단위 sticky 라우팅**이어야 한다(같은 프리픽스는 항상 같은 계정으로). 이건 P2 이후 과제지만, 지금 적어 두지 않으면 나중에 "그냥 라운드로빈"으로 들어와서 조용히 원가가 6배 된다.

### 6-D. `count_tokens` 도 릴레이 경로에 있어야 한다

#897 §6-D 는 hold 금액 산정에 `/v1/messages/count_tokens` 를 쓸 수 있다고 적었다(패스스루의 부수 이점). 이 프록시는 **`/v1/*` 전체를 릴레이**하므로 그 경로도 이미 열려 있다. 다만 그 호출도 **우리 계정으로 나가고 rate limit 을 먹는다** — P2 에서 hold 산정을 붙일 때 "본문 바이트/3.5 추정"과 "count_tokens 실호출" 중 후자를 고르면 요청 수가 2배가 된다는 점을 계산에 넣어야 한다.

### 6-E. 본문 버퍼링의 메모리 축

릴레이는 요청 본문을 **버퍼링**한다(바이트는 안 건드리고 지연만 시킨다). 상한은 `MAX_BODY_BYTES`(기본 32MB). Cloud Run 인스턴스 메모리는 **상한 × 동시성** 을 감당해야 한다. 기본값 그대로 동시 8이면 최악 256MB다 — **배포 시 동시성과 함께 조정할 값**이고, 이 PoC 는 기본값만 정해 두었다.

## 7. 판정 — L2 go / no-go

### 7-A. 관문

| 관문     | 우리 축(코드)                                 | 벤더 축(라이브)     | 종합             |
| -------- | --------------------------------------------- | ------------------- | ---------------- |
| **G-P1** | **GREEN** — 델타 +0.003%p, 바이트 동일성 실측 | **미측정**(키 없음) | **조건부 GREEN** |
| **G-P2** | **GREEN** — 툴루프 완주, 재조립 결손 0        | **미측정**(키 없음) | **조건부 GREEN** |

### 7-B. 판정

**★L2 계속 진행(조건부 GO).**

근거:

1. **L2 를 죽일 수 있었던 유일한 구조적 결함 — "프록시가 프리픽스를 변형한다" — 은 배제됐다.** 그것도 주장이 아니라, 프리픽스 해시로 청구하는 업스트림 앞에서 실제로 캐시 히트를 만들어 보임으로써.
2. **남은 미지는 프록시 고유가 아니다.** Q2(벤더 캐시 키잉)가 우리 가정과 다르다면 직접 호출도 같이 틀린다. 즉 **프록시 도입 결정을 뒤집을 수 있는 미지는 남아 있지 않다.**
3. #897 §11 의 비대칭이 유지된다 — T-A(Anthropic 패스스루)는 번역이 0이므로 G-P2 가 구조적으로 통과에 가깝고, 이 PoC 가 그 구조(번역 0)를 실제로 구현해서 확인했다.

**단, 조건 3개:**

| 조건                                                       | 왜                                                               |
| ---------------------------------------------------------- | ---------------------------------------------------------------- |
| ★**§5 라이브 측정 전에는 P2(T-6\~T-10)에 착수하지 않는다** | 원장·hold 를 먼저 지으면, G-P1 이 라이브에서 red 일 때 전부 매몰 |
| ★**이 PoC 를 라이브 키와 함께 공개 배포하지 않는다**       | 인증이 **없다**(P1 범위). 열면 우리 계정으로 아무나 쏜다         |
| **충전 UI placeholder 를 활성화하지 않는다**               | #897 §8 이 이미 못박은 규율                                      |

### 7-C. 이 판정이 틀릴 수 있는 경우

정직하게 — 이 결론을 뒤집을 수 있는 시나리오는 하나뿐이다:

> Anthropic 의 캐시가 **요청 본문 외의 것**(예: 인증 주체별 파티션, 특정 헤더, 클라이언트 지문)까지 키에 넣는 경우.

그러면 프록시 경유는 계정이 우리 하나로 고정되므로 오히려 **유리**해야 정상이지만, 예컨대 "조직 내 워크스페이스별 파티션" 같은 축이 있으면 예상 밖 동작이 나올 수 있다. **§5 의 라이브 A/B 가 정확히 이걸 잡는 측정**이고, 그래서 조건 1(라이브 전 P2 금지)이 있다.

## 8. 한계 · 정직성

- **라이브 cache-read 를 재지 못했다.** Anthropic pay-go 키가 없다(#897 §10-A L-1·L-2 미착수). §4 의 모든 수치는 **모의 업스트림** 실측이다. 이 문서는 그 둘을 표 제목에서부터 구분해 적었다.
- **모의는 벤더 동작의 *가정*이다.** 프리픽스 직렬화 순서(툴→시스템→메시지), 최소 캐시 길이 1024토큰, TTL 5분, 4자/토큰 근사 — 전부 공개 문서 기준의 가정이고 이 PoC 가 벤더에 대해 검증한 것이 아니다. 모의가 증명하는 것은 **"우리 릴레이가 프리픽스를 안 건드린다"** 이지 **"벤더가 히트를 준다"** 가 아니다.
- **gen1 이 SSE 를 못 한다는 것을 라이브로 재현하지 않았다.** #897 §13 이 남긴 한계 그대로 승계한다. 이 PoC 는 그 전제를 _가정하고_ Cloud Run 으로 갔다.
- **Cloud Run 에 실제로 배포해 보지 않았다.** Dockerfile 은 작성했으나 빌드·배포·콜드스타트·타임아웃은 미검증이다(티켓 지시: 배포는 머지 후 오케가).
- **`claude` 바이너리로 실제 왕복해 보지 않았다.** 프로브는 우리 클라이언트다. §5 런북의 `ANTHROPIC_BASE_URL` 왕복이 그 갭을 메우며, 키가 필요하다.
- **단가는 `model-registry.ts` 에서 *복사*했다.** 이 패키지는 Cloud Run 으로 나가므로 Electron 트리를 import 할 수 없다. **드리프트 리스크가 있고**, P2 에서 원장을 붙일 때 단일 소스 재확인이 필요하다(메모 `model_pricing_truth_and_kg_cold_seed`).
- **인증·allowlist·hold·원장이 전부 없다.** 의도된 범위(§11 P1)다. G-P1 이 라이브에서 green 이 되기 전에 짓지 않는 것이 이 PoC 의 결론이다.
- **동시성·부하를 재지 않았다.** 백프레셔는 코드에 있으나 부하 실측은 없다.
- **§6-B 의 캐시 존재 추론 side-channel 은 이론적 지적**이고 실증하지 않았다. 심각도 낮음으로 기록만 한다.
- 날조 없음. §4 의 모든 수치는 `npm run probe:mock` 으로 재현되고 `probe-out/mock-probe.json` 에 원본이 남는다.
