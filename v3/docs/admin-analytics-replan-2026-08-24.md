화면이 지저분한 건 결과지 원인이 아니다. 원인은 이거다:

**설치 · 계정 · clientId · 브라우저 · 사람 · 그랜트 — 여섯 개 축이 한 화면에
퍼센트로 나란히 그려진다.** 분모가 다른 숫자를 위아래로 놓으면 사람 눈은 그걸
자동으로 퍼널로 읽는다. 그래서 안 맞는 게 아니라, **애초에 맞을 수 없는 것을
맞는 것처럼 그려 놓은 것**이다.

재설계의 목적은 예쁘게 만드는 게 아니다. **하나의 알갱이로 모으는 것**이다.

### 0-1. 오늘 실제로 터진 세 건은 전부 같은 병이다

**① 첫스폰 3.1% — 분자와 분모가 둘 다 틀렸다**

`577 최초실행 → 18 첫스폰` 이 3.1% 로 떠 있었다. 두 군데가 동시에 틀렸다:

- **분모**: 577 에 개발·CI 설치가 섞여 있다. `analytics_install_profile` 608행 중
  `buildChannel='dev'` 가 실측 14건이고, CI 러너가 앱을 켜면 그대로 최초실행 1건이
  된다. 광고를 켜기 전 지금 외부 실사용자는 4명인데 분모는 577이다.
- **분자**: 18은 `agent:spawned` 옵트인 이벤트를 보낸 clientId 수다. 분모는 설치
  축(`install_profile`)인데 분자는 이벤트 축(clientId)이다. **옵트인을 껐으면
  스폰을 해도 분자에 안 잡힌다.** 즉 분자는 "스폰한 사람" 이 아니라 "스폰했고
  텔레메트리도 켠 사람" 이다.

두 축을 나눈 값이라 3.1% 는 어떤 실제 비율도 아니다. 방향조차 보장 안 된다 —
분모는 부풀고 분자는 깎였으니 진짜 값은 3.1% 보다 **높다**.

**② `install_attribution` ↔ GA4 조인 0건 — 원본 vs HMAC 키 공간 불일치**

`install_attribution.gaClientId` 는 길이 20~21의 **원시** 값이고,
`ga4_first_touch.gaKey` 는 `ga_`+24자 **HMAC 가명**이다. 원시로 가명을 조인하면
에러 없이 0행이 나온다. 그래서 화면은 "유입 채널 없음" 을 그렸고, 그건
"광고 안 켰으니 자연유입" 이 아니라 **"조인이 안 됐다"** 였다. #1195 가 원장에
`gaKeyHmac` 을 넣어 수리했다.

**③ 사람 축 daily/link 불일치 (#1171 수리)**

`analytics_user_daily` 는 설치를 **원시** `install_key` 로 들고, 링크표
`analytics_user_install` 은 **가명** 으로 들었다. 다리가 없어서 사람 축이 0으로
보였다. 0이 아니라 **미상**이었다.

**세 건의 공통 구조:**

> 서로 다른 알갱이 두 개를 이어 붙였다 → 조인이 조용히 0행이거나 축이 어긋났다 →
> 화면은 에러 없이 **작은 수 또는 0** 을 그렸다 → 사람이 그걸 **사실**로 읽었다.

에러가 안 난다는 게 이 병의 악성이다. 빨간 글씨가 뜨면 고쳤을 텐데, 조용히
틀린 숫자가 뜨니 6주 동안 그걸 보고 판단했다.

### 0-2. 그래서 재설계의 원칙은 셋뿐이다

1. **집계는 한 곳에서 한 번.** 화면은 이미 접힌 표를 읽기만 한다.
   → §3, 티켓 `L8RvsReu6Vch5eNYYCJR` 의 `v_install_unified`.
2. **0과 미상을 절대 안 섞는다.** 빈 값은 `0` 도 `'(unknown)'` 도 아니고
   **NULL + 사유 컬럼**이다. → §6-1.
3. **표본이 작으면 퍼센트를 안 보여준다.** n<5 는 수치 대신 "표본 부족".
   → §6-2.

## 4. 탭별 구성

공통 규칙:
- **상단 3줄**: 그 탭의 질문에 답하는 숫자 딱 3개. 넷째부터는 표로 내린다.

- 모든 헤드라인·표에 `trust` 배지 + 미상이면 `waitingOn`.

- 표 순서 = 결정하는 순서. 위에서부터 읽으면 "무엇을 고칠까" 가 나와야 한다.

| 1 | **설치 (외부)** — `608 중 외부 N` | `COUNT(*) WHERE NOT isDevInstall AND NOT isBotInstall`. ★분모를 화면 맨 위에 못 박는다. 3.1% 사고의 재발 방지 |
| 2 | **채널을 아는 설치** — `481 / 608 (79%)` 🟡 | `COUNTIF(hasGa4Row)`. "유입 0" 과 "모름" 을 가르는 한 칸 |
| 3 | **획득 CAC** — `광고비 ÷ 외부 설치` | 광고비 원장(#1193) ÷ 1번. 광고 전이면 "지출 0 — 산출 불가" |

**표 순서**

1. **채널별 통합표** — 행: `channelSource` × `channelMedium` × `channelCampaign` ×
   `channelContent`. 열: 설치 · 첫스폰 · D7잔존 · 결제자 · 매출.
   ★`WHERE channelMissingReason IS NULL` — 캠페인이 **실재하는** 행만.
   광고 전인 지금 이 표는 **0행**이고, 그 자리에 "유료 광고를 켠 적이 없습니다" 라고
   쓴다. 빈 표를 "유입 0" 으로 속이지 않는다.
2. **★채널 미상 사유표** — 행: `channelMissingReason` × `hasGa4Row`, 열: 설치 수.
   `no_ledger_row` / `no_ga_client_id` / `key_mismatch` / `no_ga4_row` / `no_utm`.
   **이 표가 이 페이지에서 가장 중요한 신설물이다.** 1번 표가 비었을 때
   "광고를 안 켰다" 인지 "조인이 깨졌다" 인지를 여기서만 알 수 있다.
3. **국가별** — `channelCountry` GROUP BY, 열은 1번과 동일. 다운로드 0 국가 포함.
4. **광고비 원장 × 채널** — #1193 수동 입력 원장. 채널별 지출 · 획득 설치 · CAC ·
   회수(누적 매출/지출).
5. **대기자·파운더 원장** (Firestore 🟢) — 대기자 · 선정 · 피드백 · 인터뷰.
   ★맨 아래다. 초록이라 믿을 만하지만 **광고 성과와 다른 축**이라 위에 두면 섞인다.

### 4-2. ② 활성화 — "들어온 사람이 가치를 보나"

#### 4-4-1. ★매출 합계 규칙 — `SUM(revenueTotal)` 은 틀린다

금액만 사람 단위로 접는다:

```sql
SELECT SUM(revenueTotal) AS revenue FROM (
  SELECT personKey, ANY_VALUE(revenueTotal) AS revenueTotal
  FROM `marblo-2253d.marblo_identity.v_install_unified_revenue`
  WHERE revenueMissingReason IS NULL AND personKey IS NOT NULL
  GROUP BY personKey
);
```

설치·활성화·리텐션은 설치 알갱이 그대로 센다. **금액만** 이 규칙을 탄다.

§0 재발이다.

## 6. ★유지·강화할 장치

### 6-1. `trust` + `waitingOn` — 지우지 않는다. 전부에 적용한다

실측: `trust`(🟢/🟡/🔴) 는 SectionHeader **20개 전부**에 붙어 있다 — 규율이 이미
서 있다. 반면 `waitingOn` 은 **9곳**뿐이라 🔴 인데 이유를 안 쓴 자리가 남아 있다.
이 장치가 좋은 이유는 하나다 — **빈 표를 "유입 0" 으로 속이지 않는다.**

강화 규칙:

- **신설 항목 전부에 `trust` 필수.** 없으면 렌더 안 함(개발 시 타입으로 강제).
- `trust="red"` 인데 `waitingOn` 이 없으면 **빌드 실패.** 못 믿는 이유를 안 쓰면
  못 믿는다는 표시가 무의미하다.
- ★`waitingOn` 문구는 자유 텍스트를 그만 쓰고 **§6-4 의 사유 코드 + 소관 티켓**으로.
  "선행 티켓 진행 중" 은 어느 티켓인지 안 알려준다.

### 6-2. ★n<5 — 수치 대신 "표본 부족"

지금 코드에 `SMALL_SAMPLE_MAX = 10` 경고가 이미 있다. 좋다. **그런데 경고만 띄우고
값은 그대로 보여준다.** 그게 부족하다.

| 분모 n | 지금 | **바꿀 것** |
| --- | --- | --- |
| 0 | `—` (판단 불가) | 유지 |
| **1 ≤ n < 5** | 값 + 경고 | ★**값을 안 보여준다.** `표본 부족 (n=3)` |
| 5 ≤ n ≤ 10 | 값 + 경고 | 분수 우선 + 경고 (유지) |
| n > 10 | 값 | 유지 |

**왜 5인가:** 지금 외부 사용자가 한 자릿수다. 채널×주차로 쪼개면 셀당 1~2명이
된다. n=2 에서 1명이 남으면 "50%", 안 남으면 "0%" 다. **그 두 숫자 사이에 아무
정보가 없다.** 퍼센트가 사람을 속이는 게 아니라, 우리가 퍼센트로 속는 것이다.

★**마스킹은 서버에서 한다**(PR 2). 화면에서 하면 API 응답에는 남아 있어서
다음 사람이 그걸 쓴다.

★**총계 행은 마스킹하지 않는다.** 쪼갠 셀만 가린다 — 안 그러면 전체 리텐션까지
사라진다.
