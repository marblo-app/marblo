## 1. 원인 — 가설(키 공간 단절)이 아니었다

오케의 유력 가설은 `events.userId(원본) → identity → install_key(HMAC)` 경로의
키 공간 단절이었다. **아니다.** 실측으로 배제된다.

| 확인                                         | 결과                                                                                                                                                                                                           |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `events.userId` 모양                         | 36자 소문자 UUID (4,947행 전량)                                                                                                                                                                                |
| `analytics_install_profile.install_key` 모양 | 36자 uuid36 606행 중 604행                                                                                                                                                                                     |
| 코드                                         | `installAttribution.ts:57` 이 `getClientId()` **원본**을 보내고, `logTelemetryBatch` 도 `e.clientId` **원본**을 `userId` 에 적재한다. 가명화(`pseudonymizeAnalyticsRow`)는 project/agent/task/flow 만 건드린다 |

키 공간은 같다. 갈린 건 **모집단**이다.

### 1-1. 프로필 606행을 출처별로 가르면

```
has_attribution=T / has_events=F : 564행  first_run 564 · first_spawn   0 · 활동일   0
has_attribution=F / has_events=T :  43행  first_run  12 · first_spawn  17 · 활동일 184
has_attribution=T / has_events=T :   1행  first_run   1 · first_spawn   1
```

분모 577(= 564 + 12 + 1)의 **98%가 이벤트를 단 한 줄도 남기지 않은 설치**다.
그 행들은 `first_spawn_at` 을 가질 자격 자체가 없다. 분자가 죽은 게 아니라,
분자가 닿을 수 없는 행이 분모에 들어왔다.

### 1-2. 왜 두 모집단이 갈리나 — 인증 게이트

| 경로                                                  | 인증                             | 결과                                             |
| ----------------------------------------------------- | -------------------------------- | ------------------------------------------------ |
| `linkInstallAttribution` (#906)                       | **미인증** 콜러블                | 로그인 안 한 설치도 `install_attribution` 에 1행 |
| `telemetryService.flushTelemetry` / `flushHeartbeats` | `if (!auth.currentUser) return;` | 로그인 전 이벤트를 **전량 폐기**                 |

`first_run_at` 은 두 출처를 `earliest()` 로 합치는데(`app:first_run` 이벤트 또는
어트리뷰션 `linkedAt`), `first_spawn_at` 은 **events 에서만** 온다. 그래서 분모는
비로그인까지 세고 분자는 로그인 이후만 센다.

부수 피해 하나 더 — `app:first_run` 은 로그인 **전**에 발생한다. 그래서 전 기간을
통틀어 events 에 18건뿐이고, 이벤트가 있는 설치 43개 중 12개만 `first_run_at` 이
있었다. 나머지 31개는 주차 표에서 **통째로 사라져 있었다.**

### 1-3. 시점이 08-03~08-10 에 걸린 이유 — 코드·배포 근거

| 날짜       | 변경                                                         | 지표에 준 영향                                                                                                                                       |
| ---------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |

## 2. 분모도 틀렸다 — 631 '설치' 의 실체는 브라우저 5개

`install_attribution` 631행(gaClientId 있는 것)의 **고유 `gaClientId` 는 5개**다.

```
브라우저 1개 → 539 설치
브라우저 1개 →  69 설치
브라우저 1개 →  16 설치
브라우저 1개 →   6 설치
브라우저 1개 →   1 설치
```

GA4 `client_id` 는 브라우저 프로필당 하나다. 539명이 각자 설치했다면 브라우저도
539개여야 한다. 한 브라우저가 2주에 539번 "최초 실행" 을 했다는 건 매 실행마다
`localStorage` 가 초기화되는 **개발 루프**다. 방증도 맞물린다:

- 전 행이 `MacIntel` 하나
- 버전별로 몰려 있다 — 3.0.31 **156건/2일**, 3.0.30 **121건/2일**
- `gaClientId` 는 전부 정상 GA4 형식(`nnnnnnnnnn.nnnnnnnnnn`)이라 폴백 상수가 아니다
- 채널 태그가 붙은 유일한 버전 **3.0.35 는 80건 전부 `dev`**

주차별로도 같다.

| 주(KST)    | 설치 행 | 고유 브라우저 |
| ---------- | ------- | ------------- |
| 2026-08-10 | 199     | **2**         |
| 2026-08-17 | 366     | **4**         |
| 2026-08-24 | 67      | **3**         |

브라우저 2~4개. events 의 주당 고유 유저 3~8명과 **자리수가 맞는다.**

### 2-1. `ft_build_channel` NULL 594건을 어떻게 할 것인가 — 답

**NULL 은 '알 수 없음' 이 아니라 '그 앱 버전에는 `c` 파라미터가 존재하지 않았다'
이다.** `resolveBuildChannel` / `buildInstallLinkUrl` 의 `c` 파라미터는 #1071
(2026-08-21)에 들어갔다. 그 이전에 링크백한 설치는 앱을 고쳐도 **소급해서 채워지지
않는다.** 그러니 대책은 둘로 나뉜다.

1. **앞으로**: 이미 해결돼 있다. 3.0.35 이후 링크백은 채널을 싣는다. 실제로 3.0.35
   80건 전량에 `dev` 가 찍혔다. 추가 작업 없음.
2. **과거분 594건**: `ft_build_channel` 로는 못 가른다. 대신 **이미 631/632행에
   들어 있는 `gaClientId`(브라우저 축)로 가른다.** 한 브라우저가 만든 설치 수가
   임계값 이상이면 사람이 아니라 재설치 루프다.

그래서 프로필에 두 칸을 추가했다.

- `ft_browser_installs` — 같은 `ga_key` 를 공유하는 설치 수
- `install_class` — `dev_tagged` / `reinstall_loop` / `distinct` / `unknown`

`ga_key` 가 없는 행은 조용히 `distinct` 로 접지 않고 `unknown` 으로 남긴다.
모르는 걸 아는 척하면 그게 다음 3.1% 가 된다.

## 3. 수리 — 무엇을 바꿨나

## 4. 사장님 질문에 대한 답

> "첫스폰 이슈는 비기너모드·제로마찰 자동설치로 개선한 거 아냐? 아직 더 개선
> 포인트가 있나?"

### 4-1. 기준선(배포 시점)

| 기능                            | 배포                               | 커밋             |
| ------------------------------- | ---------------------------------- | ---------------- |
| 비기너 모드                     | 2026-08-07 (릴리스 3.0.25 · 08-13) | `8604a7a6` #854  |
| 상시 시작하기 탭                | 2026-08-13 (릴리스 3.0.26)         | `35ee4745`       |

| 시작하기 git 스텝               | **2026-08-24 (오늘)**              | `d7243406` #1179 |

### 4-2. 답 — **지금 데이터로는 답할 수 없다. 그리고 그게 진짜 문제다.**

계측이 살아 있는 모집단(events)의 주차별 실측이 전부다.

| 주(KST)    | 그 주 스폰한 고유 설치 | 그 주 **첫** 스폰 | 그 주 코호트 진입(관측가능) |
| ---------- | ---------------------- | ----------------- | --------------------------- |
| 2026-07-13 | 11                     | 9                 | 29                          |
| 2026-07-20 | 6                      | 3                 | 7                           |
| 2026-07-27 | 6                      | 2                 | 3                           |
| 2026-08-03 | 3                      | 0                 | 1                           |
| 2026-08-10 | 3                      | 0                 | **0**                       |
| 2026-08-17 | 4                      | 1                 | 3                           |
| 2026-08-24 | 2                      | 0                 | —                           |

여기서 정직하게 읽을 수 있는 것과 없는 것:

**읽을 수 있는 것 (셋)**

1. **비기너 모드(08-07) 전후를 비교할 표본이 없다.** 08-03 이후 주차의 _새로_
   관측된 설치는 1 · 0 · 3 이다. n=0~3 에서 전후를 가르는 건 추세가 아니라 잡음이다.
2. **부트 게이트·git 스텝은 오늘 배포됐다.** 배포 후 데이터가 0일치다. 지금 어떤
   숫자를 대도 그 두 변경과는 무관하다.
3. **주당 실사용자는 3~8명이고, 그 대부분이 내부 도그푸드로 보인다.** 익명축에는
   `is_admin` 이 구조적으로 없어(방침이 고지한 대가) 운영자 제외가 불가능하다.
   그만큼 이 숫자는 낙관 편향돼 있다.

**읽을 수 없는 것**

- 외부 사용자의 "첫 실행 → 첫 스폰" 전환율. **한 번도 측정된 적이 없다.**
  `app:first_run` 은 로그인 전에 발생해 폐기되고(전 기간 18건), 어트리뷰션이 세는
  설치는 로그인하지 않아 events 에 나타나지 않는다.

### 4-3. 그래서 "아직 개선 포인트가 있나" 에 대한 답

**있다. 다만 제품이 아니라 계측이 먼저다.**

첫스폰을 더 개선할지 말지를 지금 결정할 근거가 없다. 두 가지가 동시에 참이다.

- 제품 쪽: 비기너·시작하기·부트게이트·git 스텝은 **효과를 확인할 데이터가 없는
  상태로 배포됐다.** 더 손대면 또 확인 없이 손대는 것이다.
- 계측 쪽: 로그인 전 구간이 통째로 미계측이라 **첫 실행 → 첫 스폰이라는 퍼널의
  앞쪽 절반이 원리적으로 안 보인다.** `onboarding:spawn_blocked`(08-13~08-24
  80건 / 3유저)만이 유일하게 살아 있는 마찰 신호다.

권고 순서:

1. 로그인 전 온보딩 이벤트를 어떻게 할지 결정한다(오케에 질문 등록됨 —
   미인증 경로로 좁게 받을 것인가, 아니면 "첫 실행 → 첫 스폰은 로그인 이후만
   측정 가능" 을 지표 정의에 못박을 것인가). 이 답 없이는 어떤 온보딩 개선도
   효과를 확인할 수 없다.
2. 그 답이 나올 때까지 **`onboarding:spawn_blocked` 를 첫스폰 마찰의 대리 지표로
   쓴다.** 이건 로그인 이후 이벤트라 지금도 관측된다.
3. 외부 유입이 실제로 잡히기 시작하면(브라우저 축이 두 자릿수가 되면) 그때
   전후 비교를 다시 한다.

## 5. ★이 숫자로 세웠던 판단들 — 다시 봐야 한다

오케가 2026-08-24 하루 동안 **3.1%(18/577)를 제품 판단의 기준선으로** 여러 번
인용했다. 그 숫자는 위 §1~2 대로 성립하지 않는다. 다음 판단들의 논거가 사라졌다.

- **광고 집행 판단** — "설치는 577인데 첫스폰이 3.1%" 를 근거로 삼았다면, 그 577은
  브라우저 5개의 재설치 루프였다. **유입 규모 자체가 성립하지 않는다.**
- **기능 우선순위** — "첫스폰이 병목" 이라는 결론의 근거였던 0%는 전환 실패가 아니라
  측정 부재였다. 병목이 첫스폰이라는 증거는 **지금 없다.**
- **비서 탭 순서** — 같은 근거를 썼다면 같은 이유로 재검토 대상이다.

워크체인 `wc_g15oicmyok` 이 이 3.1% 를 '제품 판단의 기준선' 으로 적어 둔 항목이다.
**이 티켓이 끝나면 그 항목을 갱신해야 한다.**

말해 두자면 — 세 번째다. 오늘만 같은 모양의 조용한 단절이 #1171 · #1195 · 이 건까지
셋이었고, 셋 다 사람이 손으로 갈라 보고 나서야 발견됐다. §3-3 의 검사는 그
발견 방식을 끝내려고 넣은 것이다.

### "최근 주차의 spawns 가 0 이 아니다" — 두 가지 읽기를 구분해서 답한다

**활동 주차 기준(그 주에 스폰한 고유 설치)은 0 이 아니고, events 실측과 정확히
일치한다.** 이게 "분자는 죽지 않았다" 의 증명이다(부록 A Q8).

| 주 | 프로필이 세는 스폰 설치 | events 고유 유저 |
| --- | --- | --- |
| 2026-08-03 | 3 | 3 |
| 2026-08-10 | 3 | 3 |
| 2026-08-17 | 4 | 4 |
| 2026-08-24 | 2 | 2 |

**코호트 주차 기준(그 주에 처음 온 설치 중 첫 스폰까지 간 수)은 08-10 주차가
여전히 0 이다. 그리고 그건 버그가 아니다** — 수리 뒤의 분모는 그 주에 새로
관측된 설치 **0개**이기 때문이다(수리 전에는 199였다). 분모가 0이면 비율은
0% 가 아니라 `—`(판단 불가)이고, 우리 코드는 그렇게 돌려준다
(`summarizeFirstSpawnActivation().rate === null`).
