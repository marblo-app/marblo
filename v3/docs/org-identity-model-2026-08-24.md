# 조직 정체성 모델 — 이름은 사람이 정하고, 도메인은 제안만 한다

작성 2026-08-24 · 티켓 `LJf0at2EryJ4M5iBHioi` · **설계 + 데이터모델·검증로직 구현.
사용자 노출 흐름(결제·온보딩) 변경은 제안만 하고 멈춘다.**

선행 정본 [`v3/docs/enterprise-ax-client-dashboard-design-2026-08-24.md`] (#1202) 이 조직 축이
번지는 범위를 전수로 그렸다. 그 문서가 **비워 둔 칸이 조직명과 도메인**이고, 이 문서가 그 칸이다.

---

## 0. 한 문단 요약 — 사장님 문장을 둘로 가른다

> "팀 요금제는 무조건 조직 이름을 넣도록 하거나, 안 하면 기본은 이메일에서 조직명을 찾아서
> 넣어야겠다?"

**방향은 맞다. 다만 이 문장에는 두 가지가 섞여 있고, 하나는 위험하다.**

|          | 무엇                                                       | 틀렸을 때                                 | 판정            |
| -------- | ---------------------------------------------------------- | ----------------------------------------- | --------------- |
| **(가)** | 조직**명 채우기** — 표시용 이름의 기본값을 도메인에서 제안 | 사람이 그 자리에서 고친다                 | **한다**        |
| **(나)** | 조직 **자동 가입** — 같은 도메인이면 그 조직의 멤버로 넣기 | 남의 감사 로그·비용을 본다. **못 고친다** | **하지 않는다** |

(가)와 (나)를 같은 기능으로 묶으면 사고가 난다. 이 문서는 둘을 코드에서까지 갈라 놓는다 —
`suggestOrgDisplayName()` 과 `decideMembershipGrant()` 는 다른 함수이고, 뒤엣것은 **이메일 도메인을
판정에 쓰지 않는다.**

---

## 1. ★맨 앞에 놓을 것 — 우리는 잘못 붙은 귀속을 고칠 수 없다

일반적인 SaaS 라면 "도메인 자동 가입" 은 UX 취향 문제다. 잘못 넣었으면 빼면 된다.
**우리는 아니다. 우리에게만 있는 이유가 하나 있고, 그게 이 문서의 모든 결정을 지배한다.**

```
v3/electron/mcp-server/ledger-chain.ts

  function chainPayload(event: LedgerEventWrite) {   // 이벤트 본문 전체
    ...                                              // 필드를 골라 담지 않는다
  }
  computeEventHash({ v, id, occurredAtMs, seq, prevHash, event: chainPayload(event) })

  주석: "본문은 필드를 골라 담지 않고 통째로 넣는다 —
         나중에 필드가 추가돼도 자동으로 보호 범위에 든다."
```

이 설계는 옳다. 하지만 결과가 하나 따라온다:

> **감사 원장 본문에 한번 들어간 값은 고칠 수 없다.** 고치면 그 행의 `hash` 가 어긋나고,
> `prevHash` 사슬을 타고 **그 뒤 모든 행의 검증이 깨지며**, 머클 체크포인트가 봉인해 둔
> 사슬 머리까지 거짓이 된다.

즉 자동 유추로 **틀린 조직에 붙은 기록은 영원히 그 조직 것으로 남는다.** 고객사가 "이건 우리
기록이 아닙니다" 라고 해도 우리는 지울 수도 고칠 수도 없고, 지우려 들면 우리가 파는 무결성
증명 자체가 깨진다. 선행 설계 §7.3 이 삭제권에 대해 그은 절단선과 같은 절단선이다.

**이것이 "사람이 한 번 정하게" 해야 하는 가장 강한 근거다.** 입력칸 하나를 사람에게 보여 주는
비용은 초 단위이고, 잘못 붙은 귀속을 안고 가는 비용은 계약 기간 전체다.

### 1.1 ★그래서 결론이 하나 더 나온다 — 조직 귀속은 원장 **밖**에 둔다

티켓은 "원장엔 orgId 만, 표시명은 조회 시 해석" 을 제안했다. 표시명을 원장에서 빼는 판단은
전적으로 옳다. **그런데 같은 논리를 한 칸 더 밀면 `orgId` 도 원장에 박으면 안 된다.**

|                           | 원장 본문에 `orgId` 를 박는다 | 원장 밖 결합표에 둔다 (**권고**) |
| ------------------------- | ----------------------------- | -------------------------------- |
| 귀속이 맞을 때            | 문제 없음                     | 문제 없음                        |
| 귀속이 **틀렸을 때**      | ★영구히 못 고친다             | 정정 행을 덧붙여 고친다          |
| 프로젝트가 조직을 옮길 때 | 과거는 보존됨                 | 시점 조회로 과거도 보존됨        |
| 정정 사실                 | —                             | **남는다**(추가 전용)            |
| 체인                      | 건드림                        | **안 건드림**                    |

원장 행은 오늘처럼 `projectId` 만 들고 있으면 된다. 조직으로 접는 것은 조회 시점에
`OrgProjectBinding` 을 `effectiveFrom` 으로 되짚어 한다(`resolveOrgIdAt()`).

★근거 패턴은 이미 이 프로젝트 안에 있다 — `analyticsPseudonym.ts`:
_"소급은 저장이 아니라 조회로 한다. 이벤트 행에 컬럼을 만들지 않는다. 링크는 별도 표에만 있고,
그 표를 지우면 소급이 그 자리에서 취소된다."_ 이 문장을 조직 귀속에 그대로 적용한 것이다.

선행 설계 §5.2 의 비용 쿼리도 이미 이 모양이다 — `WHERE projectId IN UNNEST(@projectIdsOfOrg)`.
새 규약이 아니라 **이미 그리기로 한 쿼리를 데이터모델이 따라가는 것**이다.

## 2. (가) 조직명 — 도메인은 **제안만** 한다

### 2.1 규칙

| 규칙                                                             | 근거 한 줄                                                                         |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 팀 요금제는 조직명 **필수 입력**                                 | 이 순간부터 그 조직의 원장이 쌓이고, 원장은 못 고친다(§1)                          |
| 도메인에서 **기본값을 제안**한다 (`hypemarc.com` → `"Hypemarc"`) | 빈칸보다 편집 가능한 문자열이 온보딩에서 낫다. 틀려도 되돌릴 수 있다               |
| 제안값은 **항상 수정 가능**                                      | 우리 추측이 상호와 같을 이유가 없다                                                |
| ★**공개 이메일 도메인은 제안조차 하지 않는다**                   | "Gmail" 은 틀린 값이고, 제안 자체가 "우리는 도메인으로 조직을 가른다" 를 알려 준다 |
| 퓨니코드(`xn--`)는 제안하지 않는다                               | 복호화하면 한글 상호가 나오지만 우리 추측이 상호와 다를 때 **조용히** 틀린다       |

구현: `orgIdentity.suggestOrgDisplayName(email)` → `{ suggested, reason, domain, domainClass }`.
반환값에 `orgId` 도 멤버십도 없다 — **이 함수는 가입과 접점이 없다**(단위테스트로 고정).

### 2.2 ★도메인은 두 갈래가 아니라 셋이다

공개/비공개로만 가르면 구멍이 하나 남는다. `snu.ac.kr` 은 무료 메일이 아니지만 수만 명이 쓰고
그들은 한 팀이 아니다.

| 종류        | 뜻                                              | 이름 제안        | **합류 키로 사용**          |
| ----------- | ----------------------------------------------- | ---------------- | --------------------------- |
| `public`    | 무료·일회용 메일                                | ✗                | ✗                           |
| `multi_org` | 기관 도메인이지만 한 조직이 아님(`ac.kr`·`edu`) | ✓(사람이 고친다) | ✗                           |
| `corporate` | 그 외                                           | ✓                | **도메인 소유 검증 후에만** |
| `invalid`   | 이메일 모양이 아님                              | ✗                | ✗                           |

공개 도메인 목록(`FREE_MAIL_DOMAINS`)은 **국내 도메인이 앞머리**다 —
`naver.com` `daum.net` `hanmail.net` `kakao.com` `nate.com` `korea.com` `hotmail.co.kr` …
글로벌은 `gmail` `outlook` `icloud` `yahoo` `proton` `qq` 등, 일회용은 별도 집합
(`DISPOSABLE_MAIL_DOMAINS`)으로 갈라 두었다 — 가입 자체를 막을지는 다른 결정이고 이 티켓 밖이다.

`go.kr`·`or.kr`·`re.kr` 은 **일부러 `multi_org` 에서 뺐다.** 그쪽은 도메인 하나가 대체로 기관
하나다(`moef.go.kr`). 반면 `ac.kr`/`edu` 는 학교 하나에 수만 명이고 연구실·산단이 서로 남이다.

★**이 목록은 완전할 수 없다**(무료 메일은 계속 생긴다). 그래서 목록은 안전장치가 아니라 제안
억제기다. **가입은 목록과 무관하게 초대·승인으로만 된다** — 목록이 새도 데이터 유출로 이어지지
않는 구조다. 이 성질이 이 설계에서 가장 중요하다: **안전이 "빠짐없는 목록" 에 기대지 않는다.**

## 3. (나) 자동 가입 — 하지 않는다

### 3.1 이건 UX 불편이 아니라 데이터 유출이다

공개 도메인으로 자동 가입시키면 **서로 모르는 남들이 한 조직에 묶여 서로의 감사 로그와 비용을
본다.** `gmail.com` 사용자 전원이 한 조직이 되는 그림을 상상하면 규모가 보인다.

★**한국 맥락에서 더 심각하다.** 소기업·프리랜서·1인 법인이 네이버·지메일을 업무용 대표 메일로
쓴다. 국내 사용자 비중이 높은 제품에서 이 실수는 예외가 아니라 기본 경로다.

### 3.2 ★그리고 도메인은 "지금 이 회사 소속" 을 증명하지 않는다

이게 자동 가입이 회사 도메인에서조차 틀리는 이유다.

- **퇴사자.** 메일 계정은 인수인계 기간 동안 살아 있다. 자동 가입은 퇴사자를 조직에 넣는다.
- **재직 중 소속 이동.** 도메인은 그대로인데 팀·법인이 바뀐다.
- **미검증 이메일.** Firebase 이메일 가입은 검증 전에도 계정이 만들어진다. 검증 없이 도메인을
  믿으면 **아무나 `@toss.im` 을 주장**할 수 있다.

그래서 우리 구현은 도메인 파생 판단 전체에 `emailVerified` 를 전제로 요구한다.

### 3.3 멤버십이 생기는 경로는 둘뿐이다

```
초대(invitation)        — {orgId}_{email} 결정적 id. 기존 프로젝트 초대 규약을 그대로 확장
관리자 승인(admin_approval) — 사람이 지금 판단한다
```

`orgIdentity.decideMembershipGrant()` 의 반환 타입에 **자동 가입 값 자체가 없다.**
그리고 그 함수는 `email` 의 도메인을 판정에 쓰지 않는다 — 입력 조합을 전수로 훑어도 부여 경로는
`invitation`/`admin_approval` 둘뿐이라는 것이 단위테스트로 고정돼 있다.

거부 사유도 코드로 갈라 둔다: `no_invitation` · `invitation_expired` ·
`invitation_email_mismatch` · `email_not_verified` · `personal_org_not_joinable`.

## 4. 조직명의 유일성 — 표시명은 자유, 식별자는 불변 id

### 4.1 판정

| 안                       | 채택       | 근거                                                                                     |
| ------------------------ | ---------- | ---------------------------------------------------------------------------------------- |
| 조직명 **전역 유일**     | ✗          | 선점(스쿼팅) 시장을 만든다. "삼성전자" 를 아무나 먼저 잡고, 우리는 분쟁 처리 비용만 진다 |
| **슬러그**만 유일        | ✗ (지금은) | 슬러그는 URL 을 위해 존재하는데 **우리는 URL 에 슬러그가 필요 없다** (§4.2)              |
| **둘 다 자유 + 불변 id** | ✅         | 식별은 이름이 아니라 id 가 한다. 이름이 겹쳐도 어떤 판정에도 영향이 없다                 |

핵심 통찰 하나: **표시명은 조직 밖으로 나가지 않는다.** 조직 이름을 보는 사람은 그 조직의
멤버뿐이라 이름이 겹쳐도 아무도 헷갈리지 않는다. 유일성은 값을 못 하는 곳에서 비용만 물리는
제약이다.

### 4.2 슬러그를 지금 만들지 않는 이유

선행 설계 §4.2 가 이미 짚었다 — `team/page.tsx` 는 **프로젝트 선택을 화면이 하지 않는다.**
서버가 uid 로 권한 집합을 도출한다. 같은 규약을 org 로 확장하면 **라우트 변경 없이** 조직 축이
열린다. 즉 `/org/hypemarc` 같은 vanity URL 이 필요하지 않고, 필요 없는 전역 namespace 를 여는
것은 순손실이다.

나중에 정말 필요해지면: **검증된 도메인을 가진 조직만, 관리자 검토를 거쳐** 옵트인으로 연다.

### 4.3 ★단 하나의 예외 — 초대 메일

표시명이 조직 **밖**으로 나가는 자리가 딱 하나 있다. 초대 메일이다.
아무나 조직명을 "토스" 로 짓고 초대 메일을 피싱에 쓸 수 있다.

이 구멍은 이름 유일성으로 막지 않는다(막히지도 않는다). 두 겹으로 막는다:

1. **초대 메일에 초대자의 검증된 이메일 도메인을 함께 표시한다.** 이름은 자칭이고 도메인은
   증명된 것이다.
2. **도메인 미검증 조직의 초대에는 "확인되지 않은 이름" 고지를 붙인다**
   (`INVITE_UNVERIFIED_ORG_NOTICE`).

그리고 이름이 **스스로에 대해 거짓말하는 것**은 입력 단계에서 막는다 — 제로폭 문자·양방향
제어문자(RLO 하나면 `moc.olbram` 이 `marblo.com` 으로 보인다)·제어문자를 거부하고, NFKC 정규화로
전각/반각이 다른 이름 행세를 하지 못하게 한다(`validateOrgDisplayName`).

## 5. 이름 변경 — 허용한다. 원장은 건드리지 않는다

### 5.1 허용하는 이유

법인명은 실제로 바뀐다(상호 변경·합병·리브랜딩). 금지하면 고객은 조직을 새로 만들고,
**그 순간 과거 원장과의 연결이 끊긴다** — 우리가 파는 것이 연속된 감사 추적인데 이름 하나 때문에
그걸 끊는 것은 본말전도다.

### 5.2 감사 원장에 어떻게 남기나

> **원장에는 이름을 박지 않는다.** 표시명은 조회 시 해석한다.

- 원장 행은 `projectId` 만 든다(오늘과 같다). 조직 귀속은 `OrgProjectBinding` 시점 조회(§1.1).
- 표시명은 `OrgNameHistoryEntry` **추가 전용 표**에 `{orgId, displayName, effectiveFrom, recordedAt, actorUid}` 로 남는다.
- 6월 감사 반출물은 `resolveOrgDisplayNameAt(history, orgId, 6월)` 로 **6월의 이름**을 찍는다.
- 변경 사실 자체는 그 표에 영구히 남아 감사된다. **이름은 몇 번이든 바뀔 수 있고, 원장 해시는
  한 번도 건드려지지 않는다.**

기계가 대신 읽는다: `assertNoOrgIdentityInLedgerPayload()` 가 원장 write 페이로드에
`orgName`/`organizationName`/`orgDisplayName`/`orgSlug`/`orgDomain`/`companyName` 이 섞이면
**write 전에 던진다.** 로그가 아니라 예외인 이유는 이 실수가 조용하고 되돌릴 수 없기 때문이다.
(`teamAudit.ts` 의 정규식 가드와 같은 규약 — _"자리가 있으면 언젠가 누가 채운다."_)

## 6. ★도메인 ≠ 조직인 경우 — 전수

| #   | 경우                                                                 | 자동 가입이 만드는 결과                                                                                   |
| --- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 1   | **한 조직 · 여러 도메인** — 우리부터가 `hypemarc.com` / `marblo.app` | 같은 회사가 두 조직으로 갈린다. 청구도 갈린다                                                             |

★9·10 때문에 도메인 소유 검증은 **상태가 아니라 만료되는 사실**로 다룬다 —
`DOMAIN_VERIFICATION_TTL_MS = 180일`. 검증은 재확인돼야 살아 있다.
★1·11 때문에 **한 조직에 도메인이 여럿**일 수 있게 스키마를 짰다(`OrgDomainBinding` 다중 행).

## 7. 도메인 기반 '합류 요청' — 둘 다 만족할 때만, 그래도 존재는 누출하지 않는다

### 7.1 판정

도메인 기반 창구를 **놓되**, 두 조건을 모두 만족할 때만 살아난다:

1. 조직이 **DNS TXT 로 도메인 소유를 증명**했고(만료 전이고),
2. 관리자가 **그 창구를 명시적으로 켰다**(`joinRequestsEnabled`). 검증했다고 자동으로 열리지 않는다.

검증 토큰은 `(orgId, domain)` 에 대한 HMAC 이다 — 랜덤 토큰을 발급해 저장하면 조직↔도메인 매핑을
담은 저장소가 하나 더 생긴다. HMAC 이면 **아무것도 저장하지 않고** 재계산된다.
솔트(`ORG_DOMAIN_VERIFY_SALT`)가 없으면 원시값 폴백 없이 **전 경로가 실패**한다
(`analyticsPseudonym.ts` 의 fail-safe 와 같은 태도: 조용한 열화보다 시끄러운 실패).

공개·다중조직 도메인은 **검증 자체를 거부**한다. 실제로 통과할 일이 없더라도, 여기서 막지 않으면
나중에 누군가 "테스트용 우회" 를 만들 때 이 함수가 문을 열어 준다.

### 7.2 ★그래도 조직 존재는 알려주지 않는다

티켓의 지적이 정확하다. 검증 없이 _"같은 도메인이니 이 조직입니다"_ 를 **보여주는 것만으로
조직의 존재가 누출된다** — 경쟁사가 도메인 하나로 우리 고객사 명단을 확인한다.

그래서 응답을 **조직 존재와 무관하게 항상 같은 모양**으로 만든다:

```
사용자에게 보이는 값 : "request_received"   ← 조직이 있든 없든 공개 도메인이든 항상 같다
서버 내부 판정        : submitted_to_org | discarded_no_target
                       | rejected_public_domain | rejected_email_not_verified
```

내부 판정은 로그·지표용이며 **응답 본문에 실으면 안 된다**(`buildJoinRequestReceipt`).
응답 JSON 에 조직명도 `orgId` 도 실리지 않는다는 것이 단위테스트로 고정돼 있다.
조직 이름은 **관리자가 승인한 뒤에야** 요청자에게 보인다.

★대상이 없어 버려지는 요청에도 접수 응답을 주는 것은 거짓말이 아니라 **존재 여부에 답하지 않는
것**이다. 계정 열거(account enumeration) 방어와 같은 패턴이다.

## 8. 개인 = personal 조직 (도메인 무관)

사장님이 정하신 기본값이다. 재론 대상이 아니고, 여기서는 **구현 성질만** 못박는다.

- `personalOrgId(uid) = "personal_" + uid` — **uid 에서 결정적으로 파생**한다. 백필 없이 과거
  사용자에게도 같은 값이 나온다.
- `defaultOrgIdForUser(uid)` 는 **이메일을 인자로 받지 않는다.** 받을 수 있게 만들면 언젠가 누가
  도메인을 본다. 회사 메일로 가입해도 개인 조직은 개인 조직이다.
- 개인 조직은 **초대로도 승인으로도 열리지 않는다**(`personal_org_not_joinable`). 개인 조직이
  팀처럼 쓰이기 시작하면 "개인은 personal 로 묶는다" 는 규칙이 조용히 무너진다.

## 11. 열린 질문 (사장님·오케 판단)

1. **§9-11 — 원장에 `orgId` 를 박지 않는 판단.** 정정 가능성(내 권고) vs 귀속 동결. 이 문서는
   전자를 골랐고 근거를 §1.1 에 적었다. 뒤집으시면 조직 축이 **첫 이벤트보다 먼저** 있어야 한다.
2. **도메인 합류 요청 창구를 v1 에 넣는가.** 검증·옵트인·존재 비노출까지 다 지으면 값이 있지만,
   초대만으로도 제품은 돈다. **내 권고: 초대·승인만 v1, 합류 요청은 고객이 요구할 때.**
3. **초대 메일의 "확인되지 않은 이름" 고지 문구.** 법무 검토 대상인지(피싱 책임 배분).
4. **조직 역할과 프로젝트 역할의 관계.** 이 문서는 org admin 이 프로젝트 **내용**을 자동으로
   보지 않는다고 정했다(선행 §4.3-3 의 감시선 유지). 기업 고객이 반대로 요구하면 제품 결정이다.
5. **공개 도메인 목록 갱신 주체.** 지금은 코드 상수다. 목록이 새도 유출로 이어지지 않게 설계했지만
   (§2.2), 제안 품질은 목록에 달려 있다.
