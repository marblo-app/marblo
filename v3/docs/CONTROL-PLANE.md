# Marblo: Control Plane for AI-Native Software Teams

> **포지셔닝 한 줄**: _Marblo is the control plane for AI-native software teams._
>
> 여러 AI 작업을 동시에 실행하고, 각 작업의 **맥락·진행·diff·테스트·의사결정**을 추적해, 사람이 **안전하게 merge** 하도록 만드는 제품.

이 문서는 Marblo의 전략적 방향(control plane)과 그 위에서의 데이터 전략·로드맵을 정의하는 단일 진실원(single source of truth)이다. 구현 스펙이 아니라 **왜 이 레이어를 만드는가**에 대한 합의 문서다.

---

## 1. 포지셔닝: Marblo는 AI-native 팀의 control plane이다

AI 코딩 에이전트는 이제 작업을 **실행**할 수 있다. 코드를 읽고, 고치고, 테스트를 돌리고, PR을 연다. 한 명의 개발자가 동시에 3개, 5개, 10개의 에이전트를 돌리는 것이 현실이 되었다. 그러나 실행 능력이 늘어날수록 병목은 실행이 아니라 **통제(control)** 로 옮겨간다.

- 지금 5개 에이전트가 각자 무엇을 하고 있는가?
- 이 에이전트가 만든 변경은 **왜** 이렇게 결정되었는가?
- 이 diff는 테스트를 통과했는가? 누가, 어떤 근거로 merge를 승인했는가?
- merge 이후 배포는 성공했는가, 리버트되었는가?

Marblo는 이 질문들에 답하는 레이어다. 여러 AI 작업을 **동시에 실행**하는 것은 시작점일 뿐이고, Marblo의 본질은 그 작업들 각각의 **맥락(context) · 진행(progress) · diff · 테스트 · 의사결정(decision)** 을 한 곳에 모아 추적하고, 사람이 그 위에서 **안전하게 merge** 하도록 만드는 control plane이다.

| 비유       | 실행기(executor)                               | control plane(Marblo)                                |
| ---------- | ---------------------------------------------- | ---------------------------------------------------- |
| 네트워킹   | 패킷을 나르는 라우터/스위치                    | 라우팅·정책·관측을 결정하는 control plane            |
| 쿠버네티스 | 컨테이너를 실행하는 kubelet                    | 스케줄·정책·상태를 관장하는 API server/control plane |
| AI 팀      | 코드를 짜는 에이전트(Claude Code/Cursor/Devin) | 작업을 추적·결정·safe-merge하는 **Marblo**           |

핵심 주장: **AI-native 팀의 가치는 "에이전트를 몇 개 돌리느냐"가 아니라 "그 결과를 얼마나 안전하고 추적가능하게 통합하느냐"에서 나온다.** Marblo는 후자를 소유한다.

## 2. 왜 이 방향인가: 실행기는 commodity, moat는 그 위 레이어

### 2.1 "에이전트 동시 실행"은 빠르게 commodity화되고 있다

에이전트를 병렬로 실행하는 능력은 이미 여러 제품이 제공하며, 빠르게 표준 기능이 되고 있다.

- **Claude Code** — 서브에이전트·병렬 태스크·워크플로우 오케스트레이션 내장
- **Cursor** — 백그라운드 에이전트, 멀티 탭 실행
- **Devin** 류 — 자율 에이전트 풀

실행 자체는 파운데이션 모델 제공사와 IDE 벤더가 빠르게 흡수하는 영역이다. 여기서 차별화를 시도하면 모델 사업자와 정면으로 경쟁하게 되고, 그들의 속도·자본을 이길 수 없다. **실행기를 만드는 것은 방어가능한 해자가 아니다.**

### 2.2 방어가능한 moat = 실행 위에 쌓이는 추적·결정 레이어

진짜 제품은 실행기가 아니라 그 위의 **추적·결정 레이어**다. 에이전트가 많아질수록 이 레이어의 가치는 선형이 아니라 **초선형(super-linear)** 으로 커진다. 에이전트 1개면 사람이 머리로 추적할 수 있지만, 10개가 동시에 돌면 추적·결정·safe-merge를 대신 해주는 시스템 없이는 팀이 마비된다.

| 레이어                  | 누가 소유하나           | 방어가능성                          |
| ----------------------- | ----------------------- | ----------------------------------- |
| 파운데이션 모델         | Anthropic/OpenAI/Google | Marblo 비관여 (BYO-model)           |
| 실행기(에이전트 런타임) | 모델 벤더·IDE           | commodity, 해자 아님                |
| **provenance 감사추적** | **Marblo**              | **높음 — 누적된 trajectory가 자산** |
| **safe-merge gate**     | **Marblo**              | **높음 — 팀 신뢰·정책의 통합점**    |
| **의사결정 기록**       | **Marblo**              | **높음 — 휘발하던 맥락을 자산화**   |

Marblo가 겨냥하는 moat는 세 가지다.

1. **Provenance(출처) 감사추적** — 모든 변경이 "어떤 문제에서 출발해 어떤 과정을 거쳐 merge되었는가"를 추적가능하게 만든다.
2. **Safe-merge gate** — 테스트·리뷰·정책을 통과해야 사람이 안전하게 merge할 수 있는 관문.
3. **의사결정 기록(decision log)** — "무엇을 왜 결정했는가"를 휘발시키지 않고 자산으로 남긴다.

**요약: 진짜 제품은 실행기가 아니라 추적·결정 레이어다.** 이 레이어가 Marblo의 정체성이며, 동시에 실행기 commodity화에 대한 방어선이다.

## 3. Control plane의 4기둥

Marblo control plane은 네 개의 기둥 위에 선다.

### ① 작업당 provenance 번들 (per-task provenance bundle)

각 작업(task)은 다음 단계가 **하나의 연결된 타임라인**으로 묶인 provenance 번들을 가진다.

```
문제(problem) → 접근(approach) → diff → 테스트(tests) → 검증(verification)
            → 리뷰 판정(review verdict) → 머지 SHA(merge SHA) → 배포 상태(deploy status)
```

이 번들은 "이 변경이 무엇이고, 왜 이렇게 되었으며, 어떻게 검증되어, 어디까지 배포되었는가"를 한눈에 보여주는 **작업의 감사 단위**다. 사람이 merge를 결정할 때 필요한 모든 맥락이 이 번들 안에 있어야 한다.

### ② 의사결정 로그 (decision log)

"무엇을 **왜** 결정했는가"의 기록. 지금은 이 맥락이 **채팅창에만 남아 휘발**된다. 에이전트가 "A 대신 B 접근을 택했다"는 판단, 사람이 "이 PR은 보류한다"고 내린 결정 — 이런 것들이 대화가 끝나면 사라진다.

decision log는 이 휘발하는 맥락을 **구조화된 자산**으로 영속화한다. 나중에 "왜 이 라이브러리를 골랐지?", "이 리스크는 누가 수용했지?"를 되짚을 수 있게 한다.

### ③ 머지/배포 이벤트 캡처 (merge/deploy event capture)

현재 머지·배포는 대부분 `gh` CLI 등 **앱 밖(out-of-band)** 에서 일어난다. control plane이 이 이벤트를 보지 못하면 provenance 번들의 끝부분(머지 SHA·배포 상태)이 비어버린다 — **구멍**이다.

이 기둥은 머지/배포 이벤트를 control plane 안으로 끌어와 캡처해, "이 결정이 실제로 어떤 SHA로 머지되어 어디에 배포되었는가"까지 타임라인을 완성한다.

### ④ 인라인 diff + PR/CI 상태 (inline diff + PR/CI status)

사람이 작업 화면을 떠나지 않고 **인라인으로 diff를 보고**, 해당 PR의 CI 상태(통과/실패)를 함께 확인할 수 있어야 한다. merge 결정은 diff와 CI 신호 위에서 내려지므로, 이 둘이 control plane 안에 있어야 safe-merge가 성립한다.

| 기둥               | 한 줄 정의                             | 해결하는 문제                                |
| ------------------ | -------------------------------------- | -------------------------------------------- |
| ① provenance 번들  | 작업 1개의 문제→배포까지 연결 타임라인 | "이 변경이 어디서 왔고 어디까지 갔나" 불투명 |
| ② 의사결정 로그    | 무엇을 왜 결정했는지 영속 기록         | 결정 맥락이 채팅에만 남아 휘발               |
| ③ 머지/배포 이벤트 | 앱 밖 머지·배포를 control plane 안으로 | gh CLI=앱밖=타임라인 구멍                    |
| ④ 인라인 diff + CI | 화면 내 diff·PR/CI 상태                | merge 근거가 분산·외부화                     |

## 4. 현재 갭 (Gap Analysis)

오늘의 Marblo는 위 4기둥의 토대(작업·활동 데이터, 보드뷰, 에이전트 런타임)는 갖췄지만, control plane으로서는 다음 갭이 있다.

- **diff/의사결정 추적이 약하다** — 변경의 diff와 그 변경을 둘러싼 의사결정이 일관된 형태로 추적·표시되지 않는다.
- **머지·배포가 control plane 밖에서 일어난다** — `gh` CLI 등으로 앱 밖에서 머지/배포가 이뤄져 타임라인의 끝이 비어 있다. (memory: "머지/배포가 앱밖"으로 이미 식별된 갭)
- **사람 결정이 휘발한다** — 리뷰 판정·보류·수용 같은 사람의 판단이 채팅 맥락에만 남고 자산으로 남지 않는다.

이 세 갭이 곧 4기둥(특히 ②③④)이 메우려는 대상이며, 로드맵의 우선순위를 결정한다.

## 5. 데이터 전략: 코드가 아니라 trajectory가 자산

### 5.1 Marblo가 쌓는 것은 코드가 아니라 trajectory다

Marblo가 누적하는 데이터의 본질은 소스코드가 아니라 **trajectory(궤적)** 다.

```
문제(problem) → 에이전트 행동(agent actions) → diff → 사람 결정(human decision) → 머지/리버트 결과(merge/revert outcome)
```

이것은 단순한 코드 스냅샷이 아니라 **labeled outcome 데이터** — "이런 문제에, 이런 행동을 했더니, 사람이 이렇게 판단했고, 결과적으로 머지되거나 리버트되었다"는 라벨이 붙은 궤적이다. Cursor류가 모으는 "edit 데이터(어떤 편집을 했는가)"보다 **결과·판정이 라벨로 붙어 있다는 점에서 가치가 높다.** edit는 행동만 담지만, trajectory는 행동 + 사람 판정 + 실제 결과를 담는다.

| 데이터 종류             | 담는 것                                 | 라벨                      | 상대 가치   |
| ----------------------- | --------------------------------------- | ------------------------- | ----------- |
| edit 데이터 (Cursor류)  | 어떤 코드 편집을 했나                   | 없음(행동만)              | 기준선      |
| **trajectory (Marblo)** | **문제→행동→diff→사람결정→머지/리버트** | **사람 판정 + 실제 결과** | **더 높음** |

### 5.2 단, Marblo는 BYO-model이다 — 용처는 base model 학습이 아니다

중요한 제약: **Marblo는 BYO-model(bring-your-own-model) 제품으로, 파운데이션 모델을 학습시키지 않는다.** 따라서 이 데이터의 용처는 base model을 트레이닝하는 것이 **아니다.** 실제 용처는 모델 **위**에서 작동하는 레이어다.

- **Routing** — 어떤 작업을 어떤 모델/에이전트에 보낼지 결정 (memory: BYO-model이라 데이터 용처는 routing/evals)
- **Evals** — 에이전트·모델의 성능을 실제 결과로 평가
- **Merge-risk 예측** — 이 변경이 리버트될 위험을 예측해 safe-merge gate를 강화

즉 trajectory 데이터는 "더 똑똑한 base model"이 아니라 **"더 똑똑한 control plane"** 을 만드는 연료다.

### 5.3 Trust가 control plane의 통화다 → 데이터는 기본 OFF + opt-in + 익명/집계

control plane의 본질은 신뢰(trust)다. 사람이 안전하게 merge하도록 돕는 제품이 데이터를 함부로 다루면 정체성과 모순된다. **Trust가 control plane의 통화(currency)** 이므로 데이터 정책은 보수적이어야 한다.

- **기본 OFF** — 데이터 사용은 기본적으로 꺼져 있다.
- **opt-in** — 사용자가 명시적으로 켜야 한다.
- **익명/집계(anonymized/aggregated)** — 식별정보를 제거하고 집계 단위로만.

방어가능한 데이터는 **코드가 아니라 결과·결정**이라는 점이 여기서 다시 중요하다. 결과/결정은 **코드 본문 없이도 집계가 가능**하다 — "이런 유형의 변경은 리버트율이 높다", "이런 리뷰 신호가 있으면 merge가 안전하다" 같은 집계는 소스코드를 수집하지 않고도 만들 수 있다. 즉 **moat가 되는 데이터를 모으면서도 사용자 코드를 가져갈 필요가 없다.**

이 방침은 기존 텔레메트리 방침과 정합한다: **1st-party 익명 수집 / opt-in / PII scrubbing** (memory: telemetry-privacy-policy — 자체 1차 BigQuery 비식별, 3rd-party 옵트인). control plane 데이터 전략은 이 기존 원칙의 자연스러운 확장이지 새로운 예외가 아니다.

## 6. 로드맵: Lite → Full 척추 → routing/evals 모델

control plane은 한 번에 완성되지 않는다. 신뢰와 스케일을 쌓아가며 3단계로 전개한다.

| 단계                   | 시점        | 범위                                     | 데이터           |
| ---------------------- | ----------- | ---------------------------------------- | ---------------- |
| **Lite**               | 베타 **전** | read-only, 기존 데이터 위                | 신규 수집 없음   |
| **Full 척추**          | 베타 **후** | 결정 로그 + 머지/배포 이벤트 캡처        | 결정·이벤트 추가 |
| **routing/evals 모델** | v4+         | trajectory 기반 routing·evals·merge-risk | opt-in 집계 후   |

### 6.1 Lite (베타 전) — read-only, 기존 데이터 위

기존에 이미 쌓이는 task + activity 데이터 위에 **read-only** 뷰를 얹는다. 신규 데이터 수집도, 백엔드/메인 프로세스 변경도 없이, **이미 있는 것을 보여주는** 단계. control plane의 첫 가시적 표면이자 가장 낮은 리스크의 진입점이다. (구체 스코프는 §7)

### 6.2 Full 척추 (베타 후) — 결정 로그 + 머지/배포 이벤트

§3의 ②의사결정 로그와 ③머지/배포 이벤트 캡처를 본격 구현해 provenance 번들의 빈 끝부분을 채운다. 이것이 control plane의 **"의사결정·감사 척추(spine)"** 다 — 작업 리스트 탭을 단순 목록에서 provenance 번들 + 결정 로그 + 머지/배포 이벤트 + 인라인 diff를 담는 감사 척추로 격상한다. (memory: 작업리스트탭을 "의사결정·감사 척추"로 격상)

### 6.3 routing/evals 모델 (v4+) — trust + 스케일 확보 후

충분한 trust(opt-in 동의)와 스케일(집계 가능한 양의 trajectory)이 쌓인 **후에야** §5.2의 routing/evals/merge-risk 예측 모델로 나아간다. 데이터가 먼저 신뢰 위에서 모이고, 모델은 그 뒤를 따른다 — 순서를 뒤집지 않는다.

## 7. Lite MVP 스코프 (검증 대상)

> 이 절은 베타 전 **Lite** 단계의 구체 MVP를 정의한다. 본 스코프의 renderer-only 실현 가능성은 별도 코드 조사(feasibility)로 검증되며, 그 결론이 출시 여부를 가른다.

### 7.1 무엇을 만드나

**read-only "작업내역" 탭.**

- 기존 **task + activity 데이터**만 사용한다.
- **DONE provenance 요약**을 렌더한다 — 완료된 작업의 problem/approach/changes/verification 요약을 activity 메시지에서 파싱해 보여준다.
- **PR 링크**를 렌더한다 — 완료 보고에 담긴 PR URL을 클릭 가능한 링크로.

### 7.2 제약 (목표)

- **electron-main 무변경**
- **백엔드 무변경**
- **배포(빌드/서명) 경로 무변경**

즉 **renderer-only**. 이미 렌더러가 읽고 있는 데이터 경로와 기존 컴포넌트를 재사용해, P0-7 서명빌드 임계경로를 건드리지 않고 베타 전에 안전하게 얹는 것이 목표다.

### 7.3 성공 기준

| 항목      | 기준                                                    |
| --------- | ------------------------------------------------------- |
| 데이터    | 신규 수집 0 — 기존 task/activity만                      |
| 변경 범위 | renderer(`v3/src/`)만, electron-main/백엔드/배포 무변경 |
| 산출물    | 완료 작업 provenance 요약 + PR 링크 read-only 뷰        |
| 리스크    | P0-7 서명빌드 임계경로 비접촉                           |

이 Lite 탭이 control plane의 첫 표면이며, 검증을 통과하면 베타 전 fast-follow로 출시한다. 이후 §6.2 Full 척추로 확장한다.

## 8. 로드맵 & 외부 연동

### 8.1 연동 우선순위

control plane이 가치를 전달하려면 실제 개발 워크플로의 이벤트가 안으로 흘러들어야 한다. 연동은 세 단계 우선순위로 접근한다.

**① GitHub 심화 (1순위)**  
현재 `gh` CLI로 앱 밖에서 이뤄지는 PR 생성·CI 확인·머지가 가장 큰 갭이다(§4, §3-③). PR 이벤트·CI 상태·머지 이벤트를 control plane 안으로 끌어오면 provenance 번들의 끝부분이 채워지고, 타임라인이 완성된다. 이것은 §6.2 Full 척추와 동일한 작업이며, 나머지 연동이 의미를 갖기 위한 토대이기도 하다.

**② Slack (2순위)**  
완료·리뷰대기·실패 알림을 Slack으로 내보내면 비동기 human-in-loop가 가능해진다. 개발자가 IDE나 앱 화면을 떠나 있어도 중요 이벤트에 반응할 수 있다. GitHub 연동이 이벤트를 안으로 끌어오는 작업이라면, Slack 연동은 그 이벤트를 팀 채널로 내보내는 작업이다.

**③ Linear / Jira / GitHub Issues (3순위)**  
이슈 트래커와의 양방향 동기화는 팀 워크플로에 끼어드는 진입점이다. 단, 팀 단위 사용자 신호(팀이 Marblo를 반복 사용하는 패턴)가 충분히 쌓인 후에 시도한다. Linear·Jira·GitHub Issues는 동일 패턴의 어댑터로 구현 가능하므로 순서는 수요에 따라 조정된다.

| 연동        | 방향       | 채우는 갭                             | 우선순위 |
| ----------- | ---------- | ------------------------------------- | -------- |
| GitHub 심화 | 인바운드   | PR/CI/머지 이벤트 → 타임라인 완성     | ★★★      |
| Slack       | 아웃바운드 | 비동기 human-in-loop                  | ★★       |
| Linear 등   | 양방향     | 팀 이슈 트래커 ↔ control plane 동기화 | ★        |

### 8.2 30/60/90일 사용자 여정

연동보다 먼저 이해해야 하는 것은 **사용자가 언제 Marblo에 붙는가**다. 30/60/90일 여정은 이 패턴을 명시한다.

**0–30일: 신기함 → 무의미**  
처음 만난 사용자는 "에이전트 여러 개 동시 실행"이 신기하다. 그러나 단 한 번의 실험으로 끝나면 그것으로 가치는 종료된다. 이 구간에서 Marblo는 인상을 남기지만, 아직 습관이 되지 않는다.

**31–60일: ★ 반복 사용 — 같은 저장소에 두 번째, 세 번째**  
가치가 폭발하는 구간이다. 같은 저장소에 두 번째·세 번째 작업을 돌릴 때 Marblo의 차별화가 체감된다.

- 하던 작업 이어서(resume) — 이전 컨텍스트가 살아 있다
- 실패 복구 — 어느 지점에서 무엇이 왜 실패했는지 추적 가능
- diff 리뷰 — 변경의 내막을 앱 안에서 바로 확인
- 테스트 결과 — CI 신호를 떠나지 않고 확인
- 연동 — 팀 채널로 이벤트가 흐른다

이 반복 사용 패턴이 확인되면 Marblo는 도구가 아니라 **습관**이 된다.

**61–90일: 유료화 전환**  
습관이 된 사용자에게 유료 전환을 제안한다. 핵심 가치 명제: "없으면 다시 혼자 병렬 관리를 해야 한다." 가격 방향: 개인 $20–30/월, 팀 $50–100/월.

| 구간    | 핵심 사건                | Marblo 역할                              |
| ------- | ------------------------ | ---------------------------------------- |
| 0–30일  | 첫 실행, 신기함          | 인상 형성 — 인터페이스·속도·가시성       |
| 31–60일 | 같은 repo 반복, 습관화 ★ | 재개·컨텍스트·실패복구·diff·CI·연동 체감 |
| 61–90일 | "없으면 불편" 인식       | 유료 전환 ($20–30 개인 / $50–100 팀)     |

### 8.3 Marblo 현황: 기반 절반 보유

31–60일 구간을 지탱하는 핵심 기능의 현재 상태다.

| 기능          | 현황 | 비고                                       |
| ------------- | ---- | ------------------------------------------ |
| 작업 재개     | ✅   | 에이전트 resume 동작 구현됨                |
| 컨텍스트 유지 | ✅   | task/activity 타임라인 보존                |
| 실패 복구     | ✅   | FAILED 상태·에러 로그 추적                 |
| diff 리뷰     | 🟡   | 인라인 diff 뷰 미완성 — §3-④ 갭            |
| 테스트 결과   | 🟡   | CI 상태 인바운드 미완성 — GitHub 연동 선행 |
| 외부 연동     | ❌   | GitHub/Slack/Linear 미구현 — §8.1 우선순위 |

기반의 절반은 이미 갖춰졌다. diff·테스트·연동이 다음 레이어다.

## 9. 바이럴 전략: "보이는 작업 과정"

### 9.1 바이럴의 원천은 생성된 코드가 아니라 보이는 과정이다

AI 코딩 도구의 바이럴 계기는 "AI가 코드를 써준다"는 사실 자체가 아니다. **"AI가 일하는 과정이 보인다"** 는 시각적 증거가 공유 욕구를 만든다. GitHub의 "Built with Copilot", Cursor의 "Built with Cursor" 배지가 작동한 것은 결과물 때문이 아니라 **그 과정을 증명**하기 때문이다.

Marblo의 바이럴 앵커는 다르다. "Shipped with Marblo" — 코드를 쓴 것이 아니라 **통제하며 출시했다**는 신호다.

### 9.2 공유 카드: 작업 과정 요약

Marblo는 완료된 작업 단위에서 **공유 카드**를 자동 생성한다. 예시:

> **Marblo ran 4 parallel agents**  
> 2 PRs drafted · 17 files changed · 36 tests passed · 1 risky dependency flagged

이 카드는 X(Twitter)·LinkedIn·Discord·GitHub PR comment에 붙여넣을 수 있는 형태로 제공된다. "에이전트가 얼마나 돌았고, 무엇이 확인되었고, 어떤 리스크가 감지되었는가"를 숫자로 요약한다.

공유 카드가 소셜에 퍼지면 두 가지가 일어난다.

1. **Marblo 이름 노출** — "Marblo"가 PR comment나 포스팅에 자연스럽게 등장한다.
2. **포지셔닝 증명** — 카드 자체가 "단순 실행기가 아니라 통제 레이어"라는 메시지를 담는다.

### 9.3 GitHub PR comment 채널

PR comment는 기술 사용자에게 가장 유기적인 노출 채널이다. Marblo가 생성한 PR에 자동으로 아래와 같은 요약 블록을 붙인다.

```
🤖 Marblo orchestrated this PR
• Agents: 4 parallel · Duration: 23 min
• Files changed: 17 · Tests: 36 passed, 0 failed
• Risk flags: 1 (dependency version mismatch)
• Decision log: [view in Marblo]
```

리뷰어가 PR을 열면 Marblo의 존재와 역할이 자연스럽게 가시화된다.

## 10. 벤치마크 콘텐츠 전략

### 10.1 같은 작업을 네 도구로 비교

Marblo의 포지셔닝을 **증명**하는 가장 효과적인 콘텐츠는 "같은 작업을 Cursor / Claude Code / Codex / Marblo로 각각 수행한 결과를 비교"하는 벤치마크다. 비교는 완성된 코드가 아니라 **control plane 관점의 축**으로 한다.

| 비교 축          | 측정 방법                             | Marblo 차별화 지점                  |
| ---------------- | ------------------------------------- | ----------------------------------- |
| 작업 분해 품질   | 서브태스크 세분화, 의존관계 명시 여부 | TaskForce 구조적 분해               |
| 진행 추적        | 어느 단계에 있는지 실시간 가시성      | 타임라인·활동 로그                  |
| 테스트·검증 루프 | 에이전트가 자체 테스트 돌리는지 여부  | CI 상태·테스트 결과 인라인          |
| PR 품질          | diff 크기, 커밋 구조, PR 설명 완성도  | provenance 번들→PR comment 자동화   |
| 사람 개입 횟수   | 에이전트가 멈춰 사람을 기다리는 빈도  | 비동기 human-in-loop(Slack 연동 후) |
| 실패 복구        | 에이전트 실패 후 재개까지 걸리는 시간 | FAILED 상태·재시작 컨텍스트 보존    |

### 10.2 이 비교 축이 곧 포지셔닝이다

이 여섯 축 모두에서 Marblo가 앞서는 이유는 **Marblo만이 실행기가 아니라 control plane을 목표로 설계되었기 때문**이다. Cursor나 Claude Code는 실행기로 설계되었고, 위 축들은 그들의 설계 목표가 아니다.

벤치마크 콘텐츠는 블로그·X·YouTube에 발행되어 두 가지 역할을 한다.

1. **인지(awareness)** — "Marblo라는 카테고리가 있다"를 알린다.
2. **설득(conversion)** — "같은 작업인데 차이가 이만큼 난다"를 숫자로 보여준다.

### 10.3 발행 형식

- **영상 비교** — 같은 작업을 네 도구로 실시간 캡처, 나란히 편집 (X·YouTube)
- **수치 리포트** — 위 여섯 축 데이터를 표로 정리한 블로그 포스트
- **GitHub PR comment 스크린샷** — "Marblo vs 도구X의 PR을 나란히 놓으면 무엇이 다른가"

## 11. 메시지 샤프닝

### 11.1 시장 컨텍스트: 좌절이 기회다

Stack Overflow Developer Survey 2025 데이터는 AI 코딩 도구의 현실을 선명하게 보여준다.

- **84%** 의 개발자가 AI 코딩 도구를 사용한다
- **51%** 가 매일 사용한다
- **66%** 가 "거의 맞지만 완전하지 않은 AI"에 좌절한다

84%가 사용하고, 66%가 좌절한다. 이 간극이 Marblo의 기회다. AI가 코드를 **쓰는** 것은 이미 보급되었다. 문제는 AI가 쓴 코드를 사람이 **믿고 관리하는** 것이다.

### 11.2 틀린 메시지 vs 올바른 메시지

| 틀린 프레임 (X)                 | 올바른 프레임 (O)                                         |
| ------------------------------- | --------------------------------------------------------- |
| "AI가 코드를 대신 써준다"       | "AI가 한 일을 사람이 안전하게 믿고 관리한다"              |
| "에이전트를 더 빠르게 실행한다" | "실행한 에이전트의 결과를 추적·검증·safe-merge한다"       |
| "AI 툴 중 하나"                 | "AI 툴 위의 control plane — 어떤 AI 툴과도 함께 쓴다"     |
| "새로운 코딩 경험"              | "하던 작업을 이어서(resume) — 컨텍스트가 사라지지 않는다" |

"AI가 코드를 써준다"는 프레임은 Cursor·Copilot·Claude Code가 이미 선점했다. 거기서 경쟁하면 실행기 간 기능 비교가 된다. Marblo는 **그 위 레이어**다.

### 11.3 핵심 메시지 두 가지

**① 믿고 관리 (Trust & Control)**

> "AI가 한 일을 사람이 믿고 관리하도록 — Marblo는 AI-native 팀의 control plane이다."

실행 결과가 맞는지, 어떤 결정이 내려졌는지, 머지해도 안전한지를 사람이 판단할 수 있는 신뢰 레이어가 Marblo다. 66%의 좌절("거의 맞지만 완전하지 않은")이 겨냥하는 지점이다.

**② 이어서 (Resume)**

> "하던 작업 이어서 — 컨텍스트는 사라지지 않는다."

에이전트를 껐다 켜도, 다음 날 돌아와도, 팀원이 이어받아도 — 작업의 맥락이 살아 있다. "새로운 무언가를 시작"이 아니라 **"하던 것을 이어서"** 가 반복 사용의 핵심 트리거다(§8.2 31–60일 구간).

### 11.4 포지셔닝 문장 (단일)

> **Marblo is the control plane for AI-native teams.**  
> _Run multiple AI agents. Track every decision. Merge safely._

한국어 버전:

> **Marblo는 AI-native 팀의 control plane이다.**  
> _여러 AI 에이전트를 동시에 실행하고, 모든 결정을 추적하고, 안전하게 머지한다._
