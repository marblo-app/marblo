# gmail_draft 대체 경로 — 도구 계약 설계

> 티켓 v5Phjv1WxndUpgFJyrIn. **설계 문서다. 이 티켓에서 UI 는 만들지 않는다.**
> 구현은 후속 티켓으로 간다.

## 1. 왜 바뀌었나

`gmail.compose` 는 Google 분류상 **restricted** 스코프다(널리 퍼진 "compose 는
sensitive" 는 틀린 이해다 — Gmail 에서 sensitive 인 것은 `gmail.send` 와 addons
계열뿐이고 `readonly` · `compose` · `metadata` · `modify` · `insert` 는 전부
restricted 다). restricted 를 하나라도 요청하면 외부 공개 시 **CASA 보안평가**
(유료 · 연 1회 갱신)가 따라붙는다. 일본 출시 일정을 그 심사에 걸 수 없어 뺐다.

빠진 것은 **Gmail 초안함에 레코드를 만드는 능력**이다. "초안을 사람이 검토한 뒤
보낸다" 는 흐름 자체는 그대로 살아 있다 — 검토가 Gmail 이 아니라 Marblo 안에서
일어날 뿐이고, 오히려 사용자가 앱을 벗어나지 않는다.

## 2. 지금 무엇이 남아 있나

| 조각                           | 상태                      | 근거                                     |
| ------------------------------ | ------------------------- | ---------------------------------------- |
| `gmail.send` 스코프            | **살아 있다** (sensitive) | `GOOGLE_CONNECTOR_WRITE_SCOPES`          |
| `gmail_send` MCP 도구          | **살아 있다**             | `confirm=true` 없이는 브리지가 거절      |
| `gmail_draft` MCP 도구         | 등록돼 있으나 잠김        | `withheldCapabilityError("gmail_draft")` |
| `GmailConnector.createDraft()` | 코드 유지, 호출 경로 차단 | 되살리기 비용 최소화                     |

즉 **발송 능력과 확인 게이트는 이미 있다.** 없는 것은 "보내기 전의 초안을 담아
두고 사용자에게 보여 주는 자리" 하나뿐이다.

## 3. 핵심 설계 판단

### 3.1 초안은 어디에 사는가 — 서버 아니고 **대화**다

초안을 새 저장소(Firestore 컬렉션 / 로컬 JSON)에 넣고 id 로 참조하는 안을 먼저
검토했고, 버렸다. 이유:

- 초안은 **수명이 대화 한 턴**이다. 사용자가 확인하거나 고치거나 버리면 끝난다.
  그 수명에 영속 저장소를 붙이면 만료·정리·소유권·프로젝트 격리를 전부 새로
  설계해야 하고, 얻는 것은 "새로고침해도 남아 있다" 뿐이다.
- 이미 있는 확인 장치를 두 번 만들게 된다. `gmail_send(confirm=true)` 가 곧
  "사용자 확인" 계약이고, 그 계약은 지금도 브리지에서 강제된다.

그래서 **초안은 에이전트의 답변 안에 있고, 확인은 사용자의 다음 발화다.**
저장소는 늘지 않는다.

### 3.2 새 MCP 도구를 만들지 않는다

`gmail_compose_preview` 같은 도구를 새로 넣는 안도 버렸다. 초안을 화면에 보여
주는 일은 **에이전트가 텍스트로 답하는 것**과 정확히 같은 행위다. 도구를 하나
더 만들면 워커 프리픽스(매 요청 재전송)만 무거워지고 능력은 늘지 않는다.

대신 **`gmail_send` 의 계약을 두 단계로 명문화**한다. 도구는 하나, 호출은 두 번.

## 4. 도구 계약 (제안)

### 4.1 `gmail_send` — 변경 없음, 계약만 명시

```
gmail_send(to, subject, body, cc?, bcc?, thread_id?, confirm)
```

- `confirm=false` 또는 생략 → 브리지가 거절하고 **거절 문장을 그대로 돌려준다**.
  이것이 사실상의 "초안 단계" 다. 에이전트는 이 응답을 받기 전에 이미 본문을
  알고 있으므로, 굳이 호출할 필요조차 없다.
- `confirm=true` → 발송. **사용자의 명시 확인 없이 true 를 넣는 것은 계약 위반**
  이고, 이 규칙은 이미 도구 설명과 감사 로그(`auditedTool`)에 걸려 있다.

### 4.2 에이전트 절차 (프롬프트 계약)

역할 스킬 / 비서 미션에 다음을 넣는다:

1. 메일을 보내야 한다고 판단하면, **먼저 초안을 답변으로 출력한다.**
   받는 사람 · 제목 · 본문 전문을 그대로 보여 준다. 요약하지 않는다 —
   사용자가 검토할 대상은 실제로 나갈 문장이다.
2. "이대로 보낼까요?" 로 끝낸다. `gmail_send` 를 이 턴에 호출하지 않는다.
3. 사용자가 수정하면 1로 돌아간다.
4. 사용자가 승인하면 **그 승인 발화를 근거로** `gmail_send(confirm=true)` 를
   한 번 호출한다.
5. 발송 후 `messageId` 와 `threadId` 를 답변에 남긴다(사용자가 Gmail 에서 찾을 수
   있어야 한다).

### 4.3 UI (후속 티켓)

최소 구현은 **아무것도 만들지 않는 것**이다 — 위 절차는 지금의 대화 UI 만으로
성립한다. 그 위에 얹을 수 있는 개선은 순서대로:

1. 초안 블록 렌더링 — 에이전트 답변에 `to/subject/body` 를 담은 약속된 블록이
   오면 카드로 그린다. **[보내기] [수정] [취소]** 버튼이 각각 정해진 문장을
   사용자 발화로 주입한다. 새 IPC 가 필요 없다.
2. 발송 전 최종 확인 다이얼로그 — 되돌릴 수 없는 동작이므로 한 번 더 묻는다.
3. 발송 이력 — `gmail_send` 성공 응답을 활동 타임라인에 남긴다.

★1번까지가 "Gmail 초안함보다 낫다" 고 말할 수 있는 지점이다. 2·3은 그다음이다.

## 5. 되살리기

CASA 를 통과해 `gmail.compose` 를 되찾으면:

1. `google-restricted-scopes.ts` 의 `WITHHELD_CAPABILITIES` 에서 `"gmail_draft"`
   를 뺀다.
2. 같은 파일의 `WITHHELD_RESTRICTED_SCOPES` 에서 `GMAIL_COMPOSE_SCOPE` 를 빼고,
   `google-drive-auth.ts` 의 `GOOGLE_CONNECTOR_WRITE_SCOPES` 에 넣는다.
3. `mcp-server/tool-surface.ts` 의 `ROLE_EXTRA_MCP_TOOLS.backend` 에
   `"gmail_draft"` 를 되돌린다.
4. `mcp-server/tools.ts` 의 `gmail_draft` 설명을 원래 문장으로 되돌린다.

그 사이 `createDraft()` 구현과 브리지 엔드포인트는 손대지 않고 남겨 둔다 —
지우지 않는 이유가 이 네 줄짜리 복원 절차다.

## 6. 이 설계가 포기한 것 (정직하게)

- **다른 기기의 Gmail 앱에서 초안을 이어 쓸 수 없다.** 초안이 Google 에 없으므로
  당연한 결과다. 사용자가 그걸 원하면 CASA 트랙을 밟아야 한다.
- **초안이 세션을 넘어 살아남지 않는다.** 3.1 의 의도적 선택이다.
- 위 둘 다 "지금은 못 한다" 이지 "영원히 안 한다" 가 아니다.
