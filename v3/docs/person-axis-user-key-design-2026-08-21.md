## 3. 결정 1 — 키는 `user_key` 하나. `person_key` 를 만들지 않는다

티켓이 물은 것: "계정축과의 연결을 `person_key` 로 할지 `user_key` 로 할지 하나로
정해라. **둘 다 두면 안 된다.**"

### 3.1 왜 둘 다 두면 안 되는가 (문제의 실체)

`person_key = HMAC(salt, "person:" + uid)` 와 `user_key = HMAC(salt, "user:" + uid)` 는
**같은 uid 에서 나온 서로 다른 두 값**이다. 종류(kind)가 다르면 같은 원시값이어도
다른 가명이 되도록 `analyticsPseudonym.ts` 가 일부러 그렇게 만들어져 있기 때문이다.

그래서 둘을 다 두면 `WHERE person_key = user_key` 가 **영원히 0행**이 된다. 조인이
에러를 내지 않고 그냥 빈다 — 행은 그대로 있고 표만 비어 보인다. `analyticsUserKey.ts`
주석이 이미 그 실패 모드를 이름 붙여 뒀다: "갈라지면 조인이 **조용히** 깨진다."

### 3.2 왜 `user_key` 쪽으로 수렴하는가

1. **이미 존재하는 유일한 구현물이다.** `analytics_purchase` 는 `user_key` 를
   `REQUIRED` 컬럼이자 클러스터 키로 **테이블을 이미 만들어 뒀다**. `person_key` 로
   가면 그 테이블의 스키마·클러스터·`REJECTED_FIELDS` 테스트·MERGE 경로를 전부
   고쳐야 한다 — 그건 설계가 아니라 **이미 머지된 것의 재작업**이고, 이 티켓이
   금지한 방향이다.
2. **배선점이 하나뿐이고 그 이름이 `user_key` 다.** `analyticsUserKey.ts` 의
   `resolveAnalyticsUserKeyFn()` 이 "공용 HMAC 함수 한 벌" 을 기다리며 `null` 을
   돌려주고 있다. 이 설계가 할 일은 **그 한 줄을 잇는 것**이지 옆에 두 번째 키를
   세우는 게 아니다.
3. **처리방침 개정 초안이 쓰는 말이 "가명 사용자키" 다**(`CjNfGmXvynZ5bk5vLuCZ` 본문).
   고지 문서와 컬럼 이름이 다르면 다음 사람이 둘을 다른 것으로 읽는다.
4. **`analyticsPseudonym.ts` 가 이미 `user` kind 를 예약해 뒀다.** 파일 상단 주석:
   "★`user`(계정 uid 축)는 여기 **없다.** `analytics_purchase` 티켓이 자기 축의
   것으로 추가한다."
5. **이름이 능력을 넘어서면 안 된다.** 파생 근거는 계정 uid 하나뿐이다. "person"
   이라고 부르면 미로그인 사용자·팀 공용계정까지 포괄하는 것처럼 읽히는데, 그건
   우리가 못 하는 일이다(§8). `user`(계정) 는 정확히 우리가 아는 만큼만 말한다.

### 3.3 확정 정의

```
user_key = "us_" + HMAC-SHA256(ANALYTICS_ID_SALT, "user:" + uid).hex[0:24]
```

- kind: `"user"` **하나 추가**. 새 솔트 없음, 새 모듈 없음 — `analyticsPseudonym.ts`
  의 `AnalyticsIdKind` 유니온과 `KIND_PREFIX` 에 각 한 줄.
- prefix `us_` — 기존 `ag/tk/pj/fl/in/ga` 와 충돌 없음.
- fail-safe 그대로 계승: 솔트가 없으면 원시값 폴백이 아니라 `null`.
- 계산 위치: **Node 프로세스 안에서만.** BQ SQL 에 솔트도 원시 uid 도 넣지 않는다
  (BQ 는 쿼리 본문을 job 히스토리에 수개월 보관한다 — 기존 결정 계승).

**"사람 축" 은 산문에서 쓰는 개념 이름이고, 컬럼·kind 이름은 `user_key`/`user` 다.**
문서·티켓에서 "사람 축" 이라고 부르되 스키마에 `person` 이라는 식별자를 만들지 않는다.

### 3.4 ★지뢰 하나 — `ANALYTICS_ID_FIELDS` 에 `userId` 를 올리지 마라

`ANALYTICS_ID_FIELDS` 는 익명 세계 insert 직전 `pseudonymizeAnalyticsRow` 가 훑는
**자동 치환 목록**이다. `user` kind 를 추가하면서 여기에

```ts
userId: "user",   // ★절대 금지
```

를 같이 올리고 싶어지는데, **익명 세계의 `userId` 컬럼에 들어 있는 값은 계정 uid 가
아니라 익명 설치 UUID 다**(36자, 고유 14). 이걸 `user` kind 로 가명화하면 그 순간부터
`install` kind 로 만든 `analytics_identity.install_key` 와 값이 달라져서
**593행짜리 익명축 조인이 통째로 끊긴다.** 행은 계속 쌓이고 조인만 0 이 된다.

`install`/`ga` kind 를 이 표에 안 올린 것과 정확히 같은 이유다. `user` kind 도
**호출측이 명시적으로** `pseudonymizeAnalyticsId("user", uid, salt)` 를 부른다.

## 4. 결정 2 — `analytics_identity` 를 고치지 않고, 링크표를 하나 더한다

### 4.2 `analytics_identity` 에 `user_key` 컬럼을 더하는 안을 기각하는 이유

| #   | 이유                                                                                                                                                                                                                                                            |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **그 테이블의 정체가 바뀐다.** `analytics_identity` 는 "익명축 전용, `user_key` 없음, **컬럼 자리도 없음**" 으로 정의돼 적재됐다. 컬럼을 더하면 이미 적재된 593행의 의미가 소급해서 바뀐다 — 익명 기록이던 것이 계정 연결 기록이 된다.                          |
| 2   | **그레인이 안 맞는다.** 이 표는 **설치당 1행**이다(`install_key` REQUIRED, 고유 593). 한 설치에 계정이 둘 로그인하면 담을 자리가 없어 **조용히 하나를 버린다**(마지막 사람이 이긴다). 지금 실측 0건이지만, 값을 못 담는 스키마는 이상치를 이상치로 못 보여준다. |
| 3   | **권한을 못 가른다.** 링크가 익명 표 안에 있으면 "익명축만 읽기" 권한을 아무에게도 줄 수 없다. 표를 가르면 `analytics_identity` 는 지금처럼 넓게 읽히게 두고 링크표 하나만 잠글 수 있다.                                                                        |
| 4   | **삭제요청 대응이 달라진다.** PIPA 제36조 삭제요청이 오면 별도 표에서는 `DELETE WHERE user_key = ?` 한 줄이고 익명축은 그대로 남는다. 컬럼이면 익명 표를 UPDATE 해야 한다.                                                                                      |
| 5   | **롤백 비용.** 별도 표는 `DROP TABLE` 하나로 사람 축이 통째로 사라지고 나머지는 무사하다. §5 의 "저장 소급 안 함" 과 합쳐지면 **이 설계 전체가 표 하나 지우면 원상복구**된다.                                                                                   |

## 5. 결정 3 — ★부여 시점과 소급 (이 문서에서 제일 중요한 결정)

### 5.1 부여 시점: **그 설치의 로그인 후 첫 인증 요청**

로그인이 유일한 기준이다. 그런데 우리 경우 그 시점이 이미 서버에 있다.

**텔레메트리 수신 콜러블은 auth 강제이므로 지금도 `context.auth.uid` 를 갖고 있고,
`telemetryMetadata.ts` 가 그걸 일부러 버리고 있다**(파일 주석: "예전에는
`logTelemetryBatch` 가 여기에 `accountUserId`(=Firebase uid)를 몰래 넣었다 … 코드를
고쳐 uid 부착을 중단했으므로").

그래서 부여는 이렇게 된다.

```
인증된 텔레메트리 요청 도착
  → 서버가 이미 가진 uid 를 메모리에서 HMAC → user_key
  → 요청이 실어온 installId 를 HMAC → install_key
  → analytics_user_install 에 (user_key, install_key) MERGE
  → ★uid 도 user_key 도 이벤트 행에는 붙지 않는다. 링크표에만 간다.
```

이 방식의 성질:

- **클라이언트 변경 0.** 앱이 새로 보내는 값이 없다.
- **수집 항목 증가 0.** uid 는 이미 auth 로 서버에 오고 있고, 우리는 저장하지 않고
  파생만 한다. 문구 개정 초안이 약속한 "수집 항목은 늘지 않는다 — 파생일 뿐이다"
  가 코드 사실과 일치한다.
- **이벤트 행 무변경.** 11,219,097행을 건드리지 않는다.

### 5.2 그 전 행은 어떻게 되는가

링크가 생기기 전의 행은 사람 축에서 **NULL** 이다. 정확히는 — 이벤트 행에 사람 축
컬럼이 **아예 없으므로** NULL 이라기보다 "링크표에 붙는 짝이 아직 없다" 다.

### 5.3 ★소급할 것인가 — 세 갈래와 판정

| 안                         | 무엇을 하나                                                                                         | 얻는 것                                                                  | 잃는 것 / 위험                                                                                                                                                     | 판정     |
| -------------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------- |
| **(A) 저장 소급**          | 과거 이벤트 행에 `user_key` 컬럼을 만들어 써넣는다                                                  | 조인 없이 바로 읽힘, 쿼리 단순                                           | ★익명 세계 테이블이 **계정 연결 테이블이 된다** — #915 를 통째로 되돌리는 일. 되돌릴 수 없다(삭제요청 = 1,100만행 UPDATE). 부분 적재 중 같은 지표가 두 값을 갖는다 | **기각** |
| **(B) 조회 소급 (무제한)** | 저장은 안 하고, 링크표를 `install_key` 로 조인하되 시간 필터 없이 그 설치의 전 이력을 사람에게 귀속 | 캠페인 first_touch(정의상 로그인 **전**에 발생) → 유료전환 귀속이 열린다 | 공용 기기면 남의 행이 붙는다. 개정 **전** 고지 하에 모인 행을 개정 후 기준으로 재해석한다                                                                          | 조건부   |
| **(C) 조회 as-of**         | `event_at >= first_linked_at` 인 행만 귀속                                                          | 가장 안전. 각 행이 "그 사람이 로그인한 뒤" 라는 사실만 씀                | ★캠페인 귀속이 통째로 죽는다 — first_touch 는 항상 링크보다 앞이다                                                                                                 | 기본값   |

### 5.4 ★권고 — 저장은 소급 없음, 조회는 소급 있음, 상한은 발효일

```
저장:  절대 소급하지 않는다. 이벤트 행에 user_key 컬럼을 만들지 않는다.
조회:  뷰 두 벌로 가른다.
        v_person_since_link   (C) — 기본. 모든 리텐션·코호트·활성화 지표
        v_person_all_time     (B) — 캠페인 귀속 전용. 라벨 필수
상한:  두 뷰 모두 event_at >= PERSON_AXIS_EFFECTIVE_FROM (개정 발효일)
```

**왜 이게 답인가 — 네 가지 근거.**

1. **소급을 저장에서 조회로 옮기면 되돌릴 수 있게 된다.** (A) 는 한번 쓰면 원본이
   사라진다. 뷰는 정의를 고치면 그 자리에서 바뀌고, 링크표를 지우면 소급도 즉시
   취소된다. 이 프로젝트가 오늘 오전에 배운 것이 정확히 그거다 — **되돌릴 수 없는
   쪽을 먼저 하지 않는다.**
2. **삭제요청이 한 줄이 된다.** `DELETE FROM analytics_user_install WHERE user_key = ?`
   하면 그 사람의 과거 귀속이 전부 풀리고 익명 기록은 익명으로 남는다.
3. **★상한을 거는 비용이 실측으로 0 이다.** 발효일 이전 유입 데이터는
   `install_attribution` 550행이고 그건 **전부 개발 재실행**, 실사용자 유입 **0명**이다.
   지금 상한을 걸어서 잃는 실데이터가 **없다**. 광고를 켜면 그때부터의 트래픽은
   상한 위쪽이라 온전히 얻는다. 안전한 쪽이 공짜인데 위험한 쪽을 고를 이유가 없다.
4. **뷰 이름이 곧 고지다.** 카드가 `v_person_all_time` 을 쓰면 화면에
   "설치 전체 이력 기준(소급)" 라벨이 붙는다(§10 규칙 5). 어느 기준인지 말하지 않는
   사람 축 숫자를 금지하면, 소급이 조용히 스며들지 않는다.

> ★상한을 발효일에 두는 것과 링크표를 권한분리 데이터셋에 두는 것은 스키마가 아니라
> **정책 경계**라 오케스트레이터에 비차단 질의로 올렸다(`#qmt2exevlds2l`). 둘 다
> 나중에 바꿀 수 있는 값(상수 하나 / 데이터셋명 하나)이라 설계와 순서는 그대로다.

### 5.5 ★공용 기기 — 조용히 몰아주지 않는다

한 `install_key` 에 `user_key` 가 2개 이상 달리면:

- 링크표는 **두 행을 그대로 담는다**(그레인이 쌍이므로 자연스럽게 담긴다).
- 그 설치는 **소급 뷰(`v_person_all_time`)에서 제외**한다. 로그인 전 행이 둘 중
  누구 것인지 알 근거가 없기 때문이다.
- `v_person_since_link` 에서도 그 설치의 행은 **사람 단위 집계에서 제외**하고,
  제외된 설치 수를 `AxisLimitNote` 로 화면에 적는다. 값을 만들지 않고 **센다.**

현재 실측 0건이다. 값이 없을 때 규칙을 박아야 나중에 규칙 없이 값이 생기지 않는다.

### 5.6 ★06-13 이전(`uid28`) 구간은 링크표 없이 붙는다 — 그래도 상한을 넘기지 않는다

그 시절 텔레메트리 `userId` 는 **계정 uid 그 자체**였다(28자, 205,192행, 고유 1).
즉 `pseudonymizeAnalyticsId("user", userId, salt)` 로 **직접** `user_key` 가 나온다 —
링크가 필요 없다. 링크표에 `link_source='uid28_inline'` 로 넣으면 된다.

★단 그 구간은 전부 개정 발효일보다 **앞**이므로 §5.4 의 상한에 걸려 기본적으로 쓰지
않는다. 쓰려면 별도 판단이 필요하다(§11). 그리고 `canStitchIdScheme` 이 스킴이 다르면
항상 false 인 규칙은 **install 축의 규칙이지 사람 축의 규칙이 아니다** — 같은 계정이
확인되면 06-13 을 건너 사람 이력을 잇는 것 자체는 정당하다(§8 의 얻는 것). 둘을 섞지
않도록 링크표에 `id_scheme` 를 같이 적는다.

## 6. 스키마 제안 (★비실행 — 구현 티켓에서 만든다)

### 6.1 새 표: `analytics_user_install`

- 데이터셋: **`marblo_identity`** (권고 — `marblo_telemetry` 와 권한 분리).
  처리방침 "처리 위치" 항이 학습데이터에 대해 이미 "접근 권한이 분리됩니다" 라는
  문법을 쓰고 있어 같은 말로 고지할 수 있다.
- 그레인: **(`user_key`, `install_key`) 한 쌍 = 한 행.** 사람→설치 1:N 이 행 수로 표현되고
  설치→사람 다중도 숨지 않는다.
- 파티션 `DAY(first_linked_at)` / 클러스터 `(user_key, install_key)`.
- 멱등: `row_id = HMAC("link:" + user_key + "|" + install_key)` 로 스테이징 로드 +
  MERGE. `analytics_purchase` 가 이미 검증한 패턴 그대로다(스트리밍 insertId 중복제거는
  수 분 창 best-effort 라 재실행 중복을 못 막는다).

| 컬럼              | 타입      | 모드     | 뜻                                                                        |
| ----------------- | --------- | -------- | ------------------------------------------------------------------------- |
| `row_id`          | STRING    | REQUIRED | MERGE 키. (user_key, install_key) 의 가명                                 |
| `user_key`        | STRING    | REQUIRED | `us_` + HMAC. ★원시 uid 는 어디에도 없다                                  |
| `install_key`     | STRING    | REQUIRED | `in_` + HMAC. `analytics_identity.install_key` 와 **같은 kind·같은 솔트** |
| `id_scheme`       | STRING    | REQUIRED | `uuid36` / `uid28` / `unknown` — `analyticsIdScheme.ts` 판정              |
| `link_source`     | STRING    | REQUIRED | `telemetry_auth`(정상) / `uid28_inline`(§5.6)                             |
| `first_linked_at` | TIMESTAMP | REQUIRED | ★**소급 경계의 단일 출처.** MERGE 로 덮지 않는다(MIN 유지)                |
| `last_seen_at`    | TIMESTAMP | REQUIRED | 최근 확인 시각. MERGE 가 갱신                                             |
| `policy_version`  | STRING    | REQUIRED | 어느 고지 하에서 만들어진 링크인가 — 삭제·소급 판단 근거                  |
| `ingested_at`     | TIMESTAMP | REQUIRED | 적재 시각                                                                 |

**넣지 않는 컬럼(자리도 만들지 않는다):** 원시 `uid`, 이메일, 이름, IP, 기기명,
`person_key`. — 빈 컬럼이 있으면 다음 사람이 "채우면 되겠네" 로 읽는다(기존 규약).

### 6.2 기존 표 변경

| 표                                              | 변경                                                                  |
| ----------------------------------------------- | --------------------------------------------------------------------- |
| `analytics_identity`                            | **없음**                                                              |
| `analytics_purchase`                            | **없음** (`user_key` 가 이미 REQUIRED 로 있다 — 채워지기만 하면 된다) |
| `events` / `agent_heartbeats` / `task_outcomes` | **없음.** ★사람 축 컬럼을 만들지 않는다(§5.4)                         |
| `install_attribution`                           | **없음**                                                              |

**DDL 변경 총량: 새 표 1개 생성. ALTER 0건.**

### 6.3 조인이 어떻게 성립하나

```
analytics_purchase ──user_key──┐
                               ├── analytics_user_install ──install_key── analytics_identity
cost_logs (uid, 별건)          ┘                                                  │
                                                                          ga_key  │
                                                                  ga4_first_touch_current
```

- 사람 단위 리텐션: `events.userId`(=설치) → `install_key` → 링크표 → `user_key`
- 캠페인 → 유료전환: `ga4_first_touch_current` → `analytics_identity` → 링크표 →
  `analytics_purchase` (소급 뷰 필요 — first_touch 는 링크보다 앞이므로)

### 6.4 뷰 두 벌

| 뷰                    | 조건                                                                                     | 쓰는 곳                         |
| --------------------- | ---------------------------------------------------------------------------------------- | ------------------------------- |
| `v_person_since_link` | `event_at >= GREATEST(first_linked_at, PERSON_AXIS_EFFECTIVE_FROM)` + 공용기기 설치 제외 | 리텐션·코호트·활성화 — **기본** |

| **4**  | 인증 텔레메트리 콜러블에서 링크 MERGE 배선 (**forward-only**)                                     | 배선 revert + 표 비우기      | 커버리지 0 → 오르기 시작. **여기서부터 '적재 중'**           |
| **5a** | `analytics_purchase` 과거분 백필 (MERGE 멱등, 자가검증 통과분 재사용)                             | 재실행 안전                  | '수익' 탭이 `PendingIngestion` → 정상                        |
| **5b** | `uid28` 구간 링크 백필 (`link_source='uid28_inline'`) — ★상한 판단 나온 뒤에만                    | 그 `link_source` 행만 DELETE | 각주 추가                                                    |
| **6**  | 커버리지 지표(`personAxisCoverage`) 서버 응답에 실음                                              | revert                       | ★화면이 **'적재 중 · N/M'** 을 말하기 시작                   |
| **7**  | 사람 축 탭의 퍼센트 헤드라인 개방 (`state === "complete"` 일 때만)                                | 규칙 하나                    | 정상                                                         |

**순서가 이렇게 잡힌 이유 셋**

- 1·2·3 은 **화면을 바꾸지 않는다.** 배선이 다 되고 나서 값이 흐르기 시작하므로,
  중간에 반쯤 채워진 표가 화면에 뜨는 구간이 없다.
- 4 를 3 뒤에 둔 이유: 표가 없는데 MERGE 가 돌면 에러가 조용히 삼켜질 자리가 생긴다.
- 5a 를 6 앞에 둔 이유: 커버리지를 먼저 노출하면 백필 도중의 커버리지가 화면에 뜬다.
  **적재가 끝난 축부터 켠다.**

## 10. ★부분 적재 중에 화면이 거짓말하지 않게 하는 법

### 10.1 지금 화면에는 상태가 둘뿐이다

`5bef1b1a` 가 박아둔 규약:

- `PendingIngestion` — **'적재 전'**. "0 이 아니라 소스가 없습니다" 를 화면이 직접 말한다.
- `AxisLimitNote` — 축 한계를 표 아래 각주가 아니라 **탭 머리**에 둔다.
- `Ratio` / `RatioCard` / `fmtRate` — 퍼센트 옆에 항상 원수치, 분모 0 은 `"—"`.
- `SmallSampleNotice` — 분모 10 이하면 "퍼센트로 읽지 마라" 를 화면에 적는다.

### 10.2 ★사람 축에는 세 번째 상태가 필요하다

`PendingIngestion`(0%) 과 정상(100%) 사이가 **길다.** 링크는 그 설치가 **다시 실행돼야**
생기기 때문에, 잠자는 설치는 며칠에서 영원히 안 붙는다. 이 구간에 정상 화면을 그리면
**커버리지가 오르는 동안 리텐션이 저절로 좋아지는 것처럼 보인다** — 그게 이 프로젝트가
막아야 할 거짓말이다.

### 10.3 서버가 실어 보내는 것

사람 축을 쓰는 **모든** 응답에 붙인다.

```ts
interface PersonAxisCoverage {
  state: "pending" | "ingesting" | "complete";
  linkedInstalls: number; // 링크된 설치
  totalInstalls: number; // 전체 설치
  linkedActiveInstalls: number; // ★조회 구간에 활동한 설치 중 링크된 수
  activeInstalls: number; // 조회 구간에 활동한 설치
  excludedSharedInstalls: number; // 공용 기기로 판정돼 제외된 설치 (§5.5)
  effectiveFrom: string; // 개정 발효일 — 소급 상한
  basis: "since_link" | "all_time"; // 이 카드가 어느 뷰를 썼나
  lastLinkedAt: string | null;
}
```

★`complete` 판정은 `linkedInstalls === totalInstalls` 가 **아니다.**
`linkedActiveInstalls === activeInstalls` 다 — 잠자는 설치를 기다리면 영원히
`complete` 가 안 되고, 그러면 이 장치가 늑대소년이 된다.

### 10.4 화면 규칙 일곱

1. **`state !== "complete"` 이면 퍼센트를 헤드라인으로 그리지 않는다.** 분수만 그린다
   — 기존 `Ratio`/`RatioCard` 규약의 연장이지 새 규약이 아니다.
2. **사람 축 지표의 분모는 "전체 설치" 가 아니라 "링크된 설치" 다.** 분모 라벨에 그
   말을 쓴다. 안 그러면 커버리지 상승이 지표 개선으로 읽힌다.
3. **새 컴포넌트 `IngestionProgress`** — `PendingIngestion` 과 같은 자리, 같은 문법:
   > **적재 중** · 활동한 설치 14대 중 **6대** 연결됨
   > 남은 8대는 다음 실행 때 붙습니다 · 지금 표는 **6대 기준**입니다
   > 공용 기기로 판정돼 제외: 0대
4. **"이 수치는 아직 커집니다" 를 먼저 말한다.** `ingesting` 동안 같은 기간을 다시
   조회하면 값이 올라간다 — 캡처해서 비교하면 안 된다는 뜻을 화면이 적는다.
5. **★라벨 없는 사람 축 숫자 금지.** `basis` 를 그대로 배지로 그린다 —
   `연결 이후 기준` / `설치 전체 이력 기준(소급)`. 소급이 조용히 스며들 자리를 없앤다.
6. **커버리지 0 이면 새 상태를 만들지 않는다.** `state="pending"` → 기존
   `PendingIngestion` 을 그대로 재사용한다.
7. **`effectiveFrom` 이전 구간을 조회하면** `AxisLimitNote` 가 탭 머리에 적는다:
   "이 기간은 사람 축 발효일 이전입니다 — 여기 0 은 '없음' 이 아니라 '사람 축이 없던
   때' 입니다." + `ChartMarkerLine` 으로 발효일에 점선(06-13 경계선과 같은 장치).
