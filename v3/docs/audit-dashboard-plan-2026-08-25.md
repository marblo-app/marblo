## 0. 한 문단 요약 — 이 문서가 새로 답하는 것

앞의 세 문서가 이미 많이 정해 놓았다. 이 문서가 **새로** 답하는 것은 넷이고, 전부 실측 근거가 있다.

| #   | 새로 답하는 것                                                     | 왜 앞 문서가 못 답했나                                                           |
| --- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| ①   | **경로** — `/audit-dashboard` 가 정본이고 `/team` 은 그리로 넘긴다 | #1206 은 `/team` 을 전제로 W-3 을 짰다. 사장님이 2026-08-25 에 경로를 확정하셨다 |
| ②   | **성공/실패 축** — 서버에 집계가 없다. 새로 만든다                 | 앞 문서들은 사용량·감사 두 축만 다뤘다                                           |
| ③   | **태스크 분해 축** — 서버는 이미 보내는데 **웹 계약이 안 받는다**  | 아무도 이 갭을 센 적이 없다                                                      |
| ④   | **컨설팅 전후** — 기간 비교 + '여기서 도입' 세로선                 | 사장님 사업 모델(AX 컨설팅)이 2026-08-25 에 처음 화면 요구가 됐다                |

그리고 이 문서가 새로 세우는 **편성 원칙 하나**:

> **첫 화면은 도입 첫날부터 값이 차는 축으로만 짠다.**
> 신규 고객사에서 화면이 비면 그건 영업 자산이 아니라 **반대 증거**다.
> 그 축은 둘이다 — **감사 원장**과 **비용**. 나머지 셋은 그 아래에 놓인다.

## 1. 두 층 — 섞으면 두 번 다시 못 푼다

이 경계는 새 규칙이 아니라 **이미 코드에 못박혀 있다**. `teamAudit.ts` 헤더가 `requireAdmin`
재사용을 명시적으로 거부한다: _"팀 오너는 다른 축이고, 한번 섞으면 '이 사람이 왜 이걸 보나' 를
두 번 다시 풀 수 없다."_

|           | `marblo.app/admin`                      | **`marblo.app/audit-dashboard`** (이 문서)              |
| --------- | --------------------------------------- | ------------------------------------------------------- |
| 보는 사람 | 사장님(우리)                            | **고객사** 조직 관리자                                  |
| 권한 축   | `isPlatformAdmin()` / `ADMIN_UID`       | `isProjectOwner` / `isAdminOrOwner` / `isProjectMember` |
| 스코프    | 전 테넌트 횡단                          | 자기 테넌트 안 — **남의 존재조차 모른다**               |
| 질문      | "우리 사업이 되고 있나"                 | "우리 조직이 무엇을 시켰고 얼마 썼나"                   |
| 데이터    | 익명축(`analytics_*`, GA4)              | **계정축**(`cost_logs`, `audit_logs`)                   |
| 서버      | `adminAnalytics.ts` · `betaSegments.ts` | `teamUsage.ts` · `teamAudit.ts`                         |
| 바탕      | 검정(`zinc-950`)                        | **화이트 + 블루**                                       |

### 1.1 ★이 화면에 **넣지 않는** 것 — 명시

아래는 전부 **어드민의 것**이다. 이름이 비슷해 보여도 이 화면에 들어오면 축이 섞인다.

| 넣지 않는다                                  | 어디 것인가                               |
| -------------------------------------------- | ----------------------------------------- |
| 리텐션 · 코호트                              | 어드민 (`X2piUBsQT6yPV4BHeBRP`)           |
| 활성화(activation) · 획득(acquisition) · CAC | 어드민                                    |
| 수익 · MRR · 결제 전환                       | 어드민                                    |
| 설치 수 · 봇 트래픽 · UTM · GA4              | 어드민 (익명축이라 애초에 조인 키가 없다) |
| DAU/WAU/MAU · 퍼널                           | 어드민                                    |

★**판정 규칙 한 줄:** 그 숫자의 주어가 _"우리 사업"_ 이면 어드민, _"우리 조직"_ 이면 여기다.

### 1.2 반대로 어드민이 가져가면 안 되는 것

`/admin/ProjectAuditPanel.tsx` 는 **플랫폼 admin 게이트 뒤에 있어서** 안전한 것이지 컴포넌트가
안전한 게 아니다. 고객 화면이 그걸 재사용하면 게이트만 다르고 **노출 필드는 같아진다**.
`instructionRedacted` 가 정확히 그 함정이다(§8.1).

## 2. ★경로 판정 — `/audit-dashboard` 가 정본이다

### 2.1 충돌 사실

사장님 지시(2026-08-25)는 `marblo-web` 아래 `audit-dashboard` 라는 **별도 사별 로그인 게이트**다.
그런데 #1206 의 **W-3** 은 콘솔 껍데기를 `team/layout.tsx` 에 짓는다. 두 계획이 갈린다.

### 2.2 판정

> **`/audit-dashboard` 가 정본 경로다. `/team/*` 은 `/audit-dashboard/*` 로 넘긴다.
> #1206 의 W-3(콘솔 껍데기)은 새 경로에서 수행한다 — 폐기가 아니라 이사다.**

근거 넷:

1. **URL 이 화면의 정체를 말한다.** `/team` 은 "내 팀 페이지" 로 읽히고 `/audit-dashboard` 는
   "감사 대시보드" 로 읽힌다. 기업 계약서·보안 검토서에 적히는 것은 후자다.
2. **비용이 거의 0 이다.** `team/page.tsx` 는 13줄이고 _프로젝트 선택을 화면이 하지 않는다_ —
   서버가 `context.auth.uid` 로 권한 집합을 도출한다. 즉 **라우트는 껍데기뿐**이고 옮길 상태가 없다.
3. **SEO 위험 0.** `team/layout.tsx` 가 이미 `robots: { index: false }` 다. 색인된 URL 이 없으니
   이사에 링크 자산 손실이 없다.
4. **리다이렉트 배선이 이미 있다.** `next.config.ts` 의 `/foundation50 → /founders` 3쌍
   (`/x`, `/ko/x`, `/:locale/x`)이 그대로 쓸 수 있는 형태다.

### 2.3 로케일 — 사장님 URL 이 그대로 성립한다

`src/i18n/routing.ts` 의 `localePrefix: "as-needed"`, `defaultLocale: "ko"`:

```
ko (기본)  →  marblo.app/audit-dashboard              ← ★사장님이 말씀하신 그 주소
en         →  marblo.app/en/audit-dashboard
ja         →  marblo.app/ja/audit-dashboard
```

**새 라우팅 규약을 만들 필요가 없다.** 파일은 `marblo-web/src/app/[locale]/audit-dashboard/`.

### 2.4 라우트 표

| 경로                           | 무엇                                     | 상태                                               |
| ------------------------------ | ---------------------------------------- | -------------------------------------------------- |
| `/audit-dashboard`             | 로그인 게이트 → 조직 요약(프로젝트 전체) | 신규(껍데기)                                       |
| `/audit-dashboard/[projectId]` | 프로젝트별 드릴다운                      | 신규(껍데기) — 오늘 `/team/[projectId]` 와 같은 뷰 |
| `/team`, `/team/*`             | **301 → `/audit-dashboard*`**            | 신규 리다이렉트                                    |

★`[projectId]` 는 **권한 근거가 아니다.** 서버가 교집합 필터로만 쓴다. URL 을 고쳐 넣어도
존재 여부조차 판정하지 않는다 — 판정이 곧 정보 누설이다(#1206 §5.3).

## 3. ★있는 것 / 새로 필요한 것 — 다섯 축 전수

사장님이 열거하신 다섯 축 그대로 갈랐다. **근거는 전부 파일·필드 이름이다.**

### 3.1 축 ① 감사 로그 — **거의 다 있다**

| 항목                   | 상태        | 근거                                                                                 |
| ---------------------- | ----------- | ------------------------------------------------------------------------------------ |
| 사건 피드(키셋 페이징) | ✅ 있다     | `teamAudit.ts` `getTeamProjectAudit` · `TeamAuditView.tsx` 769줄                     |
| 허용목록 fail-closed   | ✅ 있다     | `PROJECT_EVENT_TOOLS` 9개 밖은 응답에 안 실린다                                      |
| 자유텍스트 금지 3겹    | ✅ 있다     | `FORBIDDEN_RESPONSE_KEYS`(teamAudit.ts:1240) + 누출 정규식 가드(:1374) + 계약 테스트 |
| `withheld` 10줄 고지   | ✅ 있다     | `TEAM_AUDIT_WITHHELD` — 코드 + ko 문장 쌍                                            |
| 가명 행위자(`tm_`)     | ✅ 있다     | `analyticsPseudonym.ts` kind `teamMember`                                            |
| 사건 종류 필터         | ⚠️ **없다** | `TEAM_AUDIT_EVENT_KINDS` 5종이 계약에 있으나 화면 필터 UI 가 없다                    |
| 반출(CSV/JSON)         | ❌ 없다     | #1202 PR-5                                                                           |

### 3.2 축 ② 비용 — **서버는 다 있고, 게이트가 닫혀 있다**

| 항목                                 | 상태        | 근거                                                    |
| ------------------------------------ | ----------- | ------------------------------------------------------- |
| 총계·일별·구성원별·프로젝트별·모델별 | ✅ 있다     | `teamUsage.ts` 1,811줄 · `TeamUsageEnvelope`            |
| 다섯 상태 `UsageCell`                | ✅ 있다     | `measured`/`partial`/`notCollected`/`pending`/`unwired` |
| 오케 축 `not_collected`              | ✅ 있다     | `OrchestratorAxisEnvelope` — ★`0` 이 아니라 미수집      |
| **게이트**                           | 🔒 **닫힘** | `TEAM_USAGE_EFFECTIVE_FROM` 이 어느 배포 설정에도 없다  |
| 오케 지출 수집                       | ❌ 없다     | 2026-06-22 이후 0행. #1202 PR-3                         |
| `restricted` 여섯째 종류             | ❌ 없다     | #1209 §4.2 · PR-B                                       |

### 3.3 축 ③ 성공/실패 — **★사건마다 있는데 집계가 없다**

```
teamAudit.ts  TeamAuditEvent.success: boolean | null      ← 사건 한 줄마다 있다
teamAudit.ts  AuditTicket.failedActions: number           ← 티켓마다 있다
teamAudit.ts  TeamAuditSummary { eventsInWindow, eventsByKind, tasksTotal,
                                 tasksOpen, tasksDone, attentionCount,
                                 criticalCount, agentsTotal, missions* }
                                          ↑ ★성공/실패 집계가 여기 없다
```

**필요한 것(신규):** `TeamAuditSummary` 에 세 값을 더한다.

```ts
successCount: number | null; // success === true
failureCount: number | null; // success === false
outcomeUnknown: number | null; // success === null (merge_history 행이 여기 온다)
```

★**세 값이다. 둘이 아니다.** `success` 는 `boolean | null` 이고 `merge_history` 행은 원장 행이
아니라 항상 `null` 이다. 두 칸으로 접으면 `null` 이 실패로 굴러떨어지고, 그 순간 화면이
"머지할 때마다 실패" 라고 말한다. **#1209 §4 가 센 여섯 번의 `0` 실수와 정확히 같은 부류다.**

★**비율을 서버가 계산해 보낸다.** 화면이 `success/(success+failure)` 를 짓지 않는다 — 분모를
화면이 고르면 두 화면이 다른 분모를 쓰게 되고, 그건 #1198 이 "첫스폰 3.1%" 에서 밟은 사고다.
그리고 **표본 5 미만이면 비율 대신 `표본 부족(n=4)`** 을 적는다(#1206 §8.3, 임계 5는 티켓 지정).

### 3.4 축 ④ 태스크 분해 분석 — **★서버는 보내는데 웹이 안 받는다**

이게 이번 전수에서 나온 가장 값싼 발견이다.

```
서버:  teamAudit.ts:463   missions: TeamAuditMission[]
       teamAudit.ts:278   interface TeamAuditMission {
                            id; status; taskCount; doneCount;
                            statusCounts: Record<string, number>; updatedAt }
                                                    ↑ 태스크 분해 그 자체다

웹:    teamAuditContract.ts  → `missions` 를 정규화하는 코드가 **한 줄도 없다**
                               (`missionsTotal` / `missionsActive` 스칼라 둘만 받는다)
```

즉 **서버 배포도, 새 쿼리도 필요 없다.** 계약에 `missions[]` 정규화를 더하고 화면이 그리면 된다.
같이 쓸 재료도 이미 응답에 있다:

| 재료        | 필드                          | 무엇을 그리나                                                       |
| ----------- | ----------------------------- | ------------------------------------------------------------------- |
| 미션별 진척 | `taskCount` / `doneCount`     | 분해된 태스크 중 몇 개가 끝났나                                     |
| 상태 분포   | `statusCounts`                | TODO/IN_PROGRESS/REVIEW/DONE/FAILED/BLOCKED 분포                    |
| 역할 분포   | `AuditTicket.role`            | frontend/backend/test/devops 로 어떻게 갈렸나                       |
| 정체        | `attention` + `stalledJudged` | ★`stalledJudged === false` 는 "정체 아님" 이 아니라 **판정 유보**다 |

★**`missionGoal` 은 안 받는다.** 서버가 이미 뺐다(_"미션에 적은 목표 문장 — 사람이 직접 쓴
지시문입니다"_, `withheld_mission_goal`). 미션은 **id 와 숫자**로만 그린다.

### 3.5 축 ⑤ 프로젝트별 — **절반 있다**

| 항목                     | 상태               | 근거                                                         |
| ------------------------ | ------------------ | ------------------------------------------------------------ |
| 프로젝트별 비용 행       | ✅ 있다            | `ByProjectRow { projectId, projectName, costUsd, tokens }`   |
| 프로젝트 목록 + 역할     | ✅ 있다            | `TeamAuditProjectRef { id, name, role }`                     |
| 프로젝트별 **감사** 집계 | ⚠️ 단일 프로젝트만 | `getTeamProjectAudit` 는 `projectId` 하나를 받는다           |
| 프로젝트 드릴다운 라우트 | ✅ 있다            | `/team/[projectId]` → 이사 후 `/audit-dashboard/[projectId]` |
| 프로젝트 **비교 표**     | ❌ 없다            | 신규                                                         |

★**프로젝트별 감사 집계를 N+1 로 부르지 않는다.** 프로젝트 25개면 콜러블 25번이다. 첫 화면의
프로젝트 행은 **비용 봉투(`byProject`)만으로 그리고**, 감사 수치는 그 프로젝트를 열었을 때 채운다.
이건 성능 편의가 아니라 **#1209 §3.4-6 (행 개수가 곧 정보)** 과 같은 방향이다 — 안 부르면 안 샌다.

### 3.6 축을 가로지르는 것 — 기간 비교와 도입 마커 (신규)

| 항목                     | 상태               | 근거                                                                          |
| ------------------------ | ------------------ | ----------------------------------------------------------------------------- |

★마커 부품이 이미 있는 건 우연이 아니다 — 어드민이 "단위가 바뀐 날" 을 그으려고 만든 것이고,

## 4. ★첫 화면 편성 — 도입 첫날부터 값이 차는 축으로

### 4.1 원칙과 그 근거

사장님 지시: _"신규 고객사에서 화면이 비면 영업 자산이 아니라 반대 증거가 된다."_
이건 미학이 아니라 **데이터가 채워지는 시점의 문제**이므로, 축마다 "언제부터 차나" 를 센다.

| 축            | 첫 값이 언제 차나                                                           | 근거                                                            |
| ------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------- |
| **감사 원장** | ★**첫 태스크 1건에서 즉시**                                                 | `ledger.ts` 가 툴 호출마다 쓴다. 게이트 밖이라 설정도 필요 없다 |
| **비용**      | ★**첫 태스크 1건에서 즉시** — 단 `TEAM_USAGE_EFFECTIVE_FROM` 이 열려 있어야 | `cost_logs` 는 턴마다 적재된다                                  |
| 성공/실패     | 첫 태스크 1건에서 즉시(같은 원장 행의 파생)                                 | `TeamAuditEvent.success`                                        |
| 태스크 분해   | 미션을 만들어야 찬다 — **며칠 걸릴 수 있다**                                | `missions` 컬렉션                                               |
| 프로젝트별    | 프로젝트가 **둘 이상**이어야 의미가 있다                                    | 하나면 총계와 같은 값이다                                       |
| 기간 비교     | ★**최소 두 기간** — 도입 초기에는 원리적으로 빈다                           | 정의상                                                          |

### 4.2 그래서 순서가 이렇게 정해진다

```
┌ 상단 배너 ── 오케 미수집 고지 (있으면. 접히지 않는다)
├ 1층  요약 타일 4   ── 감사 사건 · 사용량 환산 비용 · 성공률 · 오케 축(미수집)
├ 2층  일별 추이 차트 ── 감사 사건 + 비용. ★'여기서 도입' 세로선 자리
├ 3층  탭 ─ [감사 원장] [비용] [태스크 분해] [프로젝트별]
└ 4층  탭 본문
```

★**1·2층은 첫날 반드시 값이 있다.** 3층 탭 중 태스크 분해·프로젝트별은 비어 있을 수 있고,
그건 **탭 안에서** 비는 것이라 첫 화면이 비지 않는다. 이 배치가 원칙의 전부다.

★요약 타일의 **1번이 '감사 사건'** 인 것도 의도다. 비용이 아니다 — 비용 타일은 게이트가
닫혀 있으면 `disabled` 문장이 되고, 그때 1번 자리가 비면 화면이 그 순간 반대 증거가 된다.

### 4.3 빈 상태를 만들지 않는다 — 상태 전량

#1206 §6.4 를 이 화면의 4개 탭에 그대로 적용한다. **`0` 을 그리지 않는다.**

| 상태                               | 화면                                                                     |
| ---------------------------------- | ------------------------------------------------------------------------ |
| `disabled` (게이트 닫힘/역할 없음) | 서버 `disabledReason` **문장 그대로**. 화면이 지어내지 않는다            |
| `not_provisioned` (적재 전)        | "아직 집계가 준비되지 않았습니다" — **`0` 이 아니다**                    |
| `empty` (행 0)                     | "이 기간에 기록이 없습니다" — `complete` + 합계 0 과 **구별해서** 그린다 |
| `partial`                          | 덮인 구간 배너 + 차트 빗금(`GapBand`)                                    |
| `restricted` (권한)                | #1209 §4.2 — "무엇이 필요한지" 를 말한다. 왜 없는지가 아니다             |
| 오류                               | 사유 + 재시도. ★이미 그린 감사 목록은 **지우지 않는다**                  |
| 로딩                               | 스켈레톤 — ★실제 차트 실루엣. 기존 값 위에는 `opacity` 만                |

## 5. 화면 구성 — 로그인 게이트부터 드릴다운까지

### 5.1 흐름

```
marblo.app/audit-dashboard
        │
        ├─ 미로그인 ─────→ 로그인 게이트 (★흰 바탕. 콘솔 스코프 안)
        │                   └→ /auth/login?redirect=… → 돌아온다
        │
        ├─ 로그인 + 역할 없음 ─→ 서버 문장 그대로 (존재 여부를 말하지 않는다)
        │
        └─ 로그인 + 역할 있음 ─→ 조직 요약
                                  ├─ 탭: 감사 원장 → 사건 필터 → 사건 상세(칩)
                                  ├─ 탭: 비용     → 구성원별/모델별/일별
                                  ├─ 탭: 태스크 분해 → 미션 → 그 미션의 사건으로 필터
                                  └─ 탭: 프로젝트별 → /audit-dashboard/[projectId]
```

### 5.2 로그인 게이트 — #1206 §5.4 를 그대로 쓴다

★**게이트도 콘솔 스코프 안에 있어야 한다.** 로그인 전엔 검고 후엔 흰 화면은 _"다른 사이트로
갔나"_ 로 읽힌다. 그리고 `[locale]/layout.tsx` 의 마케팅 크롬(`Header`/`Footer`/`PromoBar`)을
이 경로에서 끈다 — 프로모바가 붙은 화면은 SaaS 콘솔로 안 읽힌다.

게이트가 **말하는 것**: 화면 이름 · 무엇을 볼 수 있는지 · 역할에 따라 범위가 다르다는 예고.
게이트가 **말하지 않는 것**: 조직·프로젝트의 존재 여부, 초대된 이메일(§8.2).

### 5.3 상단바

```
[Marblo 콘솔]   [프로젝트 전체 ▾]        [7일 · 30일 · 90일 · 맞춤]   [내보내기] [새로고침]
```

★프로젝트 셀렉터는 **서버가 준 목록**(`envelope.projects`)만 그린다. 화면이 목록을 만들지 않는다.
★기간 선택기는 서버 `days` 를 재조회한다 — 받은 30점을 확대하는 브러시가 아니라 **실제로
정확해지는** 재조회다(#1206 §4.7).

### 5.4 탭 본문 — 다섯 축이 어디 놓이나

| 탭                | 위                                 | 아래                                                          | 인터랙션                                                                                  |
| ----------------- | ---------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| **감사 원장** ①   | 종류 필터 칩(5종) + 성공/실패 필터 | 사건 표 — 시각·행위자(가명)·종류·티켓·결과                    | 키셋 '더 보기'(오늘 그대로) · 행 클릭 → 그 티켓의 사건만 · ★하단 `withheld` **상시 노출** |
| **비용** ②        | 총계·일별 차트                     | 구성원별 · 모델별 · 일별 표                                   | 정렬 · 행 클릭 → 그 구성원/그날로 좁힘                                                    |
| **성공/실패** ③   | — **독립 탭이 아니다**             | 요약 타일 3번 + 감사 탭의 필터 + 태스크 분해의 `statusCounts` | ★§5.5                                                                                     |
| **태스크 분해** ④ | 미션 목록(진척 막대)               | 상태 분포 · 역할 분포 · 정체 티켓                             | 미션 클릭 → 감사 탭을 그 미션으로 필터                                                    |
| **프로젝트별** ⑤  | 프로젝트 비교 표(비용·토큰)        | —                                                             | 행 클릭 → `/audit-dashboard/[projectId]`                                                  |

### 5.5 ★성공/실패를 독립 탭으로 만들지 않는 이유

사장님이 다섯 축을 열거하셨지만 **성공/실패는 다른 넷의 속성이지 그 자체로 화면이 아니다.**
독립 탭으로 뽑으면 같은 원장을 세 번 세는 화면이 셋 생기고, 세 곳의 분모가 갈라진다.

**그래서 이렇게 배치한다 — 축은 살리고 화면만 안 만든다:**

- 요약 타일 **3번**이 성공률이다(첫 화면에서 바로 보인다)
- 감사 원장 탭에 **성공/실패 필터 칩**
- 태스크 분해 탭의 `statusCounts` 에 `FAILED`/`BLOCKED` 가 이미 있다
- 사건 행마다 결과 배지

★사장님께 드리는 판단 요청: 독립 탭을 원하시면 만든다. 다만 그때는 **분모를 서버 한 곳에서만
계산한다**는 조건이 붙는다(§11-1).

## 6. ★컨설팅 전후 — 이 화면이 직접 값을 만드는 자리

사장님 사업 모델이 AX 컨설팅이므로 **"도입 전에는 이랬고 후에는 이렇다"** 가 곧 청구서다.
그래서 자리를 **미리 남겨 둔다** — 나중에 끼워 넣으면 화면 전체를 다시 짠다.

### 6.1 '여기서 도입' 세로선 — 부품이 이미 있다

```ts
// marblo-web/src/components/charts/types.ts  ← ★이 티켓은 이 파일을 건드리지 않는다
export type ChartMarkerSpec = { date: string; label: string; hint?: string };
export function markerIndexOf(dates: string[], marker): number | null;
//   구간 밖이면 null — 선을 긋지 않는다
```

**필요한 것은 `date` 하나뿐이다.** 어디서 오나 — 후보 셋:

| 안  | 출처                               | 비용 | 판단                                   |
| --- | ---------------------------------- | ---- | -------------------------------------- |
| A   | 프로젝트 문서의 `createdAt`        | 0    | 도입일이 아니라 **생성일**이다. 다르다 |
| B   | 조직 설정에 **관리자가 직접 입력** | 소   | ★**권고.** 컨설팅 시작일은 사람만 안다 |
| C   | 첫 원장 행의 날짜                  | 소   | "도입" 이 아니라 "첫 사용" 이다        |

★**권고 B.** 그리고 마커는 **하나가 아니라 목록**으로 둔다 — 컨설팅이 여러 차례면
`[{date, label}]` 이 자연스럽고, `ChartMarkerSpec` 이 이미 그 모양이다.

### 6.2 기간 비교 — 서버 계약을 넓히는 유일한 자리

오늘 `getTeamUsageSummary({ days })` 는 **단창**이다. 비교는 두 창이 필요하다.

```
안 1 (권고):  화면이 같은 콜러블을 두 번 부른다 — { days: 30 } 와 { days: 30, endBefore: … }
              · 서버 변경: `endBefore` 파라미터 하나
              · 캐시가 그대로 산다(창마다 다른 키)
안 2:         서버가 { compare: true } 로 두 창을 한 봉투에 담는다
              · 봉투 모양이 바뀐다 → 기존 화면 회귀 위험
```

★**권고 안 1.** 이유는 성능이 아니라 **#1209 §3.5 의 시간 차분 공격**이다. 두 창을 한 봉투에
담으면 그 봉투에 "두 창의 차" 를 넣고 싶은 유혹이 생기고, 차분은 **권한 경계에서 가장 위험한
파생값**이다. 창을 따로 받으면 각 창이 각자의 게이트를 통과한다 — 게이트가 두 번 걸린다.

### 6.3 비교를 그릴 때의 규율 — 셋

1. **두 창의 상태가 다르면 비교를 안 그린다.** 앞 창이 `not_provisioned` 이고 뒤 창이
   `complete` 면 "300% 개선" 이 나온다. 그건 개선이 아니라 **적재 시작**이다.
   → 화면은 증감 대신 _"이전 기간은 집계 전입니다"_ 를 그린다.
2. **증감률의 분모가 0 이면 `—`.** `∞` 도 `100%` 도 아니다(#1206 §8.3 규약).
3. ★**"컨설팅 덕분" 이라고 화면이 말하지 않는다.** 화면은 _"도입 표시 이전 30일 / 이후 30일"_
   이라는 **사실만** 적는다. 인과는 사람이 말한다 — 화면이 말하면 그건 감사 대시보드가 아니다.

## 7. 화이트·블루 — 새 색을 만들지 않는다

### 7.1 #1206 이 이미 풀어 놓았다. 그대로 쓴다

```css
/* marblo-web/src/app/globals.css — PR #1206 W-0 */
@theme {
  --color-accent: var(--color-brand-500);
} /* ★inline 밖. 안 그러면 스코프가 죽는다 */
.marblo-console {
  /* ★@layer 밖 */
  --color-surface: #ffffff;
  --color-ink: #18181b;
  --color-accent: var(--color-brand-600); /* #4f46e5 · 6.29:1 */
  --color-accent-soft: var(--color-brand-50); /* #eef2ff */
}
```

★핵심 두 가지를 다시 적는다(이 문서를 읽고 구현하는 사람이 놓치면 조용히 죽는 자리다):

1. **의미 토큰은 `@theme inline` 안에 두면 안 된다.** `inline` 은 유틸이 토큰 이름 대신
   **참조된 변수**를 굽는다 → `.marblo-console { --color-accent: … }` 가 **죽은 규칙**이 된다.
   오류도 경고도 없다. 그냥 안 먹는다.
2. **알파 수식자 금지**(`bg-surface/60`). Tailwind v4 는 알파 변형의 `@supports` **폴백 가지에
   값을 리터럴로 굽는다** → 폴백에서 어두운 값이 밝은 화면에 칠해진다. 반투명이 필요하면
   그 표면을 토큰으로 만든다(`surface-sunken`).

### 7.2 강조색이 `brand-500` 이 아니라 `brand-600` 인 이유 — 취향이 아니라 계산

```
#6366f1 (brand-500) on #ffffff = 4.47:1   ← AA 본문 4.5:1 에 미달
#4f46e5 (brand-600) on #ffffff = 6.29:1   ← 통과
```

**램프에 이미 있던 값이다.** 색을 만든 게 아니라 한 칸 내려온 것이다.

### 7.3 스코프 경계 — 나머지 블랙 화면을 안 건드린다

|                                 | 적용                                                                           |
| ------------------------------- | ------------------------------------------------------------------------------ |
| `.marblo-console` 래퍼          | `/audit-dashboard/**` 에만                                                     |
| `<body>` 의 `bg-zinc-950`       | 그대로 둔다 — 콘솔 래퍼가 `bg-surface` 로 덮는다                               |
| 브랜드 스케일 `--color-brand-*` | ★**재정의하지 않는다.** 브랜드는 한 벌이다                                     |
| 차트 색 `--viz-*`               | `charts/tokens.css` 의 `.viz-root[data-viz-surface="light"]` 가 이미 갖고 있다 |
| 마케팅·랜딩·블로그              | 손대지 않는다                                                                  |

★**가드가 이 경계를 지킨다**(#1206 §3.3, W-1): 의미 토큰이 `@theme` **와** `.marblo-console`
**양쪽에** 정의됐는지, `@theme inline` 에 색 별칭이 있는지를 기계가 본다. v4 의 실패는 빨간
글씨가 아니라 **무색**이라 눈으로는 절대 못 잡는다.

## 8. 지켜야 할 규율 둘

### 8.1 자유텍스트 — 화면이 조심하는 게 아니라 봉투에 자리가 없다

| 금지                                   | 근거                                                                                                        |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `params` 원문                          | `FORBIDDEN_RESPONSE_KEYS`(teamAudit.ts:1240)                                                                |
| ★`instructionRedacted`                 | **같은 목록에 나란히 있다.** 고객 축에서 금지 — 허용되는 곳은 `projectAudit.ts:658`(우리 플랫폼 admin 축)뿐 |
| `result` · `message` · `text` · `goal` | 같은 목록                                                                                                   |
| 저장소 경로 · 원시 신원                | 같은 목록                                                                                                   |

★**이 화면이 반드시 하는 것: 안 보여준다는 사실을 보여준다.**
`withheld` 10줄을 **접어 두지 말고 감사 탭 하단에 상시 노출한다.**

> 이건 면책 문구가 아니라 **제품 기능**이다. 기업이 사는 것은 "다 보여주는 화면" 이 아니라
> **"무엇을 안 보는지 말할 수 있는 화면"** 이다. 고객사가 자기 직원에게 이 화면을 설명해야
> 하고, 그때 필요한 게 정확히 이 목록이다.

★그리고 **감사 탭에 금액 필드가 한 개도 없다는 사실**도 밝힌다. 이유가 있다 — 감사 탭은
사용량 게이트 **밖**이라, 돈을 실으면 `TEAM_USAGE_EFFECTIVE_FROM` 게이트가 감사 탭을 경유해
우회된다(`teamAudit.ts:32`). 밝은 화면에서 _"요약 타일에 비용도 넣자"_ 는 제안이 나올 자리가
정확히 여기다. **넣으면 게이트가 뚫린다.**

### 8.2 권한 경계 — 총계는 뺄셈 경로다

#1209 §3.3 의 불변식을 그대로 진다:

> **총계는 그 총계를 이루는 항목을 전부 볼 수 있는 사람에게만 보인다.** > `f(S)` 를 `u` 에게 보이려면 `S ⊆ visible(u)`.

★**1단계는 대칭 공개 스위치를 만들지 않는다**(사장님 승인). 관리자가 전부 보면 충분하다.
그래서 이 화면의 1단계 규율은 짧다:

| 시점                       | 이 화면                                                                                   |
| -------------------------- | ----------------------------------------------------------------------------------------- |
| 조직 관리자                | 전체를 본다 — 총계·순위·평균·차트 Y축 전부                                                |
| 프로젝트 관리자(팀장)      | 자기 프로젝트만. **조직 총계 칸은 `restricted`** — 값이 아니라 *무엇이 필요한지*를 적는다 |
| 일반 멤버(`scope: "self"`) | 본인 것만. ★**팀 총계를 그리지 않는다** — 2인 팀에서 `팀총계 − 내사용량 = 상대방`         |

★**차트 Y축 자동 스케일이 뺄셈 경로다.** 축 상단이 총계에 맞춰 늘어나면 눈금이 곧 총계다.
→ **스코프 밖 값이 Y축 계산에 들어가지 않는다.** 서버가 봉투에 안 실으면 자동으로 지켜진다
(#1209 §6.4 — _"봉투에서 뺀다. 화면에서 숨기지 않는다"_).

★**`scope === "self"` 면 타일 개수가 달라진다.** 4개가 아니라 3개다. 빈 자리를 남기지 않고
_"본인 기록만 표시됩니다"_ 배지로 **사실로 채운다**.

## 9. 해외 SaaS 느낌 — 판정 기준 6개를 규칙으로

사장님이 주신 기준을 막연히 두지 않고 **구현 가능한 규칙**으로 옮긴다. 시안이 이 규칙대로 지어졌다.

| 기준                               | 규칙                                                                                                                                                                 |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **tabular-nums**                   | 숫자를 그리는 모든 자리에 `font-variant-numeric: tabular-nums`. 표는 `text-align: right` + 소수점 자리 고정. 숫자가 바뀔 때 열이 흔들리면 그 화면은 콘솔로 안 읽힌다 |
| **위계는 크기가 아니라 무게와 색** | 본문 크기는 **두 단**뿐(13px 본문 / 11px 라벨). 값은 24px 하나. 나머지 위계는 전부 `font-weight`(400/500/600)와 잉크 3단(`ink`/`ink-muted`/`ink-faint`)              |
| **격자를 거의 안 보이게**          | 표에 세로선 없음. 가로선은 `--color-line`(#e4e4e7) 1px 만. 카드 테두리 1px, 그림자 없음. 차트 격자선은 가로만                                                        |
| **여백 하나로 통일**               | **8px 배수 하나**. 카드 안 패딩 16px, 카드 사이 12px, 섹션 사이 24px. 다른 값을 쓰지 않는다                                                                          |
| **스켈레톤이 실제 차트 실루엣**    | 회색 사각형이 아니라 **그 차트의 실제 모양** — 축 자리·막대 자리·라벨 자리가 실물과 같은 좌표에 있다. 로드 시 화면이 튀지 않는 것이 목적이다                         |
| **전이 150ms 안쪽**                | `transition: … 120ms ease`. 넘는 값 금지. `prefers-reduced-motion` 이면 0                                                                                            |

★하나 더 — **밝은 바탕에서 '빈칸' 은 그냥 흰색이라 아무것도 없는 것처럼 보인다.** 어두운
화면보다 훨씬 위험하다. 그래서 미수집 칸은 흰 여백이 아니라 **`--color-warn-soft` 바탕 + 빗금 +
아이콘**으로 **적극적으로 그린다**(#1206 §8.1).

## 11. 열린 질문 (사장님·오케 판단)

1. **성공/실패를 독립 탭으로 원하시나.** 내 권고는 §5.5 의 배치(타일 + 필터 + 상태 분포)다.
   독립 탭을 만들면 **분모를 서버 한 곳에서만 계산한다**는 조건이 반드시 붙는다.
2. ★**게이트 개방 순서.** 비용 축이 첫 화면 요약 타일에 있는데 `TEAM_USAGE_EFFECTIVE_FROM` 이
   닫혀 있다. #1202 §10.2 가 **PR-3(오케 수집) → PR-4(게이트 개방)** 순서를 못박았다 —
   지출의 29%가 비는 화면을 기업에 먼저 보여주면 나중에 채웠을 때 _"그럼 그때 본 숫자는
   뭐였냐"_ 가 온다. **신뢰는 그 한 번에 깨진다.** 이 화면의 영업 투입 시점이 그 순서에 묶인다.
3. **도입일 입력 주체**(§6.1). 권고는 **조직 관리자 직접 입력**(안 B)인데, 컨설팅 계약 정보라
   우리가 넣어 드리는 게 맞을 수도 있다. 넣어 드리면 그 값은 **고객사가 못 고치는 값**이 된다.
4. **데모 테넌트를 우리 실데이터로 쓰나**(#1202 §11-5 재확인). 실제 원장이라 설득력이 크지만
   우리 티켓 제목·프로젝트 이름이 노출된다. 시안은 **가상 데이터**로 지었다.
5. **차트 라이브러리 최종 확정.** 티켓 본문은 `recharts 확정` 이라 했는데 리포에 머지된 것은
   **visx**(`package.json` `@visx/*` 5개 · `docs/CHART-LIBRARY-DECISION-2026-08-24.md`)이고,
   #1210 이 둘을 실물로 비교해 사장님 판단을 기다리는 상태다. **이 문서는 어느 쪽이든 성립한다**
   — 이 티켓은 화면 구성이고 부품은 병행 티켓의 것이다. 다만 §6.1 의 도입 마커는 오늘 `visx`
   쪽 `ChartMarkerSpec` 에 붙어 있으므로, recharts 로 확정되면 **그 부품이 같이 이사해야 한다**.
6. **`/team` 301 의 시점.** 지금 `/team` 을 쓰는 외부 사용자가 실질적으로 없다면 즉시 옮기는
   게 싸다. 있다면 한 배포 동안 양쪽을 살려 두는 편이 안전하다. 실사용 여부는 우리가 안다.
