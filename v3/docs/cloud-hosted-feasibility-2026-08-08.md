## 2. 전제 재검토 — "CLI 설치가 핵심 마찰"은 어디까지 사실인가

티켓 코멘트는 "#850 이 CLI 설치 전제를 핵심 마찰로 지목"이라고 적었다. 정확히 하면 **#850 이 실제로 말한 것은 이거다**:

| #850 § | 실측                                                                                           | 클라우드가 여기에 듣는가                       |
| ------ | ---------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| §S1    | 30일 GA4 방문 542 → lead 52 → `/download` 141 → GH 인스톨러 82 → **로그인까지 간 신규 설치 6** | **★여기가 최대 누수. 클라우드가 정면으로 침**  |
| §S2    | `b304e231` 트레이스: ①install 단계 진입 → **2시간 15분 공백** → 재실행 후에야 ②auth 통과       | **★직접 지문 1건. 클라우드가 이 단계를 삭제**  |
| §4     | "설치했지만 로그인 안 함"은 **영구 비가시** — 몇 명인지 모른다                                 | 클라우드는 이 사각 자체를 없앰(브라우저 =설치) |
| §5-B   | 로그인한 외부 6명 중 **3명(50%)이 첫 완료 도달**                                               | ✕ 여긴 이미 되고 있다. 클라우드가 고칠 게 없음 |
| §S6    | 6명 중 5명이 **하루만** 씀. 완료한 3명 중 2명도 하루만                                         | ✕ 재방문 절벽은 클라우드로 안 고쳐진다         |

**정직한 결론 셋**:

1. **클라우드는 활성화(첫 완료) 레버가 아니다.** 첫 완료는 이미 절반이 통과한다. 클라우드가 겨냥하는 건 **그 앞 단계(유입→설치→로그인)** 이고, 규모로 보면 거기가 압도적으로 크다(141 vs 6).
2. **"CLI 설치=핵심 마찰"의 직접 증거는 아직 n=1 이다**(§S2 의 2시간15분 공백). 나머지는 "141 → 6 사이 어딘가에서 샌다"는 간접 증거이고, #850 §4 대로 **그 사이가 안 보인다**. 클라우드의 기대효과를 숫자로 약속할 수 없다는 뜻이다.
3. 그래서 이 문서의 MVP(§10)는 **전면 이전이 아니라 실험**이다. install-ping(#850 P1-1)이 붙으면 "설치→로그인" 전환율이 처음 산출되고, Cloud Try 는 그 분모를 **우회하는 대조군**이 된다. 두 개를 같이 굴려야 클라우드가 실제로 레버인지 판정된다.

### 2-B. ★wzb8(오카) 이 이 문서 집필 중 착지했고, 전제 하나를 깬다

이 스파이크의 티켓 코멘트는 "오카 대비(wzb8) H1 가설=오카가 셋업마찰 적음"을 근거로 든다. wzb8 이 #865 로 착지하면서 **H1 을 "결론 지지 / 근거 기각"으로 판정**했다:

| wzb8 H1 판정                                                                                                                                                                 | 이 스파이크에 대한 함의                                      |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| **기각**: 오카는 호스티드가 **아니다.** 공식 문서 "Not a hosted VPS product" · "Orca does not sell managed VPS hosting". 데스크탑 설치도, CLI 도 필요하다                    | **"경쟁사가 호스티드니 우리도"라는 논거는 성립하지 않는다**  |
| **지지**: 그럼에도 체감 마찰은 실제로 적다. 이유 셋 — ①**계정 없음**("Orca has no account system") ②CLI 작업이 **퍼널 밖** ③첫 실행에 `~/.claude`·`~/.codex` **자동 임포트** | 마찰의 원인은 실행 위치가 아니라 **퍼널 경계**               |
| wzb8 결론: _"우리가 호스티드로 가야 한다는 결론이 아니라, **퍼널 경계를 다시 그으면 된다**"_ (§8 NEW-B)                                                                      | **더 싼 대안이 같은 지문을 겨냥한다**                        |
| wzb8 §7 이탈 진범 순위: (1)측정 축 오류 (2)재방문 장치 부재 (3)퍼널 경계 (4)첫 가치 정의                                                                                     | 클라우드가 겨냥하는 건 **3위**. 1·2위는 클라우드로 안 고쳐짐 |

**이게 이 문서의 권고를 바꾼다 — 결론이 아니라 순서를.**

`b304e231` 의 ①install 2시간15분 단절은 이 스파이크와 wzb8 NEW-B 가 **같이 겨냥하는 단 하나의 실측 지문**이다. 그런데 두 개입의 비용이 다르다:

| 개입                                                                                                              | 규모                                | 겨냥                         |
| ----------------------------------------------------------------------------------------------------------------- | ----------------------------------- | ---------------------------- |
| **wzb8 NEW-B** 퍼널 경계 재설정(①②를 차단 스텝→조용한 전제 점검, 이미 충족 시 접기, "CLI 없이 둘러보기" 1급 승격) | 렌더러 3파일, **중**                | 같은 지문                    |
| **wzb8 NEW-C** 첫 가치를 오케 앞으로(폴더 연결 직후 에이전트 1기 즉시)                                            | 기존 스폰 경로 재사용, **중**       | 같은 dead-end(#850 §S4)      |
| **이 문서의 Cloud Try**(§10)                                                                                      | 신규 런타임+컨테이너+운영, **중대** | 같은 지문 + 설치 자체를 제거 |

**따라서: NEW-B/NEW-C 를 먼저 태운다.** 둘 다 클라우드보다 싸고, 같은 증거를 겨냥하고, 성공하면 클라우드의 한계 가치가 줄어든다. 그래도 141→6 이 안 움직이면 — 그때는 "앱을 켜기 전에 이탈한다"가 남고, **그건 클라우드만 풀 수 있다.**

**클라우드가 오카 대비 갖는 진짜 우위 하나**: 오카는 마찰을 _퍼널 밖으로 밀어냈지만 없애지는 못했다_(유저는 여전히 CLI 를 설치·인증한다). 클라우드는 **그 작업 자체를 소멸**시킨다. 이건 오카가 현재 아키텍처(데스크탑 + BYO 컴퓨트)로는 따라올 수 없는 유일한 축이다. 다만 §8-A 대로 **하이퍼스케일러들은 이미 거기 있다.**

**클라우드가 오카 대비 못 따라가는 것 하나 (정직하게)**: 오카의 마찰 우위 3요소 중 첫째가 **"계정 없음"** 이다. 우리 클라우드는 정의상 **계정이 필수**다 — 누구에게 컨테이너를 주고 누구에게 한도를 걸지 알아야 한다. 즉 **클라우드는 ②③(CLI 설치·인증)을 없애지만 ①(계정 게이트)은 오히려 강제한다.** 순 마찰 감소량은 "설치+인증 − 계정" 이지 "설치+인증" 이 아니다.

| 메인프로세스 → 헤드리스 Node 서버(`ipcMain.handle` → HTTP/WS 라우트) | 139개 핸들러. **MVP 는 그중 ~25개면 됨**(pty·agent·orchestrator·fs 최소)          |
| `preload.ts` → WS RPC 클라이언트 어댑터                              | 946줄 1파일 재구현                                                                |
| 렌더러                                                               | **거의 무변경**(node builtin 0, electronAPI 계약 유지)                            |
| 컨테이너 이미지                                                      | Node + git + claude/codex CLI + 언어 런타임                                       |
| 신규로 지어야 하는 것                                                | 세션 오케스트레이션(프로비저닝·suspend·GC), 크레덴셜 볼트, egress 정책, 남용 방지 |

**가장 큰 미지는 코드가 아니라 운영이다.** 스테이트풀 컨테이너 fleet 을 굴리는 일은 지금 인력(사장님 1인 + 에이전트)에게 새 상시 부담이다 — 그래서 §4 의 옵션 비교에서 "우리가 fleet 을 굴리는가"가 핵심 축이 된다.

## 4. 아키텍처 옵션

### 옵션 A — 유저별 관리형 컨테이너 (Codespaces/Replit 모델)

마블로 런타임 전체(헤드리스 메인프로세스)를 유저당 컨테이너 1개에. 브라우저의 렌더러가 WSS 로 붙는다. 워크트리·PTY·에이전트 전부 진짜.

- ✅ 데스크톱과 의미가 1:1. **라이브 오케 해자가 그대로 보존**된다
- ✅ §3-B 덕에 데이터 경계·제어면·인증 UX 를 재설계 안 해도 됨
- ❌ 활성 유저-시간당 원가 발생(§7-A). 콜드스타트. 스테이트풀 운영
- ❌ 보안 표면 최대: 에이전트가 임의 코드를 실행한다

> **선례**: Anthropic 의 self-hosted environments 가 정확히 이 모양이고, 격리 규칙이 **"runner 1대 = 유저 1명 락"** 이다 — "최소 fleet 크기 = 동시 활성 유저 수". 우리도 같은 제약을 물려받는다.[출처]

### 옵션 B — 서버리스 / 태스크당 일회용 샌드박스 (Jules·Codex cloud·Copilot cloud agent 모델)

퍼시스턴트 워크스페이스 없음. 티켓 1건 = 샌드박스 1개가 clone → 에이전트 1기 실행 → 브랜치/PR push → 소멸.

- ✅ 제일 쌈. 0 으로 스케일. 스테이트가 없어 보안이 단순
- ❌ **해자를 죽인다.** 라이브 오케가 없다 = 지켜보는 오케 없음, 멀티에이전트 실시간 조율 없음, 유저가 말 걸 PTY 없음
- ❌ 그 자리는 이미 Jules(무료 15태스크/일)·Copilot cloud agent($0.04/세션)가 점유. **우리가 열화 카피가 된다**
- **판정: 기각.** 마블로의 정체성은 "티켓 하나 돌려주는 봇"이 아니라 "라이브 오케 중심 통제면"이다(memory: `marblo_vs_orca_strategy_and_moat`)

### 옵션 C — 씬 컨트롤플레인 + 유저 소유 러너 (BYO runner)

웹 UI 는 우리가 호스팅, 실행은 유저가 띄운 러너(자기 맥, 자기 클라우드)에서. Anthropic 이 self-hosted environments 로 출시한 바로 그 모양이고, 우리 `bridge-server` 가 이미 반쯤 그것이다.

- ✅ COGS 거의 0. 해자 보존. **크레덴셜이 유저 인프라를 안 떠나서 ToS 문제 자체가 소멸**
- ✅ "모바일/다른 기기에서 내 fleet 보기"라는 별개의 진짜 수요를 푼다
- ❌ **제로셋업 문제를 안 푼다.** 유저는 여전히 러너를 설치한다
- **판정: 가치 있으나 이 티켓의 답이 아니다.** 별도 축으로 백로그(§12 후보)

### 옵션 D — 시연 전용 관리형 컨테이너 (Cloud Try) → 이후 데스크톱/유료 클라우드로 인계

옵션 A 의 축소판을 **첫 성공까지만** 쓴다. 데모 레포 + 우리 토큰 + 하드 캡 + 시간 제한. 첫 완료를 브라우저에서 보여주고 나서 (a) 데스크톱 설치 또는 (b) 유료 클라우드로 인계.

- ✅ 가설(§2)을 **월 $80 수준**으로 산다(§7-C). 호스팅 경제성에 회사를 안 건다
- ✅ ToS 회색지대를 **우회**한다 — 데모는 **우리 API 키**(Commercial Terms, 명확히 합법)로 돌고 유저 구독을 안 만진다
- ✅ 실패해도 버리는 비용이 작고, 성공하면 그대로 A 의 1단계가 된다
- ❌ 데모 레포 한정이라 "내 코드로 일 시킨다"는 진짜 가치는 아직 못 준다
- **판정: ★MVP 는 이것**(§10)

### 5-C. 모델 2·4 의 ToS — 무엇이 확인됐고 무엇이 안 됐나

**[출처] 확인된 것 (긍정)**

- `claude setup-token` 은 **1년짜리 OAuth 토큰**을 발급하고 "CI 파이프라인·스크립트용"이라고 공식 문서화돼 있다. "Pro/Max/Team/Enterprise 구독 필요", 그리고 **"모델 요청만 가능"** — Remote Control 수립이나 claude.ai 커넥터 접근은 못 한다. 즉 **탈취돼도 블래스트 반경이 모델 호출로 제한**된다.
- Anthropic devcontainer 문서는 **"코드스페이스 간 인증을 나르려면 `CLAUDE_CODE_OAUTH_TOKEN` 을 Codespaces secret 으로 저장하라"** 고 명시한다. **서드파티 클라우드에 구독 토큰을 주입하는 것을 벤더가 직접 안내**하는 선례다.
- `CLAUDE_CONFIG_DIR` 로 크레덴셜 디렉터리를 임의 볼륨에 재배치할 수 있다 → 유저별 격리가 공식 경로.
- Codex 는 대응물이 정확히 있다: **`CODEX_ACCESS_TOKEN`**("ChatGPT 또는 Codex 액세스 토큰을 신뢰된 자동화에 제공"), `CODEX_HOME` 로 상태 루트 분리.

**[출처] 확인된 것 (부정)**

- Anthropic **Consumer Terms of Service §2**(2025-10-08 발효): _"You may not share your Account login information, Anthropic API key, or Account credentials with anyone else. You also may not make your Account available to anyone else."_

**해석과 그 한계**

두 사실은 정면충돌하지 않는다. "다른 사람에게 공유"가 금지된 것이고, 유저가 자기 토큰을 자기가 고른 실행 환경에 넣는 건 Codespaces 사례가 보여주듯 상정된 사용이다. **그러나** 우리 모델에서는 그 토큰이 **마블로가 운영하는 인프라에 상주**하고, 이론상 우리 운영자가 접근 가능하다. Codespaces(Microsoft)와의 차이는 규모·신뢰·계약이지 구조가 아니다.

**→ 이건 엔지니어가 판정할 문제가 아니다.** 권고:

1. MVP(§10)는 **모델 1(우리 키·하드캡)** 로만 간다 → ToS 문제를 만나지 않는다.
2. 유료 클라우드로 확장하기 **전에** 사장님이 Anthropic/OpenAI 에 서면 확인을 받는다(§12 S8). 확인 못 받으면 **모델 3(BYO API 키)만** 지원한다 — 이건 Commercial Terms 상 명확하고 앱에 이미 경로가 있다.
3. 어느 경우에도 **우리 크레덴셜과 유저 크레덴셜을 같은 컨테이너에 두지 않는다.**

### 5-D. 모델 4 가 UX 상 최선인 이유

비기너 설계(§5)가 이미 답을 갖고 있다: `cliSetupActions.launchLogin(model, cmd)` 이 실 PTY 세션에 `claude login` 을 타이핑하고, 그 세션을 **연결 카드 안에 인라인 `<TerminalView>` 로 임베드**해 CLI 가 인쇄하는 인증 URL 을 유저가 보게 한다.

컨테이너에서도 **똑같이 동작한다** — PTY 가 진짜고, URL 은 텍스트고, 유저 브라우저가 그 URL 을 연다. 즉 **클라우드 인증 UX 를 새로 설계할 필요가 없고, 유저가 토큰 문자열을 다루지 않아도 된다.** 다만 ToS posture 는 모델 2 와 동일하다(크레덴셜이 우리 볼륨에 남는다).

### 5-E. 그록

memory `grok_orchestrator_and_byom_stack`·`grok_native_harness_two_layer_spawn_bugs` 대로 그록은 **브라우저 인증(SuperGrok 구독)** 이고 `XAI_API_KEY` 와 다르다. 헤드리스 토큰 주입 경로가 공식 문서화돼 있지 않다. **MVP 에서 그록은 제외**하고, 클라우드 1차 벤더는 **Claude + Codex** 로 한정한다.

### 8-A. 이미 이 자리에 누가 있나 **[출처]**

**냉정한 사실**: "브라우저에서 코딩 에이전트를 돌린다"는 **이미 상품화됐고, 사실상 공짜로 배포되고 있다.** 우리가 그 자리에 늦게 들어가 같은 것을 판다면 이길 이유가 없다.

### 8-B. 그러면 우리가 파는 것은

memory `marblo_product_positioning`·`marblo_vs_orca_strategy_and_moat` 대로 마블로의 해자는 **실행이 아니라 통제면**이다 — 라이브 오케, 여러 물리 에이전트의 동시 지휘, 추적(원장·비용·라우팅), safe-merge.

| 저들이 파는 것                  | 우리가 파는 것                                              |
| ------------------------------- | ----------------------------------------------------------- |
| "티켓 하나 던지면 PR 하나 온다" | **"에이전트 팀 하나를 지휘한다"** — 보드·오케·워크트리·머지 |
| 세션 = 프롬프트 1개             | 세션 = **여러 에이전트가 동시에 도는 워크스페이스**         |
| 벤더 락인(각자 자기 모델)       | **벤더 중립**(claude/codex/grok/로컬모델 혼용 + 라우팅)     |

**클라우드 전략의 함의**: 우리가 클라우드로 가는 이유는 _실행을 팔기 위해서가 아니라_, **통제면을 체험하는 문턱을 없애기 위해서**다. 그래서 옵션 B(태스크당 서버리스)는 기각이고 — 그건 실행을 파는 모양이다 — 옵션 D 는 통제면(비기너 셸 = 오케챗 + 라이브 스트립)을 첫 화면에 그대로 보여준다.

### 8-C. 오카 대비

§2-B 에 상세. 요약하면 **"오카가 호스티드라서 이긴다"는 틀렸고**(wzb8 실조사: "Not a hosted VPS product"), 오카의 마찰 우위는 계정 부재 + 퍼널 경계에서 왔다. 그래서 이 스파이크의 원래 동기 중 하나("오카 따라잡기")는 **소멸**한다.

남는 것은 더 좁고 더 정직한 동기다:

| 축                         | 오카가 할 수 있는 것              | 클라우드만 할 수 있는 것 |
| -------------------------- | --------------------------------- | ------------------------ |
| CLI 설치·인증 마찰         | 퍼널 **밖으로 밀기**(여전히 존재) | **소멸**                 |
| 계정 게이트                | **없앰**                          | ✕ 오히려 필수(과금·한도) |
| 데스크탑 앱 설치           | 필요                              | **소멸**                 |
| 라이브 오케 + 멀티에이전트 | 있음(Experimental 뒤)             | 있음(첫 화면)            |

즉 클라우드는 **오카를 이기는 수가 아니라, 오카도 우리도 못 없앤 마찰층(설치)을 없애는 수**다. 그 값어치가 §7-C 의 원가와 §11 의 리스크를 넘는지가 이 문서의 질문이고, §10 MVP 가 그 답을 사는 방법이다.

## 13. 한계 · 정직성

- **효과 크기를 모른다.** "CLI 설치 제거 → 전환 +N%"를 이 문서는 주장하지 않는다. #850 의 직접 지문은 1건이고, 141→6 구간은 §4 대로 **비가시**다. MVP 는 그 미지를 사는 것이지 없애는 게 아니다.
- **비용은 전부 [추정]이다.** 단가는 공시가 실측이지만, "월 활성 25시간" 같은 사용량 가정에는 데이터가 없다 — 외부 코호트 6명 중 5명이 하루만 썼으니(§2) 오히려 과대추정일 수 있고, 반대로 파워유저 1명이 전체를 태울 수도 있다. S5 가 이걸 실측한다.
- **환율 ₩1,400/$ 는 가정이다.** COGS 비율은 환율에 그대로 흔들린다.
- **ToS 해석은 법률 자문이 아니다.** 인용한 것은 공개 약관 문구뿐이고, 판단은 사장님/법무의 몫이다.
- **포팅 규모는 코드 계측 기반의 자릿수 추정이지 견적이 아니다.** "IPC 139개 중 25개"는 MVP 범위 판단이고, 실제로 어떤 25개인지는 S2 에서 확정된다.
- **관리형 샌드박스 3사를 실제로 써 보지 않았다.** 단가는 공시가고, 격리 등급·콜드스타트·세션 수명 한도는 S6 에서 실측해야 한다.
- **오카 실조사는 이 문서가 한 게 아니다.** wzb8(#865)이 했고, 이 문서는 집필 중 그것이 착지해 §2-B·§8-C 를 다시 썼다. 오카 관련 주장은 전부 wzb8 인용이며, 이 문서가 독립 검증하지 않았다.
- **S-1 이 클라우드보다 낫다는 것도 [추정]이다.** "퍼널 경계 재설정이 141→6 을 움직인다"는 증거도 같은 n=1 지문에 걸려 있다. 다만 **틀렸을 때의 비용이 훨씬 싸서** 먼저 태우라는 것이다.
- 날조 없음. 모든 벤더 수치는 §14 의 URL 을 `/browse` 로 직접 열어 읽었고, 코드 인용은 파일·행 번호로 확인 가능하다.
