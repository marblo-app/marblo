### 3-B. ★F2 가 생각보다 강한 제약이다 [코드]

우리 프록시는 유저 머신의 **`claude` 바이너리**에게 붙는다. 그 바이너리는 `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN` 으로만 방향을 튼다([코드] `model-registry.ts:183,545,625,726` 의 env-swap 3벤더가 전부 이 모양).

**다른 하네스는 우리 레포에 base-url 우회 배선이 없다**: `OPENAI_BASE_URL` · `model_providers` · `base_url` 을 `v3/electron/` 전체에서 grep 하면 **0건**이다 [코드]. 즉 —

| 하네스             | 벤더   | 우리 프록시로 돌릴 수 있나                                                      |
| ------------------ | ------ | ------------------------------------------------------------------------------- |
| `claude`           | 전부   | ✅ env 2개로 끝(env-swap 축 그대로, #883 §5-B)                                  |
| `gpt`(codex)       | OpenAI | ⚠️ **배선 없음.** codex 의 provider 설정을 새로 다루는 별도 작업이 필요(미검증) |
| `grok`(Grok Build) | xAI    | ⚠️ **배선 없음.** 게다가 Shape A 네이티브 하네스라 스폰 이슈 이력이 있다        |

★**따라서 어느 벤더를 고르든 실행 경로는 "claude 하네스 + 우리 Anthropic 호환 게이트웨이" 하나다.** 벤더가 Anthropic 이 아니면 게이트웨이가 **번역기**가 되고, Anthropic 이면 **패스스루**가 된다. 이 차이가 §3-D 판정의 절반을 만든다.

### 3-C. ★F3(품질)이 #883 §4 의 결론을 뒤집는다

#883 §4 는 "ToS·하네스·마진 세 조건을 동시에 만족하는 유일한 칸 = MiniMax pay-go" 라고 적었다. 그 판단은 **틀리지 않았다 — 렌즈가 다르다.**

| 렌즈               | #883 §4 (무료·CAC 온램프) | **L2 (유료 크레딧)**                              |
| ------------------ | ------------------------- | ------------------------------------------------- |
| 실패의 대가        | 활성화 실험이 오염된다    | **돈을 받고 결과를 못 준다** = 환불 + 신뢰 손실   |
| 최적화 대상        | 유저당 원가 최소화        | **첫 유료 티켓의 완주율**                         |
| 저품질 모델의 비용 | 기회비용                  | **직접 손실**(잔액은 소모됐는데 티켓은 안 끝났다) |

여기에 사내 실측이 겹친다: **저가·타 벤더 모델은 조사·단순 작업엔 되지만 복잡한 in-repo 코딩에서 산출이 없었다**(메모 `spawn_model_pref_codex_grok_save_claude`·`grok_orchestrator_and_byom_stack`). MiniMax-M2.7 로 ₩10,000 이 19티켓을 사 준다는 #883 §3-C 의 산술은, **그 19티켓이 하나도 안 끝나면 마진이 아니라 환불 대기열**이다.

> **정직성**: 우리는 MiniMax/Kimi 로 **실제 티켓 완주율을 재 본 적이 없다**(#883 §10 이 같은 한계를 적었다). "탈락"은 측정된 실패가 아니라 **미검증 리스크를 유료 첫인상에 태울 수 없다**는 판단이다. §11 의 품질 게이트(G-P2)를 통과하면 언제든 복귀할 수 있다.

## 4. ★단위경제 — 진짜 지배변수는 마크업이 아니다

### 4-A. 프롬프트 캐시가 깨지면 원가가 6.4배 [추정 = #885 §3 실측 × Anthropic 승수]

#885 §3 이 실측한 태스크당 **평균 토큰 믹스**: 순수 입력 74.3k · **캐시 재읽기 11.9M** · 캐시 쓰기 249k · 출력 79.0k.
Anthropic 승수[출처, #883 §3-F]: 캐시 읽기 **0.1×** · 5분 캐시 쓰기 **1.25×**. `claude-opus-5` = $5/$25 per 1M [코드 `model-registry.ts:374`].

| 시나리오                      | 산식                                               | 티켓 1건 원가 |
| ----------------------------- | -------------------------------------------------- | ------------: |
| **캐시 보존**(정상)           | 0.074M×$5 + 11.9M×$0.5 + 0.249M×$6.25 + 0.079M×$25 |     **$9.85** |
| **캐시 파손**(전량 정가 입력) | 12.223M×$5 + 0.079M×$25                            |    **$63.10** |
| 배수                          |                                                    |     **6.4배** |

**★이 한 줄이 L2 엔지니어링의 최우선 요구사항을 정한다**: 마크업 30% 가 티켓당 버는 돈은 **≈$3**(= $9.85×0.3)이다. 캐시 파손의 대가는 **+$53** 이다. **마진의 17배가 캐시 한 조각에 걸려 있다.**

캐시가 깨지는 현실적 경로 넷 — 프록시 설계가 전부 막아야 한다:

| 경로                                                | 왜 깨지나                                  | 설계 요구                                       |
| --------------------------------------------------- | ------------------------------------------ | ----------------------------------------------- |
| 프록시가 `cache_control` 블록을 **정규화·재직렬화** | 프리픽스 바이트가 1비트만 달라도 캐시 미스 | ★**요청 본문 변형 금지** — 바이트 그대로 릴레이 |
| 시스템 프롬프트에 **우리 헤더·필드 주입**           | 프리픽스가 바뀐다                          | 메타데이터는 **헤더로만**, body 는 불변         |
| 유저별 라우팅이 업스트림 **계정/리전을 섞음**       | 캐시는 계정+프리픽스 스코프                | 단일 계정·단일 리전 고정                        |
| 재시도·리트라이가 캐시 TTL(5분)을 넘김              | 재시도마다 새 캐시 쓰기(1.25×)             | 재시도 상한 + 백오프를 TTL 안에                 |

> **정직성**: 위 산술은 **평균 믹스**로 계산한 값이라 #885 의 **중앙값 실측 $5.25** 보다 높다(꼬리가 평균을 끌어올린다). 절대값은 흔들리지만 **배수(6.4배)** 는 믹스 비율에서만 나오므로 유지된다. 그리고 이 배수는 PoC 에서 **직접 측정 가능**하다(§11 G-P1).

### 4-B. 마크업 — 1.1× 인가 1.3× 인가

#883 §3-C 의 산식(환율 ₩1,400/$ · PG 실효 3.74% · 해외결제 1.5%)에 **고정비 회수선**을 더한다. 게이트웨이 상주 원가 ≈**$43/월**[문서 #885 §2-D], 토스 연 관리비 ₩110,000[문서 #883 §3-E].

| 마크업         | 충전 ₩10,000당 마진 | 마진율 | 게이트웨이($43/월) 회수에 필요한 **월 충전건수** | 연 관리비 회수 **연 건수** |
| -------------- | ------------------: | -----: | -----------------------------------------------: | -------------------------: |
| **1.1×**(10%)  |            **₩398** |   4.0% |                                     **151건/월** |                   276건/년 |
| 1.2×(20%)      |              ₩1,168 |  11.7% |                                          52건/월 |                    95건/년 |
| **★1.3×**(30%) |          **₩1,818** |  18.2% |                                      **33건/월** |                **61건/년** |

**판정: 1.3×(30%) [제안].** 이유 둘 —

1. **1.1× 는 고정비를 못 넘는다.** 현행 유입은 `/download` 월 141명이고(#850), 그중 충전 전환이 100% 여도 151건에 못 미친다. 즉 **1.1× 에서 L2 는 구조적 적자**다.
2. **1.3× 라도 유저에게 정직하게 말할 수 있다.** ₩10,000 이 사 주는 것은 opus-5 기준 티켓 **약 1.1건**(#883 §3-C). 이건 "싸다"가 아니라 "**카드만 있으면 지금 당장 한 건**"이다 — §4-C 의 프레이밍이 그걸 감당한다.

**마크업 적용 규칙**: 입력·출력·캐시읽기·캐시쓰기 **네 종류 전부에 동일 배수**를 적용한다. 우리 원가 기준(캐시 승수 포함)에 균일 배수를 곱하는 것이라 **어떤 워크로드에서도 마진율이 일정**하고, 유저에게 설명하기도 쉽다("정가의 1.3배").

### 4-C. ★정직한 프레이밍 — 이건 매출이 아니라 CAC 다

#883 §3-A 가 못박은 사실을 이 스펙이 **제품 문구 수준까지** 승계한다: **도매가가 없다.** 우리가 사는 가격 = 유저가 살 수 있는 가격 = 정가. 그러므로 **마크업은 곧 "유저가 직접 사는 것보다 비싸다"** 는 뜻이다.

| 우리가 파는 것이 아닌 것 | 우리가 파는 것                                                     |
| ------------------------ | ------------------------------------------------------------------ |
| ✕ "시장보다 싼 토큰"     | ✅ **콘솔 가입·해외카드·USD 결제·키 관리 없이, 원화로, 지금 즉시** |
| ✕ 헤비유저용 SKU         | ✅ **구독을 만들기 전 첫 1\~3건**                                  |

그래서 세 가지가 **설계에 못박힌다**:

1. **회계상 CAC 로 잡는다.** 유저당 마진 ₩2,000\~4,000 은 사업이 아니다(#883 §3-D). 매출 KPI 를 걸지 않는다.
2. **헤비유저를 밀어낸다.** 누적 소비가 임계를 넘으면 **우리가 먼저** "구독이 더 쌉니다"라고 말한다(#886 §5-C 의 M3(b)). 매출을 스스로 깎는 것이 맞다 — 안 그러면 유저가 나중에 스스로 알아내고, 그때 우리는 "편의를 판 곳"이 아니라 "비싸게 판 곳"이 된다.
3. **성공지표 = 크레딧 유저의 구독 전환율.** 크레딧 매출액이 아니다.

### 5-A. 호스팅 — Functions 가 아니라 Cloud Run [코드]

→ **Cloud Run**(상시 1인스턴스 최소, HTTP/2, 스트리밍 릴레이). #883 §7 M1 과 같은 결론이며, 이 문서는 **왜 Functions 로는 안 되는지**를 코드 근거로 확정한다.

### 5-B. 요청 1건의 수명

```
claude CLI ──(ANTHROPIC_BASE_URL=api.marblo.app/anthropic, AUTH_TOKEN=단명토큰)──▶ 프록시
   1. 인증        토큰 검증 → {userId, spawnId, allowlist, exp}
   2. 검문        모델 allowlist · max_tokens 상한 · 동시성
   3. 예약(hold)  예상 최대비용 산정 → creditHolds 생성 (잔액 부족 → 402)
   4. 릴레이      요청 본문 **무변형** 업스트림 전송 · SSE 를 양방향 그대로 흘림
   5. 정산(settle) 최종 usage 로 debit 원장 1행 + hold 해제 (한 트랜잭션)
   6. 관측        요청ID·모델·usage·지연만 기록 (프롬프트/응답 본문 **저장 금지**)
```

**불변식 4개**

| #   | 불변식                                       | 왜                                                                         |
| --- | -------------------------------------------- | -------------------------------------------------------------------------- |
| P1  | **요청 본문을 변형하지 않는다**              | 캐시 프리픽스 보존(§4-A). 우리 메타는 헤더로만                             |
| P2  | **차감은 업스트림 응답의 `usage` 로만 한다** | `cost_logs`(15초 폴 델타·멱등키 없음)로 차감하면 오차가 곧 손실(#883 §5-D) |
| P3  | **응답 1건 = 원장 1행**                      | `debit_{proxyRequestId}` 결정적 id 로 재시도 멱등(§6-C)                    |
| P4  | **프롬프트·응답 본문을 저장하지 않는다**     | 유저 코드가 우리 로그로 들어오면 보안·프라이버시 표면이 통째로 바뀐다      |

### 5-C. ★토큰 수명 — "단명 토큰"과 장시간 세션의 모순

#883 §5-C 는 완화책으로 "스폰당 단명 토큰(TTL 분 단위)"을 적었다. **그대로는 안 된다** — 에이전트 세션은 수 시간 살아 있고, `claude` 프로세스의 env 는 **스폰 시점에 고정**된다. TTL 이 세션보다 짧으면 작업 중간에 401 이 나고, 그건 유저에게 "돈 냈는데 끊겼다"로 보인다.

**해소안**: 수명이 아니라 **결속(binding)과 상한**으로 막는다.

| 축            | 설계                                                                                                                 |
| ------------- | -------------------------------------------------------------------------------------------------------------------- |
| TTL           | **24h**(세션을 덮는 길이) — 짧은 TTL 대신 아래 결속으로 위험을 줄인다                                                |
| 결속          | 토큰 = `{userId, spawnId, modelAllowlist, maxTokensCap}` 서명. **다른 모델·다른 유저 불가**                          |
| **금전 상한** | ★토큰이 훔쳐져도 **쓸 수 있는 돈의 상한 = 그 유저의 잔액**이다. 이게 진짜 방어다(§9)                                 |
| 즉시 폐기     | 스폰 종료·유저 로그아웃·이상탐지 시 서버측 revoke(토큰 목록은 서버 진실)                                             |
| 저장          | 유저 머신에서는 기존 **safeStorage 벤더 시크릿 축** 재사용 [코드 `electron/vendor-secrets.ts`]                       |
| 노출 규율     | 앱 UI·로그·텔레메트리에 **키 이름과 boolean 만** — 값 금지(기존 게이트 규율 그대로 [코드 `harness-manager.ts:1335`]) |

**남는 노출(정직하게)**: 유저가 그 토큰으로 우리 엔드포인트를 직접 때릴 수 있다(#883 §5-C). **막지 못한다.** 다만 선불이라 **그건 자기 잔액을 자기가 쓰는 것**이고, 우리 손실이 아니다. 계약상 방어는 §10 의 약관 조항이다.

### 5-D. 모델 allowlist 와 alias 접힘 [코드]

`claude` CLI 는 `--model` 핀 밖의 내부 경로(대화 요약·제목 생성)에서 `opus`/`sonnet`/`haiku` 를 **자체 해석**한다. env-swap 벤더 행들이 `ANTHROPIC_DEFAULT_OPUS_MODEL`/`_SONNET_`/`_HAIKU_` 3키를 전부 접는 이유가 그것이다 [코드 `model-registry.ts:531,547-552`].

**크레딧 축에서 이게 왜 더 중요한가**: 그 내부 호출도 **유저 돈을 쓴다.** 접히지 않으면 (a)allowlist 밖 모델로 402 가 나서 세션이 깨지거나 (b)우리가 의도하지 않은 비싼 모델이 과금된다.

| 규율                                                                                |
| ----------------------------------------------------------------------------------- |
| L2 레지스트리 행도 `ANTHROPIC_DEFAULT_*` **3키를 전부** 접는다(기존 벤더 행과 동형) |
| 프록시는 allowlist 밖 모델을 **400 으로 명시 거절**한다(조용한 폴백 금지)           |
| 요약·제목용 저가 모델은 **allowlist 에 포함**시키되 원장에 `modelId` 로 구분 기록   |

### 5-E. 스트리밍·중단·실패의 정산

| 사건                           | 업스트림 과금         | 우리 처리                                                                                                                               |
| ------------------------------ | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 정상 완료                      | 있음                  | 최종 `usage` 로 debit + hold 해제                                                                                                       |
| **유저가 중간에 중단**(Ctrl-C) | **있음**(생성된 만큼) | SSE 로 받은 마지막 usage 델타까지 debit. **못 받았으면 hold 를 debit 으로 확정**(보수적으로 우리 손해 방향 아님)                        |
| 업스트림 5xx / 타임아웃        | 보통 없음             | debit 0, hold 해제. **재시도는 새 `proxyRequestId`**                                                                                    |
| 프록시가 죽음(정산 유실)       | 있음                  | ★**hold 만료 시 자동 정산**(TTL 15분 → hold 금액을 debit 으로 확정 후 감사 플래그). 유실을 유저에게 유리하게 두면 무료 토큰 구멍이 된다 |
| 잔액 초과 오버런               | 있음                  | hold 상한(=max_tokens 기준 최악치)까지만 가능. 초과분은 **우리가 흡수**하고 다음 요청부터 402                                           |

★**402 의 UX 계약**: `/v1/messages` 가 402 를 내면 `claude` CLI 는 에러로 끝난다. 그 봉투를 앱이 해석해 **M3(a) 소진 모달**로 바꿔야 한다(§8). 조용한 실패는 금지다.

### 5-F. 관측 — 무엇을 남기고 무엇을 안 남기나

| `proxyRequestId` · userId · modelId · usage 4종 · 지연 · 상태코드 | **프롬프트·응답 본문**                 |

| `createdAt` · `expiresAt`                          | TTL **15분**[제안] — 스윕이 이걸 본다 |

| --------- | --------------------------- |

| **debit** | `debit_{proxyRequestId}`    |

### 6-D. ★예약(hold) → 정산(settle) 상태기계 — #886 에 없던 조각

**왜 필요한가**: 스트리밍이라 **usage 를 사후에만 안다.** 선차감(pre-debit)은 금액을 모르고, 후차감(post-debit)만 하면 잔액 0 인 유저가 $60 짜리 요청을 시작할 수 있다.

```
요청 도착
  │  reserved = est_input_tokens × rate_in
  │           + max_tokens        × rate_out
  │           (둘 다 마크업 적용)
  ├─ reserved > (balance − openHolds) ────▶ 402 + M3(a)
  ▼
creditHolds{status:open}  ──── 업스트림 릴레이 ────┐
  │                                               │
  ├─ 정상완료/중단  ──▶ [트랜잭션] debit 원장 create + account decrement + hold=settled
  ├─ 업스트림 실패  ──▶ hold=released (차감 0)
  └─ TTL 15분 경과  ──▶ 스윕: reserved 를 debit 으로 확정, hold=expired, 감사 플래그
```

| 결정               | 값 [제안]                                                                                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `est_input_tokens` | 요청 본문 바이트/3.5(보수적 과대추정). ★Anthropic 패스스루면 `/v1/messages/count_tokens` 로 **정확히** 낼 수 있다 — T-A 의 부수 이점 |
| `max_tokens` 상한  | 서버가 강제(요청값이 크면 400). 상한이 곧 hold 상한이고, 오버런 상한이다                                                             |
| 동시 hold 상한     | 유저당 **4건** — 오버런 노출 = 4 × 1홀드                                                                                             |
| 최소 가용잔액      | 1홀드 미만이면 요청 자체를 402. **잔액 꼬리는 못 쓴다** → UI 가 "충전/환불" 로 안내(§8)                                              |
| 오버런 처리        | hold 초과 실사용분은 **우리가 흡수**(유저 잔액 음수 금지). 상한이 있으므로 손실이 유한                                               |

**트랜잭션 불변식**: 원장 create 와 계정 decrement 와 hold 상태전이는 **한 트랜잭션**. 원장 행이 이미 있으면(재시도) decrement 를 **건너뛴다**.

### 6-E. ★Firestore rules — #886 초안의 자세를 정정한다

#886 §7-C 는 `creditLedger` 에 `create: if false; update: if false;` 를 제안했다. 두 가지를 바로잡는다.

**(1) 쓰는 주체가 Admin SDK 면 rules 는 write 를 판정하지 않는다.**
프록시·Functions 는 Admin SDK 로 쓰고, Admin SDK 는 **rules 를 우회**한다. 즉 위 두 줄은 "클라이언트가 못 쓴다"는 선언일 뿐이고, **멱등성·불변성의 실제 집행자는 rules 가 아니라 §6-D 의 트랜잭션**이다. 이걸 혼동하면 #886 §12 가 걱정한 #406 실패모드(메인프로세스 인증 경로가 렌더러와 다름)를 그대로 밟는다.

**(2) `update: if false` 는 이 레포에서 이미 한 번 사고를 냈다** [코드 `firestore.rules:325-338`]:

> "…같은 id 로의 재시도는 Firestore 가 update 로 판정한다 → `update: if false` 에 걸려 permission-denied → 스풀이 그 레코드에서 **영원히 고착**한다(실측: 1s/2s/4s/9s/24s 백오프마다 PERMISSION_DENIED 반복)."

`audit_logs` 는 그래서 **"동일 내용 재쓰기만 허용"**(`request.resource.data == resource.data`)으로 바뀌었다.

**크레딧 원장의 판정**: 클라이언트가 쓰지 않으므로 그 고착은 **일어나지 않는다.** 그러나 **그 이유를 rules 주석에 남긴다** — 나중에 누군가 "렌더러에서도 원장을 쓰자"고 하는 순간 같은 함정이 살아나기 때문이다.

```
match /creditLedger/{entryId} {
  allow read:   if isAuthenticated() && resource.data.userId == request.auth.uid;
  allow create, update, delete: if false;
  // ★쓰기 주체는 프록시/Functions(Admin SDK)뿐 — Admin SDK 는 이 규칙을 우회한다.
  //   즉 불변성·멱등성의 집행자는 이 줄이 아니라 서버 트랜잭션이다(설계 §6-D).
  //   ★만약 훗날 클라이언트 쓰기를 허용하게 되면, audit_logs(:325) 의 교훈대로
  //   "동일 내용 재쓰기 허용"으로 열어야 한다 — 통짜 false 는 재시도 고착을 만든다.
}
match /creditAccounts/{userId} {
  allow read:  if isAuthenticated() && isOwner(userId);
  allow write: if false;   // subscriptions/{userId}(:541) 와 같은 자세
}
match /creditHolds/{holdId} {
  allow read, write: if false;   // 서버 내부 상태 — 클라이언트는 잔액만 본다
}
```

**배포 규율**: `npm run test:rules`(에뮬레이터, Java21 필요 — 메모 `test_rules_emulator_runbook_this_mac`)로 **폼 실페이로드 검증**까지 한 뒤 배포한다. 룰 조이기로 이 프로젝트는 이미 두 번 라이브가 죽었다([`L2-ledger-read-scope-live-verification.md`](./L2-ledger-read-scope-live-verification.md) 서두).

## 9. ★abuse — 선불이라 위협모델이 다르다

#885 §8 은 **무료** 티어를 전제로 C1\~C8 을 세웠고, 그중 최우선이 **C6 전역 예산 킬스위치**였다("마케팅 성공이 사고가 되는 것"). **L2 에서는 그 공포가 대부분 사라진다.**

| 무료 티어(#885)의 공포         | L2 에서                                               |
| ------------------------------ | ----------------------------------------------------- |
| 토큰 추출 → 무한 무료 LLM API  | **손실 상한 = 그 유저의 잔액.** 자기 돈을 자기가 쓴다 |
| 익명 계정 재발급으로 한도 우회 | 재발급해도 **잔액이 0** 이다                          |
| 성공이 곧 청구서               | 성공이 곧 **선입금**이다                              |

**그래서 L2 의 진짜 위협은 셋으로 좁혀진다.**

| #   | 위협                                                                        | 심각도   | 방어                                                                                                                              |
| --- | --------------------------------------------------------------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------- |
| A1  | ★**Chargeback 사기** — 도난카드로 충전 → 토큰 소진 → 지급거절               | **높음** | 신규 계정 **첫 충전 한도**(₩10,000) · 소진 속도 이상탐지 · 동일카드 다계정 · **PG 위험관리 룰**을 켜 둘 것. 토큰은 되돌릴 수 없다 |
| A2  | **우리 벤더 계정을 통한 금지 콘텐츠 생성** — 계정 정지 위험(돈 아니라 계약) | 중간     | 약관에 벤더 AUP **전가**(xAI 명시 의무) · 업스트림 정책 위반 응답을 그대로 유저에게 전달 · 반복 위반 계정 차단                    |
| A3  | **토큰 유출로 남의 잔액 소모**                                              | 중간     | §5-C 결속 + revoke + 이상탐지. 피해자 보상 경로(`kind:"adjust"`)를 원장에 내장                                                    |
| A4  | 계량 오차(우리 쪽 버그)                                                     | **높음** | §5 P2·P3 + `hold_expired` 비율 감시 + **일 1회 원장↔업스트림 청구액 대조**(§11 T-8)                                               |

★**그래도 남기는 전역 킬스위치**: 금전 손실 때문이 아니라 **우리 벤더 계정 보호**를 위해 남긴다(전역 RPS·일일 상한). 규모가 다르다 — #885 의 C6 은 예산 방어, 여기서는 계정 방어다.

## 13. 한계 · 정직성

- **§4-A 의 6.4배는 [추정]이다.** #885 §3 의 **평균** 토큰 믹스에 Anthropic 승수를 곱한 값이고, 같은 문서의 **중앙값 실측**($5.25)보다 절대값이 높다. **배수는 믹스 비율에서만 나오므로 유지**되지만, 실제 값은 G-P1 이 처음 측정한다.
- **캐시 승수(0.1×/1.25×)는 Anthropic 기준**이다. T-B(xAI 등)는 캐시 정책이 다르고, 이 문서는 **확인하지 못했다** — 벤더가 바뀌면 §4 산술을 다시 해야 한다.
- **품질 판정(MiniMax·Kimi 탈락)은 측정이 아니라 미검증 리스크 회피다**(§3-C 각주). 우리는 그 모델들로 티켓 완주율을 재 본 적이 없다.
- **codex·grok 하네스의 base-url 우회 가능성을 "불가"라고 말하지 않았다.** 확인한 것은 **우리 레포에 그 배선이 없다**는 것뿐이다(grep 0건). 벤더 CLI 자체의 설정 경로는 조사하지 않았다.
- **Cloud Functions gen1 의 스트리밍 제약은 플랫폼 제약**으로 서술했다. 버전(`firebase-functions@^5`, `functions.https.onRequest`)은 [코드]로 확인했으나, 이 제약 자체를 라이브로 재현해 보지는 않았다 — PoC 가 확인한다.
- **원장 스키마·rules 는 설계다.** 구현·`npm run test:rules` 검증을 거치지 않았다. 특히 Admin SDK 쓰기 경로는 배포 전 **라이브 실측**이 필요하다(#406 교훈).
- **hold TTL 15분·동시 4건·첫충전 ₩10,000 은 [제안]** 이고 도출값이 아니다.
- **세무 항목은 전부 [확인필요]** 다. 법 정의 대조 수준이며 세무 자문이 아니다.
- **마크업 30%·환율 ₩1,400/$·PG 3.74% 는 #883 §3-C 의 가정을 승계**한 것이고, 실제 PG 요율은 가맹점 계약에 따라 다르다.
- **ToS 판정은 #883 이 정본이며 이 문서가 재검증하지 않았다.** #883 §10 의 한계(법률 자문 아님, D.4 를 좁게 읽음)가 그대로 승계된다.
- 날조 없음. `[코드]` 인용은 전부 파일·행으로 확인 가능하고, 원가·ToS 수치는 §14 의 선행문서가 1차 출처를 들고 있다.
