## 1. ★프레이밍 교정 — 커서가 실제로 소유한 것

### 1-A. "우리 모델로 오케를 돌린다"가 왜 최악의 첫 베팅인가

오케스트레이터는 **분해·라우팅·머지판단**이다. 이 셋의 공통점:

- **정답이 늦게 나온다** — 분해가 틀렸다는 걸 알려면 하류 에이전트 3기가 며칠을 태우고 나서다
- **실패가 조용하다** — 에러가 아니라 *그럴듯하게 틀린 계획*으로 나온다
- **정답 판정이 비싸다** — 사람이 읽어야 안다

여기에 우리 실측이 겹친다: **프론티어급인 gpt·grok 도 복잡 in-repo 코딩에서 무산출**이었다(메모 `spawn_model_pref_codex_grok_save_claude`). #885 §7-B 가 같은 결론을 별도 근거로 냈다. 우리가 처음 훈련하는 모델을 여기에 놓는 것은 **가장 어려운 자리에 가장 약한 카드를 놓는 것**이다.

### 1-B. 커서의 구조 — 프론티어 추론 + 좁은 자체모델

커서는 자체모델을 만들지만, **추론의 몸통은 Claude/GPT 에 맡긴다.** 자체모델이 소유한 자리는 좁다 — **fast-apply**(모델이 낸 편집 의도를 파일에 실제로 적용), **tab autocomplete**(다음 편집 예측). [출처: 2차 — 커서 공개 블로그·발표 정리, §10 정직성 참조]

그 자리가 왜 골라졌는지를 보면 **선택 규칙**이 나온다. 자체모델이 이기는 자리는 아래 셋이 **동시에** 성립하는 곳이다:

| 조건                                   | 왜 필요한가                                           | fast-apply 가 만족하는 이유                            |
| -------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------ |
| ① **입출력이 구조적으로 좁다**         | 작은 모델이 열린 문제를 못 푼다                       | 입력=원본+편집안, 출력=편집된 파일. 창의성이 필요 없다 |
| ② **정답 판정이 싸다**                 | 라벨을 자동으로 만들 수 있어야 데이터가 쌓인다        | 적용 결과가 파싱되나·테스트가 도나 — 기계가 판정       |
| ③ **호출량이 커서 단가·지연이 아프다** | 안 아프면 소유할 이유가 없다(그냥 프론티어 쓰면 된다) | 편집 1회마다 호출 — 프론티어로 하면 느리고 비싸다      |

**★이 로드맵의 유일한 선택 규칙이 이것이다.** ①②③ 이 겹치지 않는 자리는 후보가 아니다. 오케 분해는 ①②③ 전부 실패한다.

### 1-C. 그래서 이 로드맵의 목표

> **오케를 대체하는 것이 아니라, 오케 주변의 좁은 결정 하나를 소유하는 것.**
> 그리고 그 하나가 검증되면 **태스크 단위로만** 표면을 넓히는 것.

프론티어 추론은 **전 구간에서 계속 산다.** 이건 타협이 아니라 커서가 이미 검증한 구조다.

| **G10** | `errorCategory` 세분화(MODEL_FAIL/AUTH/TOOL/…)   | ★"막힘(BLOCKED 33)"과 "모델 실패(FAILED 6)"가 뭉쳐 있다 — 지금 음성 라벨의 대부분은 모델 잘못이 아니다 |
| **G4**  | `cost.taskId` 26.9% → 폴러가 항상 바인딩         | 비용은 승격 판정(§5)의 두 축 중 하나다                                                                 |
| **G13** | explicit 경로에서도 후보 점수 스냅샷 강제        | §3-D — 이게 없으면 라우팅 학습셋이 원리적으로 못 쓴다                                                  |
| **G1**  | `agent:spawned.taskId` 0%                        | 스폰 단위 조인의 최단 경로(현재는 dispatch 우회 필요)                                                  |

**P0-3. 데이터 계약 문서화** — "후일 파인튜닝용 스키마"가 일반 텔레메트리와 다른 **4가지 요구**:

1. **입력 재구성 가능성** — 결정 시점의 **후보집합과 피처**가 남아야 한다. 결과만 남으면 "왜 그걸 골랐나"를 못 배운다(`perModelScores` 빈 배열이 정확히 이 실패다)
2. **출력이 이산·검증 가능** — 선택된 `model@effort`, 분해된 티켓 N개처럼 **기계가 채점 가능한 형태**
3. **늦게 붙는 라벨의 조인 가능성** — 머지는 결정보다 며칠 뒤에 온다. `taskId` 안정키가 유일한 다리(메모 `cost_axis_userid_spaces_and_reread_dupes`)
4. **네거티브 존재** — 성공만 있는 데이터로는 분류기가 "항상 성공"을 예측해 이겨 버린다

동시에 **금지선**도 문서화한다: 원장 `params` 원문 금지(§2), 프롬프트 본문 금지(해시+길이만), 스크럽은 **denylist** 라 필드 추가 시 스크럽 규칙 동반 검토 필수(`lib/telemetry/scrub.ts`).

### 3-D. ★Phase 0 의 진짜 위험 — explicit 우회 97.8%

2026-07-18 실측: 디스패치의 **97.8%가 유저/오케가 모델을 명시**해 스코어링이 통째로 우회됐다(`decisionReason: "Explicit model … scoring bypassed"`). **이 데이터로 학습하면 라우터가 아니라 "사람이 무엇을 고르는지 흉내내는 모델"이 나온다.** 자동선택의 목적이 사람보다 나은 배정이라면, 사람이 고른 경우만 있는 데이터는 **원리적으로** 그 목적에 못 쓴다.

완화 둘 — (a) G13 으로 explicit 경로에서도 **후보 점수를 스냅샷**해 최소한 비교축을 남긴다, (b) `model-autoselect.ts` 의 **ε-greedy·tie-band 회전이 만드는 non-explicit 케이스**를 별도 집계한다. (b)는 이미 코드에 있다 — 세지 않고 있을 뿐이다.

### 3-E. ★그리고 진짜 병목: 활성 유저

라우팅 SLM 문서 §7.4 의 계산: 유효 라벨은 **활성 유저 수에 정비례**한다(활성 10명 → 룰PoC 12일 / 30명 → 4일). 반대로 **결과행 유저가 2명이면 영원히 안 모인다.** 그리고 우리 실측은 외부 실사용 ≈0 이다(메모 `admin_exclude_johnkim_external_zero_value_2026_07`).

> **함의**: 이 로드맵의 속도를 정하는 것은 ML 기술이 아니라 **활성화·배포**다. Phase 0 은 그걸 기다리는 동안 **공짜로 할 수 있는 유일한 준비**다.

왜 (b)인가 —

- **baseline 이 공짜로 이미 있다.** `model-autoselect.ts` 는 손튜닝 가중합이지만 **근거 기반**이고(#654\~656), 각 성분의 breakdown 을 남긴다. **여기를 못 이기면 학습할 이유 자체가 없다** — 이게 세상에서 가장 싼 형태의 "실패 조기 확인"이다
- **shadow 인프라가 사실상 있다.** `dispatch:decision` 이 `perModelScores`·`agentScore` 를 남기므로 **학습층 예측 vs 현행 점수**를 사후 비교할 수 있다
- **얹을 자리와 안전 패턴이 이미 코드에 있다.** `routing-graph.graphBias` 가 정확히 그 모양이다 — **가법 성분 ±20, 콜드=0, 클램프, 즉시 폴백**. 학습층이 죽어도 기존 점수로 안전하게 떨어진다
- **정직한 한계**: 이건 LLM 파인튜닝이 아니라 그냥 분류기다. 비용 $0\~50. **파인튜닝 근육은 안 길러진다.**

그래서 **1.5번 = (c) PR/커밋 요약**을 나란히 둔다 —

- 진짜 **seq2seq LoRA** 를 한 번 완주해 보는 자리(데이터 준비→학습→서빙→평가 전체 사이클)
- **distillation 이 가장 자연스러운 자리**: 프론티어를 우리 워크로드에서 **이미 돌리고 있으므로**, 교사 출력은 별도 비용 없이 나오는 **부산물**이다(단 Phase 0 에서 저장 계약을 미리 잡아야 한다 — 안 담으면 §3-A 대로 영원히 없다)
- 실패해도 **문구가 어색할 뿐** — 첫 실전 모델을 놓기에 가장 안전한 자리

(a) 분해가 마지막인 이유는 #885 §7-C 와 **정확히 같다**: 잘못된 분해는 하류 전부를 낭비시키고, 실패가 조용하다.

### 5-A. ★P2-0 — 평가 하네스가 첫 관문이다

> **측정 못 하면 개선 못 한다.** 계측 티켓(`9dXgBdk`)이 남긴 교훈이 그대로 적용된다 — **하네스 없이 학습 결과를 켜는 것은 금지**한다.

| 층           | 무엇                                                                      | 한계(정직하게)                                                                                               |
| ------------ | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **오프라인** | 홀드아웃 리플레이 — 과거 결정을 재현해 실제 outcome 과 대조               | ★**counterfactual 한계**: 우리가 **안 고른** 모델의 결과는 영원히 모른다. 라우팅 오프라인 평가의 원리적 상한 |

### 5-C. 승격 기준 — 세 조건 동시

```
승격  ⟺  품질 유지(회귀 없음)  AND  (더 싸다  OR  더 빠르다)  AND  shadow 승률 확인
```

- **품질이 동률이어도 싸거나 빠르면 승격**한다 — 그게 narrow-task 오너십의 존재 이유다
- **품질이 조금이라도 나쁘면 승격 안 한다** — 아무리 싸도. 우리 제품의 실패모드는 "싸게 틀리는 것"이다
- **롤백은 상시 1클릭** — `routing-graph` 콜드스타트 프라이어 제거 패턴(`removeColdStartPriors`)을 그대로 쓴다

### 5-D. Phase 2 의 고유 리스크 — 자기강화 루프

학습층이 **자기 선택이 만든 데이터로** 학습하면 확증편향이 고착된다. `model-autoselect.ts` 주석이 이미 이 문제를 명시하고 ε-greedy·UCB1 로 방어한다 — **학습층을 얹을 때 이 탐색 성분을 끄면 안 된다.** 오히려 학습층 도입 직후엔 ε 을 **키워야** 비교 데이터가 계속 생긴다.

| **사람이 실제로 수용했나**(merge_history) | ✕                                |
| 태스크 단위 실비용(모델 교차)             | ✕                                |

**★핵심**: 벤더는 **턴**은 본다. 하지만 **"그래서 사람이 머지했나"** 는 못 본다. 그 라벨은 우리 제품이 존재하는 이유(오케·감사·머지)에서 **부산물로** 나온다 — 데이터를 위해 별도 잡을 돌리지 않는다는 뜻이고, `merge_history`/`task:merged` 단일소스 이중사용이 이미 그 구조다.

### 7-B. Distillation — 교사가 이미 돌고 있다

우리는 **프론티어를 우리 워크로드에서 매일 돌린다.** 그래서 "프론티어=교사 / 소형=학생" 구조에서 **교사 추론 비용이 이미 지불돼 있다.** 남은 것은 **그 출력을 학습 가능한 형태로 담아 두는 계약**(Phase 0)뿐이다. 이게 이 로드맵에서 가장 비대칭적으로 싼 지점이다.

### 7-C. ★정직하게 — 지금 그 해자는 1인분이다

메모 `admin_exclude_johnkim_external_zero_value_2026_07` 대로 **외부 실사용은 ≈0** 이고, `task_outcomes` 결과행 유저는 한 자릿수다. **데이터 해자는 활성 유저 수에 비례한다.**

> **그래서 "데이터가 우리 해자"는 현재형이 아니라 조건부 미래형이다.** 이 문장을 대외 서사로 쓸 때 정확히 이 조건을 붙여야 한다.

## 10. 한계 · 정직성

- **커서의 내부 아키텍처는 2차 출처**다(공개 블로그·발표 정리). fast-apply·tab autocomplete 를 자체모델로 소유한다는 것은 널리 보고된 사실이지만, 우리는 그들의 학습 파이프라인을 검증할 수 없다. **§1 의 가치는 "커서가 이렇게 한다"보다 ①②③ 선택 규칙 자체**에 있다 — 그 규칙은 커서와 무관하게 우리 실측(#885 §7-B, gpt·grok 무산출)으로도 지지된다.
- **수치는 스냅샷이다.** 조인율 58.4%·음성 4.4%·`cost.taskId` 26.9% 는 **2026-08-08**, explicit 97.8%·유효라벨 정의는 **2026-07-18** 실측이다. explicit 비율은 **2026-08-08 에 재측정되지 않았다** — Phase 0 첫 작업(P0-1 뷰)이 이걸 상시 관측 가능하게 만든다.
- **§4-C 비용 구간은 [추정]** 이다. 서버리스 FT 실단가를 벤더 페이지에서 확정하지 않았다(#885 는 **추론** 단가만 확정했다). Phase 1 착수 시 재확인이 선행이다.
- **우리는 파인튜닝을 한 번도 해본 적이 없다.** 이 로드맵의 가장 큰 미검증 변수는 모델이 아니라 **조직 역량**이다(R9).
- **§4-B 의 임계치는 인용이지 재도출이 아니다.** 300/1,000/15%/80% 는 라우팅 SLM 문서 §7.2 의 값이고, 그 문서 스스로 "실무 하한"이라고 적었다. 사장님/오케가 조정할 값이다.
- **원가·게이트웨이·GPU 판정은 이 문서가 하지 않았다** — #885 가 정본이다. 여기서 재계산하면 두 문서가 갈라진다.
- **이 문서는 Phase 0 조차 실행하지 않았다.** 로드맵이고, 다음 단계는 §11 의 티켓 분해다.
