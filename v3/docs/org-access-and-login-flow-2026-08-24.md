## 0. 한 문단 요약

사장님 문장은 둘로 갈린다 — **"관리자가 보고"** 와 **"일부 팀장들한테 팀 내용만"**. 앞엣것은
쉽고 뒤엣것이 어렵다. 뒤엣것의 어려움은 화면에 있지 않다. **팀장에게 자기 팀만 보여주는 화면
어딘가에 조직 전체 합계가 하나라도 있으면, 뺄셈으로 남의 팀이 드러난다.** 팀이 둘이면 완전
노출이다. 그래서 이 문서의 척추는 화면 구성이 아니라 문장 하나다:

> **총계는 그 총계를 이루는 항목을 전부 볼 수 있는 사람에게만 보인다.**
> 부분만 보는 사람에게 총계를 주는 순간, 그가 못 보게 한 부분이 뺄셈으로 나온다.

그리고 이건 우리가 처음 만나는 문제가 아니다. **한 층 아래에서 이미 판정했다** — `teamUsage.ts`
머리 주석 4번이 프로젝트 축에서 똑같은 결론을 냈다. 이 문서는 새 규칙을 발명하지 않고 **그
규칙을 한 층 위로 올린다.**

### 0.1 이 문서가 답하는 것

1. **"팀" 이 무엇인가** (§1) — 팀 = 프로젝트다. 새 개념을 만들지 않는다
2. **역할 축 둘의 합성 규칙** (§2) — 합집합. 교집합 금지. 넓히는 방향으로만
3. **집계 뺄셈** (§3) — 총계·순위·평균·share 를 누구에게 주나
4. **`0` 과 `권한 없음`** (§4) — 부재의 여섯 가지 뜻, 그리고 두 가지 거절 모양
5. **로그인 상태 전수** (§5) — 15개 상태, 각각의 착지점
6. **룰 위에 얹는 법** (§6) — 화면에서 가리는 건 권한이 아니다

### 0.2 이 문서가 답하지 않는 것

| 무엇 | 어디로 |
| --- | --- |
| 색·레이아웃·차트 라이브러리 | #1206 |
| 조직명·도메인·멤버십 생성 경로 | #1204 |
| 좌석 과금·인보이스 | #1202 §4.3-2 (별건 티켓) |
| 비용 계산식·BQ 뷰 | #1202 §5 (이미 정본이 있다) |

### 0.3 재론 금지 (#1204 확정)

자동 가입 없음 · 도메인은 제안만 · 개인 = `personal_<uid>` 조직 · 원장엔 `orgId` 를 박지 않고
밖의 결합표(`OrgProjectBinding`)로 시점 조회.

★그중 하나가 이 문서의 §5 를 통째로 단순하게 만든다: **로그인 후 "조직 없음" 상태는 존재하지
않는다.** 개인 조직이 항상 있다. 그런 화면을 설계하지 않는다.

## 1. ★먼저 답할 것 — "팀" 이 무엇인가

티켓의 지적이 옳다. 이게 안 정해지면 나머지가 전부 모호하다. 그리고 지시대로 **새 개념을 즐기지
않는다** — 먼저 팀 = 프로젝트로 둘 수 있는지 검토한다.

### 1.1 판정: **팀 = 프로젝트다.** 새 엔티티를 만들지 않는다

근거는 취향이 아니라 census 다. 오늘 코드에서 **경계 역할을 하는 축이 전부 `projectId` 하나**다:

| 경계 | 무엇으로 그어져 있나 | 근거 |
| --- | --- | --- |
| **행 격리(보안)** | `projectId` | `firestore.rules:27` `isProjectMember(projectId)` — 1,081줄이 이걸 강제 |
| **역할** | `projectId` | `memberRoles/{projectId}_{uid}` (`firestore.rules:762` docId 결속) |
| **초대** | `projectId` | `invitations/{projectId}_{email}` (`firestore.rules:133`) |
| **비용** | `projectId` | `cost_logs.projectId` → `buildTeamUsageDailyQuery` |
| **감사 원장** | `projectId` | `canReadLedgerDoc()` (`firestore.rules:89`) · `projectAuditLog` |
| **사람 그룹** | `projectId` | `projects.members[]` |

즉 **계정·비용·감사·역할·초대의 경계가 이미 전부 프로젝트다.** 여기에 "팀" 이라는 일곱 번째
축을 넣으면, 그 축은 위 여섯 중 **아무것도 소유하지 않은 채** 여섯 개 전부와 매핑을 유지해야
한다. 그 매핑이 틀리는 날이 유출이 나는 날이다.

### 1.2 그래서 "팀장" 은 무엇인가

> **팀장 = 그 프로젝트의 `owner` 또는 `admin`.**

이것도 발명이 아니다. 이미 세 곳에서 같은 판정이다:

```
firestore.rules:55   isAdminOrOwner(projectId)
teamUsage.ts:738     canSeeTeamBreakdown(role)   // 주석: "firestore.rules 의 isAdminOrOwner 와 같은 판정"
teamAudit.ts:76      scopeForRole(role) === "team"
```

세 곳이 이미 "팀 전체를 볼 수 있는 사람" 을 같은 값으로 정의해 두었다. 조직 축이 할 일은 그
정의를 바꾸는 것이 아니라 **그 위에 조직을 얹는 것**이다.

### 1.3 "팀이 프로젝트를 여럿 가진다" — 이미 배선돼 있다

가장 흔한 반론이다. "우리 팀은 리포가 3개인데요."

**그 경우가 이미 동작한다.** 팀장이 3개 프로젝트의 `owner`/`admin` 이면, 그의 팀 = 그 3개의
합집합이고, 서버가 그 집합을 **uid 에서 도출**한다:

```
marblo-web/src/app/[locale]/team/page.tsx (파일 머리 주석)
  "★프로젝트 선택을 화면이 하지 않는다. projectId 를 안 보내면 서버가
    context.auth.uid 로 도출한 자기 권한 집합 전체를 스코프로 잡는다"

v3/functions/src/teamUsage.ts:718  intersectProjectScope(requested, allowed)
  → 클라가 고른 값은 허용 집합과의 교집합으로만 쓰인다
v3/functions/src/teamUsage.ts:710  capProjectScope(ids, 25)
  → 상한을 넘으면 조용히 자르지 않고 잘린 개수를 돌려준다
```

즉 **"프로젝트 묶음으로서의 팀" 은 이미 일급 개념이다.** 이름이 없을 뿐이고, 이름은 필요 없다 —
그 묶음은 저장되는 값이 아니라 **uid 에서 매번 도출되는 값**이라 저장하면 오히려 낡는다(사람이
프로젝트에서 빠졌는데 팀 문서에는 남아 있는 상태가 생긴다).

★이건 팀=프로젝트 안의 부수적 이점이 아니라 **핵심 논거**다. 별도 팀 엔티티를 만들면 그
엔티티는 반드시 `projects.members` 와 어긋나고, 어긋나는 순간 둘 중 무엇이 권한의 정본인지
모호해진다. 도출값은 어긋날 수 없다.

### 1.4 ★그럼 언제 깨지나 — 안 되는 경우 전수

정직하게 적는다. 팀=프로젝트가 **못 하는 것**이 셋 있다.

| # | 경우 | 팀=프로젝트가 못 하는 것 | 판정 |
| --- | --- | --- | --- |
| 1 | **한 프로젝트를 두 팀이 나눠 쓴다** (모노리포 하나에 프론트팀·백엔드팀) | 프로젝트 안에서 사람을 갈라 볼 수 없다 | ★**지원하지 않는다.** 프로젝트를 쪼갠다 |
| 2 | **팀은 그대로인데 프로젝트가 바뀐다** (분기마다 리포가 바뀜) | "팀의 작년 지출" 이 프로젝트 집합 변경으로 끊긴다 | 조직 축이 답한다(§1.6) |
| 3 | **사람 묶음 자체가 산출물** (인사·평가·좌석 배정) | 프로젝트는 사람 묶음이 아니다 | ★**우리가 팔 것이 아니다**(§3.9) |

**1번을 지원하지 않는 이유**가 이 절의 핵심이다. 지원하려면 `cost_logs` 에 팀 컬럼이 필요하고,
`memberRoles` 가 프로젝트 하위로 한 단계 더 들어가야 하고, `firestore.rules` 의 12개 컬렉션
read 게이트가 전부 두 단계 판정이 된다(#1202 §4.2 가 센 그 12개다). **그 비용은 프로젝트를
쪼개는 비용보다 두 자릿수 크다.** 프로젝트를 쪼개면 경계 여섯 개가 전부 따라온다 — 공짜로.

★그리고 1번을 지원하는 순간 **감사 경계가 프로젝트보다 잘게 쪼개진다.** 우리가 파는 것은
"이 프로젝트에 무슨 일이 있었나" 의 무결한 기록인데, 그 안에서 일부만 보이는 뷰를 만들면
"전부 보여준다" 는 주장이 성립하지 않는다. 이건 성능 문제가 아니라 **제품 주장의 문제**다.

**2번**은 조직 축이 이미 답한다. `OrgProjectBinding` 이 프로젝트를 조직에 시점으로 붙이므로
(#1204 §1.1), 프로젝트가 바뀌어도 조직 수준의 연속성은 유지된다. 팀 수준 연속성이 따로 필요한
고객이 나타나면 그때 판단한다 — 지금은 그런 고객이 없다.

### 1.5 그래서 3층이다 — 그리고 3층으로 끝이다

```
조직 (organizations)              ← 청구·정체성·감사 반출의 경계.  #1204 가 정의했다
  └ 프로젝트 (= 팀)               ← 행 격리·역할·비용·원장의 경계.  오늘 이미 있다
      └ 사람 (projects.members)   ← 개인.                          오늘 이미 있다
```

**중간에 층을 넣지 않는다.** 사장님 문장의 "팀장" 은 이 그림에서 가운데 층의 `owner`/`admin` 이고,
"관리자" 는 맨 위 층의 `org_owner`/`org_admin` 이다. 두 낱말이 이미 두 층에 정확히 대응한다.

### 1.6 용어 고정 — 이 문서 이후로 이렇게 쓴다

| 사장님 낱말 | 이 문서의 낱말 | 코드의 값 |
| --- | --- | --- |
| 관리자 | **조직 관리자** | `org_owner` / `org_admin` (`OrgRole`) |
| 팀장 | **프로젝트 관리자** | `owner` / `admin` (`ProjectRole`) |
| 팀 | **프로젝트** | `projects/{projectId}` |
| 팀 내용 | **그 프로젝트 스코프의 집계·원장** | `scope: "team"` |
| 내 것 | **본인 스코프** | `scope: "self"` |

★새 낱말을 만들지 않는다. 화면 문구도 이 표를 따른다 — `teamUsage.ts` 가 이미 확립한 어휘
(`'사용량 환산 비용(추정)'` 등)를 그대로 쓴다는 #1202 §5.4-1 의 규율과 같다.

## 2. 역할 축 둘 — 합성 규칙

### 2.1 ★먼저: 역할 어휘가 이미 넷이다 (드리프트 census)

조직 역할을 얹기 전에 **오늘의 상태를 정직하게 세야 한다.** 세 보면 이렇다:

| # | 어휘 | 값 | 어디 |
| --- | --- | --- | --- |
| 1 | `ProjectRole` / `InvitationRole` | `owner` `admin` `member` `viewer` | `githubApp.ts` · `src/types/invitation.ts` ← **정본** |
| 2 | `TeamRole` | `owner` `admin` `member` `viewer` | `teamUsage.ts:735` |
| 3 | `TeamProjectRole` | `owner` `admin` `member` **`none`** | `teamAudit.ts:64` — ★`viewer` 가 없다 |
| 4 | 룰의 문자열 판정 | `'admin'` 비교 + 문서 없으면 `'member'` | `firestore.rules:49,55` |
| 5 | `OrgRole` (신규, 미배선) | `org_owner` `org_admin` `org_member` | `src/types/organization.ts` |

**3번이 이미 드리프트다.** `index.ts:14224 resolveTeamProjectRole` 은 `viewer` 를 만나면
`member` 로 접는다(멤버 배열에 있으면 `member`). 결과적으로 viewer 가 자기 감사 피드를 본다 —
오늘은 이게 맞는 동작이지만(본인 기록 열람은 정보주체 권리), **아무도 그렇게 결정한 적이
없다.** 어휘가 갈려서 생긴 값이다.

★이 census 가 §6 의 결론을 미리 정한다: **판정이 다섯 곳에 복제된 상태에서 여섯 번째 축을
얹으면 드리프트가 곱해진다.** 조직 역할을 넣기 전에 판정을 하나로 모아야 한다.

### 2.2 두 축은 **다른 것을 준다** (#1204 재확인, 재론 아님)

```
v3/src/types/organization.ts (OrgRole 주석)
  "조직 역할이 프로젝트 역할을 자동으로 주지 않는다 — org admin 이라고 모든
   프로젝트의 내용을 보는 것이 아니라, 조직 설정과 청구를 볼 뿐이다."
```

이건 #1202 §4.3-3 이 그은 선을 조직 축에서 유지한 것이다:

> *"공유 산출물에 일어난 사건은 보여준다. 그 사람이 무슨 명령을 쳤는지는 안 보여준다"*
> — 이 선을 파는 순간 우리는 감시 도구가 되고, 그건 trust 통화를 태우는 일이다.

**그래서 두 축의 능력 집합이 서로소(disjoint)다.** 이게 §2.3 의 합성 규칙을 안전하게 만드는
전제다.

### 2.3 능력 네임스페이스 — 어느 축이 무엇을 주나

| 능력 | 프로젝트 역할이 준다 | 조직 역할이 준다 |
| --- | --- | --- |
| 프로젝트 **내용** 읽기 (티켓·활동·채팅·플로우) | ✅ `member`+ | ❌ **절대 아니다** |
| 프로젝트 **원장 내용** 읽기 (누가 무엇을 했나) | ✅ `owner`/`admin` = team, `member` = self | ❌ |
| 프로젝트 **집계** (그 프로젝트의 비용·사용량) | ✅ `owner`/`admin` | ❌ |
| 코드 write · merge | ✅ `roleCanMerge` | ❌ |
| 멤버 관리 (프로젝트) | ✅ `owner`/`admin` | ❌ |
| **조직 설정** (이름·도메인) | ❌ | ✅ `org_admin`+ |
| **조직 멤버 관리** | ❌ | ✅ `org_admin`+ |
| **조직 청구·좌석** | ❌ | ✅ `org_owner` |
| **조직 전체 집계** (전 프로젝트 비용 합) | ❌ | ✅ `org_admin`+ — §3 의 게이트를 탄다 |
| **조직에 어떤 프로젝트가 있는지 목록** | ❌ | ✅ `org_admin`+ (이름·비용까지. **내용은 아니다**) |

★마지막 행이 미묘하고 중요하다. 조직 관리자는 **프로젝트가 존재한다는 것과 그것이 얼마를
썼는지**는 본다(그들이 낸다). **그 안에서 무슨 일이 있었는지**는 프로젝트 역할이 있어야 본다.
"청구서에는 항목이 보이지만 항목의 내용은 안 보인다" — 이게 우리가 파는 선이다.

### 2.4 ★합성 규칙 — 합집합. 한 방향으로만

> **유효 능력 = (프로젝트 역할이 주는 능력) ∪ (조직 역할이 주는 능력)**
>
> **교집합·최솟값·덮어쓰기를 쓰지 않는다.** 어느 축도 다른 축이 이미 준 것을 **뺏지 않는다.**

두 축의 능력 집합이 서로소이므로(§2.3), 합집합은 실제로는 단순한 병치다. 그래도 **합집합이라고
못박아 두는 것**이 중요한 이유:

- **교집합을 쓰면** 프로젝트 owner 인데 org_member 라는 이유로 자기 프로젝트를 못 보는 락아웃이
  난다. 조직 축을 켜는 날 기존 사용자 전원이 여기 걸린다.
- **덮어쓰기(조직이 이긴다)를 쓰면** 방향이 양쪽으로 열린다. org_admin 이 프로젝트 viewer 를
  이겨서 넓게 보는 건 의도지만, 같은 규칙이 **org_member 가 프로젝트 owner 를 이겨 좁게** 만드는
  경로도 연다. 그게 권한 상승의 거울상 — 락아웃 — 이고, 락아웃은 조용해서 더 늦게 발견된다.

★티켓의 지적("이기는 방향이 한쪽으로만")이 정확하다. 합집합은 **방향이 하나뿐인 유일한
연산자**다. 그래서 "조직 역할이 이긴다" 라고 쓰지 않고 **"합집합"** 이라고 쓴다.

### 2.5 반례 전수 — 이 표가 구현의 테스트 케이스다

| # | 조직 역할 | 프로젝트 역할 | 프로젝트 내용 | 그 프로젝트 집계 | 조직 전체 집계 | 조직 설정 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `org_admin` | `viewer` | **viewer 만큼**(읽기) | ❌ | ✅ | ✅ |
| 2 | `org_admin` | 없음 | ❌ | ❌ (이름·비용은 §2.3 마지막 행) | ✅ | ✅ |
| 3 | `org_member` | `owner` | ✅ 전부 | ✅ | ❌ **§3 게이트** | ❌ |
| 4 | `org_owner` | `owner` | ✅ | ✅ | ✅ | ✅ |
| 5 | `org_member` | 없음 | ❌ | ❌ | ❌ | ❌ — 조직 안에 있지만 **볼 것이 없다** |
| 6 | 없음(외부) | `member` | ✅ | ❌ | ❌ | ❌ — ★대행사 케이스(#1204 §6-5) |
| 7 | `org_admin` | `owner` (**다른 조직**의 프로젝트) | ✅ | ✅ | 자기 조직 것만 | 자기 조직 것만 |

★**1번이 티켓이 물은 것이다.** 답: 프로젝트 내용은 **viewer 만큼만** 본다. 조직 역할이 프로젝트
내용 능력을 아예 담고 있지 않으므로(§2.3) 합집합에 더해질 것이 없다. 그리고 이건 "조직 역할이
졌다" 가 아니다 — 조직 역할은 **다른 것을 이겼다**(조직 전체 집계·설정). 두 축은 경쟁하지 않는다.

★**6번이 우리가 놓치기 쉬운 것이다.** 외부 대행사 직원이 고객사 프로젝트의 멤버일 수 있다.
그는 조직 멤버가 아니므로 조직 화면에 접근할 수 없지만, **프로젝트 내용은 본다.** 이게 맞다 —
그가 그 프로젝트에서 일하기 때문이다. 조직 관리자는 이 사람이 조직 멤버 목록에 없다는 이유로
"외부인이 우리 데이터를 본다" 고 놀랄 수 있으므로, **조직 멤버 화면에 "프로젝트 멤버이지만 조직
멤버가 아닌 사람" 을 별도 목록으로 보여준다.** 숨기지 않는다.

### 2.6 조직 역할은 프로젝트 역할을 **자동 생성하지 않는다**

#1202 §4.2 가 남긴 미결 질문 — *"org 가입 시 어느 프로젝트에 자동 참여하나"* 에 대한 답:

> **어느 것에도 자동 참여하지 않는다.**

근거는 #1204 §3 의 논리를 그대로 한 칸 옮긴 것이다. 자동 참여는 자동 가입의 다른 이름이고,
같은 결과(모르는 사람이 남의 프로젝트 원장을 본다)를 낳는다. 도메인이 소속을 증명하지 않는
것처럼, **조직 멤버십도 "이 프로젝트에 참여한다" 를 증명하지 않는다.**

**대신 UX 는 한 번으로 만든다** — 데이터는 둘, 동작은 하나:

```
초대 발송 화면(한 폼)
   조직 역할:   [org_member ▾]      → orgMembers 초대 문서
   프로젝트:    [☑ 프로젝트A(admin) ☐ 프로젝트B]  → invitations/{projectId}_{email} 문서 N개
                                       ↑ 초대자가 admin 인 프로젝트만 목록에 뜬다

수락(한 번)  →  서버 콜러블이 두 종류를 원자적으로 처리
```

★목록에 **초대자가 관리하지 않는 프로젝트가 뜨면 안 된다** — 그 순간 초대 화면이 조직 전체
프로젝트 목록의 열람 창구가 된다. `intersectProjectScope` 와 같은 규율이다.

## 3. ★집계 뺄셈 — 이 기획이 가장 쉽게 새는 곳

### 3.1 우리는 이미 한 층 아래에서 이 판정을 했다

새 규칙이 아니다. 프로젝트 축에서 이미 판정하고 문장까지 써 두었다:

```
v3/functions/src/teamUsage.ts (머리 주석 4번)
  "★일반 멤버는 자기 것만 본다. 팀 총계도 못 본다 — 2인 팀에서
     팀_총계 − 내_사용량 = 상대방 사용량
   이라 총계를 여는 순간 약속이 산술로 깨진다(차분 공격).
   그리고 지금 유일한 다중 멤버 프로젝트가 정확히 2인이다."

v3/functions/src/teamUsage.ts:280  MEMBER_SELF_ONLY_NOTE
  "멤버는 자기 사용량만 봅니다. 팀 합계도 보이지 않습니다 — 2인 팀에서는
   '팀 합계 − 내 사용량' 이 곧 상대방의 사용량이 되기 때문입니다."
```

★**이 문서는 그 규칙을 한 층 위로 올린다.** 아래층에서 `멤버 : 팀` 이었던 관계가 위층에서는
`팀장 : 조직` 이 된다. 완전히 같은 산수다.

### 3.2 조직 축에서의 같은 공격

```
조직 = { 팀A, 팀B }
팀장A 는 팀A 만 본다.   팀A = 1,240 USD
화면 어딘가에 조직 합계가 있다.  조직 = 3,100 USD
        ⇒ 팀B = 3,100 − 1,240 = 1,860 USD      ← 완전 노출. 한 번의 뺄셈
```

팀이 셋이면 나머지 둘의 합이 나온다. 그리고 **한 팀이 조직에 추가된 시점의 차분**을 보면 신규
팀의 값이 단독으로 나온다(§3.5). 즉 팀이 늘어난다고 안전해지지 않는다.

### 3.3 ★불변식 — 이 문서 전체에서 한 문장을 고른다면

> **총계는 그 총계를 이루는 항목을 전부 볼 수 있는 사람에게만 보인다.**
>
> 형식화: 어떤 집계값 `f(S)` 를 사용자 `u` 에게 보이려면 `S ⊆ visible(u)` 여야 한다.
> `S ⊄ visible(u)` 이면 **그 값은 봉투에 실리지 않는다.**

이 불변식이 좋은 이유는 **기계가 검사할 수 있다**는 것이다. 서버가 집계를 만들 때 스코프 집합
`S` 와 사용자 가시 집합 `visible(u)` 을 이미 둘 다 들고 있다(`intersectProjectScope` 가 정확히
그 계산이다). 부분집합 판정 한 줄이면 된다.

**따름정리:** `f` 가 무엇이든 상관없다 — 합계든 평균이든 순위든. `S` 만 본다.
그래서 §3.4 의 census 를 빠짐없이 만들 필요가 있다.

### 3.4 파생값 전수 — "총계" 는 합계만이 아니다

★이게 실무에서 실제로 새는 지점이다. 합계는 눈에 띄어서 막는데, **합계의 변형**은 무심코
지나간다. 전수:

| # | 화면 요소 | 왜 뺄셈이 되나 | 판정 |
| --- | --- | --- | --- |
| 1 | 조직 **합계** 카드 | 직접 | ❌ 스코프 밖이면 안 실린다 |
| 2 | **share / 비율** (`ByMemberRow.share`) | `내_값 ÷ share = 총계` — **총계와 동치다** | ❌ 분모가 스코프 밖이면 |
| 3 | **평균** | `평균 × N = 총계` (N 은 보통 화면에 있다) | ❌ |
| 4 | **순위 / "N위"** | 순위 자체가 남의 값과의 비교 결과 | ❌ |
| 5 | **백분위 / "상위 25%"** | 순위의 연속판 | ❌ |
| 6 | **팀 개수 N** | 4·5 의 분모. 그리고 조직 규모 자체가 영업 정보다 | ❌ 스코프 밖 개수는 안 준다 |
| 7 | **정렬 순서** (내 팀이 3번째로 그려짐) | 앞에 두 팀이 있다는 것과 그들이 나보다 크다는 부등식 | ❌ 스코프 밖 행은 **행 자체가 없다** |
| 8 | 차트의 **조직 평균선 / 벤치마크선** | 3과 같다. 시각적이라 더 놓치기 쉽다 | ❌ |
| 9 | **스택 차트의 전체 높이** | 스택 높이 = 총계. 내 조각을 빼면 나머지 | ❌ |
| 10 | **Y축 자동 스케일 최댓값** | 최댓값이 남의 팀 값이면 그 값이 축 눈금에 인쇄된다 | ★❌ 축은 **내 스코프 기준**으로 잡는다 |
| 11 | **필터·자동완성 드롭다운**의 팀 이름 | 존재 노출 | ❌ |
| 12 | **"전체" 토글** | 눌렀을 때 무엇이 나오나가 전부다 | ❌ 스코프 밖이면 토글 자체를 안 그린다 |
| 13 | **CSV / 감사 반출물** | 화면보다 반출물이 더 새기 쉽다 | ❌ 같은 게이트를 탄다 |
| 14 | **에러·빈 상태 문구** ("12개 중 1개만 조회됨") | 12 가 새는 값 | ❌ §4.3 |
| 15 | **캐시 키·ETag** | 스코프가 다른데 키가 같으면 남의 응답이 온다 | ★❌ 캐시 키에 스코프 해시 필수 |

★**10번과 15번이 이 표에서 가장 잘 잊히는 둘이다.** 10번은 차트 라이브러리가 자동으로 하는
일이라 코드에 안 보인다(#1206 이 차트 라이브러리 도입을 검토 중이니 **거기에 이 제약을
전달해야 한다**). 15번은 `teamUsage` 봉투에 이미 `cache` 필드가 있어 실재하는 위험이다.

### 3.5 시간 차분 — 창을 옮겨가며 빼는 공격

정적 게이트를 통과해도 **여러 조회의 차분**이 남는다:

```
팀장A 가 조직 합계를 볼 수 있다고 하자(가정).
  1~30일 합계 − 1~29일 합계 = 30일 하루치 조직 지출
  그 하루에 팀B 만 일했다면 = 팀B 의 그날 지출 (단독 노출)
  팀이 하나 새로 추가된 날 앞뒤 차분 = 신규 팀 값 (단독 노출)
```

★그래서 **"팀이 k개 이상이면 총계를 허용" 같은 k-익명 규칙이 여기서는 안 먹힌다.** 이유가
일반적인 k-익명 비판과 다르다:

> **집합이 시간에 따라 변한다.** k-익명은 정적 집합을 전제하는데, 우리 팀 집합은 프로젝트가
> 생기고 사라지면서 계속 변한다. **집합이 변하는 순간의 차분이 그 변화분을 단독으로 드러낸다.**
> k 를 아무리 크게 잡아도 이 경로는 안 막힌다.

그리고 현실적으로 우리 고객사의 팀 수는 2~5개다. k=5 를 걸면 거의 모든 고객에게 총계가 안 보이고,
k=2 를 걸면 뺄셈이 그대로 성립한다. **먹히는 k 가 존재하지 않는다.**

### 3.6 ★판정 — 팀장에게 조직 전체 합계를 보이나

> **기본값: 보이지 않는다.** 조직 전체 집계는 `org_admin` / `org_owner` 전용이다.
> 그들은 §2.3 에 따라 **모든 프로젝트의 집계를 전수로 보므로**, §3.3 의 불변식을 만족한다.

`org_member` 인 팀장은 자기 스코프 합계만 본다 — 그리고 그 합계는 **자기 프로젝트들의 합**이라
같은 불변식을 만족한다. 개인 조직에서는 스코프 = 자기 자신이라 규칙이 자연히 접힌다(총계 =
self 값).

**화면이 말하는 것:** 조직 전체 칸을 `0` 이나 빈칸으로 그리지 않는다. §4 의 `restricted` 로
그리고, 문장은 기존 `TEAM_SCOPE_DENIED_NOTE` 규약을 조직 축으로 옮긴 한 줄을 쓴다 —
**"조직 전체 사용량은 조직 관리자만 볼 수 있습니다."** 프로젝트가 몇 개인지, 다른 팀이
있는지는 말하지 않는다.

### 3.7 켜고 싶으면 — 대칭 공개 스위치

기업 고객이 "우리는 서로 다 보게 하고 싶다" 고 요구할 수 있다. 그건 정당한 요구고, 우리가
막을 이유가 없다. 다만 **여는 방식이 중요하다**:

> **총계를 열려면 분해를 열어야 한다. 총계만 여는 스위치는 만들지 않는다.**

```
Organization.aggregateDisclosure: "scoped" | "org_wide"     기본 "scoped"

"scoped"   조직 관리자만 전체를 본다. 팀장은 자기 스코프만            ← 기본값
"org_wide" 조직 멤버 전원이 모든 프로젝트의 집계를 전수로 본다
             ⇒ 총계도 보인다. 뺄셈으로 얻을 것이 남아 있지 않으므로
```

**"총계만 보여주고 분해는 감추는" 중간 단계를 두지 않는다.** 그 중간 단계가 정확히 뺄셈이
성립하는 상태이고, 그런 스위치가 존재하면 언젠가 누가 켠다 — *"자리가 있으면 언젠가 누가
채운다"*(`teamAudit.ts` 규약).

부대 조건 셋:

1. **`org_owner` 만 바꾼다.** 청구 주체가 정보 공개 범위를 정한다
2. **변경 이력은 추가 전용**이다 — `OrgNameHistoryEntry` 와 같은 패턴. *언제* 열렸는지가 감사 대상
3. **켜진 사실을 조직 멤버 전원이 본다.** 조용히 켜지지 않는다. 조직 설정 화면 최상단 배너

★3번을 빼면 안 된다. 사람이 "내 사용량이 누구에게 보이는가" 를 모르는 상태를 만들면, 그게
#1202 §4.3-3 이 말한 **감시 도구**다. 스위치를 만드는 것과 몰래 켜는 것은 다른 일이다.

### 3.8 ★그래도 못 막는 것 — 정직하게 적는다

이 설계는 **뺄셈을 막지, 추론을 막지 않는다.**

| 남는 경로 | 왜 못 막나 | 완화 |
| --- | --- | --- |
| 청구서 총액 | 조직 관리자가 팀장에게 슬랙으로 알려준다 | 제품 밖. 막을 수 없고 막을 일도 아니다 |
| 좌석 수 · 조직 멤버 목록 | 조직 관리자가 멤버 관리 화면에서 본다 | 그건 그의 권한이다 |
| 팀장이 여러 팀의 관리자인 경우 | 그의 스코프가 원래 넓다 | 정상 동작 |
| 자기 팀 값의 **자기 자신** 추론 | 1인 팀이면 팀 합계 = 본인 | 정상 — 자기 것이다 |

★적어 두는 이유: 이 문서를 읽은 사람이 "그럼 아무도 남의 팀 숫자를 못 아는군" 이라고 읽으면
**틀린 안심**이 된다. 우리가 보증하는 것은 *"우리 화면이 그 값을 계산해 주지 않는다"* 이지
*"그 값을 아무도 못 안다"* 가 아니다.

### 3.9 그리고 한 줄 — 이 화면은 근무 평가 자료가 아니다

`TELEMETRY_OPT_OUT_NOTE` 가 이미 화면에 이 문장을 싣고 있다:

```
"★이 순위는 근무 평가 자료가 아닙니다."
```

조직 축으로 올라가면 이 문장이 **더** 필요하다. 프로젝트 축에서는 몇 명이었지만 조직 축에서는
회사 전체가 한 표에 들어오기 때문이다. **팀 단위 순위표를 기본 화면에 두지 않는다** — 정렬은
사용자가 요청할 때만.

## 4. ★부재의 여섯 가지 뜻 — `0` 을 그리지 마라

### 4.1 우리는 이미 이 부류를 다섯 번 밟았다

티켓의 지적이 맞다. 세어 보면 다섯이다 — 전부 같은 실수의 다른 얼굴이고, 전부 **문장으로
수리돼 코드에 남아 있다**:

| # | 무엇을 `0` 으로 그릴 뻔했나 | 수리된 자리 |
| --- | --- | --- |
| 1 | 오케스트레이터 지출 | `OrchestratorAxisState = "not_collected" \| "collecting"` — ★`0` 은 상태가 아니다 |
| 2 | 적재 전 파이프라인 | `TeamUsageState` 5값 중 `not_provisioned`. `empty` 로 접으면 3분법이 2분법으로 무너진다 |
| 3 | 텔레메트리 끈 멤버 | `TELEMETRY_OPT_OUT_NOTE` — *"0 은 '안 썼다' 가 아니라 '안 보냈다' 일 수 있습니다"* |
| 4 | 기록 여부 미확인 멤버 | `ByMemberRow.hasRows: boolean \| null` + `MEMBER_ROWS_UNKNOWN_NOTE` — ★`false` 는 0 이 아니다 |
| 5 | 프로젝트 귀속 불명 행 | `UNATTRIBUTED_ROWS_NOTE` — *"건수만 밝히고 금액은 세지 않습니다"* |

여섯 번째가 **권한으로 가려진 값**이고, **그 자리는 아직 타입에 없다.**

### 4.2 오늘의 `UsageCell` 에는 여섯 번째가 없다

```ts
// marblo-web/src/app/[locale]/team/teamUsageContract.ts
export type UsageCell =
  | { kind: "measured";     costUsd: number; tokens: number }
  | { kind: "partial";      costUsd: number; tokens: number; coveredFrom: string }
  | { kind: "notCollected"; reasonCode; reason; legacySegment }
  | { kind: "pending";      since: string | null }
  | { kind: "unwired" };
//  ← 권한으로 가려진 값을 담을 종류가 없다
```

★**타입에 자리가 없으면 값은 `0` 이나 `undefined` 로 접힌다.** 그 파일의 머리 주석이 정확히 그
위험을 경고한다 — *"`Number(undefined)` 로 접으면 **0 이 된다.** 빈칸도 0 도 이 화면에서는
거짓말"*. 조직 축을 여는 순간 이 구멍으로 값이 흐른다.

**제안 — 여섯 번째 종류:**

```ts
  | {
      kind: "restricted";
      /** 무엇이 있어야 보이나. ★"왜 없는지" 가 아니라 "무엇이 필요한지" 를 말한다 */
      requires: "org_admin" | "project_admin";
      reasonCode: ReasonCode | null;
      reason: string | null;
    }
```

`requires` 를 넣는 이유: 사용자가 **다음에 할 일**을 알아야 한다. "권한이 없습니다" 는 막다른
길이고, "조직 관리자에게 요청하세요" 는 길이다. 그리고 이 값은 **역할 이름만 담지 조직·프로젝트
식별자를 담지 않는다** — 담으면 존재가 샌다.

### 4.3 ★두 가지 거절 모양 — 생략(omit) 과 가림(restricted)

여기가 이 절의 진짜 내용이다. **`restricted` 를 아무 데나 쓰면 그 자체가 새는 채널이 된다.**

```
남의 팀 행을 표에 넣고 값만 "권한 없음" 으로 가리면
  → 그 팀이 존재한다는 것이 샌다
  → 행 개수를 세면 조직의 팀 수가 샌다 (§3.4-6)
  → 정렬 위치를 보면 크기 부등식이 샌다 (§3.4-7)
```

| 상황 | 존재가 이미 알려졌나 | 모양 | 예 |
| --- | --- | --- | --- |
| 내 스코프 안의 축인데 권한이 모자람 | ✅ (화면에 그 칸이 있다는 걸 안다) | **`restricted`** | 조직 전체 합계 칸 · 조직 청구 탭 |
| 스코프 밖 항목 | ❌ | **omit — 행 자체를 안 보낸다** | 남의 팀 행 · 남의 조직 |
| 내 조직 안이지만 내가 멤버가 아닌 프로젝트 (org_admin 시점) | ✅ (조직 관리자는 프로젝트 목록을 본다, §2.3) | **행은 있고 내용 칸만 `restricted`** | 프로젝트 목록의 '원장 보기' |

**판정 규칙 한 줄:**

> 그 항목의 **존재를 이미 알 권한이 있으면** `restricted`, **존재 자체가 스코프 밖이면** omit.

★**omit 할 때 개수를 말하지 않는다.** 그리고 이게 함정인데 — 우리에겐 개수를 말하는 문구가
**이미 있다**:

```
teamUsage.ts:253  PROJECTS_TRUNCATED_NOTE
  "프로젝트가 많아 일부만 집계했습니다 — 아래 숫자는 전체 프로젝트의 합이 아닙니다."
  + capProjectScope() 가 omitted 개수를 돌려준다
```

이 문구는 **안전하다** — 잘린 것이 전부 *내 스코프 안*이기 때문이다(상한 25개 절단). 반면
**권한 절단은 개수를 말하면 안 된다.** 두 절단이 같은 화면에 나타나므로, 문구를 재사용하고
싶은 유혹이 생긴다.

> ★**성능 절단과 권한 절단을 같은 문구·같은 필드로 합치지 마라.** 앞엣것은 개수를 밝히는 것이
> 정직이고, 뒤엣것은 개수를 밝히는 것이 유출이다. 봉투 필드도 갈라 둔다:
> `coverage.omittedForLimit: number` (밝힌다) vs 권한 절단은 **필드 자체가 없다**.

### 4.4 문장 규약 — 새 낱말을 만들지 않는다

기존 note 상수의 어투를 그대로 잇는다. 신규 3개면 충분하다:

| 코드 | 문장 | 어디 |
| --- | --- | --- |
| `org_scope_denied` | "조직 전체 사용량은 조직 관리자만 볼 수 있습니다." | 조직 합계 칸 (`TEAM_SCOPE_DENIED_NOTE` 의 조직판) |
| `org_content_denied` | "이 프로젝트의 내용은 프로젝트 멤버만 볼 수 있습니다 — 조직 관리자 권한으로는 열리지 않습니다." | 프로젝트 목록의 내용 칸 |
| `org_membership_revoked` | "이 조직에 대한 접근이 해지되었습니다." | §5.13 |

★두 번째 문장이 중요하다. 조직 관리자가 **자기 권한으로 열리지 않는다는 사실 자체**를 알아야
한다 — 안 그러면 "버그인가?" 로 읽고 지원 티켓이 온다. 이건 제약이 아니라 **우리가 파는
성질**이므로 화면이 그렇게 말해야 한다.

### 4.5 타입으로 막고, 문장으로 막는다 — 둘 다

`MEMBER_ROWS_UNKNOWN_NOTE` 주석이 이 규약을 이미 써 두었다:

> *"타입이 접기를 막고, 문장이 오독을 막는다."*

같은 두 겹을 조직 축에도 적용한다:

- **타입**: `restricted` 종류를 두어 프론트가 숫자로 접을 수 없게 한다
- **문장**: 서버가 `reason` 산문을 같이 보낸다. 화면이 해석을 지어내지 않는다
- **테스트**: 봉투 JSON 에 **금지 키가 존재하지 않는다**를 단위테스트로 고정
  (#1204 `buildJoinRequestReceipt` 테스트와 같은 방식)

## 5. 로그인 플로우 — 상태 전수

### 5.1 ★먼저: "조직 없음" 은 존재하지 않는다

```
v3/functions/src/orgIdentity.ts
  personalOrgId(uid) = "personal_" + uid        ← uid 에서 결정적 파생. 백필 불필요
  defaultOrgIdForUser(uid)                      ← ★이메일을 인자로 받지 않는다
```

**로그인에 성공한 모든 사용자는 최소 하나의 조직(개인)을 갖는다.** 백필도 필요 없다 — 값이
파생이라 과거 사용자에게도 같은 값이 나온다.

★그래서 다음 화면들을 **만들지 않는다**: "조직 없음" 빈 상태 · "조직을 만드세요" 온보딩 강제 ·
"조직에 초대받으세요" 안내. 이런 화면은 존재할 수 없는 상태를 그리므로, 만들면 **도달 불가능한
코드**가 되고 도달 불가능한 코드는 검증되지 않은 채 언젠가 도달한다.

### 5.2 상태 전수 — 15개

### 5.3 초대 — 룰이 이미 정해 놓은 것

새로 설계할 것이 거의 없다. **초대의 뼈대는 `firestore.rules` 에 이미 못박혀 있다:**

```
firestore.rules:133  hasValidPendingInvite(projectId)
   invitations/{projectId + '_' + request.auth.token.email.lower()}
   ∧ inv.status == 'pending'
   ∧ request.time < inv.expiresAt

firestore.rules:147  isInvitedSelfJoin(projectId)
   affectedKeys().hasOnly(['members','updatedAt'])      // 다른 필드 위조 차단
   ∧ 결과 members ⊆ 기존 ∪ {본인}                        // 타인 추가 차단
   ∧ 결과 members ⊇ 기존                                  // 기존 멤버 제거 차단
   ∧ 본인 uid ∈ 결과
   → arrayUnion 재시도가 no-op 으로 통과해 **멱등 수락**이 성립한다
```

★**수락은 멱등이다.** 네트워크가 끊겨 사용자가 링크를 두 번 눌러도 안전하다. 화면은 이걸 믿고
재시도 버튼을 그냥 두면 된다 — 별도 잠금이 필요 없다.

**조직 초대도 같은 규약을 쓴다:** `orgMembers` 초대 문서 id = `{orgId}_{email.lower()}`.
#1204 가 이미 *"기존 프로젝트 초대 규약을 그대로 확장"* 이라고 정해 두었다. 새 규약을 만들지
않는다.

### 5.4 ★이메일 불일치 화면은 우리가 고른 것이 아니라 룰의 결과다

```
firestore.rules:702  match /invitations/{invitationId} {
  allow read: if isAuthenticated()
    && (isProjectMember(resource.data.projectId)
        || resource.data.invitedEmail == request.auth.token.email);
```

다른 계정으로 로그인한 사용자는 **초대 문서를 읽을 수조차 없다.** 따라서 화면은:

- ❌ "이 초대는 `j***@hypemarc.com` 으로 발송되었습니다" — **쓸 수 없다.** 값이 없다
- ❌ "당신은 초대받지 않았습니다" — 링크 소지자에게 프로젝트 존재를 확인해 주는 문장
- ✅ **"이 계정으로는 이 초대를 열 수 없습니다. 초대 메일을 받은 계정으로 로그인해 주세요."**
  \+ [다른 계정으로 로그인]

★이건 제약이 아니라 **좋은 소식**이다. 화면 설계자가 실수로 이메일을 노출할 방법이 없다 —
데이터가 애초에 안 온다. `resolveUsageScope` 주석의 규율(*"존재 여부를 말하지 않는다"*)이
초대 축에서는 **룰 수준에서** 강제돼 있다.

### 5.5 만료·취소·오타를 한 화면으로 접는다

7·8번을 **같은 문구**로 접는 이유:

- 만료: 문서를 읽을 수 있다(이메일 일치) → 만료를 알 수 있다
- 취소: 문서가 삭제됐다 → 이메일 일치 확인 자체가 불가능
- 오타: 애초에 그런 문서가 없다 → 취소와 구별 불가

**취소와 오타를 서버가 구별할 수 없으므로**, 만료만 따로 문구를 주면 *"만료됨"* 과
*"유효하지 않음"* 의 차이가 **초대가 실재했는지**를 알려주는 신호가 된다. 링크를 주운 사람에게
"이 프로젝트에 이 이메일이 초대된 적 있다" 를 확인해 주는 셈이다.

> **접는 문구:** "이 초대는 더 이상 사용할 수 없습니다. 초대해 주신 분께 다시 요청해 주세요."

★단 **본인이 확실한 경우**(이메일 일치 + 문서 읽힘 + 만료)에는 만료 시각을 보여줘도 안전하다.
그 사람은 이미 초대받은 사람이다. 즉 **구별할 수 있을 때만 구별한다.**

`expiresAt` 이 지난 문서는 룰이 `'expired'` 전이를 허용하므로(`firestore.rules:718`), 화면이
그 전이를 쳐서 목록을 정리한다.

### 5.6 퇴사 — 룰이 T+0 에 막는다. 화면은 `0` 이 아니라 **해지**로 그린다

이미 회귀 테스트가 있다:

```
v3/firestore.rules.test.ts:937
  "★ 탈퇴 차단: members 에서 빠지는 즉시 프로젝트 문서를 못 읽는다 (T+0)"
```

**행 격리는 이미 지켜진다.** 남는 문제는 화면이다 — 읽기가 `permission-denied` 로 떨어질 때
프론트가 그걸 **빈 데이터로 접으면 `0` 이 된다.** 정확히 §4 의 실수다.

> **규칙:** `permission-denied` 는 데이터 부재가 아니다. `restricted` 로 접는다.
> 그리고 **현재 보고 있던 화면에서 조용히 값만 비우지 않는다** — 접근이 해지되었다고 말한다.

### 5.7 ★조직 역할을 **커스텀 클레임에 넣지 않는다**

이 절에서 가장 되돌리기 어려운 결정이다.

```
firestore.rules:61  isPlatformAdmin()
  request.auth.token.admin == true || request.auth.token.role == 'admin' || …
```

우리는 **운영자 축에서 이미 커스텀 클레임을 쓴다.** 조직 역할도 클레임에 넣고 싶은 유혹이
크다 — 룰에서 `get()` 을 안 해도 되니 읽기 비용이 준다. **하지 않는다:**

| 이유 | 결과 |
| --- | --- |
| Firebase ID 토큰은 **최대 1시간 캐시**된다 | 멤버십을 해지해도 **최대 1시간 동안 유효**하다 |
| 강제 갱신은 클라이언트가 협조해야 성립한다 | 악의적 클라이언트는 협조하지 않는다 |
| 퇴사·계약해지가 정확히 이 창에 몰린다 | ★**해지가 즉시여야 하는 유일한 축**이 여기다 |

운영자 축은 우리 내부라 1시간 지연을 감수할 수 있다. **고객 조직 역할은 아니다.** 문서 기반
판정(`orgMembers/{orgId}_{uid}`)은 **다음 요청에 즉시 반영**된다 — `firestore.rules.test.ts:937`
이 프로젝트 축에서 증명한 T+0 성질을 조직 축에서도 얻는다.

★비용 반론(룰에서 `get()` 한 번 더): #1202 §4.2 가 이미 셈했듯 룰 `get()` 은 읽기 1회다.
**해지 지연 1시간과 읽기 1회를 맞바꾸지 않는다.**

### 5.8 조직 착지 규칙 (11번)

```
1) 마지막으로 본 조직 (localStorage)  — 단 여전히 멤버인지 서버가 확인한다
2) 없으면: 비개인 조직이 정확히 하나면 그것
3) 여럿이면: 조직 선택 화면 (개인 조직도 목록에 포함)
4) 비개인 조직이 없으면: 개인 조직
```

★1번에 "서버가 확인한다" 를 붙이는 이유: localStorage 는 사용자가 고칠 수 있다. 임의 `orgId` 를
넣어도 서버가 멤버십을 확인하므로 아무 일도 일어나지 않아야 하고, 그때 **"그 조직은 없습니다"
가 아니라 "볼 수 없습니다"** 도 아닌, 그냥 **기본 조직으로 조용히 착지**한다 — 존재 여부에 답하지
않는 가장 단순한 방법이다.

★**자동으로 회사 조직에 떨어뜨리지 않는다**(2번에 "정확히 하나" 조건). 조직이 둘 이상이면
사람이 고른다. 대행사 직원이 고객 A 화면을 열어 둔 채 고객 B 와 회의하는 사고를 막는다.

### 5.9 만들지 않는 화면 — 명시

| 만들지 않는다 | 왜 |
| --- | --- |
| "조직 없음" 빈 상태 | §5.1 — 도달 불가능 |
| "조직을 만드세요" 강제 온보딩 | 개인 조직이 이미 있다. 팀 요금제 결제 시에만 조직명을 묻는다(#1204 §9-1) |
| "당신은 초대받지 않았습니다" | 존재 노출 (§5.4) |
| 조직 전체 프로젝트 개수를 보여주는 빈 상태 | §3.4-6 |
| 도메인이 같다고 조직을 제안하는 화면 | ★#1204 §3 — 자동 가입 없음. 제안조차 하지 않는다 |

## 6. 룰 위에 얹는 법 — 화면에서 가리는 건 권한이 아니다

### 6.1 ★콜러블은 룰 밖이다 — 여기가 진짜 경계다

행 격리는 룰에 있고, 그건 지켜진다. **그런데 이 화면의 숫자는 룰을 타지 않는다.**

```
v3/functions/src/index.ts:14224  resolveTeamProjectRole()
  주석: "★docId ↔ 본문 결속 확인. 룰(…)이 같은 규약을 강제하지만
         Admin SDK 는 룰을 안 타므로 여기서 다시 본다."
         ↑ 원문의 룰 행번호는 낡았다(지금은 memberRoleDocIdMatches, :762). 주석의 요지는 유효하다.
```

집계는 BigQuery 와 Admin SDK 로 만들어진다 — **룰이 그 경로를 보호하지 않는다.** 즉:

> **룰은 "행" 을 지키고, 콜러블은 "집계" 를 지킨다. 집계의 안전은 전적으로 콜러블이 자기 손으로
> 도출한 스코프에 달려 있다.**

그래서 티켓의 지시("룰을 우회하지 말고 그 위에 얹어라")를 이 문서는 이렇게 구현한다:
**콜러블의 스코프 판정이 룰의 판정과 같음을 기계가 증명하게 한다**(§6.3).

### 6.2 ★판정: 조직 축은 룰의 read 게이트를 **넓히지 않는다**

#1202 §4.2 가 org 축의 가장 비싼 칸으로 지목한 것:

> *"`isProjectMember` 를 `isProjectMember ∪ isOrgMember` 로 넓힘. ★넓히는 순간 **12개 컬렉션의
> read 게이트가 동시에 바뀐다.** 잘못 넓히면 크로스테넌트, 좁히면 기존 사용자 락아웃"*

**이 문서는 그 칸을 열지 않는다.** 근거는 §2.3 이다:

> 조직 역할은 **프로젝트 내용 권한을 아예 포함하지 않는다.**
> 포함하지 않으므로, 그 12개 컬렉션의 게이트를 넓힐 이유가 **없다.**

두 결정이 맞물린다. §2.3 이 감시선을 지키기 위한 제품 결정이었는데, **그 결정이 #1202 가 센
가장 비싼 엔지니어링 비용을 통째로 지운다.** 조직 관리자에게 필요한 것은 행이 아니라 집계이고,
집계는 콜러블이 준다.

**그래서 룰에 추가되는 것은 신규 컬렉션 6개뿐이다:**

```
organizations/{orgId}          read: isOrgMember(orgId)              write: ✗ 서버 전용
orgMembers/{orgId}_{uid}       read: 본인 문서 || isOrgAdmin(orgId)   write: ✗ 서버 전용
orgProjectBindings/{id}        read: isOrgMember(orgId)              write: ✗ 서버 전용
orgDomainBindings/{id}         read: isOrgAdmin(orgId)               write: ✗ 서버 전용
orgNameHistory/{id}            read: isOrgMember(orgId)              write: ✗ 서버 전용 (추가 전용)
orgJoinRequests/{id}           read: ✗ 아무도 (★요청자에게도)         write: ✗ 서버 전용
```

★**클라이언트 write 를 전부 닫는 이유**는 `memberRoles` 가 밟은 사고 때문이다:

```
firestore.rules:762 주석
  "이전 룰은 '본문 projectId 의 admin 이면 아무 docId 로나 생성'을 허용했다
   → A 프로젝트 admin 이 docId='B_자기uid' 로 위조 문서를 만들어 B 의 admin 권한을 얻는
     크로스프로젝트 권한상승 구멍"
```

**`orgMembers` 는 정확히 같은 `{orgId}_{uid}` 결정적 id 규약을 쓴다.** 같은 함정이 그대로 있다.
docId 결속 룰을 다시 쓰는 대신 **클라 write 를 아예 닫으면 그 함정이 존재하지 않는다.** 조직
멤버 변경은 빈도가 낮아(초대·승인·해지) 콜러블 왕복 비용이 문제되지 않는다.

★`orgJoinRequests` 를 **요청자에게도 닫는** 이유: #1204 §7.2 — 응답은 조직 존재와 무관하게 항상
같은 모양이어야 한다. 요청 문서를 읽게 하면 `orgId` 가 그대로 보인다.

### 6.3 판정을 하나로 모은다 + 동치성 테스트

§2.1 의 census 대로 판정이 이미 다섯 곳에 복제돼 있다. 여섯 번째 축을 얹기 전에:

```
v3/functions/src/orgAccess.ts        ★신규. 순수 함수. Firebase 무의존
  composeAccess({ orgRole, projectRole }) → EffectiveAccess     // §2.4 합집합
  canSeeAggregate({ scopeSet, visibleSet }) → boolean           // §3.3 불변식
  denialShape({ existenceKnown }) → "omit" | "restricted"       // §4.3
```

그리고 **동치성을 기계가 지킨다**:

| 테스트 | 무엇을 고정하나 | 어떻게 |
| --- | --- | --- |
| `orgAccess.test.ts` | §2.5 반례 7개 전수 | `node --test` (orgIdentity.test.ts 와 같은 방식) |
| 봉투 키 부재 테스트 | `org_member` 응답 JSON 에 `orgTotal` 키가 **존재하지 않는다** | #1204 `buildJoinRequestReceipt` 테스트와 같은 패턴 |
| 룰 동치 테스트 | 룰의 `isOrgAdmin` 판정 == `composeAccess` 판정 | `npm run test:rules` (에뮬레이터, 이미 있다) |
| ★**회귀 테스트** | 기존 12개 컬렉션 게이트가 **바뀌지 않았다** | 조직 PR 마다 돈다 (§6.2 가 지켜지는지 감시) |

★마지막 줄이 이 표의 핵심이다. §6.2 의 판정("룰을 넓히지 않는다")은 **문서에 적어 두면 언젠가
새는 약속**이고, 회귀 테스트로 적어 두면 지켜지는 약속이다.

### 6.4 봉투에서 뺀다 — 화면에서 숨기지 않는다

> **응답 JSON 에 실리지 않은 값만 안 샌 값이다.**

`display: none` · 조건부 렌더 · 라우트 가드는 전부 **네트워크 탭에 값이 남는다.** 이 프로젝트는
이 규율을 이미 두 곳에서 지킨다 — `teamUsage` 가 멤버 스코프에서 팀 행을 **서버에서** 거르고
(*"그래서 **서버가** 거른다"*, `teamAudit.ts:76` 주석), `buildJoinRequestReceipt` 가 내부 판정을
응답에 싣지 않는 것을 단위테스트로 고정한다.

조직 축 체크리스트:

- [ ] `org_member` 봉투에 조직 합계·평균·순위·팀 수 키가 **없다**
- [ ] 스코프 밖 프로젝트 행이 **배열에 없다** (`restricted` 로도 없다 — §4.3)
- [ ] 캐시 키에 스코프 해시가 들어간다 (§3.4-15)
- [ ] CSV·감사 반출물이 같은 봉투를 쓴다 (§3.4-13)
- [ ] 차트 Y축 스케일이 **봉투에 실린 값만** 보고 잡힌다 (§3.4-10 → #1206 에 전달)

## 9. 열린 질문 (사장님·오케 판단)

1. **§3.6 — 팀장에게 조직 전체 합계를 끝까지 안 보이나.** 내 권고는 "기본 비노출 + §3.7 대칭
   스위치" 다. 반대 의견(팀장은 자기 팀이 조직에서 차지하는 비중을 알아야 예산을 짠다)도
   성립한다. 다만 그 요구는 **비중(=share)** 이고, share 는 §3.4-2 대로 총계와 동치다.
   중간이 없다 — 열거나 닫거나다.
2. **§2.5-6 — 외부 대행사 표시.** "프로젝트 멤버이지만 조직 멤버가 아닌 사람" 을 조직 관리자에게
   보여주자는 것이 내 권고인데, 그 목록은 **대행사 입장에서 자기 직원 명단이 고객사에 보이는
   것**이다. 계약상 문제가 없는지는 제품·법무 판단이다.
3. **§3.7 공개 스위치를 v1 에 넣나.** 내 권고는 **넣지 않는다** — 고객이 실제로 요구할 때 짓는다.
   #1204 §11-2 가 합류 요청에 대해 낸 것과 같은 판단이다.
4. **§5.7 — 조직 역할 클레임 금지.** 룰 `get()` 비용을 감수하는 결정이다. 조직 규모가 커져 읽기
   비용이 실제로 문제되면 재검토 대상이지만, 그때도 답은 클레임이 아니라 **캐시 계층**이어야
   한다(해지 즉시성을 잃지 않는 방향).
5. **§4.2 `restricted.requires` 의 값 집합.** 지금은 `org_admin | project_admin` 둘로 잡았다.
   "요청 보내기" 버튼을 여기에 달지(합류 요청 창구, #1204 §7)는 3번과 묶인 결정이다.
6. **§2.1 드리프트 — `TeamProjectRole` 에 `viewer` 가 없다.** 오늘 viewer 는 `member` 로 접혀
   자기 감사 피드를 본다. 맞는 동작이라고 판단했지만 **아무도 결정한 적이 없는 값**이다.
   조직 축 PR 과 별개로 별건 티켓이 받아야 한다.
