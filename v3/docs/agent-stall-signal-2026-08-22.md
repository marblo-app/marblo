> 2026-08-22. P0 프로덕션 배포를 물고 있던 devops 에이전트가 **80분간 activity 0건**으로
> 멈췄다. 프로세스는 살아 있었고 보드는 `working` 이었다. 재배정(`dispatch_task`)은
> _"Agent already bound to task with live activity evidence"_ 로 **같은 정지 에이전트에게
> 되돌아갔다.** 사람이 다른 걸 물어서 발견했다.

| 층                                                   | 종전                                                                       | 구멍                                                                                                                                                       |
| ---------------------------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 워치독 `agent-watchdog.ts`                           | 생존 시계 = `max(보드활동, PTY work-output)`                               | 스피너(`esc to interrupt`)를 그리는 CLI 는 툴 호출이 행(hang)해도 **영원히 살아있음**. W7 도 "입력 프롬프트에 서 있음" 만 잡고 "바쁘게 멈춤" 은 못 잡는다. |
| dispatch `bridge-server.ts isLiveTaskAgentCandidate` | `projection.lastAgentId === agentId && summary 가 'dispatched to' 가 아님` | **시각을 안 본다.** 활동 1건이라도 남긴 에이전트는 영구히 "live".                                                                                          |

## 2. 설계 — 사장님 말씀 그대로

> "일정시간 멈추면 워치독이 체크가 되서 일중인지 죽은건지 판단이 되도록해서 **오케가 판단 후** 새로 스폰하거나"

- **신호 축은 보드 활동 하나다.** `projection.lastActivityAt` 이 임계를 넘으면 "조용하다". PTY 는
  설명(busy / parked / awaiting-input / silent)으로만 붙여 오케가 "열심히 일하는 중" 과 "서 있는 중" 을
  가르게 한다.
- **워치독은 행동하지 않는다.** 신호 경로 4개뿐: ① 오케 PTY 주입 ② 티켓 타임라인 activity
  (`🔧 [Watchdog quiet] …`) ③ 텔레메트리 `agent:quiet_signal` (★구체 모델 동반) ④ 에이전트의
  `stallSignal` 마커 → `get_agents` 에 `⚠ quiet 80m on task …`, `cleanup_agents` suspects 줄.
  nudge/kill/respawn 은 이 신호에서 단 하나도 파생되지 않는다(테스트로 고정: 대조군과 행동 횟수 동일).
- **재알림은 30분마다.** 한 번 올렸으면 오케가 "기다린다" 고 결정했을 수 있다.
- **dispatch 는 신호가 울리는 그 시점부터 우회한다.** 바운드 에이전트의 마지막 보드 활동이 같은 임계를
  넘으면 되돌려보내지 않고 새로 배정한다. 구 에이전트는 **바인딩만 해제, 죽이지 않는다.** 결과에
  `bypassedStaleAgents` 로 실어 오케가 `kill_agent` 를 결정한다(같은 워크트리 두 워커 위험을 결과 문구로 경고).
- **정체 레인도 같은 상수를 쓴다.** STALE 카드는 `StateBlock(failed)` 배너 — 경과 분 + 사유 + "다시 시도".
  "멈춘 것 같다" 는 빨간 점이 아니라 다음 행동이 붙는 상태다.

## 3. 임계 — 하나가 아니라 둘, 근거

`electron/agent-stall-policy.ts` (env 덮어쓰기 가능):

| 티어   | 우선순위 | 임계     | 근거                                                                                                                                                        |
| ------ | -------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| urgent | P4–P5    | **20분** | 살아서 일하는 워커의 실측 보고 간격 2~11분(2026-07-18)의 약 2배. 오늘 P0 배포는 5~10분짜리 일이 80분 조용했다. 신호 비용은 오케 메시지 1건이라 오탐이 싸다. |
| normal | P1–P3    | **45분** | 버그 재현·대규모 리팩터·벤치는 30분을 넘길 수 있다. 정체 레인이 쓰던 30분보다 보수적으로 잡아 "정상 장시간 작업을 오판하지 않는다" 쪽에 기울였다.           |
| repeat | —        | 30분     | 오케의 "기다린다" 결정을 존중.                                                                                                                              |

우선순위로 가른 이유: 티켓 종류(role)보다 우선순위가 "얼마나 빨리 알아야 하나" 를 직접 말한다. P0 배포는
P5 로 올라오고, 긴 실험은 대개 P2–P3 이다. role 별 분기는 필요해지면 같은 모듈에 한 줄이다.

## 4. 오판 방지 근거 (정상 장시간 작업)

1. **자동 조치가 없다.** 최악의 오탐은 오케에게 메시지 1건. 사람 신뢰를 잃는 "멀쩡한 작업 킬" 은 구조적으로 불가.
2. **임계 ≥ 실측 최대 보고 간격 × 2**, 일반 티어는 45분.
3. **신호에 PTY 상태가 붙는다.** `busy`(출력 중)면 오케는 기다리고, `parked`/`awaiting-input` 이면 바로 행동한다.
4. **워커가 add_activity 한 줄이면 신호가 걷힌다**(quiet-cleared). 역할 스킬이 이미 요구하는 행동이다.
5. dispatch 우회도 **죽이지 않는다.** 우회는 오케가 재배정을 _이미 결정한_ 경로에서만 일어난다.

## 5. 범위 밖 / 판단

  않는다)을 지킨다. 대신 suspects 줄에 `⚠ quiet …m — stall suspect, orchestrator decides` 로 **표시**한다.

  agent-reap.ts 의 게이트를 건드리지 않는다.
- 기존 사다리의 born-dead 단(첫 관측 후 3분 무활동 → respawn)은 손대지 않았다(W3 가드가 운영에서 막는다).
  다만 `hasLiveWorkerForTask` 에 한 가지 예외를 추가했다: **이 태스크에서 풀려난 선임**(currentTaskId null ·
  lastTaskId = task)이 워크트리에 앉아 있다는 이유로 후임의 복구를 영원히 stand-down 시키지 않는다.

## 7. 보강 — "스폰 직후 무산출" 을 못 잡던 구멍 (2026-08-23, 티켓 O1OQKukSSCmMaJCoGHGP)

> CEO리뷰 티켓(P5)에 스폰한 MiniMax-M3 에이전트가 activity 0건으로 멈췄다. `get_agents` 는 죽일
> 때까지 `[working]` 이었고, 워치독은 20분 임계 전이라 아무 신호도 안 올렸다. §3의 두 임계는
> "11분마다 보고하다 멈춘 에이전트" 를 재는 자였지, "한 번도 보고한 적 없는 에이전트" 를 재는
> 자가 아니었다.

`agent-stall-policy.ts` 의 `sweepQuiet`(agent-watchdog.ts)가 이제 **세 축**을 순서대로 본다 —
한 판정 구간에는 정확히 하나의 축만 신호한다(같은 "아무것도 안 왔다" 는 사실을 두 번 알리지 않는다):

| 축                  | 조건                                                                                                    | 임계                                                                           | 근거                                                                                                                                                              |
| ------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `exit`              | 이 프로세스가 로컬에서 `stopped`/`error` 로 확정(agent-manager `status`/`lastExitCode`/`terminalSince`) | **즉시**(threshold 0)                                                          | 죽음은 추론이 아니라 이미 아는 사실이다. 20/45분을 더 기다릴 이유가 없다.                                                                                         |
| `first-activity`    | `lastActivityAtMs === null`(활동 기록이 아예 없음), `activeSinceMs` 기준                                | **5분**(`STALL_FIRST_ACTIVITY_QUIET_MS`, env `MARBLO_STALL_FIRST_ACTIVITY_MS`) | 실측 첫 보고는 반복 보고 간격(2~11분)보다도 빨라야 정상. 사다리의 born-dead 단(3분)보다 신호는 살짝 여유를 둬 사다리가 이미 손댔는지 오케가 함께 볼 수 있게 했다. |
| `board-quiet`(기존) | 한동안 보고하다 멈춤(`lastActivityAtMs` 는 있으나 오래됨)                                               | 20/45분(§3, 불변)                                                              | §3 그대로.                                                                                                                                                        |

`StallSignal` 에 `axis`(위 세 값) · `boardIdleMs`(축과 무관하게 항상 채우는 "마지막 실보고 이후
경과") · `exitCode` 가 추가됐다. 오케 PTY 메시지·텔레메트리(`agent:quiet_signal` metadata)가 축별로
문구를 가른다 — "죽음" 과 "침묵" 이 같은 얼굴로 오지 않는다.

**판단 보류(④, 모델 실적 n 기반 임계 단축) — 반영하지 않음.** MiniMax-M3 는 이 보드 실적 n=1 이었지만,
n 을 임계에 반영하려면 그 값을 세는 카운터가 프로세스를 넘어 영속해야 한다 — 이 모듈/워치독은 순수
로컬 메모리라 앱을 재시작할 때마다 모든 모델이 n=0 으로 리셋되고, 그러면 매 부팅마다 이미 검증된
모델조차 첫 실행에서 짧은 임계로 오탐을 낸다("오탐이 미탐보다 나쁘다" 불변식 정면 위반). 진짜 실적은
이미 텔레메트리(`agent:quiet_signal`, 이제 axis/exitCode 까지 포함)에 모델별로 쌓이고 있고, 그게
세션 하나의 기억보다 정확하다. 대신 후속 티켓(`DQYoyas3ESx33zXJOCOa`, 능동 프로브)에게 넘긴다 — "안
써본 모델이라 불안하다" 는 걱정은 짧은 임계로 _기다리는_ 것보다 _찔러보는_ 쪽이 낫다. 자세한 근거는
`agent-stall-policy.ts` 하단 주석("판단 보류") 참조.
