## 0. 한 줄 결론

> **1층 wow의 주어는 "자율(autonomy)"이다 — "임무 하나만 주면 오케가 알아서 조율한다(give it a mission, it orchestrates itself)".** 유저가 DAG를 그리는 게 아니라, 임무 1개를 던지면 엔진이 분해→의존성→복잡도별 스폰→선행완료 후 후행스폰→★와치독 자가치유→머지판단→유저확인→머지의 8단계를 **스스로** 돈다(§1 상세). 이 **자율 + 자가치유**가 Orca(수동 worktree·수동 재기동) 대비 결정적 체감차다. **4축은 이 자율 엔진 해자를 서로 다른 방향으로 "더 깊게 파는" 삽이다:** (a)(b)는 엔진의 **폭과 품질**(어떤 모델이든 복잡도에 맞춰 자동 배분 = 벤더 중립을 Orca와 대등하게 맞추되 "자동 조율"로 이김), (c)는 엔진이 굴러갈수록 쌓이는 **데이터 해자**(라우팅 SLM = 쓸수록 똑똑해지는 오케 브레인), (d)는 엔진 위에 얹는 **생태계/네트워크 해자**(하네스 스토어 = Orca의 OSS 커뮤니티에 정면 대응하는 우리만의 마켓플레이스). 서사의 주어는 여전히 **자율 orchestration 엔진**이고, audit는 수익화 술어, 4축은 그 엔진을 시간이 갈수록 **복제 불가능**으로 만드는 **누적 자산 레이어**다.

핵심 통찰: 확정 서사의 최대 약점은 "특허 + 시스템 엔지니어링 깊이"라는 해자가 **정적(static)**이라는 점이다 — 충분한 자원을 가진 경쟁자(Orca 238 컨트리뷰터)는 시간이 지나면 따라올 수 있다. **4축 중 (c)와 (d)는 해자를 정적에서 동적(누적)으로 바꾼다.** 라우팅 데이터와 스토어 생태계는 **시간과 사용량에 비례해 벌어지는** 격차라서, 경쟁자가 오늘 우리 코드를 전부 복제해도 우리의 6개월 뒤 데이터·생태계는 복제할 수 없다. 이것이 이 로드맵의 전략적 무게중심이다.

## 1. 확정 서사 요약 (발전의 출발점)

재검증 문서가 확정한 3단 계층 — 이 로드맵은 이 계층을 **훼손하지 않고 그 위에 4축을 얹는다.**

```
1층 (HOOK · 복제불가 엔진 · 특허):   "임무 하나만 주면 오케가 알아서 조율한다." (자율 + 자가치유)
        ↓ (엔진이 낳은 궤적을)
2층 (WEDGE · 수익화 아티팩트):        "그 병렬 작업을 감사가능한 merge 결정으로." (Free→Team 과금 게이트)
        ↓ (둘을 묶어)
3층 (CATEGORY):                       "Marblo = AI-native 팀의 control plane."
```

### ★1층 wow = "자율(autonomy)", "유저가 DAG를 그린다"가 아니다 (사장님 프레이밍 교정 2026-07-18)

> **서사의 주어 = "Give it a mission, it orchestrates itself."** 유저는 DAG를 그리지 않는다. **임무 1개**만 던지면 오케 엔진이 **8단계를 스스로** 돈다:

```
① 임무 → 티켓으로 자동 분해            (task-decomposer)
② 티켓 간 의존성 자동 판정             (dag-generator / 청구항 4 게이트)
③ 복잡도별 모델 분배 스폰              (Codex=난이도↑ / Claude 등 — 축 a·b)
④ 선행 완료 후에만 후행 자동 스폰      (dag-resolver / 의존성 자동 해소)
⑤ ★와치독: 멈춘 에이전트 감지 → 오케 알림 → 다른 에이전트 재스폰  (자가치유)
⑥ 산출물 머지 가능 여부 판단           (audit/safe-merge = 2층 웨지)
⑦ 유저 확인(승인 게이트)              (사람 개입은 "결정"에만)
⑧ 머지                                (merge SHA로 provenance 종결)
```

- **이 8단계 자율 루프 = 1층 데모 스토리.** DAG를 유저가 손으로 그리는 그림(Orca식 수동 worktree)은 **서사에서 금지.** 우리 그림은 "임무를 던지고 지켜보는" 것.
- **결정적 체감차 vs Orca:** Orca는 사람이 worktree를 손으로 만들고·에이전트를 손으로 붙이고·멈추면 손으로 되살린다(**수동 오케스트레이션**). Marblo는 ①~⑧을 **엔진이 자율로** 돈다. 특히 **⑤ 와치독 자가치유**(멈춘 에이전트 감지→재스폰)는 Orca에 대응물이 없는, "손 떼고 맡긴다"의 핵심 증거 — 이것이 재검증 문서가 말한 "상위 링"의 실체다.
- **자가치유의 코드 실재:** 와치독 복구·재스폰 계보는 메모리에 다수(`watchdog_recovery_check_marblo_managed_worktree`, `watchdog_stale_status_and_reuse_over_pending`, `reuse_agent`/`spawn_agent` MCP). ⑤는 vaporware가 아니라 **이미 도는 루프의 서사화** — 단, 1층 서사가 여기 걸리므로 **와치독 신뢰성 = 서사 신뢰성**(제1원칙에 직결).
- **인간의 자리:** 자율이라고 사람이 사라지는 게 아니라 **사람은 ⑦(승인)과 임무 정의에만** 개입 — "결정"에 집중하고 "노동"은 위임. 이 프레이밍이 2층 audit(누가 승인했나)와 자연스럽게 연결된다.

- **엔진이 primary 해자**(특허 청구항 4/5/8/9/10 + submit-retry·fd누수·레이스가드 등 시스템 깊이).
- **audit가 secondary 수익화 웨지**(GitHub+Slack로 부분 복제되지만, 엔진 위의 audit는 복제 안 됨).
- 재검증 문서 §4.4 리스크 4의 경고를 이 로드맵의 **제1원칙**으로 승격: _"엔진을 primary로 내세우는 순간 PTY 유실·오케 먹통 회귀가 곧 핵심 서사의 반증이 된다."_ → **안정성이 곧 전략.** (메모리: injectMessage silent drop, onExit 레이스, MCP -32000 등 회귀 이력)

**4축이 이 계층의 어디에 붙는가 (한 장 지도):**

## 2. 새 비전 4축 — 해자 편입 포지셔닝 (개별)

### 축 (a) — 복잡도 기반 고성능 모델 스폰 (Codex 5.6 등)

**무엇:** 태스크 복잡도를 판정해 그에 맞는 모델 티어를 자동 스폰. 어려운 태스크에는 최상위 모델(Codex 5.6, Opus 4.8, Fable 5 등), 단순 태스크에는 경량/저가 모델.

**기존 토대(이미 있음):**

- `auto-mix.ts` — 복잡도 3티어(`simple|standard|complex`), **complex 한정** top-tier 자동 승급 + Codex 교차검증. simple/standard 는 절대 안 건드림(비용 방어).
- `dispatch-scoring.ts` — 매칭점수의 `w3 비용효율지표`가 모델 단가 버킷(`:147`)을 이미 인지. spawn model policy v2 + Fable5(메모리: `spawn_model_policy_v2`).

**해자 기여 = 벤더 중립 + 품질.** 두 가지를 동시에:

1. **품질 증폭:** "수십 개 에이전트를 스폰한다"(1층 hook)의 가치는 스폰된 에이전트가 **각자 제 몫을 할 때만** 산다. 복잡한 리팩터에 경량 모델을 붙이면 병렬성이 오히려 쓰레기를 양산한다. **복잡도↔티어 매칭은 "많이 스폰"을 "잘 스폰"으로 바꿔 엔진 가치를 증폭.**
2. **벤더 중립의 실체화:** "Codex 5.6이 나오면 자동으로 어려운 태스크에 쓴다"는 것은, 우리가 **특정 벤더에 묶이지 않고 그때그때 최고 모델을 흡수**한다는 뜻. 신모델 출시가 우리에겐 위협이 아니라 **자동 업그레이드**다.

**엔진 가치 증폭의 논리:** 오케 엔진의 청구항 9(매칭점수)는 이미 `역할×부하×비용`을 본다. (a)는 여기에 **복잡도 차원**을 정식 축으로 승격 — `매칭점수 += w4 × 복잡도-티어 적합도`. 이는 특허 청구항의 자연스러운 확장이자, "우리 엔진은 단순 라운드로빈이 아니라 태스크 난도를 읽는다"는 **엔진 지능의 증거**.

**서사 카피:** _"Hard task? Marblo spawns your top model. Trivial task? It saves your budget. Automatically."_

### 축 (b) — 플릿 확장: Grok · Hermes 등 최신 모델을 하네스탭 편입

**무엇:** 현 플릿(Claude/Codex/Gemini/Antigravity — 메모리 `marblo_v3_fleet_codex_naming`)에 Grok, Hermes 등 최신 모델을 하네스(harness) 어댑터로 추가. 사용자가 하네스탭에서 원하는 모델을 붙인다.

**해자 기여 = 플릿 폭(벤더 중립성).** Orca의 최대 GTM 자산 중 하나가 "any CLI agent, 30+ 에이전트 중립 지원"(GTM 문서 §1 축1). **(b)는 이 중립성을 Orca와 대등하게 맞추는 방어 축**이다. 단, 대칭이 아니다:

- **Orca:** 사용자가 에이전트를 고르고 worktree를 손으로 관리. 중립성 = "골라 쓰세요."
- **Marblo:** 사용자가 플릿을 넓게 붙여두면 **오케가 (a)의 복잡도↔티어 로직으로 자동 배분.** 중립성 = "다 붙여두면 알아서 씁니다."

즉 **(b)는 폭을 제공하고 (a)는 그 폭을 지능적으로 소비한다.** (b) 없이 (a)는 선택지가 좁고, (a) 없이 (b)는 그냥 모델 목록(Orca와 동급). **둘이 붙어야 "넓은 플릿을 자동 조율"이라는 Orca가 못 하는 그림**이 된다.

**리스크:** 플릿을 넓힐수록 하네스별 PTY submit-retry·SUBMIT_SIGNAL 정규식(각 CLI TUI마다 다름)·resume 계약(메모리 `codex_resume_contract_unknown_id_kills` — 모델별 resume 격리)이 늘어나 **안정성 표면이 넓어진다.** → 제1원칙(안정성=전략)에 직결. 신규 하네스는 반드시 라이브 submit/resume 왕복 검증을 게이트로.

**서사 카피:** _"Bring any model — Claude, Codex, Gemini, Grok, Hermes. Marblo routes each task to the right one."_

### 축 (c) — ★모델 라우팅 SLM (오케 브레인): 디스패치 데이터 축적 → 학습 = **데이터 해자**

**무엇:** 오케스트레이터의 라우팅 결정(어떤 태스크를 어떤 모델/에이전트에 배분했고, 그 결과가 좋았는지)을 데이터로 축적해, 소형 언어모델(SLM)을 학습시켜 **라우팅 자체를 지능화**. 지금은 `dispatch-scoring.ts`의 **정적 가중합(w1/w2/w3)**이 라우팅을 결정 — (c)는 이를 **데이터로 학습된 라우터**로 진화.

**해자 기여 = ★데이터 해자 (이 로드맵의 전략적 무게중심).**

- **왜 데이터 해자인가:** 매 디스패치가 `(태스크 특징, 선택된 모델, 결과 품질/비용/재작업 여부)` 튜플을 생산한다. 이 데이터는 **우리 엔진을 쓰는 사용자가 많을수록, 오래 쓸수록** 쌓인다. 경쟁자가 우리 라우팅 코드를 전부 복제해도, **우리가 축적한 수백만 디스패치의 결과 라벨은 복제할 수 없다.** 라우팅 SLM은 이 데이터로 학습돼 "이런 태스크엔 Codex가, 저런 태스크엔 Claude가 더 낫다"를 **경험적으로** 안다.
- **정적→동적 전환:** 축 (a)/(b)/기존 dispatch-scoring은 **규칙 기반**(사람이 가중치를 정함). (c)는 그 규칙을 **데이터가 대체**한다. 이 순간 해자가 "복제 어려운 코드"에서 "**복제 불가능한 누적 자산**"으로 질적 도약. 재검증 문서가 지적한 정적 해자의 한계(§4.4 리스크 3 "Orca가 238 컨트리뷰터로 따라올 수 있음")를 **정면으로 해소하는 축.**
- **선순환(플라이휠):** 더 나은 라우팅 → 더 나은 결과 → 더 많은 사용 → 더 많은 데이터 → 더 나은 라우팅. **이것이 4축 중 유일하게 "쓸수록 벌어지는" 축.**

**데이터 파이프라인 그라운딩:** 우리는 이미 텔레메트리 BQ 적재(메모리: 프로덕션 텔레메트리 ON, `telemetry_production_on_2026_07_17`)와 cost-tracker가 있다. **디스패치 결과 라벨링**(재작업률·리뷰 반려율·완료시간을 품질 프록시로)이 (c)의 학습 데이터 스키마의 시작점. 별도 대규모 인프라 없이 **기존 축적 위에 라벨 레이어만** 얹으면 데이터 수집이 시작된다.

**전제·주의:**

- **프라이버시 경계:** 라우팅 학습은 태스크 **메타특징**(길이/역할/의존성 깊이/도구 호출 수)으로 하고, 코드 원문·프롬프트를 학습 데이터로 빨아들이지 않는다(트러스트 패킷 T-5와 정합). 온프렘/셀프호스트 팀은 로컬 라우팅 or 옵트인.
- **콜드스타트:** 데이터 없을 땐 (c)가 정적 dispatch-scoring로 폴백. **(c)는 dispatch-scoring를 대체가 아니라 그 위에 학습층을 얹는 것** → 무데이터 구간에도 안전.
- **이것이 진짜 승부수:** 특허(정적)는 방어층이지만, 데이터 플라이휠(동적)은 **공격층**이다. 로드맵 중기의 핵심 투자.

**서사 카피(대외):** _"Marblo's router learns from every dispatch — the more your team ships, the smarter it routes."_ (내부 프레임: **데이터가 우리의 진짜 특허.**)

### 축 (d) — ★하네스 스토어: 오피셜 GitHub + 스킬/MCP 스토어 + 유저 업로드 = **생태계/네트워크 해자**

**무엇:** 오케가 스폰하는 에이전트의 **하네스(harness = 스킬 + MCP 서버 + 에이전트 설정 프로파일)**를 유통하는 마켓플레이스. 3계층: ①**오피셜 GitHub**(우리가 관리하는 검증된 하네스), ②**스킬/MCP 스토어**(큐레이션된 서드파티), ③**유저 업로드**(커뮤니티 기여).

**해자 기여 = ★생태계/네트워크 효과 (Orca OSS 커뮤니티에 정면 대응).**

- **Orca의 유일한 진짜 해자는 커뮤니티다.** GTM 문서가 반복 경고: 21.1k star, 238 컨트리뷰터, "changelog가 곧 기능 목록"인 OSS 플라이휠. star 수로는 못 이긴다. **(d)는 "star 경쟁"이 아니라 "다른 종류의 네트워크 효과"로 되받아친다.** Orca의 컨트리뷰터는 *Orca 코어*에 기여하지만, 우리 스토어의 기여자는 **우리 플랫폼 위에서 재사용되는 자산(스킬/MCP/하네스)**을 만든다 — VS Code 익스텐션 마켓이 에디터 코어 컨트리뷰터보다 강력한 락인인 것과 같은 구조.
- **네트워크 효과의 방향:** 하네스가 많아질수록 → 사용자에게 Marblo가 더 유용 → 사용자 늘수록 → 하네스 제작 유인 증가. **양면 시장(제작자↔사용자) 플라이휠.** 이건 코드 복제로 못 따라온다 — 마켓의 가치는 **콘텐츠 축적량**에 있지 마켓 코드에 있지 않다.
- **엔진과의 결합:** 하네스 스토어는 **오케 엔진이 있어야 의미가 있다.** 스킬/MCP/하네스는 "오케가 에이전트를 스폰할 때 입히는 옷". 즉 (d)는 **엔진(1층)을 플랫폼으로 확장**하는 축 — 엔진이 없으면 그냥 또 하나의 프롬프트 갤러리, 엔진 위에서는 "조율되는 에이전트에게 즉시 입혀지는 능력 마켓".
- **(b)/(c)와의 시너지:** 스토어가 넓어지면(플릿·하네스 폭↑ = b와 결) → 라우팅이 배분할 선택지↑ → 라우팅 데이터 다양성↑(= c의 학습 신호 풍부화). **(d)는 (b)(c)의 연료 공급원.**

**기존 자산 그라운딩:** 우리는 이미 marblo MCP 서버(32툴)와 `skills/` 디렉토리, `run_skill`/`get_agent_skill` MCP 툴이 있다. **하네스 스토어는 이 내부 스킬/MCP 체계를 외부 유통 가능한 형태로 개방**하는 것 — zero-to-one이 아니라 기존 내부 자산의 외부화.

**리스크(중대):**

- **공급망 보안(치명적):** 유저 업로드 하네스 = 스킬 supply-chain 공격면. 악성 MCP/스킬이 사용자 코드/토큰에 접근할 수 있음. **오피셜 검증 + 서명 + 권한 스코핑 + 스킬 스캐닝(cso 스킬의 skill supply-chain 스캔)** 없이는 열면 안 됨. → (d)는 반드시 **보안 게이트를 선결**로.
- **콜드스타트(양면 시장 공통):** 제작자도 사용자도 없는 초기. → **오피셜 GitHub(①)를 우리가 씨앗으로 채우고**, 파운더 베타 100인을 첫 제작자 커뮤니티로(GTM 문서 §축5 "파운더 100인 고밀도 커뮤니티"와 정합).

## 3. 로드맵 시퀀싱 (안정성·데모 먼저 → 스토어·라우팅SLM 데이터는 중기)

사장님 지시(안정성·데모 먼저, 스토어·라우팅SLM 데이터는 중기)를 3구간으로 구현. **GTM 문서의 T-1~T-11과 인터리브**(중복 티켓 신설 금지, 참조).

### Phase 0 (지금~단기, 0–6주) — 서사 토대 = 안정성 + 엔진 데모

> **원칙: 엔진을 primary로 내세우려면 엔진이 안 죽어야 한다. 4축을 얹기 전에 1층을 단단히.**

1. **[안정성 P0] 오케↔에이전트 통신 회귀 방어 하드닝.** injectMessage silent drop·onExit 레이스·MCP -32000·PTY fd누수 회귀 이력(메모리 다수)을 **라이브 왕복 테스트 스위트**로 고정. 재검증 문서 제1원칙의 직접 이행. → **NEW-1**
2. **[데모 P0] ★자율 오케 히어로 데모** — "임무 1개 던지면 오케가 알아서" 8단계 자율 루프(§1: 분해→의존성→복잡도별 스폰→후행 자동스폰→**⑤ 와치독이 멈춘 에이전트 감지→재스폰 자가치유**→머지판단→유저확인→머지)를 원테이크로 시연. **DAG를 유저가 그리는 장면 금지** — "던지고 지켜보는" 그림. GTM **T-1(REVIEW Cockpit)**과 짝. Orca(수동 worktree·수동 재기동)가 못 보여주는 그림. → **NEW-1b**
3. **[축 a 착수] 복잡도↔티어 매칭 정식화.** `auto-mix.ts`의 complex-한정 로직을 **dispatch-scoring에 `w4 복잡도적합도`로 승격**(3티어 전체 대상). Codex 5.6 등 신모델 티어 테이블 편입. → **NEW-2**

- **측정:** 오케 먹통/PTY 유실 회귀 0건(주간), 엔진 데모 영상, 복잡도-티어 배분 정확도.

### Phase 1 (단기~중기, 6–14주) — 엔진 폭 확장 + 데이터 수집 시작

> **원칙: (b)로 폭을 넓히고, 동시에 (c)의 데이터 라벨링을 "지금부터" 켠다 — 데이터는 빨리 켤수록 중기에 두꺼워진다.**

4. **[축 b] 플릿 확장 — Grok·Hermes 하네스 어댑터.** 각 하네스 라이브 submit/resume 왕복 검증 게이트 필수. → **NEW-3**
5. **[축 c 데이터 파이프라인 — ★중기 핵심의 선행투자]** 디스패치 결과 라벨링 스키마 + BQ 적재. `(태스크 메타특징, 선택 모델, 재작업률/반려율/완료시간)` 튜플 수집 시작. **학습은 나중, 수집은 지금.** 프라이버시 경계(메타특징만) 준수. → **NEW-4**
6. **[축 d 선결] 하네스 스토어 보안·패키징 스펙.** 서명·권한 스코핑·스킬 스캐닝 설계(cso). 오피셜 GitHub(①) 씨앗 하네스 정의. **스토어 열기 전 보안 먼저.** → **NEW-5**

### Phase 2 (중기, 14–24주) — 데이터 해자·생태계 해자 가동

> **원칙: 축적된 데이터로 (c) 학습을 켜고, 보안이 선 뒤 (d) 스토어를 연다. "쓸수록 벌어지는" 두 축을 이 구간에 점화.**

7. **[축 c 학습]** 수집 데이터로 라우팅 SLM v0 학습, dispatch-scoring 위 **학습층으로 배치**(무데이터/온프렘 폴백=정적). shadow 모드→정확도 검증 후 flip(텔레메트리 shadow-flip 패턴, 메모리 `evidence_enforce_flip_pending` 선례). → **NEW-6**
8. **[축 d 오픈]** 하네스 스토어 ①오피셜→②큐레이션→③유저업로드 순차 개방. 파운더 100인 첫 제작자. GTM **T-9(Orca 상호운용 브릿지)**와 결합(외부 ADE에서도 우리 하네스 접근 = 배포 무임승차). → **NEW-7**
9. **[통합 서사]** 랜딩 리론치에 4축 편입: "넓은 플릿(b)을 복잡도로 자동 배분(a)하고, 쓸수록 똑똑해지며(c), 능력을 마켓에서 입힌다(d) — 전부 하나의 오케 엔진 위에서." GTM T-3/T-7 런치와 동기화.

- **측정:** 라우팅 SLM vs 정적 A/B 품질·비용, 스토어 하네스 수/설치 수/제작자 수, Free→Team 전환(북극성 유지).

### 시퀀싱 근거 (왜 이 순서인가)

- **안정성·데모가 먼저인 이유:** 엔진이 primary 서사인데 엔진이 불안정하면 서사가 자기반박(재검증 제1원칙). 데모 없이 4축을 말하면 "vaporware".
- **(c) 데이터 수집을 Phase 1에 당기는 이유:** 데이터 해자는 **시간의 함수**다. 학습(Phase 2)은 미뤄도 **수집은 최대한 일찍** 켜야 중기에 학습할 데이터가 쌓인다. "스토어·라우팅SLM **데이터**는 중기"라는 지시를 "데이터 **학습·활용**은 중기, 데이터 **수집 파이프라인**은 선행"으로 해석.
- **(d) 스토어가 중기인 이유:** 양면 시장은 콜드스타트 + 공급망 보안이 선결이라 서두르면 위험(악성 하네스 1건이 트러스트 전체를 태움). 보안 스펙(Phase 1) 후 개방(Phase 2).
- **(a)(b)가 앞선 이유:** 엔진 폭·품질은 (c)의 데이터 다양성과 (d)의 스토어 가치의 **연료**. 폭이 좁으면 라우팅이 배울 것도, 스토어에 담을 것도 적다.

## 6. 최종 요약

- **★1층 wow = 자율(autonomy):** "Give it a mission, it orchestrates itself." 유저가 DAG를 그리는 게 아니라 임무 1개를 던지면 엔진이 8단계(분해·의존성·복잡도별 스폰·후행 자동스폰·**와치독 자가치유**·머지판단·유저확인·머지)를 스스로 돈다. 이 **자율 + 자가치유**가 Orca(수동 worktree·수동 재기동) 대비 결정적 체감차이자 1층 데모 스토리. **DAG 그리기 서사 금지.**
- **서사 발전 방향:** 확정 3단 계층(엔진→웨지→카테고리)을 훼손하지 않고, 4축을 **자율 엔진을 시간이 갈수록 복제 불가로 만드는 누적 자산 레이어**로 얹는다. 서사 주어는 여전히 자율 orchestration 엔진.
- **4축의 해자 편입:**
  - (a) 복잡도↔티어 = **벤더중립 + 품질**(엔진 배분 지능 증폭, 청구항 9 확장).
  - (b) 플릿 확장 = **폭**(Orca 중립성과 대등하되 우리는 자동 배분).
  - (c) 라우팅 SLM = **★데이터 해자**(쓸수록 벌어지는 동적 해자 — 정적 특허의 한계를 정면 해소).
  - (d) 하네스 스토어 = **★생태계/네트워크 해자**(Orca OSS 커뮤니티에 "다른 종류의 네트워크 효과"로 응수).
- **시퀀싱:** Phase 0 안정성·데모(제1원칙) → Phase 1 플릿 폭 + **데이터 수집 조기 점화** → Phase 2 라우팅SLM 학습 + 스토어 개방. "데이터·스토어는 중기"를 "**학습·개방은 중기, 수집·보안 선결은 선행**"으로 해석.
- **전략적 무게중심:** (c) 데이터 플라이휠 + (d) 생태계 = 재검증 문서가 남긴 **"정적 해자는 언젠가 복제된다"**는 유일한 약점을 메우는 두 동적 축. **특허는 방어층, 데이터·생태계는 공격층.**
- **제1원칙(불변):** 엔진이 primary 서사인 한, **안정성이 곧 전략.** 오케 통신 회귀는 신규 축보다 우선한다.
